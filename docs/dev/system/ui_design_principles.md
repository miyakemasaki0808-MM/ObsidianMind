## 1. 国際規約 — どの基準をどこへ当てるか

WCAG 2.1 AA を土台にする。**重要なのは「文字か記号か」で基準が変わること。**

| 対象 | 基準 | 根拠 | 例 |
|---|---:|---|---|
| 読む文字 | **4.5:1** | 1.4.3 コントラスト（最低限） | 本文・ラベル・見出し・ボタンのラベル |
| 大きい文字（18pt / Bold 14pt 以上） | 3:1 | 1.4.3 の大文字例外 | 画面見出し |
| **状態を示す記号** | **3:1** | **1.4.11 非テキストのコントラスト** | **バッジの ✓ / !・アイコン** |
| 操作要素の輪郭 | 3:1 | 1.4.11 | ボタンの塗り・入力枠 |
| 装飾のみ（情報を持たない） | 対象外 | 1.4.11 の除外 | 背景の飾り |
| **色で区別させるもの** | **色以外の手がかりを併記** | **1.4.1 色の使用** | **状態の色分け・分類の色帯・エラー表示** |

**1.4.1 は画像プレースホルダの表示で初めて必要になった。**
上の4行はすべて**コントラスト比**の話で、「色が唯一の手がかりになっていないか」は
別の基準である。比を満たしていても、**赤い枠だけで「失敗」を伝えていれば 1.4.1 に反する。**

適用の形は「色を使うな」ではなく**「色以外にもう1つ」**:

| 場面 | 色以外の手がかり |
|---|---|
| 画像が出せなかった | **理由の文** ＋ 枠 ＋ 記号（色は手がかりに留める） |
| 状態バッジ | 記号（✓ / !）そのもの |
| 分野の色帯（未実装の候補） | ラベルか位置。**色数を増やして識別させない** |

**判定は「その色を灰色にしても伝わるか」で行う。** 伝わらないなら手がかりが1つ足りない。

**「記号は3:1」を明示的に採る。** WCAG は実装（`Text()` で描いているか）ではなく**機能**で分類する。
バッジの中の ✓ は読む文字ではなく状態の指示なので 1.4.11 側であり、4.5:1 は要求されない。

**この線引きは、同じ塗りの上で前景が2つに割れることを意味する。**
`buttonSecondary`（緑）はボタンの塗りでもバッジの塗りでもあるが、
ボタンのラベルは 4.5:1（黒）、バッジの記号は 3:1（ライトは白）になる。
**非対称を消そうとすると、どちらかが不必要に制約される。**

**判定に迷ったら厳しい側（4.5:1）を採る。** 記号扱いにするのは、
「読んで意味を取る対象ではない」と言い切れるときだけにする。

### 適用しないと決めたもの

- **AAA（7:1）は目指さない。** AA を全面的に満たすことを完了条件とする
- **アプリはOSのダークモードに追従しない**（切り替えの主導権はオプション画面）
  → [AppTheme.kt](../../../app/src/main/java/com/example/newproject/ui/theme/AppTheme.kt)

## 2. このアプリの好み — やること

- **ステータスは「塗り＋白抜きの記号」で示す。** ライトでは Success も Error も同じ形にする
  （2026-08-02 まで Error が白・Success が黒で不揃いだった）
- **色相は動かさず、明度で調整する。** 見分けの根拠が色相の差しかない要素
  （関連ノート／AI推薦の見出しなど）では、色相を動かすと可読性と引き換えに意味が壊れる
  → [theme_and_ui_refactor](theme_and_ui_refactor.md) 判断2
- **明暗で解き方が反転してよい。** ライトで敷くものをダークで敷かない、
  ライトで白い記号をダークで黒くする、はいずれも正しい。**値をコピーしない**
- **足りているなら何も足さない。** ダークで輪郭線を置かないのは忘れているのではなく
  足りているからで、それをテストで示す

## 3. このアプリの好み — やらないこと（差し戻した実物）

**ここは実際に実装して差し戻したものの記録。** 同じ案を再提案しないために置いてある。

| やらないこと | 何を試したか | なぜダメだったか |
|---|---|---|
| **小さい部品に輪郭線を足す** | バッジに `LogoNavy` 1dp（2026-08-02） | 10dp程度の円に濃紺の環が乗ると、**汚れのように見える**。数値は3.15で通っていた |
| **小さい塗りの中に濃い記号を置く** | バッジの ✓ を黒に（2026-07-29〜08-02） | 面積の大半が黒く見えて重い。5.53で通っていたが好みに合わなかった |
| **グラデーションの上に暗幕を敷く** | 見出しに `LogoNavy` α=0.42（2026-07-30） | 帯として重く、角丸を付けるとカードにしか見えない → 白ヘイズへ |

**共通する構造:** どれも**大きい部品で成立した解き方を、小さい部品へそのまま移した**失敗である。
グラデーション上のボタンで輪郭線が成立するのは面積が大きいからで、
**面積が変われば同じ手は移らない。**

> **装飾を足す前に、その部品の面積を数える。** 輪郭・影・濃い記号は、
> 部品が小さいほど面積比で支配的になる。

## 4. 迷ったときの順序

1. **その部品は文字か記号か**を決める（→ §1 の表で基準が決まる）
2. **その色が実際に載る面をすべて数える。** パネルだけでなくナビ帯・グラデーション・
   半透明の下地まで。**代表値で測らない** → [theme_and_ui_refactor](theme_and_ui_refactor.md) 判断5・判断6
3. 基準を満たす候補が複数あるなら、**§3 に当たらないものを選ぶ**
4. **見た目に触るなら、実装前にモックか計算結果を出して合意する。**
   数値だけで進めると §3 の3件と同じ差し戻しになる

**§3 の表へ1行足す**こと。そうしないと同じ提案が戻ってくる。
