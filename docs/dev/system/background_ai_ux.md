## 1. 基本思想

オンデバイスの Gemini Nano は生成に数十秒かかることがあり、さらに `AiClient` の Mutex で直列化されているため順番待ちも起きる。

> **生成はAIの都合、読書はユーザーの都合。前者が後者をブロックしてはいけない。**

したがって**生成開始で待機画面へ遷移しない。** ノートタブへ戻して読書を継続させ、完了・エラーは後から知らせる。

## 2. 通知は3層

| 層 | 中身 |
|---|---|
| **Snackbar** | 開始「作成中…」／完了「保存しました＋見る」／失敗「作成できませんでした＋詳細」 |
| **AIタブのバッジ** | 未確認の重要度順に**1状態だけ**表示（エラー > 未確認完了 > 生成中）。タブの✨の意味は変えず、右上の小バッジのみで伝える |
| **AIタブ内ボタンのラベル多態** | 状態に応じて「作る／作成中…／✓開く／!エラーを確認／↻再試行」と役割が変わる |

**3層すべてが要るのは「投げっぱなしにできる」機能だけ**（→ §4）。

## 3. 状態設計と競合ガード

**未確認管理（`isViewed`）.** Success / Error に「結果はあるがユーザーがまだ見ていない」を持たせる。
通知とバッジは未確認のものだけを対象にし、結果を開いた時点で確認済みにする。結果自体は同じノート内では保持し続ける。

**競合ガード（`requestId` ＋ `isCurrent`）.** ノート切替後に旧ノートの結果が新しい画面へ混入するのを防ぐため、
要求ごとに `requestId` を採番し、suspend 地点の後で `isCurrent(requestId)` を確認してから状態を更新する。
**Jobキャンセルだけに頼らない** — キャンセルが届く前にすり抜ける完了通知（モデルDLコールバック等）があるため。

**例外方針.** `CancellationException` は握りつぶさず再throwする。
広い `catch (e: Exception)` でキャンセルをエラー表示へ変換すると、**ノート切替のたびに偽のエラーが出る。**

**Snackbar は「一度きりのイベント」、生成状態は「持続する状態」.** 性質が違うので同じ扱いにできない。
`remember { SnackbarHostState() }` は Activity 再生成で初期化され、状態から通知を導出する `LaunchedEffect` が
再実行されて**画面回転で同じ Snackbar が再表示される**。表示済みイベントキーを `rememberSaveable` に記録して抑止し、
状態が Idle へ戻ったらキーもリセットして同じノートの再生成では再び通知できるようにする。

- **割り切り: 未確認の Success も回転後は再表示しない**（バッジが未確認を伝え続けるため）
- イベントキーの組み立ては `toEventKey()`、バッジ優先順位は `resolveAiTabBadgeState` として**純関数へ切り出してある** —
  UI分岐は関数に切り出せばそのままテストになる

## 4. 通知層は「結果をどこへ置くか」に従属する

**これがこの文書の中心的な判断である。** 通知層の設計は「何を通知するか」ではなく**結果の置き場所**で決まる。

**3層通知が成立する条件は、ユーザーが生成を投げたあと別の場所へ行けること。**
見に行くまで気づけないからこそ Snackbar とバッジが要り、`isViewed` が意味を持つ。

**逆に、生成の起点と結果の閲覧が同じ画面で完結するなら未確認管理は要らない。**
ノートへのひとことがこの形で、`RemarkScreen`（専用ルート）を開いてそこで生成し、そこで読む。
投げて別の場所で待つ経路が無いので、完了✓・失敗! のバッジは対象ごと落ちた。

> **AIタブにあるのは入口のボタン1つだけである**（`RemarkPanel` — ラベルは `✨ ノートへのひとこと` /
> 生成中は `考えています…`）。**結果の本体はAIタブに出ない。**
> 旧版はここを「結果がAIタブのパネルへ直接出る」と書いていたが**実装と逆で、2026-08-11 に訂正した。**
> 未確認管理が消えた理由は「結果がAIタブへ出るから」ではなく「**起点と結果が同じ画面で閉じるから**」である。

**生成中のインジケータだけは残す。** 押してから読書へ戻る導線が実在し、Nano は1回数十秒かかる。
こちらは自動で消えるので確認管理を必要としない。

**したがって未確認管理（`markViewed()` ＋ Snackbar）を持つ機能はクイズ1つだけ。**
[architecture](architecture.md) の Controller 共通化の再検討条件は「3つ目が現れたとき」なので、**条件はさらに遠のいている。**

**副産物として、塗りバッジのコントラスト問題が消えた。** 下部ナビ帯（ライトはブランド色 Indigo）の上で
3:1 を取れなかったのは完了✓（1.61）と失敗!（1.04）の**塗り**で、その2つが無くなった。
残る生成中表示は線のインジケータなので同じ問題を持たない。
**輪郭線を足す・ナビ帯の色に触るといった、ブランド配色へ踏み込む案は不要。**

> **結果の置き場所を動かす変更は、必ずこの文書を見に来ること。** 置き場所が変わった時点で通知層の前提が崩れる。

## 5. Controller は共通化しない

Q&Aを `NoteViewModel` のベタ書きから `QuizController` へ切り出したとき、相似形のControllerを共通化するか判断を保留した。
**4度の検討を経て「共通化しない」で決着している。**

共通なのは `requestId` ガードの数行だけで、モデルDLポリシー（自動再開 vs 明示タップ）・通知の有無・状態数・責務の形がいずれも違う。
比較表と再検討の条件は [architecture](architecture.md)「Controller共通化はしない（決着済み）」が持つ。
