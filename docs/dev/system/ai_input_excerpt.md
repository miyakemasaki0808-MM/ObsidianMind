## 1. 背景 — 「後ろを全部捨てる」実装だった

本文は `PromptBuilder` 内の `String.take()` で先頭から固定長に切っていた。
切り方が問題だったのではなく、**捨てる場所が常に「後ろ」だった**ことが問題だった。

長いノートの後半には、**結論・検証結果・残課題・次にやること**が置かれる。つまり
**ノートの価値が集まっている場所が、構造的に毎回捨てられていた。**

これは「後半が少し欠ける」程度の劣化ではない。案を3つ検討して案2で解決し残課題を1つ残したノートは、
先頭1,200文字だけを見ると「解決策を検討中のノート」に見える。
**要約は精度が低かったのではなく、系統的に間違っていた。**

## 2. 判断1: 捨てる場所を「後ろ」から「真ん中」へ

| | 捨てるもの | 残るもの |
|---|---|---|
| 旧 | 後ろを全部 | 冒頭のみ |
| 新 | **真ん中だけ** | 骨格 ＋ 冒頭 ＋ 末尾 |

真ん中を捨てる代償は「捨てた部分に何があったか分からない」ことなので、**見出しの骨格で補う**（判断2）。

**冒頭と末尾は 60% / 40%。** 冒頭を厚くするのは、主題の宣言が読み取れないと末尾の結論も解釈できないため。
末尾を4割確保するのは、そこが最も価値が高いから。

## 3. 判断2: 見出しは削らず、骨格へ「昇格」させる

Markdown記法を削ってスリムにしたのではない。**`#` の行だけを全文から抜き出し、
`## Note outline` という専用枠へ並べ直す。** 本文側にも見出しはそのまま残るので**抜粋中に2回現れる。**

**この重複は意図的に許容する。** 骨格は「全体の地図」、本文は「実際の中身」で役割が違い、
地図から見出しを間引くほうが害が大きい。

見出しが予算に収まらない場合は**全体から均等選抜する**（先頭からN件ではない）。
最初と最後の見出しは必ず含め、飛ばした区間には `…` を置く。
**先頭からN件では「前半の目次」にしかならず、全体構造を伝えるという目的を果たさない。**

## 4. 判断3: 予算は変えず、配置だけ変える

既存の文字数上限は**1文字も変えない**。生成時間・Mutex直列化・出力256トークン上限へ
影響を与えないまま、品質だけを動かすため。

**予算調整を分離したのは、単独の数字を見て増減してはいけない領域だから。**
関連ノートの予算は、候補ブロック・指示文・タイトルと合わせた**完成プロンプト全体**で評価する必要がある。

## 5. 判断4: 単一の巨大ブロックは、捨てずに切る

段落・コードブロック・表・リストが1個で枠を超える場合、そのブロックを捨てるのではなく
**そのブロックだけを枠まで切る**。捨てる仕様にすると「末尾が巨大なコードブロック1つ」のノートで
末尾枠が空になり、判断1の目的そのものを失う。

**コードブロックを切ったときは閉じフェンスを復元する。** 未閉じフェンスはモデルの読解を確実に壊す。

## 6. 判断5: 正規化の副作用は「損失の種類」で引き受けるか決める

抜粋は表示用の Markdown パーサをそのまま流用する。専用パーサを起こさない代わり、
次の変換が**予算超過ノートにだけ**起きることを仕様として明記する。

| 変換 | 評価 |
|---|---|
| YAML frontmatter を除去する | **利得**。タグ・別名・プラグインのメタデータが予算を占領しなくなる |
| 段落内の改行を空白へ畳む | 実質無害 |
| 箇条書き記号 `-` / `*` / `+` を `-` へ統一する | 実質無害。記号の違いは意味を持たない |
| コードフェンスの言語名が落ちる | 軽い損失 |

**副作用を仕様として引き受けるかどうかは、損失の大小ではなく種類で決める。**
上表はいずれも「表記の揺れ」であって、書き手が込めた意味ではない。

**リストの番号と入れ子段数は保持する側へ変えた。** 全項目が `- ` へ潰れると、
番号自体に意味があるノート（手順書など）で順序がモデルへ届かない。
他の副作用が**冗長な情報を落とす**のに対し、これだけは**本文の意味を落として**いた。

**短いノート（予算内）はパースせず原文をそのまま渡す。**
同じノートでも長短で挙動が変わるが、「超過した入力だけを圧縮する」という仕様の当然の帰結として受け入れる。

## 7. 判断6: 抜粋であることをモデルへ明示する

区切りは `…（中略）…` のような記号ではなく、
`## Note outline` / `## Beginning excerpt` / `## Ending excerpt` / `(omitted)` という明示ラベルにする。
**小さいモデルほど、プロンプト要素間の境界が曖昧だと誤読する。**

注意書きの `A (omitted) marker denotes a skipped span **when present**` を条件付きにしてあるのは、
正規化だけで全ブロックが収まり `(omitted)` が出ないケースが実在するため。
**無条件に「省略箇所は (omitted) で示す」と言うと、モデルが存在しない省略を探しに行く。**

注意書きと本文をつなぐ改行までを `ABRIDGED_NOTICE_PREFIX` として描画と予算計算で共有し、
**AIへ渡る本文由来領域の全体が用途別上限を1文字も超えない**不変条件へ揃える。

## 8. 判断7: 解析はメインスレッドから外す

抜粋生成は最大1MBの本文をMarkdown解析する。実測でデスクトップJVMでも**1MBノートで約460ms**。
呼び出し元はいずれも `Dispatchers.Main.immediate` のスコープで、
特に関連ノートは**ノートを開いた瞬間に自動起動する**ため操作の引っ掛かりになる。

抜粋生成だけを `Dispatchers.Default` へ移す。各クラスは本番既定値が `Default` の
`excerptDispatcher` を持ち、JVMテストではテストスケジューラへ差し替える。

**従来の `take()` は先頭N文字のコピーで実質ゼロコストだったため、これは変更が持ち込んだ新しい負荷である。**
呼び出しが再びメインスレッドへ戻らないことは、**ソース走査テスト**（`NoteExcerptThreadingTest`）が
「`buildNoteExcerpt` を呼ぶ全箇所」を対象に固定する（Controller一覧ではない）。

## 10. 得られた知見

### 効いたのは「量」ではなく「配置」だった

実際にモデルへ渡る本文は**減っている**（要約なら1,200文字連続 → 冒頭406＋末尾272＝678文字）。
それでも出力が良くなるなら、結論は一つしかない。

**同じ予算なら、連続した先頭より、構造を伝える不連続な断片のほうが強い。**
オンデバイスの小さいモデルでは、**指示の精緻化より入力設計のほうが伸びしろが大きい**可能性がある。

**この結論は両方向から追認された。** 予算を 600→800 へ**増やしても体感は変わらなかった**。
減らしても増やしても品質が動かないので、動かしていたのは配置のほうだった。

### AI出力を別のAI入力へ流す箇所では、改善も劣化も乗算される

ひとことのプロンプトは本文だけでなく**AI要約と関連ノートも入力として受け取る**ので、
今回の変更で入力が3つとも同時に良くなった。逆に言えば**要約の品質はひとことの品質でもある。**
→ [lessons L5](../lessons.md#l5-ai出力を別のai入力へ流す箇所では改善も劣化も乗算される)

### 文字数の比率とトークンの比率は別物

注意書きは226文字で、**関連ノートの予算600に対して38%**を占めていた。
これは長く最優先の改善候補として積まれていたが、**実測すると44トークン＝完成プロンプトの1.7%**だった。

**桁が違う。** 注意書きが英語で本文と候補が日本語のため、文字数比がトークン比にならない。
しかも38%は**抜粋予算だけを分母**にした値で、**2つの誤差が同じ向きに効いて問題を実際より大きく見せていた。**
→ [lessons L22](../lessons/L22.md)・[L23](../lessons/L23.md)

## 11. 保証していないこと

- **品質改善は測定していない。** 上記の因果はコードから導いた説明であり、A/B比較は行っていない
- **予算は文字数で切っており、トークン数では切っていない。**
  測る手段（`PromptTokenBudgetTest`）は入ったが、それで予算の切り方が変わったわけではない。
  **§13 の完成プロンプト上限も同じく文字数**で、トークン上限に対する余裕は実機計測が答える
- **トークンの基準線は取り直し待ち。** 2026-08-22 に字下げの漏れ（§13）を直したので、
  **それ以前に採った計測値と直接は比べられない**（→ [device_validation](../../review/device_validation/ai_input_budget.md)）
- **予算内のノートは1文字も変わっていない。** 抜粋経路8本すべてを回帰テストで固定している。
  **短いノートで品質が変わったように見えるなら、それは Gemini Nano の出力揺らぎである**
- **Nanoが抜粋レイアウトをどう解釈するかは未検証。** `## Note outline` を要約対象と誤解して
  目次を返す、足場の文字列が出力へ漏れる、といった失敗は実機でしか確認できない

## 12. やらないこと

- ~~関連ノート専用の短縮注意書き~~ — **実測で落とした**（浮くのは44トークン未満で意味を持たない）
- ~~関連ノートの予算のさらなる引き上げ~~ — **実機確認で落とした**（600→800 で体感が変わらない）
- **予算調整という方向自体を打ち止めにする。** 関連ノートの品質に不満が出たら、
  **原因は予算ではなく候補の選び方・再ランク・指示文の側**を疑う
- **フォーカスセクション文脈**は別機能として扱う（→ [related_notes_ai](../features/related_notes_ai.md)）

## 13. 完成プロンプトの上限（抜粋の外側）

**用途別の本文上限だけでは、AIへの入力を閉じたことにならない。**
会話履歴・質問・候補名・見出しはどれも抜粋の外側にあり、そこが伸びれば完成プロンプトは伸びる。
実際に2つの経路が開いていた — セクションチャットは**会話履歴を全件そのまま**渡し、
関連候補は**タイトルだけで文字数予算を超えた場合に収まりを確かめ直さず**返していた。

### 判断8: 強制は1箇所、削るのは材料だけ

`PromptBudget.assemble(instructions, body, closing)` が最後に1回だけ上限を当てる。
11本すべての builder がここを通る。

| 部位 | 例 | 上限を超えたとき |
|---|---|---|
| 指示文 | 役割・出力形式・クイズの書式契約 | **削らない**（欠けるとモデルが何をすべきか分からなくなる） |
| 材料 | タイトル・本文抜粋・候補一覧・会話履歴 | **末尾から削り、`(truncated)` を残す** |
| 締め | 新しい質問・ユーザーの返事 | **削らない**（欠けると答える対象が消える） |

**各 builder に切らせない。** 思い思いに切ると、どこが効いているのか誰も言えなくなる。
部分予算（下表）は「**何から削るか**」という機能ごとの判断を担い、
`assemble` は「**必ず収まる**」という不変条件だけを担う。

### 判断9: 上限は計測からではなく「意図する最大構成」から決める

`MAX_PROMPT_CHARACTERS = 6,000` はトークン計測から逆算した値ではない。
**現行設計が意図する最大構成**（関連ノート＝指示文＋タイトル＋抜粋800＋候補ブロック3,500）に
余白を足したものである。

こうしたのは**上限を「新しい制約」にしないため**で、この値ではどの経路の入力も短くならず、
閉じるのは**意図しない伸び**だけになる。部分予算を上げると `PromptBudgetTest` が落ちるので、
**上限も一緒に決め直すことになる**（片方だけ動かして黙って入力が削られるのを防ぐ）。

**トークン上限との関係はここでは主張しない。** 文字数とトークンの対応は端末とモデル世代に依存する
（→ [L22](../lessons/L22.md)）。実トークンの余裕は `PromptTokenBudgetTest` が測る。

| 定数（`PromptLimits`） | 値 | 用途 |
|---|---:|---|
| `MAX_PROMPT_CHARACTERS` | 6,000 | 完成プロンプト全体 |
| `LABEL_CHARACTERS` | 200 | タイトル・見出し・出典ラベル |
| `SECTION_CHAT_HISTORY_CHARACTERS` | 1,200 | 会話履歴の取り分 |
| `QUESTION_CHARACTERS` | 400 | 質問1件 |
| `REPLY_CHARACTERS` | 400 | AIへ渡す返事（**保存する返事は切らない**） |
| `QUERY_CHARACTERS` | 200 | AIピッカーの自然文クエリ |
| `PICKER_CANDIDATES_CHARACTERS` | 2,000 | ピッカーの候補タイトル一覧 |

**見出しを閉じたのは、それがMarkdownの1行で長さの保証が無いため。**
ノート名はファイル名なので実質短いが、見出しは段落まるごとになり得る。

### 判断10: 落とし方は「照合キーかどうか」で決める

同じ「候補が予算に入らない」でも、切ってよいものと切ってはならないものがある。

| 経路 | 照合キー | 予算超過時 |
|---|---|---|
| 関連ノート・蒸留・ひとこと | **ID** | タイトルを切ってよい。末尾の候補から落とす |
| AIピッカー | **タイトルそのもの** | **切らない。行ごと落とす** |

ピッカーでタイトルを切ると受け側の照合が黙って落ち、
**「3件選ばせたのに1件しか出ない」が原因不明のまま起きる**（ピッカーがID契約から外れている件は別課題）。

**落とした候補は許可集合からも外す。** 関連ノートは応答IDを候補集合と照合するが、
プロンプトへ載らなかった候補が許可集合に残ると、**見せていない候補をモデルが当てずっぽうで
指したときに通ってしまう**。蒸留の `validIds` が最初から持っていた契約を関連ノートへも揃えた。

### 判断11: 会話履歴は古い側から落とす

直近ほど文脈として効くので、新しい側から詰めて入らなくなった時点で打ち切る。
**直近の1件だけは切ってでも必ず載せる** — 落とすと「直前に何を聞かれたか」が消え、
会話として成立しなくなる。

### 教訓: 静的な指示文へ複数行の値を補間しない

`trimIndent()` は**補間後の文字列**に効く。複数行の値を埋めるとその2行目以降が
インデント0の行として混ざり、**共通インデントが0と判定されてテンプレート側の字下げが全行に残る。**
本文抜粋も候補一覧も会話履歴も複数行になり得るので、**実運用ではほぼ常に発生していた。**

静的な部分だけを `trimIndent()` して可変部を後から連結する。
`PromptIndentationTest` が全 builder を複数行の値で組み立てて固定する。
**既存の回帰テストは値を単一行でしか渡しておらず、2本は字下げが残った出力を期待値として固定していた**
→ [L44](../lessons/L44.md)。
