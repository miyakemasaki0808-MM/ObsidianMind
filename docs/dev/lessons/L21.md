# L21. 切り分けが止まったら、能力を1つずつ独立に試し、「動くはずのもの」を対照に置く

**教訓:** **対照は「壊れていないはずのもの」なので、それが落ちれば前提が間違っている証拠になる。**
[L11](../lessons.md#l11-テストが効いているかは変異させて確かめる) の調査版 — L11 が「消して落ちるか」でテストの効き目を確かめるのに対し、
**原因調査では「通るはずのものを足して、通るか」で前提を確かめる。**

**いつ当てるか:** 原因の切り分けが止まったとき。
実装上の要点が2つ — **最初の失敗で止めない**（止めると2つ目以降の可否が分からない）、
**ログ取得のような補助処理で失敗させない**（本題の前に終わると何が使えないのかが残らない）。

**再発の証拠:**
- **2026-08-01** — [L20](L20.md) を解いたのは推論ではなく対照実験だった。
  最初の実装は `checkStatus()` → `getBaseModelName()` → `getTokenLimit()` → `countTokens()` を
  一続きで呼んでいて**どれが落ちたか分からなかった**。分解し、落ちないはずの `generate()` を対照に入れた

| プローブ | 結果 | 読み取れること |
|---|---|---|
| `getTokenLimit()` | 成功 | メタデータ照会は通る |
| `countTokens()` | ✗ 10003 | 推論を伴う経路は落ちる |
| **`generate()`（対照）** | **✗ ErrorCode 30** | **計測API固有ではない。原因は環境側** |

**対照が無ければ「トークン系だけが壊れている」という誤った像で確定していた。**
