# L47. 不在を破壊的処理の根拠にするなら、**不在を返しうる全境界で「不能」と分ける**

**いつ当てるか:** 「見つからない」を根拠に、上書き・削除・新規作成を決めるとき
**検査:** `ReadingTraceBackupControllerTest`（端末側を読めない痕跡を新規扱いにしない）

---

痕跡の孤児掃除では、この規則を**一覧の境界**で守っていた。
`ReadingTraceKeyListing` は「列挙できなかった」を `Unavailable` として型で分け、
KDoc にも「畳むと、不在を根拠にする処理が全痕跡を削除対象と誤読する」と書いてある。

**それでも読み戻しは同じ穴を踏んだ。** 分けていたのは一覧の境界だけで、
**1件を読む境界（点読込）は例外を `None` へ畳んだまま**だった。
SAF の `openInputStream` が一時的に失敗すると「痕跡が無い」と読め、
退避側を新規として丸ごと書き、**端末側の返事が警告も保留もなく消える**。
書き込み自体は成功するので、保留にも失敗にも残らない。

**規則が適用済みに見えることが、見落としの原因になる。** 一覧側の型と KDoc が
立派であるほど「この論点は閉じている」と読めてしまう。**閉じているのは境界1つぶんである。**

**当て方:** 破壊的な分岐を書くとき、その判断材料が通ってきた境界を**すべて**列挙し、
どこかで「失敗」が「不在」に化けていないかを見る。片方だけ型で分かれていたら、
それは残りが未対応であることの合図であって、対応済みの証拠ではない（→ [L14](../lessons.md#l14-横展開は最後の1本を取り残す)）。
