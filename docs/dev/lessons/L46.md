# L46. リフレクションで全欄を見る検査でも、**入力を手で書いていれば新しい欄は素通りする**

**いつ当てるか:** 状態型へ欄を足したとき／「全フィールドを見る」形の検査を書くとき
**検査:** `NoteSessionCoordinatorTest`「リセット検査の入力は全フィールドが初期値と異なる」

---

`NoteUiState` のリセット漏れは、リフレクションで**全フィールド**を初期値と突き合わせる
検査が守っている。フィールドを足したときに書き忘れるのがまさに防ぎたい失敗なので、
個別の `assertEquals` を並べない、という設計だった。

**それでも新しい欄は素通りした。** 突き合わせる側は全欄を見るが、
**突き合わせられる入力（`fullyPopulatedState()`）は手で書いている**。
欄を足してそこへ登録し忘れると、その欄の値は初期値のままなので、
検査は「初期値が初期値へ戻ったこと」を確かめて緑になる。
**リセットの登録を丸ごと落としても落ちない。**

L29 と同じ形である — **検査そのものが、守りたい対象より狭い範囲しか数えていない。**
違うのは狭さの出どころで、L29 は判定条件、こちらは**入力**にあった。
「全部見ている」と読める実装ほど、入力側の欠けが見えにくい。

**対策は入力を検査すること。** 「`fullyPopulatedState()` の全欄が初期値と異なる」は
機械で確かめられるので、1本足せば以後は登録漏れが赤で出る。

**一般化:** **「全部を見る」検査を書いたら、その「全部」がどこから来るかを1度たどる。**
判定がリフレクションでも、入力が手書きなら**守られる範囲は手書きの側で決まる**。
