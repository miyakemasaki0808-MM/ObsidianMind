# L52. **上限テストは、長さだけでなく処理対象の要素数も最大化する**

**いつ当てるか:** 入力サイズの上限を決めたとき／全文を走査する処理を足したとき
**検査:** `DistillSourceModelTest`（リンク密・既存太字密の最大サイズ入力）

---

蒸留は 256KB の最大サイズ入力で一段目を計測していた。中身は `x` の反復で、
**記法spanが1つも無い**。そのため「記法数×文字数」で効く経路を1本も通らず、
リンクが密な合法入力で段階1が **7.9秒**（別環境では17.7秒）になっていたのを、上限テストが緑のまま通した。

**長さだけを最大化した入力は、長さに比例する経路しか踏まない。** 実際に効いていたのは
文字数ではなく、**記法の数**（リンク28,000件）と、その一覧を文字ごとに舐める形だった。

**種類を増やしても足りなかった。** 次の巡では、リンク密・太字密の2本を持っていながら
**「候補数×保護範囲数」の経路を両方とも通っていなかった** — リンク密は句点が無いので候補1件、
太字密は保護範囲を1つも増やさない。**要素の種類だけでなく、掛け合わさる2つの量を同時に最大化する。**

**時間で測れない経路は構造で固定する。** 同じ巡で見つかった句分割の再併合は、最大入力でも
23ms→118msにしかならず、閾値を置ける差が出なかった。**二乗であることは変わらない**ので、
「一覧を先頭から舐める書き方を足さない」をソース走査（`DistillProtectedScanTest`）で守る。

**当て方:** 上限を決めたら、**その上限の中で「処理対象の要素」が最大になる入力**を別に作る。
種類ごとに通る経路が違うので1本にまとめない。**閾値が置けないほど差が小さい経路は、
時間ではなく形で縛る。**
