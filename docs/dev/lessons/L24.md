# L24. 判定の根拠が壊れているなら、ユーザー確認を挟んでも訂正されない

**教訓:** **確認UIは根拠を検算しない。** 候補一覧を作るのはアプリであり、その一覧は壊れたシグナルから
生成される。ユーザーは「アプリが孤児だと言っている」以上の情報を持たないので、全選択すれば
自動削除と同じ事故が同じ確率で起きる。**手動化が減らすのは「アプリが独断で消す」ことであって、
「判定が間違っている」ことではない。**

**いつ当てるか:** 危険な操作を設計するとき。**手動か自動かより先に**、次の3つを書く。

1. **「判定の根拠は何か」「その根拠は誤りうるか」を先に書く。**
   順番を逆にすると「確認を挟んだから安全」で思考が止まる
2. **失敗を正常値へ畳む下位関数を疑う。** `?.use {}`・`catch { emptyList() }`・既定値フォールバックは、
   その上に建てられる機能の選択肢を静かに奪う
3. **削除で解く前に、削除しない解が無いか探す。** 消さずに軽くできるなら判定の正しさを問わなくて済む

**集計量で部分欠損は捉えられない。** 「全体件数が0や激減なら走査失敗とみなす」では
サブツリー1つの欠落は動かない。**健全性チェックは故障と同じ粒度に置く。**

**再発の証拠:**
- **2026-08-01** — 読書痕跡の孤児掃除で、論点は最後まで「自動削除は危険だから手動確認を挟めば安全では」の
  形で進んでいた。実際の分岐点は `querySafChildren` の `?.use {}` で、
  **`query()` が null を返すと空リストになり「読めなかった」と「本当に空」が区別不能**だった。
  **SAFの1行が、機能設計1つを不成立にしていた**
- **2026-08-01（同日・出口の更新）** — 「根拠が壊れているから判定は不可能」で閉じたが、より良い出口が出た。
  **根拠を直すのではなく、根拠の性質を「証明」から「証拠」へ落とす** — 1回の不在を根拠にせず票として積み、
  **故障と同じ粒度（フォルダ単位）に遮断器を置く**。効いたのは票数ではなく**粒度の一致**だった。
  **「根拠が信用できない」と言うときは、どの粒度で・どう間違うのかまで書く**
