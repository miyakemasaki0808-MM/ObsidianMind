# L35. ユーザーが必ず実行できるべき操作を、完了保証のない suspend に直列依存させない

**教訓:** 「閉じる」「戻る」のように**ユーザーが必ず実行できなければならない操作**を、
完了が保証されない `suspend`（スクロール・アニメ・mutex獲得）の**後ろ**に置かない。
副作用（位置の書き戻しなど）はベストエフォートにして、**主導線から切り離す。**

**いつ当てるか:** 主要導線の中に `scope.launch { somethingSuspend(); action() }` を書いたとき。
`action()` が**呼ばれない状況が1つでもあるか**を問う。
`LazyListState` へのスクロール指示は、UI応答性が要る場面では suspend の `scrollToItem` ではなく
非suspendの `requestScrollToItem` を検討する。

**片方の競合状態を潰す修正が、別の競合状態を作っていないか要注意。**
この件では「フリング中に書き戻しが消える」を直すために `action()` を後ろへ移した修正が、
別の状態遷移（Fold再生成）で「**そもそも閉じられない**」という**より重い不具合**を生んだ。

**再発の証拠:**
- **2026-07-21** — 折りたたみ状態で全画面ノートを開き、展開すると**✕もシステムバックも無反応**になった。
  ✕・バック・FABが全部 `leaveWith(action)` を通っており、そこが
  `scope.launch { tabListState.scrollToItem(...); action() }` の形だった。
  `android:configChanges` が無いため Fold開閉で Activity が再生成され、
  直後の `tabListState` が再アタッチ／再measureのはざまで `scrollToItem` が**完了しない** →
  後続の `action()`（`popBackStack`）に到達しない。
  **両導線が一点に集約されていた**ことが「同時に無反応」という症状と一致していた。
  修正は非suspendの `requestScrollToItem` で保留位置を積むだけにし、`action()` を即実行する形
  （コルーチンを介さないので元の「書き戻し消失」も原理的に起きない）
