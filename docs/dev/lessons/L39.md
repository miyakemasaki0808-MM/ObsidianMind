# L39. テストダブルは、確かめていないSDKの契約を固定してしまう

**いつ当てるか:** 外部SDKのテストダブルを書くとき／SDKの定数の意味に依存する分岐を書くとき
**検査:** `AiAvailabilityUsageTest`（等値比較とメンバーimportの禁止）。守るのは比較の書き方だけで、
Fake の能力が SDK と一致するかは見ない
**正本:** `FeatureStatus` の意味と扱いは [background_ai_ux](../system/background_ai_ux.md) §6 判断5

---

2026-08-12、`AiAvailability` の統一で `FeatureStatus` の意味を**推測で決めて2件とも誤った**
（`UNAVAILABLE` を恒久非対応と断定した／`DOWNLOADING` のときの `download()` が走行中のDLへ合流すると書いた）。

**2つ目はJVMテストが全件緑のまま通り抜けた。** `FakeAiClient` が DL の Channel を返せることが、
**実在しない「走行中のDLを購読できる」契約**をテストの中に作っていた。
テストは本番の契約ではなく、**こちらが想像した契約**を固定していた。

> **Fakeは仕様書ではない。** 外部APIの意味に依存する分岐を書くなら、
> **先に実装（AAR・逆アセンブル）で裏を取り、その結果をFakeの能力に反映する。**
> 「呼ばれないこと」を確かめたいなら、Fakeに呼び出し回数を持たせる。

CLAUDE.md の「SDKの制約は公式ドキュメントではなくバイナリで確認する」を、**定数の意味と Fake の作りにも当てる。**
