# L39. テストダブルは、確かめていないSDKの契約を固定してしまう

**いつ当てるか:** 外部SDKのテストダブルを書くとき／SDKの定数の意味に依存する分岐を書くとき
**検査:** `AiAvailabilityUsageTest`（等値比較とメンバーimportの禁止）
**正本:** [background_ai_ux](../system/background_ai_ux.md) §6 判断5

---

2026-08-12、`AiAvailability` の統一で `FeatureStatus` の意味を**推測で決めて2件とも誤った**。

- `UNAVAILABLE` を恒久非対応と断定した。実際は AICore 対応端末でも返る値で、
  **あとで使えるようになる端末から再試行導線を奪っていた**
- `DOWNLOADING` のとき `download()` を呼んで「走行中のDLへ合流する」と書いた。
  実装（`downloadFeatureInternal`）に状態の門番は無く、合流できる保証がない

**2つ目はJVMテストが全件緑のまま通り抜けた。** `FakeAiClient` が `downloadModel()` で
Channel を返せることが、**実在しない「走行中のDLを購読できる」契約**をテストの中に作っていたため。
テストは本番の契約ではなく、**こちらが想像した契約**を固定していた。

> **Fakeは仕様書ではない。** 外部APIの意味に依存する分岐を書くなら、
> **先に実装（AAR・逆アセンブル）で裏を取り、その結果をFakeの能力に反映する。**
> 「呼ばれないこと」を確かめたいなら、Fakeに呼び出し回数を持たせる。

CLAUDE.md は既に「SDKの制約は公式ドキュメントではなくバイナリで確認する」と書いていた。
**足りなかったのは、それを定数の意味と Fake の作りにも当てるという読み方**である。
