# L49. **中止は要求であって完了ではない。** 止めた側が、まだ動いている書き手の途中経過を確定しない

**いつ当てるか:** 走行中の処理へ「中止」を付けるとき／中断の結果に件数・進捗を添えるとき
**検査:** `ReadingTraceBackupControllerTest`（まとまりの途中で止めても報告と実保存が一致する）・
`ReadingTraceBackupThreadingTest`（中止の結果は書き手を `join()` してから確定する）

---

痕跡の読み戻しは、中断しても「どこまで適用したか」を件数で見せる設計だった。
`cancel()` は `job.cancel()` の直後に集計を読んで結果を確定していた。

**`cancel()` は印を付けるだけで、書き手はまだ走っている。** 実機では表示55件に対し
75件が保存された。原因は2つが重なったこと — I/O 1まとまり（25件）の中に中断点が無く、
**止めた後もまとまりを走り切る**うえ、集計を読むのが停止前だった。

**「少なく報告する側へ倒してある」という言い分が、欠陥を正当化していた。** 正本にも
テストにも「ずれは最大1件」と書いてあったが、**その1件はどこからも導かれていない**。
中断テストがちょうど25件目（まとまりの境界）で止めており、途中で止める順序を一度も通していなかった。

**当て方:** 中止を「要求 → 生産者の停止 → 結果の確定」の3手に割り、**結果は停止後に1度だけ**数える。
生産者側には、外から観測できる粒度（1件ごと）で協調キャンセル点を置く。
**受理条件は「表示と実体が一致する」**であって「少なめに出る」ではない。

**境界でだけ止めるテストは、境界を走り切る欠陥を通す。** 中断を試すなら、
**まとまりの途中**で止める（→ [L11](../lessons.md#l11-テストが効いているかは変異させて確かめる)）。
