# L49. **中止は要求であって完了ではない。** 止めた側が、まだ動いている書き手の途中経過を確定しない

**いつ当てるか:** 走行中の処理へ「中止」を付けるとき／中断の結果に件数・進捗を添えるとき／完了待ちを入れたとき
**検査:** `ReadingTraceBackupControllerTest`（まとまりの途中で止めても報告と実保存が一致する／
停止待ち中の再タップで停止前の件数を確定しない）・`ThreadingScanTest`（中止の結果は書き手を `join()` してから確定する）。
走査と動的検査の分担、別スレッドとラッチが要る理由は両テストの KDoc が持つ

---

痕跡の読み戻しは、中断しても「どこまで適用したか」を件数で見せる。`cancel()` の直後に集計を読んで確定していたため、
実機では表示55件に対し75件が保存された。**`cancel()` は印を付けるだけで、書き手はまだ走っている。**

**「少なく報告する側へ倒してある」という言い分が、欠陥を正当化していた。** 「ずれは最大1件」はどこからも導かれておらず、
中断テストがちょうどまとまりの境界で止めていたので、途中で止める順序を一度も通していなかった。

**当て方:**

- 中止を「要求 → 生産者の停止 → 結果の確定」の3手に割り、**結果は停止後に1度だけ**数える。
  受理条件は「表示と実体が一致する」であって「少なめに出る」ではない
- 中断を試すなら、**まとまりの途中**で止める。境界でだけ止めるテストは、境界を走り切る欠陥を通す
- **待ち合わせを入れたら、待っている間に同じ入口をもう一度通れるかを見る。** この教訓を書いた直後の修正が、
  停止待ちの間の2度目の中止で同じ型に戻った。受理を1回に絞るのは、待ち合わせと対になる
