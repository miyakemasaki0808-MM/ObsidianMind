# L60. **SDKの単位は実装ではなく出力で確かめる。同じ語でも変換を1段挟んでいることがある**

**いつ当てるか:** SDKへ**寸法・時間・容量を渡す**とき（`cameraDistance`・トークン上限・タイムアウト等）
**検査:** `BookletSheetPerspectiveTest`（`cameraDistance` の実効距離を画素から逆算する — **この1つの値だけ**）。
一般則は検査できない（渡した値が妥当かは機能ごとに違う）ので参考にとどまり、ほかのSDKの単位はその都度確かめる。
逆算の方法と測定条件は、このテストの KDoc が持つ

---

冊子の紙を回すとき、`graphicsLayer.cameraDistance` に紙の高さ（ピクセル）× 1.5 を渡していた。
根拠は Compose と `RenderNode` の KDoc の「expressed in pixels」で、**両方とも実際の出力と違った。**

**1度目の訂正も間違っていた。** `View.setCameraDistance` が `densityDpi` で割ることを読んで「物理的な長さ」と結論したが、
Compose の `ViewLayer` はその割り算を打ち消しており、本筋の `RenderNodeLayer` は素通しする。**読んだのは使っていない入口の実装だった。**
遠すぎた値では遠近が静かに消え、近すぎた値では倒した紙がカメラの裏へ回って表示域を覆った。

**画素を数えて初めて決まった。** 倒した面の投影された縦の長さから逆算すると、測った端末では渡した値の約72倍が画素だった。
これは測った範囲での値であって、すべての端末での保証ではない。

**当て方:**

- **既定値から単位を逆算する。** 既定が 8 で、面の高さが 2000 なら、**桁が違う時点で単位が違う**
- **上限と下限の両方をテストで挟む。** 値が大きすぎても何も起きない側（遠近が消えるだけ）は、何ヶ月も気づかれない
- **KDocの単位語（pixels / ms / tokens）を鵜呑みにしない。** 入口が複数あるAPIは、**自分が通る入口の実装**でなければ読んだことにならない
- **最後は出力を測る。** 渡した値を変えて画面（画素）がどう動くかを測れば、単位の議論そのものが要らなくなる（→ [L61](L61.md) と同じ形）

これは2件目である。1件目は `maxOutputTokens` の 1〜256 制限で、公式ドキュメントに無い制約を踏んで全AI生成が落ちた
（→ CLAUDE.md 禁止事項）。1件目は「書いていないことがあった」、2件目は「**書いてあることが違った**」。
