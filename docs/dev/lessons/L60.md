# L60. **SDKの単位はKDocではなく実装で確かめる。同じ語でも変換を1段挟んでいることがある**

**いつ当てるか:** SDKへ**寸法・時間・容量を渡す**とき（`cameraDistance`・トークン上限・タイムアウト等）
**検査:** なし（**参考**。渡した値が妥当かは機能ごとに違う）。ただし**上限・下限をテストで挟むことはできる**

---

冊子の紙を回すとき、`graphicsLayer.cameraDistance` に **紙の高さ（ピクセル）× 1.5** を渡していた。
根拠は Compose の KDoc — 「The distance is expressed in **pixels**」「回すなら面の高さより遠く」。
`RenderNode` 側の KDoc も同じく「expressed in pixels」と書いてある。**両方とも実装と違った。**

`View.setCameraDistance` は **`densityDpi` で割ってから** `RenderNode` へ渡す。
`View` の既定は「mdpi で 1280」で、**1280 ÷ 160 = 8** — Compose の `DefaultCameraDistance = 8.0f` と一致する。
**そこで「単位はピクセルではなく画面上の物理的な長さだ」と結論し、高さをインチ相当へ直して渡した。**

渡していた値は既定の**約350倍遠い**。**遠近は最初から効いておらず、倒れた紙は縦に潰れるだけの板だった。**
実機で出た「紙が曲がる感じが足りない」はここから来ていた。
**2.5 → 1.5 と「立体感を上げた」変更も、実際には何もしていなかった。**

## その訂正も間違っていた（同日、2度目）

**`View` の実装から Compose の単位は決まらない。** Compose の `ViewLayer` は
`View.setCameraDistance` の割り算を打ち消すために**渡す前に `densityDpi` を掛けている**し、
本筋の `RenderNodeLayer` はそもそも素通しする。**読んだのは「関係のある別のAPI」の実装だった。**

訂正後の実効距離は**紙の高さの約 0.28 倍**。**23度を越えると紙の下端がカメラの裏へ回る**ので、
実機では倒した紙が拡大して表示域を覆い、**次の紙の見え方も表裏の入れ替わりも判定できなかった**
（それらは「承認済みパラメータの許容事項」として不具合に数えられていなかった）。

**画素を数えて初めて決まった。** 倒した面の投影された縦の長さから逆算すると、
**渡した値の 72 倍が画素**である（画面密度を 390 → 320 に変えても実効画素数は同じだったので、密度には依らない）。
検査は `BookletSheetPerspectiveTest` が持つ。

**これは2件目である。****これは2件目である。** 1件目は `maxOutputTokens` の 1〜256 制限で、
**公式ドキュメントに無い制約を踏んで全AI生成が落ちた**（→ CLAUDE.md 禁止事項）。
1件目は「書いていないことがあった」、2件目は「**書いてあることが違った**」。

## なぜ気づけなかったか

**値が大きすぎても何も起きない。** 小さすぎれば像が破綻して一目で分かるが、
遠すぎる側は**遠近が静かに消えるだけ**で、エラーも警告も出ない。
**片側にしか安全弁が無い値は、反対側へ振り切ったまま何ヶ月も走る。**

## 当て方

- **既定値から単位を逆算する。** 既定が 8 で、面の高さが 2000 なら、**桁が違う時点で単位が違う。**
  「既定と同じ桁か」を最初に問う
- **上限と下限の両方をテストで挟む。** 公式の指示が片側しか無くても、**反対側は自分で決めて書く**
- **KDocの単位語（pixels / ms / tokens）を鵜呑みにしない。** フレームワークが変換を挟んでいることがある。
  `View` / `RenderNode` のように**入口が複数ある**APIは、どの入口の単位かまで見る
- **「実装で確かめた」の中身を問う。** 2度目の取り違えは、**使っていないほうの入口**（`View`）の実装を読んで
  出した結論だった。**自分が通る経路の実装でなければ、読んだことにならない。**
- **最後は出力を測る。** 単位が争点になったら、**渡した値を変えて画面（画素）がどう動くかを測る。**
  そこまでやれば単位の議論そのものが要らなくなる（→ [L61](L61.md) と同じ形）
