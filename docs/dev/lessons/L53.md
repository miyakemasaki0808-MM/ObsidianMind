# L53. **実機でしか走らないテストは、効いていることを確かめられない**

**いつ当てるか:** 描画・レイアウト・タップの契約を `androidTest` で守ろうとしたとき
**検査:** `DistillRangeHighlightTest`・`DistillRangeNoticeTest`（JVMへ引き出した観測点）

---

太字範囲の調整シートは「確定範囲を太字＋下線で示す（色だけの手がかりにしない）」を契約に持ち、
`androidTest` で親文が表示されることを見ていた。**強調を丸ごと外してもこのテストは緑のまま通る。**
テスト名とコメントには太字と書いてあり、**主張だけが検査の顔をしていた**（外部レビューで発見）。

根は「観測点を間違えた」ことだけではない。**このリポジトリで検査が効いていると言えるのは
変異させて落としたときだけ**（→ [L11](../lessons.md#l11-テストが効いているかは変異させて確かめる)）
だが、`androidTest` は端末が要るので**手元で変異を回せない**。
つまり実機側へ置いた契約は、**構造的に変異確認を省かれる**。

**当て方:** 実機テストへ契約を置く前に、**値として観測できる部分をJVMへ引き出す**。
今回は `highlightedParent`（AnnotatedStringのspan）と `overlapNotice`（文言の主語）を
`internal` の純関数にし、JVM側で変異確認した。実機側には
「そのspanが実際に描かれる」ことだけを残す。

**残すものと引き出すものの線引き:** 実測（レイアウト・可視判定・再コンポーズ・タップの届き先）は
実機に残す。**値の組み立ては引き出す。** 引き出せない契約だけが、変異確認なしで残る。
