# L40. 改名した型は、正本の機能仕様まで同じPRで当て直す

**いつ当てるか:** 状態・列挙の値を改名／削除するとき
**検査:** `DesignDocStateNameTest`（`features/` `system/` に実在しない `AiAvailability.<名前>` を書かせない）
**正本:** [background_ai_ux](../system/background_ai_ux.md) §6

---

2026-08-12、`AiAvailability` の改名で **2回連続、独立レビューに正本のドリフトを指摘された。**
1回目で `quiz` / `section_ai_chat` / `ai_picker` / `related_notes_ai` を直したが、
**同じPRの2回目で `reflect_remark` / `source_code_analysis` / 実装計画が残っていた。**

**原因は「気づけなかった」ではなく、気づく仕組みが無かったこと。**
コードの改名はコンパイラが全箇所を挙げてくれるが、**文書は何も言わない。**
だから grep で目視確認する限り、毎回どこかが残る。

> **コンパイラが挙げてくれる範囲を、そのまま「直すべき範囲」だと思わない。**
> 改名の影響は正本の機能仕様にも及ぶ。**そちらには検査を置く。**

歴史的な言及（「旧 `Available` を畳んでいた」）は**型名を付けずに書く**規約にした。
これで検査に許容リストが要らなくなり、例外を数えずに済む
（許容リストを持つ検査は、例外が増えるほど守らせる力が落ちる → [L29](../lessons.md)）。
