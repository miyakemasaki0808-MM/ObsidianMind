# L27. 仕様を変えるときは、その仕様を固定しているテストと文書を先に数える

**教訓:** **良い仕様であるほど、テストと文書に明示的に書かれている。**
だから**「よく書けている仕様」ほど、変更時に直す場所が多い。**
[L14](../lessons.md#l14-横展開は最後の1本を取り残す) が「同じ変更を全箇所へ広げる」漏れなら、
こちらは**「変更前の姿を記録した全箇所を消す」漏れ**である。向きが逆で、見落とし方も違う。

**いつ当てるか:** 仕様を変えると決めたとき。**実装に触る前に旧仕様の記述を grep で数え、
その件数を計画に書く。** 検索語は機能名ではなく**落ちていた情報そのもの**で引く。
**コード内のKDocも対象に含める — 仕様はコメントにも書かれている。**

**あわせて:** 「原文を尊重する」のような方針を決めたら、**型がその判断を裏切っていないか確かめる。**
方針を文章で決めた直後に、その方針が保持すべき情報を1つずつ型へ当てる。
