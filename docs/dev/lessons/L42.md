# L42. 「測る道具が要る」と判断したら、それがアプリの中に要るかを先に問う

**いつ当てるか:** 「効果を測る道具が先に要る」「実機で分布を見るのが先」と判断したとき。

---

`feature_ideas` の型2 は「効果を測る道具が先に要る」候補を3件束ね、その道具として
**アプリ内の計測器**（同じ入力を流す台・出力を採点する物差し）を名指しした。計測器は実機を要する。
結果として3件が**まだ作っていない道具の完成待ち**になり、うち1件の最大の分岐（二度書き検出の粒度）は
18日間「未決」のまま置かれた。

実際にその分岐を解いたのは、**リポジトリ内の `docs/` 80本へ既存の純ロジックを当てた1回の計測**だった。
端末もアプリもNanoも要らず、粒度・段構え・ノイズ除去・レコード単位が同時に決まり、
**当初の段構え（ノート全体のDiceで粗く絞る）が成立しないことまで**分かった。

**分岐が「アプリの挙動」ではなく「入力データの性質」に属するなら、測る場所はアプリの中でなくてよい。**
アプリ内の計測器が本当に必要なのは、モデルの出力揺らぎのように**アプリを動かさないと現れないもの**だけである。

**代理コーパスで測れる条件は、純ロジックがAndroid依存から切れていること。**
`domain` を素のJVMで扱えるようにしてある価値は、テスト容易性だけではない
（→ [architecture](../system/architecture.md) 判断3・判断5）。**同じ分離が、着手前の測定も可能にする。**

**代理コーパスは実データの代わりにならない。** 上の計測でも、アルゴリズムの性質
（粒度・重複報告の仕方）はコーパスに依らず決まったが、**件数の内訳は代理コーパス固有**として
実Vaultでの確認を残件にしている。**何がコーパス非依存かを、結論ごとに分けて書く。**
