# L29. 規則は検査へ変えるまで守られない。そして検査は、守りたい性質より狭い対象を数える

**教訓 — 運用は3つ。**

1. **規則を書いたら、「守られなかったことをどう検出するか」を同じコミットで決める。**
   決められないなら、その規則は**次も守られない**と考えてよい。
   実績として、このリポジトリで規則が守られたのは**検査に載せたときだけ**である
2. **検査を書いたら、「この検査が数えていない経路」を先に3つ挙げる。**
   記法・置き場・書式のどれかで狭めていることが多い（[L14](../lessons.md#l14-横展開は最後の1本を取り残す) の検査そのものへの適用）
3. **検査を入れたら、必ず1回変異させて落ちることを確かめる**（[L11](../lessons.md#l11-テストが効いているかは変異させて確かめる)）。
   **落ちない検査は、無い検査より悪い** — 「守られている」という認識だけが残るため

**いつ当てるか:** 文書に「〜する」「〜しない」と書いたとき。
**スクリプトにしない** — 「走らせる」という手動契約が新しく生まれ、同じ罠を1段ずらすだけになる。

**再発の形（2026-08〜09）:**
- **規則が2箇所にあっても守られなかった。** 総評の指摘が2日間起票されなかった。
  チェックリストは自分の変更に向いているので、**文書を貼るだけの作業では発火しない**
- **検査自身が狭かった。** 文書参照のリンク検査が、守りたい「参照」ではなく記法で引き、旧パスを3回取り残した
- **検査が一度も走らなかった。** Gradle が `docs/` を入力と見なさず、`UP-TO-DATE` で飛ばしていた
- **守られたのに壊れた。** 「change_history へ1行」は毎回守られたが、1行の長さに上限が無かった
- **規則の置き場所を誤った。** 規則は、それを破りうる人が必ず読む文書に置く（`owner/` の更新規則が `owner/` の中にしか無かった）

**検査（代表例）:** `ReviewFindingsLedgerTest`（起票漏れ）・`SourceDocSyncTest`（文書との同期）・
`AiAvailabilityContractTest`（契約の口を全経路へ当てる）。この教訓は検査全般に当たるので、全件の一覧は持たない。
各検査が数えていない経路は、それぞれの KDoc が持つ。
