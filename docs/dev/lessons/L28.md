# L28. Boolean は「何が起きたか」ではなく「呼び出し側が次に何をするか」で決める

**教訓:** `true` と `false` を、それぞれ**「呼び出し側が次にすること」で言い換えてみる。**
言い換えられない側があれば、返しているのは呼び出し側の関心事ではなく実装の内部状態である。
**言い換えは両側に当てる** — 片側だけ見ると、正反対の次の行動が同じ値に同居していても割れない。
次の行動が3つ以上あるなら Boolean をやめて sealed で分ける。

**「分岐が3つ以上なら Boolean をやめる」では捕まらない。** 4度目の事例は
呼び出し側の行動が2つしかなく、**Boolean 自体は最後まで正当**だった。壊れていたのは `false` の中身。

**いつ当てるか:** 境界に新しい戻り値・シグネチャを足したとき。
**同じ意味の判定が2箇所にあるなら、両方が同じ強さかを見る** — 規則が違っていたら
**弱いほうは常に後から書いたほう**である（これが5度目で効いた唯一の観測可能な兆候）。

**再発の証拠 — このコードベースで6度出ている。**

**4度目で気づけなかった理由が重要。** 過去3件を**「失敗と不在」という語**で覚えていたため、
**「捨てたか」という別の語をまとった4件目に気づかなかった。**
5度目は**同じ機能の中**で、洗い出し側は同じ状況を `Blocked` として正しく分けていたのに、
削除側を書くときに Boolean を選んでいる。

> **この教訓から作った検査自身が、一度この罠を踏んだ。** 旧 §0 の初版は
> 「分岐が3つ以上なら Boolean をやめる」を問いにしていて、**その問いを当該diffへ当てても素通りした**。
> **検査を書いたら、まず元の失敗へ当て直す。**
