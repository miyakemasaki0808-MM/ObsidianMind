## 1. 概要

ノートの中から**読み直す価値のある原文箇所をAIに選ばせ**、ユーザーが確定したものを**太字にして本文へ書き戻す**。

**このアプリで唯一、Vault のノート本文を書き換える機能**である
（→ [ADR-0004](../decisions/ADR-0004-do-not-rewrite-vault-body.md)）。

## 2. ゴールと非ゴール

### ゴール
- 読み直すべき箇所を**原文のまま**残す（生成しない）
- 書き戻しで**ユーザーのノートを壊さない**

### 非ゴール
- **AIに文章を生成させない**（→ §8 判断1）
- **装飾記号の挿入以外をしない。** 削除も並べ替えもしない
- **frontmatter を触らない**
- **範囲調整を汎用ノート編集にしない。** 文字を打てないだけでなく、
  **原文の任意の場所を指せない**（確定範囲は親文の内側に閉じる → §8 判断15）
- **調整結果を永続化しない。** 覚えるのはノート本文に入った `**` だけ

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 候補の提示 | AIが選んだ文（長文は句、括弧内は語句）が候補として並ぶ | AIタブの明示操作 |
| 候補の取捨 | チェックで選び直せる | 候補表示中 |
| 範囲の調整 | 候補をタップすると親文が開き、段を選ぶか端のつまみを引いて太字の範囲を決められる | 候補表示中 |
| 重なりの自動解消 | 他の選択候補と範囲が重なったら、**相手の選択が外れる。** 外れた候補には理由の印が残る | 範囲変更時とチェック時 |
| 書き戻し | 選んだ文が本文で太字になる | 確定操作 |
| 復旧 | 中断した書き込みを次回起動で検出する | アプリ起動時 |

## 4. 現在のユーザーフロー

1. AIタブで蒸留を始める
2. **非AIで候補を絞る**（サリエンススコア → §8 判断3）
3. **AIに1回だけ**、残った候補からIDを選ばせる（→ §8 判断2・判断5）
4. ユーザーが候補を取捨する
5. **調整したい候補をタップし、段を選ぶか端を引いて範囲を決めて閉じる**（任意 → §5 太字にする範囲の調整）
6. 確定する
7. **キャッシュ構築 → 復旧レコードを原子的に確定 → SAF一気書き → 検証**（→ §8 判断7）
8. 保存後は**本文専用リロード**で表示を更新する（→ §8 判断9）

## 5. 機能仕様

**この節が数値・除外契約・オフセット規約の正本。** §8 は理由だけを持ち、値は書かない。

### 上限（`DistillLimits`）

**すべて実機調整前提の初期値。**

| 対象 | 値 | 定数 |
|---|---|---|
| 対象ファイル | 256KB（超は機能を無効表示） | `MAX_FILE_BYTES` |
| スコアリングする文の数 | 400 | `MAX_SENTENCES_FOR_SCORING` |
| AIへ渡す候補 | 24 | `MAX_AI_CANDIDATES` |
| AI候補の文字予算 | 1,500 | `AI_CANDIDATE_CHAR_BUDGET` |
| 最終選択 | **6件** | `FINAL_SELECTION_LIMIT` |
| 1文の最大長 | 160文字（超過文は候補外） | `MAX_SENTENCE_CHARACTERS` |
| 句へ割る文の下限 | 60文字（超える文だけ読点で割る） | `CLAUSE_SPLIT_THRESHOLD` |
| 句の最小長 | 15文字（未満の断片は結合する） | `MIN_CLAUSE_CHARACTERS` |
| 1文から入れる句 | 2件 | `MAX_CLAUSES_PER_SENTENCE` |
| 語句候補の件数 | 2件 | `MAX_TERM_CANDIDATES` |
| 語句候補の長さ | 2〜20文字 | `MIN_TERM_CHARACTERS` / `MAX_TERM_CHARACTERS` |
| チャンクの文字数 | 1,200 | `CHUNK_CHARACTER_LIMIT` |
| 太字の比率上限 | **30%** | `MAX_BOLD_RATIO` |

**内部ストレージは対象ノートの約2倍以上の空きが要る**（完成後キャッシュ＋元本文入り復旧レコードを同時に持つため）。

### 候補の対象と除外

- **まるごと候補対象外:** コードフェンス・テーブル・frontmatter（YAML `---`）・見出し
- **インラインコードを含む文は候補に含めてよい**（`` **Use `foo` to run.** `` のように外側からの太字化は成立する）
- **除外するのは次の2つだけ:**
  - 候補の**開始/終了位置が保護範囲の内部に入る**（コードスパン・リンク・**斜体 `*…*`・太字斜体 `***…***`・打ち消し線 `~~…~~`**）
  - 候補が**既存 `**` 強調と部分的に重なる**
- **保護範囲は、文・句の境界を置かない範囲でもある。** 同じ集合で両方を守る（`InlineSyntax.protectedSpans`）。
  片方だけに掛けると「割らないが端は入る」「端は入らないが割る」のどちらかが残る
- 通常リンク・wikilink は**構文全体が文の内側に収まれば太字内に含める**（範囲がまたぐ場合のみ除外）
- **ただしリンクを除くと実質的な文字が残らない文は候補にしない。**
  リンクは既にリンクなので、太字にしても読み返しの手がかりにならない。
  **判定に長さを使わない** — 比率で見ると `[[Vigilith]]を採用する。` のような意味のある主張を落とし、
  文字数で見ると区切り記号の数で結果が反転する（`[[A]]、[[B]]、[[C]]、[[D]]。` が残り `[[A]]は核。` が落ちる）。
  **リンク範囲を除いた残りから記号を取り除き、文字か数字が残るか**で決める。
  **接続語（閉じた一覧）を取り除くのは、両側がリンクの断片だけ。** 日本語は助詞と普通名詞の語境界が
  空白で分かれないので、位置を問わず取り除くと語中まで剥がれる（`[[A]]のもの。` が空になる）。
  **正規化の対象と、意味を捨ててよい位置は別々に決める。**
  リンクを含まない文には掛からないので、短文の扱いは従来どおり
  （判定は `isLinkOnlyRange`。候補の単位が句へ変わっても再適用できるよう、文ではなく範囲を受ける）
- **リンクしか無いセクションはチャンク代表を持たない。** これは追加の分岐ではなく、
  上記の除外を候補選定の入口で掛けた帰結である（除外後のチャンクは代表の抽選に現れない）
- 重複・重なり候補は排除する

**保護範囲は表示と同じ解釈器から取る。** `domain/markdown/InlineSyntax.kt` の `scanInlineSyntax` が
唯一の解釈器で、表示（`inlineMarkdown`）も蒸留もその答えを使う（→ [lessons](../lessons.md) L51）。

**記法の一覧を揃えるだけでは足りなかった。** 種類を合わせたあとも、**バッククォートの数え方・
エスケープの扱い・リンクの消費・ブロックの単位**という解釈規則が食い違い、
表示上は1つの装飾の内側へ蒸留が候補境界を置ける状態が残っていた（2026-08-29 のレビュー）。

- **入力の単位は表示側と同じ** — 段落は連続する本文行を連結し、**リスト項目と引用行は1行ずつ独立**させる。
  連結すると、別々に描かれる行のあいだに偽の対ができて候補が消える
- **エスケープ（`\*`）は対を開かない。** 表示側も `\` を出さず記号だけを描く（Obsidianと同じ）
- **コードは開いた連なりと同じ長さの連なりだけが閉じになる。** 2個で開いて3個しか無ければコードにしない
  （CommonMark と同じ。部分一致を許すと、閉じていない連なりが「閉じている」ことになる）
- **リンクは構文全体を消費し、内側の記号を装飾に使わない。** 対の探索もリンクとコードを飛ばす
- **内側が空白で始まる／終わる対は作らない**（`2 * 3 * 4` が斜体にならない）
- **長い記号で閉じられなければ、同じ位置で短い記号を試す。** `*斜体*。` を太字にした `***斜体*。**` に
  余分な `*` が本文として出ないようにするため
- **入れ子を保つ。** 強調の内側はもう一度解釈し、表示側も再帰的に描く。
  **保たないと、文を太字にした瞬間にユーザーの斜体・コード・リンクが表示から消える**
- **`_…_` / `__…__` は保護しない。** 表示側が解釈せず、`some_var_name` を装飾と誤認して候補を不当に減らす。
  Obsidian 側では装飾として読まれうるので、**保証しないことに数える**
- **代償: 装飾の内側にある鉤括弧の語句候補は消える。** 保護範囲と重なる語句を採らないため。安全側への縮小として受け入れる
- **保存の受理条件は「種別と対象文字列の組が残ること」。** 文字列の部分一致で見ると、
  `Italic:斜体` が `Bold:*斜体*。` へ変わっても通ってしまう（一度それで見逃した）
- **走査は入力サイズに比例させる。** 守るのは3つ — ①位置ごとに記法の一覧を先頭から探さない
  ②**閉じ記号を見つけられなかったことを覚える**（未閉じの `[` が並ぶ本文で、開始記号ごとに末尾まで
  探し直して250,000文字で8.4秒になった。表示側も同じ解釈器を通るのでMainが止まる）。
  **バッククォートは連なりを1単位として読む** — 位置ごとに `` "`".repeat(n) `` の検索キーを作ると、
  長さの違う未閉じの連なりで96,002文字が `OutOfMemoryError` になる
  ③**候補ごとに保護範囲の先頭へ戻らない**（装飾された短文が32,000件並ぶ入力で5.2秒）。
  保護範囲は `ProtectedCursor` 越しにだけ読み、**用途ごとに別のカーソルを持つ**
  （端点照合は文末まで進むので、そのまま句分割へ渡すと必要なスパンを追い越す）。
  上限テストは**文字数・記法数・候補数×保護範囲数**の3系統を持つ（→ [lessons](../lessons.md) L52）

### 句分割（長文だけ）

**`CLAUSE_SPLIT_THRESHOLD` を超える文だけ**、読点（`、` `,`）で句へ割る。短い文はまるごと候補にする。
全文を割ると、短文の選定まで細切れになって「単語まみれ」に寄るため。

- **読点そのものは句に含めない。** 含めると `**AAA、**BBB。` のように区切り記号まで太字になる
- **前から貪欲に積み、`MIN_CLAUSE_CHARACTERS` へ届いた時点で閉じる。**
  末尾に残った下限未満の余りは直前の句へ吸収する（下限未満の句を作らない）。
  **下限だけでは結合の向きが決まらない**ので、向きまで決めてはじめて挙動が定まる
- **鉤括弧の内側では割らない。** 割ると括弧が2つの句へまたがり、**語句候補が取れなくなる**
  （`「設計、検証」` が `…「設計` と `検証」…` に割れた）。保護範囲は `protectedSpans`（コードスパン・リンク・装飾）＋鉤括弧
- **読点が無い長文は割れないまま残す。** 無理に割ると意味が壊れる
- 割った文は**親文を候補にしない**（全文と句で枠を二重に食わないため）。1文から入れる句は `MAX_CLAUSES_PER_SENTENCE` まで
- **リンクだけかの判定は句ごとに掛け直す**（親文が通常文でも断片はリンクだけになり得る）
- **構造ボーナスは位置を占める句だけへ付く** — 段落先頭・見出し直下は先頭句、チャンク末尾・ノート末尾は末尾句。
  全句へ継承すると1文で構造点を多重取りする。**これは分配を書いた結果ではなく、
  位置フラグを「グループ内で最初／最後の候補」として数えていることの帰結である**

### 語句候補（括弧内）

鉤括弧（`「」` `『』`）の中身を語句候補にする。長さは `MIN_TERM_CHARACTERS`〜`MAX_TERM_CHARACTERS`。

- **入口を括弧に限るのは、アプリが原文範囲を決定的に取れるから。** 任意の名詞句は形態素解析を要する
- **`〜とは` の定義対象は採らない。** 語の開始位置を決めるのに閉じた一覧が要り、
  一覧の扱いで既に失敗している（→ 判断13）
- **コロン前・箇条書き先頭のラベルも採らない。** `- **ラベル**: 説明` の形で既に手で太字にされていることが多く、
  既存強調として編集対象から外れるため、候補になる前に消える
- **同じ表層文字列の語句は1件へ落とす。** 語は文と違って何度も出るので、候補が同じ語で埋まる
- **位置の重み付けには参加しない。** 本文の線形構造ではなく、その上に重ねる候補だから。
  短文ペナルティの対象にもしない（語句は短いのが当たり前）

### 候補どうしは重ならない

**選定の出口で、候補集合が互いに重ならないことを保証する。重なったら細かいほうを残す。**

`applyDistillBold` は重なる範囲を `require` で拒む。文と句は互いに重ならないので従来は問題にならなかったが、
**語句候補は親（文・句）の内側に重なる初めての候補**であり、
重なったまま両方を選べる状態をUIへ出すと**保存が例外で落ちる**。
細かいほうを残すのは、粒度を細かくすることが語句候補の目的だから。

### 文分割

`。！？`＋改行を境界とする。ただし次で誤分割しない。

- **番号リスト `1. `**（パース済みリスト項目として記号を範囲外に置く）
- **小数点・英略語**
- **インラインコード内の句読点**（境界にしない）

### オフセット規約

| | |
|---|---|
| 編集範囲 | **UTF-16 コードユニットのインデックス** |
| 入力 | **UTF-8 を厳格にデコード。** 非UTF-8・不正バイトは**書き込まずエラー** |
| BOM・CRLF・末尾改行 | **元の文字列構造を維持する** |
| 絵文字・サロゲートペア | それ以降の文も正しい位置へ挿入できること |

### 一段目スコア（非AI）

**チャンク定義:** **見出し間が基本単位**。見出しが無い、またはチャンクが `CHUNK_CHARACTER_LIMIT` を超える場合は
**固定文字数窓で非重複分割**する（ハイブリッド）。各文は所属チャンクと**直近見出し**を保持する。

```
score = 1.0 * dice(文, タイトル)
      + 0.7 * dice(文, 直近見出し)
      + structuralWeight
```

- `dice` は `RelatedCandidateScoring` の文字bigram Dice技法を流用する
- **`structuralWeight`（加算）**

  | 位置 | 加点 |
  |---|---|
  | 段落先頭文 | +0.3 |
  | チャンク・ノート末尾文 | +0.4 |
  | 見出し直下 | +0.2 |

- **長さ補正:** 15字未満は減点。`MAX_SENTENCE_CHARACTERS` 超は候補対象外
- **タイブレーク:** `rankByScore` 既存規約（score → tieBreak → 入力順で決定的）

**網羅と間引き:**

- **チャンク最低枠** — 各チャンクから最低1件を候補へ入れる
- **計算量上限** — 文数が `MAX_SENTENCES_FOR_SCORING` を超えたら、位置・長さで事前間引きしてからスコアする
- **チャンク数 > 候補上限のとき** — 構造的重み優先で二次間引きし、`AI_CANDIDATE_CHAR_BUDGET` 内へ収める

### 文ID選択プロトコル（二段目）

- アプリが候補文へ `S001…` の**固定3桁ID**を付与し、AIには**IDだけ**返させる
- 抽出は**前後境界必須**の regex で行う:

  ```
  (?i)(?<![A-Z0-9])S\d{3}(?![A-Z0-9])
  ```

- **無効として破棄するもの**（自動補正しない）: 桁落ち（`S01`）・4桁以上・境界不正（`S001A` 等）・
  存在しないID・重複ID
- 保存時はIDが指す**原文オフセット範囲**だけを**オフセット降順**で `**` 挿入する
- **UIに出すのは常に原文**（AI選定は既定チェック）

### 競合検知

- 候補生成時に、**URIから読んだ原バイト列**の SHA-256 を基準ハッシュとして保持する
- 保存直前にURIから全文再読込して再計算し、**不一致なら中断**する（`lastModified` は補助のみ）
- 書き込み後に再読込し、**期待出力ハッシュと一致するまで成功扱いにしない**
- **TOCTOU は残る。** 確認と書き込みの間の外部編集は汎用SAFで完全排除できない（→ §8 判断6）

### 書き込みの性質

**装飾記号の挿入のみ・ユーザー確定・冪等・frontmatter 保護。**

- 全文を書き直して途中へ `**` を挿入する。**既存文字を削除しない**
- AI候補（既定チェック済み）をユーザーが間引き、**明示保存したものだけ**書く
- **既に太字の文はスキップ**する
- 書き込み前に**空き容量不足・キャッシュ生成失敗・復旧レコード生成失敗**を検知して安全に中断する
- キャッシュファイルは**成功・失敗・起動時に必ず掃除**する

### 累積太字上限ポリシー

Markdownだけでは**既存太字とアプリ追加太字を区別できない**ため、編集対象本文内の
**全太字文（ユーザー既存＋アプリ追加）を `MAX_BOLD_RATIO` の累積上限に含める**。
見出し・コードフェンス・テーブル・frontmatter 等の蒸留対象外領域にある太字は、**分母にも分子にも含めない**。
AIが返した重要度順に、上限以内へ収まる候補だけを既定選択する。

**短文の例外:** 本文が短く、既存太字だけでは上限未満だが、どの候補も1件だけで上限を超える場合は、
**最重要の1箇所だけ**を例外として選択可能にする。
候補画面と保存確認の両方で変更後の太字率と上限超過を明示し、**2箇所以上の例外保存は認めない**。
既存太字だけで上限以上の場合は例外を認めず追加を止める。
**例外は文だけでなく句・語句でも成立する**ので、画面の文言を「1文」と書かない（→ 判断13）。

### 復旧UI（v1）

起動時の判定（→ §6）で「部分書込 or 外部編集」と出たときだけ、**自動復元せず3択を出す**。

- `現在ファイルを維持`
- `元本文へ復元`
- `元本文を別ファイルへ書き出す`

URIアクセス不能のときは書き出し手段を提示する。

### 候補カードと保存ボタン

- 候補カードは**原文**＋所属見出し＋ノート内位置＋（必要なら直前1文の薄いコンテキスト）＋選択件数/累積上限。
  **指示語を含む文の採否判断を助ける**ため。**保存対象は候補文のみ**（補助文は保存しない）
- **文脈欄は必ず親文の単位で引く**（`contextRange`）。候補が句なら自分の親文、未分割文なら
  **直前の候補単位の親文**。直前の候補の `text` を使うと、直前が分割された文のときに
  **最後の句だけへ縮む**（実機レビューで発生）。**「直前1文」は句ではなく文である。**
- 保存ボタン周りは「選択したN箇所を太字にします」・選択件数・**変更後の簡易プレビュー**・キャンセル
  （既定チェック＋直接編集＋取り消し無しのため）
- **カードに出ている本文が、そのまま `**` で囲まれる文字列である。** 範囲を変えるとこの表示も変わる。
  調整の導線はカードの行タップ（→ 太字にする範囲の調整）

### 太字にする範囲の調整

**「この候補は重要か」と「どこからどこまでを太字にするか」を分ける。**
太字にする位置には個人差があるので、AIは重要箇所のアンカーを探すことに集中し、
**範囲の最終決定はユーザーが持つ**。自動の粒度判定（句分割・語句抽出）は
「操作しなくても保存できる初期値」を作る役へ回る。
**未調整なら従来どおり**チェックして保存するだけで完了する。調整は増える口であって、増える手順ではない。

#### 候補が持つ3つの範囲

| 範囲 | 意味 |
|---|---|
| 文脈範囲 | カードとシートに読ませる親文。**太字にしない**（`DistillSentence.contextRange`） |
| 提案範囲 | 非AI段＋AI選定が出した初期値（`DistillSentence.range`） |
| 確定範囲 | 実際に `**` を挿す範囲。**未調整なら提案範囲と同じ**（`DistillConfirmedRange`） |

**提案範囲を上書きしない。** 上書きすると「最初の範囲に戻す」を実装できず、再計算のたびに初期値が動く。

**画面では「提案」と呼ばない。** AIが選ぶのは候補IDだけで、初期範囲を決めているのは非AIの句・語句分割である
（→ §8 判断5）。**「AIの提案」と書くと、既存の安全契約と食い違う。**

#### 外枠 — 確定範囲は必ず親文の内側

これが「汎用ノート編集機能」との一線である（→ §8 判断15）。外枠を親文にすると、**次の3つが規則を書かずに満たされる**。

| 満たされること | 理由 |
|---|---|
| 既存の `**` 強調と重ならない | 親文は `subtractRanges(bodyStart, bodyEnd, strongSpans)` で既存強調を差し引いた区間から作られる |
| 見出し・コードフェンス・表・frontmatter に触れない | それらの行には親文が存在しない |
| 確定範囲は最大160文字 | 候補の入口が `contextRange.length <= MAX_SENTENCE_CHARACTERS` を見ている |

**外枠は型で表す。** [`DistillConfirmedRange`](../../../app/src/main/java/com/example/newproject/model/DistillModels.kt) が
「文脈範囲の内側」を不変条件として持ち、UIの分岐では守らない。

#### プリセットの3段

**新しい分割規則を作らない。** 3段はすべて `DistillSourceModel.sentences` に既にある要素を引き直すだけで、
v1で確立した境界（記法をまたがない・リンクだけを避ける・鉤括弧の内側で割らない）がそのまま効く。

| 候補の種類 | `語句` | `意味節` | `文全体` |
|---|---|---|---|
| 語句候補（`isTerm`） | 自分 | 自分を含む非語句要素 | 文脈範囲 |
| 句・文の候補 | **提案範囲の内側にある語句要素がちょうど1つのときだけ** | 自分 | 文脈範囲 |

- **同じ範囲になる段は1つに畳む**（割れなかった文では `意味節` と `文全体` が一致する）
- **存在しない段のボタンを出さない。** 押せない選択肢は「なぜ押せないか」の説明を毎回要求する
- **語句が複数あるときに段を出さないのは、どれを指すか決められないから。** 語句は独立候補として一覧に並びうるので、そちらで選ぶ道が残る
- **モデルへ欄を足さない。** 句・語句はすべて `sentences` に平らに入っているので、包含関係だけで引ける

#### 自由範囲 — 端を引いて任意の範囲にする

**プリセットだけでは「この部分だけ」を常には満たせない。** 確定範囲の両端につまみを置き、
親文の内側なら任意の範囲を決められるようにする。

**段は残す。** 1タップで済む一番多い操作なので、**自由範囲は足す口であって置き換えではない。**
どの段とも一致しない範囲へ動かすと、段の印だけが外れる。

- **つまみの近くで始まった押下だけを掴む。** 本文のどこでも掴めるようにすると、
  シートを縦に送ろうとした指が範囲を動かしてしまう
- **描く点と、文字へ当てる点を分ける。** つまみは行の下辺に描くと自然に見えるが、
  **行の下辺は次の行の上辺でもある**ので、その座標をそのまま文字へ当てると次の行として解決される。
  当て先は文字の縦中央に置き、**掴んだ点との差を保ったまま**動かす —
  折り返した親文でつまみを横へ引いただけで範囲が次行へ飛ぶのを防ぐ
- **掴む端は押下の1回で決める。** 引いている途中で近いほうを選び直すと、範囲が潰れる手前で反対の端へ乗り換わり、
  指を動かしていないのに別の端が動き出す
- **端の微調整ボタンを併置する。** 15sp の本文でつまみを引いても書記素1つの精度は出ない。
  スナップと同じ一覧を使うので、**引いて到達できない位置へは微調整でも行けない**
- **UIは寄せ先を知らない。** 送るのは親文の中の位置だけで、置ける位置へ寄せるのは
  [`snapDistillRangeEdge`](../../../app/src/main/java/com/example/newproject/domain/DistillRangeSnap.kt) が決める。
  原文オフセットはUI状態へ出さない（確定範囲を `DistillController.ActiveSession` が持つ理由と同じ）

#### 端を置いてよい位置（スナップ）

**不正な状態を作らせない側に倒す**（→ §8 判断18）。置ける位置を親文ぶん全列挙し、そこからしか選ばない。

**補正手順を重ねない。** 「保護範囲から押し出す」「書記素の切れ目へ寄せる」「端の空白を落とす」を順に当てると、
1つ目の補正が2つ目の禁止域へ落とす形が残り、何度当て直せば収まるかが読めなくなる。
親文は最大160文字なので、全列挙のほうが安く、正しさも読める。

| 置けない位置 | 中身 |
|---|---|
| 書記素の内側 | サロゲートペア・結合文字・異体字セレクタ・ZWJ 連結・肌色修飾子・国旗の対 |
| 保護範囲の内部 | コードスパン・リンク（`[[...]]` / `[](...)`）・斜体 `*…*`・打ち消し線 `~~…~~` |
| **バックスラッシュの直後** | 挿した `**` が `\*` になり、先頭の `*` がエスケープとして消える |
| 端に空白が残る位置 | 開始位置はその文字、終了位置は直前の文字。`trimmedRange` と同じ規則を列挙の段で効かせる |

**バックスラッシュだけは「元の本文に無い並び」を防いでいる。** `C:\Users` の `\U` は記法ではないので、
保護範囲にもエスケープ一覧にも載らない。それでも `U` の前へ `**` を挿すと `\**` が生まれ、
表示側は先頭の `*` を文字として消して残りを斜体の開始として読む。
**守る対象は元の本文ではなく、挿入後に生まれる並びである。**

- **対の内部かどうかではなく、対を割っているかどうかで数える。** 端が一致するだけなら置いてよい
- **向きで倒す先が変わる。** 広げているときは外側の安全境界へ、狭めているときは内側の安全境界へ
  （句分割が「下限未満の余りは直前の句へ吸収する」と向きを固定したのと同じ型の決めごと）
- **向きは指が直前に指していた位置から決める。確定範囲から推測しない。**
  スナップは端を指より先へ送ることがあり、**送った結果で次の向きを判定すると、
  指が止まっていても広げると狭めるが交互に立って端が2点を往復する**。
  指の位置はUIがジェスチャの間だけ覚えて渡す
- **同じ位置を指し直したときは動かさない。** 指が文字の内側で動くだけでも同じ整数offsetが
  続けて届くので、ここが動くと往復の入口になる
- **反対の端を越える位置は候補から除く。** 範囲が潰れる形をスナップの側で作らない
- **既存の `**` 強調はスナップ対象に入れない。** 外枠が親文である限り到達できないので、落ちるテストを書けない
- **`BreakIterator` に寄せない。** 端末とデスクトップJVMで ICU の版が違うと**同じ入力へ別の答えを返し**、
  JVMテストで固定できなくなる。割ってはいけない連結だけを自前で数える

**保護範囲は文書全体ぶんを [`DistillSourceModel.protectedSpans`](../../../app/src/main/java/com/example/newproject/model/DistillModels.kt) が持ち**、
親文に掛かるぶんを二分探索で引く。**候補生成時の `ProtectedCursor` は使えない** —
カーソルは前へ戻れないのに対し、調整は同じ親文を何度も問い直すし、**候補にならなかった位置も指せる**。

#### 重なりの解決

**調整は実行時に重なりを作れる。** v1は選定の出口で候補集合を非重複にしていたので
`applyDistillBold` の `require` に届く経路が無かったが、調整を入れると届く。

| 重なる形 | 起きる条件 |
|---|---|
| 同じ親文の2つの句を、両方 `文全体` にする | `MAX_CLAUSES_PER_SENTENCE = 2` なので1文から句が2つ候補に入りうる |
| 語句候補を広い段や自由範囲へ広げる | 親の内側にいた語句が親と重なる |

**解決:** **選択済み集合を変えるすべての入口**で非重複を維持する。範囲変更だけに置くと、
外された候補を**チェックし直すだけで重なりが復活する**。

| 入口 | 挙動 |
|---|---|
| 選択中の候補の範囲を変えた | 重なる既選択候補の選択を外し、外したことを告げる |
| **未選択**の候補の範囲を変えた | **他候補の選択状態を変えない。** 保存対象でないものの編集が取捨を動かしてはいけない |
| 候補をチェックした | 重なる既選択候補の選択を外す（**最後の明示操作を残す**） |
| 保存直前 | 非重複を検証する。破れていたら保存へ進まない |

**未選択かどうかで呼び出し側が分岐しない。** `resolveOverlaps` は選択集合に居ない候補を優先しても
誰も押し出さないので、Controller側に `isSelected` の分岐を置いても**落ちるテストを書けなかった**（変異で確認）。
契約は純関数側の検査で持ち、等価な分岐を増やさない。

**保存直前の検証は「念のため」ではない。**
[`saveSelection`](../../../app/src/main/java/com/example/newproject/controller/DistillController.kt) は
`applyDistillBold` を **Main で try なしに同期呼び出し**しているので、部分重複は例外ではなく**その場のクラッシュ**になる。
同一範囲なら `distinct()` に畳まれて落ちない代わりに、**画面の選択件数と保存件数が食い違う**
（`Saved.changedCount` は選択数を数える）。**`require` へユーザー操作から到達できない状態にする**のがこの契約の目的である。

#### 重なり解消の告知

**外れる候補はシートの裏にいる。** 範囲を変えている間、影響を受ける候補は画面に見えていない。
一時的な通知（Snackbar）にすると、**見ていない場所の変化を、見ていない間に流す**ことになる。
**状態として残し、対象そのものへ出す。**

| | |
|---|---|
| 何を持つ | 直近の解消で外した候補ID。`DistillState.Candidates` の1欄（`NoteUiState` へ欄を足さない） |
| どこへ出す | ①調整シート内に1行 ②候補一覧の該当カードに印（**チェックが外れた理由がカード側に残る**） |
| 読み上げ | シート内の1行を live region にして、選択が外れたことを読み上げる |
| いつ消える | **次に選択集合か確定範囲が変わったとき。時間で消さない**（見ていない間に消えるものは告知にならない）。**同じ段をもう一度押しても確定範囲は変わらないので消えない** — 同値ガードはController境界に置く |
| 複数外れたとき | 件数で言う。単位は「箇所」 |
| **主語** | **開いている候補との関係で決まる。** 自分が外された側なら「ほか」と呼ばず「この箇所」と言う。外された候補自身のシートも開けるので、件数だけを言うと関係を逆に読ませる |

#### 太字率・短文例外・文言

- `projectedBoldRatio` / `isWithinDistillBoldLimit` は**範囲のコレクションを受ける**ので、
  確定範囲を渡すだけで正しく動く。計算式は変えない
- **範囲を読んでいる箇所を全部付け替える。** 1つでも提案範囲を読み続けると
  「表示は広がったが保存は元の範囲」になり、**未調整のときは同じ出力になるためテストが緑のまま通る**
  （→ [lessons](../lessons.md) L14）
- **短文例外は「どの候補か」を固定したまま、超過判定だけ引き直す。**
  範囲を狭めれば例外が要らなくなり、広げれば例外の説明に出す太字率が変わる
- 文言の単位は「箇所」。**調整シートも `DistillCandidateUnitCopyTest` の走査範囲に入れる**
  （規則は検査に載せたときだけ守られた → [lessons](../lessons.md) L29）

#### 確定範囲の寿命

**シートを閉じても確定範囲は残る。閉じることが確定である。**
破棄の契機は**候補セッションのキャンセル・再解析・ノート切替・保存完了の4つだけ**で、
閉じることは破棄ではない。同じ候補を開き直したら直前に確定した範囲を表示する。

**永続化しない。** ノートに残るのは本文の `**` だけで、サイドカーへ調整履歴を書かない。
**新しいノート単位の状態も増えない**ので、契約2箇所（`cancelNoteScopedJobs()` / `withNoteScopedReset()`）の変更は不要。
調整シートの開閉も `DistillState.Candidates` の中に持つ — 範囲変更は状態を作り直すので、
**開閉情報を同じ更新の中で持ち回らないとシートが落ちる**。

**常駐Vigilithは調整シート表示中も隠す。** 第二の状態を足さず、`DistillState.Candidates` が持つ
シート情報から `resolveVigilithPresentation` が導出する。

### 再蒸留

追加蒸留は未太字文へ太字を**追加**する（累積）。歯止めは累積太字上限。真の多層蒸留はv2。

### UXエッジケース（実装契約）

| 状況 | 挙動 |
|---|---|
| 有効ID 0件 | 再試行 or エラー表示（**ヒューリスティック候補を「AI候補」として出さない**） |
| Nano未対応 | **説明付き無効状態を画面に表示**（機能を隠さず、なぜ使えないかを明示） |
| 未ダウンロード | 明示確認（**自動DLしない**） |
| 他タブへ移動 | バックグラウンド継続＋候補を保持 |
| ノート切替 | ジョブをキャンセルし候補を即破棄（requestIdガード） |
| 競合検知 | **「再解析」を主アクション**に |
| 保存対象0件 | 保存ボタンを無効化 |
| 短文の1箇所例外 | 最重要箇所と変更後太字率を明示し、保存前に再確認 |
| 保存失敗 | 復旧画面へ |

## 6. 状態とデータ

**UI状態:** `DistillState`（`NoteUiState.distillState`）。

**AI待ちの表示状態:** `AI待ち/分析中` / `候補準備完了` / `保存中` / `競合検知` / `保存検証中` / `復旧が必要`。
**「順番待ち」と「分析中」は分離せず1つに統合している**（→ §8 判断2）。

**永続化:** 太字は**ユーザーのノート本文**へ書く。
復旧レコードは **`noBackupFilesDir`**（アプリ内部・バックアップ対象外）に置く（→ §8 判断8）。

### 復旧レコード

| | |
|---|---|
| 内容 | 対象URI / 元本文ハッシュ / 期待書込後ハッシュ / 元本文 / 書き込みフェーズ / 作成日時 |
| 個数 | **未解決レコードは1件のみ。未解決中は他ノートの保存を禁止する** |
| 破損時 | 検知して確認扱いにする |
| 確定方法 | temp書き → **fsync → rename** で原子的に確定 |

**起動時の判定** — 現在ファイルのハッシュで4分岐する。

| 一致するハッシュ | 意味 | 扱い |
|---|---|---|
| 元ハッシュ | 書込前に終了した | 破棄可 |
| 期待ハッシュ | 書込は完了、削除漏れ | 破棄可 |
| どちらとも不一致 | 部分書込 or 外部編集 | **自動復元せず、復旧UI（→ §5）で選択** |
| URIアクセス不能 | — | 書き出し手段を提示 |

**契約2箇所への登録（ノート単位の状態）:** 登録済み。
ノート識別を状態に持ち、`requestId` で切替をガードする（→ §8 判断10）。

**保存後の本文専用リロードで維持／破棄するもの:**

| 維持 | 破棄 |
|---|---|
| 要約・関連・補記の状態とジョブ | **セクションチャット**（実行中ジョブをキャンセル・チャットシートも閉じる） |
| | **セクション由来クイズ** |
| | ノート一覧キャッシュ・関連候補キャッシュ |

```
AiTab

      ├─ buildDistillSourceModel()   ← 原文オフセット保持・Markdown構造認識
      ├─ DistillCandidateScoring     ← 非AI。サリエンス＋構造的重み・チャンク網羅
      ├─ AiClient.generate()         ← AIは1回だけ。文IDを返させる
      ├─ parseDistillResponseIds()   ← 境界付き固定3桁ID・validIds と照合
      └─ DistillWriteRepository
           ├─ DistillRecoveryStore   ← noBackupFilesDir・原子確定
           └─ SAF 一気書き → 検証
```

### 書き込み手順（4段）

**この順序が復旧可能性の全体である。**

1. **キャッシュ構築** — 装飾記号を挿入した完成後ファイルを**アプリキャッシュに生成**し内容ハッシュを検証する
   （文字列操作・OOMの失敗をSAFストリームから隔離する）
2. **復旧レコードを原子確定** — `noBackupFilesDir` へ原子的に確定する。
   **元ノートの truncate はこの確定後にのみ許可する**
3. **SAFへ一気書き** — 検証済みキャッシュ内容を `openOutputStream("wt")` へ流し込む
4. **出力検証** — 再読込し期待出力ハッシュと一致で成功 → 復旧レコード＆キャッシュを破棄する

保存後は**本文専用リロード**でURI・本文・基準ハッシュ（→期待出力ハッシュ）を更新する。
維持／破棄の対象は §6。

## 8. 設計判断と代替案

### 解決したかった問題

Reflect（AIタブ）は要約・質問候補・限定Q&A・クイズまで揃い「理解支援」は充実しているが、
いずれも**AIが説明する／問う**方向で、ノート自身は読み終えても変化しない。
Obsidian中核ワークフロー「再訪のたびに重要点を蒸留してノートを育てる（プログレッシブ要約）」を支える機能が無い。

Reflectの理想を一文で置くと「**ノートの内容を説明するAIではなく、自分の考えをもう一段深くする読書相手**」。

**制約:** オンデバイス（Gemini Nano）は `generate()` が `generateMutex.withLock` で**直列化**され（`AICoreClient`）、
1回あたり最大数十秒。プロンプト入力も先頭固定長。**AI呼び出し回数と入力量を抑える**ことが前提になる。

---

### 判断1: AIは文章を「生成」せず「選ぶ」

本文中の重要文を**抽出（選択）**するだけで新しい文を生成しない。

- **生成文が原文へ混入しない**（出力は原文の部分集合）。
  ※AIが重要でない文を選ぶ**選定ミスは残る**ため「ハルシネーションが原理的に起きない」とは言わない
- 出力が軽くオンデバイス制約に強い
- 書き込むのがユーザー自身の文だけなので心理的安全性が高い

### 判断2: 2段ハイブリッド（ヒューリスティック絞り込み → AI 1回）

非AIで候補を絞ってからAIを1回だけ呼ぶ（経路は §7）。

**効果:** AI呼び出しが**多数回 → 1回**／入力が上限内／候補は全文由来なので**位置ではなく重要度で選べる**／
AIは意味判断に集中できる。

**AI待ちを「順番待ち」と「分析中」に分けなかったのは、`AICoreClient.generate()` が Mutex 取得の前後を
通知しないため**、そもそも区別できないからである。分離には `AiClient` の拡張が要り、
優先度付きスケジューラは過剰と判断した。

### 判断3: 一段目スコア＝サリエンス（タイトル別・直近見出し別）＋構造的重み

**タイトルと直近見出しへの近さで測る**（式と重みは §5）。

**純・文間中心性（TextRank型）は不採用。** 繰り返し現れる一般文が上位に来て、
**1回きりの結論が沈む**ため。計算量も O(N²) になる。

**タイトル類似と直近見出し類似は別々に計算する。** 全見出しを連結すると、
**見出しが増えるほど一つ一つが薄まる**。

**構造的な加点を入れているのは、結論の取りこぼしを安価に防ぐ**目的で、意味解析を避けている。
**長い文を候補から外している**のは、長大な太字化とAI入力予算の占有を避けるため。

**チャンク最低枠は先頭偏りを防ぐためにある。** スコアだけで採ると、
ノート前半のチャンクが候補を占有して後半の結論が入らない。

既存 `rankByScore`（[RelatedCandidateRanking.kt](../../../app/src/main/java/com/example/newproject/domain/RelatedCandidateRanking.kt)）は
採点を委ねる並べ替えの器なので流用し、蒸留の重要度だけを別途定義した。

### 判断4: `DistillSourceModel`＝原文オフセット保持 × Markdown構造認識

`MarkdownBlock`（`Heading/Paragraph/CodeBlock` 等）は**原文オフセットを持たない**ため
`parseMarkdownBlocks` を再利用できない。
→ **原文オフセットを保持したままMarkdown構造を認識する専用トークナイザ**を新設した。

**インラインコードの扱いは当初矛盾していた。** 「コードは除外」と書きながら、
`` **Use `foo` to run.** `` のような**外側からの太字化は成立する**。
そこで除外条件を「コードを含むか」ではなく**「太字の範囲がコードスパンや既存強調を途中でまたぐか」**へ
置き直した（契約は §5）。**またぐときだけ壊れる**、が正確な条件である。

### 判断5: 文ID選択プロトコル＋境界付き緩いIDパーサー

Nanoは前置き（「はい、IDは：S001, S005」）を吐くため**完全一致は期待せず緩く抽出する**。
既存 [RelatedCandidateId.kt](../../../app/src/main/java/com/example/newproject/domain/RelatedCandidateId.kt)（`C\d{1,2}` 抽出）・
`QuizResponseParser`（前置き除去）の実証済みパターンを流用した。

**ただし緩さには境界が要る**（regex は §5）。

- `S\d{3}` 単体だと **`S0012` から `S001` を誤抽出する**
- 後方だけ `(?!\d)` にすると **`S001A` から `S001` を誤抽出する**ため、**前後を対称に英数字禁止**にした

**桁落ちや境界不正を自動補正しないのは、別IDへ誤って解決されるのを防ぐため。**
**黙って違う文を太字にするより、破棄して0件にするほうが安全**という判断である。

### 判断6: 競合検知は SHA-256 を必須にする（TOCTOU残存を明記）

**基準ハッシュはURIから読んだ原バイト列で取る**（UTF-8再エンコードした文字列ではない）。
`lastModified` は補助にとどめる。

**TOCTOU は仕様として受け入れる。** 確認と書き込みの間の外部編集は汎用SAFでは完全に排除できない。
**排除できないものを「対策した」と書かない**ことを優先した。

### 判断7: 書き込み手順＝キャッシュ構築 → 復旧レコード原子確定 → SAF一気書き → 検証

`openOutputStream("wt")` は元ファイルを truncate してから書き直すため**損失窓がある**（手順は §7）。

**窓自体は塞げない。** この手順が改善するのは**「損失を復旧可能にする」ことだけ**であり、
truncate 中の部分状態が Obsidian Sync 等で**他端末へ伝播する可能性は消えない**。
**塞げたと書かない**のがこの判断の要点である。

キャッシュ生成をSAF書き込みから切り離したのは、**文字列操作やOOMの失敗をSAFストリームの外で起こさせる**ため。
ストリームを開いた後に失敗すると、それがそのまま損失窓になる。

**代償として、完成後キャッシュと元本文入り復旧レコードを同時に持つ間だけ内部ストレージが要る**（必要量は §5）。
書き込み前に空き容量を検知して中断する契約を置いたのはこのため。

### 判断8: 復旧レコードは `noBackupFilesDir`・起動時判定・v1最小復旧UI

アプリは `allowBackup="true"`（[AndroidManifest.xml](../../../app/src/main/AndroidManifest.xml)）のため
`noBackupFilesDir` に置く（**自動バックアップ対象になるのを防ぐ**）。
vault の `_AI補記` は用途が違うため使わない。

**「どちらとも不一致」で自動復元しないのは、部分書込と外部編集を区別できないため。**
外部編集を自動で巻き戻すとユーザーの編集を消すことになる。**判断できないときは選ばせる。**

レコードのスキーマと4分岐は §6、3択UIは §5。

### 判断9: 保存後は「本文専用リロード」（`openNote()` を使わない）

`NoteViewModel.openNote()` は `NoteSessionCoordinator.onNoteChanged()` ＋ `fetchSummary()` ＋
`fetchRelatedNotes()` を発火する。流用すると**太字追加だけでAIが2回再生成**され、
再利用可能なノート全体のAI結果まで消える。

**一方で、セクションチャットとセクション由来クイズは破棄しなければならない。**
これらは保存前の生Markdown本文に結び付いており、`**` 挿入後に旧 `sectionContext` を完全一致検索すると
**誤ったセクションへフォールバックする**。

**「ノート全体から作った結果は残せるが、本文の文字位置に依存した結果は残せない」**が分け方の基準である
（維持／破棄の一覧は §6）。

### 判断10: ノート識別を状態に持ち、requestId で切替をガード

`NoteState.Success(title, content)`（[NoteUiState.kt](../../../app/src/main/java/com/example/newproject/model/NoteUiState.kt)）は
**URIもハッシュも持たず、タイトルは非一意**なので、そのままでは「結果が今のノートのものか」を判定できない。

→ URI＋基準ハッシュを状態へ持たせ、生成完了コールバックで現在の identity と照合して捨てる
（PR #31 の全画面遷移×`scrollToItem` と同種の状態不整合を防ぐ）。

### 判断11: 書き込みは「装飾記号の挿入のみ」・ユーザー確定・冪等・frontmatter保護

**「追記のみ」という言い方は不正確だった。** 実際には末尾 append ではなく
**全文を書き直して途中へ `**` を挿入する**。正しくは「**装飾記号の挿入のみ／既存文字を削除しない**」。

確定制と冪等・frontmatter保護の契約は §5。

### 判断13: 粒度は「長文だけ句へ落とす」（判断12の部分的な撤回）

**出発点は「太字が文まるごとで重い」というオーナーの実感**で、判断12 が v1 で切った句単位抽出にあたる。
数値と分割契約は §5、当時の検討過程は git 履歴（`_wip/distill_phrase_granularity.md`）が持つ。

**全文を割らないのが要点。** 一律に割ると、いま良く効いている短文の選定まで細切れになり
「単語まみれ」へ寄る。**閾値を超えた文だけ**を割ることで、困っている一点だけを直せる。

**AIには範囲を返させない。** アプリが非AIで句へ割ってIDを振り、AIはIDを選ぶだけという
判断1・判断5 の契約はそのまま。**句にしても安全性の核は動かない。**

**判定の分配は割った瞬間に生まれる。** 構造ボーナスの4フラグは位置のフラグなので、
全句へ継承すると1文で多重取りになる。**ただし専用の分配は書いていない** —
位置フラグを「グループ内で最初／最後の候補」として数えているため、句が候補単位になると
自動的に先頭句・末尾句だけへ付く。**同じ形で入力上限は自動では効かなかった**（→ 下記）。

**親と子のどちらへ掛けるかを、値の読み手ごとに決め直す。** 1文が複数候補へ割れるようになったとき、
**既存の読み手が子（句）のまま取り残される**型の欠陥が2度出た（いずれも実機レビューで発覚
→ [review](../../review/README.md)）。

| 読み手 | 取り残された形 | 正しい単位 |
|---|---|---|
| 入力上限 | 句長で見るため、読点のある超過文だけが分割後に上限内の断片として復活した | **親文** |
| 候補カードの文脈欄 | 直前候補の `text` を見るため、直前が分割文だと最後の句へ縮んだ | **親文** |

**どちらも既存テストは緑のまま通り抜けた** — 超過文テストは読点を含まず句へ割れず、
文脈テストは「割れた句自身」の片側しか通していなかった。
**構造を変えたら、その値を読む箇所を列挙して、演算ごとに親と子を決める。**

**位置表示は本文の線形構造だけで数える。** 候補カードの `N / total` は文と句を数え、
**語句は線形位置を持たないので、含まれる文・句の位置を借りる。**
内部の候補列には語句が親と重なって並ぶため、その番号をそのまま出すと
**1文しか無いノートで `2 / 5` になる**（実機で発生）。
句だけでは何の断片か読めないため、**文脈欄には親文を出す**（太字にするのは候補範囲のみ）。

**画面の数え方の単位は「箇所」にする。** 候補には文・句・語句が混在するので、
「N文を太字にします」は実際の変更単位と食い違う。**本文を書き換える直前の確認画面**なので、
ここが合っていないと変更範囲を誤認させる。あわせて候補カードには語句だけ種別を1語出す。

**単位に依存した文言は件数だけではない。** 機能説明・開始ボタン・短文例外・保存プレビューも
同じ状態を読んでいる。件数の3箇所を直した変更で**残り4本を取り残し、実機レビューで数え直した**
（→ [lessons](../lessons.md) L14）。文言は型で守れないので `DistillCandidateUnitCopyTest` が走査する。
状態の名前も単位を持たせない（`isSingleCandidateException`・`Saved.changedCount`）。
機能説明と短いノートの例外説明も同じ単位を使い、句や語句を「この1文」と説明しない。

### 判断14: 語句は決定的な括弧内だけを入口にし、重なれば細かい範囲を残す

任意の名詞句は形態素解析が要るため、アプリだけで原文範囲を決定できる鉤括弧の内側から始める。
`〜とは` の定義対象は語の開始位置、コロン前と箇条書きラベルは既存太字との衝突を解けないので採らない。

語句は親文・親句の内側に重なる初めての候補である。変換器は重なる範囲を拒否するため、
**選定の出口で候補を非重複にし、重なれば細かい範囲を残す。** 粒度を細かくする目的と保存安全性を
同じ規則で満たす。同じ表層語句を1件、語句全体を最大2件にするのは、反復語だけで候補枠が埋まるのを防ぐため。
語句は本文の線形構造の位置を占めないので、位置ボーナスと短文ペナルティには参加させない。

### 判断15: 範囲調整の一線は「原文の任意の場所を指せないこと」で引く

**「文字を打てない・消せない」だけでは一線にならない。** それは太字専用エディタの説明であって、
非ゴールが避けたい形そのものになる。**確定範囲を親文の内側に閉じる**ほうを一線にする。

- **採らない案（候補の内側だけ）:** 提案範囲より外へ出せない。最も安全だが、句分割が意味を切ってしまった場合に
  伸ばせず、動機（この部分だけを太字にしたい）の片側しか満たさない
- **採らない案（本文のどこでも）:** 一線を越える側。表示用parserが原文オフセットを持たないため、
  本文全体をオフセット付きで見せる仕組みを新規に作ることにもなる（→ 判断4）

### 判断16: プリセットを先に出し、自由範囲を後から足した

`語句` / `意味節` / `文全体` は既存の分割器の出力を読み替えるだけなので、**安全判定を1つも新規に書かない**。
本文を書き換える唯一の機能で、実機確認の面を一度に広げないために段を分けた。

自由範囲は**保護範囲を候補の外まで持ち回れるようになってから**着手した。
候補生成時の濾過は「候補にならなかった位置」を守らないので、プリセットの安全性はそこへ寄りかかれるが、
自由範囲は寄りかかれない。

- **採らない案（端を1段ずつ動かすボタンだけ）:** プリセットより細かいが、**境界候補の列挙が新規実装**になる。
  自由範囲でスナップを作るなら同じものを二度作ることになるので、**スナップができた後に微調整として併置した**
- **採らない案（最初から自由ドラッグ）:** 最終形へ直行できるが、境界の安全判定・タッチ精度・実機確認が同時に来る

### 判断17: 調整は候補ごとの専用シートで行う

候補一覧はチェックのための場所として保つ。**調整という別の作業を、同じ密度の一覧へ混ぜない。**

- **採らない案（カード内インライン展開）:** 最大6件が縦に並ぶ現在のパネルでカードが伸び、
  AIタブの他パネル（要約・ひとこと）が押し出される
- **採らない案（保存直前のプレビューで調整）:** **本文を書き換える直前の確認画面**に編集操作が同居し、
  確認の役割が薄まる

**シートを閉じることが確定。** 取り消しの口は「最初の範囲に戻す」1つに絞り、
キャンセルボタンを別に置かない（口が2つあると、どちらが効いたか読めなくなる）。

### 判断18: 置けない境界には止まれない（スナップ）

**不正な状態を作らせない側に倒す。** `applyDistillBold` が重なりを `require` で拒み、
IDパーサーが桁落ちを自動補正せず破棄するのと同じ「入口で防ぐ」型に揃える。

- **採らない案（置けるが無効表示にして保存を止める）:** 詰んだ状態を作れるうえ、無効理由の文言が境界の種類だけ増える
- **採らない案（保存時に安全な位置へ丸める）:** 選んだ範囲と保存される範囲が食い違う。
  **唯一の本文書き換え機能で、黙って違う範囲を太字にすることになる**（→ 判断11 と逆を向く）

### 判断19: 重なりは「相手の選択を外す」で解く

**解決を保存時ではなく操作時に置いた**のがこの判断の要点である。保存時に解決すると、
ユーザーが最後に見た画面と保存内容が一致しない。選択を外すだけなので**本文へ書く内容は増えない**。

- **採らない案（重なったまま保存時に弾く）:** どれを直せば解けるか分からない詰みを作る
- **採らない案（保存時に自動でマージする）:** 選んだ範囲と保存範囲が食い違い、「自動補正しない」（判断5）と逆を向く
- **採らない案（重なる操作自体を禁止する）:** 「句を文全体へ広げたい」という最も普通の操作が、
  同じ文の別の句がたまたま候補にいるだけで不能になる
### 判断12: 記法・配置・レイヤーは v1で絞る

`**太字**` を採ったのは**実装ゼロで Obsidian 互換**だから。配置はAIタブの候補リスト、レイヤーは1つ。

## 9. 品質要件

- **データ保護:** **このアプリで唯一ユーザーのノート本文を書き換える**ので、
  復旧レコードと SHA-256 の競合検知が中核。理由は §8 判断6〜8、手順は §7 が持つ
- **性能:** 候補の絞り込みは非AIで、AI呼び出しは1回だけ。**調整でNanoを呼ばない**。
  重なり判定とスナップは親文（最大160文字）ぶんの範囲比較なのでMainで足りる。
  **段の導出だけは `model.sentences` を舐めるので本文の長さに比例する** —
  自由範囲のドラッグは指の動きに合わせて候補状態を作り直すため、
  **セッションを組むときに1度だけ引いて持ち回る**（`DistillRangeRebuildCostTest` が呼び出し回数で固定する）
- **アクセシビリティ:** 段と微調整のボタンは [ui_design_principles](../system/ui_design_principles.md) §1 の
  タッチターゲットとコントラストに従う。**範囲の表示を色だけに依存させない** —
  太字と下線を併用し、微調整の矢印には向きを述べる読み上げ名を付ける
- **プライバシー:** 候補文はプロンプトへ入るが端末外へ出ない（→ [ADR-0002](../decisions/ADR-0002-on-device-ai-only.md)）

## 10. 検証と受け入れ条件

- **JVMテスト:** 候補スコアリング・原文モデル・変換・応答パース・書き込み・復旧・プロンプト・Controller に加え、
  **範囲調整**（3段の導出・重なり解消の両方向・外枠・確定範囲の寿命・保存出力の突き合わせ）と
  **スナップ**（書記素5種・保護範囲・倒す向き・空白・反対の端）を持つ。
  **未調整で v1 と同一出力になることだけでは足りない** — 保存経路が提案範囲を読み続けていても緑のまま通るので、
  **変えた範囲で `**` が入ること**を段と自由範囲の両方で突き合わせる（→ [lessons](../lessons.md) L14）
- **実機確認:** `DIST-01`〜`DIST-20`、括弧内読点、実SAF経路の故障注入4地点と復旧4分岐、
  外部編集競合、保存後状態、最大256KiBをPixel実機で確認済み。復旧UIは原ハッシュ一致・期待ハッシュ一致で
  レコードを無言で解消し、不一致では自動復元せず3択、URIアクセス不能では別ファイル書き出しだけを提示した。
  **装飾の保護は 2026-08-29 に `DIST-20` で確認した** — 装飾の片側だけを含む候補は出ず、保存後も
  斜体・コード・通常リンク・wikilinkの対象文字列と描画が維持され、Obsidian側の見え方も保存前と一致した
- **太字範囲調整（プリセット）:** 2026-08-30に `DIST-21`〜`DIST-24` を4/4確認した。3段の表示・確定範囲の保存・
  重なり解消と告知・シート中のVigilith抑制・外部編集競合が契約どおりで、instrumentationも6/6成功した
- **太字範囲調整（自由範囲）:** 2026-09-20に `DIST-25`〜`DIST-31` を確認した。段に一致しない範囲の保存、
  装飾・絵文字の境界で安全側へ倒れること、バックスラッシュ直後に止まらないこと、指を止めたときに端が動かないこと、
  折り返し行で水平ドラッグが行をまたがないこと、微調整が端で無効化されることが契約どおりだった。
  **実保存22ファイルは、追加した `**` を除いて原文とバイト一致**し、元Vault 927ファイルのハッシュも不変だった
- **保証していない体感:** 指で狙ったときの掴みやすさ・縦送りの手触り・実TalkBackの音声は測っていない。
  実機検証の入力は座標指定なので、**人の指の成功率とは別物**として数える
- **最大サイズ実測:** 一段目685〜904ms、ヒープ増分26,263,552 bytes、キャッシュ262,144 bytes、
  復旧レコード262,422 bytes、管理対象ピーク524,566 bytes、事前空き容量見積851,968 bytes

### 受け入れ条件（v1着手前に確定）

- 変換後から**追加した `**` を除くと原文と完全一致**する
- **frontmatter・見出し・コードフェンス・テーブルが不変**
- **CRLF・BOM・絵文字より後ろの文**も正しい位置へ挿入される
- **既存太字と重なる候補を除外**する
- 同一文が複数箇所にあっても**IDごとの位置だけ**を変更する
- 書き込み各段階で故障注入し、**復旧レコードの4分岐**を検証する
- **外部編集後の保存が必ず競合中断**になる
- 一般文の反復より、**末尾の固有な結論が候補に残る**
- 最大サイズで**一段目処理時間・メモリ・内部ストレージ量**を計測する
- **保存後に要約・関連・補記は維持され、セクションチャット・クイズは破棄**される

### 保証していないこと

- **TOCTOU は残る。** SHA-256 の照合と書き込みの間に外部が書き換える余地がある（→ §8 判断6）
- **選ばれた候補箇所と、ユーザーが決めた範囲の意味的な妥当性を検証していない**
- **調整結果は次回の蒸留へ引き継がれない**（永続化しないため）
- **`_…_` / `__…__` のような、アプリが描画しない Obsidian 記法の保全。**
  `some_var_name` を装飾と誤検出して候補を不当に減らすため、保護の対象にしていない
