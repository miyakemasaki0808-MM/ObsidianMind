**状態:** **実装済み・実機検証待ち（2026-08-23）。** ケースは [reading_trace_backup](../../review/device_validation/reading_trace_backup.md)

## 1. 概要

`_ReadingTraces/*.json` を1ファイルへ書き出し、別端末や再インストール後に読み戻す。
**機能を足す案ではなく、既にあるデータを守る案**である。

**なぜ要るか。** アプリは「記憶をAIに持たせない」設計を選び、記憶の実体を
[`ReadingTrace`](reflect_reading_trace.md) のサイドカーとノートの太字（[蒸留](reflect_distill.md)）へ置いた。
**その裏返しとして、記憶はアプリの外にしか無い。** Vaultのフォルダが消えれば一緒に消える。

**2026-08-09 に性質が変わった。** それまで痕跡の中身は訪問履歴とAI生成物だけで、
失っても読み直せば再生成できた。[ひとことへの返事](reflect_remark.md)が入った時点で、
**再生成できないユーザー自身の言葉**が痕跡に入るようになった。

## 2. ゴールと非ゴール

### ゴール

- 痕跡を1ファイルへ書き出し、別端末・再インストール後に読み戻せる
- 書き出しの過程で、壊れた／読めない痕跡を検出して報告する
- **再生成できないもの（`visits` と `Reflection.reply`）を、読み戻しで黙って失わない**

### 非ゴール

- **保存失敗時のアプリ内回復ファイルは含めない。** 「書き込みに失敗した返事がプロセスメモリにしか無い」
  という穴は実在するが、**外部での喪失（フォルダ削除・端末移行）とプロセス断は穴の性質が違う**。
  同時に扱うと書き込み経路が増え、実機検証の面が広がる。別途扱う。
- **自動バックアップは持たない。** 走らせるのはユーザーの明示操作だけ（→ §8 判断3）。
- **ノートの move/rename への追従は行わない。** 痕跡のキーは相対パスなので、
  移動したノートの痕跡は別物として扱われる（→ [reflect_reading_trace](reflect_reading_trace.md) 判断7）。
- **暗号化しない。** 書き出したファイルには読書履歴と返事が平文で入る。守り方は置き場所の選択で扱う。

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| エクスポート | 保存先を選ぶと、Vault内の全痕跡が1ファイルへ書き出される。読めなかった件数を報告する | 明示ボタン |
| インポート | ファイルを選ぶと、痕跡が復元される。上書き・追加・保留の件数を報告する | 明示ボタン |
| 整合性の報告 | 書き出し時に、壊れて読めなかった痕跡を件数と**ファイル名**で示す | エクスポートに付随 |

> **報告できるのはファイル名までで、ノート名でも相対パスでもない。** 壊れていて中身を
> 読めていないうえ、痕跡のファイル名は相対パスの SHA-256 なので逆に辿れない。
> ファイル名なら `_ReadingTraces/` の中で現物へ辿り着けるので、そこを出す。

## 4. 現在のユーザーフロー

**エクスポート**

1. オプション →「データ管理」で「書き出す」を押す
2. SAF の保存先選択が開く。**既定はVault外**（→ §8 判断2）
3. 全痕跡を列挙して読み、1ファイルへ書き出す。**進捗と中止を出す**
4. 完了時に「N件を書き出した／M件は読めなかった」を示す

**インポート**

1. 「読み戻す」を押し、退避ファイルを選ぶ
2. 版を確認する。読めない版なら、その旨を示して中止する
3. **下見**（書かずに数えるだけ）を出す。「新規N件／合わせるM件／**返事が置き換わるK件**」
4. ユーザーが確定したら、痕跡ごとに突き合わせ規則（§5）を当てて書き込む
5. 完了時に「新規N件／マージM件／保留K件」を示す。保留は一覧で見せる

> **下見と確定を分けるのは、読み戻しが不可逆だから。** 先に見せるのは件数ではなく
> **失われるもの**（置き換わる返事の数）で、そこへ最初に答える。

## 5. 機能仕様

- **前提条件:** Vaultが選択されていること。`_ReadingTraces` が作成・列挙できること
- **入力と出力:** 入力は Vault内の全痕跡（エクスポート）／退避ファイル1つ（インポート）。
  出力は退避ファイル1つ／更新された痕跡群
- **上限:** 1痕跡あたりのバイト上限は既存の `ReadingTraceJson` の制約に従う。
  退避ファイル全体は **5,000件かつ8MB**（`ReadingTraceBackupLimits`）。
  **件数とバイト数の両方を持つ**のは、片方だけでは効かない相手がいるため —
  巨大な返事を持つ少数の痕跡はバイト側で、小さい痕跡が大量にある場合は件数側で止まる。
  読み込み側では**アプリの管理外のファイルに対する防壁**も兼ねる
- **状態遷移:** 待機 → 実行中（進捗）→ 完了／失敗／中断
- **保存と寿命:** 退避ファイルはアプリの管理外。作った後の寿命はユーザーが持つ
- **画面遷移:** 専用画面（オプション →「データ管理」）。Rediscover→Reflect のループとは別軌道に置く（→ 判断5）
- **他機能との連携:** 整合性の検査と孤児の掃除は `ReadingTraceCleanupController` が持つ。**重複させない**
- **エラー／キャンセル時:** Vault単位の機能なので、無効化の契機は Vault切替だけ。
  ノート単位の契約へは登録しない（→ [architecture](../system/architecture.md) 判断2・4）

### 突き合わせ規則（インポートの本体）

**同じノートの痕跡が端末側と退避側の両方にあるとき、欄ごとにマージする。**

| 欄 | 規則 | 理由 |
|---|---|---|
| `visits` | 時刻で重複排除して結合し、直近30件を残す | 両方で読み進めても履歴が残る |
| `totalVisitCount` | **大きい方を採る** | 累計は保持件数と別に数えているためマージ後の件数から復元できない。足すと重複を二重計上する |
| `reflection` | **返事を持つ側を優先。** 両方が持つなら `repliedAt`（無ければ `remarkedAt`）が新しい方 | 1ノート1組でマージできない。**再生成できないユーザーの言葉を最優先で守る** |
| `aiSummary` / `aiSummaryVisitCount` / `aiSummaryKind` | 採用後の `totalVisitCount` と噛み合わなければ**3つまとめて捨てる** | 訪問履歴から再生成できるので、捨てても失うものが無い。**種別だけ残すと、内容の無い前置きが出る** |
| `markedAtEpochMillis` / `markedSummary` / `markedKind` | **印を持つ側を優先。** 両方が持つなら `markedAtEpochMillis` が新しい方。**3つまとめて動かす** | **`aiSummary` の一族に見えるが、捨ててはいけない側。** 下記参照 |
| `documentId` | **端末側を保つ。退避ファイルには最初から書かない** | 端末／権限グラントごとに変わる高速引き当てキャッシュで、別端末はもちろん**同じ端末の再インストール後でも無効**。checksum の対象外。しかも SAF の documentId には端末内のパスが入るので、**平文で外へ出すファイルへ載せる理由が1つも無い**（書き出しで落とせば、読み戻し側の規則にも自動的に沿う） |
| `noteTitle` | 採用した `reflection` 側に揃える | 表示名だけなので、対話と食い違わない側に寄せる |

**同点はすべて端末側が勝つ。** いま使っている側を理由なく動かさないため。

**退避ファイルの中に同じノートの痕跡が2件あったら、捨てずに畳む。** 手で結合された
退避ファイルがこの形になり、片方を落とすと返事を失う。畳み方は上の表と同じ規則
（`mergeReadingTraces` をそのまま適用する）。

> **`reflection` の規則は直感とずれる場合がある。** 古い返事が新しいひとことを上回るため、
> 「新しい方が残る」と期待した利用者には意外に映る。**それでもこちらを採る** —
> ひとことは本文から再生成できるが、返事は二度と作れない。

> **`marked*` を `aiSummary` の一族として扱わない。** 名前も置き場所も似ているうえ、
> `markedSummary` に入るのは**AIが書いた文**なので、「AI要約系だから捨ててよい」に吸い込まれやすい。
> **だが作り直せない。** 印は*その内容*への意図なので、生成し直すと別の文が出て意図とずれる
> （→ [reunion_card](reunion_card.md) §6）。**性質としては `reflection` と同じ「守る側」**であり、
> 捨てると「まだ考えたいと押したのに、次の再会で普通の要約が出た」が起きる。
> **再生成できないユーザーの意図を最優先で守る**という本項の原則が、そのまま当てはまる。

## 6. 状態とデータ

**Vault単位の機能なので、ノート単位の契約2箇所へは登録しない。** 世代は `vaultGeneration` を使う
（→ [architecture](../system/architecture.md) 判断4）。

**退避ファイルは版を持つ。** 痕跡のスキーマは現に上がり続けており（現行 v6、読めるのは v1〜v6）、
版の無い形式で書き出すと、拡張したときに古い書き出しを読めなくなる。
**退避形式の版は痕跡のスキーマ版とは別に持つ** — 束ね方が変わっても中身の版は変わらないため。

**書き出しは decode してから現行版で再encode する。** 生バイトをそのまま束ねると、
壊れたファイルもそのまま運んでしまい、「読めないものを検出する」というゴールと噛み合わない。
`ReadingTraceJson` の checksum は**書かれた版の正規形**で照合されるので、
decode は版を跨いで正しく効き、再encode で版が揃う。

## 7. システム設計

```
DataManagementScreen（データ管理・→ 判断5）
 └── ReadingTraceBackupController（Vault単位・vaultGeneration・SAF I/O は ioDispatcher へ）
      ├── ReadingTraceStore.listKeys() / loadByKey() / load() / save()  ← 列挙と読み書き（既存）
      ├── ReadingTraceJson.encode() / decode()          ← 版と checksum（既存）
      ├── ReadingTraceBackupJson.encode() / decode()    ← 束ね方（新規・data）
      ├── mergeReadingTraces()（domain・純関数）        ← 突き合わせ規則（新規）
      └── NoteViewModel → SAF createDocument / openInputStream  ← 保存先の選択（既存）
```

**新規は3つだけ** — 退避形式の組み立てと解釈、`mergeReadingTraces()`、専用画面。
**列挙・読み出し・版管理・checksum・孤児検査はすべて既存**で、作り直さない。

**`mergeReadingTraces()` は `domain` に置いて Android 非依存にする。** 突き合わせ規則はこの機能で最も
壊れやすく、かつ最も検証が要る部分なので、JVMテストで固定できる形にする
（→ [architecture](../system/architecture.md) 判断3）。

**Controller は `Uri` を扱わない。** 保存先・読み込み元の解決は `NoteViewModel` が持ち、
Controller へは `write: suspend (ByteArray) -> Unit` と `read: suspend () -> ByteArray` として渡す。
蒸留の元本文書き出しと同じ形で、`controller` を Android 非依存に保つ規律
（→ [architecture](../system/architecture.md) 判断5）。

**痕跡の read-modify-write は、訪問の追記と同じ錠で直列化する。** 読み戻しの適用は
「端末側を読む → 突き合わせる → 書く」で、`ReadingTraceController` の訪問追記と
まったく同じ形をしている。錠をクラスごとに持つと、**保存先を選ぶあいだにアプリが背面へ回って
訪問が書き出された**ときに読み取りが古いまま上書きし、そのノートの読み戻しが黙って効かなくなる。
錠は `NoteSessionCoordinator` が1つ作って両方へ配り、**握るのは1件ぶんだけ**にする
（まとまり全体で握ると、適用中は訪問の書き出しが止まる）。

**I/O は25件ずつまとめて渡す。** 1件ずつ `withContext` すると遠いプロバイダで切替コストが
件数分載り、全件を1回で渡すと進捗も中断も出せない。**進捗の粒度とI/Oの粒度は同じ数字で決まる。**

## 8. 設計判断と代替案

### 判断1: 衝突は欄ごとにマージする

採らなかった案は3つ。**丸ごと上書き**は規則が最も単純だが、古い側の訪問履歴と返事がまとめて消える。
**衝突を取り込まず一覧で見せる**は何も失わないが、両方で読み進めた場合に手当てが要る。
**1件ずつユーザーが選ばせる**は件数が多いと現実的でなく、確認UIの規模が本体を上回る。

欄ごとのマージを採るのは、**失う可能性のある欄が `reflection` だけに絞られる**ためである。
`visits` は結合でき、`totalVisitCount` は規則で決まり、`aiSummary` は再生成できる。

### 判断2: 既定はVault外。Vault内も選べる

書き出したファイルには読書履歴と返事が平文で入る。**Vault内に置くと Obsidian の同期経路に乗り、
クラウドへ渡る。** したがって既定は Vault外とし、ユーザーが都度保存先を選ぶ
（[プロンプトログの設計](../system/ai_input_excerpt.md)と同じく「外へ出すなら都度ユーザーが選ぶ」）。

同期で別端末へ運びたい要求も実在するので、Vault内も選べるようにする。
**`_ReadingTraces/` の中へ置いても壊れないことは既定のファイル名の長さで担保している**
（→ §11 の最初の決めごと1）。

### 判断3: 走らせるのは明示ボタンだけ

自動バックアップは「保存先を固定して権限を持ち続ける」ことを要求し、**都度選ぶ形と両立しない**。
返事を書いた直後に走らせる案は最も失いにくいが、書くたびに SAF 書き込みが走り、読書の流れを止める。
**忘れれば守られない**という弱点は受け入れる。

### 判断4: 保存失敗時の回復ファイルは含めない

「アプリが落ちれば書けなかった返事が消える」穴は実在し、[蒸留](reflect_distill.md)が
復旧レコードで同じ問題を解いている。**それでも同時にやらない** — 外部での喪失とプロセス断は
穴の性質が違い、同時に扱うと書き込み経路が増えて実機検証の面が広がる。

### 判断5: 単独の画面を建てず「データ管理」へ統合する

**着手時に一緒に決める申し送りがあった判断**（→ current_issues の「AI補記メモ削除が
移行専用の単発後片付けUIのまま常設されている」）。オプション直下に
「痕跡を書き出す」を並べると、既にある「AI補記メモを削除」「読書痕跡を整理」と合わせて
**設定の第一階層に片付け系が3つ並ぶ**ことになり、直後に統合を求められる。

3つはどれも「**アプリが管理している非表示データを人間が扱えるようにする**」という
同じ性質を持つ一方、**寿命が違う** — 旧補記の片付けは移行が済めば価値を失うが、
退避と整理は残る。同列に並べると、移行済みの利用者に無用な選択肢が見え続ける。

したがって「データ管理」1画面を作り、**退避を本体**（この画面にしか無い操作）、
整理と旧補記の片付けを**その下の行**として置く。退避を上にするのは、
失われうるものを守る操作のほうが掃除より先に要るため。

**旧補記の片付けを条件表示（ファイルが存在する場合だけ出す）にはしない。** 表示の可否を
決めるためだけに画面を開くたび SAF の列挙が要るうえ、統合によって
「常設の第一階層に無用な選択肢が残る」という問題自体は解けている。

## 9. 品質要件

- **プライバシー:** 退避ファイルは平文。既定でVault外へ出し、同期経路へ自動で乗せない
- **データ保護:** インポートは不可逆。**実行前に「何件が上書きされるか」を示してから確定させる**
- **性能:** 列挙と読み出しは SAF I/O なので `ioDispatcher` へ逃がす。
  遠いプロバイダ（Google Drive等）では痕跡の件数だけIPCが要るため、進捗と中断を持つ
- **オフライン・端末制約:** AIを使わないので Nano 非対応端末でも完全に動く

## 10. 検証と受け入れ条件

- **JVMテスト（実装済み）:** `ReadingTraceMergeTest` が突き合わせ規則の全項目を持つ。とくに
  ①両方に返事があるとき新しい方が残る ②片方だけ返事があるとき古くても残る
  ③`totalVisitCount` が大きい方になる ④`aiSummary` が噛み合わないとき3つまとめて捨てられる
  ⑤`documentId` が端末側のまま保たれ、新規受け入れでは落ちる
  ⑥マージ結果が `validateReadingTrace` を通る。
  `ReadingTraceBackupJsonTest` が束ね方（別形式・新しすぎる版をファイルごと止める／
  壊れた1件を数える／`documentId` を書き出さない）を持つ。
  `ReadingTraceBackupControllerTest` が結線（列挙失敗を空の退避ファイルへ畳まない／
  下見が1件も書かない／下見後のVault切替で書かない／中断の報告が実際に書けた件数と揃う）を持つ。
- **変異確認（実施済み）:** `withVaultScopedReset()` から `readingTraceBackupState` の登録を外すと
  `NoteSessionCoordinatorTest` の2件が落ちる。**登録漏れが検出されることを確かめてある。**
- **instrumentation:** **持たない。** 退避の往復は SAF の保存先選択を伴うので、
  端末テストからは操作できない。往復そのものは JVM テストが `encode`→`decode` で見ており、
  SAF 側は実機ケースが受け持つ。
- **実機確認:** 保存先の選択（Vault外／Vault内）、読めない痕跡がある状態での書き出し、
  衝突がある状態での読み戻し、走行中のVault切替で結果が捨てられること
  → [実機ケース](../../review/device_validation/reading_trace_backup.md)
- **保証していないこと:**
  - **move/rename したノートの痕跡は引き当てない。** キーが相対パスのため別物として扱う
  - **退避ファイルの改竄は検出しない。** checksum は各痕跡の整合性だけを見る
  - **アプリが落ちた瞬間に書けなかった返事は救わない**（→ 判断4）

## 11. 既知の制約・未解決事項

### 最初の決めごと（2026-08-23 に確定）

1. **退避ファイルは `_ReadingTraces/` の中でも「64文字未満の名前」なら安全。**
   `ReadingTraceStore` の索引はフォルダ内の**全ファイルの先頭64文字をキーとして解釈する**が、
   **64文字に満たない名前は索引に載せない**（`key.length == 64` を要求している）。
   既定のファイル名は `vigilith_traces_yyyyMMdd.json`（29文字）なので、そのまま
   `_ReadingTraces/` へ保存されても痕跡として索引に載らず、孤児スキャンの削除候補にも出ない。
   **長い名前へ変えるとこの前提が消える**ので、`ReadingTraceBackupTextTest` が長さを固定している。
   ユーザーがピッカーで64文字以上へ改名した場合は防げないため、Vault外を勧める案内は残す。
2. **退避ファイル全体の上限は5,000件かつ8MB。** 件数とバイト数の両方を持つ（→ §5「上限」）。
3. **読めない版を渡されたときは全体を中止する。** 版が新しすぎる退避ファイルは部分的に読まない
   （部分適用は不可逆な操作を中途半端に残すため）。**個々の痕跡が壊れている場合は別扱い**で、
   その1件だけを保留にして残りは適用する（束ね方は正しいので、全体を止める理由が無い）。

### 制約

- **1ノート1組の `reflection` は構造上マージできない。** 両方に返事があれば必ず片方が消える。
  規則で決まるのは「どちらを残すか」までで、失われること自体は避けられない
- **`totalVisitCount` は厳密には復元できない。** 大きい方を採る規則は過小になりうる
- **読み戻しても、いま画面に出ている再会カードは更新されない。** カードは開いた時点の痕跡から
  作られており、読み戻しはファイルを書き換えるだけだから。**データは失われない**
  （次にそのノートを引き当てれば読み戻した内容が出る）が、直後に確かめようとすると
  古い内容が見える。読み戻しを読書の流れの外＝データ管理画面へ置いているのはこのためでもある
- **書き出しに失敗すると、保存先に0バイトのファイルが残る。** SAF は保存先を確定した
  時点でファイルを作るので、その後の失敗（痕跡の列挙に失敗した・どれも読めなかった）を
  こちらから取り消せない。**予見できる失敗＝Vault未選択はボタンを押せなくして塞いである**が、
  残りは塞げない。作ったファイルを消す案は採らない — ピッカーで既存ファイルを
  選び直した場合に**ユーザーのファイルを消し得る**
- **中断の報告は実際に書けた件数と最大1件ずれる。** 数えるのは書いた後なので、
  **書けていないものを「適用した」と言うことはない**（少なく報告する側へ倒してある）
