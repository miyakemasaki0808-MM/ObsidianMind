## 1. 概要

`_ReadingTraces/*.json` を1ファイルへ書き出し、別端末や再インストール後に読み戻す。
**機能を足す案ではなく、既にあるデータを守る案**である。

**なぜ要るか。** アプリは「記憶をAIに持たせない」設計を選び、記憶の実体を
[`ReadingTrace`](reflect_reading_trace.md) のサイドカーとノートの太字（[蒸留](reflect_distill.md)）へ置いた。
**その裏返しとして、記憶はアプリの外にしか無い。** Vaultのフォルダが消えれば一緒に消える。

**2026-08-09 に性質が変わった。** それまで痕跡の中身は訪問履歴とAI生成物だけで、
失っても読み直せば再生成できた。[ひとことへの返事](reflect_remark.md)が入った時点で、
**再生成できないユーザー自身の言葉**が痕跡に入るようになった。

## 2. ゴールと非ゴール

### ゴール

- 痕跡を1ファイルへ書き出し、別端末・再インストール後に読み戻せる
- 書き出しの過程で、壊れた／読めない痕跡を検出して報告する
- **再生成できないもの（`visits` と `Reflection.reply`）を、読み戻しで黙って失わない**

### 非ゴール

- **保存失敗時のアプリ内回復ファイルは含めない。** 「書き込みに失敗した返事がプロセスメモリにしか無い」
  という穴は実在するが、**外部での喪失（フォルダ削除・端末移行）とプロセス断は穴の性質が違う**。
  同時に扱うと書き込み経路が増え、実機検証の面が広がる。別途扱う。
- **自動バックアップは持たない。** 走らせるのはユーザーの明示操作だけ（→ §8 判断3）。
- **ノートの move/rename への追従は行わない。** 痕跡のキーは相対パスなので、
  移動したノートの痕跡は別物として扱われる（→ [reflect_reading_trace](reflect_reading_trace.md) 判断7）。
- **暗号化しない。** 書き出したファイルには読書履歴と返事が平文で入る。守り方は置き場所の選択で扱う。

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| エクスポート | 保存先を選ぶと、Vault内の全痕跡が1ファイルへ書き出される。読めなかった件数を報告する | 明示ボタン |
| インポート | ファイルを選ぶと、痕跡が復元される。上書き・追加・保留の件数を報告する | 明示ボタン |
| 整合性の報告 | 書き出し時に、壊れて読めなかった痕跡を件数と相対パスで示す | エクスポートに付随 |

## 4. 現在のユーザーフロー

**エクスポート**

1. 設定の奥（棚卸し軸の画面）で「痕跡を書き出す」を押す
2. SAF の保存先選択が開く。**既定はVault外**（→ §8 判断2）
3. 全痕跡を列挙して読み、1ファイルへ書き出す
4. 完了時に「N件を書き出した／M件は読めなかった」を示す

**インポート**

1. 「痕跡を読み戻す」を押し、退避ファイルを選ぶ
2. 版を確認する。読めない版なら、その旨を示して中止する
3. 痕跡ごとに突き合わせ規則（§5）を当てて書き込む
4. 完了時に「新規N件／マージM件／保留K件」を示す。保留は一覧で見せる

## 5. 機能仕様

- **前提条件:** Vaultが選択されていること。`_ReadingTraces` が作成・列挙できること
- **入力と出力:** 入力は Vault内の全痕跡（エクスポート）／退避ファイル1つ（インポート）。
  出力は退避ファイル1つ／更新された痕跡群
- **上限:** 1痕跡あたりのバイト上限は既存の `ReadingTraceJson` の制約に従う。
  退避ファイル全体の上限は着手時に決める（→ §11）
- **状態遷移:** 待機 → 実行中（進捗）→ 完了／失敗／中断
- **保存と寿命:** 退避ファイルはアプリの管理外。作った後の寿命はユーザーが持つ
- **画面遷移:** 専用画面。Rediscover→Reflect のループとは別軌道に置く
- **他機能との連携:** 整合性の検査と孤児の掃除は `ReadingTraceCleanupController` が持つ。**重複させない**
- **エラー／キャンセル時:** Vault単位の機能なので、無効化の契機は Vault切替だけ。
  ノート単位の契約へは登録しない（→ [architecture](../system/architecture.md) 判断2・4）

### 突き合わせ規則（インポートの本体）

**同じノートの痕跡が端末側と退避側の両方にあるとき、欄ごとにマージする。**

| 欄 | 規則 | 理由 |
|---|---|---|
| `visits` | 時刻で重複排除して結合し、直近30件を残す | 両方で読み進めても履歴が残る |
| `totalVisitCount` | **大きい方を採る** | 累計は保持件数と別に数えているためマージ後の件数から復元できない。足すと重複を二重計上する |
| `reflection` | **返事を持つ側を優先。** 両方が持つなら `repliedAt`（無ければ `remarkedAt`）が新しい方 | 1ノート1組でマージできない。**再生成できないユーザーの言葉を最優先で守る** |
| `aiSummary` / `aiSummaryVisitCount` | 採用後の `totalVisitCount` と噛み合わなければ捨てる | 訪問履歴から再生成できるので、捨てても失うものが無い |
| `documentId` | **端末側を保つ** | 端末／権限グラントごとに変わる高速引き当てキャッシュで、別端末の値は無効。checksum の対象外 |
| `noteTitle` | 採用した `reflection` 側に揃える | 表示名だけなので、対話と食い違わない側に寄せる |

> **`reflection` の規則は直感とずれる場合がある。** 古い返事が新しいひとことを上回るため、
> 「新しい方が残る」と期待した利用者には意外に映る。**それでもこちらを採る** —
> ひとことは本文から再生成できるが、返事は二度と作れない。

## 6. 状態とデータ

**Vault単位の機能なので、ノート単位の契約2箇所へは登録しない。** 世代は `vaultGeneration` を使う
（→ [architecture](../system/architecture.md) 判断4）。

**退避ファイルは版を持つ。** 痕跡のスキーマは現に上がり続けており（現行 v5、読めるのは v1〜v5）、
版の無い形式で書き出すと、拡張したときに古い書き出しを読めなくなる。
**退避形式の版は痕跡のスキーマ版とは別に持つ** — 束ね方が変わっても中身の版は変わらないため。

**書き出しは decode してから現行版で再encode する。** 生バイトをそのまま束ねると、
壊れたファイルもそのまま運んでしまい、「読めないものを検出する」というゴールと噛み合わない。
`ReadingTraceJson` の checksum は**書かれた版の正規形**で照合されるので、
decode は版を跨いで正しく効き、再encode で版が揃う。

## 7. システム設計

```
専用画面
 └── ExportImportController（Vault単位・vaultGeneration・SAF I/O は ioDispatcher へ）
      ├── ReadingTraceStore.listKeys() / loadByKey()   ← 列挙と読み出し（既存）
      ├── ReadingTraceJson.encode() / decode()          ← 版と checksum（既存）
      ├── mergeTraces()（domain・純関数）               ← 突き合わせ規則（新規）
      └── SAF createDocument / openInputStream          ← 保存先の選択（既存）
```

**新規は3つだけ** — 退避形式の組み立てと解釈、`mergeTraces()`、専用画面。
**列挙・読み出し・版管理・checksum・孤児検査はすべて既存**で、作り直さない。

**`mergeTraces()` は `domain` に置いて Android 非依存にする。** 突き合わせ規則はこの機能で最も
壊れやすく、かつ最も検証が要る部分なので、JVMテストで固定できる形にする
（→ [architecture](../system/architecture.md) 判断3）。

## 8. 設計判断と代替案

### 判断1: 衝突は欄ごとにマージする

採らなかった案は3つ。**丸ごと上書き**は規則が最も単純だが、古い側の訪問履歴と返事がまとめて消える。
**衝突を取り込まず一覧で見せる**は何も失わないが、両方で読み進めた場合に手当てが要る。
**1件ずつユーザーが選ばせる**は件数が多いと現実的でなく、確認UIの規模が本体を上回る。

欄ごとのマージを採るのは、**失う可能性のある欄が `reflection` だけに絞られる**ためである。
`visits` は結合でき、`totalVisitCount` は規則で決まり、`aiSummary` は再生成できる。

### 判断2: 既定はVault外。Vault内も選べる

書き出したファイルには読書履歴と返事が平文で入る。**Vault内に置くと Obsidian の同期経路に乗り、
クラウドへ渡る。** したがって既定は Vault外とし、ユーザーが都度保存先を選ぶ
（[プロンプトログの設計](../system/ai_input_excerpt.md)と同じく「外へ出すなら都度ユーザーが選ぶ」）。

同期で別端末へ運びたい要求も実在するので、Vault内も選べるようにする。
**ただし `_ReadingTraces/` の中には置けない**（→ §11 の最初の決めごと）。

### 判断3: 走らせるのは明示ボタンだけ

自動バックアップは「保存先を固定して権限を持ち続ける」ことを要求し、**都度選ぶ形と両立しない**。
返事を書いた直後に走らせる案は最も失いにくいが、書くたびに SAF 書き込みが走り、読書の流れを止める。
**忘れれば守られない**という弱点は受け入れる。

### 判断4: 保存失敗時の回復ファイルは含めない

「アプリが落ちれば書けなかった返事が消える」穴は実在し、[蒸留](reflect_distill.md)が
復旧レコードで同じ問題を解いている。**それでも同時にやらない** — 外部での喪失とプロセス断は
穴の性質が違い、同時に扱うと書き込み経路が増えて実機検証の面が広がる。

## 9. 品質要件

- **プライバシー:** 退避ファイルは平文。既定でVault外へ出し、同期経路へ自動で乗せない
- **データ保護:** インポートは不可逆。**実行前に「何件が上書きされるか」を示してから確定させる**
- **性能:** 列挙と読み出しは SAF I/O なので `ioDispatcher` へ逃がす。
  遠いプロバイダ（Google Drive等）では痕跡の件数だけIPCが要るため、進捗と中断を持つ
- **オフライン・端末制約:** AIを使わないので Nano 非対応端末でも完全に動く

## 10. 検証と受け入れ条件

- **JVMテスト:** `mergeTraces()` の全規則。とくに
  ①両方に返事があるとき新しい方が残る ②片方だけ返事があるとき古くても残る
  ③`totalVisitCount` が大きい方になる ④`aiSummary` が噛み合わないとき捨てられる
  ⑤`documentId` が端末側のまま保たれる
- **instrumentation:** 退避ファイルの書き出しと読み戻しの往復で内容が保存されること
- **実機確認:** 保存先の選択（Vault外／Vault内）、読めない痕跡がある状態での書き出し、
  衝突がある状態での読み戻し、走行中のVault切替で結果が捨てられること
- **保証していないこと:**
  - **move/rename したノートの痕跡は引き当てない。** キーが相対パスのため別物として扱う
  - **退避ファイルの改竄は検出しない。** checksum は各痕跡の整合性だけを見る
  - **アプリが落ちた瞬間に書けなかった返事は救わない**（→ 判断4）

## 11. 既知の制約・未解決事項

### 最初の決めごと（着手前に確定させる）

1. **退避ファイルを `_ReadingTraces/` の中に置いてはいけない。**
   `ReadingTraceStore` の索引はフォルダ内の**全ファイルの先頭64文字をキーとして解釈する**ため、
   退避ファイルが痕跡として索引に載り、孤児スキャン（`traceKeys - noteKeys`）で削除候補に出る。
   Vault内へ置く場合は**別フォルダ**にする。
2. **退避ファイル全体のサイズ上限。** 1痕跡あたりの上限は既存だが、束ねた全体の上限は無い。
   痕跡はノート数に比例するので、決めないと大きなVaultで破綻する。
3. **読めない版を渡されたときの止め方。** 版が新しすぎる退避ファイルは部分的に読まず、
   **全体を中止する**（部分適用は不可逆な操作を中途半端に残すため）。

### 制約

- **1ノート1組の `reflection` は構造上マージできない。** 両方に返事があれば必ず片方が消える。
  規則で決まるのは「どちらを残すか」までで、失われること自体は避けられない
- **`totalVisitCount` は厳密には復元できない。** 大きい方を採る規則は過小になりうる
