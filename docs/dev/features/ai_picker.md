# さがす（AIピッカー・閲覧履歴）

**状態:** Implemented — 稼働中
**最終検証:** 2026-08-11 / `c25bcea`（フォールバック仕様・上限3種・世代照合を実装から起こし直した。**旧ヘッダにあった乖離1件は解消**）
**関連コード:** `controller/SearchController.kt` / `domain/SearchPickerUseCase.kt` / `domain/SearchKeywordMatching.kt` / `data/NoteHistoryStore.kt` / `ui/screen/SearchScreen.kt`
**関連テスト:** `SearchControllerTest` / `SearchKeywordMatchingTest`
**正本:** この文書

**対象領域:** ノートを見つける導線（フォルダ選択・キーワード検索・スコープ内ランダム・当日履歴）

---

## 1. 概要

Rediscover（純粋ランダム）だけでは**意図を持って探せない**。
このタブは「**フォルダで絞ってから探す**」という別の引き方を提供する。

**探索範囲を人間が絞る**ことが設計の中心で、そのうえで
🔎キーワード（Nano が3件選ぶ）と 🎰ランダム（AI不使用で3件）の2モードが乗る。

> **Rediscover の純粋ランダムには混ぜない。** ここは**別の引き方**であって、
> ランダムに条件を足したものではない。

## 2. ゴールと非ゴール

### ゴール
- 「あのノートを読みたい」という**意図を持った探索**に応える
- **AI非対応端末でも壊れない**
- 「さっき読んだノート」に戻れる

### 非ゴール
- **全文検索をしない。** Nano は埋め込み検索を持たず、全ノートを読ませられない
- **選定理由を見せない**（プロンプトとパーサを既存流用するため）
- **履歴を翌日へ持ち越さない**

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| フォルダ選択 | 第一階層のフォルダをチップで選ぶ（未選択＝ルート直下） | タブを開いたとき |
| 🔎キーワード検索 | 自然文を入れると**3件**出る | 検索実行 |
| 🎰スコープ内ランダム | スコープから**3件**を無作為に出す | ボタン |
| AI不使用の注記 | 「キーワード一致で表示しています」等を添える | Nano が使えない／候補外を返した |
| 今日読んだノート | タブ下部に**当日分だけ**の履歴（最大10件） | 常時 |

## 4. 現在のユーザーフロー

1. さがすタブを開く → `loadFolders()` が第一階層のフォルダを並べる
2. フォルダを選ぶ（省略可。未選択ならルート直下がスコープ）
3. **🔎キーワード** を実行する
   - スコープ内のノートを集める（**スコープ単位の走査キャッシュ**あり → §5）
   - 候補が**40件超のときだけ**、文字bigramの重なりで40件へ粗く絞る
   - `checkAvailability()` を見る
     - `Available` → プロンプトを組んで Nano に選ばせ、**タイトルの正規化照合**で実在ノートへ戻し、先頭3件
     - それ以外 → **フォールバック**（§8 判断3）
   - Nano が**候補外や空を返した場合もフォールバック**
4. **🎰ランダム** なら `shuffled().take(3)`（AI を通さない）
5. 結果をタップすると `openNote` でノートタブへ渡る
6. 開いたノートは当日履歴の先頭へ入る

**中断:** 新しい要求を出すと前の要求は `cancel()` され、`activeRequestId` が進んで結果が捨てられる。

## 5. 機能仕様

- **前提条件:** Vault が選択済み。**未選択なら黙って返る**（→ [saf_boundary_gateway](../system/saf_boundary_gateway.md)）
- **上限:**

  | 対象 | 値 | 定数 |
  |---|---|---|
  | Nano へ渡す候補 | **40件**（超えたときだけ絞る） | `CANDIDATE_LIMIT` |
  | 結果の件数 | **3件**（両モード共通） | `PICK_LIMIT` |
  | 当日履歴 | **10件** | `MAX_ENTRIES` |
  | 走査キャッシュの寿命 | 60秒 | `NOTES_CACHE_TTL_MS` |

- **状態:** `SearchState`（`Idle` / `Loading` / `Success(results, aiStatus)` / `Error`）。
  `aiStatus` は `Ready` / `Unavailable` / `NeedsDownload` の3値で、**UIの注記はこれで出し分ける**
- **フォルダ階層は第一階層のみ**（ドリルダウンなし）。**中身は再帰収集する**ので、後方互換で拡張できる
- **`_AI補記` フォルダはスコープに出す。** 除外ロジックを書かず実装を軽くする割り切り
  （**Rediscover は除外する** — あちらは「読むノート」を引くため）
- **エラー／AI非対応／キャンセル時:**
  - Nano が使えない → フォールバックし、`aiStatus` で注記する。**エラーにしない**
  - 例外 → `Error`。`CancellationException` は**素通しする**（→ §8 判断4）

## 6. 状態とデータ

**UI状態:** `SearchState` ＋ `folders` ＋ `selectedFolder`（いずれも `NoteUiState`）。

**当日履歴は SharedPreferences。** 日付キーを添えて保存し、
**読み出し時に「保存日 ≠ 今日」なら空を返す。** 削除バッチも期限管理も要らず、
**日付が変わった瞬間に自然消滅する。** 同じノートは重複させず先頭へ移動する。

**この機能はVault単位で、ノート単位の契約には登録しない。**
無効化の契機は Vault 切替だけで、`vaultGeneration` を使う。
**ノートを開き直しただけでフォルダ一覧や履歴が消えるのは誤り**
（→ [architecture](../system/architecture.md) 判断4）。
Vault切替では履歴も破棄する（**旧VaultのURIは新Vaultで開けない**）。

**スコープ単位の走査キャッシュは `SearchController` が持つ**（キーは選択フォルダの `documentId`）。
SAF の再帰走査は1フォルダごとに IPC が発生して重く、「検索→ランダム→検索」の連続操作で再走査しないため。
**素の `mutableMapOf` で足りるのは、読み書きが必ず Main 単一スレッドで起きるから** —
別ディスパッチャから触る変更を入れるなら同期が要る。

## 7. システム設計

```
SearchScreen
 └─ SearchController                        ← vaultGeneration で無効化
      ├─ loadFolders() / selectFolder()
      ├─ searchByKeyword() ─┐
      │                     └─ SearchPickerUseCase.pick()
      │                          ├─ recallCutByKeyword()  ← 40件超のときだけ
      │                          ├─ AiClient.generate()   ← Nano が3件選ぶ
      │                          └─ fallback()            ← スコア順・0件なら空
      ├─ pickRandomInScope()  ← shuffled().take(3)。AI を通さない
      └─ スコープ走査キャッシュ（Main単一スレッド前提）

NoteHistoryStore（SharedPreferences・日付キー）
```

## 8. 設計判断と代替案

### 判断1: 「絞る」を人間にやらせる

Nano は**埋め込み検索を持たない**ので、全ノートを読ませて探すことはできない。
関連ノートと同じ「**候補を絞る → AIに選ばせる**」の2段構えが現実解になる。

この「絞る」を**ユーザーのフォルダ選択**に担わせることで、
**日本語クエリのトークナイズ（分かち書き）という難所を機械側から排除した。**

**「無関係が出る」という不満は、探索範囲を人間が絞った時点で原理的に解消される。**

### 判断2: bigram再現率カットは40件超のときだけ

Nano に渡せる候補数に上限があるため、40件を超えるときだけ**文字bigramの重なり数**で並べ替えて絞る。

**目的は精度ではなく再現率。** 日本語トークナイザ辞書を要さず、部分的な文字並びの一致で
「狙いのノートを取りこぼさない」ことを狙う。**最終精度は後段の Nano が担保する**ので、粗い一致で十分。

### 判断3: フォールバックは候補数に依らずスコア順。0件なら返さない

`checkAvailability()` が `Available` 以外、または Nano が候補外・空を返した場合は、
**キーワード一致の強い順に3件**返し、UIへ注記を添える。**端末が Nano 非対応でも機能は動く。**

> **旧仕様は「絞り込み結果の先頭をそのまま返す」だった。** そのため候補が40件以下だと
> **並べ替えを通らず、SAF の列挙順のまま「キーワード一致で表示しています」と出ていた**
> — UI文言と実装の不一致である。**候補数に関係なくスコア順へ統一し、一致0件は返さない**
> （0件なら画面は「見つかりませんでした。」になる）。
> 旧ヘッダはこの乖離を未解決として掲げていたが、**実装側は既に修正済みで、本文だけが古かった。**

### 判断4: `CancellationException` を `Error` へ畳まない

`SearchPickerUseCase.pick` は**内部で結果型を返す**経路なので、`cancel()` だけでは足りない。
キャンセルを `Error` へ畳むと、呼び出し側は「正常に失敗が返った」と区別できず、
**追い越された古い要求がエラー表示になる。**

照合は `setStateIfCurrent` の1箇所に集約する（呼び出し側へ `if (!isCurrent) return` を重ねない）。

### 判断5: 履歴は当日分だけ

見返したくなるのは「**あ、さっきのやつ**」というその瞬間で、翌日へ持ち越す価値はない。

**この割り切りが実装を1行に縮めている** — 日付キー付きで保存し、読み出し時に日付を見るだけ。
明示的な削除バッチも期限管理も不要。

### v1で見送ったもの

サブフォルダ選択（ドリルダウン）・リファインループ・音声入力・時間クエリ・
タグ／エイリアスの再現率カット反映・選定理由の表示。

**件数を両モードとも3件にしたのは、1件だと Rediscover と重複するため。**

## 9. 品質要件

- **性能:** 走査は `Dispatchers.IO`。スコープ単位のキャッシュで連続操作の再走査を避ける
- **プライバシー:** クエリと候補タイトルはプロンプトへ入るが端末外へ出ない
  （→ [ADR-0002](../decisions/ADR-0002-on-device-ai-only.md)）
- **端末制約:** **Nano 非対応でも機能する**（この点が他のAI機能と違う）

## 10. 検証と受け入れ条件

- **JVMテスト:** `SearchControllerTest`（世代照合3種・検索とランダムの実行・走査キャッシュのヒットと破棄）/
  `SearchKeywordMatchingTest`（bigram の再現率カットとスコア順）
- **instrumentation:** `VaultScanInstrumentationTest`（実物SAFでの走査）
- **保証していないこと:**
  - **Nano の選定精度を測っていない。** 「狙いのノートが3件に入るか」の指標が無い
  - **bigram カットの再現率も測っていない。** 40件という上限は見積もり
  - フォルダが第一階層しか出ないので、深い階層のノートは親フォルダ経由でしか絞れない
