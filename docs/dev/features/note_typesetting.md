## 1. 概要

ノートを開くたびに目にする読む面を、白く事務的なカードから、モダンな紙面（**プレート**）に組み直す。
プレートの中の組み方は**ノートの型**（技術書・読書ノート・標準）で変える。

- **ノートの文字は変えない。** 見出しと部品の役割に合わせて組むだけで、Vault も書き換えず、データも増えない
- **型は本文から表示の前に決まる。** 設定を作らず、AI も使わない（→ 判断1）
- **見え方はオーナーと合意したモックが基準になる**（Design キャンバス「読む面の紙 モック」の標準・技術書・読書ノートの型と、区切り1の案C）。
  借りたのは Apple の開発者ドキュメントと Apple Books の組み方だけで、見た目と SF フォントは写さない

### 紙面の3つの層

| 層 | 中身 | 型による違い |
|---|---|---|
| **1. プレートと書式** | 紙の形と浮き・題 > 見出し > 本文の大きさ・行間・字間・斜体をやめる・藍のアクセント | 無い |
| **2. 型に関係ない部品** | 題の欄（フォルダの道筋・タグ）・コードの枠・コールアウトの面・番号付きの箇条・インラインのコード・引用・表 | 無い。**どの型のノートも同じ部品で組む**（→ 判断13） |
| **3. 型に意味のある部品** | 技術書: 目的の箱・レベルの札・見出しの番号・実行結果・用語集・注意点の箱／読書ノート: 情報カード・紹介文の帯・要点カード・関連の札・自分の言葉の面・章の扉 | 型ごとに違う |

**標準の型は層1と層2だけでできている。** 技術書と読書ノートは、その上に層3を足す。

### 区切り

**層で切る**（2026-11-27、オーナー判断 → 判断3）。区切り1で層1と層2を全ノートに入れ、ほとんどのノートが開いた瞬間に変わって見えるようにする。
その後で、当たるノートの多い型から層3を足す（Mac の写しの Vault で、コードの枠を持つノートは240本、資格試験の骨格は166本、読書の骨格は30本。端末の Vault と同じかは確かめていない）。

| 区切り | 入れるもの | 型の扱い |
|---|---|---|
| **1. プレートと型に関係ない部品** | 層1・層2・ダークの夜の紺・最初の1枚を引く前の場・全画面の末尾の余白 | 判定の純関数を作るが画面には配線しない。全ノートを層1・層2で組む |
| 2. 技術書の意味の部品 | 層3（技術書） | 技術書を組み分ける |
| 3. 読書ノートの意味の部品 | 層3（読書ノート） | 読書ノートを組み分ける |

## 2. ゴールと非ゴール

### ゴール

- 開いたノートが、型に合った紙面で読める。**区切り1で、白く事務的な紙面が全ノートから消え、コード・コールアウト・箇条・引用・表を持つノートは開いた瞬間に変わって見える**
- 書式は1か所にあり、縦の流し・全画面・見開き・右の並べ読みが同じ値で組む
- 型の判定はノートを開く前に終わり、読み始めた後に紙面が組み替わらない

### 非ゴール

- **型を選ばせる設定を作らない。** 型は本文から決まる（→ 判断1）。明示したいときは Obsidian 標準の `cssclasses` に書く
- **型で地の色・プレートの形を変えない。** 地の色は年代、プレートの形は面の役割が持つ（→ 判断2）
- **紙の配色を選ばせない。** 年代の紙の案（地を生成りにする3案）は採らない。年代の紙は今のオプション（既定オフ）のまま、プレートの地に載せる。
  選べるのは、何も表さない読む画面の背景の強さだけにする（→ 5.1）
- **ノートの分野（AI の判定）で型を決めない。** 判定は開いた後に届く（→ 判断1）
- **書体を同梱しない（区切り1）。** 本文も等幅も端末の書体で組む。等幅は実機で読み比べ、足りなければ区切り1の中で決め直す
- **コードの色分けのためにライブラリを足さない。** 自前の小さな切り分けで、3つの言語の4種だけを色分けする（→ 判断15）
- **和文と欧文の間のアキを入れない。** 文字列を書き換えずに入れる手段が無い（→ §11）
- **見開きを本の版面に組まない。** ノドと小口の非対称・1面のページ送りは別の変更で、版面の上にこの組み方が載る
- **プレートの外の部品は扱わない。** 見出しの帯・ボタン・下のタブ（クロームを退かせる形と記号の線画）・読書中のスリープ防止・AI の短い文と再会カードの形は、面の形のチャネルと取り合うかを別に確かめる
- **人と AI の声を書体で分けない。** 書体と行間はノートの型が持つ（→ [bearing_channels](../system/bearing_channels.md) §11）

## 3. 詳細機能一覧

区切り1の分だけを書く。区切り2・3は着手するときにこの表へ足す。

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| プレート | 通常表示では、読む画面の場の上に、角の丸い紙が浮いて見える。全画面は画面全体が紙になる | ノートを開いているとき |
| 紙面の書式 | 題が見出しより大きく、H1・H2 の上に藍の短い線が付く。最初の段落はリード文として少し大きく組まれる。行間が広がる | 全ノート |
| 題の欄 | 題の上にフォルダの道筋、下にタグの札が並び、罫で本文と分かれる | 全ノート（道筋とタグは有るときだけ） |
| コードの枠 | コードが暗い窓に入り、右上に言語の札が付き、主な言語は色分けされる | コードのブロックがあるノート |
| コールアウトの面 | まとめ・問い・例とヒント・注意が、記号と言葉の付いた色の薄い面になる | コールアウトがあるノート |
| 番号付きの箇条 | 番号が藍の小さな札に入る | 番号付きの箇条があるノート |
| インラインのコード | 等幅の字に淡い面が敷かれる | インラインのコードがあるノート |
| 引用 | 藍の大きな引用符に続けて、少し大きな字で組まれる | 引用があるノート |
| 表 | 外枠と罫が淡くなり、頭の行が淡い面になる | 表があるノート |
| 1行の長さの上限 | 広い窓でも本文の1行が約32字を超えない | 本文の列が 520dp より広いとき |
| ダークの夜の紺 | ダークで、読む画面の場と紙が深い紺になる。紙の上端にごく淡い光が当たる | ダークのとき |
| 年代の紙 | オンにすると、プレートの地に年代の色が載る | 今のオプション（既定オフ）・ライトのとき |
| 背景の強さ | 読む画面の背景は既定で3色を淡くした地になる。オンにすると今の鮮やかなグラデーションに戻る | オプション（既定オフ）・ライトのとき |
| 最初の1枚を引く前の場 | ノートを引く前は、本文と同じ紙に、次の操作を1文で添えて静かに待つ | ノートが出ていないとき |
| 全画面の末尾の余白 | 全画面を出入りした後も、末尾へ送ると最後の段落が見える | 見出しから開いたノートで全画面を出入りしたとき |

## 4. 現在のユーザーフロー

1. ノートを引く（ランダム表示・リンク・関連・さがす・冊子）
2. 本文の解析と同じジョブで、コードの言語の札・色分け・タグを読み、型を決める（型は区切り2から使う → §7）
3. 紙面がプレートに組まれて出る。部品も型も表示の前に決まっているので、出た後に組み替わらない
4. 全画面・見開き・右の並べ読みへ移っても、同じ書式で組まれる
5. ノートが出ていない間（起動の直後・Vault が空・読めない）は、最初の1枚を引く前の場が出る

## 5. 機能仕様

**数値は区切り1の初期値である。** 合意したモック（CSS の px を dp・sp と読む）から取り、実機で読み比べて動かす。
**値を動かすのは書式の1か所だけ**で、見開きの計測は同じ値を読む（→ 判断4）。

### 5.1 プレート（層1）

| 項目 | 値 |
|---|---|
| 形 | 読む面の形（`ReadingSurfaceShape`）。角を **8dp → 16dp** にする。冊子の眺める面（2dp）との差は広がる側に動く |
| 中の余白 | 上 26dp・左右 22dp・下 30dp（今は4辺 18dp） |
| 浮き | ライトは淡い影。ダークは影の代わりに、ごく細い明るい縁（大きい部品なので [ui_design_principles](../system/ui_design_principles.md) §3 に当たらない） |
| 紙の色 | ライトは今の `panel`。年代の紙がオンなら年代の色（今の `notePaperColor` の口のまま）。ダークは夜の紺（→ 5.6） |

- **通常表示は、読む画面の場（背景のグラデーション）の上にプレートを浮かせる**（→ 判断9）
- **場は既定で、今の3色を淡くした地にする。** オプションの「読む画面の背景を鮮やかにする」（既定オフ）をオンにすると、今のグラデーションに戻る（2026-11-28、オーナー判断 → 判断17）
  - 淡い3色は、今の3色（`MutedIndigo`・`MutedAqua`・`MutedCoral`）の色相を保ち、OKLch で明度 0.94・彩度 0.025 にそろえる**規則で作る**（冊子の分野色と同じ作り方）。値は `#E8E9FC`・`#DAEFF7`・`#FBE5E8`。
    モックの手で選んだ値は色相が最大11度ずれていたので使わない。検査は OKLch の色相の差（3度未満）で見る
  - **ライトだけで効く。** ダークは設定によらず夜の紺（→ 5.6）。年代の紙と同じ扱い
  - **場の3色と強さは設定から引く形にする。** 背景の3色を選ぶ機能は、区切り1の後に別の機能として足す（このとき作り直しが要らないように、色の組と強さを分けて持つ）
  - 机の上端の帯は今どおり読む画面の場と同じ色を引くので、強さの切り替えに付いてくる
  - **起動の画面と冊子の地は今のまま**（低彩度の3色）。設定はノートを読む画面（`ReadingGround`）だけに効く
  - 場は何も表さない（→ [bearing_channels](../system/bearing_channels.md)）。強さを選ばせても、年代・型の見え方は変わらない
- **全画面は、プレートを浮かせず画面全体を紙にする。** 今の全ブリードのまま、本文の列だけを 5.5 の上限で絞る
- **見開きの左右のページは、プレートと同じ形と色を引く。** 版面の非対称は扱わない（→ §2）
- **右の並べ読みの本文**は同じ書式と部品で組む。面の形は今のまま（右の面はプレートにしない）

### 5.2 紙面の書式（層1）

| 部品 | 今 | 区切り1 |
|---|---|---|
| ノートの題 | 20sp・太字 | **24sp**・太字・約物を詰める（`palt`） |
| 見出し | H1 24 / H2 21 / H3 19 / H4 17 / H5 15 / H6 14sp（H6 は斜体） | **H1 21 / H2 19 / H3 18 / H4 17 / H5 16 / H6 16sp**。すべて太字・斜体なし・約物を詰める |
| 見出しの線 | なし | **H1・H2 の上に、藍の短い線（22×2dp）**。線と見出しの間は 10dp |
| リード文 | なし | **本文の最初のブロックが段落なら（見出しより前）、16.5sp・中太**で組む |
| 本文（段落・箇条） | 16sp・行の高さ 24sp | 16sp・**行の高さ 30sp** |
| 字間 | Material の本文の既定（0.5sp）を引き継ぐ | **0**（和文をベタで組む） |
| 太字 | 太字 | 太字のまま。マーカーを敷かない |
| 箇条の点 | 本文の色 | **藍** |
| 本文のリンク | 青（`linkText`） | **藍**・細い下線 |
| ブロックの間 | 一律 8dp | 一律 **14dp** |
| 見出しの上の余白 | H1・H2 8dp / H3 以下 4dp | H1・H2 **18dp** / H3 以下 **10dp** |
| 改行の規則 | `LineBreak.Simple` | 変えない（→ 判断4） |

- **藍は関連ノートの見出しの色と同じ値**（ライト `#6054DE`・ダーク `#A79EFF`）だが、**読む面のアクセントという別の役割の色として持つ**。
  値が同じでも、片方を動かしたときにもう片方が付いて動かないようにする（→ [ADR-0005](../decisions/ADR-0005-bearing-channel-allocation.md) の帰結「区別は値ではなく役割の違いとして持つ」）
- **書き手が `*…*` で付けた斜体は残す。** やめるのはアプリが付けていた斜体（引用・H6）だけである（→ 判断5）
- 余白は「ブロックの間の一律の間隔」と「見出しが自分の上に持つ余白」の2つだけで作る（→ 判断4）。
  **見出しの線は見出しのブロックの高さに含める** — 見開きの計測も同じ高さを足す
- **リード文かどうかはブロックの位置だけで決まる。** 描画と見開きの計測が同じ純関数を呼び、片方だけがリード文の書式で組む形にしない

### 5.3 題の欄（層2）

- **題の上にフォルダの道筋、題の下にタグの札を置き、欄の下に罫を引く。**
  - 道筋: Vault の中の親フォルダを ` / ` でつないだもの。藍の 11sp・字間を少し空ける。Vault の直下のノートと、相対パスが分からないノート（リンクで開いて走査の結果に無いもの）は出さない。
    相対パスは、結晶の絞り込みと同じく、ノートを開いて確定した今のノートの相対パス（ノート単位で消える）を読む
  - タグ: frontmatter の `tags` を、関連ノートのタグと同じ読み方（`frontmatterList`。`domain` に置き、ノートの索引と本文の解析が共有する）で本文の解析と一緒に読み、淡い面の札（11sp）に並べる。本文の中の `#タグ` は拾わない。無ければ札の行を出さない
  - 罫: 1dp の淡い線。欄と本文の間はブロックの間より 4dp 広い
- 道筋とタグは**表示だけ**で押せない
- 見開きでは最初のページの頭に置く。右の並べ読みは今の題の出し方のまま（題の欄を出さない）
- 道筋とタグは AI へ渡す文・痕跡・知識索引に入れない（今と同じ）

### 5.4 型に関係ない部品（層2）

**どの型のノートも同じ部品で組む**（→ 判断13）。部品の色は、読む面の地の色ではなく部品の中の色で、年代のチャネルに当たらない。

#### コードの枠

- **テーマに関わらず暗い窓にする**（ライト `#0F1626`・ダーク `#070C18`、文字 `#D7DEEA`、角 10dp・中の余白 12/14dp）（→ 判断14）
- 字は端末の等幅で 13sp・行の高さ 22sp（今は 14sp・20sp）
- **頭の行の右に言語の札を出す。** 札は原文の ```` ``` ```` の後ろの語のまま（`python`・`kotlin` など）。札の無い枠は頭の行を出さない。
  ファイル名は Markdown のコードの枠に無いので出さない（モックの `Header.kt` は見本）
- **言語を解析で残す。** 今のコードのブロックは言語の札を捨てている。札は AI へ渡す文と知識索引に入れない（今と同じ）
- **色分けは Python・Kotlin・シェル（`sh`・`bash`・`zsh`）の3つで、キーワード・文字列・コメント・数字の4種だけ**（→ 判断15）。
  ほかの言語と札の無い枠は1色で描く。色はモックの値（キーワード `#C3A6FF`・文字列 `#A6E3A1`・数字 `#F5A97F`）から始め、コメントだけはモックの `#6E7A93` がライトの窓で 4.19 に留まるので `#7A86A0`（4.94）にする。どれも2つの窓の上で 4.5:1 を超える
- 行番号は付けない（→ 採らなかった案）
- 横に長い行は今どおり折り返す（見開きの割り方が行で測っている）
- 見開きで割れたときは、各片をそれぞれ枠で描き、言語の札は最初の片だけに出す

#### コールアウトの面

- **種類（今の役割の分け方 `CalloutRole`）ごとに、紙に薄い面を敷く。** 枠線は付けない（[ui_design_principles](../system/ui_design_principles.md) §3）。角 10dp・中の余白 12/14dp

  | 役割 | 面（ライト／ダーク） | 頭の色（ライト／ダーク） |
  |---|---|---|
  | まとめ（知らない種類もここ） | `#EEF1F7`／`#18233A` | `#4A5A78`／`#A9BBDD` |
  | 問い | `#F3F1FF`／`#1C2244` | `#6054DE`／`#A99CFF` |
  | 例・ヒント | `#EAF5F2`／`#12302C` | `#0C796C`／`#5FD0C0` |
  | 注意 | `#FBF3E2`／`#2E2614` | `#8A6414`／`#E3B85A` |
  | 引用（`quote`・`cite`） | 面を敷かない。引用と同じ形 | — |

- 頭は「記号＋言葉」、続けて題。**記号は 16dp の単色の線画を4つ描き起こし**、言葉と同じ色で塗る。アイコン集は入れない（依存が増える）。
  **見分けの主役は今どおり言葉**で、色と記号は補助（色だけで伝えない）
- 中身は 14sp・行の高さ 26sp の本文の色
- 見開きでページをまたぐときは、各片をそれぞれ角の丸い面で描き、頭は最初の片だけに出す
- 畳み（`-` で閉じて始まるもの）は扱わない（Mac の写しで0個）

#### 番号付きの箇条

- **番号を藍の薄い札（22dp 角・角 6dp）に、等幅の藍の字で入れる。** 番号は原文の数字のまま
- 札は行の高さ（30sp）の中に収まり、行の高さを変えない
- 番号の無い箇条は藍の点（5.2）、タスクの箇条は今のチェックボックスのまま

#### インラインのコード

- 等幅・12.5sp・淡い面（ライト `#F1F3F6` 上に `#2B2F36`、ダーク `#1B2640` 上に `#D7DEEA`）
- **文字の背景として描き、角丸と前後の余白は付けない**（→ 判断16）

#### 引用

- **頭に藍の大きな引用符（34sp）を置き、本文を 17sp・中太・本文の色で組む。** 縦線と控えめな色はやめる
- 複数の段落の引用も同じ形で、引用符は最初の行の頭に1つ。見開きで割れたときは最初の片だけに出す
- 引用の中の箇条と表（→ [markdown_rendering](../system/markdown_rendering.md) §8）は、引用の字下げの中で同じ部品で描く

#### 表

- 外枠を内側の 1dp の淡い線、角 10dp にし、頭の行を淡い面に控えめな色の太字で組む。セルは 13sp・中の余白 9/12dp
- 列の多い表の扱い（横へ送るか）は今のまま

### 5.5 1行の長さの上限（層1）

- **本文の列の最大幅を 520dp にする**（16sp で約32字）。列は紙の中で中央に置く
- 全画面は今の最大 720dp の列をこれに置き換える（720dp では余白を除いて約42字になる）
- 通常表示で本文の紙が広いとき（開いた Fold で机を出していないときなど）も、紙は幅いっぱいのまま、列だけを絞る
- 見開きの1面にも同じ上限を掛ける。今の窓では1面が 520dp に届かないので効かないが、**計測の幅と描画の幅は同じ上限から取る**
- 文字の倍率を上げた人は、同じ 520dp に入る字数が減る。dp で決めるのは、倍率を上げた人の1行を広げないため

### 5.6 ダークの夜の紺

- **読む画面の場と紙を、起動のオープニングと結晶の展示室と同じ LogoNavy 系の深い紺にする**（今の紙は `#2A2D45`）。
  紙の上端からごく淡い光を重ねる。**光はどのノートでも同じで、何も表さない**
- **載る面は読む画面だけにする**（2026-11-27、オーナー判断 → 判断10）。ほかのタブの面は今の色のまま。読む画面がほかの画面より静かという関係（→ [dark_mode](dark_mode.md) 判断3）を深める側に動く
- **読む画面の上に乗る部品の明るさの段を、夜の紺に合わせて組み直す。** 今は `panelBlue`（`#22273F`）と `panelRow`（`#262A40`）が紙（`#2A2D45`）より暗い。
  場 < 紙 < 紙の上の部品、の順にそろえる。**コードの枠だけはこの順の外**で、紙より暗い窓にする（→ 判断14）
- **値は次のとおり（2026-11-28、オーナー判断でモックの推奨を採った）:**

  | 面 | 値 | 相対輝度 |
  |---|---|---|
  | 場 | 今の3色の色相を残したまま紺へ沈めたグラデーション（`#0D1230`・`#071426`・`#140F24`） | 0.0062〜0.0073 |
  | 紙 | `#111A2E`。上端から青みの白をごく淡く重ね（5%）、240dp で消す | 0.0106 |
  | 紙の上の部品・場に置く部品 | `#18233A`。再会カードのように場に置く部品は、ごく細い明るい縁を付ける | 0.0170 |

  - **場は平らな紺にしない。** ライトの場と同じく3色の気配を残す
  - **再会カードは紙より1段明るくする。** 紙と同じ色にすると、本文の紙と別のものだと分かりにくい
  - 文字の比はモックで計算した。本文から最も弱い文字・藍まで、紙と部品の上で 4.5:1 を超える
- 年代の紙はダークでは今どおり効かない（→ [note_age_paper](note_age_paper.md) 判断5）。**年代の色を夜の紙へ持ち込む提案は、その判断を改める提案である**

### 5.7 最初の1枚を引く前の場

起動のオープニングの後、まだノートを引いていない読む面。今は「ノート未表示」と案内文の白いカードが出る。

- **本文と同じ位置に、同じプレートを置く。** 題（「ノート未表示」）は出さず、藍の短い線と、次の操作の1文だけで静かに待つ。Vigilith はここに置かない（→ [character_vigilith](character_vigilith.md)）
- 文は状態ごとに1つ。**`「」` で指す名前は、今の画面にあるボタンの文字にする**

  | 状態 | 文（案） |
  |---|---|
  | Vault を選んでいない | 「Vaultを選択」から、読むノートのフォルダを選びます |
  | Vault を選んだが、まだ引いていない | 「別のノートをひらく」で、今日の1枚を引きます |
  | Vault に Markdown のノートが無い | このVaultにMarkdownノートが見つかりませんでした |
  | Vault を読めなかった | Vaultを読み込めませんでした |

- **案内の文は1か所に置き、本文の紙はそれを読むだけにする。** 今は読む面の空の場と本文の紙が別々に文を持ち、本文の紙の文は今は無い「ランダム表示」ボタンを指している
- **本文の紙は、読み込み中に案内の文を出さない。** 紙だけを出す。コードから読むと、全画面でリンクを開いて次のノートを読み込む間に、本文の紙の文が出る経路がある（実機で確かめる）
- **紙は本文の紙と同じ位置・大きさに伸ばし、藍の線と文は上に置く。罫は敷かない**（2026-11-28、オーナー判断でモックの推奨を採った → 判断11）
- 失敗の2つの文は、失敗が分かる言葉のまま残す（色だけで伝えない）

### 5.8 全画面の末尾の余白

見出しから開いたノートで全画面に入って出ると、全画面で足した末尾の余白が通常表示へ運ばれ、末尾へ送ると本文が空白だけになる。
区切り1で全画面の1行の長さが変わり、2つの窓の高さの差が広がるので、ここで直す。

- **余白の量は運ばない。運ぶのは「どの見出しを上端に置いているか」だけにし、戻った窓で足りない分を測り直す**（→ 判断12）
- 不変条件: **末尾の余白は、その窓で見出しを上端に置くのに要る分を超えない**

### 5.9 型の判定（区切り1では作るだけ）

型は3つ: **技術書・読書ノート・標準**。上から順に当て、最初に当たったものに決める。

1. **frontmatter の `cssclasses` に型の名前があれば従う。** 名前は `techbook`・`readingnote`・`standard`（`技術書`・`読書ノート`・`標準` でもよい）。
   読めない frontmatter はこの段を飛ばす（失敗にしない）
2. **見出しの骨格で決める。** 見出しの頭の記号（絵文字・番号）を外した語を、型ごとの語の辞書と完全一致で照らす。
   **一方の型の語に当たる見出しが2つ以上あり、もう一方より多ければ**その型にする
   - 技術書: 目的・構文・ユースケース・注意点・レベル・関連知識 など
   - 読書ノート: 概要・紹介文・要点メモ・コメント・感想 など
   - 両方の型にまたがる語（「関連」「まとめ」など）は辞書に入れない。**辞書の正本はコード**（`NoteFormJudge.kt`）で、Mac の写しの Vault の見出しの実物から取った
   - 見出しの頭と末尾の、文字でない記号（絵文字・番号・約物・強調の記号）だけを外して照らす。中の記号は残す（「解説・注意点」は1つの語）
3. **どれにも当たらなければ、コードの枠を持つノートは技術書、持たないノートは標準**

- **検算:** Mac の写しの326本に当てると、技術書237本（骨格で101本・コードの枠で136本）・読書ノート30本・標準59本に分かれた。
  読書のフォルダの30本のうち29本が読書ノートに当たり、残る1本はコードの枠を持つので技術書になった。`cssclasses` を書いたノートは0本（端末の Vault と同じかは確かめていない）
- **入力は解析済みの本文（ブロックの並び）と frontmatter の `cssclasses` だけ。** AI の結果・痕跡・ファイルの場所を使わない
- **区切り1ではこの判定を画面に配線しない。** 全ノートを層1・層2で組む。配線は区切り2で、本文の解析と同じジョブで行う（→ §7）

### 5.10 型に意味のある部品（層3。区切り2・3。モックで合意した形）

区切り2・3は着手するときにこの節を値まで詰める。今は何をどの部品にするかだけを置く。

- **技術書:** タイトルの採番を小さなラベルに分ける・🎯 目的をリードの箱に・📶 レベルをタイトルの下の札に・見出しに番号を付ける・
  🧪 実践コードの後の実行結果を枠に続く欄に・📚 関連知識を用語集に・
  ⚠️ 注意点を黄土の箱にまとめ、【件名】に番号を付け、❌ before と ✅ after を上下に並べる
- **読書ノート:** 🕓 概要の「項目：値」を本の情報カードに（ステータスは札）・📝 紹介文の `[!quote]` を紙面を渡る帯に・
  💡 要点メモを番号付きの要点カードに・🔗 関連をリンクの札に・
  ✍️ コメントを「自分の言葉」の面として分け、「第N章」を章の扉、「N.N」を番号付きの小見出しに
- **標準:** 層3を持たない。層1・層2そのもの
- **型が読み取る書き方の約束から外れた書き方は、層2の部品で描く。** 型は書き方を強いない

### 5.11 前提条件・連携・失敗

- **前提条件:** なし（AI を使わず、Nano 非対応の端末でも同じに組む）
- **保存と寿命:** 何も保存しない。言語の札・色分け・タグは区切り1から、型は区切り2から、解析結果と同じ寿命で持つ（→ §6）
- **他機能との連携:** 見開き（同じ書式で測る → [note_spread](note_spread.md) 判断8）・年代の紙（プレートの地 → [note_age_paper](note_age_paper.md)）・見出しを上端に置く送り（→ [note_links](note_links.md) 判断6）・
  AI へ渡す文と知識索引（言語の札・タグ・道筋を入れない。コードの本文は今のまま）
- **エラー／AI非対応／キャンセル時:**

  > **該当なし:** 区切り1は非同期の処理を足さない。言語の札・色分け・タグ・型は今の解析のジョブに載り、取り消しはそのジョブの規則に従う。色分けできない言語と読めない frontmatter は、色分けしない・タグを出さないに倒し、失敗として見せない。

## 6. 状態とデータ

- **`NoteUiState` に欄を足さない。** 契約2箇所（`cancelNoteScopedJobs()`・`withNoteScopedReset()`）への登録も無い
- **設定を1つ足す。** 読む画面の背景を鮮やかにするか（`AppPreferences`・既定オフ）。年代の紙と同じく `NoteUiState` の外に置き、`AppTheme` が色へ写す（→ [architecture](../system/architecture.md) の「状態が `NoteUiState` の外に出るもの」の設定の行）
- **解析結果が持つものが増える**（`NoteUiState` の外 → [architecture](../system/architecture.md) の「状態が `NoteUiState` の外に出るもの」）。
  - 区切り1: コードのブロックの言語の札（`MarkdownBlock.CodeBlock` に欄を足す）・色分けの切れ目・frontmatter のタグ
  - 区切り2: 型
  - **本文とこれらを別々に届けない。** 別々に届くと、本文が出た後に色分けや型が届いて紙面が組み替わる
- 末尾の余白の直しは、画面が持つ `EndSpace` の中で閉じる（`NoteUiState` の外。寿命は今の本文の位置と同じ）
- 設定のほかに永続化するものは無い。部品と型は開くたびに本文から決め直す

## 7. システム設計

```
ノートを開く
 └─ 本文の解析（Main の外。setNoteState() と applyReloadedBody() の2か所）
      ├─ ブロックの並び（コードのブロックは言語の札を持つ）
      ├─ 色分けの切れ目（区切り1。codeTokensOf(言語, 本文) ← 純関数・JVMテスト）
      ├─ タグ（区切り1。今の frontmatter の読み方）
      └─ 型（区切り2。noteFormOf(frontmatter, ブロック) ← 純関数・JVMテスト）
           └─ 型ごとの書式（区切り1は層1・層2の1つ）
                ├─ 縦の流しの描画（MarkdownRenderer）
                ├─ 見開きの計測と描画（SpreadBlocks・NoteSpread）
                └─ 右の並べ読みの本文
```

- **型は `model` の列挙、判定は `domain` の純関数に置く。** 型はノートの書き方の意味を決める判定なので `domain`（→ [architecture](../system/architecture.md) 判断5の4）。
  列挙は区切り2で解析結果に載るので、葉の `model` に置く
- **色分けの切れ目も `domain` の純関数に置く**（コードの解析にあたる）。どの切れ目を何色にするかは `ui` が決める
- **書式は描画と見開きの計測の両方へ、同じ値を引数で渡す。** 区切り1では今の `MarkdownBodyStyle` の値を替え、部品の寸法も同じ場所に置く。
  区切り2で型ごとの書式を同じ形の値として持ち、`CompositionLocal` のような暗黙の経路で片方にだけ届く形にしない（→ 判断4）
- **ノートの題と題の欄の書式も書式の側へ移す。** 今は本文の紙（20sp）と見開き（`TitleStyle`）が別々に持っている
- **見開きの定数を書式と組で変える。** `SPREAD_BODY_FONT_SP`・`SPREAD_BODY_LINE_SP` は本文の段落の書式と同じ値でなければならない。行の高さを 30sp にするなら定数も 30 にする
- **部品の高さは見開きの計測に入れる。** コードの枠の頭の行・コールアウトの頭と面の余白・引用の字下げ・表の余白・題の欄は、片ごとに描画と同じ高さを計測が足す
- 色分けの切り分けと型の判定は本文の長さに比例する。解析と同じく Main の外で回す（→ [architecture](../system/architecture.md) 判断3）
- **`CodeBlock` に欄を足すので、それを読む全箇所を当て直す**（AI へ渡す抜粋・知識索引のリンク・余白メモの照らし直し・見開き・描画）
- **実装したら直す正本:** [markdown_rendering](../system/markdown_rendering.md) §8（引用とコールアウトの形）とコードのブロックの節・[note_fullscreen](note_fullscreen.md)（列の 720dp）・
  [note_age_paper](note_age_paper.md)（紙が浮くプレートになる）・[dark_mode](dark_mode.md)（読む画面の紺と淡い場）・[bearing_channels](../system/bearing_channels.md) §11 の持ち主の行

### 実装の区切り（区切り1の中の順）

修正1件を1コミットにする。上から順に入れる。

1. **型の判定。** `model` の列挙と `domain` の純関数、JVM テスト。画面には配線しない
2. **紙面の書式。** 題・見出し・リード文・行の高さ・字間・斜体・余白・藍の色の役割。見開きの定数を組で変える
3. **プレートと1行の長さ。** 角・中の余白・浮き・全画面の列
4. **場の強さ。** 淡い3色の規則・オプションの切り替え・設定から3色と強さを引く形
5. **題の欄。** 道筋とタグと罫
6. **コードの枠。** 解析で言語を残す → 暗い窓と言語の札 → 色分け
7. **コールアウトの面。** 種類ごとの面と記号の線画
8. **番号の札・インラインのコード・引用・表**
9. **ダークの夜の紺。** 場・紙と上端の光・部品の段
10. **最初の1枚を引く前の場と、案内の文の一本化**
11. **全画面の末尾の余白。** 画面のテストを先に落としてから直す

## 8. 設計判断と代替案

### 判断1: 型は本文から表示の前に決める。設定も AI も使わない（2026-11-26、オーナー判断）

型を選ばせる設定を作ると、ノートごとに選び直す手間が増え、選ばないノートは標準のままになる。
**分野の判定（AI）は開いた後に届くので、最初に読むときに組めず、途中で組み替えると紙面がずれる。** 分野は冊子の紙と宝石の色が持っている。
本文の骨格（見出しの語とコードの枠）は解析と同時に分かり、Obsidian の書き方の約束（`cssclasses`）で明示もできる。

### 判断2: 型で変えるのはプレートの中の組み方だけ（2026-11-26、オーナー判断）

書体と行間のチャネルはノートの型が持ち、地の色は年代、プレートの形は面の役割が持つ（→ [bearing_channels](../system/bearing_channels.md) §11・[ADR-0005](../decisions/ADR-0005-bearing-channel-allocation.md)）。
**型の違いが地の色やプレートの形へ漏れると、2つのチャネルに同じ意味が載る。** 型を足すたびにプレートの色や形も変えたくなるが、変えてよいのは中の組み方だけである。

### 判断3: 区切りは層で切る。区切り1で層1と層2を全ノートに入れ、型の判定は作るが使わない（2026-11-27、オーナー判断）

層1だけでは、紙の角と行間と見出しの大きさが変わるだけで、紙面はほとんど変わって見えない。
**合意したモックの華やかさの多くは、型に関係ない部品（暗いコードの枠・色の面・番号の札・大きな引用符・淡い表）から来ている。**
それを型の区切りに入れると、型に当たらないノートは最後まで受け取れず、当たるノートも型の区切りまで待つことになる。層2を先に入れれば、ほとんどのノートが区切り1で変わる。
**判定を先に作っておくのは、区切り2・3で判定を変えずに層3だけを足すため。** 判定と組み方を同じ区切りで作ると、どちらが原因で紙面が変わったかを実機で分けられない。

### 判断4: 書式は1か所に置き、描画と見開きの計測が同じ値を読む。余白は2種類だけで作る

見開きはブロックを計測してページへ割り、割った段落の残りを組み直して描く（→ [note_spread](note_spread.md) 判断5・判断8）。
**描画と計測が別の書式を読むと、ページの末尾がはみ出すか空く。** 型ごとに書式が変わっても、両方へ同じ値を渡せば計測はずれない。

- **余白は「ブロックの間の一律の間隔」と「見出しが自分の上に持つ余白」の2つだけにする。** 見開きの割り方はこの2つで高さを測っている。
  「この部品の後だけ広く」のような組み合わせごとの余白は、割り方の側に組み合わせの規則を持ち込む。部品の中の余白（面・枠）は部品の高さに含める
- **改行の規則は `LineBreak.Simple` のまま。** 段落全体を見て改行を決める規則は、見開きが割った段落の残りを組み直すときに行の切れ目がずれる。
  禁則や行の長さの釣り合いのために変えるなら、見開きの組み直しも同じ規則で行う

### 判断5: アプリが付けた斜体をやめ、書き手の斜体は残す

日本語の斜体は、傾けただけの字になって読みにくい。引用の斜体と H6 の斜体はアプリが決めた形なので、やめる。
**書き手が `*…*` で付けた斜体は、書き手の指定なので残す。** 引用は大きな引用符と字下げで見分けられ、斜体が無くても引用と分かる。

### 判断6: 1行の長さは列の最大幅（520dp）で決める

全画面の 720dp の列では、余白を除いて1行が42字を超えうる。**読みやすい1行は和文で30字台**なので、列を 520dp（16sp で約32字）に絞る。
字数ではなく dp で決めるのは、文字の倍率を上げた人の1行を広げないため（倍率を上げると1行の字数が減り、文字が大きいまま読める）。
見開きの入る条件が字数で決まる（→ [note_spread](note_spread.md) 判断9）のとは向きが逆で、あちらは「狭すぎて入らない」を、こちらは「広すぎて読みにくい」を見ている。

### 判断7: 字間は0にし、約物の詰めは題と見出しだけ

Material の本文の既定（0.5sp）は欧文のための字間で、和文では字の間が空いて見える。和文はベタで組む。
**約物の詰め（`palt`）を本文に掛けると、行ごとに字の並びが不揃いになる。** 題と見出しは短く大きいので、詰めたほうが締まる。
`palt` を持たない書体では何も起きないので、端末の書体で効き方が変わるのは害にならない。

### 判断8: 題 > H1 > … ≥ 本文の順に組む

今はノートの題（20sp）が本文の H1（24sp）より小さく、H5・H6（15sp・14sp）が本文（16sp）より小さい。
**大きさの順が役割の順と逆になると、見出しの段が読み取れない。** 題を最大にし、H5・H6 は本文と同じ大きさで太さだけで分ける。

### 判断9: 通常表示は場の上にプレートを浮かせ、全画面は画面全体を紙にする

読む画面の場（背景のグラデーション）は「読む画面は触る画面より静か」という関係を持つ（→ [dark_mode](dark_mode.md) 判断3・[note_age_paper](note_age_paper.md) 判断3）。
場は残し、プレートをその上に浮かせる。**場の色を3色のまま淡くしても、この関係は保てる**（触る画面の鮮やかなグラデーションより静かになる）。強さは判断17。
**灰色の無地にはしない。** モックの灰色の地は見本の台で、ブランドの3色が読む画面から消え、事務的に見える。
全画面はそのノートに深く集中する入口（→ [note_fullscreen](note_fullscreen.md)）で、画面全体が紙になっている今の形がプレートの行き着く先に当たる。

### 判断10: ダークの夜の紺は、読む画面の場と紙に限る（2026-11-27、オーナー判断）

アプリ全体のダークの面を夜の紺にすると、冊子の分野色（ダークの紙の床を `panel` に置いている）とほかの全画面のコントラストを組み直すことになり、読む面の変更の外へ広がる。
**読む画面だけを深くすると、読む画面が触る画面より静かという今の関係を強める側に動く。** ほかのタブとの差は場のグラデーションで既にある。
読む画面の上に乗る部品（再会カード・要約の行など）は、夜の紺に合わせて段を組み直す。

### 判断11: 案内の文は1か所に置き、題を出さない

今は読む面の空の場と本文の紙が同じ状態の案内を別々に持ち、片方だけが古いボタンの名前を指していた。**文を1か所に置けば、ボタンの名前を変えたときに片方だけ古くなることがない。**
「ノート未表示」という題は、状態を報告する事務的な言葉で、引く前の場に要らない。次の操作の1文だけで足りる。
**紙は本文の紙と同じ位置・大きさに伸ばす。** 1枚目を引いたとき、紙面が動かずに中身だけが入れ替わる。内容なりの高さだと、引いた瞬間に紙が伸びて場が動く。

### 判断12: 末尾の余白は窓ごとに測り直す

末尾の余白は、見出しを上端に置くのに窓の高さから決まる量である（→ [note_links](note_links.md) 判断6）。
**量を別の窓へ運ぶと、高い窓で足した余白が低い窓に残り、末尾へ送ると余白だけが見える。** 置いている見出しだけを運び、戻った窓で足りない分を測り直す。

### 判断13: 型に関係ない部品は、全部の型でそろえる

コード・コールアウト・箇条・引用・表は、型に関係なく Markdown の書き方として現れる。
**部品の形を型ごとに変えると、同じ書き方が型によって違って見え、型に当たらないノートは部品の形を受け取れない。**
型が変えるのは、見出しの役割（目的・注意点・概要など）に意味を持たせた層3だけにする。

### 判断14: コードの枠はテーマに関わらず暗い窓にする

コードは本文と読み方が違い（字の形・行の切れ目・記号の多さ）、暗い窓に入れると紙面のどこからがコードかが一目で分かる。色分けの色も暗い窓の上でそろえられる。
**ダークでは紙より暗い窓になり、「紙の上の部品は紙より明るい」順（5.6）の外に出る。** 窓は部品の段ではなく、紙に開けた穴として扱う。

### 判断15: コードの色分けは、自前の小さな切り分けで3つの言語の4種だけ

色分けのライブラリを入れると依存が増え、更新の確認が要る（→ [dependency_policy](../system/dependency_policy.md)）。
Vault のコードはほぼ Python で、ほかは Kotlin とシェルが主なので、3つの言語でほとんどの枠が色分けされる。
**4種（キーワード・文字列・コメント・数字）に限れば、行ごとの切り分けで足り、純関数として JVM テストに閉じる。** 色分けは補助で、色が無くてもコードは読める。

### 判断16: インラインのコードは文字の背景で描き、角丸と余白を付けない

角丸と前後の余白を付けるには、字の幅を変える置き換えが要る。**字の幅が変わると、見開きが割った段落の残りを組み直したときに行の切れ目がずれる**（→ 判断4）。
淡い面と等幅の字で、インラインのコードは本文から見分けられる。

### 判断17: 背景は既定で淡くし、オプションで今のグラデーションに戻せる（2026-11-28、オーナー判断）

区切り1では、紙の上にコールアウトの色の面や暗いコードの枠が載る。**背景まで鮮やかだと、それらと色が張り合う。** 既定は淡くする。
一方で、今のグラデーションは読む画面の気分を作っていて、気分で戻したいときがある。場は何も表さないので、強さを選ばせても割り当ての表（→ [bearing_channels](../system/bearing_channels.md)）に触れない。
**色の組と強さを分けて持つ**のは、背景の3色を選ぶ機能を後で足すときに、強さの切り替えを作り直さないため。

### 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 地を年代の紙（生成り）にする3案 | 配色を選ばせることになり、年代の紙の意味（古さ）が既定の見た目に溶ける。年代の紙はオプションのまま、プレートの地に載せる |
| 区切り1を層1だけ（全ノートを今の部品のまま標準の書式で組む） | 紙面がほとんど変わって見えない（判断3） |
| 太字にマーカーを敷く | 蒸留の候補を淡いマーカーで見せる案と見分けにくくなる。太字は太字のまま |
| 型を分野（AI）で決める | 判断1 |
| 等幅や本文の書体を区切り1で同梱する | APK が数百KB増える。端末の書体で始め、実機で読み比べて足りなければ決め直す |
| コードの枠に行番号を付ける | 選択してコピーした文字に番号が混じる。見開きで割った後の番号の扱いも要る |
| 色分けのライブラリを入れる | 判断15 |
| 余白をブロックの組み合わせごとに持つ | 判断4 |
| ダークの場を平らな紺にする | ライトの場と同じく3色の気配を残す。平らにすると読む画面だけ別の世界に見える |
| 最初の1枚を引く前の場に淡い罫を敷く | 書き込む道具に見えるが、このアプリはノートを編集しない（汎用の編集はしない） |

## 9. 品質要件

- **コントラスト:** 紙の上の文字はすべて 4.5:1（→ [ui_design_principles](../system/ui_design_principles.md) §1）。`AppColorContrastTest` で強制する:
  - 藍のリンクを、年代の紙の4段すべてとダークの夜の紙の上で
  - コールアウトの頭の色と中身の字を、それぞれの面の上で
  - コードの字と色分けの4色を、暗い窓の上で
  - インラインのコードの字を淡い面の上で、番号の札の字を札の上で
  - 見出しの帯の文字とボタンの輪郭を、淡い3色の場と今のグラデーションの両方の上で（今のグラデーションは今の検査が持つ）
  - 見出しの線と箇条の点は装飾で、見出しは大きさと太さでも見分けられる
- **色だけで伝えない:** コールアウトの種類は言葉で伝え、色と記号は補助。色分けは補助で、色が無くてもコードは読める。最初の1枚を引く前の場の失敗は言葉で伝える（→ [ui_design_principles](../system/ui_design_principles.md) §1 の 1.4.1）
- **文字の倍率:** 1行の上限は dp で決め、倍率を上げた人の字数を減らす（→ 判断6）。見開きの入る条件は今のまま
- **性能:** 色分けの切り分けと型の判定は本文の長さに比例し、解析のジョブの中で回す。描く Main で切り分けない
- **依存:** 足さない（書体もアイコン集も色分けのライブラリも入れない）
- **アニメーション:** 足さない

## 10. 検証と受け入れ条件

- **JVMテスト:**
  - 型の判定: `cssclasses` が骨格より優先される／骨格の語は頭の記号と番号を外して照らす／2つ以上かつ多いほうに決まる／同数や1つだけでは決まらない／どれにも当たらなければコードの枠で決まる／読めない frontmatter は飛ばす
  - 解析: コードのブロックが言語の札を残す／札の無い枠は札を持たない／AI へ渡す抜粋と知識索引の結果が今と変わらない
  - 色分けの切り分け: 3つの言語それぞれでキーワード・文字列・コメント・数字を切り分ける／閉じていない文字列や複数行の文字列で落ちない／知らない言語と札の無い枠は切り分けない
  - 題の欄: 道筋は Vault の直下で空になる／タグは今の frontmatter の読み方の結果をそのまま使う
  - 書式の関係: 題 > H1 > … ≥ 本文の大きさの順／アプリの書式に斜体が無い／字間が0／**見開きの定数が本文の段落の書式と一致する**（値ではなく関係を見る）
  - 色: §9 の組み合わせがすべて 4.5:1／ダークで場の3色 < 紙 < 紙の上の部品の明るさの順
  - 形: 読む面の角が眺める面より大きい（`BearingChannelTest` は今のまま通る）
  - 案内の文: `「」` で指す名前が、画面にあるボタンの文字として実在する（ソース走査）
  - 末尾の余白: 窓を替えて戻すと、余白が戻った窓で要る分を超えない（`EndSpaceTest`）
  - 場の強さ: 淡い3色が今の3色の色相を保ち、今のグラデーションより明るい／ダークでは設定によらず夜の紺
- **instrumentation:**
  - 見開きの計測と描画が一致する（今のテストを新しい書式で通し、コードの枠・コールアウトの面・引用・題の欄が割れる場合を足す）
  - 全画面を出入りした後に末尾へ送ると、最後の段落が見える（`EndSpaceUiTest` に足す。今は戻った直後の見出しの位置までしか見ていない）
- **実機確認:**
  - ライトとダーク・スマホと開いた Fold（通常表示・机・見開き・全画面・右の並べ読み）で、紙面と部品が組まれて見える
  - コードの枠（色分けする言語・しない言語・札の無い枠）・4つのコールアウト・番号付きの箇条・インラインのコード・引用・表を持つノートで、それぞれの形が出る
  - 見開きでコードの枠・コールアウト・引用がページをまたぐとき、片ごとに描かれ、頭の行が最初の片だけに出る
  - 年代の紙をオンにしてプレートの地に色が載る／ダークでは載らない
  - 背景を鮮やかにするオプションの切り替えで、読む画面と机の上端の帯が淡い3色と今のグラデーションの間を行き来する
  - 文字の倍率 1.3 で、1行の上限と見開きの入る条件がどちらも効く
  - 最初の1枚を引く前の場（Vault を選ぶ前・選んだ後・空の Vault）と、全画面でリンクを開いて読み込む間に古い案内が出ないこと
  - 末尾に近い見出しから開いて全画面を出入りし、末尾へ送って最後の段落が見えること
- **実機で起こせないので自動テストが持つ順序:**

  > **該当なし:** 区切り1は非同期の処理を足さない。

- **保証していないこと:**
  - 型に意味のある部品（区切り2・3）。区切り1では型の判定の結果が画面に出ない
  - 3つの言語のほかの色分け。色分けの正確さは4種の字句の切れ目までで、文法の解析はしない
  - 約物の詰めの効き方と等幅の字の形は端末の書体による
  - 和文と欧文の間のアキ
  - 見開きの版面（ノドと小口）

## 11. 既知の制約・未解決事項

- **和文と欧文の間のアキは入らない。** Compose の文字組みには自動で入れる手段が無く、文字列に空白を足すと本文を書き換えたのと同じになる（選択・引用・痕跡の位置がずれる）
- **区切り2で決めること:** 📶 レベルをタイトルの下へ動かすか（表示の順が Obsidian と変わり、見開きの計測も同じ並びで扱う）／
  型が読み取る書き方の約束（「項目：値」の箇条・【件名】・❌ before と ✅ after・`[!quote]`）の範囲／内側の部品の角の段
- **区切り3で決めること:** 読書ノートの紹介文の帯の色の強さ（部品の色で、読む面の地の色ではない）
- **後の案:** 型で見出しの役割が分かれば、注意点だけを集めて読む冊子も作れる。暮らしの型は後で足す
- **右の並べ読みに層3を広げるか**は区切り2で決める。区切り1では右も層1・層2で組む
