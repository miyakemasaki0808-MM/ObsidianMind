## 1. 概要

ノートを開くと関連ノートが並ぶ。**その関連ノートの本文から、いま読んでいるノートの主張と最も食い違う一文を1つだけ選び、
原文のまま見せる。** 出どころの行を押すと、そのノートへ移る（開いた Fold の余白ペインでは右で並べて読む）。

関連ノートは「似ている」で並ぶ。思考をもう一段深めるのは似た意見ではなく反対の意見なので、
**同じ Vault の中の、過去の自分が書いた反対意見**を1文だけ差し出す。生成はしない。AIは選ぶだけである。
候補が無ければ何も出さず、AIが「食い違うものは無い」と答えても何も出さない。

北極星の判断基準「Rediscover→Reflect のループを濃くするか」に、
**関連ノートの既存の経路に選択を1回足すだけ**で応える。

## 2. ゴールと非ゴール

### ゴール
- 関連ノートの中から**反対の意見**を1文、原文のまま見せる
- Nano の呼び出しは**ノートあたり1回**。入力は既存の抜粋と候補ブロックの形をなぞる
- 失敗・非対応・空振りは**黙って劣化**する（自動起動の機能の一般則 → [background_ai_ux](../system/background_ai_ux.md) §6）

### 非ゴール
- **生成しない。** 反証を書かせない。要約もしない。出すのは他ノートの原文1文だけ
- **今のノート側の「どの主張と食い違うか」は示さない**（→ 判断の「採らなかった案1」）
- **正誤を判定しない。** 食い違いは「確かめたくなる」までで、どちらが正しいかは言わない
- **本文へ書かない。** 本文を書き換えるのは蒸留だけ（→ [ADR-0004](../decisions/ADR-0004-do-not-rewrite-vault-body.md)）
- **モデルDLを始めない。** 未取得・DL中は黙って諦める（分野判定と同じ）
- **進捗を見せない。** 「探しています…」を出さない。結果があるときだけ枠が現れる
- **関連ノートの選び方には手を入れない。** 関連ノートの候補・再ランク・プロンプトは変えない

|---|---|---|

| 反証の一文（余白ペイン） | 開いた Fold の余白ペインで、「このノートの関連」の直下に**畳まずに**出る | 同上。ペインを出しているとき |
| 出どころへ移る | 関連タブでは、出どころの行を押すとそのノートへ切り替わる（関連ノートのタップと同じ） | 枠のタップ |
| 出どころを右で開く | 余白ペインでは、出どころの行を押すと右で並べ読みになる。今のノートは替わらない | ペインのタップ |
| 枠が出ない | 何も出ない。理由も出ない | 候補ゼロ／AIが `NONE`／非対応・未取得・DL中・失敗／ノート切替で追い越された |

## 4. 現在のユーザーフロー

1. ノートを開く（Rediscover・冊子の「これを読む」・さがす・関連のいずれか）
2. 要約・分野判定・関連ノートが自動で始まる（既存）
3. 関連ノートの結果が届く → 関連タブに関連ノートが並ぶ（既存）
4. **同じ1手で反証の選定が始まる。** 画面には何も出ない
5. 関連ノートに出た最大8件の本文（先頭8KB）を読み直し、**主張の形をした文**を規則で列挙する
6. 今のノートの抜粋との語の重なりで候補を並べ、上位12件を `X01..` のIDで Nano に渡す
7. Nano がIDを1つ返す → 関連タブの関連ノートの下（Fold のペインでは「このノートの関連」の直下）に枠が出る。`NONE` なら何も起きない
8. 出どころの行を押す → 関連タブならそのノートへ移り 1 へ戻る。ペインなら右で開き、「このノートへ移る」で移れる

**中断:** ノートを切り替えると 5〜7 は止まり、旧ノートの一文は新しいノートの画面に出ない。
**再実行:** モデルDLの完了で関連ノートが呼び戻されると、反証も同じ経路で呼び戻される。

## 5. 機能仕様

- **前提条件:** 関連ノートの結果に1件以上のノートがあり、Nano が `Ready`
- **入力と出力:** 入力は今のノートのタイトルと本文、関連ノート（AI推薦と決定的）、関連ノートの本文の先頭。出力は「原文の1文と出どころのノート」の組か、無し
- **上限:** 下の定数表
- **状態遷移:** 無し → 1文。**読み込み中と失敗の段を持たない**
- **保存と寿命:** 保存しない。ノート単位（ノートを替えると消える）。蒸留の本文差し替えでは残る
- **画面遷移:** 関連タブでは出どころへ移る。余白ペインでは右で開く（並べ読み → [margin_pane](margin_pane.md) §5）
- **他機能との連携:** 関連ノートの完了に鎖でつなぐ。読み出しの口は関連ノートの再ランクと同じ
- **エラー／AI非対応／キャンセル時:** 下の「エラー・非対応・取り消し」

### 候補の列挙（非AI・[`scanRebuttalClaims`](../../../app/src/main/java/com/example/newproject/domain/RebuttalClaimScanner.kt)）

**規則で列挙し、選別だけをAIに任せる。** 規則は文の形だけを見て、反証かどうかは見ない。入力は関連ノート1件の本文（先頭8KB）。
**候補は枠に原文のまま出すので、文の単位と文字は本文の画面と同じ解釈器で決める**（→ 判断8）。

| 手順 | 規則 |
|---|---|
| 1 | コードフェンスの中とリンクだけの行を**空行に替える**（詰めると前後の段落がつながる。表の行は替えない） |
| 2 | 本文の画面と同じパーサ（`parseMarkdownBlocks`）でブロックに分ける。frontmatter・見出し・コード・画像・水平線は候補にしない |
| 3 | 単位は段落・リスト項目・引用の段落（空行まで）・表の本文のセル。**表の見出しの行は列の名前なので候補にしない** |
| 4 | 段落の折り返しは**日本語の側では空白なしで**つなぐ（`joinSoftWrappedLines`）。改行の両側が英数字や記号のときだけ空白を入れる。どこで折り返しても同じ文になる |
| 5 | 文字は**本文に見えるとおり**にする（`inlineVisibleText`）。コードの中身は記号ごと残し、リンクは表示名（`[[note|表示名]]` は表示名）、強調は記号だけを落とす |
| 6 | 文へ割る。括弧の内側では切らない。**英文はピリオドでも割る**が、小数・版番号・略語・頭文字・省略記号では割らない |
| 7 | 長さ 12〜120 字、文字か数字を含み、終止符（`。！？!?.`）で終わる |
| 8 | **疑問文を落とす。** 再会カードが問いとして拾う判定と同じ正規表現を使い、真なら捨てる |
| 9 | 同一の文を1つに畳み、原文順を保つ |

**何を候補にするかはこの機能が持つ。** 再会カードと冊子の扉は別の前処理（`MarkdownPlainText.kt`）を使い、ここを直しても変わらない。

**`docs/` を代理コーパスにした実測（2026-10-11）。** 365文書のうち343（93%）が1文以上の候補を返した。
無作為の40文に、ラベル・コード断片・セルをつないだ表の行は無かった（表はセルごとに候補にする）。

### 順位付け（非AI・[`rankRebuttalCandidates`](../../../app/src/main/java/com/example/newproject/domain/RebuttalCandidateRanking.kt)）

Nano は先頭の候補を選びやすいので、**今のノートと話題の近い文を先頭へ寄せる**（関連ノートの再ランクと同じ狙い）。

```
score(claim) = diceCoefficient(textBigrams(今のノートの抜粋), textBigrams(claim))
```

1. ノートごとに score 降順で上位3件。同点は原文順
2. 全ノートを混ぜて score 降順。同点は**関連ノートの並び**（AI推薦 → 未リンクの決定的 → リンク済み）、次に原文順
3. 先頭12件。この順で `X01..` を振る

**score が 0 でも捨てない。** 日本語の短文は bigram が重ならないことが普通にある。
**今のノート側の材料は、AIへ渡す抜粋と同じ文字列**にする — 順位付けとAIが別の本文を見ると「近いから先頭に置いた」が成り立たない。

### プロンプト（[`buildRebuttalPrompt`](../../../app/src/main/java/com/example/newproject/ai/PromptBuilder.kt)）

- 候補行は `X01 | 文`。**出どころのタイトルは載せない**（食い違いの判定に要らず、入力を増やすだけ）
- 候補ブロックは取り分で閉じ、超える行は**飛ばして先へ進む**。飛ばした候補は許可するIDにも入れない
- 指示文は英語。「今のノートの主張と最も直接に食い違う1文」を選ばせ、同意・言い直し・補足の文は除かせる。
  **IDだけ**を返させ、食い違うものが無ければ `NONE` を返させる

### 応答の扱い

| 応答 | 扱い |
|---|---|
| 許可したID1つ（装飾・桁落ち・大小文字は吸収） | その候補の原文を、出どころの関連ノートと組にして状態へ書く |
| `NONE`（前後の飾りは許す） | 何も書かない。**失敗ではない** |
| 空・候補外のID・散文 | 何も書かない。約束違反だが、次にノートを開いたとき素直に試し直す |

**表示する文は手元の候補から引く。** 応答の本文は使わない（言い換え・翻訳が混ざると「本文にある1文」でなくなる）。

### エラー・非対応・取り消し

- 可用性は網羅 `when`。**`Ready` 以外の4値はすべて「何もしない」**で、本文も読まない。`downloadModel()` を呼ばない
- 可用性の確認そのものが落ちたときも何もしない
- 本文の読み直しに失敗した関連ノートは**そのノートだけ落として続ける**
- 生成の例外（タイムアウト・途切れ・AICore の拒否）は握って何も書かない。理由を画面に出さない
- `CancellationException` は再throw。ノート切替後の後着は requestId で `update` の直前に1箇所で落とす
- **自動で走る生成なので、生成の直前に門番を通す**（→ [background_ai_ux](../system/background_ai_ux.md) §7）。
  関連ノートが既に通っていればすぐ返る
- 連続失敗の抑制は持たない（下の判断5）

### 画面

- **関連タブ:** 関連ノートの枠の下に、同じ `PanelBlue` の面で1枠。見出し「反証の一文」（`AccentText`・13sp・Bold）、
  添え書き「いま読んでいるノートと食い違う、別のノートの一文」（`OnSurfaceFaint`・11sp）、本文の一文（`OnSurface`・14sp）、
  区切りの下に出どころのノート行（関連ノートの行をそのまま使う）
- **余白ペイン（開いた Fold）:** 「このノートの関連」の直下に、**関連の一覧を畳んでいても出す。**
  見出しはペインの並びに合わせて `OnSurfaceMuted`・13sp。中身（添え書き・一文・出どころの行）は関連タブと共有する。
  **出どころの行は関連の候補と同じく右で開く**（→ 判断7）
- スマホの「この部分」のシートには出さない（関連ノートの一覧もペインにしか無い）
- **色を足さない・形を足さない。** 面の色は年代と分野が持ち、形は面の役割が持つ（→ [bearing_channels](../system/bearing_channels.md)）
- **読み上げ:** 見出しは見出しとして読む。出どころの行は「開く」の操作名を持つ（関連ノートの行も同じ）
- 状態が null なら描かない。読み込み中の表示も、失敗の表示も無い

## 6. 状態とデータ

**ノート単位の状態を1つ足した。契約2箇所へ登録してある**（→ [architecture](../system/architecture.md) 判断2）。

| 項目 | 内容 |
|---|---|
| 状態型 | `RebuttalSentence(text, source)`。`source` は関連ノートの `RelatedNote` |
| `NoteUiState` の欄 | `rebuttalSentence: RebuttalSentence?`。**null が「出さない」**（Loading／Error の段を持たない） |
| Writer | `RebuttalStateWriter`（担当の欄だけを書ける） |

| 永続化 | **しない。** 痕跡サイドカーにも端末内ストアにも書かない。開き直せば選び直す |
| 蒸留保存後の本文差し替え | **残す。** 一文は他ノートの原文なので有効なまま |
| バッジ／通知 | 無し。結果は関連タブ（ペイン）を開けば見え、後から辿れるので未確認管理を持たない（→ [background_ai_ux](../system/background_ai_ux.md) §4） |

**欄を読む箇所。** `RelatedTab`（枠）と `NoteReaderTab`（ペインへ渡す `PaneRelatedInputs.rebuttal`）の2箇所だけ。
`RelatedNotesState` には欄を足していないので、それを読む編む冊子・ペインの関連一覧は変わらない。

## 7. システム設計

```
NoteViewModel.fetchRelatedNotes（窓口のノート単位ジョブ）
 └─ RelatedNotesUseCase.findRelated → RelatedNotesResult.Success
      └─ NoteSessionCoordinator.completeRelatedNotes(...)        ← 1手
           ├─ 関連ノートの状態を Success にする
           └─ RebuttalController.select(...)
                ├─ 候補を取る関連ノート: AI推薦 → 未リンク → リンク済み、参照で重複を畳み最大8件
                ├─ checkAvailability() — Ready 以外は何もしない（DLしない・本文も読まない）
                ├─ readContent(ref) を順に呼ぶ（8KB境界読み出し。失敗した件は落とす）
                ├─ withContext(excerptDispatcher) { 抜粋 } / { 列挙 → 順位付け }
                ├─ 候補ゼロなら終わり
                ├─ buildRebuttalPrompt → 門番 → generate
                ├─ NONE・空・候補外・例外 → 終わり（何も書かない）
                └─ requestId を確かめてから状態へ書く

RelatedTab ── uiState.rebuttalSentence?.let { RebuttalPanel }          （押すとそのノートへ移る）
MarginMemoSheetContent ── PaneRelatedInputs.rebuttal → PaneRebuttal   （押すと右で開く）
```

**本文の読み出しの口は関連ノートと同じ**（窓口が `readNoteSnippet` をラムダで渡す）。Controller は Android の型を持たない。

## 8. 設計判断と代替案

### 判断1: 関連ノートの1回とは別に、Nano を1回呼ぶ

関連ノートのプロンプトへ「ついでに反証のIDも返せ」と足せば呼び出しは増えない。採らないのは、
**候補文は関連ノートが選ばれた後でないと8件に絞れない**ことと、1つの出力枠（256トークン）に2種類の答えを求めると
**両方が薄くなる**ことによる（→ [ai_input_excerpt](../system/ai_input_excerpt.md)「出力枠256トークンはゼロサム」）。

### 判断2: 起動契機は「関連ノートの完了」に鎖でつなぐ

ノートを開いた瞬間に独立して走らせない。関連ノートの結果を材料にするので、その完了を契機にすれば
**要求の世代・取り消し・DL完了後の呼び戻し**を関連ノートと共有できる。結果を出す手と選定を始める手は
`completeRelatedNotes` の1手に閉じ、片方だけを呼ぶ経路を作らない。
門番は関連ノートが通った後なのでほぼ素通りだが、**自動で走る生成は門番を通す**という横断の規則に従って置いている。

### 判断3: 本文は読み直す。関連ノートのキャッシュを太らせない

関連ノートの候補キャッシュに候補文を持たせれば追加I/Oはゼロになるが、**最大40候補すべてで列挙を走らせ**、
キャッシュが膨らむ。使うのは最大8件なので、**その8件だけを同じ口（8KB境界読み出し）で読み直す**ほうが
CPU もメモリも小さい。読む経路を2本にしない。

### 判断4: 候補は「主張の形をした文」を規則で列挙し、選別だけをAIに任せる

「反証かどうか」を文の形だけで決めることはできない。一方で「問いではない」「ラベルではない」「コードではない」は
規則で落とせる。**規則は取りこぼさない側へ、選別は落とす側へ寄せる**（再会カードと同じ配分）。
順位付けを非AIで持つのは、Nano の位置バイアスに対して**話題の近い候補を先頭へ置く**ためである。

### 判断5: 失敗も空振りも黙る。抑制も記録も持たない

自動起動の機能は黙って劣化する。分野判定は全ノートで走るので連続失敗の抑制を持つが、
反証は関連ノートの結果が届いた回にしか走らず、**永続もしないので「永久停止」を作る材料が無い**。
空振り（`NONE`）を記録しないのは、候補が関連ノートの選び方で変わり、同じノートでも次回は別の候補が並びうるため。

### 判断6: 出どころへの導線は関連ノートの行をそのまま使う

新しい行の部品を作らない。関連ノートの行を使えば、タップの先・`linked` の表示・更新日が揃い、
**同じ意味の行が2つの見た目で並ぶ**ことを避けられる。

### 判断7: 開いた Fold の余白ペインでは「このノートの関連」の直下に畳まずに出し、押すと右で開く（2026-10-11、オーナー判断）

机の画面ではタブのレールを畳むので、関連タブだけに出すと**一文が目に入らない。** 関連の一覧の中に入れると、
一覧は畳んで件数だけを出すので同じく目に入らない。そこで一覧の直下に、畳まずに1文だけ置く。
押した先は**ペインの関連の候補と同じく右で開く**（今のノートは替えない → [fold_experience](../system/fold_experience.md) の不変条件）。
反対の意見を今のノートの隣に並べて読めるのは、机の使い方そのものである。同じ面の中で「関連の行を押すと右で開く」を揃える。

### 判断8: 候補の単位と文字は、本文の画面と同じ解釈器で決める

枠には「本文にある一文」を原文のまま出すので、候補が本文の見え方とずれると、AIが正しく選んでも**別の主張**が出る。
記法を正規表現で別に落とすと、コードの中の `|` や `*` が消え、`[[note|表示名]]` がリンク先の名前に化けた。
行ごとに割ると、段落の中で折り返した1文から条件節が落ち、無条件の主張になった。
そこで**段落の切れ目は本文と同じパーサ、見える文字は本文と同じインラインの解釈器**から作る（→ [lessons L51](../lessons/L51.md)）。
描いた文字と見える文字が一致することは `InlineMarkdownTest` が固定する。

本文の画面と変えているのは**折り返しのつなぎ方だけ**である。本文は空白でつなぐが、候補は日本語の側では空白を入れない —
空白でつなぐと、どこで折り返したかで文が変わる。

### 採らなかった案1: 今のノート側の主張も対で示す

「今のノートのこの文と、あのノートのあの文が食い違う」と対で見せる案。分かりやすいが、
今のノートの候補文もプロンプトへ載せる必要があり**入力が倍になる**うえ、出力に2つのIDを求める。
まず片側だけで**実機の体感を見てから**判断する。

### 採らなかった案2: 再会カードの枠に出す

再会カードは排他1件で、枠を取り合う案が既にある。反証は Rediscover 以外の入口でも成立するので、
**関連タブに置けば枠の取り合いに入らない。**

### 採らなかった案3: 反証の一文を痕跡サイドカーへ保存する

「前回はこの反証が出た」を残す価値はあるが、痕跡のスキーマを上げ、退避・復元・併合を直す費用が付く。
**開き直せば数秒で選び直せる**ので持たない。

## 9. 品質要件

- **性能:** 追加のI/Oは最大8件の8KB境界読み出し。列挙・順位付け・抜粋は `Dispatchers.Default`。Nano は1回、関連ノートの後ろ
- **プライバシー:** 候補文と抜粋はプロンプトへ入るが端末外へ出ない（→ [ADR-0002](../decisions/ADR-0002-on-device-ai-only.md)）
- **データ保護:** 本文にもサイドカーにも書かない。壊れてもユーザーのノートは失われない（ベストエフォート側）
- **アクセシビリティ:** 枠の見出しは見出しとして読む。出どころの行は操作名「開く」を持つ。色だけで意味を持たせない
- **端末制約:** Nano 非対応端末では枠が一度も出ない。それ以外の画面は変わらない

  - `NoteSessionCoordinatorTest` — 関連ノートの完了から選定が始まる／ノート切替で実物の Controller の選定が止まり後着しない／リセット検査の入力に欄を登録

- **instrumentation:** `RebuttalPanelTest` — 関連タブで一文と出どころが描かれ、押すと出どころへ移る／null で枠を出さない／
  ペインで関連を畳んだままでも一文が出て、押すと右で開く／null で出さない。**実生成は通していない**（`OnDeviceGenerationTest` の未保証に列挙）
- **実機確認:** ケースは実機検証の担い手が起こす（[共通手順](../../review/device_validation/README.md) の「誰が行うか」）。確かめる面は次のとおりで、Nano 非対応の端末を除いて確かめてある
  - 反対の主張を書いた関連ノートがある一時Vaultで、枠が出て**本文にある文がそのまま**出ること。押すと出どころへ移ること
  - 食い違う文が無いノート・関連ノートが0件の Vault で、枠が出ずエラーも出ないこと
  - 生成中にノートを切り替えて、旧ノートの一文が新しいノートに出ないこと
  - 枠が出た状態で蒸留を保存しても、回転しても枠が残ること
  - 開いた Fold の余白ペインで、関連の一覧を畳んだまま一文が見え、押すと右で並べ読みになること
  - Nano 非対応の端末で枠が一度も出ず、他の画面が変わらないこと
- **実機で起こせないので自動テストが持つ順序:** 実機検証の選抜では射程外として扱う（→ [共通手順](../../review/device_validation/README.md) の「実機検証前」）
  - 取り消しに従わない生成が、ノートを離れた後に返る（本番の `AiClient` は取り消しに従う）
  - 同じノートで選び直した後に、前の要求の生成が返る（モデルDLの完了による呼び戻しと前の生成の交錯）
  - 関連ノートの本文の読み直しが、一部のノートだけ失敗する
  - 可用性の確認そのものが例外で落ちる
- **保証していないこと:**
  - **選ばれた文が本当に「反証」かは測らない。** 似た話題の文が選ばれることは普通に起きる
  - **`NONE` の頻度は未測定。** 多ければ「候補があるのに何も出ない機能」に見える
  - **候補は本文の先頭8KBから拾う。** 長いノートの後半にある反対意見は届かない
  - **同点の並びと score の扱いは初期値。** 実データで当て直す
  - **AICore の短い時間窓の回数制限**に対して、自動の呼び出しが1回増える影響は測っていない
  - Fold の物理的な開閉をまたいで枠が残るかは、回転と同じ経路（ViewModel の状態）であることまでしか確かめていない

## 11. 既知の制約・未解決事項

| | |
|---|---|
| 自動の呼び出しが1回増える | 要約・分野・関連の後ろに並ぶ。Mutex 直列なので、枠が出るまでの時間は前の生成の合計に依存する |
| 先頭8KBしか見ない | 読み直しが関連ノートと同じ口を使うため。後半を見るなら口を増やす判断が要る |
| 「前提の更新」との区別が無い | 時間による更新と食い違いは同じ候補集合から出る。プロンプトの基準で分けているだけで、実機で混ざるなら種別を持つ判断が要る |
| 文の言語が混ざる | 日本語のノートに英語の候補が並ぶと bigram が重ならず、順位付けが効かない |
| 表のセルが候補に入る | 理由を表の中に書く文書があるので、本文のセルは文の形をしていれば候補にする。AIの選別に任せる |
| 引用は本文と違う形で1文になる | 本文の画面は引用を行ごとに描くが、候補は空行までを1段落としてつなぐ。折り返した1文を割らないため |
| 英文の略語は一覧にあるものだけ | 一覧に無い略語の後に大文字が続くと、そこで割る |
| Nano 非対応の端末で確かめていない | 対象の端末が無い。対応端末の設定を変えて作ることはしない |
