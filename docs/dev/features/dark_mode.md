**状態:** Implemented — 稼働中・実機確認済み
**最終検証:** 2026-08-12 / `521768b`（テーマの伝播経路を実装と突合。トークン値とコントラスト比は `AppColorContrastTest` が固定しているため個別には数えていない）

## 1. 概要

オプション画面のトグルで明暗を切り替える。**OS設定には追従しない**ので、この値が唯一の真実。

## 2. ゴールと非ゴール

### ゴール
- 暗所で本文が読める（WCAG AA を満たす）
- **ブランドの見え方を保つ**（グラデーションを捨てない）

### 非ゴール
- **システム追従をしない**（→ §8 判断1）
- **Vigilith の素材を作り直さない**（→ §8 判断4）

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 明暗の切替 | 全画面が暗い配色になる | オプション画面のトグル |
| 設定の永続化 | 次回起動時も維持される | 常時 |

## 4. 現在のユーザーフロー

1. オプション画面のトグルを押す
2. `AppPreferences.darkTheme` が更新される
3. `AppTheme` が `DarkAppColors` / `LightAppColors` を切り替える
4. アプリ全体が即座に切り替わる

**伝播経路:** `NoteViewModel` が `MutableStateFlow(preferences.darkTheme)` を持ち、
`MainActivity` が `collectAsStateWithLifecycle()` で受けて `AppTheme(darkTheme = …)` へ渡す。
**`NoteUiState` を経由しない** — 状態17項目の変更でアプリ最上位まで再評価されるのを避けるため
（→ [architecture](../system/architecture.md)「状態が `NoteUiState` の外に出る例外」）。

## 5. 機能仕様

- **切替方式:** オプション画面の明示トグル。**OS設定には追従しない**
- **既定値:** ライト（既存ユーザーの見た目を勝手に変えない）
- **適用範囲:** 全画面（判断1から導かれる帰結）
- **システムバー:** XML ではなく **Compose から制御**する（→ §8 判断5）
- **紙の年代表現との関係:** **ダーク時は無効**（→ [note_age_paper](note_age_paper.md)）
- **エラー時:**

  > **該当なし:** 設定値の読み書きだけで、失敗しうる処理を持たない。

### トークンと配色の契約

**色の実値をこの文書に写さない。** トークンは20個超×明暗2値あり、写すと必ず片方が古くなる。

| 何 | 正本 |
|---|---|
| 役割トークンの定義と全色値 | `ui/theme/AppColors.kt` の `AppColorScheme`（`LightAppColors` / `DarkAppColors`） |
| コントラスト比 | **`AppColorContrastTest`**（28本）。数値をアサーションで固定している |

**守る規約:**

- **コントラスト基準は文字 4.5:1・非文字（塗りの輪郭）3:1**（→ §9）
- **塗りに使う色は必ず前景トークンを対で持つ**（`errorSurface` に対する `onErrorSurface` など）。
  対を欠くと、暗所で塗りが明るくなった瞬間に前景が破綻する（→ §8「レビューで見つかった3件」）
- **アクセント色は塗り用と文字用で2値になる。** 文字は 4.5:1 が要るので塗り用より明るい値を使う
- **ライトとダークで全トークンが別値を持つか、共有が意図的であること**を
  `AppColorContrastTest` が固定する（片方だけ定義した漏れを検出する）
- **クイズ画面はテーマに追従しない。** 元から単独でダーク配色を持つ

## 6. 状態とデータ

**永続化:** `SharedPreferences`（`AppPreferences.darkTheme`）。**Vault にも痕跡にも書かない小さな値。**

**UI状態:** `NoteUiState` の外の `StateFlow<Boolean>`。
これは「状態の単一ソース」の**意図的な例外2つのうちの1つ**で、
状態17項目の変更でアプリ最上位まで再評価されるのを避けるため
（→ [architecture](../system/architecture.md)「状態が `NoteUiState` の外に出る例外」）。

## 7. システム設計

```
OptionsScreen（トグル）
 └─ AppPreferences.darkTheme（SharedPreferences）
      └─ StateFlow<Boolean>
           └─ AppTheme  ← DarkAppColors / LightAppColors を選ぶ
                └─ 全画面
```

## 8. 設計判断と代替案

> **数値はこの節に置かない。** トークン値は `AppColors.kt`、コントラスト比は
> `AppColorContrastTest` が正本（→ §5）。ここは「なぜその判断にしたか」だけを持つ。

### なぜ死亡宣告を覆すのか

2026-07-22 のgrillでは「独自配色（ステータスバー非表示・ReadingGradient等）との**整合コスト**に対し不要」として死亡とした。判断そのものは当時の情報では妥当だった。

再オープンの理由は、**その「整合コスト」の正体を数えた結果、大半がダークモードとは独立に存在する色設計の負債だったこと**。

| 事実 | 数値 |
|---|---|
| `MaterialTheme` の適用 | **0箇所**（Material3は依存にあるが一度も通していない） |
| `AppColors.kt` のトークン | 約20個。すべて**色名ベース**（`Indigo` `Panel` `Coral`）で、明暗2値を持てない構造 |
| トークン参照 | 163箇所 |
| `Color(0x…)` の直書き | **61箇所／9ファイル**（QuizScreen 25、SectionChatSheet 9、RelatedTab 8、MarkdownRenderer 7 ほか） |
| グラデーションの重複定義 | `OptionsScreen.kt:40` が `AppGradient` と同一内容をローカル再定義（集約漏れ） |
| XML側 | `Theme.Material.Light` 固定、statusBar/navBar に `@color/indigo` 直指定、`values-night/` なし |

「色名トークン＋直書き61箇所」は、**ダークモードをやらない場合でも**配色ルール（AppColors.kt 冒頭の「ボタン3役ルール」）を強制できない状態を意味する。したがって問うべきは「ダークモードは不要か」ではなく、**「色設計を直した上でなお不要か」**である。

#### 判断1. 切替方式 — オプション画面での明示切替（システム追従はしない）

`OptionsScreen` に「ダークモード」行を置き、ユーザーが明示的にオン／オフする。`isSystemInDarkTheme()` によるOS追従は**採らない**。

このアプリの配色は Material の動的配色ではなく、ブランド由来の独自配色
（Indigo/Aqua/Coral のグラデーション＋Vigilith の月光色）。OSの設定に自動で引きずられると、
**ユーザーが意図しないタイミングで作品性のある画面が別物になる**。
「読む場所を自分で選ぶ」ための機能なので、**選択権はアプリ内に置く**。

永続化に既存の `SharedPreferences` へ1キー足すだけにしたのは、新しいストアを作るほどの値ではないため。

#### 判断2. 適用範囲 — 全画面（判断1から導かれる帰結）

段階適用（「読む」画面だけ先に暗くする）は**採らない**。

オプション画面にトグルを置いた瞬間、それは「アプリをダークにする」という約束になる。読む画面だけ暗く、さがす／AIタブは鮮やかなグラデーションのまま、という状態は**設定として破綻している**（ユーザーはオンにしたのに半分明るい）。切替方式を先に決めたことで、範囲は自動的に決まった。

ただし「読む画面と触る画面で性質を分ける」既存の思想（`ReadingGradient` vs `AppGradient`）は**ダーク側でも維持する**（判断3）。

#### 判断3. 暗所は別配色として設計する — 3色を捨てず、明度で沈める

ダークは「明るい画面を暗くしたもの」ではなく、**暗所で読むための別配色**として設計する。

**3色（Indigo/Aqua/Coral）を捨てないのがポイント。** 全面に敷いて暗く濁らせるのではなく、
**色相を保ったまま明度で沈める**（実値は §5）。
「読む画面と触る画面で性質を分ける」既存の思想（`ReadingGradient` vs `AppGradient`）は
**ダーク側でも維持し、読む画面のほうをさらに静かにする**。

| | ライト | ダーク |
|---|---|---|
| 触る画面（さがす・AI・オプション等） | `AppGradient` 全面 | **色相を保ったまま明度で沈めた面** |
| 読む画面（ノート・AI補記・OP） | `ReadingGradient` 全面（低彩度版） | **同じ解き方でさらに静かに** |
| パネル（本文カード等） | `Panel` 白系 | ベースより一段明るい面 |

> **却下した案 — グラデーションを「背景」から「アクセント」へ降格する。**
> 当初は「暗いベース面＋上端／縁にグラデーションを細く残す」、つまり
> **面積を減らして彩度を活かす**方向を採るつもりだった。
> **各画面のレイアウト変更を伴うため見送った** — 得られるのは見え方の好みで、
> 払うのは全画面の構造変更だったため。
> **色相の面積を減らす案自体は否定されていない**ので、実機で見てから再検討する余地がある。

#### 判断4. Vigilith のWebPは作り直さない

`vigilith_{idle,summary,distilling,messenger}_rich.webp` の4点は、黒曜石の胴体を `VigilithSlate #314158`（月光色）で背景から分離する前提で描かれている。暗背景ではこの分離が弱まる。

- **やらないこと:** 暗色版WebPの再生成（コストが検討全体を超える）
- **やること:** ダーク時のみ、Vigilith の背後に**低α のhalo**（`LogoPurple`／`Aqua` 系）を敷いて輪郭を確保する。既に `lensGlowAlpha` という輝度制御の概念があるので、その隣に置ける。
- **検証:** halo有無のスクリーンショット比較は実機で行う（→ §10）。

#### 判断5. システムバーはXMLではなくComposeから制御する

**実装前**の `themes.xml` は statusBar/navBar に `@color/indigo` を直指定していた。システム追従しない以上 `values-night/` は使えない（OS設定とアプリ設定が食い違う）。

→ **statusBar/navBar を透明にし、`enableEdgeToEdge()` に任せる**。テーマ切替時にXMLリソースを差し替える必要がなくなり、切替がプロセス再起動なしで完結する。`Theme.Material.Light` 固定も外す。

---

#### 判断6. トークンは色名ではなく役割名で定義する

`Indigo` `Panel` `Coral` のような**色名トークンは明暗2値を持てない**。
役割名（`surface` `panel` `onSurface` `buttonAi` …）へ置き換えることで、
同じ参照のまま明暗で別値を配れるようになる。

**移行時点の方針は「ライト値は既存値をそのまま引き継ぐ」だった。**
改名だけなら見た目に出ないので、**ダークをやるかどうかと切り離して先に払える作業**になる。
これが「色設計を直した上でなお不要か」を問える形にした。

**ただし方針が保たれたのは移行の入口までで、最終的にはライト側も一部変わった**
（AA是正など。実際に変わったものと、網羅を確認できていないことは §10）。
**「改名は見た目に出ない」は作業の入口の話であって、この機能の結果ではない。**

**値そのものは §5 の正本（`AppColors.kt` / `AppColorContrastTest`）が持つ。**

#### ボタン3役をどう決めたか

**塗りボタンに要る基準は2つで、文字とは別物である** — 塗り vs 周囲の面（非文字 3:1＝輪郭が見つかること）と、
ラベル vs 塗り（文字 4.5:1）。この2つを分けて測って初めて、次のことが分かった。

1. **Indigo はボタン色として悪くない。** ライトでは3役中唯一、塗り・ラベルとも基準を満たす。
   ダークで落ちるのは品質の問題ではなく、**Indigo の相対輝度が暗面にほぼ等しい**という物理的事情
2. **逆に Primary / Secondary はライトで既に基準割れだった**（白ラベル・Secondary は塗り自体も）。
   これは**ダークモードと無関係に今そこにある問題**
3. 3役はもともと**色相の弁別性**で選ばれており輝度は揃っていない。結果として
   各色が明暗どちらか一方でしか成立しない**鏡像の関係**になっていた

**採った解 — ダークは「塗りを明るく、ラベルは黒で統一」。**
暗面では塗りを明るく置くと、塗り vs 面と黒ラベル vs 塗りが同時に取れる。
ライトでは色ごとに白／黒を使い分けざるを得ないので、**ダークのほうがルールとして綺麗になる**。

**変わったのは `buttonAi` の1色だけ。** 色相と彩度を保ち明度だけを上げたので、
ライトの Indigo と並べても「同じ色の明るい版」に見える。**別ブランド色を増やす話にはならない。**
より暗い候補は 3:1 に対する余裕が薄く面の明度を少し変えると割れ、
より明るい候補は **Aqua との輝度差がほぼ無くなり暗所でAI系とAqua系が混ざる**ため採らなかった。

> **提案時に測った比は、暗面 `#101A2E` を前提にしている。この面は後に取り下げた**
> （`QuizScreen` が既に `#1A1C2E` / `#2A2D45` を持っていたため
> → [theme_and_ui_refactor](../system/theme_and_ui_refactor.md) 発見1）。
> **現行の比は `AppColorContrastTest` だけが持つ。** 上の結論は面を変えても向きが変わらないので残す。

**ライト側の白ラベル基準割れは、ラベル色をロール別に明示するだけで解消する** — ここは塗り色を変えない。

> **ただし「ライト側の配色は変えない」という Non-Goal は、最終的に一部破った（2026-07-29）。**
> `buttonSecondary` はライト面に対する塗り自体が基準を割っており、
> **ラベル色の明示では解消しない**（塗り vs 面の比の問題なので、前景をどう変えても直らない）。
> D案でライト側だけ差し替え、**`buttonSecondary` は明暗で別値になった**（実値は §5）。
> 経緯は [theme_and_ui_refactor](../system/theme_and_ui_refactor.md) の 2026-07-29 追記・判断3。
>
> **Non-Goal を守れなかったのではなく、守ると基準割れが残ると分かったので降ろした。**

> **実装上の落とし穴:** ラベルの白は「既定 lightColorScheme の `onPrimary`」というテーマ由来の値だった。
> `MaterialTheme` へ独自 colorScheme を渡すと **`onPrimary` が変わり全塗りボタンのラベル色が一斉に変わる**。
> **各ボタンに `contentColor` を明示してからテーマを被せる。**
> この順序を守らないと、ダークと無関係な回帰がライトに出る。

### Non-Goals（やらないと決めたこと）

- **OSのダークモード追従**（判断1）
- **Material dynamic color / Material You**（ブランド配色と衝突する）
- **AMOLED純黒（#000000）**（ロゴ由来の `LogoNavy #050E1D` を使う。純黒はグラデーションの階調が死ぬ）
- **Vigilith WebPの暗色版**（判断4）
- **ライト側の配色変更**（トークン名の付け替えのみ）。**ただし基準割れの解消と引き換えに降ろした** — 実際に変わったものは §10
- **画面ごとの個別テーマ設定**（「この画面だけ暗く」は作らない）
- **Markdownのシンタックスハイライト新設**（既存のグレー7色を意味トークンに寄せるだけ）

### 実施判断

**結論: 進める。ただし条件つき。**

- **払う価値がある部分（ダークモードの可否と無関係に得):** トークンの意味ベース化、直書き61箇所の回収、`OptionsScreen` の重複グラデーション解消、ボタン文字色の明示。これは Vigilith 周辺のリファクタ（R-1〜R-4）と同じ「触るなら今」の領域。
- **ダークモード固有で増えるコスト:** ダーク値の決定、Vigilith halo、システムバーの透明化、切替UIと永続化、コントラストテスト。
- **当初想定した中止条件は消えた:** 初版では「Indigoのダーク版が別ブランド色になる」ことを最大の分岐点としたが、ボタン3役の再評価で**変更は `ButtonAi` の明度のみ（色相・彩度は不変）1色**に収まると分かった。ブランド色を増やす判断は不要。
- **むしろ前倒しの理由が増えた:** ライト側の白ラベル基準割れが判明した。これはダークをやらなくても直すべきもので、R-4 の `contentColor` 明示と同じ作業で片付く。

### 提案から変わった点（実装の結果）

- **`Indigo` はボタン以外にも約30箇所で文字色として使われていた**（AIタブの見出し・チャット・
  関連ノート・補記結果・再会カード）。暗面では文字として基準に届かないため、役割トークン
  `accentText` を新設して置き換えた。**文字は 4.5:1 が要るので塗り用より明るい値になる** —
  **塗りと文字でアクセント色が2値になる**のが実装上の帰結（→ §5）。
- **下部ナビ／レールもトークン化した。** `Indigo` 固定のままではダークで明るい帯が残るため、
  `NavBar` を新設。
- **クイズ画面はテーマに追従させない。** 元から単独でダーク配色であり、ライトでの見た目を
  変えないため固定のまま残した。ダークでは自然に周囲と馴染む。
- **判断4のhaloは実装した**（ダークのみ、`LogoPurple` 系の低αな放射グラデーション。値は §5 の正本）。効き具合は実機判断。

#### レビューで見つかった3件（修正済み）

いずれも「ライトでは成立していた組み合わせが、暗所で裏返る」型。**文字色として定義した色を塗りに流用していた**のが共通の原因で、ダークで塗りが明るくなった瞬間に前景の白が破綻した。

| 指摘 | 症状 | 修正 |
|---|---|---|
| `enableEdgeToEdge()` の既定 | システムバーのアイコン明暗を**OSの uiMode** から決める。アプリのテーマはOSと独立なので「OSライト＋アプリダーク」で暗い背景に暗いナビアイコン | `isAppearanceLightNavigationBars = false` を明示固定。ナビの下地は明暗どちらも暗い側なので切替不要 |
| `errorText` / `dangerAction` を塗りへ流用 | 暗所で明るい赤＋白文字＝2.52〜2.78 | 塗り用に `errorSurface`／`onErrorSurface`／`onDangerAction` を新設し、**塗りと前景を必ず対で持つ**構造へ |
| Vigilith Ready バッジ | `Indigo` 固定のため暗背景に対し 2.20（輪郭が出ない） | `accentSurface` ＋ `onAccentSurface` へ |

**教訓:** 役割トークンを「文字用」と「塗り用」で分けていなかったのが根本原因。`AppColorScheme` では塗りには必ず `onXxx` を対で定義する。`AppColorContrastTest` に対の検証を追加した。

### ライト側で実際に変わったもの

**「ライト側の配色は変えない」は Non-Goal として掲げたが、守り切っていない。**
基準割れの解消と引き換えに降ろした。**確認できているのは次の4つ。**

| 変わったもの | なぜ |
|---|---|
| `buttonSecondary` の**塗り** | ライト面に対する塗り自体が基準割れで、**ラベル色では直らない**（→ §8） |
| Primary / Secondary の**ラベル**（白→黒） | 既定 `lightColorScheme` の `onPrimary` 由来の白が塗りに対して基準割れ |
| 最も薄い文字（直書き `#888`） | 白面で 4.5:1 に届かない。役割トークンへ集約する際に AA を満たす値へ寄せた |
| **システムバー**（`@color/indigo` 固定 → 透明） | テーマ切替でXMLを差し替えられないため（→ §8 判断5）。ライトでも見た目が変わる |

> **この4つで全部だとは言えない。** 直書き61箇所を役割トークンへ寄せる作業を含むので、
> **同じ経路で他の色も動いた可能性がある**。
> **スクリーンショット比較を持たないため、網羅的には確認していない。**

- **保証していないこと:**

  > **未確認:** 実機での見え方（有機ELの黒つぶれ、屋外での視認性）は測っていない。
  > **ライト側の非回帰も目視のみで、機械的には固定していない**（上記のとおり網羅もできていない）。
