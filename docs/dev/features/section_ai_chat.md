## 1. 概要

読んでいる節の要約を、「この部分」の面（スマホのシート・開いた Fold のペイン）に出す。入口は2つある。

- **見出しの要約ボタン（✎ ⛶ の隣の 💬）は全節の要約を作る。** 今の節から順に作り、本文を読み進めると、作った節の要約が押さずに面に出る
- **面の「この節を要約」は今の節を1本頼む。**

**面が出ていなければ、見出しの要約ボタンは作り始めるだけで面を出さない** — 読書を止めずに頼み、記号で進み具合を見る（→ [この部分](margin_pane.md) §5.4）。
**全画面には入口を置かない** — 要約は全画面に入る前のおさらいという立ち位置（→ [全画面](note_fullscreen.md) 判断5）。

> クラス名の `SectionChat…` は、質問と回答を持っていた頃の名残である。
> 改名は影響が広いので、撤去とは分けて扱う。

## 2. ゴールと非ゴール

### ゴール
- 長いノートでも**入力をコンテキスト長に収める**
- 要約の根拠を「今見ている部分」に絞る
- **読書を止めずに**節の要点を確かめられる
- **節を読み進めるたびに押して待たずに済む**
- 要約した節へ戻ったとき、作り直さずに見返せる

### 非ゴール
- **質問に答えない。** 候補の質問も自由記述の質問も持たない（→ §8 判断3）
- **設問を作らない**（→ §8 判断3）
- **要約を永続化しない**（面を閉じても同じノートの間は全部残るが、端末には残さない）
- **ノート横断にしない**

## 4. 現在のユーザーフロー

1. 本文をスクロールすると、止まったところで面の節が替わる（→ [この部分](margin_pane.md) §5.3）
   - **見出しより前は見出しより前だけ、見出しの無いノートは全体**が1つの節になる
2. 見出しの 💬 を押す → 全節の要約を今の節から順に作る。面が出ていれば、面を要約の行まで送る
   - **面が出ていなければ、面を出さない。** 記号が ⏳ 3/12 のように進み、作り終えたら ✓ になる。⏳ か ✓ を押すとシートが出て、要約の行まで送る
   - **端末AIが使えなければ全節を始めず、理由を押した時点の今の節に出す。** 理由が届いたときだけ面を出して見せる（理由では記号が 💬 のまま変わらないため）。
     見せるのは頼んだ節を本文が映しているときだけで、読み進めていれば戻ったときに見せる（→ [この部分](margin_pane.md) §5.4）
3. 読み進めると、作った節の要約が押さずに面に出る。まだできていなければ、その節を次に作り、面に「次に作ります」と出す
4. 上限で止まると、記号が 💬 15/34 になる。押すと続きを作る
5. 面の「この節を要約」を押す → その節を1本作る
   - **その節の要約を持っていれば作り直さない**（生成中・完成・生成の失敗・非対応の説明は、それを見せる）。
     **後で使えるようになる説明（準備待ち・一時的に使えない）だけは、押し直すと状態を確かめ直す** — 準備待ちの説明には再試行のボタンが無い
   - 全節の外なら、**生成中に別の節を頼むと前の生成を取り消して新しい節を始める**（取り消した節はボタンに戻る）。全節の間は取り消さず、次に作る
6. `checkAvailability()` を見る
   - `Ready` → 節の要約を生成する
   - それ以外 → `aiStatusNotice()` の説明を `summaryProblem` へ載せる。
     **文言も導線も `AiStatusNotice` が持つ**（message だけ取り出すと再試行できず、
     赤いエラー表示になる）。再試行は `retry()` が受ける。**ここではDLしない** → §8 判断4
7. 面を閉じても要約は残る。ノートを替えるか、蒸留で本文が解析し直されると全部消える

## 5. 機能仕様

- **前提条件:** ノートが表示され、本文の解析が済んでいること（どの節かが決まらないので、それまでは要約の行を出さない）。
  **蒸留の差し替えで解析し直している間は頼んでも何もしない** — 描画に残る前の解析から引くと、前の本文の要約が新しい本文に残る
- **対象の節:** 見出しのある節は、直近の見出しから**次の同レベル以下の見出しの直前まで**。見出しより前は最初の見出しの直前まで、
  見出しの無いノートは全体。**本文は頼んだ時点の解析から引き、要求に持たせる**（`NoteSectionModel.summarySourceOf`）
- **全節の要約が作る節:** 固有の本文（次の見出しまで）が100字以上の節（`NoteSectionModel.summaryTargets`）。解析と一緒に決める。
  **親の節も固有の本文があれば作り、範囲は1節の要求と同じ配下込みのまま**（先頭の H1 はノートのほぼ全体の要約になる）。
  **全部の節が線より短いノートでは今の節だけを作る** — 押しても何も起きない入口にしない
- **作る順:** 今の節から末尾まで、続けて先頭から今の節の手前まで（`summaryTargetsFrom`）。今の節が対象でなければ、その後ろの最初の対象から始める
- **上限:**

  | 対象 | 値 | 定数 |
  |---|---|---|
  | プロンプトへ渡す節の本文 | **1500文字** | `NoteExcerptLimits.SECTION` |
  | 全節の要約が1回に作る節の数 | **15節**（根拠の実測 → [background_ai_ux](../system/background_ai_ux.md) §6） | `SECTION_BATCH_LIMIT` |
  | 全節の要約が作る節の線 | 固有の本文 **100字** | `SECTION_SUMMARY_MIN_OWN_CHARS` |
  | 断られてからやり直すまで | **10秒**（窓の長さではなく、実測で足りた待ち時間） | `SECTION_BATCH_REFUSAL_WAIT_MS` |
  | 同じ節で続けて断られたら全節を止める回数 | **3回** | `SECTION_BATCH_REFUSAL_LIMIT` |
  | 続けて失敗したら全節を止める節の数 | **3節** | `SECTION_BATCH_FAILURE_LIMIT` |
  | 出力枠 | 256トークン | `genai-prompt` |

<!-- state-fields: SectionChatState -->
- **状態 `SectionChatState`:** `summaries`（最近作った順）/ `batch`（全節の要約。頼んでいなければ null）
<!-- /state-fields -->
<!-- state-fields: SectionBatch -->
- **全節の要約 `SectionBatch`:** `targets`（作る節）/ `isRunning` / `stoppedBusy`（断られ続けて止まった）
<!-- /state-fields -->
<!-- state-fields: SectionSummary -->
- **1節分 `SectionSummary`:** `section`（見出し名と同名の中での順番）/ `requestId` / `sectionTitle` /
  `sectionContext`（**LLMへ渡すだけで表示しない**）/ `summary` / `isSummaryLoading` / `summaryProblem` /
  `noticePending`（面を出さずに頼み、端末AIが使えない理由をまだ見せていない → [この部分](margin_pane.md) §5.4）
<!-- /state-fields -->
- **`GenerationFailed(message)`:** 生成が落ちた（タイムアウト・出力打ち切り）。赤で出す
- **`AiStatus(notice)`:** 端末AIが使えない。通常色で出す
  （→ [background_ai_ux](../system/background_ai_ux.md) §6）
- **再試行:** `retry()` が**頼んだときの本文のまま**作り直す。生成中か、要約を持っているなら何もしない。全節の間は次に作る。
  再試行のボタンを持たない準備待ちの説明は、面の入口を押し直すと確かめ直す（`isShownAsIsOnRequest`）
- **入口:** 見出しの要約ボタンは全節を頼む。**✎ とは分ける** — ✎ は書く入口、💬 は AI の入口。
  どの面に出すか（面が無ければ始めるだけ）は `summaryEntryFor` が決める（→ [この部分](margin_pane.md) §5.4）。
  読み上げ名は「全節」を核にする（記号と読み上げ名は `sectionBatchEntrySymbol` / `sectionBatchEntryCount` / `sectionBatchEntryDescription` の純関数）
- **記号と押した結果:** `sectionBatchStatus` が全節の状態から導く。**進み具合の数は持たず、対象の節と要約から数える。**

  | 状態 | 記号 | 押すと |
  |---|---|---|
  | `Idle`（頼んでいない） | 💬 | 全節を始める |
  | `Working`（生成中） | ⏳ 3/12 | 面を出して要約の行へ送る |
  | `Partial`（止まって、作れる節が残っている） | 💬 10/12 | 続きを作る |
  | `Ready`（全部できた） | ✓ | 面を出して要約の行へ送る |
  | `Error`（出せなかった節がある） | ! | 出せなかった節と残りを作り直す |

  節が1つのノートは数を添えない。面の行には進み具合と次の行動を言葉で添える（`sectionBatchNote`）
- **全節の中の出来事:**

  | 出来事 | 扱い |
  |---|---|
  | 1節の生成の失敗（打ち切りなど） | その節を飛ばす。理由はその節に残り、記号が ! になる。**3節続いたら全節を止める**（節によらない失敗を節の数だけ繰り返さない） |
  | BUSY（`isAiCoreRefusal`） | **節を失敗にしない。** 10秒待って同じ節をやり直し、3回続けて断られたら全節を止めて `stoppedBusy` を立てる。押し直すとその節から作る |
  | 背面の拒否（`BACKGROUND_USE_BLOCKED`） | BUSY と同じく節を失敗にしない。**背面の間は次の節を始めず**、前面へ戻ると続ける（`pause` / `resume`）。冊子では止めない |
  | 端末AIが使えない | 全節を終える（`batch = null`、記号は 💬）。理由は押した時点の今の節に出す。**その節の要約を持っていれば、要約を残して並べて出す**（`hasNoticeWithSummary`）。ほかの節に置くと、押した本人に届かない。再試行は全節を頼み直し、全節を頼み直すと理由は下がる |
  | 面の節が替わった | まだできていなければ次に作る（`prioritize`）。**生成中の節は取り消さない** |
  | 面の「この節を要約」・再試行 | 次に作る。対象でなかった節は対象へ足す。**足した節は本文が替わるまで対象に残り**、止めて押し直しても失敗して押し直しても作る（押し直しでは上限に数える）。できたら列の残りへ戻る |

- **キャンセル:** 全節の外では、別の節の要求と「生成を中止」で今の生成を止める。全節の間は「全節の生成を止める」（`stopAll()`）だけで、生成中の節はボタンに戻り、できた要約は残る。
  ノート・Vault切替と本文の解析し直しでは `cancelAndClear()` で全部捨てる
- **後着:** 結果は `requestId` が一致する要約にだけ書く。取り消しに従わない生成が遅れて届いても、取り除いた節や頼み直した節を上書きしない

## 6. 状態とデータ

**UI状態:** `NoteUiState.sectionChat`（`SectionChatState`）。面を出すかどうかは「この部分」の側が持つ
（シートは `isMarginMemoSheetVisible`、ペインは並べ方と設定）。**面の可視と要約の有無を分けている** — 閉じても要約は残る。
面を出さずに頼んだ要求は、端末AIが使えない理由をまだ見せていない印（`SectionSummary.noticePending`）を持ち、
理由の行が組まれたら `acknowledgeNotice(requestId)` で下ろす（面が出ているだけでは下ろさない）。**画面の値ではなくここに置く** — 画面を作り直しても失わない。

**永続化しない。** 全節の作る節の列と残りの数は Controller の中にあり、`NoteUiState` には載せない（押し直しは数え直すので控えない）。

**契約2箇所への登録（ノート単位の状態）:**
`cancelNoteScopedJobs()` → `sectionChat.cancelAndClear()`、
`withNoteScopedReset()` → `sectionChat = SectionChatState()`。**両方に登録済み。**
蒸留の差し替え（`applyReloadedBody`）でも `cancelAndClear()` し、状態は `withDistillBodyReloaded` が空にする。

**節の構造の解析は別 Controller が持つ。** `NoteSectionController` が
`Dispatchers.Default` で解析して `StateFlow<NoteSectionModel?>` を配る
（→ [architecture](../system/architecture.md)。**最大1MBの解析はMainで走らせない**）。
見出しより前の本文もこの解析で一緒に組み立てる（見出しの無いノートでは全体に比例するため）。

## 7. システム設計

```
本文（LazyColumn）── スクロールが止まった位置 ──> 面の節（SectionRef）
 ├─ 見出しの要約ボタン ── NoteSessionCoordinator.requestAllSectionSummaries(今の節)
 │     └─ NoteSectionModel.summaryTargetsFrom(今の節)・summarySourceOf(節) で本文を引き
 │          └─ SectionChatController.requestAll()   ← 作る節の列・1回15節
 ├─ 面の「この節を要約」 ── NoteSessionCoordinator.requestSectionSummary(節)
 │     └─ SectionChatController.request()   ← 全節の外は取り消して始める／全節の間は次に作る
 └─ 面の節が替わる ── SectionChatController.prioritize()

SectionChatController の生成係 ── 列の先頭から1節ずつ（生成は一度に1本・錠は1節ごとに取り直す）
 └─ 「この部分」の面の SectionSummaryRow に出す

NoteSectionController（Dispatchers.Default）── NoteSectionModel ──> 上記
```

## 8. 設計判断と代替案

### 判断1: なぜ「節単位」なのか

長いノート全体を Nano に渡すと**コンテキスト長制限で後半が切り捨てられ**、要約の的確さも落ちる。
「今見ている部分だけ」を対象にすれば、長いノートでも入力が収まり、**要約の根拠も絞られる。**

**対象はユーザーに選ばせず、スクロール位置から自動追従する。** 選ばせると手数が増え、
「読んでいる場所を確かめる」という動機と噛み合わない。

### 判断2: 節ごとに持ち、ノートを開いている間は全部残す

要約は節ごとに持ち、同じ節を頼み直しても作り直さない。**スクロールだけでは全節の外の生成を始めも取り消しもしない** —
生成が走るのは入口を押したときだけで、できた要約は作り始めた節に入る。
1つのセッションを最初の節に固定する形では、別の節で 💬 を押しても前の節の要約が出て、新しい節を要約するには
明示的に終わらせる操作が要った。節ごとに持てば終わらせる操作は要らず、少し前の節へ戻っても見返せる。
保持はかつて「戻って見返す」に足りる3節だったが、全節の要約で読み進めて出す形にしたので外した（→ 判断7）。
生成は一度に1本に留める（Nano の Mutex を待たせない）。置き場所と面の並びは [この部分](margin_pane.md) §5.8。

### 判断3: 質問とクイズを撤去した（オーナー判断・2026-09-28）

質問候補から回答を作る2段の生成と、形式を守った複数項目の生成（クイズ）は、
出力256トークン・1回数十秒の中で、**待ったうえで読んで得をする水準に届かなかった**（オーナーの体感）。
どちらも本文から選ぶのではない自由生成で、**結果はシートを閉じるかノートを替えると消える** —
「次の再会の材料として残るか」に答えない。**部分要約だけを残した。**

### 判断4: ここではモデルDLを始めない

`NeedsDownload` のときは**文言で案内するだけ**で、ダウンロードを開始しない（自動の要約は始める）。

**したがって `AiNoticeAction.Download` を運ばない。** 共通変換へ
`canStartDownload = false` を渡し、「Gemini Nanoの準備ができると〜を使えます。」という
**待てば使えることだけを言う文**にする。運ぶと終端UIがコールバックを渡さず、
**ボタンが描かれないまま「開始してください」だけが残る** — 開始する操作が存在しない案内になる。

**読書中に開く面なので、数分かかる処理をここから起こさない。**
DLの起点は自動生成される要約側に寄せてある（→ [architecture](../system/architecture.md) の比較表）。

### 判断5: 終了のボタンを置かない（オーナー判断・2026-10-03）

専用シートにあった「確認を終了」は撤去し、生成中だけ「生成を中止」を出す。
要約は面を閉じても残り、古い節は3節を超えると自動で消えるので、終わらせる操作に役目が無い。
**UXの観点で無駄なボタンは削る**という方針に沿う。

### 判断6: 節の要約も常に日本語で書かせる（2026-10-11、オーナー判断）

ノートの要約と同じ理由で、出力の言語を節の本文に任せない。コードや英語の用語が多い節で英語の要約が返るのを防ぐ。
理由と経緯の正本は [note_summary](note_summary.md) 判断10。

### 判断7: 見出しの 💬 は全節の要約にする（2026-11-01 オーナー判断、値は 2026-11-03 の実測の後）

節を読み進めるたびに押して待つ手間があり、入口が2つとも同じ「今の節」で 💬 が余っていた。
💬 を全節へ、面の「この節を要約」を今の節へ分ける。

- **上限は15節。** 実測（→ [background_ai_ux](../system/background_ai_ux.md) §6）は短い節の多いコーパスの値で理論値に近いので、オーナー判断で20節から安全側へ倒した。超えた節は押し直すと作るので、見失わない
- **短さは固有の本文で測る。** 節の本文は配下の見出しを含むので、節の本文で測ると見出しだけの親も長く見え、枠を重複に使う。100字未満の節では要約のほうが長くなりやすかった
- **列は1つ、生成係も1つ。** 全節の間の要求を別の経路で走らせると、一度に1本の約束と「取り消さない」が割れる。全節の外の取り消しの挙動はそのまま残した
- **BUSY と背面の拒否を節の失敗にしない。** どちらも約30msで返るので、節の失敗にすると残りが一瞬で全部 ! になり、断られただけなのに再試行を求めることになる。自動で待ち直すのは、実測で10回とも10秒で通ったため
- **全節の間は「生成を中止」を出さない。** 1節が約2秒で押す間が無く、「全節の生成を止める」と並ぶと違いが分からない
- **面で足した節は全節の一部として扱う。** 対象は押すたびに解析から作るので、足した節を落とすと、失敗が残ったまま ✓ になり、止めて押し直すと分母から消える
- **理由は押した節に出す。** 全節を止めた理由を別の節に置くと、押した本人には 💬 に戻るだけで何も起きないように見える（→ [background_ai_ux](../system/background_ai_ux.md) §6 判断6）。要約を消さないために、要約と理由を並べて持つ
- **進み具合の数を持たない。** 持つと実物とずれる（→ [L49](../lessons/L49.md)）。対象の節と要約から数える。続きから作るのも、持っていない節を数え直すだけで済む
- **作った要約はノートを替えると消える。** 保存しない判断（§2）は変えない

## 9. 品質要件

- **性能:** 節の解析は `Dispatchers.Default`（`ThreadingScanTest` がソース走査で固定）。全節の対象も解析と一緒に作る。抜粋の組み立ても Main の外
- **ほかの生成との順序:** 全節は押して使うので自動の生成の門番（→ [background_ai_ux](../system/background_ai_ux.md) §7）を通らない。**錠は1節ごとに取り直す**ので、自動の生成が節の間に入れる
- **プライバシー:** 節の本文はプロンプトへ入るが端末外へ出ない
  （→ [ADR-0002](../decisions/ADR-0002-on-device-ai-only.md)）
- **端末制約:** Nano 非対応・モデル未準備は**面の中の文言**で伝える

  BUSY を待ってやり直す・断られ続けたら止める・背面で進まない・止める・切替で捨てる・走行の印が残らない・古い生成係が新しい列を進めない）/

  `NoteSessionCoordinatorTest`（ノート切替で後着しない・要約の生成中にメモを置く・メモの保存中に要約を始める。全節: 解析から引く・解析し直している間は作らない・3つの切替で捨てる・背面の合図が届く）/ `ThreadingScanTest`
- **instrumentation:** `OnDeviceGenerationTest`（節の要約の実生成）/ `NoteReadingFlowTest`（記号と押した結果・面の節が替わると伝える）/ `MarginMemoSheetUiTest`（全節の間の要約の行）

- **実機で起こせないので自動テストが持つ順序:**
  - 取り消しに従わない生成と状態確認の後着（`SectionChatControllerTest`）。実クライアントは取り消しに従う
  - 同じ節で BUSY が3回続く順序（`SectionChatControllerTest`）。実測では10秒待ちで毎回通った
  - 生成中に背面の拒否が返る順序（`SectionChatControllerTest`）。背面へ回す瞬間と生成の交錯を選べない

- **保証していないこと:**
  - **節の追従の精度を測っていない。** 本文の最上端に見えているブロックの節なので、読んでいる位置とずれうる
  - **要約の質を測っていない**
  - **全画面の間の読む位置は全節へ伝わらない。** 全画面は本文の位置を別に持ち、作る順を変えない
