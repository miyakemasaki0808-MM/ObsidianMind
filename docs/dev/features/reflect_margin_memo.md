## 1. 概要

読んでいる最中に、**何にも紐づかない短い断片を何度でも置ける口**。
本文（`.md`）は触らず、読書痕跡サイドカーへ追記する。

**AIを1回も呼ばない。** Reflect 系で唯一、端末AIの可否と無関係に動く機能である。

置き換える相手（ノートへのひとこと）は、**AIが問いを投げ、ユーザーがそれに答える**という形だった。
Reflect の中でユーザーへの要求が最も重く、しかも1ノート1件・上書きで溜まらない。
本機能はその要求を全部外す — **問いを出さず、答えさせず、溜める。**

出どころは 2026-08-02 の外部壁打ち。当時「ひとことの返事との差を言語化できるか」が採否の分かれ目として
保留されていたが、**返事が無くなることで、これがユーザーの言葉を受け取る唯一の口になった。**

## 2. ゴールと非ゴール

### ゴール
- 読む流れを止めずに、いま浮かんだ短い言葉を置ける
- **1ノートに何度でも置ける**（追記であって上書きではない）
- **保存できる条件を、生成物の有無に結びつけない**（→ §8 判断3）
- 置いた言葉を失わない。**次の再会で、自分の言葉として戻ってくる**

### 非ゴール
- **AIを呼ばない。** 要約も分類も提案もしない
- **汎用エディタにしない。** 長文はノート本体で書くもの（ただし壁ではなく合図で守る → §5）
- **本文へ書かない**（→ [ADR-0004](../decisions/ADR-0004-do-not-rewrite-vault-body.md)）
- **メモを編集しない。** 直したければ消して書き直す（→ §8 判断9）
- **Vault横断で読む面を作らない。** 本機能は1ノート分まで。横断は別機能が受け持つ
- **催促しない。** 件数バッジも未読管理も持たない（→ §8 判断10）

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| メモを置く | ヘッダの `✎` でシートが上がり、書いて置ける。**シートは開いたまま**で続けて書ける | ノート表示中（Vault選択済み） |
| このノートのメモ一覧 | シートの中に、置いた順の**新しい順**で並ぶ | シートを開いたとき |
| メモを消す | 各行の `✕` → 確認 → 消える | 一覧に1件以上あるとき |
| 上限の知らせ | 長いときは静かに知らせ、満杯のときは置けない理由を出す | §5 の上限に触れたとき |
| 再会で気づく | 再会カードの行が **`前回のメモを見る`** になり、押すとシートが開く | Rediscover で引き当て、メモが1件以上あるとき |

## 4. 現在のユーザーフロー

> **未実装のため、以下は設計した想定フローである。** 実装後に実機と突き合わせて `最終検証` を進める。

1. ノートを開いて読む
2. ヘッダ右の **`✎`**（全画面ボタン `⛶` の隣）を押す → ボトムシートが上がる。**本文はスクロール位置ごと背後に残る**
3. シートの上段が入力欄、下段がこのノートの既存メモ（新しい順）
4. 書いて `置く` を押す → 一覧の先頭に増え、入力欄が空になる。**シートは閉じない**
5. シートを閉じる → 読書へ戻る。**スクロール位置は動かない**
6. 後日 Rediscover で同じノートを引き当てると、再会カードに `前回のメモを見る` が出る。押すと同じシートが開く

**中断:** ノートを切り替えるとシートは閉じ、状態は `Idle` へ戻る（契約2箇所 → §6）。

**全画面表示中は書けない。** `✕` で通常表示へ戻ってから置く（→ §8 判断7）。

## 5. 機能仕様

- **前提条件:** Vault選択済み・ノート表示中。**端末AIの可否は前提に入らない** —
  Nano 非対応端末でも同じに動き、`AiNotice` を出さない
- **入力:** ユーザーの自由文
- **出力:** なし（AI生成物を持たない機能である）
- **上限（すべて実装の定数）:**

  | 対象 | 値 | 定数 |
  |---|---|---|
  | メモ1件の保存 | **1,024バイト**（日本語で約340字） | `MAX_MEMO_BYTES` |
  | 静かに知らせる目安 | 200字（**壁ではなく合図**） | `SOFT_MEMO_CHARS` |
  | 1ノートの保持件数 | **20件**（**古いものから捨てない** → 判断4） | `MAX_MEMOS` |
  | 書いた場所（見出し名） | 512バイト（訪問と同じ枠を使う） | `MAX_SECTION_TITLE_BYTES` |
  | 痕跡ファイル全体 | 128KB | `MAX_FILE_BYTES` |

  > **`MAX_FILE_BYTES` との整合は、計算ではなく実シリアライザで測って固定する**
  > （`ReadingTraceLimitsTest` → 判断11）。
  > **生の文字列長を足す形では保証にならない** — JSONは `"` と `\` を2バイトへ、
  > 制御文字を `\u00XX` の6バイトへ広げるので、各欄の上限を満たしたまま
  > 128KBを超えられる。**上限を足したり上げたりしたら、測る対象へ必ず加えること。**

- **入力の正規化（容量上限の前提）:** メモ本文は保存前に
  **改行とタブ以外の制御文字を落とす。** これで JSON 化後の膨張が最悪2倍に抑えられ、
  上の件数が成り立つ。**正規化をやめるなら件数上限を測り直すこと。**

- **長さの扱い:** **受け取ってから切り、切ったら必ず示す。**
  200字を超えたら静かに知らせるだけで、切りも拒否もしない。
  1,024バイトで初めて切り、「ここまでを置きました」と示す（→ [reflect_remark](reflect_remark.md) 判断6 と同じ作法）
- **満杯の扱い:** 20件に達したら**置けない**。
  **入力欄の文字は消さない** — 消すと「置けなかった」と「消された」が同じ顔になる。
  1件消してから置き直せる
- **容量で置けない場合も同じ扱い。** 件数が20件未満でも、書くと痕跡ファイルが
  `MAX_FILE_BYTES` を超えるなら置けない。**既存のファイルは触らず、入力も預かりも保持する**
  （→ 判断11）
- **合流が上限を超える場合:** 退避ファイルの読み戻しで、合流後の件数が20件を超えるノートは
  **無変更のまま保留する。** 端末側を書き換えず、退避側も捨てず、成功として数えない。
  件数を下見と結果の両方で示す（→ 判断5）
- **状態遷移:** §6
- **保存と寿命:** 読書痕跡サイドカー `_ReadingTraces/*.json`（**本機能で schema を v7 へ上げる**）。
  ノートを消しても痕跡は残る（孤児掃除が受け持つ）。Vault のフォルダが消えれば一緒に消える
- **画面遷移:** **ルートを増やさない。** ボトムシート1枚で完結する
  （ひとことは専用ルート `remark` を持っていたが、これは結果が長く、待ち時間があったため）
- **他機能との連携:**
  - **再会カード:** `前回の返事を見る` の行を `前回のメモを見る` へ置き換える（→ 判断8）
  - **退避と復元:** メモは配列なので**欄ごとの突き合わせで合流できる**（→ 判断5）
  - **セクションチャット／蒸留のシート:** 同時には出さない（既存のシートと同じ排他）
- **エラー／AI非対応／キャンセル時:**
  - **AI非対応は関係しない。** この機能は端末AIを呼ばない
  - 保存失敗 → `Failed`。**本文は状態に残し、再試行できる**
  - 痕跡ファイルがまだ無い → `Held`（離脱時の書き込みへ預ける → 判断3）
  - ノート切替 → シートを閉じ、`cancelAndClear()`。`CancellationException` は再throwする

## 6. 状態とデータ

### UI状態

`MarginMemoState`（`NoteUiState.marginMemoState`）:
`Idle` / `Loading` / `Ready(memos, saveStatus)` / `Error(message)`

`MemoSaveStatus`: `None` / `Saving` / `Held` / `Saved` / `Failed` / `Full`

> **`Boolean` の束にしない。** 「保存中かつ未保存」のような無意味な組み合わせを型として作れてしまう
> （→ [reflect_remark](reflect_remark.md) の `ReplyStatus` と同じ理由）。
> **`Full` を `Failed` に畳まない** — 再試行して直るものと、消さなければ直らないものは、次の行動が違う。

シートの開閉は `NoteUiState.isMarginMemoSheetVisible`（セクションチャットのシートと同じ形）。

### 永続化モデル

```kotlin
data class MarginMemo(
    val text: String,
    val writtenAtEpochMillis: Long,
    /** 置いたときに見ていた見出し。**歴史的記録で、改名しても再解決しない** */
    val sectionTitle: String? = null
)
```

`ReadingTrace` へ `memos: List<MarginMemo>`（既定 `emptyList()`）を足し、**`reflection` を落とす**。

- **並びは追記順（古い順）で持つ。** 表示側が新しい順へ並べ替える
- 検証は「件数 ≤ `MAX_MEMOS`・本文が空でない・バイト上限内・日時が非負」。**順序は要求しない**
  （別端末とのマージで前後しうる）

> **欄を足したら [reflect_reading_trace](reflect_reading_trace.md) のデータ表も直す。**
> `SourceDocSyncTest` が `<!-- state-fields: ReadingTrace -->` の区切りを読んでおり、
> **主コンストラクタの欄が載っていなければ落ちる。**

### スキーマ版

**v6 → v7。** 読めるのは v1〜v7（書き戻しは常に現行版）。

| v7 での扱い | 欄 |
|---|---|
| **足す** | `memos` |
| **読み捨てる** | `remark` / `remarkedAt` / `reply` / `repliedAt` / `mirrored` |

**読み捨ての作法が要点で、ここを素直に書くと既存の痕跡が全部消える**（→ 判断6）。

### 契約2箇所への登録（ノート単位の状態）

- `NoteSessionCoordinator.cancelNoteScopedJobs()` → `marginMemo.cancelAndClear()`
- `NoteUiStateStore.withNoteScopedReset()` → `marginMemoState = Idle` ＋ `isMarginMemoSheetVisible = false`

**両方に登録する。** シートの可視フラグを落とすと、ノートを切り替えたときに
**前のノートのメモを載せたシートが開いたまま**残る。

## 7. システム設計

```
NoteReaderTab（ヘッダの ✎）／ReadingTraceCard（前回のメモを見る）
   └─ NoteSessionCoordinator
        └─ MarginMemoController      open() / save() / delete() / cancelAndClear()
             ├─ MarginMemoComposer（純関数：正規化・切り詰め・合図）  ← JVMテスト
             └─ ReadingTraceController  loadMemos() / appendMemo() / deleteMemo() / setPendingMemos()
                  └─ ReadingTraceStore（writeMutex で直列化・退避スロット）
```

**AI層を1本も通らない。** `PromptBuilder` も `AiClient` の `generateMutex` も関係しない。

**保存はひとことの返事と同じ3経路。** ユーザーが書いた言葉なので、生成物とは扱いが違う。

| 状況 | 結果 | 次に何が起きるか |
|---|---|---|
| 痕跡ファイルがある | `Saved` | その場でサイドカーへ書けた |
| **痕跡ファイルがまだ無い**（初読の最中） | `Held` | セッションが預かり、離脱・背面化時の書き込みに載る |
| 預ける先も無い（Vault未選択・別ノートへ移った後） | `Lost` | 画面は未保存のまま。書き直せる |

### 預かり・退避・ファイルの合流（**判定条件の差し替えでは済まない**）

既存の退避（`pendingWrites`）は**1ノート1組の返事を上書きで持つ**ことを前提にしている。

- `rememberPendingWrite` は同じノートの退避を**丸ごと置換**する
- `flushPendingWrites` は**新しい返事を採って古い方を捨てる**
- 訪問の保存が成功すると、そのノートの退避を**丸ごと忘れる**

**上書き型の返事には正しいが、独立した要素が並ぶメモには成立しない。**
メモAの保存が失敗して退避に積まれたまま、メモBを置いて保存が失敗すると、
退避が丸ごとBで置換されて**Aが消える。** プロセス死亡は関係しない。

**そこで合流点を契約として決める。**

1. **メモの真実は3箇所に分かれて存在しうる** — 永続ファイル／セッションの預かり／退避。
   **どれか1つを真実と見なさない。**
2. **書き込みのたびに3つを合流させてから書く。** 「ファイルを読む → 退避にある同ノートのメモを合流
   → セッションの預かりを合流 → 今回のメモを足す → 保存」。合流は `(日時, 本文)` の重複排除。
3. **退避から外してよいのは、その要素が永続ファイルに在ることを確認できたときだけ。**
   **ノート単位で丸ごと捨てない**（訪問の保存が成功しただけでは、退避中のメモは書けていない）。
4. **退避の書き直しは、錠の内側で退避を読み直す。** 先に取ったスナップショットで書くと、
   その間に消されたメモを**書き戻して復活させる。**
5. **削除は3箇所すべてへ、書き込みの錠の内側で当てる。**

**この5つが `MarginMemoControllerTest` の受け入れ条件になる**（→ §10）。

## 8. 設計判断と代替案

### 判断1: AIを1回も呼ばない

**要求を減らすのが作り直しの目的**なので、AIを足すと目的を自分で壊す。
好き嫌いは *AIが何をするか* ではなく ***ユーザーに何を要求するか*** で並んでいた —
要約＝要求ゼロ／蒸留＝判断3回／ひとこと＝**AIの問いに答える作文**。

副産物として、この機能だけが **Nano 非対応端末でも完全に動く。**
Mutex 直列の待ち行列にも並ばないので、要約・関連ノート・痕跡要約の待ち時間を1ミリ秒も増やさない。

| 検討した案 | 却下理由 |
|---|---|
| 置いたメモをAIが1文に畳む | **その場で要求ゼロでも、結果を読む面が要る。** 横断して畳むのは別機能の役目で、ここで先取りすると両方が半端になる |
| メモを書くと関連ノートを出す | 断片を置いた直後に読むものが増える。**流れを止めない**という一点と正面から衝突する |

### 判断2: 何にも紐づけない。ただし**書いた場所は控える**

**紐づけない**とは「AIの生成物にも、ユーザーが選んだ本文の範囲にも結び付けない」という意味で、
**書いた時点の状況を控えないという意味ではない。**

置いたときに見ていた見出し名を `sectionTitle` として残す。**ユーザーの操作は1つも増えない**のに、
数か月後に読み返したとき断片が読める文になる。訪問の `deepestSectionTitle` と同じ**歴史的記録**で、
後から本文が編集されて見出しが消えても再解決しない。

**本文の範囲へ紐づける案（長押しした段落に付ける）は採らない。** 紐づけた瞬間、
ユーザーは「どこに付けるか」を決めることになり、要求が1つ増える。
本文が編集されれば紐づけ先も壊れる。

### 判断3: 保存できる条件を、生成物の有無に結びつけない

**ひとことの返事はここを踏んでいた。** 痕跡ファイルはあるのに、**ひとことがまだ保存されていない**
状態で返事を書くと捨てられ、その場で再試行しても失敗した（組で持つため、
ひとこと無しに返事だけを保存する経路が存在しなかった）。

メモは何にも紐づかないので同じ形にはならないが、**規則としてはっきり書いておく** —
保存の可否を決めてよいのは「置き場所があるか」だけで、「AIが何かを作ったか」ではない。

構造としては、`appendMemo` に**組の相手を確かめる分岐を作らない**ことで守る。
ひとことの `saveReply` にあった「相手が居なければ `Lost`」に相当する分岐は、この機能には存在しない。

### 判断4: 件数の上限では**古いものから捨てない**

訪問は 30件を超えたら古いものから捨てる。**メモは捨てない。**

**訪問は作り直せるが、メモは作り直せない。** 同じノートをもう一度読めば訪問は付き直るが、
そのとき何を思ったかは戻らない。溜まるものの上限には、**捨ててよいものと、
捨ててはいけないものがある。**

満杯のときは置けないと示す。**壁を作ることになるが、入力欄の文字を消さない**ので
書いた言葉は画面に残り、1件消せばそのまま置ける。

**上限は1本だけ持つ。** 「書ける上限」と「保持できる上限」を分け、合流のときだけ広げる案は採らない。
広げた分がそのまま容量の最悪ケースになり、**上限を2本に増やしても境界の判断は消えない**
（広げた先で同じ問題が起きるだけ）。20件は容量から逆算した暫定値である（→ §10）。

### 判断5: 配列にしたことで、**退避と復元の既知の欠陥が1つ消える**

[reading_trace_backup](reading_trace_backup.md) は「1ノート1組の `reflection` は構造上マージできない。
両方に返事があれば必ず片方が消える」を**保証していないこと**として持っていた。
だから確定前に「失われる返事の件数」を、**どちら側が失われるかまで言い分けて**見せていた。

**メモは配列なので合流できる。** 端末側と退避側を `(日時, 本文)` で重複排除して結合し、
日時で並べ替える。**規則が「どちらかを選ぶ」から「両方を残す」へ変わる。**

**ただし上限を超える合流は起こりうる**（端末20件＋退避20件が全部違えば40件）。
**ここで切ると判断4に違反し、全部持つと検証と容量に違反する。**
**どちらも選ばず、そのノートを無変更のまま保留する。**

- 端末側を書き換えない。退避側も捨てない（**退避ファイルは手元に残り続ける**）
- 成功として数えない。**下見と結果の両方で、保留したノートの件数を示す**
- 同じ規則を**1つの退避ファイル内に同じノートが重複している場合**にも当てる

**「失われない」と言えるのは、アプリが捨てないからであって、全部入るからではない。**
保留は合流できなかったという報告であって、消失ではない。

消えるもの:

- 突き合わせ規則の `reflection` の行と、その「直感とずれる」注記
- `droppedReplySide()` / `DroppedReplySide` と、それを数える経路
- 確定前の「失われる返事」の告知文

**合流の副作用を1つだけ引き受ける。** 削除したメモが退避側に残っていると、読み戻しで復活する。
同じ端末の中では §7 の契約5（削除は3箇所すべてへ錠の内側で当てる）が防ぐ。
別端末の退避ファイルから戻る場合は起こりうるが、**それは「削除の同期」であって突き合わせ規則の話ではない**
ので、ここでは扱わない（→ §11）。

### 判断6: ひとことは v7 で読み捨てる。ただし **checksum は v6 の正規形で検証してから落とす**

**オーナー判断（2026-09-20）。** 「ひとことというサービスの終了」であり、無意味にデータを残さない。

**素直に書くと既存の痕跡が全部消える。**

checksum は「**書かれた版の正規形**」で照合している。v6 の正規形には `remark` / `reply` / `mirrored` が
含まれるので、読む段でこれらを捨ててから照合すると**全ファイルが不一致＝破損扱い**になる。
破損した痕跡は孤立扱いで、次の訪問が**新規として上書き**するので、**訪問履歴まで道連れになる。**

正しい順序はこう。

1. v6 のファイルは **v6 の正規形どおりに読み、checksum を検証する**
2. 検証に通ってから、**モデルへ載せる段で落とす**
3. 次の書き込みで v7 として書かれ、そこで初めてファイルから消える

**落とした値はモデルへ入れない。** `ReadingTraceJson` の中だけで持つ
（デコーダの中に閉じ込める。移行の知識が置かれるべき場所はそこしかない）。

**窓は欄ごとに違う。ここを一律にすると、守るつもりの訪問履歴まで失う。**
旧欄は同時に入ったのではなく、版をまたいで1つずつ足されている。
**null も存在フラグを1バイト書く**ので、「その版にまだ無かった欄」を足すだけでもハッシュが変わる。

| 欄 | 正規形へ書く版 |
|---|---|
| `remark` | **v3〜v6** |
| `remarkedAt` / `reply` / `repliedAt` | **v4〜v6** |
| `mirrored` | **v5〜v6** |

**一律に v4〜v6 とすると、v3 の `remark` が checksum から抜ける。**
v3 は実機へ書き出された版で、`ReadingTraceJsonTest` に実ファイルを組み立てる fixture が現存する。
抜けた瞬間に正しい v3 ファイルが破損扱いになり、**次の訪問記録が上書きして訪問履歴ごと消える。**

**「追加した欄は末尾に足すだけ」という原則の、初めての例外**になるので、コメントで理由を残す。

| 検討した案 | 却下理由 |
|---|---|
| 返事をメモ1件へ移送する | 返事の上限は 25,600バイトで、短い断片を前提にしたメモの枠と桁が違う。**メモ側の上限設計が歪む**うえ、移送は不可逆 |
| 欄を残して新規作成だけ止める | データは守られるが、使わない欄が検証・突き合わせ・正規形に残り続ける。**オーナー判断で採らない** |

### 判断7: 入口は本文ヘッダの `✎`

**オーナー判断（2026-09-20）。**

`GradientHeader` の `trailing` に、全画面ボタン `⛶` と並べて置く。

- **常に同じ位置にある。** 本文のどこを読んでいても探し直さずに押せる
- **ジェスチャを取り合わない。** 本文スクロール・蒸留の範囲つまみ・全画面の `💬` と競合しない
- 既存の枠を使うので、新規UIは**シート1枚**で済む

| 検討した案 | 却下理由 |
|---|---|
| 画面端から引き出すシート | 読書位置を動かさずに書けるのが最大の利点だが、本文スクロール・蒸留のつまみ・全画面の `💬` と縁を取り合う。**この1機能の中で最も重い部分になる** |
| AIタブのボタンを置き換えるだけ | 最も安く、廃止と置き換えが1対1で対応する。ただし**読んでいる流れを止めずに置く**が満たせず、既存機能と差別化していた点が消える |

**全画面表示中は書けない。** 全画面にはヘッダが無く、`💬` は既に別の役目を持っている。
`✕` で戻る一手を要求することになるが、**読む面を増やさない**ほうを採る。

### 判断8: 再会カードの行は削除ではなく**置き換える**

再会カードは今回の範囲外だが、**`前回の返事を見る` の行は触らざるを得ない** —
ひとことを廃止すると、この行は**存在しない画面を指す。**

削除しても置き換えても、カードは同じだけ変わる。**置き換えるほうが、ユーザーにとって厳密に良い。**

- `ReadingTraceCard.hasReflectionReply` → `hasMemos`
- 行の文言 `前回の返事を見る` → `前回のメモを見る`
- 押したときの行き先: ルート遷移ではなく**シートを開く**

これで「メモが書き捨てになる」という、この案が長く保留されていた懸念に**1本だけ答えが付く**
（Vault横断で読む面は別機能が受け持つ）。

**カードの構造・行数・畳み方は変えない。** 中身も載せない —
**在ることだけ**を示して画面へ渡す、という既存の役割分担をそのまま引き継ぐ。

### 判断9: 編集はしない。削除はできる

**編集しない。** 短い断片なので、直したければ消して書き直せば足りる。
編集を持つと「いつの言葉か」が曖昧になり、`writtenAtEpochMillis` の意味が壊れる。

**削除は持つ。** 溜まるものなので、誤入力を消せない設計は使えない。
不可逆なので確認を挟む。

### 判断10: 件数バッジも未読管理も持たない

`markViewed()` と Snackbar 通知を持つ Controller は**3つ目が現れたときに共通化を再検討する**
という条件があるが、**この機能はそこへ数えない。** メモは自分が書いたものなので
「まだ見ていない」が成り立たない。

**副産物としてAIタブのバッジが対象ごと消える。**
`AiTabBadgeState` は `RemarkState.Loading` だけが駆動源だったため、ひとことを畳むと
**バッジを出す理由が1つも残らない。** バッジは「生成中」を示すものなので、
生成しない機能がそこへ入る筋は無い。

### 判断11: 容量は計算ではなく**実シリアライザで測って**固定する

既存の `ReadingTraceLimitsTest` は、各欄の**生のバイト上限を足し**、JSONの器を定数で見込んでいた。
**これは保証になっていない。** JSONは `"` と `\` を2バイトへ、制御文字を `\u00XX` の6バイトへ広げるので、
**全欄が上限内なのに128KBを超えたファイルを書ける。**

しかも `ReadingTraceStore.save` は**encode後のサイズを見ずに書く**（上限を使うのは読込側だけ）。
つまり**保存は成功し、テストも緑のまま、次に開くと痕跡が消えている**という、
この検査がまさに防ぐはずだった壊れ方が残っていた。

対処は3つ。

1. **測る。** 全欄を上限まで詰め、**エスケープで膨らむ文字**（`"`・`\`・改行）で埋めた痕跡を、
   **本物の `ReadingTraceJson.encode` に通して**バイト数を数える。
   推定値を置かないので、欄が増えても計算式を直し忘れられない
2. **入力側で膨張率を抑える。** メモ本文は制御文字（改行・タブを除く）を落とす。
   これで最悪2倍が上限になり、20件という件数が成り立つ（→ §5）
3. **書く前に測る。** `ReadingTraceStore.save` は encode 後のサイズが `MAX_FILE_BYTES` を超えたら
   **書かずに失敗を返す。** 既存ファイルは truncate されず、呼び出し側の預かりと退避が言葉を保つ

**「数えるのをやめて計算で固定する」の次は「計算をやめて実測で固定する」である。**

## 9. 品質要件

- **性能:** AI生成が無いので待ち時間は**サイドカー1件の読み書き**だけ。
  シートを開いたときに1件読む（ノート表示の経路には置かない）
- **プライバシー:** ユーザーが書いた文は端末内のVaultにしか存在しない。
  **AIへ渡さないので、プロンプトにも乗らない**（→ [ADR-0002](../decisions/ADR-0002-on-device-ai-only.md)）
- **データ保護:** **この機能の核心。** ユーザーが書いた言葉は作り直せない。
  §7 の3経路・判断3・判断4・判断5 はすべてこの一点のためにある
- **アクセシビリティ:** `✎` は `IconPill` の既存の作法どおり `contentDescription` を持つ。
  シート内の削除は確認を挟むので、誤タップで消えない
- **端末制約:** **Nano 非対応端末でも全機能が動く。** Reflect 系で唯一

## 10. 検証と受け入れ条件

- **JVMテスト:**
  - `MarginMemoComposerTest` — 制御文字の正規化・切り詰めと合図の境界・空白だけの入力
  - `MarginMemoControllerTest` — 保存状態の遷移（`Saved` / `Held` / `Lost` / `Full` / `Failed`）・
    ノート切替でのキャンセル。**§7 の合流契約を3ケースで固定する:**
    - A保存失敗 → 退避の再試行も失敗 → B追加 → 保存回復で**AとBが各1件残る**
    - A退避 → 訪問だけの保存が成功 → 再試行で**Aが残る**（丸ごと忘れない）
    - 退避のスナップショット採取 → A削除 → 遅延書き込み完了で**Aが復活しない**
  - `ReadingTraceJsonTest` — **v1〜v6 をそれぞれ独立した旧形式 fixture で組み立て、
    各版で checksum 検証が通り・訪問が残り・旧欄が落ち・v7 として再保存できること。**
    **v6 だけの移行テストでは足りない**（v3 の `remark`・v4 の返事・v5 の映し返しは版が違う）。
    旧版に後付けされた未導入欄を信用しないことと、改変検出が生きていることも併せて固定する。
    v7 の往復と、v7 の正規形に旧欄が入らないこと
  - `ReadingTraceMergeTest` — メモの合流。**3ケースを定義する:** 20＋1件（新規1件を合流）／
    非重複 20＋20件（**保留**）／重複除去後20件（合流できる）。
    保留のとき**端末側が書き換わらず・退避側が黙って捨てられず・成功扱いにもならないこと**
  - `ReadingTraceLimitsTest` — **実シリアライザで測る**（→ 判断11）。
    引用符・バックスラッシュ・改行で埋めた最大件数のモデルを `encode` し、
    **保存に成功するものは同じ読込上限で再読込できること**
  - `ReadingTraceStoreTest` — encode 後に上限を超える痕跡は**書かずに失敗を返し、
    既存ファイルが残ること**
  - `ReadingTraceControllerTest` — 門番の例外が**メモを預かっているとき**に効くこと
- **instrumentation:** 蒸留の範囲調整と同じく、**タッチで書いて置く経路**は
  `androidTest` のUIテストを1本持つ（`✎` → 入力 → 置く → 一覧に出る）。
  端末AIを通さないので `Assume` による skip は要らない
- **実機確認:** 新規ケースを [device_validation](../../review/device_validation/README.md) へ起こす。
  見るのは5つ — **初読の最中に置いて離脱し、次に開いて残っていること**（`Held` 経路）／
  **満杯で入力欄の文字が消えないこと**／**旧版の痕跡を持つVaultで訪問履歴が消えないこと**
  （**v6 だけでなく、手元に v3 の痕跡があれば必ずそれで見る**）／
  **合流が上限を超えるノートが無変更で保留され、件数が下見と結果に出ること**／
  **再会カードの行からシートが開くこと**
- **保証していないこと:**
  - **プロセス死亡時の預かりは保証しない。** 預かり（`Held`）はプロセスメモリにしかない。
    保証するにはアプリ内部の回復ファイルが要る（蒸留が復旧レコードで同じことをしている）
  - **v7 を旧版のアプリが読むと破損扱いになる。** 対策は取らない（→ §11）
  - **削除は同期しない。** 別端末の退避ファイルから読み戻すと、そちらに残っているメモは復活する
  - **`MAX_MEMOS = 20` はまだ実測で裏を取っていない。** 「エスケープで最悪2倍」という
    見積もりから逆算した暫定値で、**判断11 の実測を書くのは実装時**である。
    測った結果が下回るなら**件数を下げる**（`MAX_MEMO_BYTES` を削るより先に）
  - **満杯と保留の頻度は測っていない。** 20件は容量から決めた値であって、
    「ユーザーが何件置くか」から決めた値ではない。**実機で満杯や保留が出るならここを最初に疑う**

## 11. 既知の制約・未解決事項

| | |
|---|---|
| **前方互換は取らない** | 旧版のアプリが v7 を読むと未対応版＝破損扱いになり、次の訪問が上書きして痕跡が消える。**同一端末に旧版と新版が同居しないこと**と、**まだ配布していないこと**を根拠に対策を取らない。退避ファイル側は束ね方の版を見て「新しすぎる」と言えるので、そちらは既に守られている |
| **合流が上限を超えるノートは読み戻せない** | 判断5。無変更で保留し件数を示す。**端末側が満杯なら、その1件も受け取れない** |
| **メモを編集できない** | 判断9 |
| **Vault横断で読む面が無い** | 本機能は1ノート分まで。横断は別機能が受け持つ |
| **削除が同期しない** | §10「保証していないこと」参照 |
| **全画面表示中は書けない** | 判断7 |

**この機能を足すと、痕跡サイドカーは「訪問・AI要約・印・メモ」の4系統になる。**
メモだけがユーザーの言葉で、残り3つはアプリが書いたものである。
**突き合わせ規則と退避の扱いは、この区別で決まる**（作り直せるものは捨ててよい）。
