# 設計思想 — ノートへのひとこと

**対象領域:** 読んでいるノートに対してAIが1文だけ返し、ユーザーが返事を書ける機能
**状態:** 実装済み・稼働中。保存先は読書痕跡サイドカー（schema v5）。
**関連:** [reflect_reading_trace](reflect_reading_trace.md)（保存先）・[ai_input_excerpt](../system/ai_input_excerpt.md)（入力予算）・[background_ai_ux](../system/background_ai_ux.md)
**経緯:** [開発日誌 2026-08](../../owner/journal/2026-08.md#2026-08-09--ai補記メモをノートへのひとことへ作り直す)

---

## 0. なぜ「AI補記メモ」を作り直したか — 原因は出力枠の配分だった

**再発防止のためにこの因果を残す。**

**出力枠は 256 トークン固定である**（`genai-prompt` beta2 の `maxOutputTokens` は上限も既定値も 256。
超えると `AiTruncatedException` で**生成ごと失敗する**）。つまり出力はゼロサムになる。
旧補記はその枠を分類ラベル4行（固定費）と本命3行（可変費）に割っていた。

**途切れ対策が、可変費だけを削った。** 「3〜5項目」→3項目固定、
「なぜその欠落が理解に効くか」の括弧書き→削除。**分類ラベル4行は1文字も触られていない。**
削る対象を**価値ではなく削りやすさで選んでいた**うえ、削られた括弧書きこそが
「一般論ではない」を担保していた唯一の要素だった。理由を書かせない指示に変えた時点で、
出力は構造上ラベル貼りへ近づく。

**構造的な原因は、補記だけ設計書が無かったこと。** 他機能には設計書があったが補記には無く、
[background_ai_ux](../system/background_ai_ux.md) が持つのは通知層だけだった。
**「補記が何を出すべきか」を書いた文書が存在しなかった**ので、削減が
「何を守るべきか」と突き合わされないまま2か月以上残った。**本文書はその穴を埋めるためにある。**

## 1. 判断1: 1件の「ひとこと」に振り切る（分類は全廃）

**枠を分割しないことが、この設計の中心である。** 256トークンをすべて1文へ集中させる。

```markdown
### AIからのひとこと
「読書は著者との対話である」という考えは、著者の主張に反対するときにも成り立つだろうか？
```

**画面上は種別（問い／関連ノート接続）を見せない。**

| 検討した案 | 却下理由 |
|---|---|
| 3セクション構造（診断1軸＋問い2件＋接続1件） | 分類の自己矛盾は解けるが**1件あたりの長さは変わらず**、§0 の原因が残る |
| 内部は構造・画面は1文 | **構造化した時点で枠は割れる**ので「1文が濃くなる」効果を得られない |

**分類ラベルを全廃する根拠は「行動が決まらないから」ではなく「枠を食うから」。**
実害は、それが価値のある側の枠を先取りしていたこと。

### 1.1 文体 — 「不足」「必要」「べき」を使わない

**採点して宿題を渡す感触を避ける。** ノートを診断するのではなく、考えを開く方向へ寄せる。

| 避ける | 置き換え |
|---|---|
| 具体例を追記すべきです | どんな場面が具体例になりそうだろう？ |
| 根拠が不足しています | この考えの根拠になった経験は何だろう？ |
| 関連ノートを追加してください | `[[〇〇]]` と並べると、別の見方ができそうです |

**冒頭に「あなた」を置かない。** ひとことと映し返しは**ノートについて話す**文なので、
主語に読み手を置く必要がない。日本語は主語を落とせるうえ、二人称で名指しすると**採点者の口調**になる。
（俯瞰要約は「あなたは3回開いています」と**読み手自身の行動を述べる**文なので二人称が要る。
category が違う。）

**捨てずに剥がす。** 指示を外すだけでは小さいモデルは従い切らないので後処理でも落とすが、
**文体の好みで文ごと捨てない** — 一般論や問いのように中身が契約違反であるものとは扱いを変える。
捨てると空振りが増え、「中身は悪くないのに何も出ない」という最悪の形になる。
剥がして読点始まりになるなど壊れる場合は、元のまま出す。

### 1.2 出力仕様

- 1回につき**1件**。原則1文、最大2文。80〜120文字程度
- **ノート固有の言葉を必ず含める**（一般論の禁止はこの1点で担保する）。**リンク提案でも免除しない**
- 要約・評価・称賛・前置き・追記の命令を禁止
- **問いと関連ノート接続を無理に両方出さない。** 有益なほうを1つだけ
- **「補記不要です」は出さない。** 診断結果を見せない設計なので、「不要」という診断だけ見せるのは矛盾する

## 2. 判断2: 保存先は読書痕跡サイドカー

**1文のために `.md` ファイルを作るのは釣り合わない。** 中身が80〜120字なら、
ヘッダ・`Source:`・`Created:` の体裁のほうが本文より長い。

1. **本文を触らない方針に沿う。** `.md` を作るのは Obsidian から見て「ノートが1本増える」ことで、サイドカーとは性格が違う
2. **`aiSummary` と同じ場所・同じ寿命になる。** 保存・検証・バイト上限・スキーマ版管理の基盤が既にある
3. **痕跡と一緒に運べる。** 退避・復元を作るとき対象が1系統で済む

### 2.1 保存はメモリ経由で `flush` へ相乗りさせる（**設計の要**）

**素直に「生成できたら保存する」と書くと、初回のノートで必ず失われる。**
痕跡ファイルは**離脱時（`flush`）か背面化時（`pause`）にしか書かれず**、
`validateReadingTrace` は `visits.isNotEmpty()` を要求する。したがって
**まだ一度も離脱していないノートには痕跡ファイルが存在しない**。
**ひとことは明示ボタンなので初回の閲覧中に押される。**

| 検討した案 | 問題 |
|---|---|
| 生成成功時に訪問を1件書いて痕跡を作る | **「読んだ」の定義が汚れる。** 到達率0%の訪問が痕跡へ混ざる |
| 痕跡が無ければ保存しない | 初回のノートでは**常に**失われる。仕様の破綻 |

`flush` は既に `writeMutex` で直列化され read-modify-write を守っているので、
そこへ1欄足すだけで**「1回の閲覧＝1訪問」を壊さずに**痕跡ができた瞬間へ載る。

### 2.2 1ノート1件（仕様）

サイドカーは `vaultRelativePath` が主キーなので、**新しいひとことは古いものを上書きする。**
1文の履歴を溜めても読み返す導線が無く、溜めるなら件数上限と破棄の設計が要り、
「1文を軽く出す」という判断1と釣り合わない。

### 2.3 既存の `_AI補記/*.md` は移行も削除もしない

ユーザーのVaultにある `.md` なのでそのまま残す。**アプリが作ったものをアプリが消すのは不可逆な削除にあたる。**
ただし**一覧と削除の導線は残す** — 生成をやめるだけで機能を消すわけではないので、
撤去すべきは書き込み側だけだった。撤去すると**ファイルだけがVaultに取り残され**、
ユーザーはObsidianで手作業になる。**「作らないが、片付けられる」**が正しい状態。

## 3. 判断3: 起動は明示ボタンのまま

**自動化しない。** Nano は `generateMutex` で直列化され1回数十秒かかる。ノートを開いた時点で走らせると、
要約・関連ノート・痕跡要約と待ち行列を取り合い、**開くたびの占有が1本増える**。
入力指紋キャッシュも優先度キューも無いので、自動生成が先に入るとユーザー操作が後ろで待つ。

**「ひとこと」は待って読むものではなくなるが、待たされないことのほうが効く。**

## 4. 判断4: 空振りは「何も出さない」

有益な返答が無ければ表示しない。ただし**押したのに何も起きないのは故障に見える**ので、
UI側の**固定文**で受ける（`今は新しい問いは見つかりませんでした`）。
**これをAIに生成させない** — 空振りの判定までモデルに委ねることになり、
「空振りだと宣言する文」に枠を使う。固定文なら枠を1トークンも使わない。

## 5. 判断5: 出力の検証は指示ではなく検査で担保する

1. **空・極端に短い／長い応答を弾く**（文字数範囲で機械的に判定）
2. **ノート固有の語を含むか**（`textBigrams` で本文との重なりを測る）。**例外は設けない** —
   かつて「実在ノートへのリンクを含むなら根拠として認める」免除を持っており、
   リンク先は実在するが**地の文は丸ごと一般論**という、いちばん潰したかった形が通っていた
3. **`[[...]]` は渡した候補集合の中のノート名だけを許す**（ID契約。候補を「ID | タイトル」で提示しIDを返させ `validIds` と照合）
4. **問いと接続の排他を文末の形で判定する。** 日本語の問い・勧誘は文末に現れるので、
   末尾のリンクを剥がしてから文末を見る。**中間の疑問詞や助詞の「か」で見てはいけない**
   （「…どう始めるかまで考えられそうです。」のような正しい宣言的接続が落ちる）。
   **`でしょう`／`だろう` は推量であって問いではない** — 疑問になるのは末尾に「か」が付いたときだけ

検証は純関数へ置き、JVMテストを同時に書く。

## 6. 判断6: 返事は「保存は原文・AIへは抜粋」で分ける

**上限を1本で決めたのが誤りだった。** `MAX_REPLY_CHARS = 400` は「1文だから」と置いた数字から
逆算した値で、**ユーザーの文章の長さをAIの都合ですらない思いつきで縛っていた。**

| | 値 |
|---|---|
| 保存する返事 | **8,000字**（完全保存。切り詰めない） |
| 静かに知らせる目安 | **2,000字**（壁ではなく合図） |
| AIへ渡す返事 | **先頭＋末尾で400字へ抜粋**（`excerptReplyForPrompt`） |

**「汎用エディタにしない」は壁ではなく合図で守る。** 壁にすると、長く書きたかった回に
ユーザーの言葉が消える。2,000字を超えたら「ノート本体のほうが探しやすい」と一言添えるだけにする。

**上限どうしの整合は計算で固定する**（`ReadingTraceLimitsTest`）。返事の上限を上げると
ファイル全体の読み込み上限を超え得るが、これは**保存は成功しテストも緑なのに次回読めなくなる**という
気づきにくい壊れ方をする。数えるのをやめて全フィールドの最悪ケースを足す形にした（128KB）。

**上限を超えた入力を「無かったこと」にしない。** 受け取ってから切り、切ったら必ず示す。
これはユーザーの言葉を扱うすべての口に当てはまる。

## 7. 判断7: 「保存ボタンを押した文章は必ず永続化する」を契約にする

**穴はどれも「押したのに残らない」型だった。**

- **保存結果は4値で見せる**（`未保存 / 保存中 / 保存済み / 保存失敗`）。
  **`Boolean` 2本にしない** — 「保存中かつ未保存」のような意味の無い組み合わせが型として作れる。
  **保存済みの判定には下書きとの差を入れる**（書き直している最中でも過去の日時があるだけで「保存済み」と出た）
- **失敗後も再試行できる。** 失敗時も本文は状態へ残すので `isDirty` が false になる。
  有効条件は `isDirty || replyStatus == Failed`。離脱の確認も同じ —
  **「書き換えたか」ではなく「まだファイルに残っていないか」で見る**
- **返事を預かっているときは離脱時の門番を通す。** `recordVisit` の門番（10秒以上・1ブロック以上）を
  効かせると、条件未達で離れた瞬間に返事が消える。
  **ユーザーが返事を書いた事実は、10秒のスクロールより強い関与である**
- **未保存の下書きは警告なく消さない**（「別のひとこと」「戻る」で確認を出す）

### 7.1 退避スロットは Controller が持つ

`flush()` は保存コルーチンを起動した**直後**に `session = null` にするため、
後から失敗してセッションへ戻しても**その owner はもう現役ではなく**、次の書き込み契機が来ない。
**セッションではなく Controller が持つ退避スロットへ移す。**

- **退避するのは返事ではなく `ReadingTrace` そのもの。** 返事だけを持つと
  「既存の痕跡へ載せ直す」ことしかできず、**ファイルがまだ無い＝初読で返事まで書いた回**が落ちる
- **Vault＋相対パスをキーにした Map**（上限8件）。単一スロットだと A の退避中に B で書くと A が消える
- **返事を持つ痕跡だけを積む。** 訪問だけの失敗はセッション側の巻き戻しが同じ閲覧のうちに書き直すし、
  失ってももう一度読めば付き直る。**返事は作り直せない**ので扱いが違う
- **古い退避が新しい返事を上書きしないよう、返事の日時で新旧を見る。**
  別端末が同期で書き込んだ場合はアプリの保存経路を通らないため、**日時の比較だけが唯一の防波堤**になる
- **退避を消してよい条件は `Reflection` 全体の一致**（返事が同じでも元の問い・日時・映し返しが違えば別物）
- **専用の Mutex を持つ。** `writeMutex` と兼用しないのは、退避の書き直しが
  「スナップショット → 1件ずつ `writeMutex` で保存 → 消す」の順で動くため。
  取得順は `writeMutex → pendingMutex` の一方向。
  **スナップショット後に同じキーへ新しい退避が入っていたら消さない**
- Vault切替では捨てる（旧Vaultの返事を新Vaultへ書かない）

## 8. データモデル（schema v5）

`Reflection`（ひとこと＋返事＋映し返し）を**1組で持つ**。別々の文字列にすると
片方だけ残る状態を型で作れてしまう。

- **返事はAIへ再送しない。** 往復させると「AIと会話するアプリ」になる
- **返事に対しては映し返し（AIの1文）を1回だけ添えて対話を閉じる**
- **返事だけ即時保存。** 生成物は作り直せるが**書いた言葉は作り直せない**。
  痕跡ファイルが未作成なら離脱時の書き込みへ預け直す
- **映し返しの本文は表示中のノートから引く。** 生成時に受け取った本文をフィールドへ写す形だと、
  保存済みの読み戻し経路がそこを通らず**後から返事を書くと映し返しが黙って出なかった**

|---|---|
| 自動生成 | 判断3。入力指紋キャッシュが前提 |

**`MIN_GROUNDING_RUN = 4`（原文と4文字以上一致）は見積もりでしかない。**
大きすぎれば妥当なひとことまで落ち、**画面には「見つかりませんでした」しか出ない**ので、
失敗が静かで気づきにくい。実機で空振りが続くならここを最初に疑う。
