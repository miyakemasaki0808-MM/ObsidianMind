## 1. 概要

読んでいるノートに対して、**AIが1文だけ返す**。ユーザーはそれに**返事を1回書ける**。
返事にはAIが**映し返し**を1文添えて、その場で対話を閉じる。

Reflect（省察）系の中で、**ユーザー自身の言葉を受け取る唯一の口**である。
蒸留が「本文の中から選ばせる」のに対し、こちらは「本文の外へ短く置く」。

## 2. ゴールと非ゴール

### ゴール
- ノート固有の内容に触れた**1文**を返し、考えを次へ開く
- ユーザーの返事を**失わずに**保存する
- 待たせない（明示ボタン・空振り時は即座に固定文）

### 非ゴール
- **AIとの継続的な会話にしない。** 返事はAIへ再送しない。1往復で閉じる
- **汎用エディタにしない。** 長文はノート本体で書くもの（ただし壁ではなく合図で守る → §5）
- **診断・採点をしない。** 分類ラベルも「補記不要です」も出さない
- **履歴を溜めない。** 1ノート1件（上書き）

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| ひとこと生成 | AIが1文を返す。**開始と同時にノートタブへ戻る** | `remark` 画面でボタンを明示的に押す |
| 空振り表示 | `今は新しい問いは見つかりませんでした`（**固定文・AI生成ではない**） | 検査を通る応答が得られなかったとき |
| 返事の入力と保存 | 返事を書いて保存でき、保存状態が表示される | ひとことが表示されているとき |
| 映し返し | 返事に対してAIが1文返す | 返事を保存したとき（1回だけ） |
| 保存済みの復元 | 前回のひとこと・返事・映し返しが再表示される | **`remark` 画面を開いたとき**（ノート表示では読まない） |
| 旧補記の片付け | `_AI補記/*.md` の一覧と削除 | 補記管理画面（**生成はもう行わない**） |

## 4. 現在のユーザーフロー

**入口はAIタブのボタン1つ。結果の本体は専用ルート `RemarkScreen` にある**（AIタブには出ない）。

1. AIタブの **`✨ ノートへのひとこと`** を押す → `remark` ルートへ遷移する（`RemarkPanel` はこのボタンだけを持つ）
2. **画面を開いた時にだけ** `restoreSavedRemark()` が痕跡から前回の `Reflection` を読み、あれば表示する
   - **ノート表示の経路には置かない。** 置くと**ノートを開くたびサイドカーを1件読む**ことになる
   - 保存済みの有無をAIタブ側で出し分けないのも同じ理由
3. `ひとことをもらう`（保存済みがあれば `別のひとことをもらう`）を押す → 生成を開始し、
   **自動でノートタブへ戻る**（待機画面を出さず、同じノートを読みながら待たせる）
4. 生成中は AIタブのバッジが回り、`RemarkPanel` のラベルが `考えています…` になる
5. 完了すると Snackbar `ひとことが届きました＋見る` が出る。`見る` で `remark` へ戻って読む
6. 返事を書いて保存する → `saveReply()`
   - 痕跡ファイルが**既にある**なら書き込んで `Saved`
   - **まだ無い**なら離脱時の書き込みへ預けて `Held`（→ §8 判断2.1）
7. 映し返しが1文返り、対話が閉じる
8. ノートを離れる → `flush()` が痕跡へ確定。失敗しても Controller の退避スロットが持ち続ける（→ §8 判断7.1）

**中断:** ノートを切り替えると `cancelAndClear()` で生成が止まり、状態は `Idle` へ戻る。

## 5. 機能仕様

- **前提条件:** Vault選択済み・ノート表示中。端末AIが使えないときは `AiNotice`
  （**`Unusable` でも `Error` でもない** — 生成の失敗と状態の説明を分ける
  → [background_ai_ux](../system/background_ai_ux.md) §6）
- **入力:** ノート本文の抜粋・関連ノート候補（`ID | タイトル`）・旧補記の有無
- **出力:** 1件のひとこと（原則1文、最大2文、80〜120字程度）
- **上限（すべて実装の定数）:**

  | 対象 | 値 | 定数 |
  |---|---|---|
  | 出力枠 | **256トークン固定**（上限＝既定値。超えると `AiTruncatedException` で**生成ごと失敗**） | `genai-prompt` beta2 |
  | ひとことの保存 | 512バイト | `MAX_REMARK_BYTES` |
  | 返事の保存 | **8,000字**（切り詰めない） | `MAX_REPLY_CHARS` |
  | 返事の保存（バイト） | 25,600バイト | `MAX_REPLY_BYTES` |
  | 静かに知らせる目安 | 2,000字（**壁ではなく合図**） | `SOFT_REPLY_CHARS` |
  | AIへ渡す返事 | 先頭＋末尾で400字へ抜粋 | `REPLY_EXCERPT_CHARS` |
  | 原文一致の最小連長 | 4文字 | `MIN_GROUNDING_RUN` |
  | 痕跡ファイル全体 | 128KB | `MAX_FILE_BYTES` |

- **出力の検査（指示ではなく検査で担保する → §8 判断5）:**
  1. 空・極端に短い／長い応答を弾く
  2. **ノート固有の語を含むか**（`textBigrams` で本文との重なり）。**例外なし**
  3. `[[...]]` は渡した候補集合のIDだけを許す（`validIds` と照合）
  4. 問いと接続の排他を**文末の形**で判定（末尾のリンクを剥がしてから見る）
- **通知（3層すべてを使う）:**

  | 層 | 中身 |
  |---|---|
  | Snackbar | `ひとことを考えています…` / `ひとことが届きました＋見る` / `今は新しい問いは見つかりませんでした` / 書式失敗（再試行つき） |
  | AIタブのバッジ | **生成中だけ**（`AiTabBadgeState` は `None` / `Loading` の2値）。完了✓・失敗! は持たない |
  | ボタンのラベル多態 | `✨ ノートへのひとこと` ⇄ `考えています…`（AIタブ側）、`ひとことをもらう` ⇄ `別のひとことをもらう`（画面側） |

  **空振り（`Empty`）には「見る」を出さない** — 失敗ではないので行き先を示さず、再試行しても同じだから。
  **書式失敗（`Unusable`）は空振りと分ける** — もう一度きけば変わりうる。
  **全画面ルート表示中は Snackbar を抑制する。**

- **エラー／AI非対応／キャンセル時:**
  - AI非対応端末 → `Unusable`（機能ごと出さない）
  - 生成失敗 → `Error`（メッセージを表示）
  - ノート切替 → `cancelAndClear()`。`CancellationException` は再throwする
  - 保存失敗 → `Failed`。**本文は状態に残し、再試行できる**

## 6. 状態とデータ

**UI状態 `RemarkState`（`NoteUiState.remarkState`）:**
`Idle` / `Loading` / `Ready(reflection, replyStatus)` / `Empty` / `Unusable` / `Error`

**保存状態 `ReplyStatus`:** `None` / `Saving` / `Held` / `Saved` / `Failed`
（**`Boolean` 2本にしない** — 「保存中かつ未保存」のような無意味な組み合わせが型として作れてしまう）

**永続化:** 読書痕跡サイドカー `_ReadingTraces/*.json`（schema v5、v1〜v4も読める）。
`Reflection`（ひとこと＋返事＋映し返し）を**1組で持つ** — 別々の文字列にすると片方だけ残る状態を型で作れる。

**破棄条件:** `vaultRelativePath` が主キーなので**新しいひとことが古いものを上書き**する。
Vault切替では退避スロットも捨てる（旧Vaultの返事を新Vaultへ書かない）。

**契約2箇所への登録（ノート単位の状態）:**
`NoteSessionCoordinator.cancelNoteScopedJobs()` → `remark.cancelAndClear()`、
`NoteUiStateStore.withNoteScopedReset()` → `remarkState = RemarkState.Idle`。**両方に登録済み。**

## 7. システム設計

```
AiTab / RemarkScreen
   └─ NoteSessionCoordinator
        └─ RemarkController          create() / restoreSaved() / saveReply() / cancelAndClear()
             ├─ PromptBuilder → AICoreClient（generateMutex で直列・60秒タイムアウト）
             ├─ RemarkComposer（純関数：検査・抜粋・上限）  ← JVMテスト
             └─ ReadingTraceStore（flush 時に writeMutex で直列化）
```

**保存はメモリ経由で `flush` へ相乗りさせる**（→ §8 判断2.1）。これがこの機能の構造上の要で、
ここを「生成できたら保存する」と素直に書くと**初回のノートで必ず失われる**。

## 8. 設計判断と代替案

### なぜ「AI補記メモ」を作り直したか — 原因は出力枠の配分だった

**出力枠は256トークン固定でゼロサム。** 旧補記はその枠を分類ラベル4行（固定費）と本命3行（可変費）に割っていた。
途切れ対策が**可変費だけを削り**、分類ラベル4行は1文字も触られなかった。
**削る対象を価値ではなく削りやすさで選んでいた**うえ、削られた括弧書きこそが「一般論ではない」を担保していた唯一の要素だった。

**構造的な原因は、補記だけ設計書が無かったこと。** 「何を出すべきか」を書いた文書が存在しなかったので、
削減が「何を守るべきか」と突き合わされないまま2か月以上残った。**本文書はその穴を埋めるためにある。**

### 判断1: 1件の「ひとこと」に振り切る（分類は全廃）

**枠を分割しないことが設計の中心。** 256トークンをすべて1文へ集中させる。画面上は種別（問い／関連ノート接続）を見せない。

| 検討した案 | 却下理由 |
|---|---|
| 3セクション構造（診断1軸＋問い2件＋接続1件） | 分類の自己矛盾は解けるが**1件あたりの長さは変わらず**、上記の原因が残る |
| 内部は構造・画面は1文 | **構造化した時点で枠は割れる**ので「1文が濃くなる」効果を得られない |

**分類ラベルを全廃する根拠は「行動が決まらないから」ではなく「枠を食うから」。**

### 判断1.1: 文体 — 「不足」「必要」「べき」を使わない

**採点して宿題を渡す感触を避ける。** ノートを診断するのではなく、考えを開く方向へ寄せる。

| 避ける | 置き換え |
|---|---|
| 具体例を追記すべきです | どんな場面が具体例になりそうだろう？ |
| 根拠が不足しています | この考えの根拠になった経験は何だろう？ |
| 関連ノートを追加してください | `[[〇〇]]` と並べると、別の見方ができそうです |

**冒頭に「あなた」を置かない。** ひとことと映し返しは**ノートについて話す**文なので主語に読み手を置く必要がない。
二人称で名指しすると採点者の口調になる。（俯瞰要約は「あなたは3回開いています」と**読み手自身の行動を述べる**文なので二人称が要る。category が違う。）

**捨てずに剥がす。** 文体の好みで文ごと捨てない — 中身が契約違反であるもの（一般論・問い）とは扱いを変える。
捨てると空振りが増え、「中身は悪くないのに何も出ない」という最悪の形になる。剥がして壊れる場合は元のまま出す。

### 判断2: 保存先は読書痕跡サイドカー

**1文のために `.md` を作るのは釣り合わない。** 中身が80〜120字なら、ヘッダ・`Source:`・`Created:` の体裁のほうが本文より長い。

1. 本文を触らない方針に沿う（→ [ADR-0004](../decisions/ADR-0004-do-not-rewrite-vault-body.md)）
2. `aiSummary` と同じ場所・同じ寿命になる。保存・検証・バイト上限・版管理の基盤が既にある
3. 痕跡と一緒に運べる。退避・復元を作るとき対象が1系統で済む

### 判断2.1: 保存はメモリ経由で `flush` へ相乗りさせる（**設計の要**）

痕跡ファイルは**離脱時（`flush`）か背面化時（`pause`）にしか書かれず**、`validateReadingTrace` は `visits.isNotEmpty()` を要求する。
したがって**まだ一度も離脱していないノートには痕跡ファイルが存在しない**。**ひとことは明示ボタンなので初回の閲覧中に押される。**

| 検討した案 | 問題 |
|---|---|
| 生成成功時に訪問を1件書いて痕跡を作る | **「読んだ」の定義が汚れる。** 到達率0%の訪問が混ざる |
| 痕跡が無ければ保存しない | 初回のノートでは**常に**失われる。仕様の破綻 |

`flush` は既に `writeMutex` で直列化され read-modify-write を守っているので、
**「1回の閲覧＝1訪問」を壊さずに**痕跡ができた瞬間へ載せられる。

### 判断2.2 / 2.3: 1ノート1件・旧補記は移行も削除もしない

履歴を溜めても読み返す導線が無く、溜めるなら件数上限と破棄の設計が要り、「1文を軽く出す」と釣り合わない。

既存の `_AI補記/*.md` はユーザーのVaultにある `.md` なので残す。**アプリが作ったものをアプリが消すのは不可逆な削除にあたる。**
ただし**一覧と削除の導線は残す** — 撤去すべきは書き込み側だけで、撤去すると**ファイルだけが取り残される**。
**「作らないが、片付けられる」**が正しい状態。

### 判断3: 起動は明示ボタンのまま

Nano は `generateMutex` で直列化され1回数十秒。ノートを開いた時点で走らせると、要約・関連ノート・痕跡要約と待ち行列を取り合う。
入力指紋キャッシュも優先度キューも無いので、自動生成が先に入るとユーザー操作が後ろで待つ。
**「ひとこと」は待って読むものではなくなるが、待たされないことのほうが効く。**

### 判断4: 空振りは「何も出さない」

押したのに何も起きないのは故障に見えるので、UI側の**固定文**で受ける。
**これをAIに生成させない** — 空振りの判定までモデルに委ねることになり、「空振りだと宣言する文」に枠を使う。固定文なら枠を1トークンも使わない。

### 判断5: 出力の検証は指示ではなく検査で担保する

検査の内容は §5 に置く。ここでは**なぜ指示ではなく検査なのか**だけを書く。

- **原文一致に例外を設けない。** かつて「実在ノートへのリンクを含むなら根拠として認める」免除を持っており、
  リンク先は実在するが**地の文は丸ごと一般論**という、いちばん潰したかった形が通っていた
- **問いの判定は文末で見る。** 中間の疑問詞や助詞の「か」で見ると、
  「…どう始めるかまで考えられそうです。」のような正しい宣言的接続が落ちる。
  **`でしょう`／`だろう` は推量であって問いではない** — 疑問になるのは末尾に「か」が付いたときだけ

### 判断6: 返事は「保存は原文・AIへは抜粋」で分ける

**上限を1本で決めたのが誤りだった。** 旧 `MAX_REPLY_CHARS = 400` は「1文だから」と置いた数字からの逆算で、
**ユーザーの文章の長さをAIの都合ですらない思いつきで縛っていた。**

**「汎用エディタにしない」は壁ではなく合図で守る。** 壁にすると、長く書きたかった回にユーザーの言葉が消える。

**上限どうしの整合は計算で固定する**（`ReadingTraceLimitsTest`）。返事の上限を上げるとファイル全体の読み込み上限を超え得るが、
これは**保存は成功しテストも緑なのに次回読めなくなる**という気づきにくい壊れ方をする。
数えるのをやめて全フィールドの最悪ケースを足す形にした。

**上限を超えた入力を「無かったこと」にしない。受け取ってから切り、切ったら必ず示す。**

### 判断7: 「保存ボタンを押した文章は必ず永続化する」を契約にする

**穴はどれも「押したのに残らない」型だった。**

- **保存済みの判定に下書きとの差を入れる**（書き直している最中でも、過去の日時があるだけで「保存済み」と出た）
- **失敗後も再試行できる。** 有効条件は `isDirty || replyStatus == Failed`。
  離脱の確認も**「書き換えたか」ではなく「まだファイルに残っていないか」で見る**
- **返事を預かっているときは離脱時の門番を通す。** `recordVisit` の門番
  （条件は [reflect_reading_trace](reflect_reading_trace.md) §5）を効かせると、
  条件未達で離れた瞬間に返事が消える。**ユーザーが返事を書いた事実は、短いスクロールより強い関与である**
- **未保存の下書きは警告なく消さない**

### 判断7.1: 退避スロットは Controller が持つ

`flush()` は保存コルーチンを起動した**直後**に `session = null` にするため、後から失敗してセッションへ戻しても
**その owner はもう現役ではなく**、次の書き込み契機が来ない。**セッションではなく Controller が持つ退避スロットへ移す。**

- **退避するのは返事ではなく `ReadingTrace` そのもの。** 返事だけを持つと「既存の痕跡へ載せ直す」ことしかできず、
  **ファイルがまだ無い＝初読で返事まで書いた回**が落ちる
- **Vault＋相対パスをキーにした Map**（上限8件）。単一スロットだと A の退避中に B で書くと A が消える
- **返事を持つ痕跡だけを積む。** 訪問だけの失敗は同じ閲覧のうちに書き直されるし、失ってももう一度読めば付き直る。
  **返事は作り直せない**ので扱いが違う
- **古い退避が新しい返事を上書きしないよう、返事の日時で新旧を見る。**
  別端末が同期で書き込んだ場合はアプリの保存経路を通らないため、**日時の比較だけが唯一の防波堤**になる
- **退避を消してよい条件は `Reflection` 全体の一致**（返事が同じでも元の問い・日時・映し返しが違えば別物）
- **専用の Mutex を持つ。** 取得順は `writeMutex → pendingMutex` の一方向。
  **スナップショット後に同じキーへ新しい退避が入っていたら消さない**

### 判断8: 映し返しの本文は表示中のノートから引く

生成時に受け取った本文をフィールドへ写す形だと、保存済みの読み戻し経路がそこを通らず、
**後から返事を書くと映し返しが黙って出なかった。**

## 9. 品質要件

- **性能:** 生成は Mutex 直列で1回数十秒・60秒タイムアウト。**明示ボタンなので待つ前提に立てる**
- **プライバシー:** ノート本文はプロンプトへ入るが**ネットワーク権限が無いので端末外へ出ない**（→ [ADR-0002](../decisions/ADR-0002-on-device-ai-only.md)）
- **データ保護:** ユーザーが書いた返事は作り直せない。§8 判断7・7.1 がこの一点のためにある
- **端末制約:** Nano 非対応端末では `Unusable` で機能ごと出さない

## 10. 検証と受け入れ条件

- **JVMテスト:** `RemarkComposerTest`（検査・抜粋・上限の純関数）／`RemarkControllerTest`（保存状態遷移・退避）／
  `ReadingTraceLimitsTest`（**上限どうしの整合を計算で固定**）
- **instrumentation:** 専用なし。端末AIを通す経路は `OnDeviceGenerationTest` が代表して覆う
- **実機確認:** 5巡実施済み（→ §12）。**change_history には1〜4巡目の行しかないが、5巡目まで実施されている**
- **保証していないこと:**
  - **プロセス死亡時の退避は保証しない。** 退避はプロセスメモリにしかない。
    保証するにはアプリ内部の回復ファイルが要る（蒸留が復旧レコードで同じことをしている）。
    現状は**「プロセスが生きている間は必ず書き直す」まで**
  - **別端末との同時編集は last-writer-wins。** マージも世代解決もしない
  - **空振りの頻度は測っていない。** `MIN_GROUNDING_RUN = 4` は見積もりでしかない
