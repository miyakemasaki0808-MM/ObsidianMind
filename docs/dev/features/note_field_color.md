## 1. 概要

冊子（`ひく🎲` から開く10枚の束）の紙を、そのノートの**分野**で塗り分ける。

**出どころはオーナーの体感である。** 「冊子が真っ白になるのがなんか微妙。
カテゴリ（技術記事・AI・Python など）で色分けみたいなものはできないか」（2026-09-06）。

**色を使えるのは冊子の面だけである。** 読む面の地色は年代が持ち切っており、
チャネルの持ち主は面ごとに決まる（→ [bearing_channels](../system/bearing_channels.md) 判断6）。

## 2. ゴールと非ゴール

### ゴール
- 冊子をめくっているあいだ、**眺めるだけで束の中身の散らばりが分かる**
- **眺めて捨てる速さを削らない**（→ [booklet_mode](booklet_mode.md) 判断3）
- 分野の判定を、**読む面の栞（分野を位置と本数で示す案）が後から乗れる土台**として作る

### 非ゴール
- **読む面には載せない。** 本文の紙は年代が持つ
- **分野で絞って引かない。** Rediscover の純粋ランダムには混ぜない（別機能として扱う）
- **ユーザーに分類させない。** 設定画面で分野を手当てさせる形は採らない
- **分類の正しさを機械で測らない** → §10

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 冊子の紙の色 | 束の各ページの地色が分野ごとに変わる | 冊子を開いたとき（分野が決まっているノートだけ） |
| 分野名の表示 | 紙に分野名が小さく出る | 同上。**色以外の手がかり（1.4.1）として必須** |
| フォルダからのヒント | — （ユーザーには見えない） | ノートを走査したとき |
| AIによる判定 | — （結果が色として遅れて出る） | **ノートを開いたとき。判定済みでなければ必ず走る** |

## 4. 現在のユーザーフロー

> **未確認:** 実装が無いため、以下は設計上の想定である。

1. ノートを開く。**判定済みなら何もしない**（保存から読む）
2. 未判定なら、パス（フォルダ）から**ヒント**を作る。これは判定ではなく候補である
3. **バックグラウンドでAIが、ヒントを添えて固定リストから1つ選ぶ**
4. AIが使えない／失敗したときは、**ヒントをそのまま採る**（→ §8 判断6）。どちらも無ければ未判定のまま
5. 結果はアプリ内に保存され、以後は再実行しない
6. 冊子を開くと、束10枚の紙が**保存済みの分野の色**で出る。未判定の紙は無彩色

## 5. 機能仕様

- **前提条件:** Vault が選択済み。**Nano が使えない端末ではヒントへ縮退する**（→ §8 判断6）
- **入力と出力:** 入力は `vaultRelativePath` と（AI段では）本文の抜粋。出力は固定リストの分野1つ
- **上限:** **色は6つまで。**超えた分と未判定は無彩色（→ [bearing_channels](../system/bearing_channels.md) 判断3の「5〜7色」）
- **状態遷移:** **未判定 → 暫定（ヒント由来）→ 確定（AI由来）** の3値（→ §8 判断8）。
  **一方向なのは同じ入力版の中だけ** — 本文・ヒント・語彙が変われば入力版が変わり、確定でも再判定する
- **保存と寿命:** **アプリ内に保存する**（Vault には書かない）。**索引は2つ**（→ §8 判断10）。
  鍵の構成と名前空間は判断9。**アプリ再起動・Vault の A→B→A で永続側を捨てない**
- **画面遷移:** 無し。既存の画面に色と分野名が増えるだけ
- **他機能との連携:** 冊子（紙の色）。将来、読む面の栞が同じ判定を使う → §8 判断5
- **エラー／AI非対応／キャンセル時:** **黙ってヒント（フォルダ由来）へ縮退する。**ヒントも無ければ無彩色。
  ReadingTrace と同じベストエフォート（→ [architecture](../system/architecture.md) のController比較表）。
  ノート切替では requestId ＋ `isCurrent()` で捨てる

> **未確認:** 抜粋の文字数上限と、プロンプトの具体形。
> 用途別上限は [ai_input_excerpt](../system/ai_input_excerpt.md) に1つ足す必要がある。

## 7. システム設計

```
ノートを開く
 └─ 判定済みか？
      ├─ Yes → 何もしない（保存から読む）
      └─ No  → パス → **ヒント**（非AI・即時・純関数。判定ではない）
                └─ **常に** Nano へ（ヒントを添えて固定リストから選ばせる）
                     ├─ 成功 → 確定として保存
                     └─ 失敗・非対応・キャンセル → ヒントを暫定として扱う（→ §8 判断6・§11）
     └─ 索引A（ノート→分類）と索引B（入力指紋→AI結果）へ書く
冊子を開く
 └─ 束10枚の `ref` で**索引Aだけ**を引く → 色
      **本文I/Oも保存ストアの読み出しも増やさない**（索引AはVault走査時にメモリへ載っている）
```

**非AIで候補（ヒント）を出し、AIが選ぶ形**である。**ヒントの有無で経路が分かれないこと**が判断6 の要点で、
分かれる図に戻すと採番崩壊に効かなくなる。
（→ [feature_ideas](../../_wip/feature_ideas.md) の「非AIで候補を出し、AIは選別だけさせる」型）。

## 8. 設計判断と代替案

### 判断1: 色を載せるのは冊子の面だけ

**正本は [bearing_channels](../system/bearing_channels.md) 判断6。** ここでは結論だけ持つ —
読む面の地色は年代、冊子の面の地色は分野。**面積が味方する**（冊子の紙は画面最大の部品で、
年代の地色が [ui_design_principles](../system/ui_design_principles.md) §3 を免れたのと同じ面積帯にいる）。

### 判断2: 「冊子を開いた瞬間に10件分類する」は採らない

[booklet_mode](booklet_mode.md) 判断3 は**冊子からAI生成を全部外すことで成立**しており、
理由もそこに書かれている — Nano は Mutex 直列で1回数十秒なので、**10枚を先読みすると数分占有する**。
載せるとこの判断を正面から取り消すことになる。
**判定の契機はノートを開いたときにし、冊子は保存済みの結果を読むだけにする。**

### 判断3: 保存は「後で足す最適化」ではなく前提条件

ノートを開いた契機で走る Nano は現在**要約と ReadingTrace の2本**で、分野判定が3本目になる。
**判断6 で「AIが常に判断する」を選んだ結果、この3本目は全ノートで走る。**
保存しないと、同じノートを開き直すたびに待ち時間が伸び続ける。**保存はこの機能の前提条件である。**
したがって**入力指紋によるAI結果キャッシュ**（本文ハッシュ＋抜粋方式＋プロンプト版＋機能種別を鍵にする案）の
鍵設計を、**この経路で先に実装する**。
分野は再生成できる導出値なので、**Vault には書かず、退避・復元の対象にもしない。**

### 判断4: フォルダで足りる場合でも、AI段を作る（2026-09-09、オーナー）

**実測では、AI段が実際に働く余地はほとんど無い。** 2026-09-09 にオーナーのVault（645本）を測った。

| 方式 | 結果 |
|---|---|
| フォルダ名から自動（第2階層） | **24区分**。上位6つで75.5%どまり。区分名が採番コードで**意味を読めない** |
| 採番コードから自動（4桁） | 19区分だが、**1つのコードが60%を飲む**（読書由来のものが全部入るため） |
| **中身を読んで作った対応表** | **6分野で97.2%。AIが要るのは645本中3本** |

**それでも (B)（AI段を作る）を選んだ。** オーナーの判断と理由:

> やっぱAI活用というのがテーマになっているため、(B)でいきたいですねぇ。
> 今回はたまたま想像より構造的になっているとはいえ、第三者のノートは基本ぐちゃぐちゃなためです。
> また、俺が採番体系を崩壊させるリスクもあるための選択となります。

**この判断は上の実測に反していない。** 「3本」は**いま整っているVaultのスナップショット**であって、
設計の性質ではない。対応表の 97.2% は**一人が手で維持している規約に依存した数字**で、
規約が崩れた瞬間に落ちる。**AI段は、その落ちしろを受ける。**

**代償は正直に持つ** → §11（初回は色が揃わない・全ノートでNanoが走る）。

### 判断5: 分野の判定は、いまは本書が持つ

分類軸は**読む面の栞・放置ノートの棚卸し・関連ノートの再ランク**も欲しがる。
**いまは利用者が1つなので本書に置き、2つ目が来たら `system/` へ切り出す。**
先に横断文書を作らないのは、**利用者が1つの規約は「横断」ではない**ため。

### 判断6: フォルダは判定ではなく「ヒント」にする（2026-09-09、オーナー）

**フォルダで決まったらAIを呼ばない、という形は採らない。** AIが常に判断し、
フォルダ由来の分野は**候補としてプロンプトへ添えるだけ**にする。

**理由は判断4 と同じところから来ている。** 「フォルダ優先・AIは埋めるだけ」だと、
**対応が古くなって*間違った*分野を返すようになっても、AIは呼ばれない**（決まっているので）。
採番体系が崩れるリスクに備えるために AI 段を作ったのに、**その形では崩れたときに効かない。**

**代償:** Nano が全ノートで走る（保存があるので1本1回）。**保存が前提条件へ格上げされる** → 判断3。

**縮退はヒントへ倒す。** Nano 非対応端末・生成失敗・タイムアウトのときは、
**フォルダ由来のヒントをそのまま採る**。ここを「無彩色」にすると、
**Nano が無い端末でこの機能が丸ごと消える** — 判定の精度は落ちてよいが、機能は残す。

### 判断7: 語彙は「一般語彙＋Vault別の追加」で持つ（2026-09-09、オーナー）

固定リストを実測した6分野そのままにすると、**他人のVaultではほぼ全部が「その他」**になる。
一般語彙だけにすると、**このVaultでは7割が1つの分野に集中して分かれない**。
**両方持つ** — どのVaultでも意味を持つ土台の上に、そのVaultで多い分野を足す。

> **未確認:** **追加分をどこから引くかは決めていない。** 走査結果から作る・AIに作らせる・
> オーナーが書く、のどれも候補である。**リストを作る仕組み自体が新規実装**になるので、
> 規模はここで一段上がる。**実装の前に決める。**

### 判断8: 分類は3値で持つ — 暫定を確定と区別する（レビュー P2-1）

**「未判定 / 判定済み」の2値だと、一時的なAI障害が永久に固定される。**
初回表示でモデルが未準備なら、ヒントを採って「判定済み」になり、
**AIが使えるようになってからも呼ばれない。** 判断6 の「AIで補正する」狙いがそこで死ぬ。

| 値 | 表示 | 再判定 |
|---|---|---|
| **未判定** | 無彩色 | する |
| **暫定**（ヒント由来） | **色もラベルも出す** | **する** |
| **確定**（AI由来） | 色もラベルも出す | 入力版が変わったときだけ |

**表示できることと、再判定が要ることを分ける。** 暫定は見た目の上では確定と区別しない
（ユーザーに内部状態を見せない）。

**再試行の契機は「次にそのノートを開いたとき」だけ。** 背景で回さない。
**無限再試行を避ける条件を2つ置く** — ①`FeatureStatus` が非対応を示す端末では試さない
（→ [ai_input_excerpt](../system/ai_input_excerpt.md) の skip 判定と同じ材料を使う）、
②同じ入力版で連続失敗したら、その入力版では試さない。

**キャンセルは失敗ではない。** ノート切替の `CancellationException` は**暫定にも確定にもしない** —
何も保存せず、状態も動かさない。requestId ＋ `isCurrent()` で旧要求の保存とUI更新を止める
（→ [architecture](../system/architecture.md) の並行処理の規約）。
**ここを失敗と同列にすると、ノートを速く送るだけで暫定が焼き付く。**

### 判断9: 鍵はAIへ実際に渡したものすべてを含む（レビュー P2-2）

**本文ハッシュ＋プロンプト版では足りない。** 判断6 でヒントをプロンプトへ添え、
判断7 でVault別の語彙を使うので、**本文が同じでも入力は違い得る**。

指紋に含めるもの: **本文ハッシュ／抜粋の方式と予算／実際に添えたヒント／候補集合の版（語彙のIDと定義）／
プロンプト版／機能種別**。

- **語彙の版を入れないと、リストを更新しても古い結果が出続ける。** これは
  入力指紋キャッシュで最も気づきにくい失敗の型で、**版を上げ忘れる経路を作らない**設計が要る
- **分野IDはVaultローカルなので、保存はVaultの名前空間の下に置く。**
  入れないと、別Vaultの同じIDの結果が混ざる
- **配色の設定だけを変えたときは失効させない。** 分類と色の割り当ては別の関心である

### 判断10: 索引を2つに分ける — 冊子は本文を持たない（レビュー P2-3）

**冊子から入力指紋は引けない。** 束が持つのは参照・タイトル・扉だけで、
[`BookletController`](../../../app/src/main/java/com/example/newproject/controller/BookletController.kt) は
扉のために**先頭8KBしか読まない**（→ [booklet_mode](booklet_mode.md) 判断5）。
本文ハッシュを鍵にした索引を冊子から引くには、**全文を読むか保存ストアを叩くか**しかなく、
どちらも判断2 で守った性能契約を壊す。

そこで役割を分ける。

- **索引A（ノート → 最新の分類）** … 表示が引く。**Vault走査時にメモリへ載せる**ので、
  冊子は追加I/Oなしで色を出せる。永続の鍵は `sha256Hex(相対パス)`
  （→ [reflect_reading_trace](reflect_reading_trace.md) の可搬キーと同じ形。移動・改名で失われるのも同じ）
- **索引B（入力指紋 → AI結果）** … 判定が引く。**ノートを開く経路でしか触らない**

**Vault切替で捨てるのはメモリ側だけ。** 永続を捨てると A→B→A で全部を再判定することになり、
Nano を無駄に走らせる。**「Vault単位で捨てる」は世代管理の話であって、永続の寿命ではない。**

**冊子が出すのは索引Aの現在値そのままで、鮮度を保証しない。**
外部で本文が編集されても、**そのノートを開くまで色は変わらない**。冊子で検出しに行かない。

### 判断11: 保持中の束にも色を届ける（レビュー P2-6）

**束は作ったときにしか組み立てない。** 無彩色のページから「これを読む」→ 読書中に判定が確定 →
戻る、をすると、**束は保持されているので新規作成を通らず、無彩色のまま**になる。

**索引Aを `StateFlow` として冊子画面が購読する。** 束のメンバー・並び・ページ位置・めくり量は
**一切触らない** — 更新するのは各ページが引く分類だけである。
**引く束と編む束の両方**が対象で、どちらも `ref` で引くので経路は1つで足りる。

> **束の作り直しでは解かない。** 作り直すとページ位置と並びが飛ぶ。
> これは既存の冊子で一度踏んだ型（状態を変えたのに読込の鍵が変わらず更新されない）の裏返しで、
> **鍵を変えて作り直すのではなく、purely な派生値として読む**のが正しい。

### 採らなかった案: AIなしで出す（対応表だけ）

規模が**中→小**に落ち、AI経路も保存層も要らない。**オーナーが判断4で明示的に退けた。**
再提案するなら、**「第三者のVaultでも対応表が効く」ことを示す**必要がある。

## 9. 品質要件

- **アクセシビリティ:** **1.4.1（色だけで伝えない）が要る。** 紙に分野名を添えて満たす
  （→ [ui_design_principles](../system/ui_design_principles.md) §1 の表が「ラベルか位置」と指定）。
  色は `AppColorContrastTest` の床を守る
- **性能:** 冊子を開く経路に**AI呼び出しもI/Oも増やさない**。パスは走査時に既にある
- **プライバシー:** 本文はAI段でだけ端末内 Nano へ渡る。**Vault には何も書かない**
- **端末制約:** Nano 非対応端末では**ヒントだけが働く**。**機能は劣化するが壊れない**

  > **未確認:** この縮退保証は「パスからヒントが作れる」ことを前提にしているが、
  > **その生成元を決めていない。** 判断4 の 97.2% は*中身を読んで手で作った*対応表の被覆率で、
  > 製品が自動で用意できる値ではない。**フラットなVaultや採番コードだけのフォルダ名では
  > ヒントが作れず、この保証は成立しない。**

## 10. 検証と受け入れ条件

- **JVMテスト:** パス→ヒントの生成（純関数）／6色上限と超過時の無彩色／保存の鍵（入力指紋）／
  **判定済みでなければヒントの有無によらずAI経路へ進むこと**／
  **固定リスト外・空・複数候補の応答を保存しないこと**
- **instrumentation:** > **未確認:** 要否は実装時に決める
- **受け入れ条件（レビュー由来）:**
  - 一時失敗の次の表示でAI確定へ進む／非対応端末では暫定を出し続け、無限に再試行しない
  - キャンセルされた旧ノートの結果が、新ノート・新Vaultへ保存も表示もされない
  - 本文・ヒント・語彙が同じなら再利用し、どれかが変われば再利用しない／別Vaultの同じIDが混ざらない
  - 再起動・A→B→A のあと、**冊子経路に追加I/Oなしで**既存の色が出る
  - 「未判定ページ→読む→確定→戻る」を**引く／編むの両方**で通し、ページ位置・並び・めくり量が保たれる
- **実機確認:** 冊子の紙が分野ごとに塗り分かれる／分野名が読める／明暗の両方で床を割らない。
  **AI段は実機検証用の一時Vaultで通す**（2026-09-09、オーナー）— フォルダに入っていないノートを
  数本置いた fixture を作る。**本番のVaultは触らない**（→ [共通手順](../../review/device_validation/README.md)）
- **保証していないこと:**
  - **分類の当たり外れは測らない。** 分野の正解は主観なので、プロンプト回帰再生器や機械採点になじまない。
    **実機で束を眺めて納得できるか**で判定する（→ [feature_ideas](../../_wip/feature_ideas.md) の「効果を測る道具が先に要る」型から外れると明示して進める）
  - **色の配りが偏らないことは保証しない** → §11

## 11. 既知の制約・未解決事項

- **初回は色が揃わない。** 判定はノートを開いた契機なので、**開いた本数ぶんしか色が付かない**。
  実測したVaultなら645本を開き切るまで揃わない。**一括で走らせる導線は持たない**（判断2 の理由がそのまま効く）
- **Vault別の語彙をどう作るかが未設計。** 判断7 で「一般語彙＋Vault別の追加」を選んだが、
  **追加分をどこから引くかは決まっていない。**
- **色の配りは Vault の実態に従う。** 実測したVaultは**上位3分野で82%**なので、
  10枚の束はだいたい3色が主になる。**「カテゴリごとに塗り分かれる」見え方にはならない。**
  これは実装の問題ではない
- **同じ内容のノートが別の色で2回出得る。** 実測したVaultには、同じファイル名のノートが
  別の用途のフォルダに複製されている組があった。冊子は参照で束ねるので**別のノートとして並ぶ**
- **固定リストの語彙が未確定。** 分野名と件数はオーナーの確認待ち → §5
