## 1. 概要

冊子（`ひく🎲` から開く10枚の束）の紙を、そのノートの**分野**で塗り分ける。

**出どころはオーナーの体感である。** 「冊子が真っ白になるのがなんか微妙。
カテゴリ（技術記事・AI・Python など）で色分けみたいなものはできないか」（2026-09-06）。

**色を使えるのは冊子の面だけである。** 読む面の地色は年代が持ち切っており、
チャネルの持ち主は面ごとに決まる（→ [bearing_channels](../system/bearing_channels.md) 判断6）。

## 2. ゴールと非ゴール

### ゴール
- 冊子をめくっているあいだ、**眺めるだけで束の中身の散らばりが分かる**
- **眺めて捨てる速さを削らない**（→ [booklet_mode](booklet_mode.md) 判断3）
- 分野の判定を、**読む面の栞（分野を位置と本数で示す案）が後から乗れる土台**として作る

### 非ゴール
- **読む面には載せない。** 本文の紙は年代が持つ
- **分野で絞って引かない。** Rediscover の純粋ランダムには混ぜない（別機能として扱う）
- **ユーザーに分類させない。** 設定画面で分野を手当てさせる形は採らない
- **分類の正しさを機械で測らない** → §10

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 冊子の紙の色 | 束の各ページの地色が分野ごとに変わる | 冊子を開いたとき（分野が決まっているノートだけ） |
| 分野名の表示 | 紙に分野名が小さく出る | 同上。**色以外の手がかり（1.4.1）として必須** |
| フォルダからのヒント | — （ユーザーには見えない） | ノートを走査したとき |
| AIによる判定 | — （結果が色として遅れて出る） | **ノートを開いたとき。判定済みでなければ必ず走る** |

## 4. 現在のユーザーフロー

**前提:** Vault走査の時点で、全ノートのヒントは索引Aへ**暫定**として載っている（→ §8 判断14・判断16）。
ヒントは判定ではなく候補で、**メモリにしか置かない。**

1. ノートを開く。**現在の入力版の確定があれば何もしない**（索引Aから読む）。
   **「判定済み」ではなく「現在の入力版の確定」で見る** — 本文・ヒント・語彙が変われば版が変わる
2. 無ければ索引B（入力指紋）を引く。当たれば**AIを呼ばずに確定を復元する**。
   **外れたら、そのノートの保存済みの答えは別の入力版のもの**だと決まるので、
   走査の補完材料からも外す（→ §8 判断18）
3. どちらも無ければ、**ヒントを添えてAIへ渡す**
4. 結果で分岐する。
   - **分野を1つ返した** → 確定として**索引Aへ永続**し、索引B（メモリ）にも載せる
   - **`NONE` を返した** → `確定（分野なし）`として同じように扱い、**無彩色**にする（→ §8 判断13）
   - **生成失敗・恒久非対応** → **暫定のまま**（メモリのみ）。永続はしない
   - **キャンセル**（ノート切替） → **何も書かない。**状態も動かさない（→ §8 判断8）
5. 冊子を開くと、束10枚の紙が**索引Aの現在値**で出る。未判定の紙は無彩色。
   索引が未準備なら無彩色で開き、**読み込めた時点で色が届く**（→ §8 判断11・判断17）

## 5. 機能仕様

- **前提条件:** Vault が選択済み。**Nano が使えない端末ではヒントへ縮退する**（→ §8 判断6）
- **入力と出力:** 入力は `vaultRelativePath` と（AI段では）本文の抜粋。出力は固定リストの分野1つ
- **上限:** **色は6つまで**（→ [bearing_channels](../system/bearing_channels.md) 判断3の「5〜7色」）。
  **追加語彙は親の色を継ぐので「超えた分」は出ない**（→ §8 判断13）。無彩色になるのは
  **未判定**と**`確定（分野なし）`**の2つだけ
- **状態遷移:** **未判定 → 暫定（ヒント由来）→ 確定（AI由来）** の3値（→ §8 判断8）。
  **一方向なのは同じ入力版の中だけ** — 本文・ヒント・語彙が変われば入力版が変わり、確定でも再判定する
- **保存と寿命:** **アプリ内に保存する**（Vault には書かない）。**索引は2つ**（→ §8 判断10）。
  鍵の構成と名前空間は判断9。**永続するのは索引Aの確定だけ**で、**索引Bは読み込みのたびに
  索引Aから作り直す**（確定が入力版を持つため → 判断10）。
  **アプリ再起動・Vault の A→B→A で永続側を捨てない**。
  **暫定は永続しない**（走査で作り直す → 判断14）
- **画面遷移:** 無し。既存の画面に色と分野名が増えるだけ
- **他機能との連携:** 冊子（紙の色）。将来、読む面の栞が同じ判定を使う → §8 判断5
- **エラー／AI非対応時:** **黙ってヒントへ縮退する**（暫定・メモリのみ・永続しない）。ヒントも無ければ無彩色。
  ReadingTrace と同じベストエフォート（→ [architecture](../system/architecture.md) のController比較表）
- **キャンセル時:** **何も書かない。**索引A・Bとも触らず、状態も動かさない。
  ノート切替では requestId ＋ `isCurrent()` で旧要求の保存とUI更新を止める（→ §8 判断8）

**抜粋の上限は `NoteExcerptLimits.FIELD = 600`**（2026-09-10）。要約（1200）より小さいのは、
本文全体の把握が要らないことと、**この経路が全ノートで走るので予算がそのまま待ち時間になる**ため。
**実機で測っていない** — 動かすときは `PromptTokenBudgetTest` の掃引と体感で決める。

**応答はIDで受ける**（`F1`..`F6` と `NONE`）。ラベルを返させると、AIが整えた瞬間に照合が落ちる —
AIピッカーが同じ穴を踏んでいる既知の型である。**1つに定まらなければ保存しない**（多数決も先頭優先もしない）。
**行の全体がIDであることを要求する**（2026-09-10 のレビュー P2-3）。先頭だけを見ると
`F1 / F3` や `F1 ではなく F3 が適切です` から先頭のIDを取り、**曖昧な応答と明示的に否定された分野を確定する。**

**さらに、応答全体がID行だけでできていることを要求する**（2026-09-11 のレビュー P2-2）。
行の形だけを見て**読めない行を読み飛ばすと**、`F1` の次行に `F1 ではなく F3 が適切です` が来たときに
1行目だけが残り、**否定されたほうを確定する。** 空行・箇条書き・引用符・コードフェンスは装飾として読み飛ばすが、
**「選択を無効にする内容」を装飾と同じには扱えない。**

**指紋にはタイトルも含める**（同 P2-2）。タイトルはプロンプトへ載るので入力の一部である。
落とすと**同じテンプレート本文を持つ異題ノートが同じ鍵へ畳まれ**、先に開いたほうの分類が両方へ効く。
**代償として、改名すると再判定になる** — 入力が実際に変わっているので正しい振る舞いだが、
索引Bが当たるのは「**ファイル名・本文・ヒントがすべて同じ**」ときだけになる。

**失効を見つけた時点で古い確定を落とす**（同 P2-4）。落とす先はいまのヒントの暫定で、
ヒントが無ければ未判定（無彩色）にする。**落とさないと、この後 AI が使えなかったときに古い色とラベルが残り**、
「失敗したらヒントへ縮退する」という判断8 と食い違う。**永続には触らない** —
永続の確定はその入力版での答えとして正しく、消すと入力を元へ戻したときに再利用できなくなる。

> **有効な確定のときは索引Aへ書かない。** 落として索引Bから戻すと結果は同じだが、
> 書けば画面は再描画され、**ノートを開くたびに色が一度ヒントへ点滅する。**
> 検査は「値が変わらないこと」ではなく**「書かないこと」で見る** — 値だけを見ると素通りする（実際に変異で確かめた）。

## 6. 状態とデータ

| 置き場 | 中身 | 鍵 | 寿命 |
|---|---|---|---|
| **索引A（表示用・メモリ）** | ノート → 最新の分類レコード（分野・確からしさ・入力版） | `DocumentRef` | Vault切替で捨てる。**暫定も入る** |
| **索引A（永続）** | ノート → 確定レコード | `sha256Hex(相対パス)` | 永続。**入るのは確定だけ**（暫定は走査のたびに作り直す → 判断14） |
| **復元材料** | 永続から読んだ確定の写し。**走査が索引Aを補完する材料** | `sha256Hex(相対パス)` | Vault切替で捨てる。**失効を確認したノートは外れる**（→ 判断18） |
| **索引B（再利用用・メモリ）** | 入力指紋 → 分野（null は「該当なし」） | 判断9 の指紋 | Vault切替で捨てる。**永続しない** — 読み込みのたびに永続の索引Aから作り直す（→ 判断10） |
| 連続失敗の記録 | 入力指紋 → 回数 | 入力指紋 | **アプリの起動単位**。永続しない（→ 判断8） |

- **`BookletEntry` に欄は増えない。** 索引Aをメモリ上で `DocumentRef` から引ける形にすれば、
  既にある `ref` で足りる。**`RelatedNote` も `ref` を持つので、編む束も同じ経路で引ける**（→ §8 判断11）
- **`vaultRelativePath` が要るのはヒントを作るときだけ**で、そこはノートを開く経路なので走査結果から引ける
- **索引Bは永続しない（2026-09-10、実装で決めた）。** 初版は永続＋件数上限で古い順に追い出す形だったが、
  **永続の索引Aから読み込み時に作り直せる** — 確定は入力版を持つので、
  読み込んだ時点で「入力指紋 → 分野」が揃う。**上限も追い出しも要らなくなる。**

  **代償は1つで、条件が3つ揃ったときだけ出る**（2026-09-11 のレビュー P3-1 で範囲を絞った）。
  ①本文をH1→H2と変えて確定し、**永続の索引AがH2で上書きされる**。
  ②Vault切替か再起動で**メモリの索引Bを失う**。③そのあと本文をH1へ戻す。
  このとき作り直した索引Bには**H2しか無い**ので、H1を1回生成し直す。
  **同じセッションのあいだは索引BにH1が残るので、H1→H2→H1 は生成0回**である（→ 判断18・§10）。
  初版はここを「同じセッションで元へ戻したときの取りこぼし」と**逆に書いていた。**

  > **判断の根拠だけ書いて、作り直しを実装していなかった**（2026-09-10 のレビュー P2-5）。
  > **判断を成立させる側を落とすと、判断そのものが誤りに変わる** — 索引Bを永続しないことが
  > 「移動後に再生成する」という劣化になっていた。**代替案を選んだら、その代替が働くことまでを1組で入れる。**

- **復元の入口は2つある（2026-09-10 のレビュー P2-1）。** `onVaultRestored`（起動）と
  `onVaultChanged`（明示選択）で、**読込を後者にしか置いていなかった** —
  保存が効くのはVaultを選び直した経路だけで、**通常の再起動では色が戻らなかった。**
  いまは両方が同じ `loadPersistedNoteFields()` を通る。→ [lessons](../lessons.md) L14
- **「判定中」の状態は持たない（2026-09-10）。** §6 の初版は持つ想定だったが、
  **誰も見ないものを状態にしても、落ちるテストが書けない**（→ [architecture](../system/architecture.md) の
  並行処理の規約・[lessons](../lessons.md) L11）。進捗も失敗も画面に出さない機能なので、
  同時実行は requestId ＋ Job で足りる。**ノート単位の契約へ登録するのはジョブの停止だけ**である。
- **索引Aは `NoteUiStateStore` が所有し、Vault単位のスライスとして公開する。**
  独立した可変ストアをUIへ直接公開すると、[architecture](../system/architecture.md) の
  「状態が `NoteUiState` の外に出る例外は2つだけ」に**3つ目を作る**ことになる —
  そこには「`model` を葉に保つ判断自体を見直す合図」と書いてあるので、合図を鳴らさずに済ませる。
  **ノート単位の契約2箇所には登録しない**（Vault単位なので `vaultGeneration` 側 → 判断16）

## 7. システム設計

```
Vault走査（初回とTTL失効のたび）
 └─ パス → **ヒント** → 索引Aへ**暫定**（メモリのみ）
      **確定のあるノートは上書きしない**（→ 判断16）

Vault選択・起動時（走査とは別経路 → 判断17）
 └─ **永続の索引Aだけ**を読み、そこから**索引B**と**復元材料**を作る（→ 判断10・判断18）

ノートを開く
 └─ 現在の入力版の確定がある？
      ├─ Yes → 何もしない
      └─ No  → 索引B（入力指紋）に当たる？
                ├─ Yes → AIを呼ばずに確定を復元
                └─ No  → **復元材料から外す**（保存済みの答えは別の入力版 → 判断18）
                          → **常に** Nano へ（ヒントを添えて固定リストから選ばせる）
                          ├─ 分野1つ   → 確定として**索引Aへ永続**し、索引Bへ載せる
                          ├─ `NONE`    → 確定（分野なし）として同じ扱い → 無彩色
                          ├─ 失敗・非対応 → **暫定のまま。永続しない**
                          └─ キャンセル → **何も書かない**

冊子を開く
 └─ 束10枚の `ref` で**索引Aだけ**を引く → 色
      **新しい保存ストアI/Oを足さない。**未準備なら無彩色で開き、後から色が届く（判断11・判断17）
```

**非AIで候補（ヒント）を出し、AIが選ぶ形**である。**ヒントの有無で経路が分かれないこと**が判断6 の要点で、
分かれる図に戻すと採番崩壊に効かなくなる。
（→ [feature_ideas](../../_wip/feature_ideas.md) の「非AIで候補を出し、AIは選別だけさせる」型）。

## 8. 設計判断と代替案

### 判断1: 色を載せるのは冊子の面だけ

**正本は [bearing_channels](../system/bearing_channels.md) 判断6。** ここでは結論だけ持つ —
読む面の地色は年代、冊子の面の地色は分野。**面積が味方する**（冊子の紙は画面最大の部品で、
年代の地色が [ui_design_principles](../system/ui_design_principles.md) §3 を免れたのと同じ面積帯にいる）。

### 判断2: 「冊子を開いた瞬間に10件分類する」は採らない

[booklet_mode](booklet_mode.md) 判断3 は**冊子からAI生成を全部外すことで成立**しており、
理由もそこに書かれている — Nano は Mutex 直列で1回数十秒なので、**10枚を先読みすると数分占有する**。
載せるとこの判断を正面から取り消すことになる。
**判定の契機はノートを開いたときにし、冊子は保存済みの結果を読むだけにする。**

### 判断3: 保存は「後で足す最適化」ではなく前提条件

ノートを開いた契機で走る Nano は現在**要約と ReadingTrace の2本**で、分野判定が3本目になる。
**判断6 で「AIが常に判断する」を選んだ結果、この3本目は全ノートで走る。**
保存しないと、同じノートを開き直すたびに待ち時間が伸び続ける。**保存はこの機能の前提条件である。**
したがって**入力指紋によるAI結果キャッシュ**（本文ハッシュ＋抜粋方式＋プロンプト版＋機能種別を鍵にする案）の
鍵設計を、**この経路で先に実装する**。
分野は再生成できる導出値なので、**Vault には書かず、退避・復元の対象にもしない。**

### 判断4: フォルダで足りる場合でも、AI段を作る（2026-09-09、オーナー）

**実測では、AI段が実際に働く余地はほとんど無い。** 2026-09-09 にオーナーのVault（645本）を測った。

| 方式 | 結果 |
|---|---|
| フォルダ名から自動（第2階層） | **24区分**。上位6つで75.5%どまり。区分名が採番コードで**意味を読めない** |
| 採番コードから自動（4桁） | 19区分だが、**1つのコードが60%を飲む**（読書由来のものが全部入るため） |
| **中身を読んで作った対応表** | **6分野で97.2%。AIが要るのは645本中3本** |

**それでも (B)（AI段を作る）を選んだ。** オーナーの判断と理由:

> やっぱAI活用というのがテーマになっているため、(B)でいきたいですねぇ。
> 今回はたまたま想像より構造的になっているとはいえ、第三者のノートは基本ぐちゃぐちゃなためです。
> また、俺が採番体系を崩壊させるリスクもあるための選択となります。

**この判断は上の実測に反していない。** 「3本」は**いま整っているVaultのスナップショット**であって、
設計の性質ではない。対応表の 97.2% は**一人が手で維持している規約に依存した数字**で、
規約が崩れた瞬間に落ちる。**AI段は、その落ちしろを受ける。**

**代償は正直に持つ** → §11（初回は色が揃わない・全ノートでNanoが走る）。

### 判断5: 分野の判定は、いまは本書が持つ

分類軸は**読む面の栞・放置ノートの棚卸し・関連ノートの再ランク**も欲しがる。
**いまは利用者が1つなので本書に置き、2つ目が来たら `system/` へ切り出す。**
先に横断文書を作らないのは、**利用者が1つの規約は「横断」ではない**ため。

### 判断6: フォルダは判定ではなく「ヒント」にする（2026-09-09、オーナー）

**フォルダで決まったらAIを呼ばない、という形は採らない。** AIが常に判断し、
フォルダ由来の分野は**候補としてプロンプトへ添えるだけ**にする。

**理由は判断4 と同じところから来ている。** 「フォルダ優先・AIは埋めるだけ」だと、
**対応が古くなって*間違った*分野を返すようになっても、AIは呼ばれない**（決まっているので）。
採番体系が崩れるリスクに備えるために AI 段を作ったのに、**その形では崩れたときに効かない。**

**代償:** Nano が全ノートで走る（保存があるので1本1回）。**保存が前提条件へ格上げされる** → 判断3。

**縮退はヒントへ倒す。** Nano 非対応端末・生成失敗・タイムアウトのときは、
**フォルダ由来のヒントをそのまま採る**。ここを「無彩色」にすると、
**Nano が無い端末でこの機能が丸ごと消える** — 判定の精度は落ちてよいが、機能は残す。

### 判断7: 語彙は「一般語彙＋Vault別の追加」で持つ（2026-09-09、オーナー）

固定リストを実測した6分野そのままにすると、**他人のVaultではほぼ全部が「その他」**になる。
一般語彙だけにすると、**このVaultでは7割が1つの分野に集中して分かれない**。
**両方持つ** — どのVaultでも意味を持つ土台の上に、そのVaultで多い分野を足す。

**一般語彙は判断13 が持ち、色枠もそこで固定する。** 追加語彙は色を持たずラベルだけを細かくするので、
**追加分の生成が遅れても色は出せる** — ここが規模を切り分けられる境目である。

> **未確認:** **追加分をどこから引くかは決めていない**（走査結果から作る／AIに作らせる／オーナーが書く）。
> **色に影響しないので、第一弾では一般語彙だけで出してよい。**

### 判断8: 分類は3値で持つ — 暫定を確定と区別する（レビュー P2-1）

**「未判定 / 判定済み」の2値だと、一時的なAI障害が永久に固定される。**
初回表示でモデルが未準備なら、ヒントを採って「判定済み」になり、
**AIが使えるようになってからも呼ばれない。** 判断6 の「AIで補正する」狙いがそこで死ぬ。

| 値 | 表示 | 再判定 |
|---|---|---|
| **未判定** | 無彩色 | する |
| **暫定**（ヒント由来） | **色もラベルも出す** | **する** |
| **確定**（AI由来） | 色もラベルも出す | 入力版が変わったときだけ |

**表示できることと、再判定が要ることを分ける。** 暫定は見た目の上では確定と区別しない
（ユーザーに内部状態を見せない）。

**再試行の契機は「次にそのノートを開いたとき」だけ。** 背景で回さない。
無限再試行は避けるが、**抑制には必ず解除条件を付ける** — 付けないと、
前回の「永久確定」を**「永久停止」という別の形で残す**ことになる（再レビュー P2-1）。

| 抑制 | 条件 | 解除 |
|---|---|---|
| 恒久非対応の端末では試さない | [`AiAvailability.Unsupported`](../../../app/src/main/java/com/example/newproject/ai/AiAvailabilityMapping.kt) のときだけ | 可用性が変われば自動で解ける |
| 同じ入力版で連続失敗したら止める | **生成失敗だけ**を数える | **アプリの起動単位**（永続しない）／可用性が回復したら即解除 |

**生の `FeatureStatus` で判定しない。** `featureStatusToAvailability` は
**対応端末の `UNAVAILABLE` を `TemporarilyUnavailable` へ割り当てる** — 同じKDocに
「`UNAVAILABLE` だけで恒久非対応と断定しない」と書いてある。
**instrumentation の「今回 skip する」条件を、製品の「以後試さない」条件へ流用しない**
（→ [ai_input_excerpt](../system/ai_input_excerpt.md) の skip 判定は*テスト*の規約である）。

**未準備とキャンセルは連続失敗に数えない。** `NeedsDownload` / `Downloading` は
まだ失敗していないし、キャンセルは失敗ではない（下記）。数えると、
**モデルの初回DL中にノートを数本送っただけで抑制へ入る。**

**可用性の確認は、抑制の判定より先に置く（2026-09-10、実装して分かった）。**
逆にすると、**一度抑制へ入った時点で可用性を二度と観測できず、解除条件が到達不能になる** —
「永久確定」を「永久停止」へ置き換えただけになる。**規則を書いただけでは足りず、
判定の順序がそれを実現しているかは別に確かめる必要があった**（テストで落ちて気づいた）。

> **抑制をアプリの起動単位にする代償は受け入れる。** 再起動のたびに1回は試すので、
> 端末が本当に駄目なときは毎起動1回だけ無駄が出る。**永続させると回復の契機が消える**ほうが重い。

**キャンセルは失敗ではない。** ノート切替の `CancellationException` は**暫定にも確定にもしない** —
何も保存せず、状態も動かさない。requestId ＋ `isCurrent()` で旧要求の保存とUI更新を止める
（→ [architecture](../system/architecture.md) の並行処理の規約）。
**ここを失敗と同列にすると、ノートを速く送るだけで暫定が焼き付く。**

### 判断9: 鍵はAIへ実際に渡したものすべてを含む（レビュー P2-2）

**本文ハッシュ＋プロンプト版では足りない。** 判断6 でヒントをプロンプトへ添え、
判断7 でVault別の語彙を使うので、**本文が同じでも入力は違い得る**。

指紋に含めるもの: **本文ハッシュ／抜粋の方式と予算／実際に添えたヒント／候補集合の版（語彙のIDと定義）／
プロンプト版／機能種別**。

- **語彙の版を入れないと、リストを更新しても古い結果が出続ける。** これは
  入力指紋キャッシュで最も気づきにくい失敗の型で、**版を上げ忘れる経路を作らない**設計が要る
- **分野IDはVaultローカルなので、保存はVaultの名前空間の下に置く。**
  入れないと、別Vaultの同じIDの結果が混ざる
- **配色の設定だけを変えたときは失効させない。** 分類と色の割り当ては別の関心である

### 判断10: 索引を2つに分ける — 冊子は本文を持たない（レビュー P2-3）

**冊子から入力指紋は引けない。** 束が持つのは参照・タイトル・扉だけで、
[`BookletController`](../../../app/src/main/java/com/example/newproject/controller/BookletController.kt) は
扉のために**先頭8KBしか読まない**（→ [booklet_mode](booklet_mode.md) 判断5）。
本文ハッシュを鍵にした索引を冊子から引くには、**全文を読むか保存ストアを叩くか**しかなく、
どちらも判断2 で守った性能契約を壊す。

そこで役割を分ける。

- **索引A（ノート → 最新の分類）** … 表示が引く。**Vault走査時にメモリへ載せる**ので、
  冊子は追加I/Oなしで色を出せる。永続の鍵は `sha256Hex(相対パス)`
  （→ [reflect_reading_trace](reflect_reading_trace.md) の可搬キーと同じ形。移動・改名で失われるのも同じ）
- **索引B（入力指紋 → AI結果）** … 判定が引く。**ノートを開く経路でしか触らない。**
  **メモリだけに置き、読み込みのたびに永続の索引Aから作り直す** — 確定が入力版を持つので、
  読んだ時点で「入力指紋 → 分野」が揃う。**上限も追い出しも要らない**（→ §6）

**Vault切替で捨てるのはメモリ側だけ。** 永続を捨てると A→B→A で全部を再判定することになり、
Nano を無駄に走らせる。**「Vault単位で捨てる」は世代管理の話であって、永続の寿命ではない。**

**索引Bは、移動に対するセーフティネットになる。** 索引Aの永続キーは相対パスなので、
Obsidian 側で移動すると見失う。だが**入力が同じなら索引Bは当たる**ので、
そのノートを次に開いたとき **Nano を呼ばずに索引Aを復元できる。**

> **効くのは「ファイル名・本文・ヒントがすべて同じ」ときだけである。**
> 指紋には**プロンプトへ載せるタイトル**と**実際に添えたヒント**が入っている（判断9）。
> - **改名すると当たらない**（2026-09-10 のレビュー P2-2 でタイトルを指紋へ入れた）。
>   初版は「同じフォルダ内での改名なら当たる」と書いていたが、**いまは当たらない**
> - **フォルダをまたいでヒントが変わっても当たらない。** 同じ理由である
> - **効くのは、ファイル名を変えずにヒントの変わらない移動**（どちらもヒントが出ないフォルダ間、
>   同じヒント語を持つフォルダ間）
>
> **これは欠陥ではなく正しい振る舞いである** — 入力が本当に変わっているため。
> [reflect_reading_trace](reflect_reading_trace.md) の可搬キーは失われたら終わりだが、
> **こちらは作り直せる導出値なので、自己修復の余地がある**という違いがある。

**冊子が出すのは索引Aの現在値そのままで、鮮度を保証しない。**
外部で本文が編集されても、**そのノートを開くまで色は変わらない**。冊子で検出しに行かない。
**ただし、一度開いて失効を確認した後は戻らない**（→ 判断18）。

### 判断11: 保持中の束にも色を届ける（レビュー P2-6）

**束は作ったときにしか組み立てない。** 無彩色のページから「これを読む」→ 読書中に判定が確定 →
戻る、をすると、**束は保持されているので新規作成を通らず、無彩色のまま**になる。

**索引Aを `StateFlow` として冊子画面が購読する。** 束のメンバー・並び・ページ位置・めくり量は
**一切触らない** — 更新するのは各ページが引く分類だけである。
**引く束と編む束の両方**が対象で、どちらも `ref` で引くので経路は1つで足りる。

> **束の作り直しでは解かない。** 作り直すとページ位置と並びが飛ぶ。
> これは既存の冊子で一度踏んだ型（状態を変えたのに読込の鍵が変わらず更新されない）の裏返しで、
> **鍵を変えて作り直すのではなく、purely な派生値として読む**のが正しい。

### 判断12: ヒントは一般語彙との辞書照合で作る（レビュー P2-5）

**パス→ヒントの生成元を決めていなかったため、縮退保証が根拠を失っていた。**
判断4 の 97.2% は**中身を読んで手で作った対応表**の被覆率で、製品が自動で出せる値ではない。

**フォルダ名・パスに現れる語を、一般語彙（判断13）の辞書と突き合わせる。**
当たればヒント、当たらなければ**ヒント無しでAIへ渡す**。Nano も追加I/Oも要らず、
純関数なのでJVMテストで固定できる。

**保証は条件付きへ直す。** 「Nano が無い端末でも機能は残る」のは**ヒントが作れるVaultに限る**。
採番コードだけのフォルダ名やフラットなVaultでは**ヒントが作れず、無彩色のままになる** —
これは欠陥ではなく仕様である。3例で言えることを揃えておく。

| Vault の形 | Nano なしで得られるもの |
|---|---|
| 意味のあるフォルダ名（`資格試験/`・`料理/`） | 辞書が当たり、**ヒントで色が付く** |
| 採番コードだけ（`0500_000F/`） | 当たらない。**無彩色** |
| ルート直下だけ（フラット） | 照合対象が無い。**無彩色** |

**実測したVaultは2つ目に近い。** 一般語彙で当たるのは一部だけなので、
**このVaultではAIが主役になる** — 判断4 でオーナーが選んだ形と、結果的に一致する。

### 判断13: 色は一般語彙の6つで固定し、追加語彙は親の色を継ぐ（レビュー P2-4）

**色枠を頻度で決めると、走査のたびに色の意味が入れ替わる。** 固定する。

**これは新しい規則ではなく、[bearing_channels](../system/bearing_channels.md) 判断3 の適用である** —
「2階層目は色にしない。色は大分類だけで足りる」。**Vault別の追加語彙は2階層目にあたる。**

- **色を持つのは一般語彙の6つだけ。** どのVaultでも同じ色が同じ意味を指す
- **Vault別の追加語彙は色を持たず、ラベルだけを細かくする。**色は親から継ぐ
- **どれにも当たらなければ無彩色。**「その他」に色枠を使わない

**一般語彙の案（6つ）:**

| 分野 | 含むもの |
|---|---|
| 技術・開発 | 手を動かす対象そのもの。コード・設計・環境 |
| 学習・試験 | 試験対策と、学習中の教材 |
| 仕事・ビジネス | 業務・組織・手続き |
| 創作・趣味 | 制作物、続けている関心事 |
| 暮らし・生活 | 家事・買い物・健康・予定 |
| 思考・内省 | 日記・振り返り・アイデアの断片・思索 |

**「読書・記録」は枠に入れない（2026-09-09）。** 読書は**形式であって分野ではない** —
実測したVaultでも読書由来のコードが**パスの60%**を占めており、枠にすると
**冊子の10枚がほぼ1色で埋まって「散らばりを見る」というゴールが消える**。
**定義文へ明記する** — 「本の内容であっても、技術書なら*技術・開発*、ビジネス書なら*仕事・ビジネス*を選ぶ」。

**空いた枠を「思考・内省」に充てた。** Obsidian ではデイリーノート・振り返り・
アイデアの断片が大きな塊になりやすいが、*暮らし*にも*仕事*にも入れると違和感が出る。
**実測したVaultにはほぼ無い**が、一般語彙は一つのVaultに合わせて決めない。

> **未確認:** この6語はオーナーのVault実測と一般性の両方から置いた**案**である。**確定はしていない。**

**「どれにも当たらない」は正常な結果である（再レビュー P2-3）。** 固定リストの6語に加えて、
**機械用の `NONE` を正常応答の許可集合へ入れる。** これが返ったら
**`確定（分野なし）`** として分野ありの確定とまったく同じ扱いにし（索引Aへ永続・索引Bへ載せる）、
**無彩色にして同じ入力版では再判定しない**。
分野名のラベルも出さない（色で何も伝えていないので 1.4.1 の対象外）。

**`NONE` を入れないと、正常な「該当なし」が2つの誤りのどちらかになる** —
6語から無理に選ばせるか、生成失敗として再試行し続けるか。
**空文字・未知のID・複数候補は引き続き保存しない**（それらは不正応答であって「該当なし」ではない）。
**ユーザーに見せるカテゴリは増やさない** — `NONE` は機械用の値である。

**境界は規則ではなく定義文が持つ。** 「Python の教材」は*技術・開発*と*学習・試験*のどちらにも読めるが、
**優先順位の規則で解かない** — 上の「含むもの」を語彙の定義としてプロンプトへ渡し、AIに1つ選ばせる。
**規則で解こうとすると、規則のほうがVaultごとに増えていく。**
**複数返ってきたら保存しない**（→ §10 の受け入れ条件）。

### 判断14: ヒントは走査時に一括で当てる（2026-09-09）

**「ノートを開いたときだけ判定する」と、起点の不満が最後まで解けない。**
冊子が真っ白なのを直したいのに、**開いた本数ぶんしか色が付かない**（実測Vaultなら645本）。

**ヒントの生成は辞書照合の純関数で、I/O もAI も要らない**（判断12）。
そこで**Vault走査の時点で全ノート分を計算し、索引Aへ暫定として載せる**。
数百〜千本でも走査の性能に影響しない。**3値モデルはそのまま** — 暫定で出しておき、
読書のたびにAIが確定へ昇格させる。

**暫定は永続しない。** 走査のたびに作り直せる導出値なので、**永続するのは確定だけ**にする。
索引Aの永続層が小さく保たれ、辞書や語彙を変えたときに古い暫定が残る問題も起きない。

> **効き目はVaultの形に依存する。** フォルダ名が意味を持つVaultでは初回から色が付くが、
> **実測したVaultは採番コード型なので、当たるのは一部だけ**である（→ 判断12 の3例）。
> 「導入した瞬間から色鮮やかになる」とは書かない。

### 判断15: 6色は値を選ばず、規則で作る（2026-09-09）

**手で6色を調整すると、値の妥当性を誰も検査できない。**
年代の紙は単一色相の明度差（1次元）だったが、分野は**色相のばらつき**になるので、
色ごとに背景の明るさが揃わないと、紙に載るタイトルと代表文のコントラストが色ごとにばらつく。

**OKLch で L（明度）と C（彩度）を固定し、h（色相角）だけを等間隔にずらす。**
HSL ではなく OKLch を使うのは、**HSL の L が知覚的に均一ではない**ため
（同じ L=50% でも黄は青よりはるかに明るい）。ライトとダークで L を変えた2組を作る。

**実行時に色空間の計算を持ち込まない。** 規則で作った結果の sRGB 値を表に書き、
**検査は値ではなく関係を見る**（明度が揃っていること・色相が等間隔であること）。
色の実値を書くのはその表だけにする — [note_age_paper](note_age_paper.md) と同じ扱いである。

**これはコントラストの保証ではない。** WCAG のコントラスト比は**相対輝度**から計算する値で、
OKLab の L とは別物である（相関はするが一致せず、彩度が上がるほどずれる）。
**最終判定は検査が行う**（`NoteFieldPaletteTest`）。規則が与えるのは「通る候補を最初から作れる」ことまでである。

**実装して分かったこと（2026-09-10）。** 明暗で L を共有できなかった。

| | 決めた値 | 帯を決めているもの |
|---|---|---|
| ライト | L=0.93・C=0.032（輝度 0.7941〜0.8155） | **下限だけ。**`errorText`（0xFFCC0000）が 4.5:1 を保てる 0.7527 |
| ダーク | L=0.314・C=0.042（輝度 0.0295〜0.0323） | **上下とも。**下は `panel` の 0.0280（割ると紙が背景へ沈む）、上は `errorText`（0xFFFF6B6B）の 0.0341 |

- **本文の紙の床（`panelChip` = 0.8772）を流用してはいけない。** あちらは最も弱い文字トークンまで
  載せる面の話で、**冊子の紙に載るのは `onSurface`・`onSurfaceMuted`・`errorText` の3つだけ**である。
  流用すると彩度が取れず、**L=0.965 では2色が sRGB の外へ出て潰れ、色相が最大7°ずれた。**
- **ダークの帯は幅0.006しかない。** ライトと同じ L=0.36 を使うと**6色すべてが `errorText` を割る**（実測 3.84〜3.99）。
  **「明暗で L を1つ決めれば済む」という当初の見立ては誤りだった** — 帯を決めるのは明暗で別の相手である。

> **6色が等しく見分けられるとは書かない。** 低彩度で色相を60°刻みにすると
> **青と緑のあたりが近づき**、色覚特性によっては赤と緑も近づく。
> 1.4.1 は分野名のラベルで満たしているので**破綻はしない**が、色だけで6分野を数えられる前提を置かない。

### 判断16: 索引Aへの書き込みは1箇所へ直列化し、確定を消さない（再レビュー P2-2）

**判断14 で書き手が増えたのに、合成の規則を書いていなかった。**
索引Aへ書くのは**走査（暫定）・AI（確定）・永続層の読込（確定）**の3つになった。

**走査は初回だけではない。** [`collectAllNotesCached`](../../../app/src/main/java/com/example/newproject/NoteViewModel.kt) は
`NOTES_CACHE_TTL_MS` を過ぎると走査し直すので、**判断14 の一括適用はAI確定の後にも起きる**。
規則が無いと、再走査のたびに**色がヒント側へ戻る。**

**規則は2つ。**

1. **書き込みは1箇所へ直列化する。** 索引Aを更新する経路を1つにまとめ、
   呼び出し側がそれぞれ `update` しない（→ [architecture](../system/architecture.md) 判断4 の「照合は update の直前に1箇所へ集約する」と同じ形）。
2. **確定は暫定で上書きしない。** 暫定を書けるのは**有効な確定が無いノートだけ**である。
3. **確定同士は、更新元で優先を決める。** 2 だけでは足りない —
   **古い確定が遅れて届く経路がある**（再レビュー P2-1）。

**確定同士の競合が起きる形は1つだけである。** 永続層に入力版H1の確定を持ったまま復元読込を始め、
その最中に現在の本文H2でAIが確定してメモリを更新し、**そのあとでH1の復元が届く**。
どちらも確定なので 2 では止まらず、**直列化しても後着そのものは防げない**（同一Vaultなので世代照合も効かない）。

| 更新元 | 規則 |
|---|---|
| **一括復元**（起動時・Vault選択時に永続層から読む） | **補完だけ。**有効な確定が**無い**ノートにしか書かない。**材料は失効を確認した分を外した写し**（→ 判断18） |
| **個別の確定**（AIの結果・索引Bからの復元） | **常に置き換える** |

**補完だけで足りる理由は、メモリが空から始まることにある。** 起動時とVault切替でメモリの索引Aは空になるので、
**復元の最中にそこへ確定があるなら、それは今回の個別経路が書いたもの＝必ず新しい。**
「後着かどうか」を時刻や版で判定しなくても、**更新元を見るだけで決まる。**

**ノートごとの更新番号は置かない。** 個別経路の順序は requestId ＋ `isCurrent()` が既に守っており
（判断8）、そこへ版の照合を重ねると**後から置いたほうが死ぬ**のがこのコードベースの傾向である
（→ [architecture](../system/architecture.md) の並行処理の規約・[lessons](../lessons.md) L11）。
**落ちるテストを書けるガードを1つだけ置く。**

**Vault世代を照合する。** 別Vaultの遅れて届いた走査結果を現Vaultへ合成しない
（→ [architecture](../system/architecture.md) 判断4 の `vaultGeneration`）。

**「有効な確定」は入力版で決まる。** 本文・ヒント・語彙のどれかが変われば入力版が変わり、
その確定は有効でなくなるので、暫定で置き換えてよい。**語彙版は本文を読まずに変化を検知できる**ので、
語彙を更新した直後の再走査では暫定へ戻ってよい。

### 判断17: 永続索引の読込は走査から切り離す（再レビュー P2-4）

**「索引AはVault走査時にメモリへ載っている」は、冷えた状態では成立しない。**
[`openBooklet`](../../../app/src/main/java/com/example/newproject/NoteViewModel.kt) は
`collectAllNotesCached` を呼ぶので、**再起動やVault切替の直後に冊子を開くと、そこで走査が走る**。
この走査へ永続索引の読み出しを足すと、**冊子を開く経路に保存ストアI/Oが増える。**

**読込を走査から切り離し、Vault選択時と起動時に独立して行う。**

- **未準備のまま冊子を開けるようにする。** 待たせない。**無彩色で開く**
- **読込が終わったら、判断11 の購読経路で色が届く。** 束の作り直しもAI生成も要らない —
  **仕組みは既にある**ので、新しい経路を足さずに済む
- **性能契約はこう絞る:** 「**冊子を開く経路に、新しい保存ストアI/Oを足さない**」。
  既存のVault走査I/Oはこれまでどおり走る（それは分野色が持ち込んだものではない）

**採らなかった案:** 走査に索引読込を相乗りさせ、性能契約を「描画・ページめくりで追加I/Oなし」へ緩める。
**冊子を開く速さ**（→ [booklet_mode](booklet_mode.md) 判断3）が削られるうえ、
**事前読込を選んでも完了前に冊子を開ける**ので、どのみち未準備時の挙動は要る。**なら分離するほうが単純。**

### 判断18: 「表示してよい確定」と「再利用してよい答え」を分ける（レビュー P2-1）

**降格させても、走査が元に戻していた。** 本文が変わって入力版が失効したノートを暫定へ落としても、
次のVault走査が**永続から読んだ確定をそのまま補完材料にしていた**ので、
「メモリに確定が無いノート」として同じ確定が戻る。ストアの再読込もAIの追加生成も要らずに起きる。

**根っこは、走査が入力版を照合できないことにある。** 走査は本文を読まないので、
判断16 は「入力版が有効かどうかはここでは見ない」と決めている。**見られない側で判定させない** —
判定できる側（ノートを開く経路）が、補完材料のほうを削る。

| 入れ物 | 何の正しさを持つか | 失効したらどうなるか |
|---|---|---|
| **永続（索引A）** | 「**その入力版での答え**」 | **消さない。** 消すと入力を元へ戻したときに再利用できない |
| **復元材料**（永続から読んだ写し） | 「**いまの本文に対して表示してよい確定**」 | **外す。** 走査の補完はここだけを見る |
| **索引B**（入力指紋 → 答え） | 「**同じ入力なら同じ答え**」 | 関係ない。入力が戻れば当たる |

**外す契機は「索引Bが外れたとき」。** 復元材料は読み込んだ時点で索引Bへも入れている（判断10）ので、
**索引Bが当たらない＝そのノートの保存済みの答えは別の入力版のもの**だと決まる。
ここで入力版を比べ直す検査は置かない — **落ちるテストが書けない**（→ [lessons](../lessons.md) L11）。

**代償はない。** 本文を元へ戻せば索引Bが当たり、**AIを呼ばずに確定へ戻る**。
失われるのは「開いて失効を確認したのに、走査が古い色を出す」という振る舞いだけである。
（**索引Bを失った後**に戻したときだけは生成し直すが、それは索引Bを永続しない判断の代償であって、
ここで材料を削ったこととは関係がない → §6）

> **降格単体の検査は緑だった。** 「直した状態を、別の書き手が戻す」型である
> （→ [lessons](../lessons.md#l66-直した状態を別の書き手が戻す) L66）。
> 検査も走査→降格→**再走査**まで連ねる形にした。

### 採らなかった案: AIなしで出す（対応表だけ）

規模が**中→小**に落ち、AI経路も保存層も要らない。**オーナーが判断4で明示的に退けた。**
再提案するなら、**「第三者のVaultでも対応表が効く」ことを示す**必要がある。

## 9. 品質要件

- **アクセシビリティ:** **1.4.1（色だけで伝えない）が要る。** 紙に分野名を添えて満たす
  （→ [ui_design_principles](../system/ui_design_principles.md) §1 の表が「ラベルか位置」と指定）。
  色は `AppColorContrastTest` の床を守る
- **性能:** 冊子を開く経路に**AI呼び出しもI/Oも増やさない**。パスは走査時に既にある
- **プライバシー:** 本文はAI段でだけ端末内 Nano へ渡る。**Vault には何も書かない**
- **端末制約:** Nano 非対応端末では**ヒントだけが働く**。**機能は劣化するが壊れない**

  **保証は条件付きである** — ヒントが作れるVaultに限る（→ §8 判断12 の3例）。
  フラットなVaultや採番コードだけのフォルダ名では**無彩色のままになる。**

## 10. 検証と受け入れ条件

- **JVMテスト:** パス→ヒントの生成（純関数）／**色を持つのは一般語彙6語だけで、追加語彙は親の色を継ぐ**こと／
  **無彩色になるのは未判定と `確定（分野なし）` の2つだけ**であること／保存の鍵（入力指紋）／
  **判定済みでなければヒントの有無によらずAI経路へ進むこと**／
  **固定リスト外・空・複数候補の応答を保存しないこと**
- **instrumentation:** > **未確認:** 要否は実装時に決める
- **受け入れ条件（レビュー由来）:**
  - 一時失敗の次の表示でAI確定へ進む／非対応端末では暫定を出し続け、無限に再試行しない
  - キャンセルされた旧ノートの結果が、新ノート・新Vaultへ保存も表示もされない
  - 本文・ヒント・語彙が同じなら再利用し、どれかが変われば再利用しない／別Vaultの同じIDが混ざらない
  - 再起動・A→B→A のあと、**冊子経路に追加I/Oなしで**既存の色が出る
  - 「未判定ページ→読む→確定→戻る」を**引く／編むの両方**で通し、ページ位置・並び・めくり量が保たれる
  - 一時失敗を規定回数してから解除条件が成立し、**同じ入力版を開き直すとAI確定へ進む**
  - 対応端末の `UNAVAILABLE`→`AVAILABLE` を**恒久非対応として扱わない**／抑制中の再表示とキャンセルで生成を増やさない
  - 同じ入力版で「暫定→AI確定→**再走査**」を経ても確定が残る
  - **失効を確認したノートは「降格→再走査」でも旧確定へ戻らない**／
    **同じセッションのあいだに本文を元へ戻せば生成0回で確定へ戻る**（→ 判断18）／
    **索引Bを失った後**に戻したときは生成し直す（→ §6 の代償）
  - **応答全体がID行のときだけ確定する。** 有効なID行に続く否定・併記の行があれば保存しない
  - **索引Bが当たるのはファイル名・本文・ヒントがすべて同じとき**で、改名は再判定になる（→ 判断9・判断10）
  - 「旧索引の読込開始→AI確定→旧読込完了」の順でも、**新しい確定を失わない**
    （**異なる入力版・異なる分野の確定同士**で、新しい側の分野と入力版が残る）
  - 逆順の「永続復元の完了→AI確定」では**新しい確定へ更新できる**
  - **まだ確定が無いノートには永続復元が届く**（補完は効く）
  - `NONE` も確定として同じ優先規則に従う
  - 別Vaultの遅れて届いた走査結果を、現Vaultの索引へ合成しない
  - `NONE` を保存すると**暫定の色が消えて無彩色**になり、同じ入力版ではAIを呼ばない
  - 空文字・未知のID・複数候補は保存しない（`NONE` と区別する）
  - **索引が未準備のまま冊子を開ける。**待たされず、無彩色で開き、読込完了後は
    **新しいAI生成も束の作り直しもなしに**色が届く
  - Vault走査の直後、**1本も開いていない状態で**冊子に暫定の色が出る（辞書が当たるVaultで）
  - 6色の**明度が揃っている**こと・**色相が等間隔**であることを値ではなく関係として見る（→ 判断15）
  - 6色すべてが、紙に載る文字に対して明暗の両方で 4.5:1 を満たす（`AppColorContrastTest`）
- **実機確認:** 冊子の紙が分野ごとに塗り分かれる／分野名が読める／明暗の両方で床を割らない。
  **AI段は実機検証用の一時Vaultで通す**（2026-09-09、オーナー）— フォルダに入っていないノートを
  数本置いた fixture を作る。**本番のVaultは触らない**（→ [共通手順](../../review/device_validation/README.md)）
- **保証していないこと:**
  - **分類の当たり外れは測らない。** 分野の正解は主観なので、プロンプト回帰再生器や機械採点になじまない。
    **実機で束を眺めて納得できるか**で判定する（→ [feature_ideas](../../_wip/feature_ideas.md) の「効果を測る道具が先に要る」型から外れると明示して進める）
  - **色の配りが偏らないことは保証しない** → §11

## 11. 既知の制約・未解決事項

- **初回に色が付くのは、辞書が当たるノートだけ。** 判断14 で走査時にヒントを一括適用するので
  「開いた本数ぶん」ではなくなったが、**当たらないVaultでは無彩色から始まる**（→ 判断12 の3例）。
  **AI判定を一括で走らせる導線は持たない**（判断2 の理由がそのまま効く）。
  **実測（オーナーのVault 645本、2026-09-10）では 375本（58.1%）にヒントが付く** —
  技術・開発 202／学習・試験 169／その他 4／当たらない 270。
  **初回の冊子は実質2色**になる見込みで、残りは読んだ順にAIが埋める
- **Vault別の追加語彙の生成が未設計。** 色には影響しないので第一弾を止めないが、
  **ラベルの細かさはそれまで一般語彙どまり**になる
- **一般語彙の6語は案であって確定ではない** → §8 判断13
- **色の配りは Vault の実態に従う。** 実測したVaultは技術・学習系に強く偏っており、
  10枚の束は**少数の色が主**になる見込みである。**「カテゴリごとに塗り分かれる」見え方にはならない。**
  これは実装の問題ではない。
  **旧語彙で測った「上位3分野で82%」は、判断13 で語彙を入れ替えたので当てにできない**
  （読書由来のノートが主題側の分野へ散るため）。**新語彙での分布は測り直していない**
- **同じ内容のノートが別の色で2回出得る。** 実測したVaultには、同じファイル名のノートが
  別の用途のフォルダに複製されている組があった。冊子は参照で束ねるので**別のノートとして並ぶ**
- **固定リストの語彙が未確定。** 分野名と件数はオーナーの確認待ち → §5
