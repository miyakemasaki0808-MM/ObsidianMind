## 1. 概要

ノートを開くと**自動で**、Vault 内から近いノートを選んで関連タブへ並べる。
タップするとそのノートへ切り替わる。

**「非AIで絞ってから、最後だけ Nano」**という二段構えの原型で、他の候補機能もこの型をなぞる。

## 2. ゴールと非ゴール

### ゴール
- 開いたノートから**次に読むもの**へ繋ぐ
- Vault が育つほど当たりが良くなる

### 非ゴール
- **全文検索をしない**（Nano は埋め込み検索を持たない）
- **モデルにテキストを返させない**（→ §8「モデルにはIDを返させる」）

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 決定的な関連 | wikilink 済み・採番の近いノートが並ぶ | **ノートを開いたとき**（自動） |
| 関連ノート推薦 | 関連タブにAIが選んだ候補が並ぶ | **ノートを開いたとき**（自動） |
| ノート切替 | タップでそのノートへ移る | 候補のタップ |
| 折り畳み時の左ペイン | Fold 展開時に候補を左へ出す | 展開時 |

## 4. 現在のユーザーフロー

1. ノートを開く → `fetchRelatedNotes(title, content)` が自動で走る
2. **決定的チャンネルを組む**（wikilink ＋ 採番一致）
3. **タイトルで粗く絞る**（全Vaultタイトルのスコアリング）
4. **本文シグナルで再ランクする**（二段目）
5. **最後に Nano へ渡し、IDで選ばせる**
6. 関連タブへ並べる

## 5. 機能仕様

**この節が数値の正本。** §8 は理由だけを持ち、値は書かない。

### 2つのチャンネル

| チャンネル | 中身 | 実装 |
|---|---|---|
| **決定的チャンネル** | wikilink 済み ＋ **採番の上位2桁が一致**するノート（`RELATED_NOTE_LIMIT` 件まで） | `buildDeterministicRelatedNotes` |
| **AIチャンネル** | 上記を除いた候補を Nano に選ばせた `AI_RECOMMENDATION_LIMIT` 件 | 下記の二段ランク＋Nano |

### 入力

- 現ノートのタイトルと本文。本文は**抜粋してから渡す**（上限 `NoteExcerptLimits.RELATED`）
- 候補側は タイトル ＋ 本文スニペット ＋ タグ ＋ aliases。
  **入力予算 `RELATED_CANDIDATES_BUDGET` を超えたら動的に短縮する** —
  **タグ → aliases → スニペットの順に削り、ID とタイトルは常に残す**
  （スニペットは `RELATED_MIN_SNIPPET_LEN` を下限とする）

### 一段目 — 全Vaultタイトルのスコアリング（`RelatedCandidateScoring`）

```
score = W_TITLE * titleSim(現, 候補) + W_PREFIX * prefixTier(現, 候補)
```

- `titleSim` = 採番除去・正規化したタイトルの**文字bigram Dice係数**
- `prefixTier` = 採番プレフィックスの一致段階。**どちらかに採番が無ければ 0.0**

  | 一致 | 値 |
  |---|---|
  | 上位2桁 | 1.0 |
  | 上位1桁 | 0.5 |
  | それ以外 | 0.0 |

上位 `AI_CANDIDATE_LIMIT` 件だけが次段へ進む。

### 二段目 — 本文シグナルによる再ランク（`RelatedContextScoring`）

```
score    = W_TAG * tagDice + W_BODY * snippetDice + W_TITLE_SIM * titleDice
tieBreak = titleDice
```

**件数は変えず並べ替えだけを行う。**
**タグが無い候補は本文・タイトルへ自然にフォールバックする**ので、
**タグの無いノートは再ランクが構造的に弱い**（仕様どおり）。

### パラメータ一覧

**すべて実機計測で調整する前提の初期値**（→ §8「定数は調整前提の初期値として置く」）。

| 定数 | 値 | 用途 | 定義 |
|---|---:|---|---|
| `RELATED_NOTE_LIMIT` | 5 | 決定的チャンネルの件数 | `RelatedNotesUseCase.kt` |
| `AI_RECOMMENDATION_LIMIT` | 5 | AIチャンネルの最終件数 | 〃 |
| `AI_CANDIDATE_LIMIT` | 40 | 一段目からAIへ渡す候補上限 | 〃 |
| `RELATED_SNIPPET_LEN` | 150 | 1候補あたりのスニペット最大長 | 〃 |
| `RELATED_MIN_SNIPPET_LEN` | 40 | 短縮時のスニペット下限 | 〃 |
| `RELATED_CANDIDATES_BUDGET` | 3500 | 候補ブロック全体の入力文字数予算 | 〃 |
| `CANDIDATE_CACHE_MAX_ENTRIES` | 300 | 本文キャッシュのLRU上限 | 〃 |
| `MAX_PARALLEL_READS` | 8 | SAF 同時読込数 | 〃 |
| `W_TITLE` / `W_PREFIX` | 1.0 / 0.3 | 一段目: タイトル類似 / 採番近接 | `RelatedCandidateScoring.kt` |
| `W_TAG` / `W_BODY` / `W_TITLE_SIM` | 1.0 / 0.5 / 0.5 | 二段目: タグ / 本文 / タイトル | `RelatedContextScoring.kt` |
| `NoteExcerptLimits.RELATED` | 800 | 現ノート側の抜粋上限（注意書きを含む文字数。プロンプト全体のトークン予算ではない） | `NoteExcerptLimits.kt` |

### エラー／AI非対応時

- **AI非対応・モデル未取得のどちらでも候補は出す。** `RelatedNotesResult.Success` を返し、
  `aiStatus` に `Unavailable` / `NeedsDownload` を載せてUIが注記する。
  **エラーにしない** — 非AIの二段ランクだけでも候補は成立するため
- 候補1件の本文読み取りに失敗しても、**その候補だけタイトルのみで続行**し、推薦全体を巻き添えにしない
- `CancellationException` は再throwする

## 6. 状態とデータ

**UI状態:** `RelatedNotesState`（`NoteUiState.relatedNotesState`）。

**候補本文のキャッシュ:**

| | |
|---|---|
| キー | `URI` ＋ `lastModified`（`CandidateCacheKey`） |
| 値 | スニペット・タグ・aliases（`CandidateContextData`） |
| 格納の条件 | **成功時のみ。** 失敗・キャンセルは何も残さず伝播する（→ §8「キャッシュは成功だけ保存する」） |
| 破棄 | Vault 切替で `relatedNotesUseCase.clearCache()`。LRU 上限は §5 |
| 永続化 | **しない**（プロセス内メモリのみ） |

## 7. システム設計

```
ノートを開く
 └─ RelatedNotesUseCase
      ├─ 決定的チャンネル: wikilink ＋ 採番一致           ← 非AI
      └─ AIチャンネル
           │  ① 全Vaultタイトルをスコアで全件ランク       ← 非AI・文字bigram Dice
           ▼
         上位40件
           │  ② 本文を上限付き並列で読込・キャッシュ       ← snippet / tags / aliases
           ▼
         40件＋本文
           │  ③ 現ノートの本文シグナルで再ランク           ← 非AI・並べ替えのみ
           ▼
         再ランク済み40件
           │  ④ 一時ID(C01..)を採番し、入力予算内へ整形
           ▼
          Nano
           │  ⑤ IDのみ応答 → ノートへ解決
           ▼
         関連5件
```

**設計の背骨:** 純ロジック（`android.net.Uri` 非依存・`internal`）と I/O（SAF読込・Nano生成）を分離し、
前者を JVM ユニットテストで完全にカバーする。
**並べ替え・スコア・整形・ID解決はすべて純ロジック側にある。**

## 8. 設計判断と代替案

### 背景

Obsidian Vault は数百〜のノートを持ち、多くが `0F01 タイトル` のような**16進採番プレフィックス**を持つ。
当初の関連ノートは「採番が近い（上位桁が一致する）ノート」を出すだけで、次の課題があった。

1. **採番偏重** — 「関連」が *話題が近い* ではなく *採番が近い* になっていた。話題は近いが採番の離れたノートは一切出てこない
2. **タイトルしか見ていない** — AIに候補タイトルだけを渡していたため、曖昧なタイトルの判断材料が乏しい
3. **長いノートの文脈が伝わらない** — 先頭だけを見て要約・推薦していた
4. **AI応答の解決が不安定** — モデルにタイトル文字列を返させると、言い換え・翻訳・装飾・同名衝突で解決に失敗した

**1・2・4 を Phase 1〜3（PR #27〜#29）で、3 を2026-07-27の共通抜粋基盤で解いた。**

オンデバイス（Gemini Nano / ML Kit GenAI）前提のため、
**小さいモデルの制約（出力トークン上限・入力予算）**と**SAF（別プロセス）の I/O コスト**が全設計を貫く制約になっている。

### 判断1: 「採番が近い」を主シグナルから降ろす

採番近接を捨てるのではなく、**話題類似を主・採番近接を弱い従**に置き換えた。
採番はユーザーが手で付けた分類なので情報量がゼロではないが、
**それだけを見ると「話題は近いが採番の離れたノート」に永久に辿り着けない**。

### 判断2: 決定的チャンネルとAIチャンネルを分ける

**AIには決定的枠を除外した候補だけ**を渡す。分けないと、AIの限られた枠を
「wikilink で既に見えているノート」で浪費する。
分離によってAIチャンネルを**「まだ表示していないノートの補完」に純化**でき、これが推薦の質を上げた。

### 判断3: モデルにはIDを返させる

候補に一時ID `C01..` を採番し、Nano には**IDだけ返させる**（`RelatedCandidateId.kt`）。

タイトル文字列を返させると、**言い換え・翻訳・装飾・同名衝突**で解決が壊れる。
**小さいモデルほど自由記述の返答は表記ゆれで壊れる**ため、
選択肢に番号を振って返させる設計は**解決の確実性・出力トークン・パースの頑健性すべてで有利**だった。
パース側は行頭付近のIDのみ拾い、桁落ち・大小文字を吸収する（`parseCandidateIds`）。

### 判断4: 候補は肉付けし、溢れたら決まった順に削る

タイトルだけでは曖昧な候補を判断できないので本文スニペット・タグ・aliases を足す。
ただし全部載せるとプロンプトが膨らむため、**予算超過時に何から削るかを先に決めておく**。
**ID とタイトルだけは常に残す** — この2つが欠けると候補が候補として成立せず、応答の解決も壊れるため。

### 判断5: キャッシュは成功だけ保存する

`getOrLoad` は load 成功時のみ格納し、例外（キャンセル含む）は何も残さず伝播する。
**途中結果を確定キャッシュにしない**ため、ノート切替による頻繁なキャンセルがあってもキャッシュ整合が壊れない。

### 判断6: 並列読込は「上限付き」にする

**SAF は別プロセス。** 候補40件を無制限に並列読込するとプロバイダが詰まる。
`Semaphore` で同時数を絞ると、速度を稼ぎつつ詰まりを避けられた。
順序は `awaitAll` のリスト順保証に委ね、キャンセルは `coroutineScope` で構造化する。

### 判断7: 全件はタイトルで安く、上位だけ本文で精しく

一段目で全Vaultをタイトルだけでランクし、**本文を読むのは上位40件のみ**。
本文読み込みのコストを据え置いたまま精度を上げられる。

**二段目の目的は絞り込みではなく Nano の位置バイアス対策である。**
件数を変えず並べ替えだけを行い、**プロンプト先頭に話題的に近い候補を寄せる**。

**実データでの手応え:** 二段目の適用後、`jetpackcompose` ノートの関連候補が**すべて Kotlin 系ノートで揃った**。
採番だけを見ていた頃には出てこなかった、話題的に一貫した並び。

### 判断8: 日本語の類似は「文字bigram Dice」で測る

日本語タイトルは空白で単語分割できない。形態素解析器を持ち込まず**文字2-gram集合の Dice 係数**で測ると、
**日本語・英語・ローマ字が同じ式で扱え、純ロジックのまま JVM テストできる**。追加ライブラリもゼロ。
短い文字列（タイトル・スニペット）同士の比較に特に相性が良い。

### 判断9: 採点と並べ替えを分離してから機能を足す

二段目の実装前に、ランキングを**採点戦略（`scoreOf`）を注入する汎用パイプライン（`rankByScore`）**へ
リファクタした（挙動不変の準備コミット）。
おかげで二段目は「本文シグナルの `scoreOf` を1本書いて差し替える」だけで済み、
除外・並び順・タイブレーク・上限のロジックを重複なく共有できた。
**"差し込みやすい土台"を先に作る**判断が、本体実装を最小化した。

### 判断10: 定数は調整前提の初期値として置く

重み・長さ・予算・キャッシュ件数・並列数は**関心ごとにコード1か所へ集約**し、コメントで「調整前提」と明記する。
現ノート抜粋は `NoteExcerptLimits`、候補ブロックは `RelatedNotesUseCase` に分けてあり、
**実データを見てから独立して動かせる**。

### 判断11: フォーカスセクション文脈は保留（却下ではない）

Phase 1 の当初案は「**フォーカス中セクション**を文脈にして長いノートの先頭切り出し問題を解消する」だったが、
**この案はコードに入らなかった**（2026-07-24 の実装突合で判明。Phase 1 で実際に入ったのは ID応答方式のみ）。
先頭固定の問題自体は2026-07-27に別方式で解消している —
**見出し骨格＋冒頭＋末尾**を上限内に配分する `NoteExcerpt`（上限値は §5）。

**実装する場合の論点:** 関連ノートは「ノートを開いた瞬間」に自動実行されるのに対し、
フォーカスセクションはスクロールで動く。クイズは「吹き出しから明示起動」でこの問題を回避した
（[section_ai_chat](section_ai_chat.md)）が、**自動起動の関連ノートには同じ手が使えない**。
「どの時点のセクションで推薦するか」を先に決める必要がある。

### 今後の候補（未実装）

- **フォーカスセクション文脈** — 上記の判断11。現在の全体抜粋を置き換えるか補助シグナルにするかも含め、別機能として扱う
- **全Vaultシグナルの拡張** — フォルダ近接・更新時刻近接をスコアに加算
- **重みのオンデバイス調整** — 採用/非採用のフィードバックから重みを学習
- **三段目** — 例えば採用履歴での再重み付け。現状は二段で、三段目は費用対効果を見て判断する

## 9. 品質要件

- **保証していないこと:**

  - **定数はすべて調整前提の初期値**（→ §8「定数は調整前提の初期値として置く」）
