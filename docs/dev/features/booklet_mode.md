## 1. 概要

ランダムボタンを**1回押したら10枚を用意**し、横フリックで捲る。1枚ごとにボタンへ戻らない。
**自主制作の小冊子（ZINE）を繰るような手触り**を狙う。

**起点はオーナーの実感** —「毎回ボタンを押すのが面倒」という実際の摩擦。

## 2. ゴールと非ゴール

### ゴール
- 引く行為の**摩擦**を下げる
- 「戻ってこられる」状態を作る（1枚ずつ引き直さない）

### 非ゴール
- **引きに意図を混ぜない。** 純粋ランダムは壊さない（→ §8 判断1）
- **冊子で深く作業させない。** 蒸留・クイズ・セクションチャットは載せない
- **冊子では訪問を記録せず、AIも走らせない**（→ §8 判断3）

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 冊子をひらく | 10枚の束を作り、横フリックで捲れる | ノートタブの専用ボタン |
| 扉 | 1枚ごとに**本文から選んだ代表文1行**が出る（AI不使用・即時） | ページ表示時 |
| これを読む | 通常のノート表示へ渡り、**そこで初めて**記録とAIが始まる | ページ内のボタン |
| 編む | **直前に開いていたノートの、済んだAI推薦**で束を作る。追加のAI呼び出しもI/Oも無い | 冊子の中のトグル（種があるときだけ出る） |

## 4. 現在のユーザーフロー

1. ノートタブの **📖**（主ボタンの隣の副ボタン）を押す
2. `shuffled().take(10)` で束を作る（**参照だけ**を持つ。本文は保持しない）
3. 横フリックで捲る。各ページには**扉**（代表文1行）が出る
4. 「これを読む」で通常のノート表示へ渡る
5. **ここで初めて**訪問記録・要約・関連ノートが始まる

**直前にノートを開いていた場合は、冊子の中に「引く／〈ノート名〉から編む」のトグルが出る**（→ §8 判断12）。
編む側は同じ形の紙で、束の作り方だけが違う。**引く側は純粋ランダムのまま無傷で残る。**

## 5. 機能仕様

- **束の枚数:** `min(10, 利用可能なノート数)`。**束の中では重複させない**
  （`random()` の10回呼びではなく `shuffled().take(10)` 相当）。**0件でも冊子は開き、空の束として「引けるノートがありません。」を出す**
- **束の寿命:** ノートから戻れば**同じ10枚が同じページ位置**で残る。捨てるのは**アプリ再起動とVault切替の2つだけ**で、
  「冊子をひらく」を押し直したときは作り直す（→ §8 判断6）
- **めくる向き:** **天綴じ。次へ進む操作は上スワイプ**（紙の下端を上へ送る）。`VerticalPager` の既定のまま反転させない（→ §8 判断6）。
  **「天綴じ」とだけ書かない** — 綴じの語は読み手によって逆に取れるので、**指の動きで書く**
- **10枚を使い切ったら:** 末尾に**「もう10枚引く」ページ**を置き、押して束を作り直す。**自動では継ぎ足さない**（→ §8 判断6）。
  **直前の束と同じノートが出てよい** — 束をまたぐ重複を避けると「引きに条件を足す」ことになり、§0 の一線に触れる
- **編む束:** 種は**冊子へ入る直前に開いていたノート**。中身は `relatedNotesState` の
  **AI推薦→未リンク→wikilink済み**の順で、重複を参照で畳んで `min(10, 候補数)`。
  **水増ししない**。終端は枚数だけを告げ、**「もう10枚編む」は置かない**（→ §8 判断12）
- **扉:** 本文から代表文を1つ**選ぶ**（抽出）。**生成しないので即時に出せる**。規則は §10 の受け入れ条件が持つ。
  **編む束も同じ抽出を使う**（`RelatedNote.snippet` からは作らない — 扉の作り方を2種類にしない）
- **冊子では記録しない・AIを走らせない**
- **読み出しの上限:** 扉のために本文全体を読まない。**8KBの境界読み出し**
  （[`NoteReadLimits.SNIPPET_MAX_BYTES`](../../../app/src/main/java/com/example/newproject/data/NoteRepository.kt)）を使う。
  関連ノートが最大40件を並列で読むのに使っている経路で、**冊子の扉もこれで足りる**（本文は最大1MBだが、代表文は先頭側にある）
- **エラー・境界条件:** §10 の表が持つ

## 6. 状態とデータ

**束は `BookletEntry(ref, title, coverLine)` の列**として持つ。本文は持たず、**抽出後の1行だけ**を持つ
（→ §8 判断4・判断7）。`coverLine` は現在ページと前後1ページを遅延読込し、読めたものからキャッシュする。

**束は2つある**（引く束と編む束）。それぞれが `BookletBundle`（10枚・ページ位置・世代）で、
**行き来しても両方残る**（→ §8 判断12）。

**「参照だけ」では扉が出せない。** 参照だけにすると**ページを表示するたびに本文I/Oと抽出**が要り、
めくる速度（1枚1秒未満）に間に合わない。**避けたいのは本文10枚ぶんの保持**であって、
1行のキャッシュはその制約に触れない。

**永続化しない（2026-08-30 決定）。** 束はメモリ上に持つ。

| 契機 | 束 |
|---|---|
| 「これを読む」で開いたノートから戻る | **残る**（同じ10枚・同じページ位置） |
| （ページ位置の置き場） | **束と同じ `BookletState.Open` が持つ。**画面ローカルの `rememberPagerState` に置いた版は、実機の往復でページ位置だけ失われた（2026-08-31） |
| 「冊子をひらく」を押し直す | **両方作り直す**（ボタンは常に「引く」意思表示。種もここで取り直す） |
| 「もう10枚引く」を押す | **引く束だけ作り直す。編む束と種は動かさない**（→ §8 判断12） |
| 引く⇄編むを切り替える | **どちらも残る。**ページ位置も束ごとに別々に残る |
| 冊子から開いたノートで**別タブを押す** | 捨てる（**冊子ルートごと畳まれる** → §8 判断8） |
| アプリ再起動 | 捨てる（**プロセス復元で冊子ルートだけ戻ったらノートタブへ戻す** → §10） |
| Vault切替 | 捨てる（既存の `vaultGeneration` の考え方に合う） |

**戻り先として残るのはノートから戻る経路であって、ボタンではない。** 導出は §8 判断6。

## 7. システム設計

```
ノートタブ
 ├─ [1枚ひらく]      → 通常表示（要約・痕跡・履歴をここで開始）
 └─ [📖 冊子をひらく] → 冊子ルート（非タブ・AI/痕跡/履歴は動かさない）
                          ├─ [引く／〈種〉から編む] トグル（種があるときだけ）
                          └─ これを読む → 通常表示（ここで初めて開始）
```

**入口はボタン、実体は独立ルート** — ⛶全画面と同じ形（→ [note_fullscreen](note_fullscreen.md)）。

**期待するバックスタック:**

```
note → booklet → note（冊子から開いたもの）
```

**「これを読む」で `navigateToTab` を使わない**（→ §8 判断8）。冊子ルートを畳んでしまい、
決めた「戻れば同じ10枚」が成立しなくなる。

## 8. 設計判断と代替案

> 以下は確定済みの判断をそのまま保存したもの。**節番号は本文の12節体系とは独立。**

### 背景

ランダムボタンは1回押して1枚。次を見るにはボタンへ戻る必要があり、**摩擦が読書の前に立っている**。
1回押したら10枚を用意し、横フリックで捲れるようにする。**自主制作の小冊子（ZINE）を繰る手触り**を狙う。

※「ZINN のようなイメージ」との発言を **ZINE（小冊子）** と解釈している。別の対象を指していたら差し替える。

### 判断1: 純粋ランダムは壊れない。ただし北極星には中立でない

現在の実装は [`NoteViewModel.loadRandomNote`](../../../app/src/main/java/com/example/newproject/NoteViewModel.kt) の
`notes.random()` 1回で、**10回引くことと1回引くことに偏りの差は無い**。引きに条件を足すわけではないので、
`feature_ideas` §0 の「引きに意図を混ぜない」という一線には触れない。**変わるのは引く回数ではなく、引く行為の摩擦だけ。**

**ただし正直な懸念がある。** ホーム画面ウィジェットを非優先にした理由は「Rediscover→Reflect のループを短絡させる」だった。
**めくるコストが下がると、気に入らないノートを次々飛ばす使い方を誘発しうる**ので、同じ軸に乗っている。
ウィジェットと違うのは**アプリの中に留まる**点で、短絡の度合いは小さい。
**「10枚は捲るためではなく、戻ってこられるようにするため」**と位置づけられるかが分かれ目
→ **2026-08-30、この位置づけを採ることで決着した（判断6）。**

### 判断2: 入口はボタン、実体は独立ルート（タブは増やさない）

検討は4案を経ている。**結論は「タブは増やさない。ただしモードフラグにもしない」。**

| 案 | ナビが増えない | 回転・Foldで維持 | 「記録しない」が構造で保証 | 枠（バー/レール）が消える | モードを覚えなくてよい |
|---|:--:|:--:|:--:|:--:|:--:|
| ① 冊子タブを足す（6タブ目） | ✗ | ○ | ○ | ✗ | ○ |
| ② ノートタブ内のモードフラグ | ○ | **✗** | **✗（ガード頼み）** | ✗ | **✗** |
| ③ トグルで入る独立ルート | ○ | ○ | ○ | ○ | **△（トグル状態が残る）** |
| **④ ボタンで入る独立ルート** | **○** | **○** | **○** | **○** | **○** |

**採用は④。** ③との違いは入口だけで、**事前にモードを設定させず、押したボタンで行き先が決まる**。
③のトグルは「今どちらのモードか」を覚えさせるが、④は覚える対象が無く誤操作も減る。
**「記録しない」「AIを走らせない」が構造で保証される**という③の利点は、行き先が独立ルートである限り④でも残る。

```
[ 1枚ひらく ]  [ 📖 冊子をひらく ]

ノート画面
 ├─ 1枚ひらく   → 通常表示（要約・ReadingTrace・履歴をここで開始）
 └─ 冊子をひらく → 10枚の冊子（AI・痕跡・履歴は動かさない）
                    └─ これを読む → 通常表示（ここで初めて開始）
```

**②を捨てる根拠は、このプロジェクトが既に一度通った道であること。**
全画面表示がまさに「ノートタブから入るもう1つの見せ方」で、[note_fullscreen](note_fullscreen.md) 判断1 が
**「`isFullscreen` の `remember` フラグと違い、ルートは NavController の復元対象になるため、Fold開閉による
Activity再生成でも全画面が維持される」**として、オーバーレイ＋フラグ方式から独立ルートへ移行済みである。
冊子をフラグで持つと**折りたたみ開閉や回転で冊子モードが解除され、ページ位置ごと失われる。**

**独立ルートには冊子固有の利得もある。** 同じ判断1に「非タブルートではバー/レールを出さない構造を持つため、
ルート化するだけで自動的に消える」とある。**ZINEは余計な枠が無いほうがよい。**

### 判断3: この方式で、難所2つが設計として消える

- **① 読書痕跡の汚れは、閾値を作らずに解ける。**
  当初は「めくって通過しただけのノートに `progressPercent = 0` の訪問が積まれる」
  「`MIN_VISITS_FOR_AI_SUMMARY = 2` なので2回通過で痕跡要約が走る」ため
  **「読んだ」の定義（滞在時間・スクロール量の閾値）が要ると考えていた。**
  冊子ルートが**訪問を一切記録しない**と決めれば、曖昧な判定を作る必要そのものが無くなる。
  記録は「これを読む」で通常のノートタブへ渡ってから始まる。
  **画面が分かれることで、"眺める" と "読む" の境界が判定ではなく遷移になる。**
- **② Nano が10回走る問題も消える。**
  [`setNoteState`](../../../app/src/main/java/com/example/newproject/controller/NoteSessionCoordinator.kt) は
  本文解析に加えて要約・関連ノートを起動し、**Nano は Mutex 直列で1回数十秒**なので、
  10枚を先読みすると数分占有する。冊子が出すのは扉（判断5）だけとし、
  **AI生成は通常のノートタブへ移ってから**にすれば、Mutexの取り合いが起きない。

**機能を絞れるのが、モードフラグ案に対する本質的な優位。** 蒸留・クイズ・セクションチャットは冊子に載せない。
ZINEは眺めるためのもので、深く作業する場所ではない。**フラグで同じ画面のまま切り替える案では、これら全部が
「冊子モードのときはどう振る舞うか」を1つずつ持つことになる。** 別ルートなら、そもそも置かなければ存在しない。

### 判断4: 状態は束（10件の参照）だけを持つ

`NoteUiState` は単一ノートを表し、契約2箇所（`cancelNoteScopedJobs()` / `withNoteScopedReset()`）も
**ノート切替＝旧状態を捨てる**前提で組まれている（→ [architecture](../system/architecture.md)）。

**ページャは束（10件の参照）だけを持ち、10件ぶんの状態を並列に持たない。**
冊子は扉しか出さないので、そもそも重い状態を必要としないのが有利。
通常のノートタブへ渡すときに初めて既存の入口（`setNoteState`）を1回通す。

**本文は最大1MBまで許容している**ので、10枚を本文ごと保持しない。参照と表示中の数枚だけ。

### 判断5: 要約は「扉」と「要約」の2役に分ける

現在の要約が冊子に合わないのは1点ではなく**3点で、しかも別々の理由**である。

| 合わないもの | 現状 | 冊子での要求 |
|---|---|---|
| **場所** | [`SummaryPanel`](../../../app/src/main/java/com/example/newproject/ui/screen/AiTab.kt) は **AiTab にしか無い** | めくっている最中はタブへ行かない。**ページの上に無いと存在しないのと同じ** |
| **時間** | Nano生成で数十秒・Mutex直列 | めくる速度は1枚1秒未満。**待てない** |
| **分量** | 2〜4文 | 捲りながら見るのは1行 |

**根は1つ。現在の要約は「止まって読む」ための唯一の設計で、冊子は「めくりながら見る」という新しい瞬間を作る。**
そこに置くものが無い。→ **解き方は「速い要約を作る」ではなく、役割を2つに分けること。**

- **扉（めくる瞬間・1行・待たない）:** 生成では原理的に成立しない。**本文から代表文を1つ選ぶ**（抽出）なら
  Nano を使わずに即時で出せる。`feature_ideas` §0 の「選ぶAIを徐々に強化」にも合い、
  **AI結果キャッシュすら要らない**のが利点。AIを使う案（キャッシュ済み要約の1行目を使う）はそのキャッシュが前提になり、初回は空になる。
- **要約（止まって読む・2〜4文）:** 現状のまま AiTab でよい。**変えない。**

> **注意: これで「要約らしきもの」が3つになる。** 扉・要約・再会カードの俯瞰要約（痕跡要約）。
> **3つは入力も瞬間も違う**（本文／本文／訪問履歴）ので、**同じ「要約」という語で呼ばないところから始める**。
> 名前が同じだと必ずどれかが吸収されて消える。

### 判断6: 位置づけは「戻ってこられるように」。束の寿命と使い切り後はそこから導いた

**2026-08-30、判断1が残した一点にオーナーが答えた。** 採ったのは
**「10枚は捲るためではなく、戻ってこられるようにするため」**で、飛ばす使い方を誘発しない側へ倒す。
**この一点が3つの仕様を決めている。**

| 決めごと | 決定 | 位置づけからの導出 |
|---|---|---|
| 束の寿命 | 戻れば同じ10枚・同じページ位置。再起動とVault切替で捨てる | 「戻ってこられる」が目的なので**戻り先が消えては意味がない**。一方で永続化まですると冊子が常設物になり、"引く"体験から離れる |
| 使い切った後 | 末尾に「もう10枚引く」ページ。自動で継ぎ足さない | 無限に継ぎ足すと**手が止まる箇所が無くなり**、次々飛ばす使い方そのものになる。明示の1タップが歯止め |
| めくる向き | **天綴じ**（`VerticalPager` 既定のまま。2026-09-04 に左綴じ横から差し替え） | **この1件だけは位置づけと独立。** 当初は Android の横スワイプ慣習に揃えたが、**実機で「送り」にしか感じられなかった**（→ 判断10）。綴じを天に置くと**回転軸が紙の上端に決まり**、判断9の束の縁（右下へ覗く）と衝突しない |

**歯止めは「もう10枚引く」の1タップだけである。** 冊子の中に他の制動（枚数制限・時間・警告）は置かない。
置いた瞬間に「読み方を正す」側の機能になり、催促ガジェットを避けた方針の裏返しになる。

### 判断7: 冊子は `NoteSectionModel` を要求しない。共有するのは純関数だけ

**当初の決めごと①（「新しい面は自分で解析せず `NoteSectionController` の共有モデルを受け取る」）は誤りだった。**
2つの理由で成立しない。

1. **構造として持てない。** [`NoteSectionController`](../../../app/src/main/java/com/example/newproject/controller/NoteSectionController.kt) は
   `parseJob` 1本と `model` 1つで、`parse()` は必ず走行中の解析を捨てる。
   **Pagerの現在ページと隣接ページを同時に扱えない。**
2. **そもそも要らない。** 判断3で冊子は扉しか出さないと決めたので、**本文のブロック解析を必要としない。**
   決めごと①は「3面目も本文を描く」前提で書かれていた。

**したがって共有するのは状態ではなく純関数。** 代表文を選ぶ関数を `domain` に置き、
冊子専用の軽量Controllerが呼ぶ。**将来ページに本文そのものを描くなら、その時点で3面目の問題として再検討する** —
2面の重複が長文で2回パースするバグを生んだ事実（2026-07-31 の F-1）は変わらない。

> **記法除去とフェンス除去は [`ReunionCandidateScanner`](../../../app/src/main/java/com/example/newproject/domain/ReunionCandidateScanner.kt) が
> 同じ問題を既に解いている**（再会カードの候補文抽出）。frontmatter除去・未閉じフェンス・記法落とし・文末判定・長さ範囲。
> **共有するのはその純関数まで**で、選定規則そのものは冊子側に別で持つ（用途が違えば選び方も違う → 相似形は共通化しない）。

### 判断8: 「これを読む」はタブ遷移ではなくルートを積む

[`navigateToTab`](../../../app/src/main/java/com/example/newproject/ui/AppScaffold.kt) は
`popUpTo(graph.startDestinationId) { saveState = true }` で、NavHost の startDestination は `"note"`。
**冊子から呼ぶと冊子ルートが必ず畳まれる**ので、判断6で決めた「戻れば同じ10枚」が成立しない。

| 操作 | 決定 |
|---|---|
| 「これを読む」 | `navigate("note")` で**積む**。`navigateToTab` は使わない |
| システムバック | 読んでいるノート → 冊子（同じページ位置） → 元のノートタブ |
| 冊子の中で別タブ | **起こらない。** 冊子は非タブルートなのでバー／レールが出ない（判断2の利得） |
| 冊子から開いたノートで別タブ | 冊子ルートごと畳まれ、束も捨てる（→ §6） |

**冊子へ入っても、入る前に走っていた旧ノートのAIは畳まない。** 冊子は⛶全画面と同じ「別ルートへ移るだけ」で、
戻れば同じノートが残っている。**新しいノートを開いた時点で既存の `onNoteChanged()` が畳む**ので、
冊子側に専用の停止処理は要らない。

**契約はこう書く — 「冊子候補について新しいAI・痕跡・履歴を開始しない」。**
「冊子ではAIを走らせない」だと、入る前から走っている処理まで止める意味に読めてしまう。

### 判断9: 紙面は「束の一番上の1枚」の形にする（2026-09-01）

**実機検証中のオーナーの体感が起点。** 「画面が白くて寂しい」に続けて
「ZINEと普通のノートを視覚的に区別させたい」。**後者が診断で、前者は症状である。**
寂しく見えるのは装飾が足りないからではなく、冊子の面が**通常表示の“中身が薄い版”**になっているため。

**したがって足すのは情報量ではない。** 本文の抜粋を増やすのは冊子を小さなリーダーにする方向で、
判断3が明確に否定している。足すのは**「この面は眺める場所だ」と静止画で言い切る形**である。

**主役の軸は「面の形」に決めた**（候補は字組み・動き・面の形の3つ。判定は
[bearing_channels](../system/bearing_channels.md) 判断1 が正本）。冊子に割り当てられたのはこのチャネルだけで、
**地色は年代が持ち切る**ので流用しない。

| 要素 | 決定 | なぜ |
|---|---|---|
| 紙の角 | 12dp → **2dp**（通常表示は 8dp のまま） | 断ち切った紙とUIカードを形だけで分ける |
| 紙の面 | `Panel` のまま**変更しない** | 地色チャネルは年代が持つ |
| 紙の大きさ | 四辺の余白を広げ、**下に地を残す**（画面を満たさない） | 「続く面」ではなく「手に持った1枚」にする |
| 束の縁 | 背後に**最大2枚**。ライトは沈む＝暗い面、ダークも沈む＝暗い面 | 明暗で値をコピーしない（→ [ui_design_principles](../system/ui_design_principles.md) §2） |
| 縁の意味 | **「この紙は束の1枚である」だけ。** 束の10枚には**位置によらず同じ縁**が出る | 最後の1枚で縁が消えると、残数を形で数え始めたことになる |
| 残り枚数 | **どこにも出さない**（2026-09-06 にページ表示を外した）。**数を言うのは終端の「ここまでの N 枚でした。」だけ** | 形は面の役割を運ぶチャネルで、残数を兼ねさせると割り当てが崩れる。**冊子は選ぶ前の前動作なので、途中で数えさせない** |

> **2026-09-06、下部のページ表示（「5 / 10」）を外した**（オーナー判断。「正直いらない」）。
> **冊子は選ぶ前の前動作**であって眺めて捨てる場なので、途中で数えさせない
> （色を載せないのと同じ理由 → [bearing_channels](../system/bearing_channels.md) §9）。
> **数は終端で1回だけ言う。** 読み上げの位置案内は残した（→ §9）。
> 紙はページ表示のぶんだけ下へ伸びるので、**静止時の絵はそこだけ変わる。**

**束の縁は装飾ではなく、機能の定義そのもの。** 冊子とは「10枚の束」で、現状の画面は
**そのうち9枚を一切見せていない。** 増やしているのは本文の情報量ではなく、
**すでに状態が持っている事実の見え方**である。

**「別の本」までは振らない。** グラデーション地とヘッダを落とすと別アプリに見えるが、
判断3で「眺めると読むの境界を**判定ではなく遷移**にした」以上、遷移そのものは滑らかであってほしい。
別アプリに見える面から「これを読む」で飛ぶと、境界が段差として体験される。

**通常表示は1ピクセルも触らない。** 撤回するときも冊子側だけで済み、
新しい色トークンを作らないので `AppColorContrastTest` に面が増えず、
年代の地色が持つ「`panelChip` が地色の下限を決める」制約にも触れない。
**この案が壊しうる既存の保証は無い。**

**モック（2026-09-01、オーナー合意済み）:** 見た目に触る変更は実装前にモックで合意する
（→ [ui_design_principles](../system/ui_design_principles.md) §4-4）。3案を並べて中の強さを採った。

**実装で決まった3つ（2026-09-01）。**

- **形は役割で引く。** 紙は「眺める面」、本文パネルは「読む面」の役割
  （[`BrowsingSheetShape`](../../../app/src/main/java/com/example/newproject/ui/theme/AppShapes.kt) /
  [`ReadingSurfaceShape`](../../../app/src/main/java/com/example/newproject/ui/theme/AppShapes.kt)）。
  **値を直に書かない** — 両方が同じ値を書いていたから区別が消えていた。
- **縁は `panelRow` 1つで足りた。** 明暗どちらでも `panel` より暗い唯一の既存の面トークンなので、
  **明暗の分岐を書かずに「沈む」を表せる**（新しい色トークンは作っていない）。
- **縁の幅は紙の余白を超えられない。** 縁は紙の右下へずれて描かれるので、
  [`STACK_EDGE_MAX`](../../../app/src/main/java/com/example/newproject/ui/screen/BookletScreen.kt) を上げるなら
  右と下の余白も一緒に上げる。**下げ忘れると隣のページに重なる。**

**「もう10枚引く」ページには縁を付けない。** 束の10枚に含まれない**別種のページ**だからで、
**「後ろに何も無いから」ではない。** 後者の理由で分けると最後の1枚も縁を失い、
**残数を形で数えることになる**（外部レビューはこの形を提案したが、上記の理由で採らなかった）。
判定の引数名も種別を指す `isBundleSheet` にしてある — 位置を指す名前にしていたことが、
レビューで食い違いとして現れた。

### 判断10: 綴じは天綴じ（上端が蝶番）

> **めくりの見せ方は判断11（折り目が斜めに走る）が持つ。** ここが持つのは
> **綴じの向き・束の縁・定位置への付け替え・遠近・速さ・積み直り・OS設定**である。
> **横送り → 天綴じの半回転 → 折り目、と4度作り替えた経緯は
> [開発日誌 2026-09](../../owner/journal/2026-09.md) が持つ。** ここには現在の形だけを書く。

**起点は、§1 が看板に掲げる「ZINEを繰る手触り」にどのチャネルも割り当たっていなかったこと**
（→ [bearing_channels](../system/bearing_channels.md) §8 で動きの行を二分して受け取った）。

#### 天綴じ — レポート用紙・リーガルパッドの綴じ方

紙は**上端を蝶番**（`SHEET_HINGE`）にする。**綴じの位置が決まると回転軸が決まり**、
向きだけを縦にしたときに残る曖昧さが2つ消える。

| 曖昧だったこと | 天綴じでどう決まるか |
|---|---|
| 紙はどこを軸に倒れるのか | **上端。** 下端が手前へ持ち上がる（積み直りのときだけ・最大22度） |
| 判断9 の束の縁（紙の右下へずらして描画）と衝突しないか | **衝突しない。** 軸が上端なので、傾いた紙が右下の縁を覆いに行かない。**判断9 で実機確認した静止時の絵を1ピクセルも変えずに済んだ**（左綴じの軸＝左端では正面衝突する） |

**やらないこと。**

- **紙を動かさない。倒すだけ。** ページャが送るために与えた変位は打ち消して定位置に置き直す
  （`sheetSlotShift`）。動かすと「倒れながら流れる」になり、綴じてある感じが消える
- **色を動かさない。** 中間のアルファを取った瞬間に、**年代が持つ地色のチャネルへ手を出すことになる**
- **演出に「これは冊子だ」と言わせない。** 面の役割は形が持ち切る。
  手触りは**意味を運ばない**ぶんだけ足せる（→ [bearing_channels](../system/bearing_channels.md) §8）
- **OSの「アニメーションを無効」設定を打ち消さない**（扱いは経路で分かれる → 下表）

#### 描画順・遠近・枠

**描画順が最大の関門である。** ページャは紙を**番号順に置く**ので、既定のままだと
**手前の紙が次の紙の下に描かれ、倒しても何も起きていないように見える。**
角度の計算がすべて正しくても絵にならない。`Modifier.zIndex` を番号の逆順で与えて解く
（ノードのzは**内側と全modifierのzの和**で決まるので、ページャの子でも効く）。

**カメラ距離は紙の高さから導く**（`CAMERA_DISTANCE_FACTOR` = 1.5）。寸法を直に書かず高さに比例させる
（端末の解像度と分割画面で高さが変わる）。

**ただし単位はピクセルではない。** Compose も `RenderNode` も KDoc には「expressed in pixels」と書いてあるが、
**渡した値の 72 倍が画素**である（`CAMERA_UNIT_PX`。画面密度には依らない）。
**`View.setCameraDistance` の実装から Compose の単位は決まらない** —
`ViewLayer` は割り算を打ち消すために渡す前に `densityDpi` を掛けており、本筋の `RenderNodeLayer` は素通しする。
**画素を数えるまで決まらない**（→ [lessons](../lessons.md) L60）。`BookletSheetPerspectiveTest` が実効距離を画素から逆算して固定し、
**遠すぎる側・近すぎる側の両方を挟む** — 遠近はエラーも警告も出さずに静かに消える。

**紙が回るのは積み直りのあいだだけである。** 角度は
[`sheetTiltDegrees`](../../../app/src/main/java/com/example/newproject/ui/screen/BookletScreen.kt) が
`restack` だけから決め、**0〜22度**（`RESTACK_TILT_DEGREES`）に収まる。
**めくり量は回転にも遠近にも効かない** — めくりは折り目の幾何で表すので角度を持たない（→ 判断11）。

**倒れると、紙は枠の外へ出ようとする。** 手前へ出た点は `d / (d - z)` 倍に広がるので、
倒れ量が増えるほど投影後の幅が伸びる。対して**紙の左右の余白は合わせて 1.05 倍ぶん**しかない。
**カメラ距離の調整では出口が無い** — 収まるまで遠ざけると「遠すぎて遠近が消える」側へ戻るだけである。

**だから、倒れ量から出した縮小を掛ける**（`sheetFitScale` = `(d - z) / d`）。
掛けると**投影後の最大幅がちょうど静止時の幅になる。**
**掛ける場所は回転より外側（紙の枠）である** — 投影された絵をそのまま縮めるので
**台形の比は1ミリも変わらず**、遠近の見え方は保ったまま大きさだけが枠に入る。
内側で縮めると紙の奥行きまで縮み、台形が浅くなって遠近が弱まる。
束の縁も同じ枠の中にあるので一緒に縮み、**積み直りの最中に紙と縁がずれない。**
**積み直りが終われば角度0・縮小率1で、判断9 の絵を1ピクセルも変えない。**

> **`d = 1.5` と半回転を組み合わせた「真横で3倍」という見積もりは、天綴じの半回転版のものである。**
> その版は 2026-09-06 に無くなったので、**現行の操作条件としては成立しない**（最大22度）。

**遠い紙は引き寄せない。** 定位置への置き直しを頭打ち（`coerceIn`）にすると、
**1.5枚離れた紙が半分だけ引き寄せられて画面の下半分へ顔を出す。**
前後1枚より遠い紙はページャが置いた場所に残し、主軸の切り抜きに任せる。

**束の縁は、持ち上げられた紙には付いていかない。** 縁は `matchParentSize()` の**不透明な面**で、
しかも**回らない**。めくられる紙に付けたままにすると、**紙が立つほどその縁が定位置に残って
次の紙を覆い、次の紙がその場に現れなくなる。**
**消えて見えることはない** — 送り始めた瞬間には下の紙が同じ位置にあって、同じ形の縁を同じ場所へ描く。
**縁は紙のものではなく束のもの**なので、これで辻褄が合う。

#### OSの「アニメーションを無効」設定は、経路で意味が違う

| 経路 | 倍率0のとき | なぜ |
|---|---|---|
| **指に追従する変化**（めくり・影） | **そのまま出る** | **時間を持たない。** 指を動かした量だけ進むので、進む時間が無い |
| **読み上げ操作での送り**（次へ／前へ） | **ページは移るが、途中の動きは省かれる** | `animateScrollToPage` が時間で進む。**送りが時間で進めば、それに追従する紙も一緒に省かれる** |
| **積み直り**（束が届いた瞬間） | **潰れて見えない**（次のフレームで終わる） | 時間で進む |

**分けているのは「誰が時間を進めるか」であって、演出の種類ではない。**
**「積み直りだけが時間で進む」と読める書き方をしない** — 読み上げ操作を数え落とす
（→ [lessons](../lessons.md#l14-横展開は最後の1本を取り残す) L14。関数名ではなく**性質**で経路を数える）。

**打ち消す側へは揃えない** — 打ち消すには倍率を上書きすることになり、
**設定を切っている利用者にだけ演出が戻る。**
契約は `BookletRestackTest` が固定する（倍率0と1の差＋こちらが倍率を上書きしていないこと）。
**読み上げ操作の側は実機ケースが持つ。**

> **前例としての含意:** **時間で進むものはOS設定に従い、指が進めるものは対象外。**

#### 速さ

**強さの上限は判断3（冊子で深く作業させない）から来る。** めくりが重いと「眺めて捨てる速さ」が失われる。

| 守る線 | 内容 |
|---|---|
| 追従 | **1:1。** 演出はずれから導出するだけで、指の位置に遅延もイージングも足さない |
| 送りの速さ | **指を離したあとのスナップだけ、時間を決めて置く**（`SHEET_SETTLE_MILLIS` = 620ms・減速して終わる）。**送り先の枚数と勢いの減衰には触らない** |
| 変位の総量 | **紙は自分の枠を出ない。** 折り返しが枠から出た分は落とす（→ 判断11）ので、縁の余白の制約（`STACK_EDGE_MAX`）に触れない |

**ばねではなく時間で走らせる。** ばねは「どれだけ残っているか」で速さが決まるので、
**少しだけ送って離したときと、半分送って離したときで、かかる時間が変わる。**
めくりは*紙をめくる動作*なので、**どこで離しても同じ速さで走り切るほうが紙らしい。**

**読み上げ操作の送りも同じ時間へ揃える**（`SHEET_SETTLE_SPEC`）。揃えないと
`animateScrollToPage` が既定のばねで走り、**途中の紙が1〜2フレームしか見えない。**
**「入力が同じなら手触りも同じ」は、時間が同じときにしか成り立たない。**

**判断3との緊張は消えていない。** 柔らかくするほど1枚あたりの待ちが増える。
**判定は実機ケース `BOOK-45` が持ち、重い側と速い側の両方を問う形にしてある。**
**退路は時間を縮めること**（`SHEET_SETTLE_MILLIS`）だけである — めくりが角度を持たないので、
「倒す角度を縮める」という退路は無い。

#### 積み直り（「もう10枚引く」）

**束の入れ替えだけは、指ではなくタップが起こす。** 軸に照らせば**出来事の行**に属するので、
ここでは**「紙が一度傾いて置き直される」以上のことをしない**（`RESTACK_TILT_DEGREES` = 22°）。
繰り切らないのは、**束が届いたのはめくったからではない**からである。
強度の設計（初回・久しぶり・痕跡ヒットで強める）は再会の演出が持つ。
**こう線を引いておけば、後から強度が載るときに上書きではなく重ね書きになる。**

**再生するのは「画面に束が出ている状態で、もう一度束が作られたとき」だけ。**
冊子を開いた最初の1回と、ノートから戻る往復では再生しない。**戻ってきたのは新しい束ではない**ので、
そこで置き直すと「引き当てた」と嘘をつくことになる。

**「`Loading` を通ったか」だけでは決められない。** 📖 は束を作り始めてから遷移するので、
**最初の束が画面より先に届くことがある** — その条件だけだと初回に再生されたりされなかったりする。
**タイミングで見え方が変わるのは、演出としては壊れている。**

**冊子ルートの出入り**（Navigation の既定フェード）には触らない。**入るのは引き当ての瞬間**であり、
手触りではなく強度の側だからである。

#### 何をJVMで見て、何を実機へ残すか

| 見るもの | どこで | なぜ |
|---|---|---|
| **置き方**（積み直りの傾き・遠い紙を引き寄せないか・束の縁の在不在） | `BookletTurnGeometryTest`（JVM・値） | **値で観測できる。** 純関数に切り出してあるので、実機任せにしない |
| **めくり**（折り目の向き・進み方・折り返しが伸び縮みしないこと） | `BookletPeelGeometryTest`（JVM・値） | 同上（→ 判断11） |
| **下端が本当に手前へ出るか**（投影された幅） | `BookletSheetPerspectiveTest`（**描画・実機**） | **値には現れない。** 符号の意味そのものは画素を数えるまで確かめられない（→ [lessons](../lessons.md) L61） |
| **枠へ収まっているか**（投影された最大幅） | 同（**描画・実機**）＋縮小率そのものは `BookletTurnGeometryTest`（JVM） | **率と配線は別の事実。** 率が正しいまま掛け忘れても、値の検査は1つも落ちない |
| **本番がその値を使っていること**（傾き・影・折り目の形・縁の在不在・定位置への付け替え） | 同（走査・**代入の形**で） | **純関数を残したまま代入だけ外す変異**は、上の2つを全部通る（→ [lessons](../lessons.md) L55） |
| **重さ・速さ・気持ちよさ** | 実機ケース `BOOK-31`〜`BOOK-50` | **時間の中にしかない。** 値を1つ取り出しても手触りにならない |
| **いつ再生するか**（積み直りの契機） | `BookletRestackTest`（JVM） | **見え方ではなく状態の話。** ここを実機任せにして一度落ちた |

**走査は「名前があること」では書かない。** `rotationX` を `0f` にして純関数を残すだけで
13件全部が緑になる状態が実際にあった。受理条件は `rotationX = …`・`alpha = if (…) …` のような
**どの層のどの代入か**まで書き、コメントと import を落としてから当てる。

**寸法は1箇所に集める**（`SHEET_HINGE`・`RESTACK_TILT_DEGREES`・`CAMERA_DISTANCE_FACTOR`・
`CAMERA_UNIT_PX`・`SHEET_SETTLE_MILLIS` ほか）。
**集めてあるのは検査の代わりではなく、次に触る人がそこだけを見れば済むようにするためである。**

### 判断11: めくりは折り目が斜めに走る

**実機で返ってきた「紙が曲がる感じが足りない」への答え。** 速さと遠近は判断10 の中で応えたが、
**曲がりだけは同じ道具で応えられない。**

**曲がるのは*紙*ではなく*めくる動作*である。** 本のページをめくるとき、紙は全体としては曲がらない —
机に置かれたまま、**角を持ち上げたところだけが折り返り、折り目が紙を斜めに横切って走る。**

> **紙全体を弓なりに曲げる版を先に作り、実装も検査も通ったうえで否定された。**
> 「カール」も「曲がる」も両方に当てはまり、**分かれ目は「どこが動かないか」（紙全体か、折り目の向こうか）**で、
> そこは普通、言葉にされない。**絵を見せて初めて決着した。** 経緯は
> [開発日誌 2026-09](../../owner/journal/2026-09.md) が持つ。

#### 折り目1本で表す

| 決めたこと | 内容 |
|---|---|
| めくり始める角 | **右下**。オーナーの体感（「右下から左上にめがけて」）そのもの |
| 折り目の向き | 対角線に直交。**右下の角から左上の角へ**走る |
| 進み方 | 送りの進み具合に比例（対角線の長さを 1 とする） |
| 折り返した紙 | **折り目を鏡にした像。** 紙は伸び縮みしないので、鏡像がそのまま「持ち上がって裏を見せている紙」になる |
| 裏の面 | **文字は載らない**（紙の面の色だけ。→ 判断10「色を動かさない」） |
| 枠から出た分 | **落とす。** 本のページなら外へはみ出すが、冊子の紙は画面の中に置かれた1枚である |

**紙は動かない。倒れもしない。** 動くのは折り目だけで、
**折り目の向こう（まだめくれていない側）は1ピクセルも動かない。**

#### 「曲がっている」ことは影が言う

折り目は幾何としては折れ線である。**カールに見えるのは、めくれた角が落とす影による。**
持ち上がりは折り目が長いほど深く（`peelLift`）、影がそれに従う。

**ただし、紙が3Dで回っている間は影を出さない**（`sheetCastsShadow`）。
Android の影は輪郭を親の空間へ変換して作るが、**遠近の入った射影変換の中ではパスの影が崩れ**、
**折り返しから離れた大きな灰色の影**が出る。材料が揃うのは次の2つが重なるときだけである。

| 材料 | いつ揃うか |
|---|---|
| 親が**遠近つきで3Dに回っている** | 積み直りの 320ms のあいだだけ |
| 子の輪郭が**多角形（`Outline.Generic`）で、影を出している** | めくっている最中だけ |

**束の縁は角丸矩形なので同じ形にならない**ので、切るのは**めくりの2層だけ**でよい。
**失うものは小さい** — 回っている間は傾きと遠近が「持ち上がっている」ことを言っており、
影はもともと*置かれている*ことを言う道具である。

> **影を切ると、切り抜きが `clip` だけで支えられる状態が生まれる。**
> Compose は影のために輪郭を要求するので、**影を切った層に `clip` が無いと切り抜きごと消える。**
> この面は `BookletSheetPerspectiveTest` の**積み直り×めくりの検査**が画素で押さえる
> （裏の `clip` を落とすとそこだけが落ちることを変異で確認済み）。

**色とアルファで曲面を描かない**（→ 判断10）。曲面のための陰影を足し始めた瞬間に、
年代が持つ地色のチャネルへ手を出すことになる。**影は「どれだけ立っているか」の既存チャネルなので、
ここに載せてよい唯一のものである。**

#### めくりは角度を持たない

紙を倒すのは**積み直りだけ**である。めくりと積み直りが同じ角度を取り合う構図は存在しない。
**半回転・真横・表裏の切り替えも無い**（いずれも天綴じの半回転版にあったもので、この版には無い）。

#### 静止時は紙の形をそのまま使う

多角形で切ると角丸が失われる。**送りが 0 のときは `BrowsingSheetShape` をそのまま返す**ので、
判断9 で実機確認した佇まいは1ピクセルも変わらない。

#### 受理の範囲（2026-09-08、オーナー判断）

**主要経路と既存テストの結果をもって受理した。全ケース合格を意味しない。**
残る実機確認範囲は**完了条件から除外**し、追加検証は行わない。

| 受理したときに見ていなかったもの | なぜ止めなかったか |
|---|---|
| **実機の本物のAI推薦が編む束の先頭に来るところ**（`BOOK-61`）。検証時は `aiNotes` が空で、束は決定的な関連ノートだけだった | 並び順は `BookletWeaveTest` が固定している。空なら空のまま出すのは設計どおり（水増ししない）で、**AI推薦が出るかどうかは関連ノートAI側の話**である |
| 新しい文言（判断12「残る代償」）の**狭幅・暗色での収まり**（`BOOK-63`） | 通常幅では1行に収まる。狭幅で2行になっても紙が縮むだけで、画面外へは出ない |
| 切替時の積み直りの**体感**（`BOOK-52`）・めくり途中の傾きの**目視**（`BOOK-67`） | 再生されること・めくり量が戻ることは値で固定済み。残るのは好みの側である |
| `BOOK-64`〜`BOOK-67` を現行APKで再実行していないこと（前回APKでの成功。dex差の原因は未確定） | 3件はJVMで変異確認済みで、実機注入でも一度通っている |

> **「未確認範囲がある」を、そのまま完了できない理由にしない。**
> 実機検証は必ず見ていない面を残すので、それを完了条件にすると**何も完了しなくなる**。
> **完了の線を引くのは検証の網羅度ではなくオーナー**である（→ [lessons L64](../lessons.md#l64-検証の限界をそのまま完了条件にしない)）。
> **未実施を成功に書き換えないこと**と、**受理して閉じること**は両立する — 上の表がその両立の形である。

**ケース表（`BOOK-01`〜`BOOK-67`）は将来の回帰確認用に残す。** 冊子に触るときはここから引く。

#### 残る代償

- **文字は折り目で切れる。** 折り返した紙の裏へ文字が回り込むことはない（裏は無地なので正しい）が、
  **表の側は折り目のところで唐突に切れる** — 実際の紙もそう見えるので、これは仕様である
- **当たり判定は折れない。** 絵だけが折り返るので、ボタンの押せる場所は元の位置にある。
  **送っている最中はドラッグ中でタップしない**ので実害は無いが、絵と入力がずれていることは事実である
- **折り返しが枠から出た分は消える。** 送りが対角線の3割を越えたあたりから削られ始める

#### 何をJVMで見て、何を実機へ残すか

| 見るもの | どこで | なぜ |
|---|---|---|
| 折り目の向き（右下の角から欠ける）・進み方・表と裏の面積が合うこと | `BookletPeelGeometryTest`（JVM・値） | **値で観測できる。** 折り返しが伸び縮みしたら、それは紙ではなくゴムである |
| **めくれた角が本当に空き、裏が現れること** | `BookletSheetPerspectiveTest`（**描画・実機**） | **形が正しくても `clip` を落とせば紙は丸ごと残る。** そこは画素でしか分からない |
| **めくった感じになるか・速さ** | 実機ケース | **時間と目の中にしかない。** 折り目の位置が正しいことと、めくったように見えることは別である |

#### 退路

**折り目の向きも進み方も定数と純関数1つずつ**で、描画の形は変わらない。
**取りやめる場合も、静止時の経路は元のまま**なので佇まいには影響しない。

### 判断12: 編む冊子 — 済んだAI推薦で2つ目の束を作る（2026-09-07）

**起点はオーナーの実感** —「完全にランダムなので、AI推薦した関連ノートも出せるようにしたい」
（2026-08-31、実機でZINEを触って）。

#### 追加のNano呼び出しゼロ・追加I/Oゼロで成立する

判断3の契約文は「**冊子候補について新しい**AI・痕跡・履歴を**開始しない**」であって、
**済んだ結果を読むことは禁じていない。** ノートを開いた時点で `relatedNotesState` は既に
`Success(relatedNotes, aiNotes)` を持っているので、編む束は**並べ替えるだけ**で作れる。

**§0 の「Rediscoverは純粋ランダム死守」には触れない。** 「編む」は*引く*行為ではないので、
引く冊子（📖）は純粋ランダムのまま無傷で残る。

#### 決めたこと

| 論点 | 決定 | なぜ |
|---|---|---|
| 入口 | **冊子ルートの中のトグル。**ノートタブにボタンを足さない | 判断2が捨てたのは「入る前のトグル」で、押す前に行き先を決めさせるため「今どちらのモードか」を覚える対象になった。**これは「中のトグル」**で、結果を見ながら切り替えるので覚える対象が無い（オーナー: ボタンまみれの回避） |
| 種 | **冊子へ入る直前に開いていたノート。**ラベルは `〈ノート名〉から編む` | 表示中ページのノートを種にすると推薦が未計算なので Nano を新規に回すことになり、判断3を破る |
| 種の寿命 | **束と同じ。**「もう10枚引く」でも取り直さない | 取り直すと、冊子の中で別のノートを読んで戻った後に**種が黙ってすり替わる** |
| 中身 | `relatedNotesState` の **AI推薦→未リンク→wikilink済み**。重複は参照で畳み、種自身は外す | `RemarkController` の候補選定と同じ並べ方。既に繋がっているノートへ「再会」しても新しくない |
| 薄いとき | **水増ししない。**`min(10, 候補数)` をそのまま出す | 後半をランダムで埋めると「関係ないノイズ」ではなく**「関係あると思って読むノイズ」**になり、何枚目で関連が切れたか分からなくなる |
| 束の数 | **2つ持ち、行き来しても両方残る。**ページ位置も束ごと | 切り替えるたび引き直すと引く側が毎回別の10枚になり、判断6の「戻ってこられる」が壊れる |
| 編む側の終端 | **枚数だけを告げる紙。「もう10枚編む」は置かない** | 編みは決定的なので押しても同じ10枚が出る。**数は出す** — 言わないと「関連が切れた」のか「まだ読み込み中」なのかが分からない |
| 扉 | **引く側と同じ抽出**（`RelatedNote.snippet` からは作らない） | 扉の作り方を2種類にすると、同じ画面で長さと選び方の違う1行が混ざる |
| 開いた直後 | **必ず引く側** | 冊子の入口は「偶然の再会」のまま |

#### トグルの3通り（オーナー判断、2026-09-07）

| 状況 | 見せ方 |
|---|---|
| 種が無い（ノートを開いていない） | **トグル自体を出さない。** 行き先が1つしか無いのに選択肢を見せない |
| 種はあるが編めない（関連ノートが走行中・0件・失敗） | **出すが押せない。**理由を1行添える。出さないと「なぜ押せないのか」が画面のどこにも無い |
| 編める | 両方押せる |

**3つの理由を1文に畳まない。** 「まだ探しています」と「見つかりませんでした」は
**待てば変わるかどうか**が違い、利用者の次の行動が変わる。

#### 位置は「ヘッダの直下・紙の上」

紙の面の中へ入れると、判断9で決めた「眺める面の形」へ操作子を足すことになり、
**区別を担うチャネル（面の形）を取り合う**。ヘッダの ✕ の隣も採らない —
閉じるボタンと並ぶと誤タップの形になり、**種のノート名を出す幅が無い**。
名前が出ないと「何から編むのか」が画面から消える。

**塗りに `ButtonPrimary` を使わない。** 紙の上の「これを読む」が主なので、
ここが同じ色を取ると主役が2つになる（→ [ui_design_principles](../system/ui_design_principles.md)）。

> **判断1（bearing_channels）が「面の形」を主役に選んだ決め手は、
> 「トグルに服を着せられるのは形だけだから」だった。実際には要らなかった** —
> トグルは紙の外にある普通の操作子で、区別のチャネルを1本も使っていない。
> **形を選んだ判断自体は残る3つの理由で立つ**が、決め手にした論拠は外れていた
> （→ [bearing_channels](../system/bearing_channels.md) §6）。

#### 切り替えでも積み直りが再生される

判断10の積み直りは「新しい束が届いた瞬間」に出る。**束が2つになったので、
その瞬間は引き直しだけではなくなった。** 引く側と編む側の紙面は同じ形なので、
**無音で入れ替わると切り替わったこと自体を見落とす。**

実装は行を増やさない — **束の世代（`bundleId`）を2つの束で通し番号にする**と、
画面から見た「表示中の束が別の値になった」が引き直しでもモード切替でも同じ形になる。
積み直りの再生（`BookletRestackRule`）もページ位置の合わせ直し（`alignPager`）も、
この1つの値で駆動される。

#### 寿命の違う2つを繋ぐ場所は1箇所だけ

**`relatedNotesState` はノート単位**（`withNoteScopedReset()` で消える）なのに、
**束はVault単位**である。観測し続ける形にすると、
**冊子から「これを読む」で渡った瞬間に編む束が消える。**

そこで `NoteSessionCoordinator.openBooklet()` が
**種と関連ノートの「その一瞬の値」をコピーして Controller へ渡す**。
Controller 側は `relatedNotesState` を知らない（`BookletStateWriter` しか持たない）ので、
**この非対称を繋げる場所が構造的に1つに絞られる。**

#### 引き直しの失敗で、もう一方の束を巻き添えにしない

**`BookletState.Failed` は「冊子そのものが作れない」ための状態**である。束が1つも無い。
引き直しの失敗をここへ流すと、**押してすらいない編む束と種とページ位置まで消え、トグルごと無くなる。**

そこで `Open.redrawError` を分けた。前の引く束はそのまま生き、終端の紙に理由と再試行が並ぶ。
**理由と再試行を同じ紙へ置く**のは、引き直しを押したのがそのページだからである。

> **代償:** 待っている間に別のページへ戻っていると、失敗しても終端へ行くまで気づかない。
> 冊子ルートは Snackbar を持たないので、**画面全体へ出す機構を足すより、
> 押した場所で受け取るほうを採った。**

#### `Loading` を挟まないなら、扉は自分で起こす

引き直しで `Loading` を挟むのをやめた（編む束が一瞬消えるため）が、**そのぶん画面が動かなくなった。**
画面側の扉読込Effectの鍵は**現在ページと枚数**で、位置合わせの鍵は**束の世代**である。
引き直しの前後で**ページ番号も枚数も同じ**だと、位置合わせは同じ位置なので動かず、
読込Effectはどちらの鍵も変わらない。**誰も扉を要求しないまま先頭が読み込み中で止まる。**

以前これが起きなかったのは、**引き直しが必ず終端（＝最後のページ）から押されていた**からで、
新しい束の先頭へ移る過程でページ番号が必ず変わっていた。**旧束を表示したまま待てるようにした**ことで、
待ち中に先頭へ戻れるようになり、条件が成立した。

**Controller が引き直しの完了で `ensureCovers` を起こす**（`setMode` と同じ理由・同じ形）。

#### ページ番号は位置の一部でしかない

`alignPager` はページ番号が一致すると何もしていなかった。**めくり途中の紙は
同じ `currentPage` のまま `currentPageOffsetFraction` を持ち、指を離した後の送りも走っている。**
そのため**同じページ番号のまま束を切り替えると、新しい束が前の束のめくり量を引き継ぐ**。
送りが続けば、新しい束の保存ページまで動く。

**引き直しでは露呈しなかった** — 終端から先頭へ移るので番号が必ず変わる。
**任意の時点で押せるモード切替**で初めて成立した。
束が変わったら**番号が同じでも必ず位置を付け直す**（呼び出し元は `LaunchedEffect(bundleId)` だけなので、
要求が起きるのは束が変わったときに限られる）。

> **3件に共通する形:** どれも**「引き直しは必ず終端から始まる」という暗黙の前提**に寄りかかっていた。
> モード切替を足したことで、その前提が成り立たない時点が生まれた。
> **新しい操作を足すときは、既存の状態遷移が“いつ起きるか”に依存していないかを見る**
> → [lessons L63](../lessons.md#l63-新しい入口はいつ起きるかの前提を壊す)。

#### 残る代償

- **ノートを開いた直後に📖を押すと編めない。** 関連ノートAIはノートを開くと自動で走り、
  Nanoは直列・最大60秒なので、押した瞬間が `Loading` のことがある。
  そのときトグルは押せないままで、**その冊子では編めない**
  （冊子を出て📖を押し直せば編める。引く束は作り直されるが、引く側は純粋ランダムなので失うものが無い）。

  **2026-09-08、オーナー判断で「文言を足して現状維持」に決着した。** 実機では
  意図的に最速（0.6秒後・0.8秒後）で押した2試行とも踏んだが、**日常の発生率ではない**。
  採った手当ては1つだけ —
  「関連ノートをまだ探しています。**冊子を開き直すと編めます。**」と、次の行動まで書く。
  **「探しています」だけだと、待てば編めると読める**（種は押した一瞬のコピーなので、
  開いたまま待っても変わらない）。

  **後から拾い直す形は採らない。** 観測を続けることになり、上の非対称をまた開く。
  **この判断は再検討しない** — 引き金があるとすれば「開き直しても編めない」という報告で、
  それは別の不具合である。
- **編む束は決定的なので、同じ種では何度開いても同じ10枚**である。飽きの逃げ場が無い

### 着手時の決めごと（4〜6は決定済み）

1. **冊子は `NoteSectionModel` を要求しない（→ 判断7で訂正済み）。** 参考として当初の懸念を残す —
   現在は `NoteReaderTab` と `FullscreenNoteScreen` の2面で、
   **この重複は実際にバグを生んでいる** — 2026-07-31 の F-1 で、両方が自前の `remember` で同じ本文を解析し、
   長文で2回パースしていた（→ [architecture](../system/architecture.md)）。当時の対処で `NoteSectionController` が
   解析結果を配る形になったので、**3面目は同じ共有モデルを受け取る。** ここを外すと同じ轍になる。
2. **冊子から通常表示への遷移を最初に作る。** 「これを読む」でノート画面へ送り、そこで初めて訪問記録と
   AI生成が始まる。**この1本の遷移が判断3の前提**なので、後から足す形にすると冊子側に記録判定が生えてくる。
3. **スクロール位置の継承＋書き戻しは要らない（取り下げ）。** 全画面からの写しだったが、
   **冊子ページには本文の `LazyColumn` が無い**ので共有する `LazyListState` が存在しない。冊子が持つのはPager位置だけ。
   ただし**「これを読む」は本文先頭から開く**ことを受け入れ条件に入れる（→ §10）——
   `noteListState` は Activity 生存の `rememberLazyListState()` で、**ノート切替でリセットする処理がどこにも無い**ため、
   放っておくと前のノートのスクロール位置を引き継ぐ。
4. **束の寿命は決定済み（→ 判断6・§6の表）。** 戻れば同じ10枚、捨てるのは再起動とVault切替だけ。
   Vault切替で捨てるのは既存の `vaultGeneration` の考え方に合う（→ [architecture](../system/architecture.md)）。
5. **めくる向きは天綴じで決定（→ 判断6。2026-09-04 に左綴じ横から差し替え）。**
   発案時の「右フリックで捲る」は**右綴じ（和書）の向き**で、当初は `HorizontalPager` の既定のまま
   左綴じを採った。実機で繰る手触りが出ず、**綴じを天へ移して縦にした**（→ 判断10）。
   `VerticalPager` の既定（上スワイプで次へ）が「下端を上へ持ち上げる」手の動きと一致するので、
   **ここでも既定を反転させない**。
6. **10枚を使い切った後は「もう10枚引く」ページで決定（→ 判断6）。** 自動では継ぎ足さない。

### ボタンを2つ並べるときの既知の落とし穴

配色の3役ルール（ピンク=主／緑=補助／Indigo=AI生成系）には
**「同色ボタンが並ぶと区別できない」という実機フィードバック由来の但し書き**が付いており、
識別性をルールの純粋さより優先すると決めてある（`AppColors.kt` のコメント）。
「1枚ひらく」と「冊子をひらく」は**どちらも主操作なので、素直に作ると両方ピンクで横に並ぶ** — 指摘された形そのもの。

→ **同格2つにせず「主＋副」へ落とす**（冊子側を📖アイコン付きの小さいボタンにする等）。

現在のボタン行は `weight(1f)` で、**初回セットアップ時だけ「Vaultを選択」も並ぶ**
（[NoteReaderTab](../../../app/src/main/java/com/example/newproject/ui/screen/NoteReaderTab.kt)）。
そこへ足すと**セットアップ中は48dpのボタンが3つ**になるので、その状態を実機で見る。
なお現在のラベルは「**別のノートをひらく**」なので、この案は改名を伴う。

ボトムナビは5つのままで下部ナビ帯にも触らないが、**ノートタブの操作はもう1つ増える**
（現在は ランダム・⛶全画面）ので、そこの混み具合は実機で見る。

### その他

- **束の中に同じノートが重複しないようにする**（`random()` の10回呼びではなく `shuffled().take(10)` 相当）。
- **補記メモの混入は心配ない。** ランダム経路は
  [`ANNOTATION_FOLDER_NAME` / `READING_TRACE_FOLDER_NAME` を除外済み](../../../app/src/main/java/com/example/newproject/data/NoteRepository.kt)。
- **入力指紋によるAI結果キャッシュとは相性がよい。** 冊子から通常タブへ行き来すると同じノートを何度も開くため。
  一方 **Nano実行の優先度キューは、冊子でAIを走らせない設計にすれば必要性が下がる。**

**規模感:** 中。ページャ自体は小さいが、**判断4（束だけを持つ）と判断5（扉の追加）が本体**で、いずれも既存の中核に触る。

## 9. 品質要件

- **性能:** 10枚を本文ごと保持しない。持つのは参照と抽出後の1行だけ。読み出しは8KB境界（→ §5）
- **アクセシビリティ:**
  - ボタンが2つ並ぶので、**同格にせず「主＋副」へ落とす**（→ §8 の落とし穴）
  - **ページ位置を読み上げる**（「3/10ページ」・終端は「最後のページ」）。**画面には出さない**が
    （2026-09-06 にページ表示を外した）、スワイプでしか位置が分からない画面なので、
    **見た目を外すことと、位置を伝えないことは別**である。ページャの `stateDescription` が持つ
  - **次へ・前へをセマンティック操作として持たせる**（`semantics` のカスタムアクション）。
    スワイプだけに頼ると、スイッチアクセスや読み上げ操作でめくれない
  - **読書ボタンはどのノートを開くかを名乗る**（「〈ノート名〉を読む」）。
    全ページが「これを読む」だと、めくっても読み上げでは区別が付かない。
    **ページャは隣のページも同時に持つので、同名のボタンが実際に複数存在する** —
    表示中の1件を選べずに往復テストが止まったのもこれだった（2026-08-31）

**扉（代表文）の受け入れ条件。** ここが冊子の印象をほぼ決めるので、実装前に固定する。

| 条件 | 内容 |
|---|---|
| 除外 | frontmatter・コードフェンスの中・見出し行・リンクだけの行・表の区切り。**フェンスは開始記号の種類・長さ・閉じ行の後ろが空白であることまで見る**（4本の中の3本行や `` ```` not-close `` を閉じと読まない。字下げは3空白まで） |
| 表示 | Markdown記法を落とした文字列（`**` `[[ ]]` `` ` `` などを画面へ出さない） |
| 決定性 | **同じ本文からは必ず同じ文を選ぶ**（乱数・時刻・訪問回数を選定に混ぜない） |
| 長さ | **全角40字まで。**超えたら末尾を `…` で切る（1枚1秒未満でめくる速度に合わせる） |
| 候補なし | **ノートのタイトルを出す**（必ず存在し、空ページを作らない） |
| 純関数 | `domain` に置き、JVMテストで固定する（→ §8 判断7） |

**境界条件。**

| 場合 | 決定 |
|---|---|
| ノート0件 | **冊子は開き、空の束として「引けるノートがありません。」を出す。**戻る操作で閉じられる |
| （0件の扱いを変えた理由） | 当初は「冊子へ入らない」としていたが、**入るかどうかを状態から決めると遷移が効果の中に入り**、二重に積む・戻れないといった経路が生まれる。空の束を1枚見せて戻れるほうが構造が単純で、画面の説明も自明になる |
| ノート1〜9件 | `min(10, 利用可能数)` で束を作る。**終端の文言も実際の枚数を出す**（「10枚」と決め打たない） |
| 束を作った後にファイルが削除・改名された | **そのページだけエラー表示。**束は作り直さない |
| 代表文の読込だけ失敗した | **そのページだけエラー表示。**他のページは読める。**「開けなかった」と「中身が空」を分ける**（空はタイトルを出す） |
| 冊子を開いたまま背面へ回って戻る | 読書時間は**再開しない**。停止理由は「アプリ背面」と「冊子」を別に数える |
| 停止中（背面・冊子）に読込が終わってセッションができた | **その時点からは計測しない。**停止理由が全部消えた時点を最初の読書区間の開始にする |
| Vault切替中に遅延結果が届いた | `vaultGeneration` で捨てる（→ [architecture](../system/architecture.md) 判断4） |
| プロセス復元で冊子ルートだけ戻った | 束が無いので**ノートタブへ戻す** |
| 「これを読む」から戻る | **同じページが開く。**ページ位置は束が持ち、引き直し・Vault切替・プロセス復元では束ごと消える |
| 「これを読む」でノートを開く | **本文先頭から開く**（`noteListState` を明示的に戻す → §8 決めごと3） |

**固定するテスト:** 代表文の選定（除外・決定性・長さ・フォールバック）はJVMで固定済み。
束の寿命とスタック（→ §8 判断8）は実NavHostの往復テストが持つ。

> **ページャを操作するテストは、表示中の要素を一意に選べる形にしてから書く。**
> 隣のページも同時に composed されるので、**同じラベルのボタンが実際に複数存在する**。
> 冊子では読書ボタンにノート名を名乗らせて解いた（→ §9）。位置で選ぶ（先頭を取る）形にはしない。
