# 再会カードに何を出すか

**状態:** Draft — 設計確定・実装未着手。**枠の規則と優先順位まで決めてある**
**最終検証:** 2026-08-21 / `4b0c3d7`（現行の再会カード・`ReadingTrace` スキーマ v5・生成契機と突合。**新規実装は無いので未確認節あり**）
**関連コード:** `ui/component/ReadingTraceCard.kt` / `model/ReadingTrace.kt` / `controller/ReadingTraceController.kt`
**関連テスト:** `ReadingTraceCardTest`（既存の見出し1文）。**本書の規則に対応するテストはまだ無い**
**正本:** この文書（**枠の規則・優先順位・種別**）。痕跡そのものは [reflect_reading_trace](reflect_reading_trace.md)

**対象領域:** Rediscover で再会したときにカードへ出す1件の選び方

## 1. 概要

再会カードは「前回のあなた」を1枚で伝える。見出しの1文（いつ・どこで止まったか）は行動データから
純関数で作られ、その下に**AIが用意した1件**が付く。この枠に出したい候補が4つに増えたので、
**何を出すか・どれを優先するかを本書が決める。**

**枠を取り合うのは4件。** 俯瞰要約（実装済み）・当時の問い・古い前提・「まだ考えたい」。
1件ずつ足すと奪い合いになるので、候補資料（[feature_ideas](../../_wip/feature_ideas.md)）は
**「枠を取り合う4件を先にまとめて決めてから着手する」**ことを着手条件にしていた。
**本書がその判断にあたる。**

## 2. ゴールと非ゴール

### ゴール

- 再会カードに出す1件を、**決定的な規則**で選ぶ（同じ痕跡と同じ本文なら同じものが出る）
- ユーザーが「これはまだ考えたい」と言えるようにし、**次の再会でそれを最優先で見せる**
- **Nano 生成はノートあたり1回のまま**維持する

### 非ゴール

- **Rediscover の引きに手を入れない。** 印を付けたノートが引かれやすくなることはしない
  （偶然が Rediscover の心臓であり、印は「引いた後」にだけ効く）
- **併存表示（2件同時）はしない。** カードは1文で伝える役目を持つ
- **真偽の判定はしない。** 古い前提は「確認したいかもしれない」までで、正誤は言わない
- 本文への書き込み。**本文を書き換えるのは蒸留の太字化だけ**という原則を崩さない

## 3. 詳細機能一覧

| 詳細機能 | ユーザーから見える挙動 | 起動条件 |
|---|---|---|
| 当時の問い | 「前回のあなたはこの問いで止まっていました」＋本文の疑問文 | 本文に疑問文候補があり、AIが未解決と選んだ |
| 古い前提 | 「今も有効か確認したい箇所があります」＋該当の記述 | 疑問文候補が無く、陳腐化候補があり、AIが選んだ |
| 俯瞰要約 | 現行どおり読み方のまとめ | 上2つのどちらも成立しない |
| まだ考えたい | 「前回『まだ考えたい』と印を付けています」＋**そのとき出ていた内容** | 前回の再会でボタンを押した |

## 4. 現在のユーザーフロー

1. Rediscover で同じノートを引き当て、再会カードが出る
2. 見出しの1文（いつ・どこで止まったか）が必ず出る
3. その下に、上表の優先順位で選ばれた**1件だけ**が出る
4. ユーザーは「まだ考えたい」を押せる。押した時点の枠の内容が印と一緒に保存される
5. 次に同じノートを引き当てると、印の内容が最優先で再掲される
6. もう一度押すと印は外れる。**「読んだ」では外れない**（閉じる操作と取り消しは別）

## 5. 機能仕様

- **前提条件:** Rediscover 経路であること（→ [reflect_reading_trace](reflect_reading_trace.md)）。
  生成は現行の `needsAiSummary` をそのまま使う（2回目の訪問以降・訪問数が変わったら作り直す）
- **入力と出力:** 入力は本文と非AI段が集めた候補、出力は**種別＋1件の文**
- **上限:** 既存の AI 要約と同じバイト上限。候補は種別ごとに最大10件までAIへ渡す
- **状態遷移:** 未生成 → 生成中 → 生成済み（種別つき）／空振り（種別 `Overview` として記録）
- **保存と寿命:** 痕跡サイドカー。ノートを消せば孤児掃除で消える
- **画面遷移:** 無し。カード内で完結する
- **他機能との連携:** 「前回の返事を見る」（ひとこと）と同じボタン列に並ぶ
- **エラー／AI非対応／キャンセル時:** 現行どおり**枠ごと出さない**。見出しの1文だけで意味が通る

### 優先順位は非AI段で決まる

**AIに順位を決めさせない。** 候補の列挙は正規表現で足りるので、**どの種別で生成するかは
AIを呼ぶ前に確定する**（**列挙は規則、選別だけがAI**という分け方は、このアプリのAI機能に共通する）。これで生成は常に1回で済み、判定は純関数としてJVMで固定できる。

| 順 | 種別 | 成立条件 |
|---|---|---|
| 1 | まだ考えたい | 印がある（**生成を伴わない。保存済みの内容を再掲するだけ**） |
| 2 | 当時の問い | 疑問文候補がある |
| 3 | 古い前提 | 疑問文候補が無く、陳腐化候補がある |
| 4 | 俯瞰要約 | どちらも無い |

**AIの仕事は選別だけ。** 「？で終わる文」「西暦・バージョン風の文字列・通貨記号を含む文」の列挙は
規則で行い、**その中から本当に未解決か／本当に古びる種類かを選ばせる**。

### 候補の列挙は原文全体へ当てる

AI へ渡す本文は抜粋なので、長文では**切り落とされた区間の問いが届かない**（候補資料が挙げていた懸念）。
候補の列挙は正規表現なので**原文全体に当てられる**ので、候補リストは抜粋の外からも拾い、
抜粋とは別に渡す。**「抜粋に無いものは選べない」という制約を、列挙側で外す。**

**列挙は入力サイズに比例するので `Dispatchers.Default` へ逃がす**（→ [lessons L13](../lessons.md)）。
純関数であることは軽いことを意味しない。

### 空振りの扱い

候補があってもAIが「どれも該当しない」と返すことがある。このとき**その回は枠を出さず、
種別 `Overview` を記録する。** 次の生成契機（訪問数が変わったとき）に俯瞰要約が作られる。

**同じ契機の中で2回目を呼ばない。** Nano は Mutex 直列なので、落とし直すと待ち時間が倍になり、
「1回だけ」という本書の前提が崩れる。**空振りを記録する**ので、同じ種別で何度も試すこともない。

## 6. 状態とデータ

**スキーマは v5 → v6。** 痕跡の正本は [reflect_reading_trace](reflect_reading_trace.md) §6 なので、
**欄の登録はあちらが持つ。** ここには意味だけを書く。

| 欄 | 意味 |
|---|---|
| `aiSummaryKind` | 現在の `aiSummary` が**どの種別か**。`Question` / `Staleness` / `Overview` |
| `markedAtEpochMillis` | 「まだ考えたい」を押した時刻。null なら印なし |
| `markedSummary` / `markedKind` | 印を付けた時点で出ていた内容と種別。**再掲はこれを読む** |

**種別欄を持つのが要点。** 文字列だけだと、同じ枠に別種のものが出たときに
**表示側が条件分岐できず、検査もできない**。前置きの文言を種別から決めることで、
「同じ場所に違うものが出て見分けが付かない」を構造的に防ぐ。

**印は内容ごと保存する。** 「まだ考えたい」は*その内容*への意図なので、次の再会で
生成し直すと**別の文が出て意図とずれる**。保存済みを再掲すれば生成もゼロで済む。

**契約2箇所への登録は不要。** 再会カードの状態はノート単位だが、既存の痕跡読み込みに載っており、
新しい実行中ジョブも新しいUI状態も増やさない（→ [architecture](../system/architecture.md)）。

## 7. システム設計

```
Rediscover でノートを引く
 └─ ReadingTraceController
      ├─ 痕跡を読む（印があれば、この時点で再掲が確定＝生成しない）
      ├─ ReunionCandidateScanner（純関数・Dispatchers.Default）
      │    ├─ 疑問文候補
      │    └─ 陳腐化候補
      ├─ 種別を決める（純関数）
      └─ AiClient で1回だけ選別 → 種別つきで痕跡へ保存
           └─ ReadingTraceCard（種別で前置きを変える）
```

## 8. 設計判断と代替案

### 判断1: 排他1枠にする（併存させない）

併存させると `ReadingTrace` の拡張に加えて **Nano 生成がノートあたり2回**になり、
Mutex 直列なので待ち時間が倍になる。カードも重くなり「1文で伝える」役目が壊れる。
**枠は1つのまま、種別で見分ける。**

### 判断2: 種別を欄として持つ（文言だけで見分けない）

生成文の書き出しだけで種別を伝える案は、変更が最小で済む。採らないのは、
**種別が文字列の中にしか無いと表示側が分岐できず、検査も書けない**ため。
このリポジトリで規則が守られたのは検査に載せたときだけ、という実績がある（→ [L29](../lessons/L29.md)）。

### 判断3: 問いを古い前提より先に出す

Rediscover の本体は「古いノートとの再会」なので陳腐化を先に出す案もある。採らないのは、
**狙いが思考の連続性**であり、「前回の自分の問い」のほうが近いため。
古い前提を先に出すと、再会が**確認作業**の色を帯びる。

### 判断4: 印は表示順にだけ効かせる（引きの確率を変えない）

「まだ考えたい」を Rediscover の重み付けに使う案は、意図が直接叶う。採らないのは、
**偶然が Rediscover の心臓**だからで、印で引きを歪めるとコア価値と正面からぶつかる。
**引きは偶然のまま、引いた後に前回の自分を重ねる** — ReadingTrace と同じ解き方に揃える。

### 判断5: 意図の入口は再会カードのボタンだけにする

読書中に「ここは考え続けたい」と印を付けられるほうが精度は高い。採らないのは、
**読書中の操作を増やすと「意識させない」原則と正面からぶつかる**ため。
旧 TimeCapsule が見送られたのはまさにこの理由だった（→ [reflect_reading_trace](reflect_reading_trace.md) の
「採らなかった案 — TimeCapsule」）。**作成は無意識のまま、意図だけを再会の瞬間に宿す。**

## 9. 品質要件

- **オンデバイス完結。** 追加のネットワークは無い
- **待ち時間を増やさない。** 生成はノートあたり1回のまま
- **カードの高さを増やさない。** 出るのは常に1件

## 10. 検証と受け入れ条件

- **JVMテスト:** 候補の列挙（疑問文・陳腐化）・種別の決定・印がある場合の再掲・空振りの記録。
  **いずれも純関数なので、実装と同時に書ける**
- **instrumentation:** 種別ごとの前置きがカードに出ること
- **実機確認:** 印を付けて次の再会で再掲されること。生成が1回に収まっていること
- **保証していないこと:**
  - **選ばれた問い・記述の妥当性**は測らない（機械的な受け入れ条件に落ちない）
  - **問いも陳腐化候補も無いノートでは俯瞰要約に倒れる**ので、新機能は何も見えない
  - 印の内容は保存時点のもので、**その後に本文が編集されても追随しない**

> **未確認:** 疑問文候補・陳腐化候補が実際のVaultでどのくらいの割合で出るかは測っていない。
> **`docs/` を代理コーパスに非AI段だけを回せば着手前に測れる**（→ [L42](../lessons/L42.md)）。
> ここが極端に少なければ、優先順位ではなく候補の作り方から見直す。
