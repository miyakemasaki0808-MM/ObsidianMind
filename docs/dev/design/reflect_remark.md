**対象領域:** 読んでいるノートに対してAIが1文だけ返す機能。生成内容・保存先・起動契機・撤去範囲
**初版:** 2026-08-09
**関連:** [reflect_reading_trace](reflect_reading_trace.md)（保存先）・[ai_input_excerpt](ai_input_excerpt.md)（入力予算）・[background_ai_ux](background_ai_ux.md)（通知層。**本設計で対象が消える**）・[architecture](architecture.md)
**状態:** **実装済み・実機確認済み**（2026-08-09。5巡）。1巡目は §8、2巡目（言語バグと返事）は §9、3巡目（返事を失う経路・1往復で閉じる・Rediscover連携）は §10、4巡目（長文の扱い）は §11、5巡目（リンクと問いの排他）は §11.8。**5巡で確認完了・クローズ**。

## 0. なぜ作り直すのか — 原因は「出力枠の配分」だった

出発点は**「補記の評価内容がわかりにくい」というオーナーの実感**である。
2026-08-05 にコードを当てて6件へ分解したが（うち補記は3件）、
2026-08-09 に git 履歴まで遡って**3件が1本の因果でつながっている**ことが分かった。

**補記の出力枠は 256 トークン固定である。** `genai-prompt` 1.0.0-beta2 の
`maxOutputTokens` は上限も既定値も 256 で（[dependency_policy](dependency_policy.md) §5）、
超えると `AiTruncatedException` で**生成ごと失敗する**。つまり出力はゼロサムになる。

その枠の中で、補記は次の配分になっていた。

| | 中身 | 性質 |
|---|---|---|
| 約 1/4 | 分類ラベル4行（種別・粒度・状態・補記方針） | **固定費**。選択肢が決まっているので長さが読める |
| 残り | 補記すべき内容 3行 | **可変費**。長さを調節できる |

**2026-07-20（`f5ec7be`）の途切れ対策が、可変費だけを削った。**
「3〜5項目」→3項目固定、「なぜその欠落が理解に効くか」の括弧書き→削除、
「Keep each bullet short」「Keep the entire output compact」→追加。
**分類ラベル4行は1文字も触られていない**（`git log -S"粒度評価"` で確認。
2026-05-31 の実装コミット以降、変更ゼロ）。

削る対象を**価値ではなく削りやすさで選んでいた。** そして削られた括弧書きこそが、
「一般論ではない」を担保していた唯一の要素だった。理由を書かせない指示に変わった時点で、
出力は構造上ラベル貼りへ近づく。

**入力側でも同じ非対称が起きていた。** プロンプトは
「この note に実際に出てくる用語を参照せよ」という指示を先頭に置きながら、
指示と本文の間へ**出力に一切使われない3ブロック**（関連ノート・AI推薦ノート・既存wikilink）を挟んでいる。
しかも `wikilinkTitles` は本文中の全wikilinkで**件数無制限**なので、
**リンクが多いノートほど本文が相対的に埋もれる**。

**そして、劣化を検出する仕組みが無かった。** `hasAnnotationBody` は
`REQUIRED_SECTIONS.any { }` なので「粒度評価だけ埋まって本命が空」でも保存が通り、
固定選択肢の照合もゼロだった。蒸留が `validIds` で照合しているのと非対称である。

**構造的な原因は、補記だけ設計書が無かったこと。** 蒸留・読書痕跡・セクションチャット・
関連ノート・ピッカー・抜粋にはそれぞれ設計書があるが、補記には無かった。
[background_ai_ux](background_ai_ux.md) が持つのは通知層（Snackbar・バッジ・`isViewed`）だけで、
**「補記が何を出すべきか」を書いた文書が存在しなかった。**
だから 2026-07-20 の削減が「何を守るべきか」と突き合わされないまま通り、2か月以上そのまま残った。
**本文書はその穴を埋めるために起こしたものである。**

## 1. 判断1: 1件の「ひとこと」に振り切る（分類は全廃）

**枠を分割しないことが、この設計の中心である。** 256トークンをすべて1文へ集中させる。

```markdown
### AIからのひとこと
「読書は著者との対話である」という考えは、著者の主張に反対するときにも成り立つだろうか？
```

```markdown
### AIからのひとこと
[[問いを立てる技術]]とつなげると、「対話」を具体的にどう始めるかまで考えられそうです。
```

**画面上はどちらも同じ「ひとこと」で、種別（問い／関連ノート）は見せない。**

**検討した3案:**

| 案 | 枠の使い方 | 却下理由 |
|---|---|---|
| 3セクション構造（診断1軸＋問い2件＋接続1件） | 4分割 | 分類の自己矛盾は解けるが、**1件あたりの長さは今と大差ない**。§0 の原因がそのまま残る |
| 内部は構造・画面は1文 | 4分割 | **構造化した時点で枠は割れる**ので「1文が濃くなる」効果は得られない。表示の問題だけを解く案 |
| **1件のひとことへ振り切る** | 集中 | 採用 |

**分類ラベルを全廃する根拠は「行動が決まらないから」ではなく「枠を食うから」。**
種別・粒度が読み手の次の行動を変えていないのは確かだが、
それだけなら「読みにくいラベル」で済んだ。**実害は、それが価値のある側の枠を先取りしていたこと。**

### 1.1 文体 — 「不足」「必要」「べき」を使わない

**採点して宿題を渡す感触を避ける。** ノートを診断するのではなく、考えを開く方向へ寄せる。

| 避ける | 置き換え |
|---|---|
| 具体例を追記すべきです | どんな場面が具体例になりそうだろう？ |
| 根拠が不足しています | この考えの根拠になった経験は何だろう？ |
| 関連ノートを追加してください | `[[〇〇]]` と並べると、別の見方ができそうです |
| 主張を明確にしてください | ここで最も言いたいことを一文にすると？ |

### 1.2 出力仕様

- 1回につき**1件**
- 原則1文、最大2文。80〜120文字程度
- **ノート固有の言葉を必ず含める**（一般論の禁止はこの1点で担保する）。
  **リンク提案でも免除しない** — §8.1 の経緯を参照
- 要約・評価・称賛・前置き・追記の命令を禁止
- **問いと関連ノート接続を無理に両方出さない。** 有益なほうを1つだけ

**「補記不要です」は出さない。** 診断結果を見せない設計なので、
「不要」という診断だけ見せるのは矛盾する。空振りの扱いは §5。

## 2. 判断2: 保存先は読書痕跡サイドカー（schema v3）

**1文のために `.md` ファイルを作るのは釣り合わない。** 現在の補記は
ヘッダ・`Source:`・`Created:`・`Generated by:` を持つ独立ファイルだが、
中身が80〜120字になるならファイルの体裁のほうが本文より長い。

保存先は `_ReadingTraces/*.json` へ移す。

**この選択の根拠は3つ。**

1. **§0 の「Vault書き込みはサイドカーに逃がす」に沿う。** 本文を触らないのは両案とも同じだが、
   `.md` ファイルを作るのは Obsidian から見て「ノートが1本増える」ことであり、サイドカーとは性格が違う。
2. **`aiSummary` と同じ場所・同じ寿命になる。** 再会カードで「前回のひとこと」として出せる。
   保存・検証・バイト上限・スキーマ版管理の基盤が既にある（[reflect_reading_trace](reflect_reading_trace.md)）。
3. **痕跡と一緒に運べる。** 退避・復元（`feature_ideas` N-11）を作るとき、対象が1系統で済む。

### 2.1 保存はメモリ経由で `flush` へ相乗りさせる（**設計の要**）

**素直に「生成できたら保存する」と書くと、初回のノートで必ず失われる。**

痕跡ファイルは**離脱時（`flush`）か背面化時（`pause`）にしか書かれない**。
一方 `validateReadingTrace` は `visits.isNotEmpty()` を要求する。
したがって**まだ一度も離脱していないノートには痕跡ファイルが存在しない**。
`persistSummary` はこの状況で `?: return@withLock` と黙って諦めるが、
俯瞰要約は2回目以降の訪問でしか走らないので実害が出ていなかっただけである。

**ひとことは明示ボタンなので、初回の閲覧中に押される。** 同じ書き方をすると、
**生成は成功したのに何も残らない**（しかも黙って）。

検討した3案:

| 案 | 問題 |
|---|---|
| 生成成功時に訪問を1件書いて痕跡を作る | **「読んだ」の定義が汚れる。** ボタンを押しただけで訪問が積まれ、到達率0%の訪問が痕跡へ混ざる |
| 痕跡が無ければ保存しない（俯瞰要約と同じ諦め方） | 初回のノートでは**常に**失われる。ひとことは初読で押される機能なので、これは仕様の破綻 |
| **メモリに持ち、`flush` / `pause` の書き込みへ相乗りさせる** | 採用 |

**採用案が正しい理由:** `flush` は既に `writeMutex` で直列化され、read-modify-write を守っている。
そこへ1欄足すだけで、**「1回の閲覧＝1訪問」を壊さずに**痕跡ができた瞬間へ載る。
ノート切替で捨てられるのは正しい挙動（そのノートの痕跡は結局作られない）。

### 2.2 1ノート1件になる（**仕様変更**）

現在の補記は生成のたびに別ファイルを作るので、同じノートに何本でも溜まる。
サイドカーは `vaultRelativePath` が主キーなので、**新しいひとことは古いものを上書きする。**

**これは意図した変更である。** 1文の履歴を溜めても読み返す導線が無く、
溜めるなら痕跡の `visits` と同じく件数上限・古いものの破棄を設計することになり、
「1文を軽く出す」という判断1と釣り合わない。

### 2.3 既存の `_Annotations/` は移行しない

既存の補記ファイルはユーザーのVaultにある `.md` なので、**そのまま残す。**
アプリからは見えなくなるが、Obsidian では通常のノートとして読める。
**アプリが作ったものをアプリが消すのは、不可逆な削除にあたるため行わない**
（→ 発見と削除を分ける方針は `feature_ideas` A-4 と同じ線引き）。

## 3. 判断3: 起動は明示ボタンのまま

**自動化しない。** Nano は `generateMutex` で直列化され1回数十秒かかる（`AICoreClient`）。
ノートを開いた時点で走らせると、要約・関連ノート・痕跡要約と待ち行列を取り合い、
**開くたびの占有が1本増える。**

- 入力指紋キャッシュ（`feature_ideas` P-1）はまだ無いので、同じノートを開き直すたびに再生成になる
- 優先度キュー（同 P-2）も無いので、自動生成が先に入るとユーザー操作が後ろで待つ

**「ひとこと」は待って読むものではなくなるが、待たされないことのほうが効く。**
自動化を検討するなら P-1 が前提で、そのときは「再会時だけ」も選択肢になる
（ただし再会カードの枠は A-6・A-7 と競合する → §7）。

## 4. 判断4: 名前を「ノートへのひとこと」にする

**「補記」は完成文章の生成を期待させる。** 出力が1文になるなら名前が嘘になる。
「思考のきっかけ」「別の見方」「AIからの問い」も検討したが、
**問いとリンク提案の両方を包めるのは「ひとこと」だけ**だったので採る。

画面上の見出しは `### AIからのひとこと`。
UI文言・状態型名・ドキュメントを一斉に置換する。

## 5. 判断5: 空振りは「何も出さない」

**有益な返答が無ければ表示しない。** `補記不要です` に相当する出力は作らない（§1.2）。

ただし**押したのに何も起きないのは故障に見える**ので、UI側の固定文で受ける。

```
今は新しい問いは見つかりませんでした
```

**これはAIに生成させない。** 生成させると空振りの判定までモデルに委ねることになり、
「空振りだと宣言する文」に枠を使うことになる。**固定文なら枠を1トークンも使わない。**

## 6. 判断6: 出力の検証を入れる（ANNOT-3 の置き換え）

`hasAnnotationBody` の `any` は**そのまま作り直す**。1文になるので必須セクションの概念自体が消える。

**検証は3点。**

1. **空・極端に短い／長い応答を弾く。** 文字数範囲で機械的に判定する
2. **ノート固有の語を含むか。** 既存の [`textBigrams`](../../../app/src/main/java/com/example/newproject/domain/RelatedCandidateScoring.kt) で本文との重なりを測れる。
   一般論の禁止（§1.2）を**指示ではなく検査で担保する**
3. **`[[...]]` を出す場合は、渡した集合の中のノート名だけを許す**

**3 はID契約をそのまま持ち込む。** 存在しないノート名を書かせないために、
候補は「ID | タイトル」で提示してIDを返させ、`validIds` と照合する
（蒸留の `parseDistillResponseIds`・関連ノートの `parseCandidateIds` と同じ方式）。
**この方式が有効なことは同じファイルのコメントに書かれており**、
ピッカーだけが契約から外れている（AI-4）。**ひとことを新しく外れた3経路目にしない。**

検証は純関数へ置き、JVMテストを同時に書く。

## 7. 決まってしまう帰結と、未決事項

### 7.1 撤去されるもの

判断2で保存先が変わるため、**「Vaultに補記ファイルを作る」前提の機械が全部役目を終える。**

| 撤去対象 | 理由 |
|---|---|
| `AnnotationFileWriter`・`createAnnotationFile`（Repository / VaultBrowser 両方） | 書き出す側がいなくなる |
| `SavedAnnotation`・`SafAnnotationDocumentGateway`・`sanitizeAnnotationFileTitle` | 作成経路の部品 |
| `AnnotationComposer`（Markdown組み立て・空セクション補完・日時整形） | 保存形式が JSON の1欄になる |
| `AnnotationResultScreen`（補記結果の専用画面）と `annotation` ルート | 1文なので画面を跨ぐ理由が無い |

**一覧・削除は残す（2026-08-09・実装時に §7.1 の初期案から変えた）。**
当初は `AnnotationManagerScreen` も撤去対象に数えていたが、
**§2.3 で既存の `_AI補記/*.md` を消さないと決めているので、撤去すると
ファイルだけがVaultに取り残される。** アプリから片付けられなくなり、
ユーザーはObsidianで手作業になる。**「作らないが、片付けられる」**が正しい状態なので、
`AnnotationController` は一覧・削除だけに絞って残し、
`listAnnotationFiles` と `ANNOTATION_FOLDER_NAME` も維持する
（後者はランダム経路の除外にも使われており、いずれにせよ消せない）。

**この判断は「撤去範囲を機能単位で数えていた」ことの修正である。**
補記機能を消すのではなく**生成をやめる**のが本設計なので、
撤去すべきは書き込み側だけだった。

**AIタブのバッジは「生成中」だけになった。** [background_ai_ux](background_ai_ux.md) は
「バッジ対象は補記メモのみ」と記録しており、`resolveAiTabBadgeState` の唯一の引数が補記だった。
ひとことは結果がAIタブのパネルへ直接出るので**「見たかどうか」を管理する概念が要らず**、
`isViewed` ごと落ちる。→ **[architecture](architecture.md) の共通化再検討条件
（`markViewed()` と Snackbar 通知を持つ Controller が3つ目に現れたとき）に対して、
既存の2件が1件（Quiz のみ）へ減る。** 条件はさらに遠のく。

**生成中のインジケータだけは残した（2026-08-09 実装時の判断）。**
押してから読書へ戻る導線が実在し、Nano は1回数十秒かかるため。
こちらは自動で消えるので確認管理を必要としない。

**副産物として A11Y-1 の対象が消えた。** 下部ナビ帯（ライトは Indigo）の上で
コントラストを取れなかったのは完了✓（1.61）と失敗!（1.04）の**塗り**バッジで、
その2つがなくなった。残る生成中表示は塗りではなく線のインジケータなので、同じ問題を持たない。
**輪郭線を足す・ナビ帯の色に触るといった、ブランド配色へ踏み込む必要はなくなった。**

### 7.2 `ReadingTrace` schema v3

`aiSummary` / `aiSummaryVisitCount` と並ぶ欄を1つ足す。v1・v2 と同じく読み込み互換を保つ。
バイト上限は `MAX_AI_SUMMARY_BYTES` に倣って別途定める（1文なので大幅に小さくてよい）。

`feature_ideas` N-6（余白メモ）も v3 を要求しているので、
**両方を入れるなら1回のスキーマ更新にまとめる**ほうが移行が1度で済む。

### 7.3 実装時に決めたこと（2026-08-09）

**1. 入力ブロックは「候補ノート8件だけ」に絞った（決着）。**
旧補記は関連ノート・AI推薦ノート・**無制限の全wikilink**の3ブロックを渡していた。
ひとことは候補を実際に使うが、**出力は1件なので多く見せる意味が無い。**
AI推薦を先に置き、現ノート自身とタイトル重複を除いて8件で切る。
これで「リンク集ノートほど候補が本文を押し出す」形が構造的に消えた。
`wikilinkTitles` は渡さない（旧補記が無制限に載せていた唯一の経路だったので、
入力予算の穴もここで閉じた）。

**2. 表示場所はAIタブのパネル（決着）。**
読書画面へ出す案も検討したが、本文の描画は解析待ちのため
「本文の表示を待たせない」条件を新たに設計することになる（[architecture](architecture.md) 2026-07-31）。
**専用画面をやめてパネル1枚にすることが本質**であって、どのタブに置くかは二次的なので、
要約・蒸留と同じ Reflect の面に置いた。生成は明示ボタンなので、押した人はその面にいる。

### 7.4 未決（残っているもの）

1. **保存したひとことを読み返す導線が無い。** v1 は「生成したセッション中だけ」表示する。
   サイドカーには入るが、次に開いても出てこない。**書いているのに誰も読まない状態**なので、
   ここは早めに埋めるべき穴である。自然な置き場所は再会カードだが、下記2と同じ判断が要る。
2. **再会カードに出すか。** `feature_ideas` A-6（当時の問い）・A-7（古い前提）が同じ枠を狙っている。
   **1件ずつ足すと枠の奪い合いになる**ので、先に「再会カードに何を出すか」を決める。
3. **`MIN_GROUNDING_RUN = 4` が実Vaultで未検証。** 一般論を弾くための「原文と4文字以上一致」は
   見積もりでしかない。大きすぎれば妥当なひとことまで落ち、**画面には「見つかりませんでした」しか出ない**
   ので、失敗が静かで気づきにくい。実機で空振りが続くならここを最初に疑う。

### 7.5 実装中に見つかった別件（本設計の範囲外）

**`trimIndent()` 付きテンプレートへ複数行の値を補間すると、字下げが全行に残る。**
`trimIndent()` は補間**後**の文字列に効くため、埋めた値の2行目以降（インデント0）が混ざると
共通インデントが0と判定され、テンプレート側の12スペースが全行に残る。

実測（`buildRelatedNotesPrompt`・候補2件）:

```
[            You are a note-taking assistant. Find the notes most related ...]
[            C01 | 候補A]
[C02 | 候補B]
```

**関連ノートと蒸留の既存プロンプトに、今この状態で入っている。**
本文抜粋も複数行になるので、実運用ではほぼ常に発生している。害は
①1行あたり12文字ぶんの入力トークンを無駄に払う ②整形が崩れて読み取りにくい、の2つ。
`PromptTokenBudgetTest` の計測値にもこの余白が含まれている。

ひとことのプロンプトは静的部分だけを `trimIndent()` して連結する形にしたので当たらないが、

## 8. 実機確認1巡目の反映（2026-08-09）

オーナーの実機確認で「UI/UXに違和感」、あわせて外部レビューで5件の指摘。
**5件とも実装を当てて再現し、4件を直した。**

### 8.1 リンクがあると根拠検査を免除していた（自分の仕様に反していた）

§1.2 は「ノート固有の言葉を**必ず**含める」と例外なしで書いてあるのに、
実装は「実在ノートへのリンクを含むなら根拠として認める」という免除を持っていた。
**自分で書いた仕様に、自分の実装が反していた。**

結果として通っていたのがこれ:

```
[[問いを立てる技術]]と並べると、まったく別の角度から捉え直せるかもしれません。
```

リンク先は実在するが、**地の文は丸ごと一般論**である。今回いちばん潰したかった形そのものだった。

**免除を削り、さらに根拠は `[[...]]` を除いた地の文で測る**ようにした。

短すぎる・長すぎる・一般論・候補外リンクをすべて `Empty` へ倒し、

**`NothingToSay` だけが「本当に出すものが無い」**。

**分ける根拠は「ユーザーの次の行動が違う」こと** — 前者は再試行しても同じ、後者は効く。
Snackbar も空振りは行き先なし、書式失敗は「もう一度」を出す。
これは [lessons](../lessons.md) L28（呼び出し側が次に何をするかで決める）の適用にあたる。

## 10. 実機確認3巡目の反映（2026-08-09）

### 10.1 返事を失う経路を3つ作っていた（最優先で直した）

§9.2 で「**書いた言葉は作り直せない**」と書いて即時保存にしたのに、
その直後に**失う経路を3つ作っていた。**

`saveReply` の戻り値を Boolean にし、false を「痕跡側が預かっている」と読んで
画面には常に「保存済み」と出していた。だが預かるのは**4経路のうち1つだけ**で、
Vaultキー無し・保存失敗・例外の3経路は**どこにも残らない**。
さらに下書きが `remember` だったので、画面回転でも消えた。

**Boolean へ畳んだのが誤りだった。**

| 結果 | 呼び出し側の次の行動 |
|---|---|
| `Saved` | 「保存済み」でよい |
| `Held` | 離脱時に書かれる。**失敗として見せない** |
| `Lost` | 本当に消える。**未保存として見せ、押し直せる状態を保つ** |

3通りに分かれるので `ReplySaveOutcome` にした（→ [lessons](../lessons.md) L28）。
`true`/`false` では「預かっただけ」と「完全に失った」が同じ顔になり、実際そうなっていた。

**教訓: 「呼び出し側が次に何をするか」で数えるのは、成功/失敗にも効く。**
L28 は境界の戻り値の話だが、**失敗の種類**にも同じ問いが当たる。
失敗を1つに畳んだ時点で、回復できる失敗とできない失敗の区別が消える。

### 10.2 保存済みの返事へ辿る導線が無かった

ノート切替で `RemarkState.Idle` に戻ると、AIタブのボタンは「ひとことをもらう」になり
**新規生成へ進むだけ**だった。保存済みの読み戻しは専用画面を開いた後に走るのに、
Idle からその画面を開く入口が無い。**§9.3 の「画面を開いたときだけ読む」判断が、
入口自体を非Idle状態に閉じ込めていた。**

**AIタブのボタンを常に専用画面へ向ける**ことで解いた。生成の起点も画面側へ寄せる。
これで「開く → 保存済みがあれば出る／無ければもらう」の1本になり、
**ノート表示のI/Oを増やさずに**（§9.3 の意図を保ったまま）塞がる。

**入口の状態で行き先を変えていたのが原因。** 状態がリセットされる設計なら、
状態に依存した入口は必ずどこかで行き止まりになる。

### 10.3 1往復だけ許して対話を閉じる（§9.2 の判断を一部撤回）

§9.2 は「返事をAIへ再送しない」と決めたが、実機では
**AIが問いを投げて会話を一方的に打ち切る**形のままだった。

**1往復だけ許す。** 返事を受けてAIが1文返し、そこで終わる（`Reflection.mirrored`・schema v5）。

- **問いを返させない。** 問いを返すと次の返事を誘発し、無限会話の入口になる。
  **プロンプトで禁じるだけでなく検査で捨てる**（疑問符を含む応答を拒否）—
  一般論の禁止を検査で担保しているのと同じ考え方
- **返事を先に保存してから生成する。** 生成の失敗やキャンセルでユーザーの言葉を巻き込まない
- **`Lost` のときは生成しない。** 消える返事へ応じても仕方がない
- **失敗しても何も出さない。** 映し返しは「うまくいけば添えられる」ものなので、
  失敗を通知すると返事を残したこと自体が失敗したように見える
- **返事を書き直したら映し返しを捨てる。** 古い返事への応答が残ると噛み合わない（型で保証）

### 10.4 再会カードは1行の手がかりだけ（オーナー判断）

問い・返事・映し返しの3つをカードへ並べると、**「前回のあなた」を1文で伝える**という
カードの役目が壊れる（既に4項目ある上に3つの長文が乗る）。
カードには「前回の返事を見る」だけ置き、中身は専用画面で読む。

`revealTrace` は既に痕跡を読んでいるので**追加のI/Oは無い**。
A-6（当時の問い）・A-7（古い前提）との枠の奪い合いも起きない。

### 10.5 残っているもの

- **退避・復元（TRACE-4）が未着手。** 返事に加えて映し返しも入り、失う損失はさらに増えた
- `[[関連ノート]]` はまだタップできない
- `buildRemarkPrompt` / `buildRemarkMirrorPrompt` とも実Nano生成テストの対象外。
  **映し返しは「問いを返さない」という形の制約に全面的に依存する**ので、

## 11. 実機確認4巡目の反映 — 長文の扱い（2026-08-09）

### 11.1 根っこは「上限を1本で決めた」こと

`MAX_REPLY_CHARS = 400` は `MAX_REPLY_BYTES = 1536` から逆算した値で、
その 1536 は「1文だから」と置いた数字だった。つまり
**ユーザーの文章の長さを、AIの都合ですらない思いつきで縛っていた。**

**本文は既に「保存は原文・AIへは抜粋」でやっている**（→ [ai_input_excerpt](ai_input_excerpt.md)）。
返事だけ両方を同じ数字で縛っていたのが誤りだった。

| | 変更前 | 変更後 |
|---|---|---|
| 保存する返事 | 400字 | **8,000字**（完全保存。切り詰めない） |
| 静かに知らせる目安 | — | **2,000字**（壁ではなく合図） |
| AIへ渡す返事 | 同じ400字 | **先頭＋末尾で400字へ抜粋**（`excerptReplyForPrompt`） |

**「汎用エディタにしない」（→ `feature_ideas` N-6）は壁ではなく合図で守る。**
壁にすると、長く書きたかった回にユーザーの言葉が消える。
2,000字を超えたら「ノート本体のほうが探しやすい」と一言添えるだけにした。

**上限どうしの整合を計算で固定した**（`ReadingTraceLimitsTest`）。
返事の上限を上げるとファイル全体の読み込み上限（`MAX_FILE_BYTES`）を超え得るが、
これは**保存は成功しテストも緑なのに、次回読めなくなる**という気づきにくい壊れ方をする。
数えるのをやめて、全フィールドの最悪ケースを足す形にした（64KB → 128KB へ引き上げ）。

### 11.2 上限超過を黙って捨てていた

```kotlin
onDraftChange = { if (it.length <= 400) draft = it }   // 変更前
```

401文字を貼ると**入力変更ごと無視される**。警告も出ないので、
「長文を貼ったのに無反応」＝「書いたのに保存されなかった」と読める。
受け取ってから切る形へ変えた。

**上限を超えた入力を「無かったこと」にしてはいけない。**
切るなら切ったと示す。これはユーザーの言葉を扱うすべての口に当てはまる。

### 11.3 `Held` を「保存済み」と呼んでいた

§10.1 で3値へ分けたのに、**画面では `Held` も「保存済み」と出していた。**
「離脱時に書かれるので失敗として見せない」という判断だったが、
`Held` はまだファイルに書かれていない。しかも離脱時の書き込みには門番があり、
**通らなければ本当に消える。**

- 表示を4値へ（`未保存 / 保存中 / 保存済み / 保存失敗`）。`Held` は「保存中」
- **`Boolean` 2本（`isSavingReply` / `isReplyUnsaved`）を `ReplyStatus` へ畳んだ** —
  2本だと「保存中かつ未保存」のような意味の無い組み合わせが型として作れる
- **保存済みの判定に下書きとの差を入れた。** 書き直している最中でも
  過去の日時があるだけで「保存済み」と出ていた

### 11.4 返事を預かっているときは離脱時の門番を通す

`recordVisit` の門番（10秒以上・1ブロック以上）は
「一瞬引いてすぐ送った表示を訪問に数えない」ためのものだが、
**返事を預かっているときに効かせると、条件未達で離れた瞬間に返事が消える。**

**ユーザーが返事を書いた事実は、10秒のスクロールより強い関与である。**
返事を預かっているときだけ門番を通し、到達率0の訪問として記録する。
返事が無いときの挙動は変えない（一瞬の表示は数えないまま）。

### 11.5 長文で保存ボタンが押し出されていた

画面が1本の `verticalScroll` だったため、返事が長いほど保存ボタンが下へ流れ、
**未保存のまま戻れてしまう。** スクロールする本文とボタン列を分け、
ボタンを常に見える位置へ固定した。

### 11.6 冒頭の「あなた」を外した

**「あなた」は指示として入れていたもの**で、痕跡の俯瞰要約からそのまま持ってきていた。

**category をまた取り違えていた。** 俯瞰要約は「あなたは3回開いています」と
**読み手自身の行動を述べる**文なので二人称が要る。ひとことと映し返しは
**ノートについて話す**文なので、主語に読み手を置く必要がない。
日本語は主語を落とせるうえ、二人称で名指しすると**採点者の口調**になる —
§1.1 で避けたかったものそのものだった。

§9.1 で「言語」の category は直したのに、**同じ行に混ざっていた「あなた」は
一緒に持ってきてしまった。** 1つの指示文に2つの判断が入っていると、片方だけ直す。

**捨てずに剥がす。** 指示を外すだけでは小さいモデルは従い切らないので
後処理でも落とすが、**文体の好みで文ごと捨てない** — 一般論や問いのように
中身が契約違反であるものとは扱いを変える。捨てると空振りが増え、
「中身は悪くないのに何も出ない」という最悪の形になる。
剥がして読点始まりになるなど壊れる場合は、元のまま出す。

### 11.7 「保存ボタンを押した文章は必ず永続化する」を契約にする

長文を許したあと、保存まわりに穴が5つ残っていた。**どれも「押したのに残らない」型。**

**① 失敗後に「もう一度保存する」が押せなかった。** 失敗時も本文は状態へ残すので
`isDirty` が false になり、ボタン名だけ変わって押せない状態だった。
`isDirty || replyStatus == Failed` を有効条件にする。

**② 8,000字超をまだ黙って切っていた。** `take()` で先頭だけ残し、切ったことを出していない。
**上限を超えた入力を「無かったこと」にしない**（§11.2 と同じ原則）ので、切ったら必ず出す。

**③ `Held` の離脱保存が失敗すると再試行できなかった（最も痛い）。**
`flush()` は保存コルーチンを起動した**直後**に `session = null` にする。
後から書き込みが失敗して `owner.pendingRemark` へ戻しても、
**その owner はもう現役セッションではない**ので、次の書き込み契機が来ない。

セッションではなく Controller が持つ退避スロット（`unsavedReply`）へ移した。
次の書き込み契機（別ノートの離脱・背面化・同じノートを開き直す）で書き直す。
Vault切替では捨てる（旧Vaultの返事を新Vaultへ書かない）。
**プロセスが死ねば失われる**が、それは全ての未保存データと同じ条件になる。

> **初版の退避は「返事」を1件だけ持つ形で、2つ穴があった（同日中に作り直した）。**
>
> **① 痕跡の新規作成が失敗した回を復旧できなかった。** 返事だけを持つと
> 「既存の痕跡へ載せ直す」ことしかできない。ファイルがまだ無い＝初読で返事まで
> 書いた回がまるごと落ちる。**退避するのは返事ではなく、保存しようとした
> `ReadingTrace` そのもの**でなければならない — 完成済みなら、ファイルが無くても作れる。
>
> **② 単一スロットだったので、Aが退避中にBで返事を書くとAが消えた。**
> Vault＋相対パスをキーにした Map へ変えた（上限8件）。
>
> あわせて、退避を消してよい条件を「返事の文字列が一致」から
> **`Reflection` 全体の一致**へ狭めた。返事が同じでも元の問い・日時・映し返しが
> 違えば別物である。
>
> **同じノートを二重に書かない。** 現セッションの巻き戻し（`dirty`）と退避の
> 書き直しが両方走ると、同じファイルへ2回書く。これから書くパスは退避側で除外する。

**④ 未保存の下書きが警告なく消えた。** 「別のひとこと」「戻る」で確認を出す。

**⑤ 入力欄が8,000字で巨大化した。** 最大高を決めて欄内スクロールにする。

**あわせて、痕跡が未作成のときの映し返しも預けるようにした。**
画面には出ているのに保存だけ落ちると、次に開いたとき**返事だけが残って応答が消えている**
状態になる。

### 11.8 退避の作り直し（Map方式のP1 2件）と、映し返しの本文の出所

**退避を Map にしたことで、新しい穴が2つできていた。**

**① 上限8件で最古を無条件に捨てていた。** しかも**通常の訪問痕跡の保存失敗も
同じMapへ積んでいた**ため、返事付きの退避が普通の読書に押し出され得た。

**返事を持つ痕跡だけを積む**ようにした。訪問だけの失敗はセッション側の巻き戻し
（`dirty` / `recordedVisit`）が同じ閲覧のうちに書き直すし、失ってももう一度読めば付き直る。
**返事は作り直せない**ので扱いが違う。これで上限に当たるのは
「返事の保存が8ノートぶん失敗し続けたとき」だけになった。

**② 古い退避が新しく保存した返事を上書きできた。** 返事の日時で新旧を見て、
ファイル側が新しければ書き戻さずに退避を捨てる。
**別端末が同期で新しい返事を書き込んだ場合はアプリの保存経路を通らない**ため、
日時の比較だけが唯一の防波堤になる。

**③ Map が Main と IO の両方からロック無しで触られていた。** 専用の Mutex を足した。
`writeMutex` と兼用しないのは、退避の書き直しが「スナップショット → 1件ずつ
`writeMutex` で保存 → 消す」の順で動き、保存の間はこちらを離す必要があるため。
取得順は `writeMutex → pendingMutex` の一方向に保つ。
**スナップショット後に同じキーへ新しい退避が入っていたら消さない**
（消すと、書けていない新しい返事まで捨てる）。

> 「直接保存できたら退避を捨てる」も書いたが、**外しても落ちるテストが無かったので
> 削除した**。②の日時比較が同じケースを覆っており、書き込みも発生しない
> （→ [lessons](../lessons.md) L11）。
>
> **①のテストは最初、変異させても落ちなかった。** 返事付きを**後から**積んでいたため
> 上限に当たっても押し出されない順序になっていた。
> **テストの順序がそのまま検出力**だった。

**映し返しの本文の出所も直した。** `create()` が受け取った本文をフィールドへ写していたが、
`restoreSaved`（保存済みの読み戻し）はそこを通らないため、
**保存済みのひとことに後から返事を書くと映し返しが黙って出なかった**
（Rediscover の「前回の返事を見る」から入った経路がこれ）。
表示中のノートから引く形にして、どちらの経路でも同じにした。

**離脱の確認も `Failed` を見るようにした。** 保存に失敗すると本文は状態へ残すので
`isDirty` が false になり、「未保存だが下書きと一致している」状態が生まれる。
再試行ボタンは直したのに、離脱の確認だけがすり抜けていた。
**「書き換えたか」ではなく「まだファイルに残っていないか」で見る。**

### 11.9 残っている穴: プロセスが死ぬと退避は失われる

退避はプロセスメモリにしか無い。アプリが落ちれば、書けなかった返事は消える。
**本当に「必ず残る」と言うには、アプリ内部の回復ファイルへ永続化する必要がある**
（蒸留が復旧レコードで同じことをしている）。
現状は「プロセスが生きている間は必ず書き直す」までで、そこは正直に線を引く。

### 11.10 映し返しが出ない件は §11.3 で解けた

映し返しの生成失敗は引き続き無表示のままだが、
**「保存済み」の表示が確実になった**ので「保存も失敗したのか」という誤解は消える。
映し返しは「あれば添えられる」ものという位置づけを保つ。
