# 設計思想 — 実端末を通すテスト（instrumentation）

**対象領域:** `androidTest` に何を置き、何を置かないか。実物SAFの作り方。実行の運用
**初版:** 2026-08-08
**状態:** 段階1〜3 実装済み・**実機確認済み**（2026-08-08 / Pixel 10 Pro Fold で 24/24 成功・0 skipped）。段階4は未着手

---

## 背景

課題台帳は長らく「実端末を通す統合テストの中身が無い（規模: 大）」を抱えていた。
着手前に実物を当てたところ、**「大」は前提が無かった頃の見積もりのまま**で、
その後の構造変更で条件が大きく変わっていることが分かった。

| 当時なかったもの | 現在 |
|---|---|
| instrumentation が動く保証 | 2026-08-01 に Android 16 で 2/2 成功 |
| SAF境界の差し替え口 | `VaultBrowser` が**インターフェース**（2026-08-01・段階7） |
| `androidTest` からの `internal` 可視性 | 既に利用中（`selectDistillCandidates` 等） |
| Activity/Compose のハーネス | `ActivityScenarioRule` と `ui-test-manifest` が稼働中 |

**規模感を「大」から「中」へ改める。**

## 判断1: 置くのは「実測が要るもの」だけ

判定は機能名ではなく**「JVMで書けないか」**で行う。純関数の値の伝播・分岐・境界値はJVM側が
覆っているので持ち込まない。`androidTest` に残すのは Compose のレイアウト実測、
可視判定、再コンポーズ、Activityのライフサイクル、実物のSAF/`BitmapFactory` に依存するもの。

**この基準は台帳（TEST-2）に元からあった**が、instrumentation を書き始めると
「ついでにここも」で崩れやすい。各テストのKDocに**なぜJVMでは書けないかを1行残す**ことで、
後から読んで判断できるようにする。

## 判断2: ViewModel を組み立てない（段階1）

`NoteReaderTab` / `FullscreenNoteScreen` は `NoteUiState` と `LazyListState` を
**素の引数として受け取る**。UIに業務ロジックを置かない規約の副産物として、
**ViewModelもFakeも無しに画面を描ける**。段階1が本番コードの変更ゼロで済むのはこのため。

**`MainActivity` 経由では差し替えられない。** `by viewModels()` でデフォルトファクトリを
直に使っているため、依存を注入する口が無い。段階1では画面コンポーザブルを直接 `setContent`
することで回避した。Activity全体を通したい要求が出たら、そのとき ViewModelFactory の
seam を本番へ入れるか判断する。**先回りで seam を作らない** — 使い道が確定していない
抽象を本番へ足すことになるため。

**`src/test` の Fake は `androidTest` から見えない**（別ソースセット）。段階2で共有が
必要になったら、共有ディレクトリを両ソースセットへ足す形を採る。段階1では不要だった。

## 判断3: ブロック番号を本文へ埋めて可視位置を特定する

`ReadingProgressReporter` は `visibleItemsInfo.last().index` を**そのままブロック番号として**
報告している（LazyColumn の index とブロック番号がずれない前提が本番側にある）。
したがってテスト本文を「段落0」「段落1」…と並べておくと、**可視位置を文言で特定できる**。
`LazyListState` の内部値ではなく画面に出ている文字で判定できるので、
レイアウトの細部が変わっても壊れにくい。

**全画面の引き継ぎ判定には先頭可視ブロックを使う。** 全画面はシステムバーを隠して表示域が
変わるため末尾可視ブロックは1つずれ得るが、引き継がれるのは
`firstVisibleItemIndex` / `firstVisibleItemScrollOffset` なのでそこを見る。

## 判断5: 読取失敗は「例外」ではなく「null カーソル」で作る

`querySafChildren` は `contentResolver.query(...) ?: SafChildren.UNREADABLE` という形なので、
**実物の読取失敗は「query が null を返す」こと**である。したがって
[FakeVaultDocumentsProvider] の `queryChildDocuments` も、失敗させたいフォルダで
null を返す。例外を投げる形にすると本番が通っていない経路を試すことになる。

これで初めて、**「ノートが無い」と「そのフォルダを読めなかった」の区別**を
実物のSAF経路で確かめられる。痕跡の孤児判定は不在を根拠に**削除する**ため、
ここが崩れると生きた痕跡が消える。TRACE-1・TRACE-2 で純関数側は固めたが、
**`NoteRepository` から `VaultScan` までの実配線は手動確認しか担保が無かった。**

**必要だったのは `isChildDocument` の override。** tree URI 配下の入れ子を触ると
`DocumentsProvider.enforceTree()` がこれを呼ぶので、実装しないと
ルート直下しか読めない。

**マニフェストの3条件は必須で、外すと「テストが0件」になる。**
`DocumentsProvider.attachInfo()` は自分の宣言を検査し、
`exported="true"` ／ `grantUriPermissions="true"` ／
読み書きが `android.permission.MANAGE_DOCUMENTS` で保護されている、の
どれかが欠けると `SecurityException` を投げる。
**プロバイダはアプリ起動時に生成されるので、ここで落ちるとテストは1件も走らず、
Gradle は「テスト結果を読めない」としか言わない**（テストの失敗として現れない）。
最初に `exported="false"` で書いて実際にこれを踏んだ。

`exported="true"` でも外部から触れるわけではない。`MANAGE_DOCUMENTS` は
システム（DocumentsUI）だけが持つ署名権限で、通常のアプリは取得できない。
自アプリからは同一UIDなので権限検査を通らずに済む。
**`DOCUMENTS_PROVIDER` の intent-filter は置かない** — 宣言するとSAFのピッカーに
偽Vaultが並ぶ。直接URIを組む用途では要らない。

**教訓は「0 tests は失敗ではなく起動前の墜落」と読むこと。** 個々のテストを疑う前に
プロセスが立ち上がったかを見る。原因は `adb logcat` に例外として出る。

## 判断7: 端末AIは「生成が返ること」までを assert し、書式は観測に留める

段階4a に着手して分かったのは、既存の `PromptTokenBudgetTest` が**計測しかしておらず、
`generate()` を本番プロンプトで通す経路が1つも無かった**こと。
`maxOutputTokens` の「1〜256」制限で全AI生成が落ちた前例は、ここが空いていたために
本番まで抜けた。**上限に収まることと、生成が返ることは別**である。

**assert するのは「空でない応答が返る」まで。** SDK制約・プロンプト長・API互換の破壊は
これで落ちる。**応答の書式は assert しない** — 端末AIの出力は非決定的なので、
一致を要求すると壊れていないのに赤くなる。パーサへ通した結果は logcat へ出して
人間が読む材料に留め、パーサについて assert するのは
**「実出力を渡しても例外を投げない」**ことだけにする。

**この線引きを動かしたくなったら、先に本番側を疑う。** 書式一致を assert したい＝
パース失敗時の見せ方が本番に足りていないサインかもしれない。
テストを厳しくするより、失敗したときのUXを確かめる方が効く。

## 判断6: 上限の境界はBMPで通す（PNGでは通らない）

段階3は、IMG-3 のレビューで唯一満たせなかった受理条件
「実物の `NoteImageGateway` で `TooLarge` と `Broken` を分ける」を埋めるもの。

**最初に書いた「16MiBのゼロ列を食わせる」テストは無意味だった。**
`BitmapFactory` はヘッダを読んだ時点で画像でないと判断して読むのをやめるので、
**`BoundedInputStream` が上限に到達せず、境界を1バイトも通らない。**
`truncated` が立たないため結論は `Broken` になり、
**修正前の実装でも同じ結果**＝退行を検出できない。

そこで**非圧縮の24bit BMP**を組み立てる。BMPは寸法からファイル長が決まり、
復号器が画素データを最後まで読むので、上限の内外を狙って作れる。

| 寸法 | ファイル長 | 上限（16MiB）との差 | 期待 |
|---|---|---|---|
| 2400×2300 | 16,560,054 | −217,162 | 復号成功（大きさを理由に落とさない） |
| 2400×2400 | 17,280,054 | +502,838 | `TooLarge` |

**サイズを申告しないプロバイダとして置くのが要点。** メタデータ判定
（`size > MAX_INPUT_BYTES`）を素通りさせないと、`BoundedInputStream` 側の
判断まで届かない。`COLUMN_SIZE` に null を返すプロバイダは実在するので、
再現としても正しい。

**画素の中身は問わない（全部ゼロでよい）。** ここで見たいのは長さと
読み切れるかどうかだけで、絵が正しいかではない。

**「復号器がどこまで読むか」を意識しないと、境界のテストは空振りする。**
入力を大きくしただけでは上限に触れない。

**`DocumentsProvider` の実体はシステムが生成する**ためテストから掴めない。
木の組み立てと失敗注入は `companion` 側の API（`reset` / `putFile` / `makeUnreadable`）に置く。

## 判断4: CIでは実行せず、実行を運用で担保する

**現在のCIは `assembleDebugAndroidTest`（コンパイルのみ）で、instrumentation を1件も実行していない。**
このまま増やすと「コンパイルは通るが誰も走らせないテスト」になり、
[lessons L29](../lessons.md) と同じ形（規則を書いただけで検査になっていない）になる。

それでも**CIにエミュレータジョブを足さない**と判断した。理由は2つ。

1. **端末AI依存のテストは、エミュレータでは `Assume` で skip される。** 通しても緑になるだけで
   何も守らない。ゲートに載せる価値が出るのは段階2以降の実物SAFの部分だけである。
2. CI時間の増加が大きく、現在の1人開発の回転数に見合わない。

代わりに**「PR前にAndroid Studioで実行する」を運用として明記**する。
**運用は検査に劣ることを承知の上での選択**なので、
**instrumentation が20件を超えたらエミュレータジョブを再検討する**を条件として置く
（件数はトリガーとして機能する。20は「手で回すのが面倒になる」体感の境目）。

> **2026-08-08 — 同日中に条件へ到達した（24件）。再検討の結論は「入れる価値が出た」。**
>
> 判断4を書いた時点の内訳は7件で、そのうち5件が端末AI依存だった。
> つまり**エミュレータで走らせても大半が skip される**というのが「入れない」の根拠だった。
> 段階1〜3で17件増えた結果、内訳が逆転している。
>
> | 区分 | 件数 | エミュレータで |
> |---|---|---|
> | SAF・`BitmapFactory`（段階2・3） | 13 | **走る** |
> | Compose の実測（段階1） | 4 | **走る** |
> | 土台の疎通（既存） | 2 | **走る** |
> | 端末AI（`PromptTokenBudgetTest`） | 5 | skip |
>
> **19/24 が実際に走る。** しかも走る側は「実配線でしか壊れが出ない」ものばかりで、
> ゲートに載せる価値が最も高い部分である。
> **根拠が消えたので判断4は維持しない** — ただし**端末AI依存のクラスは対象から外す**
> （通しても skip で緑になるだけで、CI時間だけ増える）。
>
> **CI時間の増加（エミュレータ起動を含めて数分）を払うかはオーナーの判断**であり、
> 技術的な当否ではないのでここでは決めない。実装するなら
> `connectedDebugAndroidTest` にクラス指定を付けた別ジョブを足す形になる。

## ソースセットが4つになった

`src/debug/` を足したので、Android Studio のプロジェクトツリーに
`com.example.newproject.testing (debug)` が並ぶようになった。役割は次のとおり。

| ソースセット | 入るビルド | 中身 |
|---|---|---|
| `main` | すべて | 本番コード |
| `debug` | debug のみ | **テスト用の偽Vault（`DocumentsProvider`）だけ** |
| `test` | ビルドに入らない | JVMユニットテスト |
| `androidTest` | 別APK（テスト用） | instrumentation テスト |

**`debug` はアプリ本体側**なので、`androidTest` と違ってアプリと同じUIDで動く。
段階2の偽プロバイダをここへ置いたのはそのため（→ 判断5の直前）。
**release ビルドには入らない** — `processReleaseMainManifest` の出力に
プロバイダ宣言が現れないことを確認済み。

## 実機確認の結果（2026-08-08）

Pixel 10 Pro Fold（Android 17）で **24/24 成功・0 skipped**
（段階1が4件・段階2が6件・段階3が7件・既存7件）。
段階1と段階3は初回から緑で、修正が要ったのは段階2のマニフェスト宣言だけ。

**判断4の再検討条件（instrumentation が20件を超えたら）に到達した。** → 下記

**副産物が2つある。**

1. **端末AIのテストが `Assume` で飛ばされずに実行された**（`PromptTokenBudgetTest` 5/5）。
   この端末では Gemini Nano が `AVAILABLE` なので、**手元の実機に限れば端末AI経路も
   実際に計測されている**。ただし「CIのエミュレータでは skip される」という
   判断4の前提はそのまま — 実行環境が変われば skip へ戻る。
2. **判定を本文の文言で行う設計（判断3）が、実測でも安定した。**
   全画面はシステムバーを隠して表示域が変わるが、先頭可視ブロックで見ているため
   影響を受けなかった。

**Claudeは instrumentation を実行できない。** したがって以後の段階も
「実装＋`assembleDebugAndroidTest` 通過」までがこちらの担保で、
**緑であることの主張はオーナーの実行結果を待つ**という往復は変わらない。
