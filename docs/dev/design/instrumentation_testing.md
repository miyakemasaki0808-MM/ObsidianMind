# 設計思想 — 実端末を通すテスト（instrumentation）

**対象領域:** `androidTest` に何を置き、何を置かないか。実物SAFの作り方。実行の運用
**初版:** 2026-08-08
**状態:** 段階1（読書画面）実装済み・**実機確認済み**（2026-08-08 / Pixel 10 Pro Fold・Android 17 で 11/11 成功・0 skipped）。段階2以降は未着手

---

## 背景

課題台帳は長らく「実端末を通す統合テストの中身が無い（規模: 大）」を抱えていた。
着手前に実物を当てたところ、**「大」は前提が無かった頃の見積もりのまま**で、
その後の構造変更で条件が大きく変わっていることが分かった。

| 当時なかったもの | 現在 |
|---|---|
| instrumentation が動く保証 | 2026-08-01 に Android 16 で 2/2 成功 |
| SAF境界の差し替え口 | `VaultBrowser` が**インターフェース**（2026-08-01・段階7） |
| `androidTest` からの `internal` 可視性 | 既に利用中（`selectDistillCandidates` 等） |
| Activity/Compose のハーネス | `ActivityScenarioRule` と `ui-test-manifest` が稼働中 |

**規模感を「大」から「中」へ改める。**

## 判断1: 置くのは「実測が要るもの」だけ

判定は機能名ではなく**「JVMで書けないか」**で行う。純関数の値の伝播・分岐・境界値はJVM側が
覆っているので持ち込まない。`androidTest` に残すのは Compose のレイアウト実測、
可視判定、再コンポーズ、Activityのライフサイクル、実物のSAF/`BitmapFactory` に依存するもの。

**この基準は台帳（TEST-2）に元からあった**が、instrumentation を書き始めると
「ついでにここも」で崩れやすい。各テストのKDocに**なぜJVMでは書けないかを1行残す**ことで、
後から読んで判断できるようにする。

## 判断2: ViewModel を組み立てない（段階1）

`NoteReaderTab` / `FullscreenNoteScreen` は `NoteUiState` と `LazyListState` を
**素の引数として受け取る**。UIに業務ロジックを置かない規約の副産物として、
**ViewModelもFakeも無しに画面を描ける**。段階1が本番コードの変更ゼロで済むのはこのため。

**`MainActivity` 経由では差し替えられない。** `by viewModels()` でデフォルトファクトリを
直に使っているため、依存を注入する口が無い。段階1では画面コンポーザブルを直接 `setContent`
することで回避した。Activity全体を通したい要求が出たら、そのとき ViewModelFactory の
seam を本番へ入れるか判断する。**先回りで seam を作らない** — 使い道が確定していない
抽象を本番へ足すことになるため。

**`src/test` の Fake は `androidTest` から見えない**（別ソースセット）。段階2で共有が
必要になったら、共有ディレクトリを両ソースセットへ足す形を採る。段階1では不要だった。

## 判断3: ブロック番号を本文へ埋めて可視位置を特定する

`ReadingProgressReporter` は `visibleItemsInfo.last().index` を**そのままブロック番号として**
報告している（LazyColumn の index とブロック番号がずれない前提が本番側にある）。
したがってテスト本文を「段落0」「段落1」…と並べておくと、**可視位置を文言で特定できる**。
`LazyListState` の内部値ではなく画面に出ている文字で判定できるので、
レイアウトの細部が変わっても壊れにくい。

**全画面の引き継ぎ判定には先頭可視ブロックを使う。** 全画面はシステムバーを隠して表示域が
変わるため末尾可視ブロックは1つずれ得るが、引き継がれるのは
`firstVisibleItemIndex` / `firstVisibleItemScrollOffset` なのでそこを見る。

## 段階

| 段階 | 内容 | 本番変更 | 状態 |
|---|---|---|---|
| 1 | 読書画面（解析待ちの描画抑止・全画面への位置引き継ぎ・進捗報告の整合） | なし | **完了**（実機 4/4） |
| 2 | 実物SAF（`src/debug/` のテスト用 `DocumentsProvider`）＋走査・補記の保存/削除・読取失敗の注入 | debug ソースセット追加 | 未着手 |
| 3 | `NoteImageGateway`（段階2の上に乗る） | なし | 未着手 |
| 4 | 端末AIの横展開・画面回転／プロセス再生成 | なし | 未着手 |

**段階2のプロバイダは `androidTest` ではなく `src/debug/` へ置く。**
`androidTest` 側に置くと別APK・別UIDになり、URI権限の付与が要る。
debug ソースセットならアプリ本体と同じUIDになるので、`DocumentsContract` の
tree URI をそのまま扱える。フォルダ読取失敗（`ReadingTraceOrphans` の三値判定が対象）も、
プロバイダ側で例外を返すだけで再現できる。

## 判断4: CIでは実行せず、実行を運用で担保する

**現在のCIは `assembleDebugAndroidTest`（コンパイルのみ）で、instrumentation を1件も実行していない。**
このまま増やすと「コンパイルは通るが誰も走らせないテスト」になり、
[lessons L29](../lessons.md) と同じ形（規則を書いただけで検査になっていない）になる。

それでも**CIにエミュレータジョブを足さない**と判断した。理由は2つ。

1. **端末AI依存のテストは、エミュレータでは `Assume` で skip される。** 通しても緑になるだけで
   何も守らない。ゲートに載せる価値が出るのは段階2以降の実物SAFの部分だけである。
2. CI時間の増加が大きく、現在の1人開発の回転数に見合わない。

代わりに**「PR前にAndroid Studioで実行する」を運用として明記**する。
**運用は検査に劣ることを承知の上での選択**なので、
**instrumentation が20件を超えたらエミュレータジョブを再検討する**を条件として置く
（件数はトリガーとして機能する。20は「手で回すのが面倒になる」体感の境目）。

## 実機確認の結果（2026-08-08）

Pixel 10 Pro Fold（Android 17）で **11/11 成功・0 skipped**。
段階1の4件はすべて初回から緑で、修正は要らなかった。

**副産物が2つある。**

1. **端末AIのテストが `Assume` で飛ばされずに実行された**（`PromptTokenBudgetTest` 5/5）。
   この端末では Gemini Nano が `AVAILABLE` なので、**手元の実機に限れば端末AI経路も
   実際に計測されている**。ただし「CIのエミュレータでは skip される」という
   判断4の前提はそのまま — 実行環境が変われば skip へ戻る。
2. **判定を本文の文言で行う設計（判断3）が、実測でも安定した。**
   全画面はシステムバーを隠して表示域が変わるが、先頭可視ブロックで見ているため
   影響を受けなかった。

**Claudeは instrumentation を実行できない。** したがって以後の段階も
「実装＋`assembleDebugAndroidTest` 通過」までがこちらの担保で、
**緑であることの主張はオーナーの実行結果を待つ**という往復は変わらない。
