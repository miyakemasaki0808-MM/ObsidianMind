# 読書痕跡の退避（書き出し・読み戻し）の実機検証ケース

## 正本

- 退避の規則・突き合わせ・上限: [reading_trace_backup](../../dev/features/reading_trace_backup.md)
- 痕跡そのもの（欄・保存・寿命）: [reflect_reading_trace](../../dev/features/reflect_reading_trace.md)
- 共通の準備と後処理: [実機検証手順](README.md)

## 適用条件

退避形式・突き合わせ規則・上限・データ管理画面を変えたときに使う。
**痕跡スキーマを上げたときも必ず通す**（退避ファイルは版ごとの中身をそのまま運ぶ）。

## 検証前

- **一時Vaultに痕跡を作る。** 余白メモを複数保存したノートと、訪問だけのノート（2回以上開く）をそろえる。
- 合流用に、同じ相対パスのノートについて端末側と退避側に異なるメモを用意する。
  `(日時, 本文)` が同じ重複、重複を除いて20件ちょうど、21件になる組を分ける。
  訪問も重複を除いて31件以上になる組を用意する。退避側を作った後に端末側だけで訪問・メモを増やす。
- `BACKUP-10` 用には、**既存データの印を保持した有効なfixture**を用意する。
  印を付けるUIは撤去済みなので、画面から新しく付ける手順にはしない。
- **壊れた痕跡を1つ用意する。** `_ReadingTraces/` のJSONを1つ選び、`noteTitle` を書き換える
  （checksum が守っている欄なので破損扱いになる）。正常系fixtureは保存形式とchecksumが有効なものを使う。
- 保存先は**Vault外**（ダウンロード等）を既定とし、Vault内も1回試す。

## ケース

| ID | 入力・操作 | 期待 |
|---|---|---|
| `BACKUP-01` | オプション →「データ管理」を開く | 退避の2ボタンと「読書痕跡を整理」がある。撤去済みの「AI補記メモを削除」は無い。オプション直下に片付け系の項目は無い |
| `BACKUP-02` | 「書き出す」→ Vault外へ保存 | 既定名は `vigilith_traces_yyyyMMdd.json`。「N件を書き出しました」。件数が痕跡ファイル数と一致する |
| `BACKUP-03` | 書き出したファイルを取り出して中身を見る | 人が読めるJSON。**`documentId` がキーごと無い**（端末内のパスが漏れていない）。余白メモは平文で入り、日時・本文が元の痕跡と一致する |
| `BACKUP-04` | 壊れた痕跡がある状態で書き出す | 「M件は壊れていて読み取れなかった」と出て、`_ReadingTraces/<64桁>.json` の形でファイル名が示される。**その1件は退避ファイルに入らない** |
| `BACKUP-05` | 痕跡が1件も無いVaultで書き出す | 保存先を選んだ後に「書き出せる読書痕跡がまだありません」。**0バイトのファイルが残るのは既知の制約**（→ 正本 §11）。残っていることを確認して控える |
| `BACKUP-05b` | Vault未選択の状態でデータ管理を開く | 2つのボタンが押せず、理由が出る。**保存先の選択が開かない**（空ファイルが作られない） |
| `BACKUP-06` | 書き出したファイルをそのまま「読み戻す」で選ぶ | 下見に新規・合わせる・上限を超えて保留する件数が出る（正常な同一データなら新規0件・合わせるN件・上限による保留0件）。**この時点でファイルは書き換わっていない** |
| `BACKUP-07` | `BACKUP-06` の下見で「やめる」 | 何も適用されない。痕跡の更新日時が変わらない |
| `BACKUP-08` | 書き出した後で同じノートに別の余白メモと訪問を追加し、その退避ファイルを読み戻す（合流後20件以内） | 下見に合わせる件数が出て、上限による保留は0件。片方のメモを置き換えるという誤った告知が無い。まだ書き換わらない |
| `BACKUP-09` | `BACKUP-08` で確定する | **両方のメモが残り、`(日時, 本文)` の重複を除いて日時順になる。** 訪問は時刻で重複排除して直近30件、`totalVisitCount` は両側の大きい方で保持件数を下回らない。本文・日時と訪問の集合を操作前後で照合する |
| `BACKUP-09b` | 重複を除くと21件になるノートと、正常に合流できる別ノートをまとめて読み戻し、下見で確定する | 下見の上限超過の保留は1件。確定しても**該当ノートの痕跡全体は無変更**で、端末側のメモが失われない。別ノートは適用され、結果の保留件数・理由が一致する |
| `BACKUP-09c` | 下見を出したままホームへ戻って同じノートを開き直し、訪問かメモを増やしてからデータ管理へ戻って確定する | 「端末側が変わったので確認し直してください」と出て、**まだ1件も書き戻していない**。作り直した下見で改めて確定すると、増えた訪問・メモを含んだまま規則どおり保存される |
| `BACKUP-09d` | 合流後20件ちょうどの組と、両側の合計は21件以上でも重複を除けば20件になる組をそれぞれ読み戻す | どちらも上限による保留0件で合流する。同じ本文でも日時が違うメモ、同じ日時でも本文が違うメモは別件として残る |
| `BACKUP-10` | 旧データの印を持つ退避ファイルを、印の無い痕跡へ読み戻す。両側に日時の異なる印がある組、同時刻の組も試す | `markedSummary` / `markedKind` / `markedAtEpochMillis` が3つ一組で保存される。片側だけならその印、両側なら新しい印、同時刻なら端末側を採る。**画面に印が再表示されることは期待しない** |
| `BACKUP-11` | **アプリのデータ・権限を消す別承認を得た場合だけ**、再インストールして同じ一時Vaultを選び読み戻す | 訪問・余白メモが規則どおり戻り、AI要約は採用した訪問累計と噛み合う場合だけ残る。**戻したノートを開いても引き当てが壊れない**（旧 `documentId` を持ち込まない）。未承認なら未検証として残す |
| `BACKUP-12` | 退避ファイルの `backupVersion` を大きい値へ書き換えて読み戻す | 「新しい版で作られています」と出て**1件も適用されない** |
| `BACKUP-13` | 退避ファイルでない `.md` や無関係なJSONを選ぶ | 「読書痕跡の退避ファイルではありません」。何も書き換わらない |
| `BACKUP-14` | 退避ファイル内の1件の `noteTitle` を書き換えて読み戻す | その1件だけが保留になり、**残りは適用される** |
| `BACKUP-14b` | 端末側の痕跡1件を、**余白メモを残したまま読み取れない状態**にして読み戻す（同名フォルダへの差し替え・権限剥奪など、プロバイダ依存の手段で `openInputStream` を失敗させる） | その1件が「この端末側の痕跡を読み取れませんでした」として保留になる。**新規として上書きされず、端末側の余白メモが残る** |
| `BACKUP-15` | 書き出し／読み戻しの走行中に「中止」を押す | 書き出しは何も保存されない。読み戻しは「途中で中止しました」＋**ここまでに適用した件数**が出る |
| `BACKUP-15b` | 読み戻しの適用中に「中止」を押し、停止待ちの表示が残っている間にもう一度素早く押す | 中止要求は1回だけ受理され、**書き手が止まってから**結果が1回だけ出る。表示件数と実際に増えた／結合した痕跡数が完全一致し、結果表示後に痕跡が増えない |
| `BACKUP-16` | 下見を出した状態でVaultを切り替え、戻ってから確定を押す | 確定できない（下見が消えている）。**別Vaultの痕跡が書き換わらない** |
| `BACKUP-17` | 退避ファイルを Vault内の `_ReadingTraces/` へ既定名のまま保存し、「読書痕跡を整理」を開く | **退避ファイルが削除候補に出ない**（ファイル名が64文字未満なので痕跡として索引に載らない） |
| `BACKUP-18` | 遠いプロバイダ（Google Drive 等）のVaultで書き出す | 進捗の件数が進み、画面が固まらない |
| `BACKUP-19` | 痕跡を数百件以上ためたVaultで書き出し、束ねている最中に画面を触る | 進捗表示が更新され続け、**中止ボタンが押せる**（JSONの組み立てでMainが止まらない） |
| `BACKUP-20` | 同じ規模の退避ファイルを読み戻し、下見の最中に画面を触る | 同上。解析中もUIが応答する |

## 後処理

- 常設検証用Vaultへ切り替えてから、ケース別一時Vaultだけを削除する。元Vaultへは戻さない。
- **書き出した退避ファイルを端末から削除する。** 読書履歴と余白メモが平文で入っている。
- 再インストールを試した場合は、常設検証用Vaultの権限を取り直す。

## 記録

ケースIDごとに入力・操作・期待・実測を対応させ、レビュー本文へ残す。
**`BACKUP-03` はJSON全体で `documentId` キーが無いことを確認し、結果を控える。**
**メモが関わるケース（`BACKUP-08`〜`09d`・`11`・`14b`）は、合成データの操作前後の日時・本文を照合する。**
合流は内容と並び順、保留は痕跡全体の無変更を確認し、件数だけで成功にしない。
下見と完了時の文言・件数も控える。過去の検証は [変更履歴](../../dev/change_history.md)、
今の作業の結果は [レビュー一覧](../README.md#レビュー一覧新しい順)を参照する。

**`BACKUP-14b` の作り方は端末とプロバイダで違う。** 再現手段が見つからない場合は
**その旨を実測欄に書き、未検証として残す** — 「成功」とも「該当なし」とも書かない。
