# 実機検証手順

**この文書が答える問い:** Vigilith AIを実機検証するとき、**どの工程を誰が持ち**、どこまでを通常操作として進め、
検証前後に何を残し、どの検証用Vaultを終了地点にするか。

実機で**何が正しいか**は各機能の正本、**どう再現するか**は本フォルダの機能別ケース、
**どれを通すか**は [実機検証（簡易版）](quick_check.md)、
**その日に何が起きたか**は最新の `docs/review/2026-*.md` と [レビュー一覧](../README.md#レビュー一覧新しい順)、
**実装の変更経緯**は [変更履歴](../../dev/change_history.md)が持つ。
本フォルダには現在の準備・操作・期待・後処理を置き、実績・修正経緯を書き戻さない。

> **既存機能の回帰確認で、見た目と手触りに触っていないなら [簡易版](quick_check.md) を使う。**
> 通すケースをスモークセットへ絞り、正常時のスクリーンショットを撮らない。
> **UIを触ったとき・新しい保証を足したとき・スキーマ版を上げたときは通し版**（変更面に対応するケースを省略しない。対象は準備1で選ぶ）。

---

## 誰が行うか

**実機検証をCodexが持つ理由は、端末を触ること自体ではなく「実装した側が期待値と合否を決めてはならない」ことにある**
（→ [L59](../../dev/lessons/L59.md)）。**判断を含まない工程はClaudeが引き受けてよい。**
検証側のトークンは、ケースを1件も判定しないうちに組み立てと片付けで削られるためである。

| 区間 | 担い手 | 中身 |
|---|---|---|
| **組み立てと配置** | **Claude** | 準備2・3・9。机上ゲート、APKの組み立て、`adb install -r`、fixtureのpush |
| **端末での検証** | **Codex** | 準備1・4〜8・10、「実機検証中」の全部、後処理1〜3。**ケースの選抜・実測・合否・起票の要否** |
| **片付け** | **Claude** | 後処理4・5。一時物と一時テストの削除、削除確認 |
| **記録の確定と検査** | **Claude** | 後処理6・7・8。片付けまで揃った `progress.md` から本文を1回で書き起こし、転記した状態で台帳検査を通してから最終報告を出す（→ [記録の確定点](#記録の確定点)） |

**引き渡しは [`progress.md` の条件ブロック](#進行チェックリスト)へ書いて行う。**
口頭の「準備できた」だけでは開始状態をCodexが確かめ直すことになり、節約が消える。
組み立て側が書くのは**基準HEADと未コミット差分のハッシュ・本体とtestのAPKのSHA先頭・`adb install -r` の結果・
一時Vaultのパスとfixtureのマニフェストのハッシュ・机上ゲートの件数**である。**中断した検証を引き継ぐ側も、同じブロックを読む。**

**Claudeが片付けに入るのは、Codexが後処理3（終了地点の確認）まで終えた後である。** 端末側の削除を先に行うと、
アプリが一時Vaultを選択したまま中身だけが消える。**削除の前に消す対象を列挙してユーザーへ一言確認する**
（「元に戻して」を全工程と読んで、検証中のfixtureを消した前例がある。バイト列は復元できない）。

**この分担はケースの中身を動かさない。** 実機で何が正しいかは各機能の正本が持ち、
判定できるのは**そのケースを実装していない側**だけである。

## 権限範囲

ユーザーから「実機検証して」と依頼された時点で、以下はその依頼に含まれる通常操作として扱う。
**途中で1操作ずつ確認を取り直さず、準備・検証・後処理の単位でまとめて進める。**

- Android Studio同梱JBRを使うテスト、lint、Debug APKの組み立て
- 接続端末の列挙、機種・シリアル・対象パッケージの確認
- Debug APKの `adb install -r`（アプリデータを維持する上書き）
- AndroidTest APKの `adb install -r` と、対象シリアル付き `am instrument` の直接実行
- 今回新たに入れた `com.vigilith.ai.test` の後処理時アンインストール（対象アプリ本体には触れない）
- 対象アプリの起動・停止、タップ、スワイプ、戻る操作
- `uiautomator dump`、`dumpsys activity activities`、スクリーンショット、ログ・検証ファイルの取得
- 対象アプリの `am force-stop`（タスクを捨てて起動経路を作り直す。アプリデータには触れない）
- 常設検証用Vault `/sdcard/Documents/VigilithDeviceReview_Home` の初回作成・選択・維持
- `VigilithDeviceReview_<feature>_<YYYYMMDD>` で始まるケース別一時領域の作成、push、移動、内容変更、削除
- SAFによるケース別一時Vaultと常設検証用Vaultへの切替
- **一時Vault内だけ**での保存・復旧・競合確認

実行環境が権限確認を必須にする場合は、`./gradlew` と対象シリアル付き `adb` の狭い接頭辞で
継続許可を求める。操作ごとの完全なコマンド列を別々に許可させない。

次は実機検証の依頼へ含めず、必要になった時点で別途ユーザーへ確認する。

- 元Vault内のノート、画像、サイドカーの変更・削除
- 対象アプリ本体の `pm clear`・アンインストール、ダウングレード、リリースAPKのインストール
- `VigilithDeviceReview_` 以外の端末領域の削除
- 端末設定、アカウント、ネットワーク、開発者向けオプションの変更
- 複数端末が接続され、対象を既存情報から一意に決められない場合の端末選択

> **実データを持つ端末で `connectedDebugAndroidTest` を使わない。** このプロジェクトの
> connectedタスクはテスト後に**対象アプリ本体をアンインストールし、アプリデータを消した**。
> 使ってよいのは破棄前提のエミュレータだけ。実機では `assembleDebugAndroidTest` までをGradleで行い、
> 対象APKとtest APKを `adb install -r` したうえで `am instrument` を直接実行する。

## 実機検証前

1. **正本とケースを読む。** 対象機能の正本で現在の定数・保証・未解決を確認し、
   本フォルダの機能別ケースから今回の差分に必要なIDを選ぶ。
   **このとき簡易版で足りるかを先に決め、選んだIDを[進行チェックリスト](#進行チェックリスト)へ書き出す**（→ [quick_check](quick_check.md)）。
   ケース表を全文読む前にスモークセットを見る — **67ケースの表を読むこと自体が費用**である。
2. **机上ゲートを通す。** `testDebugUnitTest lintDebug --offline` を実行し、失敗状態のAPKを端末へ入れない。
3. **APKを組み立てる。** `assembleDebug assembleDebugAndroidTest --offline` を通し、
   対象APKとtest APKの更新時刻を確認する。
4. **端末を特定する。** `adb devices -l` でシリアルとモデル名を取得し、以後のコマンドへ必ずシリアルを付ける。
   **シリアルは文書へ残さない**（本フォルダは追跡されるため）。複数台つながっているときだけ、どれを使うかユーザーへ確認する。
   端末の値を恒常的に固定したい事情があるときだけ、`local_config.md` を作る（`.gitignore` で除外済み。
   証跡の置き場も同様に `evidence/` を使う）。**通常は作らなくてよい。**
5. **常設検証用Vaultを開始地点にする。** `/sdcard/Documents/VigilithDeviceReview_Home` を使う。
   初回だけ作成し、アプリが読める固定の待機ノートを1件置く。ケースfixtureや証跡の保存先にはせず、
   **検証後も削除しない。** 別のVaultが選択されていた場合は最初にここへ切り替え、元Vaultへは戻さない。
6. **開始状態を記録する。** パッケージ名、常設検証用Vaultの選択、表示中ノートを文字で記録する。
   開始したことを示すだけのスクリーンショットは撮らない。
7. **ケース別一時Vaultを作る。** 端末側は
   `/sdcard/Documents/VigilithDeviceReview_<feature>_<YYYYMMDD>` とし、同名があれば中身を確認してから作り直す。
8. **ケースを分離する。** ランダム選択が検証を不安定にする場合は、1ケース1Vaultまたは一時退避で
   対象ノートを一意にする。元Vaultのファイルを移動してはならない。
9. **APKとfixtureを配置する。** 対象APKとtest APKをそれぞれ `adb install -r` し、
   一時Vaultへのpushを行って配置したファイル一覧を記録する。instrumentationは次の形で直接実行する。
   `connectedDebugAndroidTest` へ置き換えてはならない。

   ```text
   adb -s <serial> shell am force-stop com.vigilith.ai
   adb -s <serial> shell am instrument -w -r \
     -e class <test-class[,test-class...]> \
     com.vigilith.ai.test/androidx.test.runner.AndroidJUnitRunner
   ```

   **`am instrument` の前に `am force-stop` する。** `ActivityScenario` は
   `MAIN`＋`LAUNCHER` 付きのIntentで `MainActivity` を起動するので、
   **素のコンポーネント指定で作ったタスクが残っていると、その上へ積まれた1枚として
   [重複起動のガード](../../dev/features/opening_animation.md)に畳まれ得る**
   （テストがActivityの起動待ちでタイムアウトする）。タスクを捨ててから走らせれば起きない。
10. **ケース別一時Vaultへ切り替える。** SAFでフォルダ利用を許可し、対象ノートが読めることを確認する。

> **アプリの起動は、素のコンポーネント指定で行う。**
>
> ```text
> adb -s <serial> shell am start -n com.vigilith.ai/com.example.newproject.MainActivity
> ```
>
> **`MAIN`＋`LAUNCHER` 付きへ揃えない。** 揃えるとタスクの基点Intentがランチャーのものと一致するので、
> ランチャー再タップは既存タスクへ復帰し、**重複起動を畳むガードが一度も呼ばれない**
> （＝ [`LAUNCH-01`・`LAUNCH-02`](app_launch.md) の回帰を検知できない）。
> **この起動でしか作れない状態を見るために、意図してこちらを使う。**
>
> ガードが入る前は、この起動が原因でランチャー再タップのたびに `MainActivity` が積み重なり、
> 2026-08-26 の検証は1試行を判定対象から外している。**いまは積み重ならないので、この起動のままでよい。**

正本と実装が食い違う場合は、勝手に期待値を実装側へ寄せない。正本どおりの期待値でケースを実行し、
差を指摘として記録する。

## 実機検証中

- ケースIDごとに、入力・操作・期待・実測を対応させる。AIの自由出力ではなく、候補集合や状態遷移など
  アプリが保証する境界を判定する。
- 観測は下の「観測とスクリーンショット」に従う。通し版でも、操作ごとの画像取得は行わない。
- 保存が受理条件にある場合は一時Vaultへ実際に保存し、pullしたファイルを原文と比較する。
- Nano待機中も60秒を超えて無言にならない。待機を観測し、完了後にUI階層を取り直す。
- 想定外を見つけたら、その場で最小の境界fixtureを追加して再現を確定する。
  ただし実装修正は、ユーザーが修正まで依頼していない限り行わない。
- 実機だけでなく、既存テストがなぜ捕まえなかったかもコードとテストから特定する。

### 観測とスクリーンショット

**通し版・簡易版とも、スクリーンショットは原則として検証NG時のみ取得する。**
正常結果の証跡は、ケースID・操作・期待・実測を文字で残す。

| 確認対象 | 観測方法 |
|---|---|
| 文字・状態遷移 | UI階層から対象の `text`・`content-desc` を抽出して前後比較。生のXML全体を出力しない |
| 押せるか | 対象とクリックを受ける親ノードの `enabled`・`clickable`、必要ならタップ後の状態 |
| 保存・永続化 | 端末上の実ファイルの件数・内容・差分 |
| 遅延・失敗・走行中の切替 | instrumentation／[一時テスト](quick_check.md#一時テスト)の状態と結果。注入と実プロバイダの観測を区別する |
| 色・影・欠け・重なりなどの外観 | 描画テストや既存の同条件の証跡で判定できる範囲を先に確認。画像が不可欠な範囲だけ下記の例外を使う |

- **NG時も、画像が原因説明に役立つ場合だけ代表1枚を撮る。** ログやファイル差分で十分なら撮らない。
  同じNGを繰り返し撮影せず、再現条件と実測を追記する。
- **例外は、外観の合否判定自体に画像が必要なケース。** 通し版で、何を見るかとケースIDを先に明記し、
  まず代表1枚だけ取得・確認する。別テーマや修正後の比較など追加が不可欠な場合は、その理由を記録する。
  同じ画像で確認できる複数ケースは共用する。簡易版に外観ケースを混ぜない。
- 開始・終了の記念撮影、正常画面の網羅撮影、状態遷移を追う連続撮影は行わない。
  録画や別ツールでの連続画像取得へ置き換えない。手触りや演出の確認が必要なら、静止画像で保証せず別途観測方法を決める。
- 画像を省いたため判定できない外観は**未確認**と記録し、合格に数えない。

**途中再開では、対象実装・APK・条件が変わっていない成功結果を再利用する。**
再開時に読むのは[進行チェックリスト](#進行チェックリスト)だけで足りるようにしておく。
未実施・失敗・変更で無効になった範囲だけを実行し、再利用した結果と今回追加した結果を区別する。
ケース表の画像取得指定にも本節を適用し、正常時に一律で撮影する理由にはしない。

## 実機検証後

1. **必要な証拠を取得する。** 抽出したUI情報、保存後ファイル、比較結果をローカルへ取得する。
   スクリーンショットは上記の条件で取得したものだけを使い、後処理のために追加撮影しない。
2. **常設検証用Vaultへ切り替える。** SAFで `/sdcard/Documents/VigilithDeviceReview_Home` を選ぶ。
   **検証前に使っていた元Vaultへは戻さない。** 次回もこの常設検証用Vaultから開始する。
3. **終了地点を確認する。** 常設検証用Vaultが選択済みで、固定の待機ノートを正常表示できることを確認する。
4. **ケースごとの一時物だけを削除する。** 今回作った `VigilithDeviceReview_<feature>_<YYYYMMDD>`、一時退避、UIダンプを明示パスで削除する。
   **一時テスト（`*DeviceProbeTest.kt`）を書いたなら、ここで削除する** — 残ると `DeviceProbeResidueTest` が落ちて 7. を通せない。
   常設の `VigilithDeviceReview_Home` と元Vaultは削除しない。
   AndroidTest APKを今回新たに入れた場合は `com.vigilith.ai.test` だけをアンインストールし、
   **対象の `com.vigilith.ai` はアンインストールしない。**
5. **削除を確認する。** ケース別一時領域が存在せず、常設検証用Vaultと元Vaultが残っていることを確認する。
6. **結果を記録する。** 最新レビュー、未解決なら `findings.md` と `_wip/current_issues.md` を同じ作業で更新する。
   **本文を起こすのは 4・5 まで終えた後で、検査（7）はさらにその後である**（→ [記録の確定点](#記録の確定点)）。
7. **台帳検査を強制再実行する。** 文書はGradleの入力追跡外になり得るため、レビュー受付検査は
   `--rerun-tasks` を付ける。
8. **最終状態を報告する。** 片付けが済んでいないまま出すときは**未完了**と書く。
   ケースの合否、保存の有無、ケース別一時物の削除、保証していない範囲に加え、
   **「元Vaultへは戻さず、検証用Vaultを選択した状態」**と明記する。

端末から削除するのはCodexが作った**ケース別**一時物だけで、復旧不能でも問題のないfixtureに限る。
常設検証用Vaultは次回の開始・終了地点なので削除しない。
ローカル証跡は `/tmp` に置き、レビュー本文へ必要事項を転記した後は恒久資料として扱わない。

## 記録

実機レビューには最低限、次を残す。

| 項目 | 内容 |
|---|---|
| 基準 | HEAD、ブランチ、未コミット差分の有無 |
| 実行環境 | 端末モデル、パッケージ、APK種別（**シリアルは書かない**） |
| 机上ゲート | テスト件数、lint、APK組み立て結果 |
| 実機ケース | ケースID、入力、期待、実測、合否 |
| 画像 | 取得枚数（0枚も記載）。取得した場合はケースIDとNG内容、または外観判定に必要だった理由 |
| 書き込み | 実保存したか、比較方法、元データ不変の証拠 |
| 後処理 | 常設検証用Vaultの選択、ケース別一時領域削除、残した証跡。**「元Vaultへは戻さず、検証用Vaultを選択した状態」**と明記 |
| 未保証 | 実行しなかったケースと理由 |

機能別ファイルは**結果を持たない**。ケースを追加するのは、機能の正本へ新しい保証が増えたとき、
実機でしか見えない欠陥が見つかったとき、または既存ケースでは変更面を踏めないときだけにする。

### 進行チェックリスト

**検証を始める前に `progress.md` を本フォルダ直下へ作る**（`.gitignore` 済み・使い捨て）。
**1件判定するたびに埋める。最後にまとめて書かない。**

**冒頭に「条件」を置く。** 中断した検証を別のセッションが引き継ぐとき、
**前回の成功をそのまま使ってよいかは、ここだけを読んで決まる**（履歴を探し直すなら節約の意味が消える）。

| 条件の欄 | 中身 |
|---|---|
| 基準 | HEAD、ブランチ、**未コミット差分のハッシュ**（差分が無いなら「なし」） |
| APK | 本体とtestのSHA先頭、`adb install -r` した時刻 |
| fixture | 一時Vaultのパスと、**push直前の入力のマニフェストのハッシュ**（マニフェスト本体は証跡へ置く） |
| 実行条件 | 端末モデル、通し版か簡易版か、注入したもの（一時テスト・テーマ・画面の向き） |
| 証跡 | pullしたものの置き場（`/tmp` 配下） |
| 現在地 | いま何をしているか、**次の操作は何か** |

**条件が変わったら、書き換えずに新しい条件ブロックを追記して番号を振る**（条件1・条件2…）。
組み立て直し・fixtureの追加・HEADの移動は、すべて条件の変更である。

**照合は名前ではなく中身で行う。** 同じパスへ違う内容を置いても、
**ファイルの一覧も `git status --short` も変わらない**ので、
一覧だけを条件に置くと**条件番号が自己申告になり、変更検知の基準にならない**。

```bash
find <push元のfixture> -type f -exec shasum -a 256 {} \; | sort | tee /tmp/fixture_manifest.txt | shasum -a 256
```

差分は `git diff HEAD | shasum -a 256` の先頭を同じ欄へ書く。
再開する側は**両方を取り直して突き合わせ**、一致しなければ条件を1つ進める。
**マニフェストが残っていない条件ブロックの成功は継承しない** — 元の入力を確認できないためである。

**端末の現在状態は条件ではない。** 一時Vaultの中身は検証中の保存で変わるので、
条件が持つのは**push直前の入力**であって、いま端末にあるものではない。
変わった後の姿は各行の実測が持つ。

| 行の欄 | 中身 |
|---|---|
| ケースID | 選抜した全件。通さないと決めたIDも「射程外」として1行置く |
| 合否 | 成功／失敗／未実施。**どの条件で判定したかを必ず添える**（「成功（条件1）」） |
| 実測 | 判定の根拠になった値だけ。生のダンプは置かない。入力と期待はケース表を指せばよい |
| 手順の変更 | **手順を変えて回避したら、理由を1行残して起票の要否をその場で判定する**（→ [L65](../../dev/lessons.md#l65-検証側の回避は不具合の起票を止める)） |

**再利用してよいのは、いまの条件と同じ番号で成功している行だけである。**
条件が変わった行と、**条件番号が書かれていない行は成功を継承しない** — 再実行するか、
再判定が要るかを先に決める。空欄は未実施として扱う。
これが無いと、止まった検証が「だいたい見た」に化けて、省いた面と回避した面が記録に残らない。

### 記録の確定点

**日付つきレビュー本文は後から書き換えない。** 本文には後処理の結果まで要る（→ [記録](#記録)）ので、
**確定させるのは片付けまで終わった後の1回だけ**である。途中の実測は `progress.md` が持つ。

1. **Codex** が実測と合否を `progress.md` へ書き、後処理3まで終えて引き渡す。**ここでは本文を作らない**
2. **Claude** が後処理4・5を行い、**削除結果と削除確認を条件ブロックへ書き足す**
3. **Claude** が揃った `progress.md` から本文を1回で書き起こし、
   **受付簿・課題台帳・レビュー一覧まで同じ作業で揃える**（後処理6）
4. **揃った状態で台帳検査を通す**（後処理7・`--rerun-tasks`）。
   **順序を入れ替えない** — 本文より先に検査を走らせると、**今回の転記漏れを一度も検査しないまま終わる**
5. 検査が通ったら最終報告を出し（後処理8）、`progress.md` を削除する（使い捨て。恒久資料として扱わない）。
   **検査結果は最終報告へ書く**（本文を編集し直さずに済む）

**書き起こすのはClaudeでよいが、合否・未保証の範囲・起票の要否はCodexの文を変えない。**
**判定を動かす必要が出たらCodexへ戻す** — 実装した側が合否を書き換えないための線であって、転記の手間の問題ではない。

**片付けが失敗した、検査が落ちた、または途中で止まったときは先へ進まない。**
`progress.md` を残したまま最終報告を**未完了**として出し、**端末に残った一時物を課題台帳へ起票する**
（リポジトリ側の消し忘れは `DeviceProbeResidueTest` が落とすが、**端末側の一時Vaultは誰も検査していない**）。
