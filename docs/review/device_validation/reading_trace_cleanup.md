# 読書痕跡の整理（孤児掃除）の実機検証ケース

## 正本

- 判定の根拠・遮断器・削除の直列化: [reflect_reading_trace](../../dev/features/reflect_reading_trace.md) 判断14〜18
- 痕跡そのもの（欄・保存・寿命）: [reflect_reading_trace](../../dev/features/reflect_reading_trace.md)
- 共通の準備と後処理: [実機検証手順](README.md)

## 適用条件

孤児判定・削除の実行制御・整理画面を変えたときに使う。
**削除の直列化と走行中の表示は実機でしか確かめられない** — SAFの削除は同期I/Oで、
JVMのフェイクでは「キャンセルしても物理削除が巻き戻らない」という肝心の性質を再現できない。

## 検証前

- **一時Vaultに痕跡を作る。** 孤児にするノートが要る。
  - 別々のフォルダに**3件以上**のノートを作り、それぞれを開いて痕跡を作る
    （同じフォルダの痕跡がまとめて孤児になると、遮断器が保留して候補に出ない）
  - 痕跡ができたら、**そのノートだけを一時Vaultから消す**（`_ReadingTraces/` は残す）
- **削除に失敗する状況は作らなくてよい。** SAFプロバイダ次第で再現できないため、
  `CLEAN-05` は観測できたときだけ記録する。

## ケース

| ID | 入力・操作 | 期待 |
|---|---|---|
| `CLEAN-01` | オプション →「データ管理」→「読書痕跡を整理」を開く | 候補が件数付きで並ぶ。ノート名・相対パス・訪問回数が出る |
| `CLEAN-02` | 候補1件の「×」→ 確認ダイアログで実行 | 一覧からその1件だけが消える。**`_ReadingTraces/` の対応JSONが実際に消えている**（端末上のファイル件数で確認） |
| `CLEAN-03` | **候補A・Bの「×」を続けて素早く押し、両方を実行する** | **両方とも一覧から消え、どちらも復活しない**。JSONも2件とも消えている。**片方が「消えたのに一覧へ残る」状態にならない** |
| `CLEAN-04` | `CLEAN-03` の操作中に一覧を見る | 実行中の候補の記号が `…` になり、**その行の削除ボタンが押せない**（`uiautomator dump` の `enabled` で確認）。完了後は行ごと消える |
| `CLEAN-05` | 削除に失敗する状況を作れたとき | 「N件を削除できませんでした」が出て、**その候補は一覧に残る**。別の候補を消してもこの報せは消えない |
| `CLEAN-06` | 候補が残っている状態でVaultを切り替える | 一覧が旧Vaultの候補を出したままにならない（画面を開き直すと新Vaultで洗い直す） |
| `CLEAN-07` | ノートを消していないVaultで開く | 「対応するノートが見つからない痕跡はありませんでした」。**無表示にならない** |
| `CLEAN-08` | **削除の実行中にVaultを切り替える**（`CLEAN-04` の停止状態から、オプション → Vault選択で別Vaultへ） | 切替先の痕跡は1つも消えない。整理画面を開き直すと新Vaultで洗い直す。**旧Vaultの候補が残らない** |

## 後処理

- 常設検証用Vaultへ切り替えてから、ケース別一時Vaultだけを削除する。元Vaultへは戻さない。
- **元Vaultの `_ReadingTraces/` には一切触れない。** このケースは痕跡を実際に消すので、
  対象は一時Vaultの中だけに閉じる。

## 記録

`CLEAN-03` と `CLEAN-04` は**削除の実行制御そのもの**なので、合否だけでなく
一覧の件数と `_ReadingTraces/` の実ファイル件数を前後で控える。

`CLEAN-08` が見ているのは **SAF境界の下にあるVault束縛**（`ReadingTraceStore` の
`folderIndex(vaultKey)`）である。Controller 側の世代照合はJVMで固定済みだが、
**こちらは `ContentResolver` の向こう側なのでJVMテストが届かない。**
削除の実行制御を触ったときは、`CLEAN-03` `CLEAN-04` と一緒に通す。
