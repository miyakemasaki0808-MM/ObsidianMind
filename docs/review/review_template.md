# 総評の様式

**レビュアーへ渡す様式。** これに沿って書いてもらい、`review/YYYY-MM-DD-<対象>.md` として置く。

## 何を残し、何を落としたか

過去4本の総評を読み返して、**実際に何かを動かした部分**と**そうでない部分**を分けた結果がこの様式である。

| 残す | 落とす |
|---|---|
| 個々の指摘（該当箇所・再現順序・影響・修正方針） | **総合点・軸別の採点表** — 7.2→8.0→8.1→8.5 と推移したが、この数字で判断が変わった場面が無い |
| **受理条件** | **強い部分の列挙** — 「壊してはいけない不変条件」だけ残し、称賛は落とす |
| 前回指摘の判定（解消／部分解消／未解消＋根拠） | **推奨する実施順序** — 順序は `_wip/roadmap.md` が持つ。二重に持つと必ず片方が古くなる |
| 保証していない範囲 | |
| 検証コマンドと実測値 | |
| 過去の指摘と同型か | |

## 守ってほしい規則

1. **指摘の見出しは `### P1-1.` の形にする。** 受付簿の機械検査がこの形を数える。
2. **受理条件を必ず書く。** 判定基準は「**修正前に失敗し、修正後に成功するテストへそのまま落とせるか**」。
   落とせないならそれは受理条件ではなく感想である。
3. **判定は「実装が入ったか」ではなく「元の不具合を再現する順序が閉じたか」で行う。**
4. **末尾に「課題起票」節を置く。** どの指摘を起票させたいかを明示する。
   これが無かった 2026-08-01 の総評は、4件が2日間追跡されなかった。
5. **本文は後から書き換えない。** 対象コミット時点のスナップショットとして、次のレビューまで残す。
   未解決の指摘は [findings.md](findings.md) で課題台帳へ対応づけ、修正確認が済んだら受付行を削除する。
   新しいレビューを受け付けたら前の本文も削除し、過去の記録はgit履歴へ任せる。
6. **実機レビューは [共通手順](device_validation/README.md) と対象機能のケースを使う。**
   実行したケースIDと省略理由、元環境への復帰、一時物の削除を本文に残す。
