# レビュー指摘の受付簿

**この文書が答える問い:** **レビューで出た指摘を、1件も取りこぼしていないか。**

---

## なぜ要るか

「総評で問題と書いたものは課題台帳へ起票する」という規則は
[CLAUDE.md](../../CLAUDE.md) と [document_map](../dev/document_map.md) に以前からあった。
**それでも 2026-08-01 の総評の指摘4件が、2日間どこにも追跡されなかった。**
規則を2箇所へ書いても守られなかったので、**規則を増やすのではなく、
全件の処遇を1枚に並べて機械検査に載せる**形にした。

検査は [`ReviewFindingsLedgerTest`](../../app/src/test/java/com/example/newproject/architecture/ReviewFindingsLedgerTest.kt) が行う。
`./gradlew testDebugUnitTest` と CI で毎回走るので、**新しいレビューを足して受付簿を更新し忘れると落ちる。**

## 書き方

- **1指摘＝1行。** レビュー本文の `### P1-1.` 等の見出し1つにつき1行。
- **受付IDは `<レビューのファイル名から `.md` を除いた全体>/<P番号>`。** 例: `2026-08-03-image-n3/P1-1`。
  P番号はレビューごとに再利用されるので、ファイル名を含めないと一意にならない。
  **日付だけでは足りない** — 同じ日に2本のレビューを置くと別々の指摘が同じIDへ潰れ、
  受付簿を更新しなくても検査が通ってしまう。
- **処遇は空にしない。** 使えるのは下の5つだけ。
- **内容はここに書かない。** 根拠と詳細は日付別のレビューが、進行中の対応内容は
  [_wip/current_issues.md](../_wip/current_issues.md) が持つ。**受付簿は「存在と処遇」だけ。**

| 処遇 | 意味 |
|---|---|
| `起票` | 課題台帳へ載せた。**実在する課題IDを併記する** |
| `統合` | 既存の課題と同じものだったので、そちらへまとめた |
| `解消` | 対応が完了した（実機確認まで含む） |
| `見送り` | 対応しないと決めた。理由を1行書く |
| `誤検知` | 指摘が事実と違った。根拠を1行書く |

## 遡って埋めて分かったこと

**未起票だったのは 2026-08-01 の4件だけではなかった。**
`2026-07-28-code-quality/P2-3`（Android境界のテスト容易性）と `2026-07-31-code-quality/P2-5`（release構成）も、
台帳の課題（Android境界のテスト容易性・release構成）と**同じ内容が既にあった**ので実質は追跡されていたが、
**どのレビュー由来かは、この受付簿を作るまでどこにも記録されていなかった。**

**同じ指摘が版をまたいで再掲される。** 21件のうち6件は前の版の再指摘で、
P番号だけでは同一性が分からない。受付IDにレビューのファイル名を含めたのはこのためである。
