# コードコメントと経緯の置き場所

**プロジェクト:** Vigilith AI（旧 Obsidian Mind）
**作成:** 2026-09-14 / 基準 `d356b73`。**同日 `da0c414` で §4 を決着後の状態へ更新**
**この文書が答える問い:** コードにどこまでコメントを書き、設計書に何を書き、経緯はどこへ置けばよいのか。経緯を後から知りたくなったら、どう取り出すのか。

**位置づけ:** オーナーの学習用。外部の指針を調べた結果と、このリポジトリで実際に確かめた結果をまとめている。
**判断そのものは CLAUDE.md が持つ。** 規約として採ることは同日に決まり、この文書は §4 にその結果と残りを書いている。
`owner/` の他の文書と同じく検査には載せない（→ [README](README.md)）。

## 1. 背景

Fable 5.1 の評価で、本番コードのコメント密度が **28%** と指摘された。測り直すと、比率は次のように上がり続けていた。

| 時点 | 本体（コメント・空行を除く） | コメント | 比率 |
|---|--:|--:|--:|
| 2026-07-20 | 5,203 | 389 | 6% |
| 2026-08-01 | 12,435 | 2,611 | 16% |
| 2026-08-15 | 14,317 | 4,760 | 23% |
| 2026-09-01 | 17,569 | 6,758 | 25% |
| 2026-09-14 | 18,676 | 8,098 | 28% |

**09-01以降は、本体 +1,107行に対してコメント +1,340行**で、コメントのほうが速く増えている。

中身を分類すると、「なぜそうしたか」は強みとして残す価値がある。一方で、次のものが混ざっていた。

- **経緯**：日付・レビューの指摘番号・「以前は〜していた」・「何度直した」の表。約1,500行（18%）
- **設計書の写し**：KDoc 内に `##` 見出しが69個、表の行が41行
- **宙に浮いた説明**：KDoc が2つ続き、前の1つがどの宣言にも付いていない箇所が本番に9つ。長い説明と宣言のあいだに、後から別の宣言を挿し込んだのが原因

経緯を設計書へ移せば済むかというと、それも過剰だった。
設計書から経緯を落とす作業は、2026-09-12 に既に一度行っている。

## 2. 外部の指針

### 2.1 各出典の要点

| 出典 | 要点 |
|---|---|
| Google コードレビュー指針 | コメントは**なぜコードが存在するか**を書き、何をしているかは書かない。コードで伝わらないなら、コードを単純にする |
| Google 文書のベストプラクティス | コードのドキュメントには「コードが守るべき約束」を書く。文書は**小さく新鮮に保ち**、盆栽のように刈り込む。**古い文書は消す** |
| Stack Overflow Blog | コードの言い換えは価値がマイナス（読む手間が増え、古くなる）。バグ修正時のコメントは推奨するが、例は**「今も効く制約」＋課題番号**の形 |
| Chris Beams（コミットメッセージ） | 差分は「何が変わったか」しか示さない。**変更前はどうで、何が悪く、なぜこう直したか**はコミット本文に書く |
| Ousterhout『A Philosophy of Software Design』 | **コメントはコミットログではなくコードに置く**。未来の変更者はログを探さないため。複数モジュールにまたがる判断は**1箇所にまとめ、コードからは短く参照する** |
| Google のデザインドキュメント | 設計書は判断時点のトレードオフと代替案を書く場。実装後は更新されにくく、**当時の考えを知る入口**になる |
| ADR（Nygard） | 覆りにくい判断を1〜2ページで残す。**書き換えず、新しい ADR で置き換える** |
| Linux カーネル | 関数本体の中へのコメントは避け、**先頭に目的を書く** |

**コメント比率の数値目標を掲げている出典は無かった。** 問われているのは量ではなく中身である。
Ousterhout は、良いコメントには開発時間の1割程度をかける価値があるとも書いている。

### 2.2 割れている点と、その解き方

Beams は「なぜはコミットへ」、Ousterhout は「コミットではなくコードへ」と言っており、一見逆に見える。
**両者が指しているものは違う。**

- Ousterhout がコードに置けと言っているのは、**今のコードを変える人が知らないと壊す情報**
- Beams がコミットに置けと言っているのは、**変更の物語**

Stack Overflow Blog はもう1点指摘している。ファイルを移動すると `git blame` から修正の経緯を辿りにくくなる。
だから、**今も効く制約はコードに残す価値がある。**

### 2.3 置き場所の整理

| 情報 | 置き場 |
|---|---|
| 契約・不変条件（スレッド、錠の順序、戻り値の意味） | KDoc |
| 直観に反する実装の理由（外すと何が壊れるか） | コード。**現在形で1〜3行**に書き、教訓の番号（L番号）か正本へリンク |
| 複数ファイルにまたがる判断・代替案・トレードオフ | `dev/features/` `dev/system/`。コードからはリンクだけ |
| 覆りにくい判断の「なぜ」 | ADR（`dev/decisions/`、30行以内） |
| **経緯**（前はどうだったか・日付・レビューの指摘番号・何度直したか） | **コミットメッセージ**＋`change_history` に1行 |

**1文ごとの判定基準は1つで足りる。** 「今これを知らないと、次に変える人が壊すか」に当てはまればコードか正本へ置く。
当てはまらず、「過去に何があったか」ならコミットへ置く。

レビューの指摘番号（`P2-1` など）は、外部の指針が勧める「課題番号での参照」に当たらない。
このリポジトリではレビュー本文をコミットせずに消すので、**書いた時点から参照先が存在しない。**
参照先には、番号を振り直さないと決めてある教訓の番号か、正本を使う。

### 2.4 実際のコードに当てた例

`ReadingTraceController` の返事を保存する処理にある4行を当てはめると、次のようになる。

```kotlin
// 要求の所有者を、非同期へ入る前に固定する（→ L26）。                    ← 残す（制約）
// この後の load は同期I/Oで、戻る頃には別のノートを開いている場合がある。   ← 残す（理由）
// 所有者を見ずに預け直すと、Aへ書いた返事がBの痕跡へ保存される。          ← 残す（壊れ方）
// 保存先の vaultKey は既に固定していたが、失敗側だけが現在値を読んでいた。 ← 消す（経緯）
```

**削るのは理由ではなく、経緯の文である。**

冊子のカメラ距離を決める `sheetCameraDistance` の KDoc は約30行あり、「2度取り違えた」の表を持っている。
この表の中身は [L60](../dev/lessons/L60.md) と [booklet_mode](../dev/features/booklet_mode.md) に既にあるので、KDoc は次の3行に収まる。

```kotlin
/**
 * 紙の高さの [CAMERA_DISTANCE_FACTOR] 倍を実効距離にする `cameraDistance` の値。
 * `cameraDistance` は渡した値×[CAMERA_UNIT_PX] が画素で、画面密度に依らない（実測 → L60）。
 */
```

### 2.5 設計書側への示唆

外部の型に照らすと、仕様・判断・経緯は次のように分かれる。

| 種類 | 外部の型での置き場 |
|---|---|
| 現行の仕様 | 短く保ち、古くなったら刈り込む文書 |
| 判断の「なぜ」 | ADR |
| 経緯 | git |

このリポジトリの `dev/features/` は「現行の仕様」と「判断の経緯」を兼ねていることがあり、文書が膨らむ原因になりやすい。
これは文書費用全体の問題として別に扱っている。

## 3. 経緯はAIがコミットから復元できるか

**できる。** このリポジトリで実際に試して確かめた。

### 3.1 試した結果

冊子の「カメラ距離を2度取り違えた」経緯を、コメントを見ずにコミットだけから引いた。
定数名 `CAMERA_UNIT_PX` で検索すると、2件で全部出てきた。

| コミット | 本文に書いてあったこと |
|---|---|
| `3ca3ec9`（2026-09-06） | 当初は約350倍遠く、訂正時は約0.28倍近かったこと。何が根拠で間違えたか。実機で出ていた症状の正体。72倍を画素の実測で決めたこと |
| `a785da1`（2026-09-12） | 設計書からこの経緯を落とした理由。同じ内容が開発日誌にあること |

**KDoc にある表の中身は、コミット本文にほぼそのまま入っていた。** KDoc の表は3つ目か4つ目の写しであり、消しても経緯そのものは失われない。

土台も揃っている。

- 2026-09 のコミット149件のうち **143件に本文**があり、「何を・なぜ」が書かれている
- PR は**マージコミット方式**なので、個々のコミットが main に残っている
- 実機の体感やオーナーの判断は、[開発日誌](journal/) と GitHub の PR 本文にもある

### 3.2 調べ方

「〇〇はなぜこうなっているの？」と聞けば、AIは次の順で調べる。

1. 関数名や定数名が足された・消えたコミットを検索する（`git log -S`）
2. ファイル移動をまたいで追う（`git log --follow`、`git blame -C`）
3. 見つかったコミットの本文、開発日誌、PR 本文を読み合わせる
4. **コミットハッシュを添えて**まとめる（あとから原文で確かめられるように）

関数や定数1つ分なら数分で済む。「冊子機能の変遷全体」のように広い問いでも作れるが、読むコミットが増えるぶん時間がかかる。
[project_chronology](project_chronology.md) は、この方法で Git 履歴から編んだ年表である。

### 3.3 成り立つ条件と弱点

| 条件・弱点 | 対策 |
|---|---|
| **コミットに書いていないことは出てこない** | 本文に「何を・なぜ」を書く今の規約を続ける |
| **GitHub のマージ方式を squash に変えると、個々のコミットが1つに潰れる** | 今のマージコミット方式を維持する |
| ファイルを分割すると経緯を辿りにくくなる | 分割は「移動だけ」のコミットにする |
| レビュー本文はコミットしないので、指摘の原文は残らない | コミット本文に指摘の要点を書く（今もそうなっている） |
| **コミット本文に `_wip/` の項目番号を書くと、`_wip/` を廃棄した時点で意味が消える** | 番号ではなく内容を書く。設計書に課している規則をコミットにも広げる |

最後の1点は、今の運用に実際にある小さな穴である。上の `3ca3ec9` も本文の冒頭で課題番号を使っている。

## 4. 決まったことと、残っていること

**2026-09-14 にオーナー判断で規約を採った。** CLAUDE.md の必須原則に「コメント」の節が入り、文言は §3 で示した案のとおりである。

> コードコメントには「今のコードを変える人が知らないと壊すこと」だけを書く。契約と直観に反する理由を現在形で短く書き、全体の判断は正本へリンクする。
> 経緯、つまり日付・レビューの指摘番号・「以前は」・何度直したかは書かない。それはコミットメッセージが持つ。

規約と対で、検査を2つ置いた。どちらも `SourceCommentShapeTest` が持つ。

| 検査 | 落とすもの | 置いた理由 |
|---|---|---|
| KDoc が2つ続いたら落とす | 宙に浮いた説明 | 本番に9箇所・テストに6箇所あった。書いた本人には付いているように見え、読み返しでは気づけない |
| 本番コードのコメントに日付・レビューの指摘番号があったら落とす | 経緯の混入 | 14ファイル・45行から落とし、付随する「以前は」を今も効く制約の現在形へ書き直した。理由は削っていない |

**検査を置く過程で、走査テスト固有の穴を1つ見つけた。** 同じ行の中でコメントだけを直すと、クラスファイルが1バイトも変わらない。
Gradle はテストタスクを UP-TO-DATE と判定し、コメントを走査する検査が走らないまま緑になる。
`src/main/java` をテストタスクの入力に足して塞いだ。文書・`androidTest`・`res/xml` を入力に載せてあるのと同じ理由である。

同じ日に、CLAUDE.md の「同じ事件を重ねて書かない」対象へコードコメントを加え、
コミットメッセージも `_wip/` の項目番号ではなく内容で書くことにした。§3.3 で挙げた運用の穴はこれで閉じる。

**残っているのは削る範囲である。** 3本のPRに分けて進める案になっている。

1. **保守の足場。** 宙に浮いたKDoc・キャンセルの再throw・死んだ失敗枝・規約と検査2本。**実装済み。別の目のレビュー待ち**
2. **分割。** 1,000行を超える2本を責務で分け、分けたファイルのコメントを整理する
3. **上位10ファイルのコメント整理。** コメント行数の上位10本、全コメントの31%を規約に沿って整理する

**数値目標は置かない。** 見込みは全体で約22〜24%で、基準の 2026-09-14 は28%である。
コメント行数を増やさない検査も置かない。新機能の契約コメントまで抑え込み、書く先が文書へ移るだけになるためである。
