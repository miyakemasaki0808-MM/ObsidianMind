## 0. 決まったこと

### 0.1 ひとことで

**本文の隣に「この部分」という面を置く。** 今読んでいる節の余白メモ、前回の読書の跡、節の要約が集まる面である。
スマホでは ✎ で出すシート、開いた Fold では常設のペインになる。**中身と操作の契約は共有し、置き場所と表示の配分は器ごとに変えてよい。**

### 0.2 目的と範囲 — grill で決めた

| 問い | 決定 |
|---|---|
| 範囲 | Fold のペイン、余白メモの作り直し3件、プラスアルファ3件 |
| 余白メモの作り直し | 見出し名から節へ飛ぶ・書くとき本文を見せる・見出しの脇の印。段落の控えは範囲外 |
| プラスアルファ | 前回の読書の跡、この節の部分要約、2本の並べ読み |
| 並べ方 | 開いた Fold ではヒンジで半分ずつ。ペインは既定で開いている |
| シートの統合 | ✎ の余白メモのシートと部分要約のシートを1枚にまとめる |
| 全画面 | ペインは範囲外。ただし 💬 から開いたシートではメモを書ける |
| マスコット | **常駐のマスコットは撤去し、オプションも置かない**（2026-09-30）。起動時のオープニングとアイコンは残す |
| 部分要約の入口 | 見出しの ✎ ⛶ の隣に固定ボタンを置く。✎ では兼ねない |

### 0.3 操作の決定 — 設計レビューの後にオーナーが選んだ

| 問い | 決定 | 選ばなかった案 |
|---|---|---|
| 書いている途中で本文を進めたら | **書き込み先だけ固定する。** ペインは本文についていき、入力欄の上に「〇〇へ書き込み中」を出す | ペインごと固定する。本文と余白がずれ、AIの要約が見えない場所に作られる |
| 開いた Fold の ✎ | **常にペインの開閉。** 最後の状態を覚える。細部はペインを出せる窓かどうかで決まる（→ §3.4） | 閉じた Fold ではシートを出し、シートに「横に表示」を置く |
| スマホで書き始めたら | **入力を優先する。** 要約とメモを1行に畳み、本文と入力欄を残す | 上から順のまま。入力欄がキーボードの下に隠れうる |
| 前回の読書の跡の文言 | **「前回はここまで読んだ」** | 「前回はこのあたりまで表示」 |
| 部分要約の保持 | **ノートを開いている間は数節分を持つ。** 端末には残さない | 最後に作った1節分だけ |
| 並べ読みから「このノートへ移る」 | **右で読んでいた位置から開く** | 先頭から開く |

### 0.4 体感で確かめる仮説

次は採否ではなく、**強さ・順番・持続時間を試作と実機で調整するもの**である。調整しても機能の範囲は変えない。

- ペインでの並び順。今の節のメモを上に、ほかの節のメモは下に畳む
- 再会カードをペインの一番上に置くこと。長いカードが今の節への入口を押し下げないか
- 節の切り替わりの時機。スクロールが止まってからとしているが、短い節を続けて読む場合と長い節に留まる場合を比べる
- スマホのシートの高さ。書いていない間は半分としている
- 並べ読みが Fold を閉じると終わること。比較の途中で閉じたときに困らないか

### 0.5 範囲外

- 全画面でのペイン
- 段落の控え。痕跡のスキーマを上げるので別に扱う
- この部分に近いノート。今回のペインは、ノートを開いたときに作られる関連ノートの結果を使う
- 半開きの形、見開き冊子、開くと本文へ移る体験。Fold だけの体験の残りで、`_wip/feature_ideas.md` に候補として置いてある
- 質問とクイズ。断捨離で撤去する側なので、まとめたシートへは持ち込まない

### 0.6 前提

**セクションの質問とクイズの撤去が先に済んでいること。** まとめるシートは部分要約だけを引き継ぐ。
撤去より先にまとめると、質問とクイズの画面を一度作り直してから捨てることになる。

## 1. いまの Fold

- 開いた Fold で変わるのは、下のタブバーが左のレールになることだけ。`AppScaffold` が `WindowWidthSizeClass.Expanded` を見て切り替える
- 読書画面は `readerLayoutFor` が「十分に高い画面」として縦に積む。見出し、操作ボタン、再会カード、本文の順で、本文は画面中央の折り目の上を通る
- 余白メモは `MarginMemoSheet` で開く。開き切って本文を暗くするので、書く間は本文が見えない
- 部分要約は `SectionChatSheet` で開く。通常画面の入口はマスコットのタップだけで、全画面では 💬 の `FullscreenAiFab` が開く。マスコットは断捨離で撤去し、入口は見出しの固定ボタンへ移る
- 全画面は読書画面とは別のルートで、2枚のシートはどちらも本文を覆う

**材料はそろっている。** 今の節は `sectionForBlockIndex` が本文の最上端のブロックから引いている。
メモは置いたときの見出し名 `sectionTitle` を持ち、訪問記録は最も深く読んだ見出し名 `deepestSectionTitle` を持つ。
足りないのは、これらを節で突き合わせる純関数と、置き場所と、状態の契約である。

## 2. 線引き — 機能は共有し、体験は Fold 専用を許す

Fold 専用のデータや重複した機能は作らない。Fold でしか成立しない表示と操作は積極的に作る。迷ったら2つを問う。

1. **閉じたときに、書いたものや記録を失うか**
2. **保存するデータや「今のノート」が増えるか**

どちらかに当たれば機能として扱い、スマホにも同じものを置く。

| 中身 | 判定 | スマホでは |
|---|---|---|
| 余白メモ・前回の読書の跡・部分要約 | 機能 | シートに同じものが出る |
| 本文と余白が同時に見えること | 体験 | シートを半分で止めて近づける |
| 2本の並べ読み | 体験。右のノートは眺めるだけにする | 無い。閉じれば元のノートだけに戻る。右で選んでいたノートと位置は失うが、書いたものも記録も失わない |

**並べ読みの右のノートに痕跡・AI・メモを乗せると、2問目に当たる。**
このアプリは「今のノート」が全体で1つという前提で作られていて、ノート単位の状態も、自動で走る生成の門番もそこに立っている。

## 3. 画面と操作

### 3.1 並べ方と、判定の優先順

| 並べ方 | 中身 |
|---|---|
| 縦積み | 見出し → ボタン → 再会カード → 本文 |
| 左右2列 | 低い横長の画面。左に操作と再会カード、右に本文 |
| **余白ペイン** | 左に操作と本文、右に「この部分」 |

判定は上から順に当て、最初に当たったものを採る。今と同じく純関数 `readerLayoutFor` に置き、入力に折り目の情報を足す。

1. ペインを閉じている → 既存の規則で、左右2列か縦積み
2. 高さ480dp未満の横長 → 左右2列。高さの足りない窓では、ペインより本文の高さを優先する
3. 縦の折り目が報告されている → 折り目で割る。平らでも半開きでも割り、`isSeparating` が偽でも除外しない
4. 折り目は無いが横幅が Expanded → 本文領域の中央で割る
5. 横の折り目、つまり卓上の形 → 縦積み。半開きの体験は範囲外
6. それ以外 → 縦積み

- **割った後の幅が足りなければ縦積みへ戻す。** 本文320dp・ペイン280dp を下限の仮置きにし、実機で調整する
- **折り目の座標は本文領域へ直して使う。** 折り目は窓の座標で届くので、左のレールと余白の分を引いてから割る位置にする。折り目がレールの中や端に寄りすぎていれば、本文領域の中央で割る
- **キーボードの出入りで並べ方を変えない。** 今の判定は安全領域の内側の大きさを見ており、キーボードが出ると高さが縮む。そのまま条件を足すと、書き始めた瞬間に並べ方が切り替わりうる。判定にはキーボードを除いた大きさを使う
- 分割窓などで窓が狭ければ、開いた Fold でもペインは出ない。窓の大きさで決まるのであって、端末の種類では決めない
- 折り目は `androidx.window` の `FoldingFeature` から取る。このライブラリは既に依存にあり、まだどこでも使っていない。平らに開いた状態で報告されるかは、公式の説明ではなく実機で確かめる

```
┌────┬──────────────┬──────────────┐
│    │ Rediscover 💬✎ ⛶│ 再会カード            │
│    │ [ひく] [冊子]    │ ## 3. 余白に書く      │
│    │                  │ 前回はここまで読んだ  │
│レー│ ## 3. 余白に書く │ [この節を要約]        │
│ ル │ 本文…            │ 2. 線を引く へ書き込み中│
│    │ 本文…            │ [書きかけ…]      置く │
│    │                  │ ・メモ  9/20          │
│    │                  │ ▸ ほかの節のメモ 3件  │
│    │                  │ ▸ このノートの関連 3件│
└────┴──────────────┴──────────────┘
                       ↑ 折り目
```

**操作は本文の上に残す。** 低い横長の画面で操作をわきの列へ寄せたのは高さが足りなかったからで、開いた Fold は高さが十分にある。

### 3.2 「この部分」の中身

ペインでの並びを上から示す。スマホのシートも書いていない間は同じ並びで、書いている間は §3.5 の配分に変わる。

1. **再会カード** — Rediscover で引いたときだけ。ペインのときだけここに来て、スマホは今のまま本文の上に出る
2. **節の見出し** — 今の節の名前。見出しより前は「ノートの冒頭」、見出しの無いノートは「ノート全体」
3. **前回の読書の跡** — 1行（→ §3.7）
4. **部分要約** — 持っている節ならその要約、無ければ「この節を要約」のボタン（→ §3.8）
5. **書き込み先の表示** — 書き込み先が今の節と違うときだけ「〇〇へ書き込み中 · 本文を戻す」
6. **入力欄と保存の状態** — 置いても閉じない。保存中・預かり・満杯・失敗の表示は今の作法をそのまま残す
7. **この節のメモ** — 新しい順
8. **ほかの節のメモ** — 畳んで件数だけ見せる。開くと節ごとに本文の順で並び、見出し名を押すと本文がその節へ飛ぶ（→ §3.6）
9. **このノートの関連** — ペインだけ。畳んで件数だけ見せる（→ §3.9）

- **静かにするのは、この節のメモが0件のときだけ。** 何も無いことを知らせる文は置かない。要約のボタンと入力欄は残る
- **利用者が開いたものの状態は隠さない。** 読み込み中・読み込み失敗・保存中・満杯・保存失敗は出す
- **入力欄に触れている間は、上に中身が増えても入力欄の画面上の位置を保つ。** 再会カードの中身や要約は遅れて届くので、押そうとしている入力欄やボタンを動かさない

### 3.3 本文・書き込み先・要約の3つの対象

| 対象 | 何で決まるか |
|---|---|
| 本文の節 | 本文の最上端に見えているブロックの節。スクロールが止まってから確定する |
| ペインの節 | **常に本文の節と同じ。** 書いている間も動く |
| 書き込み先 | 書き始めた時点の本文の節。入力欄に文字がある間は動かない |
| 要約の対象 | 押した時点のペインの節。どの入口から押しても同じ |

- **節は見出し名だけでなく、今の本文での見出しの位置で識別する。** 同名の見出しや同じ本文の繰り返しでも、別の節として扱う。位置は今の本文の解析結果の中でだけ有効で、保存形式には入れない
- 本文が解析し直されたとき、たとえば蒸留で太字を書き戻したときは、書き込み先を見出し名と順番で引き直す
- **見出しより前と、見出しの無いノートは、表示と要約の範囲をそろえる。** 前者は「ノートの冒頭」として見出しより前だけを、後者は「ノート全体」として全体を要約する。今は見出しより前で要約を頼むとノート全体へ戻る実装なので、ここを直す
- 置いたメモの見出しは書き込み先の名前になる。書き始めたときに見ていた場所を「書いた場所」とみなす

### 3.4 入口と ✎ の遷移

**入口の表は、端末の種類ではなく「ペインを出せる窓か」で分ける。** 並べ方の判定が窓の大きさで決まるので、入口も同じ基準にそろえる。

- **ペインを出せる窓** — ペインの開閉の設定を開いているとみなして §3.1 を当てたとき、余白ペインになる窓。つまり 3 か 4 に当たり、割った後の幅も足りる
- **ペインを出せない窓** — それ以外。スマホ、カバー画面、狭い分割窓、低い横長、横の折り目、下限の幅を割る窓がここに入る

**✎ の規則は1つ。出ている余白をしまう。出ていなければ、その窓で出せる面を出す。** 面は常に1つだけで、ペインとシートを同時に出さない。

| 窓 | 出ている余白 | 操作 | 結果 | ペインの設定 |
|---|---|---|---|---|
| 出せる | ペイン | ✎ | ペインをしまう | 閉じるへ |
| 出せる | 無し | ✎ | ペインを出す。生成はしない | 開くへ |
| 出せる | シート | ✎ | シートをしまう | 変えない |
| 出せる | 無し | 見出しの要約ボタン | ペインをこのノートの間だけ出し、要約を始める | 変えない |
| 出せない | シート | ✎ | シートをしまう | 変えない |
| 出せない | 無し | ✎ | シートを出す。生成はしない | 変えない |
| 出せない | どれでも | 見出しの要約ボタン | シートを出し、要約を始める | 変えない |
| どちらでも | どれでも | 見出しの印・再会カードの「前回のメモを見る」 | その窓で出せる面を出し、該当するメモまで送る | 変えない |
| 出せる | ペインで並べ読み中 | ✎ | ペインをしまい、並べ読みも終わる | 閉じるへ |
| 出せる | ペインで並べ読み中 | 戻る | 余白へ戻る | 変えない |
| 全画面 | — | 💬 | 全画面の上にシートを出し、要約を始める。メモも書ける | 変えない |

窓が切り替わったとき。**書きかけ・書き込み先・入力のフォーカスを引き継ぎ、面は常に1つにする。**

| 切り替わり | 出ていた余白 | 結果 |
|---|---|---|
| 出せない → 出せる。Fold を開く、窓を広げる | シート | 設定が開くならシートをしまってペインへ移す。閉じるならシートのまま |
| 出せない → 出せる | 無し | 設定が開くならペインを出す。閉じるなら何も出さない |
| 出せる → 出せない。Fold を閉じる、窓を狭める | ペイン | 書きかけがあるか入力中ならシートへ移す。そうでなければ何も出さない。並べ読みは終わる |
| アプリを再起動 | — | 設定のまま |

たとえば、閉じる設定のままカバー画面でシートを出し、Fold を開いて ✎ を2回押すと、1回目でシートをしまい、2回目でペインを出して設定を開くへ変える。

- **✎ は書く入口、見出しの要約ボタンと全画面の 💬 は AI の入口。** ✎ からは生成しない
- **入口から目的の中身へ直接届く。** ✎ は入力欄へ、AI の入口は要約の位置へ、「前回のメモを見る」は該当するメモへ送る。同じ面を開くことと、同じ位置を初めに見せることは別に扱う
- **見出しの要約ボタンは、同じ節が生成中か要約を持っていれば作り直さない。** その要約を見せるだけにする
- **見出しの要約ボタンは、全画面の 💬 と同じ導出で生成中・完了・失敗を静かに示す。** 浮く通知は作らない。読み上げ名は「この節を要約」にし、撤去した自由な質問を期待させない
- ペインの開閉の設定は `AppPreferences` に置き、`NoteUiState` には入れない。ダークモードや年代の紙色と同じ扱いである
- 通常画面に浮くものは無い。常駐のマスコットは断捨離で撤去する

### 3.5 スマホのシート

- **主画面と併存する、暗幕を出さないシートにする。** 今の `ModalBottomSheet` の暗幕を透明にしても本文は操作できない。半分・画面いっぱい・隠す、の3段とキーボード時の振る舞いは、採用中の Material3 の版で確かめる
- **書いていない間は半分の高さ。** 並びはペインと同じで、中身も今の節についていく
- **書いている間は入力を優先する。** 入力欄に触れている間は、見出し・書き込み先の表示・入力欄・置くボタン・保存の状態だけを残し、要約とメモは「要約とメモ N件」の1行に畳む。置くかキーボードを閉じれば元に戻り、開いていた畳みの状態も戻る
- 本文側には、反応している数行が読める高さを残す
- **戻る操作は内側から順に閉じる。** まずキーボード、次にシートを半分へ、次にシートを閉じる。1回で読書画面や全画面から離れない
- 閉じ方は下へ払うほかに閉じるボタンを置く。TalkBack で本文・入力欄・閉じるへ移れる。拡大文字でも入力欄が見える

### 3.6 見出しの照合

- **照合の前に、今の見出しにも保存時と同じ整形をかける。** 制御文字を落とし、前後の空白を削り、512バイトで切る。保存側の `composeMemoSectionTitle` をそのまま使う。保存値は書き換えない
- 結果は3つに分ける

| 結果 | 出し方 |
|---|---|
| 一意に一致 | その節に出す。印・件数・飛ぶ先もこの結果から作る |
| 候補が複数 | 候補のどの節にも出し、「同名の見出しに共通」と添える。飛ぶときは候補を並べて選ばせ、黙って先頭へ決めない。候補は親の見出しか順番で見分けられる名前にする |
| 見つからない | 「見出しが見つからないメモ」にまとめる。本文へは飛べない |

- 見出しを持たないメモは、見出しより前か、見出しの無いノートの全体に出す
- **本文の見出しの脇の印は、件数と読み上げ名を持つ。** 色だけにしない。見た目は小さくても押せる範囲は広く取り、押すとその節のメモへ届く。メモを消せば印と件数も同時に変わる

### 3.7 前回の読書の跡

- **文言は「前回はここまで読んだ · 9/12」。** 記録されているのは画面に出たいちばん深い位置で、読み戻っても更新されない。だから「ここで止まった」とは言わない
- **見る訪問は1件だけ。** 今の読書が始まるより前の、最新の訪問である。それが最後まで読んだ訪問なら出さない。古い読みかけの訪問まで遡らない。「最後まで読んだ」の判定は再会カードと同じものを使う
- 節は §3.6 と同じ照合で決め、一意に一致したときだけ出す
- 読むのはノートを表示した後の1回だけ。同じ読書の途中で、自分の訪問に置き換わらない
- ノートの開き方を問わず出す。回数や割合は出さない

### 3.8 部分要約

- **ノートを開いている間、最近作った3節分まで持つ。** 端末には残さない。4節目を作ると最も古いものから消える。ノートを替えるか本文が解析し直されると、全部消える
- 生成は一度に1本。**生成中に別の節の要約を押すと、前の生成を取り消して新しい節を始める。** 取り消された節はボタンに戻る
- **スクロールでは生成も取り消しもしない。** 生成中に本文を進めても、できた要約は作り始めた節に入る
- 要求はノートの世代・本文の版・節の位置と組にし、届いた結果が今の要求のものかを確かめてから書く。古い要求の結果は捨てる
- 同じ節の要約を頼み直したときは、生成中ならその生成を、持っていればその要約を見せる。毎回作り直さない
- 端末 AI が使えないときの見せ方は、今の部分要約の作法をそのまま使う

### 3.9 2本の並べ読み

- ペインの下の「このノートの関連」を開くと、ノートを開いたときに作られた候補が並ぶ。**AI を新しく呼ばない。** 節ごとの推薦ではないので、節の推薦と誤解されない名前にする
- AI の推薦が後から届いても、開いている一覧の並びは入れ替えず、下へ足す
- 候補を押すと、ペインの中身がそのノートの本文に替わる。上に「← 余白へ戻る」と「このノートへ移る」を置く
- **右のノートは眺めるだけ。** 訪問を記録せず、要約も分野判定も走らせず、メモも置けない。左の読書の進捗にも右のスクロールを入れない
- **並べ読みの状態は、読み込み中・読めた・失敗の3つと、選んだ要求の番号を持つ。** 番号は並べ読みの中だけで数え、世代の層は増やさない
- **次の契機で要求を失効させ、遅れて届いた結果を書かない。** 別の候補を選ぶ、余白へ戻る、ペインを閉じる、余白ペインでない並べ方になる、ノートを替える、Vault を替える
- 読み込みの失敗は右側だけに出し、そこで再試行できる。左の読書と書きかけは止めない
- 左のスクロール位置と書きかけは並べ読みの間も保ち、余白へ戻れば元どおりになる
- **「このノートへ移る」は右で読んでいた位置から開く。** 関連タブで候補を押したときと同じ `openNote` を通り、そこで初めて普通のノートになる。訪問はその位置から始まる
- 移った後に元のノートへ戻る専用の操作は置かない。さがすタブの「今日読んだノート」から戻れる。**ただし戻るのはノートまでで、読書位置は戻らない。** 閲覧履歴は題と参照だけを持ち、位置を持たないため。困ったときだけ一時的な復帰位置を考える
- Fold を閉じたら並べ読みは終わり、開き直しても復元しない
- 右では画像の寸法の入れ物を渡さない。今のノートの読書の報告と混ざらないようにするため

## 4. 書きかけ

書いた言葉と保存先を失わないことが、この設計でいちばん壊してはいけない約束である。

- **書きかけは一組で持つ。** ノートの識別、書き込み先の節、文字、それに送信の4つである。送信は1回の保存の依頼で、中身は §4.1 に書く。文字だけを持ち上げても、書き込み先と受理の対応が切れる
- **持つ場所は画面ではなく ViewModel 側。** シートとペインの切替、通常と全画面の往復、Fold の開閉や回転による画面の作り直しをまたいで、同じ一組を使う。全画面は別のルートなので、読書画面の中で持ち上げるだけでは足りない
- 入力中の文字は、Compose の状態として同期的に持つ。StateFlow を経由させると、日本語の変換中に入力が崩れやすい
- **ノートごとに持つ。** 別のノートへ移っても、そのノートの書きかけは同じ Vault の間だけメモリに預かり、戻れば書き込み先ごと復元する。Vault を替えると捨てる。プロセスが終わったときの保護までは今回の条件にしない

### 4.1 送信と受理の対応

**受理件数では数えない。** 今の受理件数はノートの画面状態の一部で、ノートを替えると0に戻る。書きかけだけを長生きさせても、保存の結果との対応は保証できない。

**送信は4つを持つ。** 保存では本文を整えるので、入力欄の原文と、実際に保存される本文は一致しない。今の `composeMarginMemo` は制御文字を落とし、前後の空白と末尾の改行を削り、1024バイトで切る。だから用途ごとに持ち分ける。

| 持つもの | 使い道 |
|---|---|
| 送信時の原文 | 入力欄を空にしてよいかの判断。今の入力がこれと同じときだけ空にする |
| 保存値 | 整えた後の本文。**整えるのは送信を作るときの1回だけ**で、その結果をそのまま保存に渡し、照合にも使う |
| 送信の時刻 | 保存を頼んだ瞬間に1度だけ決め、メモの `writtenAtEpochMillis` に使う |
| 切り詰めたか | 受理の後も失わない。戻った後の照合で受理が分かったときも「ここまでを置きました」を出す |

- **照合は保存値と時刻の組で行う。** この組はメモを合流するときに重複を畳む鍵と同じなので、本文がたまたま同じ別のメモと取り違えない。原文は照合に使わない
- **受理かどうかは2つの道で分かる。**
  1. そのノートを開いている間に保存の結果が返る。保存・預かりなら受理、満杯・失敗なら未受理
  2. 結果を待たずにノートを離れたなら、戻ってメモを読んだときに照合する。結果は下の3つに分ける

| 照合の結果 | 条件 | 扱い |
|---|---|---|
| 一致あり | 永続・保存待ち・預かりのどこかに組がある | **受理。** 送信を消費し、入力が原文のままなら空にする |
| 不在を確認 | 永続を正常に読めたか、痕跡ファイルが無いと確かめられ、保存待ち・預かりにも無い | **未受理。** 送信を取り下げ、原文を残す |
| 確認できない | 永続を読めず、保存待ち・預かりにも無い | **未確定。** 送信と原文を持ち続け、「保存を確認できません」と出す。未保存と断定しない |

- **未確定の送信は、入力欄とは別に持ち続ける。入力を編集しただけでは捨てない。** 入力が変わっても、整えた後の本文が同じなら、同じメモをもう一度置くことになるからである。空白や末尾の改行を足しただけのとき、1024バイトより後ろだけを直したとき、編集して元へ戻したときがそれに当たる
- **ボタンの役目は、今の入力を整えた本文で決める。** 未確定の送信の保存値と同じなら「保存を確かめる」になり、新しい保存は頼まない。違えば「置く」で、別のメモとして新しく送る。整える関数は保存と同じ `composeMarginMemo` を使う。次にノートを表示したときにも自動で確かめ直し、本文を読むことと入力の編集は止めない
- **古い送信の追跡をやめるのは、保存値の違う内容を実際に新しく送ったときだけ。** 未確定の送信は1ノートにつき1件までにし、履歴は溜めない。やめた後に古い送信の確認結果が届いても、新しい入力は消さない
- 確かめて受理が分かったときも、入力欄を空にするのは今の入力が送信時の原文と同じときだけ。空白だけ直した入力も勝手に消さない
- 保存を頼む前にノートを離れた場合は、送信を作らない。書き始めた後に止められた保存は、戻ったときの照合で決まる
- **保存の結果は、ノートを替えた後も元のノートの書きかけにだけ届け、今のノートの画面は更新しない。** 結果は Vault の世代でも照合し、古い Vault の結果が新しい Vault の書きかけを消さない
- 痕跡のスキーマは変えない。時刻は今もメモに入っている欄である

### 4.2 読み込みと表示を分ける

- ペインの開閉やシートとの行き来では読み直さない。今の `open()` は読み直しのたびに世代を進めて保存の完了通知を捨てるので、表示の切替で呼んではいけない。読むのはノートを表示した後の1回だけである
- 永続済み・保存待ち・預かりの3箇所を合流する `loadMemos` の一覧は変えない
- **ただし照合には、永続を読めたかどうかも渡す。** 今の `loadMemos` は、痕跡ファイルが無いときも、破損や読み出しの失敗で読めなかったときも、どちらも空の一覧にする。一覧に無いことだけでは、不在なのか読めなかったのかを区別できない。読み込みは「正常・ファイル無し・読めない」を一緒に返す（→ [lessons L47](../dev/lessons/L47.md) と同じ形）
- **「ファイル無し」を不在として扱ってよいのは、確かめたうえでの「無し」だけ。** 今のストアは、見つからないとき索引を1回読み直してから「無し」を返す。読み直しを経ずに「無し」が返る経路があるなら、それは「確認できない」に分ける。実装時に `loadByKey` の分岐をテストで固定する

> **今のコードにも同じ危うさがある。** 今のシートは書きかけの文字を作り直しの後も残すが、送った文字と受理件数は作り直しで消える。
> 保存の最中に Fold を開閉すると、保存済みの文字が消えずに残り、もう一度置けてしまう。本設計の送信はこれも塞ぐ。

## 5. 状態とデータ

**保存するデータは増えない。痕跡のスキーマも上げない。** 読むのは既にある訪問記録とメモだけで、書くのはメモだけである。

| 状態 | 変更 | 契約への登録 |
|---|---|---|
| `MarginMemoState.Ready` | 前回の訪問の欄を足す。見出し名・日時・最後まで読んだか | 登録済み |
| 書きかけ | **新規。** ノートごとの一組と、未確定の送信。Vault 単位で持つ | `withVaultScopedReset()`。アーキテクチャの判断4の3行目と同じく、ジョブはノート単位で止め、書きかけは Vault 切替でだけ捨てる |
| 部分要約 | 1節分から最近の3節分へ形を変える。節の位置と本文の版を持つ | 登録済み |
| シートの可視フラグ | 2本を1本にまとめる | 登録済みの片方へ寄せる |
| 並べ読み | **新規。** 3つの状態と要求の番号 | **新しく登録する** — `cancelNoteScopedJobs()` と `withNoteScopedReset()` |

**メモを読む時期が変わる。** 今は ✎ でシートを開いたときに1回読み、ノートを表示する経路では読まない。遠いプロバイダでは読み込みが体感に乗るからである。
ペインは開いた Fold で常に見えていて、見出しの脇の印はスマホでも本文と一緒に出るので、**ノートを表示した後に1回読む**形へ変える。
本文は待たせない。届くまでペインと印は静かに空いている。前回の読書の跡も同じ1回で取る。

## 9. 検証

**純関数と JVM**

- 入口の遷移。狭い分割窓・低い横長・横の折り目・下限の幅の前後で、各入口が出せる面を開く。閉じる設定でシートを出したまま Fold を開き、✎ を2回押したときの面と設定が §3.4 の例どおりになる。✎ では生成は0回
- 並べ方の判定。既存の縦長・低い横長に加え、幅の境界の前後、縦と横の折り目、レールの有無、分割窓、キーボードの出入りで期待が一意になる。`ReaderLayoutTest` の表に足す
- 見出しの照合。長い見出し、整形後に同じになる見出し、同名、改名と削除、見出し無し、冒頭の各場合で、メモの件数が失われず、印と飛ぶ先が一致する
- 前回の訪問の選び方。読み進めてから読み戻った順序で「止まった」を断言しない。最新が読了でその前が読みかけなら出さない。訪問無し、今の読書の訪問の混入
- 書きかけ。節Bで書く → 節Cへ進む → Fold の往復・画面の作り直し・通常と全画面の往復の各場合で、文字と書き込み先Bが一致する。保存中に表示を替えても1回の送信で1件だけ増える。満杯と失敗で原文が残る。送った後に書き足した文字が消えない。ノートA→B→Aと、Vault 違いの同名パスで誤保存が無い
- 送信と受理。Aで保存を保留したままBへ移り、保存・預かり・失敗・保存を頼む前の取り消しをそれぞれ終端まで進めてからAへ戻る。受理だけが送信を消費し、未受理は原文を残す。保存されたメモは1件、Bの画面は更新されない。Vault A→B→A で古い結果が新しい書きかけを消さない
- 保存値と原文。空白なし、前後の空白や末尾の改行あり、落とす制御文字あり、1024バイトを超える日本語、の各入力で、結果を直接受ける場合とA→B→Aで照合する場合を通す。保存・預かりでは同じ送信の保存値が1件だけになり、入力が原文のままなら空になる。切り詰めの知らせはどちらの道でも失わない
- 読めないときの照合。永続済みで保存待ち・預かりに無いメモについて、戻ったときの永続の読み込みだけを失敗か破損にする。未受理へ落とさず、送信と原文を持ち続け、読めるようになったら元のメモを受理して重複は0件。正常に読めて本当に無ければ未受理。永続を読めなくても保存待ちか預かりに一致があれば受理
- 未確定の間の編集。実保存済みで読み込みだけが失敗した送信に対し、末尾の空白・末尾の改行・1024バイトより後ろだけの編集・編集して元へ戻す、の各操作の後にボタンを押す。新しい保存は0回で、元の送信を確かめる。読めるようになったら既存の1件を受理し、編集した入力は残る。保存値の違う内容なら新しく送れ、古い確認結果でその入力が消えない
- 部分要約。B の生成中に C を押し、B が遅れて届いても C を上書きしない。スクロールだけなら生成は0回。3節を超えると古いものから消える
- 並べ読み。B を選んで C に替え、B が遅れて届く。読み込み中に余白へ戻る・ペインを閉じる・Fold を閉じて開く。Vault A→B→A。右だけの失敗。いずれも古い本文が戻らず、右では訪問・要約・分野判定・メモが増えない
- 契約。書きかけと並べ読みを、`NoteSessionCoordinatorTest` のリセット検査の該当する側へ載せる
- **両方向。** 部分要約の生成中にメモを置く、メモの保存中に要約を始める。共存しうる2つの処理なので、片方ずつのテストでは面が空く

## 11. Claude が決めたこと

技術と細部の判断として、こちらで決めた。覆してよい。

- 操作は本文の上に残す
- 節の切り替えはスクロールが止まってから
- ✎ からは生成しない。AI の入口は要約を始める
- Fold でペインを閉じている間に見出しの要約ボタンを押したら、そのノートの間だけペインを開く。覚えている開閉は変えない
- 見出しの要約ボタンの見た目は、全画面と揃えて 💬 にする
- 並べ方の下限は本文320dp・ペイン280dp の仮置き
- 部分要約の保持は3節分。別の節の要約を押すと前の生成を取り消す
- 前回の読書の跡は、最新の訪問1件だけを見て、見出しが一意に一致したときだけ出す
- 書きかけは同じ Vault の間だけ、ノートごとにメモリへ預かる。受理は送信の時刻と保存値の組で照合する
- 照合で保存を確認できない間は、未確定の送信を入力欄とは別に持ち続ける。今の入力を整えた本文が同じなら「保存を確かめる」、違えば「置く」にする。追跡をやめるのは、違う内容を実際に新しく送ったときだけ
- ✎ は「出ている余白をしまう、無ければ出せる面を出す」の1つの規則にする。Fold を閉じたとき、書きかけが無ければシートを出さない
- 並べ読みから移った後に元のノートへ戻る専用の操作は置かない
- 並べ読みの Controller を新しく1つ作る
