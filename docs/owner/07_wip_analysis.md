**断捨離の性質を持つ課題は無くなった。** 前回あった「残す価値があるか」の行は、片付ける対象が無いまま閉じた。

### 実機1回で決まるものが5つ並んだ

2件の疑いは、どちらもコードを読んで見つけた。開いた位置の疑いは並べ読みを実装しているとき、見出しの霞の疑いは見出しの余白を直す前である。
保守の週は実機を使わなかったので、疑いのまま台帳に残っている。**どちらも実機で一度見れば、課題にするか消すかが決まる。**
検討枠の3件、つまり大規模 Vault の走査時間・ダークモードの視認性・TalkBack も同じ種類で、合わせて5つが実機を待っている。

### 保守の2回は、実機なしで閉じた

断捨離は削除が中心で、保守 No.01 は純関数と寸法の対応だった。どちらも受理条件の大半を JVM テストで言える。
オーナーはそこを見て実機を外した。代わりにレビューが反例を作り、2回とも1件ずつ捕まえた。
断捨離のほうは、撤去の見え方だけをオーナーが自分の端末で確かめている。

### レビューの2件は、同じ形だった

断捨離のレビューでは、退避の正本が「失われない」という保証をすべての欄へ広げていた。実装が守っているのはメモだけである。
保守 No.01 のレビューでは、日付だけの行を扉から落とす規則が、説明の付いた日付まで落としていた。
**前者は文書、後者はコードで場所は違うが、言葉が狙いより広いという形は同じである。** どちらも、レビューが反例を1つ作って見つけた。
レビュー自身は、同じ欠陥を繰り返した根拠は無いとして教訓を起こしていない。2回目と数えるかは判断が要る。

## 6. 横断して見えたこと

1. **実機を外すかどうかが、変更の性質で決まるようになった。** 削除・純関数・寸法の対応のように、受理条件を JVM テストで言える変更は、机上のゲートとレビューで閉じた
2. **机上のレビューが、実機の無い分の反例を作った。** 保守の2回とも、レビューが反例を1つずつ作って P3 を1件ずつ捕まえ、修正確認で解消を見届けた
3. **実機の無い間は、疑いが台帳に溜まる。** コードを読んで見つけた疑いは、実機で一度見るまで課題にも消去にもならない
4. **言葉が狙いより広い、という形が2回続いた。** 保証の書き過ぎと、除外の規則の広さである。どちらもレビューの前には、近い形を残す反例を持っていなかった
5. **撤去は、前提にしている文書の後始末までで1件になる。** 機能を消しても、その機能を前提にした実機ケースが残った。断捨離ではそれを同じ PR に入れ、実機ケースの起こし直しだけが課題に残った
