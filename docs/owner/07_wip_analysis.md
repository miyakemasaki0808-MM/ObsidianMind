## 2. 課題台帳 — 19件のうち12件は「1回の実機検証で消える」

### 性質は3種に分かれる

| 性質 | 件数 | 内容 |

| **検証待ち** — 机上では閉じている | 12 | 余白メモの11件と、ひとことの再生成1件。すべて「実機で確かめたら削除する」行である |
| **不具合** — 使う人が困る | 3 | 引用ブロックの問いを書き手の問いとして拾う／AICoreの短期回数制限で要約タブに英文が出うる／横画面で再会カードが本文を覆う |
| **保守・運用** — 開発側の負債 | 4 | R8と署名が未設定／依存が12件古い／画面見出しの全幅化が手動契約／文書費用がコードと同じ速度で増える |

**台帳は「壊れている」に答える文書だが、いま重いのは壊れているからではない。**
12件は修正コードまで書けていて、残っているのは端末に載せて確かめる1工程だけである。
**この形は前回には1件もなかった。**

### 「高4件」の読み方

一覧だけを見ると高優先度が0件から4件へ増えている。中身は余白メモの4件で、いずれも
**保存済みのユーザーの言葉を失いうる**という同じ形をしている。読めない痕跡を訪問保存が上書きする、
合流が上限を超えたときに切り落とす、重複を捨てて成功と数える、保存失敗で入力を戻せない。

**4件が同じ形をしているのは偶然ではない。** 余白メモは「溜める」ことを設計の中心に置いたので、
**溜めたものを失う経路が新しく4本生まれた。** ひとことは1ノート1件・上書きだったので、
この形の欠陥がそもそも成立しなかった。**機能の性質が、欠陥の性質を決めている。**

**古い5件は台帳自身が「別の契機を待つ」と書いている。** 未対応ではなく待機中である。
前回もここを指摘し、オーナーは「契機の列は足さず、本文で読む」と決めた（→ §8）。その判断は変えていない。
ただし**待機中5件と検証待ち12件では待ち方が違う** — 前者は契機が来るまで動かず、後者は端末1台で一斉に消える。

## 3. ロードマップ — Now が実体を持った

**前回の2つの指摘はどちらも解消した。** Reflect が Now のテーマになり、設計未決の演出は Later へ戻った。

### Now の2件

| Now の項目 | 状態 |
|---|---|
| Reflect 機能リニューアル（3本柱） | 柱1（蒸留の自由範囲）は実機検証まで完了して削除済み。柱2（余白メモ）は実装と机上ゲートが済み、**別の目のレビューと実機検証待ち**。柱3（結晶）は柱2の材料が溜まってから着手 |
| 蒸留の「読み直す観点」 | 着手条件は「要約との差を言語化できること」。まだ言語化できていない |

**3本柱は「1本ずつ終わらせる」形になっていて、これはよく効いている。**
柱1が完了して行ごと消え、いま柱2が検証待ちで止まり、柱3は柱2の実データを待つ。
**依存が直列なので、止まっている理由が一目で分かる。**

### 物差しの外で線を引いた項目が3件に増えた

Reflect リニューアル・蒸留の観点・反証の一文。いずれも「頻度×重さ」では上がらず、オーナー判断で入っている。

**これは物差しの失敗ではなく、物差しの守備範囲の話である。** 昇格基準は「ユーザーがどれだけ困るか」を測るので、
「ループを濃くするか」は原理的に測れない。**3件とも同じ理由で入っているなら、
それは例外ではなく2本目の物差しが要るという合図**かもしれない。いまは判断を保留する材料として書いておく。

### Later は「条件付き」の器のまま

5件（フォーカス文脈の関連ノート・Reflect機能群の連携・Vault規模への投資・公開可能な成果物・再会の演出）。
いずれも「実際に困ったら」「配布の意思が固まったら」「設計が決まったら」で動く。
**Later と呼ぶより「条件付き」と呼ぶほうが正確**という前回の見立ては変わっていない。

## 4. 機能アイデア — 実装が追いついて2箇所が古くなった

候補は27件から26件へ減った。減ったのは「読む面の分野の栞」1件で、
**分野はタイトルと本文からその場で分かる**という理由の取り下げである。
同じ巡で**欠番の本文を末尾の一覧へ畳んだ**のが大きい変更で、33行減り、
本文の合間に死んだ候補が挟まらなくなった。

### 足場の鮮度が2件で切れている

前回「足場行の鮮度は守られない」と書いた形が、実際に2件出ている。

- **余白メモの候補は、採用済みと書きながら足場が古い。** 「現行 `schemaVersion = 6`、v1〜v5 も読める」とあるが、
  実装は v7 で v1〜v6 を読む。**その候補自身の実装で上がった版を、その候補が知らない。**
- **蒸留の範囲調整の候補は、冒頭で「自由範囲まで実機検証済み」と書いた直後に「残るのは段階2（自由範囲）」と書いている。**
  同じ項目の中で前後が矛盾している。

**どちらも `_wip/` 側の話なので、本書では直していない**（実装と文書の食い違いは報告して判断を仰ぐ規約）。
形としては「**着手が近い候補だけが当て直される**」という前回の見立てそのもので、
**今回は着手した候補のほうが取り残された**点だけが新しい。実装中は正本（`features/`）を見ているので、
アイデア帳へ戻って足場行を直す契機が来ない。

## 6. 横断して見えたこと

1. **いま `_wip/` を止めているのは、判断でも設計でもなく「端末に載せる1工程」である。**
   台帳19件のうち12件、ロードマップの Now 2件のうち1件が、同じ1工程を待っている。
   **前回は「待っている」が見えないことが問題だったが、いまは見えたうえで全部が同じ1点に詰まっている。**
2. **待ち行列の長さが、そのまま台帳の重さに見えている。** 高4件は品質の悪化ではなく検証待ちの列の長さである。
   一覧の優先度列は「壊れている度合い」を書く欄なので、この違いは表からは読めない。
3. **机上レビューの収穫は、対象が新しいほど大きい。** 12件は書いた当日のコードから出た。
   同じ手続きを実機確認済みの機能へ当てても同じ収穫は出ないので、
   **「レビューを増やす」ではなく「新しいコードに当てる」が効いている要因である。**
4. **物差しの外で入れた項目が3件になった。** 例外が3つ並んだら、例外ではなく規則の不足かもしれない。
5. **廃止した機能の跡が1つ残っている。** 「封をした返事」の設計は、封をする対象だった返事が無くなって前提を失った。
   **2026-09-20 に据え置きで決着**し、決めるのは開発の再開後になった（→ §8）。

## 7. 提案

**Fable 5.1 が独自に出した案を含む。** 採否はオーナーが決める。費用は文書だけで済むものから並べた。

| | 提案 | なぜ | 費用 | 効く先 |
|---|---|---|---|---|
| A | **検証待ちの12件を、実機セッション1回分の順序表にまとめておく** | 12件は独立した課題ではなく1回の検証で一斉に消える。Codex が戻る前に順序と観測点を決めておけば、当日の消費を減らせる | 文書のみ | 実機検証の一発通過率 |
| B | **検証が止まっている間は、レビューを要さない作業へ寄せる** | 別の目を通すまで確定しない規約があるので、実装を積んでも検証待ちの列が伸びるだけである。文書・計測・設計の起こしはこの制約の外にある | 運用のみ | 待ち行列を伸ばさない |
| C | **柱3（結晶）の設計を、柱2の検証を待たずに起こす** | 柱3は「柱2の材料が溜まってから着手」だが、**設計を起こすのに実データは要らない**。溜まる形は正本で決まっている | 小。文書のみ | 検証待ちの期間を設計に使える |
| D | ~~**「封をした返事」の処遇をいま決める**~~ | **2026-09-20 に据え置きで決着。** 前提を失ったことは状態欄に書いてあるので、次に読む人が現役の予定と読む心配は無い | — | — |
| E | **物差しの外で入れた3件を見て、2本目の物差しを置くか決める** | 例外が3つ並び、どれも同じ理由で入っている。「ループを濃くするか」を測る軸を昇格基準へ足すか、例外のままにするか。**急がない** — 3件の決着を見てからのほうが材料が多い | 判断のみ | ロードマップの説明力 |
| F | **アイデア帳の足場行を、実装が済んだ候補にだけ当て直す** | 2件が古い。全候補を当て直すのは費用に合わないが、**実装した候補は正本ができているので当て直しが安い** | 文書のみ | アイデア帳の信頼性 |
| G | **`_wip/` の総行数を月1回測り、恒久文書の増加率と並べる**（前回から再掲） | 今月は台帳が増えても総量が減った。減った事実は測って初めて分かる | 計測のみ | 文書費用 |

**A と B は、Codex が 2026-09-25 まで使えないという前提から来ている。** 検証を待つあいだに何をするかの提案で、
待ち時間そのものを短くする案ではない。**オーナーは「いまは何も進めない」と決めた**ので、この2件は出したまま残す。
