## 2. 課題台帳 — 15件のうち3件は「残す価値があるか」の課題

### 性質

| 性質 | 件数 | 内容 |
|---|:--:|---|
| **断捨離** — 残す価値があるか | 3 | 常駐するマスコットが読書の邪魔／セクションの質問とクイズが Nano の制約で品質に見合わない／片付ける対象の無い「AI補記メモを削除」 |
| **不具合** — 使う人が困る | 3 | 引用ブロックの他人の問いを本人の問いとして拾う／先頭に BOM があるノートで最初の見出しが崩れる／冊子の扉に日付や表の見出し行が選ばれる |
| **強化・使い心地** | 2 | 関連ノートが算出した根拠を捨てている／余白メモが本文の余白に無く、書いた場所へ戻れない |
| **保守・運用** — 開発側の負債 | 7 | R8と署名が未設定／依存が12件古い／画面見出しの全幅化が手動契約／痕跡索引の作成がファイル数に比例する／文書費用がコードと同じ速度で増える／検討枠の実機3件が束ねられていない／fixture の原本を残す運用が手順に無い |

**断捨離の3件は、つながっている。** マスコットは通常画面で部分要約シートを開く唯一の入口で、そのシートがクイズを開く。
さらに、質問とクイズの代わりに置く「この部分に近いノート」は、Later にある関連ノートの推薦が止まっていた理由
「どの時点の節で推薦するか」を解く。もう1つの代わり「この部分の余白メモ」は、余白メモの使い心地の課題と部品を分け合う。
**1件ずつ見ると小さいが、束ねると Later の1件と台帳の1件を同時に動かす塊になる。** ここは一覧からは読めない。

**不具合の2件は、結晶の測定のついでに出た。** 扉の抽出器を Vault 全体へ当てたら、BOM の付いたノートの見出しが
本文の表示でも崩れていることが分かった。柱3の範囲の外なので、別の課題として起票してある。

### 出どころ — 今回は実機検証から新しい不具合が出なかった

結晶で現れた6件を出どころで分けると、次のとおりだった。

| 出どころ | 件数 | 内容の傾向 |
|---|:--:|---|
| 測定 | 1 | 本人の文が読んだノートにほとんど無い。設計の前提を変えた |
| 設計レビュー | 3 | 同じ材料での作り直し・保存中の取消・再会カードとの生成順序。1件は修正レビューでもう一度指摘された |
| 実装レビュー | 2 | 旧 Vault の走査が切替後に戻る・候補IDの表記揺れ |
| 実機検証 | 0 | 7ケース中6件合格、1件は通常の切替だけ確認 |

**再会カードのときは実機で2件が出たが、今回は0件だった。** 机上の5巡が、競合と表記の穴を先に閉じていた。
実機でしか見えない出力の性質、たとえばモデルの復唱のような形は、結晶では実Nanoの応答が素直に2行の形で返って現れなかった。

### 完了の線を、今回は「前提の外」で引いた

実機で作れなかった1件、つまり切替の前に始まった走査が遅れて返る順序は、オーナーが閉じた。
理由は検証の限界ではなく、**アプリはローカルの Vault を読むので走査が速く、遅い置き場はそもそも前提の外**というものだった。
教訓の L64 は「検証の限界をそのまま完了条件にしない」だが、今回はそれより手前で、**確かめる必要があるかを前提から判断した。**
保証していない範囲は正本の結晶 §10 に書いたので、台帳から消しても追跡は切れない。

## 4. 機能アイデア — 動いていないが、置き場が1つずれている

候補は23件のまま。結晶はロードマップから入った機能で、アイデア帳を通っていない。

**断捨離の代わりの機能2つは、アイデア帳ではなく台帳の中に書かれている。** 「この部分に近いノート」と
「この部分の余白メモ」は、作っていない機能の候補であり、アイデア帳の問いに当たる。
台帳は「何が問題か」だけを持つと冒頭で決めているので、**解決策の設計が台帳に入り込んでいる。**
着手するときに正本の設計書を起こせば解消するので急がないが、それまでに候補の検討が進むなら置き場を分けたほうがよい。

## 5. Fable 5.1 検討枠 — 未検討6件のうち3件は、今回も実機に載らなかった

## 6. 横断して見えたこと

1. **計画の作業が、割り込みと同じ速さで閉じた。** 前回は再会カードの割り込みが2日で閉じた。今回は計画の柱3が3日で閉じた。
   どちらも、設計を起こしてから机上レビューで競合を先に潰し、実機を最後に1回だけ当てる形だった。
2. **机上レビューが、実機の役割の一部を肩代わりし始めた。** 結晶では実機から新しい不具合が1件も出なかった。
   保存中の切替や遅れて返る走査のような順序は、実スレッドやスケジューラで JVM の上に作れるようになっている。
3. **断捨離は、足すことより判断が重い。** 3件とも撤去の範囲と波及を台帳に書き込むほど厚い。
   撤去は契約・文書・テストの削除を伴い、CLAUDE.md が例に挙げるテストまで入れ替えが要る。
4. **実機ケースの形を見る検査が、書いた側で走っていなかった。** Codex が回した文書検査は受付と設計書の4本で、
   新しい実機ケースの見出しや代表セットを見る検査は含まれていなかった。取り込むときに落ちて整えたので実害は無い。
