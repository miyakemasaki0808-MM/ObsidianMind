## 2026-09-01〜02 — 見た目に「チャネル」を割り当てる

冊子と通常表示が見分けられない、という実感から始まった。
案を出すと**どれも「もう1本、色か形か動きを足す」形**になり、4件が同じチャネルを取り合っていた。

そこで**意味を1対1に固定した**（→ [bearing_channels](../../dev/system/bearing_channels.md)・ADR-0005）。

| チャネル | 表すもの |
|---|---|
| 色 | 年代 |
| **形** | **面の役割**（眺める・読む） |
| 位置と本数 | 分類 |
| 書体と行間 | **何も表さない** |
| 動き | 出来事の強度 |

冊子と本文の見分けは**形**が引き受ける。角が立った紙・四辺の余白・背後に控える縁が「眺める面」、
丸いカードが「読む面」である。値を変えるだけだと**次に誰かが「揃えたほうが綺麗」と言った瞬間に戻る**ので、
役割トークンとして持ち、どの面がどちらを引くかを検査（`BearingChannelTest`）で固定した。

### 走査を狭めたら、今度は狭すぎた

その検査の受理条件を、最初は「ソースにその名前があること」で書いた。**L55 の2度目である。**
名前があることは、その面がそう描かれた証拠にならない。**代入と呼び出しの形まで狭めた。**

### 規格を、自分の判断の補強に使ってしまった

束の縁を全10枚へ出す判断に「WCAG 1.4.1 の対象になる」と理由を足した。
**1.4.1 は色だけで情報を伝えることを禁じる基準で、形はむしろ代替手段の側**である。
**製品判断としては正しかったのに、適合必須の基準で補強したせいで理由のほうが誤りになった。**
「その基準を外しても結論は変わるか」を先に問えば足りた。 → [lessons L57](../../dev/lessons.md#l57-製品判断を適合必須の基準で補強しない)

## 2026-09-03 — 繰る手触りに持ち主を与える

「動き」のチャネルが**出来事の強度**と**操作への追従**の2つを抱えていたので、二分した。
そのうえで冊子のページ送りに手触りを与えている。

### 「通ったか」を契機にすると、速い経路で一度も起きない

新しい束を引いたときに紙が一度傾いて置き直される演出（積み直り）を、
**「読込中を通ったか」**で起こしていた。キャッシュから返る経路は読込中を**通り過ぎてしまう**ので、
同じ操作なのに再生されたりされなかったりする。

**中間状態は届くとは限らない。** 契機を**束の世代**（値そのもの）に置き換えた。
→ [lessons L58](../../dev/lessons/L58.md)

## 2026-09-06 — 曲がるのは紙ではなく、めくる動作だった

「**紙が曲がる感じが足りない**」と言われ、**紙全体を弓なりに曲げる**版を作った。
記録した絵を8枚の帯に切り、帯ごとに角度を変えて積む方式で、
**幾何の純関数・画素の検査・エミュレータでの確認まで通した。**

**狙いは別だった。**

> 紙をカールさせるんじゃなくて、**捲った時にカールさせたい**。
> ページをめくる時に、**右下から左上にめがけて捲るイメージ**

本のページは全体としては曲がらず、机に置かれたまま**角を持ち上げたところだけが折り返り、
折り目が斜めに走る。** 作り直して、速さも「ゆっくり紙をめくる」620ミリ秒に落ち着いた。

**「カール」も「曲がる」も両方に当てはまる。** 分かれ目は「**どこが動かないか**」（紙全体か、折り目の向こうか）で、
**そこは普通、言葉にされない。** 聞き返しても「曲がってほしい」としか返らない。
**エミュレータで撮った画を見せたら、1往復で決着した。**

> この件は一度 L62 として教訓カードにしたが、**翌日オーナー判断で取り下げた** —
> 滅多に起きない形なので教訓に置かない、という判断である。日誌には出来事として残す。

## 2026-09-08 — 実機検証を安くし、教訓を棚卸しする

### 費用を測ってから運用を変えた

中断の直接の原因は利用枠だが、**何にどれだけ使っているかを誰も測っていなかった。**

| 費用 | 実測 |
|---|---|
| スクリーンショット1枚 | 約2,400トークン |
| UI階層の生ダンプ1回 | 1,400トークン（**テキストだけ抜くと26トークン**） |
| 冊子のケース表を読む | 約12,000トークン |

冊子の67ケースのうち**6割は機械が判定できる面**で、そこに人間向けの観測手段を使っていた。
**通すケースを絞る[簡易版](../../review/device_validation/quick_check.md)**を用意し、
スモークセットの選抜規則（入口・契約2箇所・不可逆な書き込み・実機でしか見えなかった欠陥）を決めた。
**簡易版はスクリーンショットを撮らない** — 見た目が判定の手段になるのは佇まいのケースだけなので、
そこは射程外にした。

使い捨ての一時テストは `*DeviceProbeTest.kt` と名付けさせ、**残っていたらJVMゲートが落ちる**
検査（`DeviceProbeResidueTest`）を置いた。**赤くなるのは「作ったまま終えた」ときだけ**である。

### 教訓62件を数え直したら、49件だと思っていた

棚卸しのために全件を通読した。**最初に数えた「49件」は索引の行数**で、
`L1`〜`L16` が1行に畳まれていることを見落としていた。実数は **62件**（カード36・索引内26）。
検査の件数も同じ理由でずれており、**畳まれた行は検査列を持てない**ので
`L7`・`L9`・`L13` が「検査なし」に見えていた。

**目録を作る作業自体が、目録の数え方を間違える。** 8月10日に索引を作った編集で番号を振り直した
（→ L33）のと同じ場所である。

### 役目を終えた教訓を2件畳んだ

- **`L12`** — 前提だった「モデルに実際に何を渡したかを見る手段が無い」が計測器の投入で解消
- **`L15`** — 「抑制するかゲートに載せるか」という**二択の立て方そのものが誤り**だった

どちらも**本文が自分で「終わった」と書いていた。** 行ごと消す取り下げ（前例 `L62`）は使わず、
**転送**へ置き換えている — 生きた参照が2箇所あり、消すと壊れるためである。

`L7`（整理した≠境界が効いている）・`L9`（テストが緑≠検証条件が実物）・`L10`（組み立つ≠動く）は

索引は「いつ当てるか」で引くので、まとめると1行に引き金が3つ並んで引けなくなる。
**統合せず、相似のまま維持**と決め、骨格と再検討条件を `L7` に書いた。
この形で数えると同型の教訓は14件あり、**まとめると索引そのものが機能しなくなる。**

## 2026-09-09 — 分野の色を、フォルダではなくAIに決めさせる

「冊子が真っ白になるのがなんか微妙。カテゴリで色分けみたいなものはできないか」という 09-06 の実感が起点である。
色を使えるのは冊子の面だけで、読む面の地色は年代が持ち切っている。だから冊子に限る。

**最初の案はフォルダ名で決めるものだった。** オーナーの Vault はフォルダが分野を表しているので、それで足りる。
**それでもAI段を作ると決めた。** フォルダが無い Vault でも成立させたいためで、フォルダは判定ではなく**ヒント**へ降ろした。
語彙は一般語彙6つに Vault 別の追加語彙を継がせ、追加語彙は親の色を継ぐので色は6つを超えない。

設計だけで3巡のレビューを受け、7件・5件・1件を設計で閉じてから実装に入った。
**分類は3値で持つ。** 未判定・暫定・確定で、確定でも本文やヒントや語彙が変われば入力版が変わり、再判定する。
入力指紋にはAIへ実際に渡したものをすべて入れる。**この鍵の設計は、翌週には要約のキャッシュ案が先例として参照する**
ものになった。

### 実機検証が踏んでいた不具合が、9日後にオーナーの端末で出た

同じ日、ランチャーのアイコンを再タップすると起動OPがもう一度走る、という体感が上がった。
`launchMode` を持たないので、素のコンポーネント指定でタスクが作られているとランチャーの Intent は既存タスクと一致せず、
新しい `MainActivity` が上へ積まれる。積まれるたびに OP が再生され、戻るボタンでは1枚ずつ剥がれるだけでアプリを抜けられない。

**Codex は 08-26 の実機検証でこれを踏んでいた。** 「新しい Activity が起動され下見画面が失われた」として
その試行を判定対象から外し、手順を変えて先へ進んでいる。台帳へは来なかった。
**回避は検証を進めるための正しい判断で、消えたのは起票の契機のほうである。**
手順を変えたら理由を1行残し、起票の要否をその場で判定する、という当て方を教訓にした → [lessons L65](../../dev/lessons.md)。

ガードは `onCreate` の先頭で「タスクの最初の1枚ではなく、受け取った Intent がランチャーのもの」なら畳む。
`launchMode` は変えない。変えるとランチャー再タップは別の経路へ回り、**ガードは呼ばれないまま残って死ぬ**。
アプリもテストも緑のまま。だから `LauncherEntryTest` がマニフェストを見て前提を固定する。
実機検証の起動コマンドも素のコンポーネント指定を**意図して残す**ことにした。揃えるとガードが一度も呼ばれない。

## 2026-09-10〜11 — 直した状態を、別の書き手が戻す

実装は7コミットで済んだ。壊れていたのはその後で、レビュー4巡で出た指摘のうち2つが形として新しかった。

**返事が別のノートへ保存されていた。** 返事の保存は同期I/Oで、戻る頃には別のノートを開いていることがある。
保存先の Vault キーは開始時に固定していたが、失敗側の預け先だけが「いまのセッション」を読み直していた。
Aへ書いた返事がBのひとことと組になり、Bのサイドカーへ入る。
要求の所有者を非同期へ入る前に固定し、預ける前に照合する。所有者が違えば預けず「保存できなかった」と言う。
別のノートへ混ぜて「保存できた」ことにするより正直だからである。**成功側だけを固定して失敗側の後始末を取り残す形**は、
L26 の型として正本へ書いた。

**降格は効いていたのに、次の走査で戻った。** 本文が変わって入力版が失効したら、確定をヒントの暫定へ落とす。
その処理は正しく動いていた。だが同じ索引には Vault 走査という別の書き手がいて、走査は永続から読んだ確定を
そのまま補完材料にしていた。ストアの再読込もAIの生成も要らずに、確定が戻る。

降格単体のテストは緑だった。検査が「操作 → その直後の値」で終わっていて、**もう片方の書き手を1回も走らせていなかった**。
設計書は書き手が3つあると数えていたのに、検査を1つの書き手で閉じていた。
走査は本文を読めないので入力版を照合できない。**判定できる側が材料のほうを削る**形にして閉じた
→ [lessons L66](../../dev/lessons.md)。

小さい発見がもう1つある。有効な確定のときは索引へ書かない、という契約を**値ではなく書き込み回数**で検査した。
値だけを見ると素通りする。書けば画面が再描画され、ノートを開くたびに色が一度ヒントへ点滅する。

## 2026-09-12 — 外からの評価を受け止める

前日、Fable 5.1 に「今のコード・文書の状態を一気に分析し、様々な観点で評価報告書と課題を作る」と依頼した。
8軸の採点と課題候補29件が返り、**報告書本体は git 管理外の特別枠**にして、処遇だけを `_wip/` の検討枠で追うことにした。
台帳へ起票せず枠で追うのは今回限りの運用で、枠が「消す前に決め切る」規則を自分で持っている。

### 保証がソースにはあり、成果物には無かった

報告書の最重要指摘は、マージ後のマニフェストに `INTERNET` と `ACCESS_NETWORK_STATE` が入っていることだった。
出どころは ML Kit GenAI が推移的に引く `transport-backend-cct` で、アプリ自身は宣言していない。
「ネットワーク権限を持たない」という ADR の保証が、端末に入る APK では成立していなかった。
通常権限なのでインストール時に黙って付与され、設定画面には「インターネット」と出る。

依存からは外せない。`exclude` するとクラスごと消えて実行時に落ちる。**権限だけを `tools:node="remove"` で除く。**
モデルDLと生成は AICore アプリが別プロセスで行うので、こちら側の権限は要らない。

**危ないのは混ざったことより、混ざったのに誰も気づけなかったこと**である。依存を1つ足すだけで再発する。
だから人の注意ではなくビルドで数える。`INTERNET` を名指しで禁じるのではなく、期待する権限集合と双方向で突き合わせる。
片方向だと次に別の権限を持ち込む依存を素通しし、`remove` が AICore の権限まで巻き込む事故も落とせない。
見たいのはソースではなくビルド出力なので、JVM テストではなく Gradle タスクにした。
debug は Lint の途中で走るが、release は CI がビルドしないので、名指しで呼ぶ。

実機では既存モデルで13プロンプトの生成、前面5分と背面5分の連続観測、機内モードの3経路が通った。
モデル未DLの端末が無いので、モデルDLの確認だけは契機待ちにした。確かめるために未DL状態を作りにはいかない。

### 文書費用を3手で減らす

報告書のもう1つの指摘は、Markdown の行数が製品コードの本体行数とほぼ同じで、直近200コミットの52%が文書だけ、というものだった。
台帳が自分で「過剰な検証の実体は検査ではなく文書の量」と診断していたとおりである。

3手を当てた。ヘッダの検証内容を落として日付とコミットだけにし、32本で2,938字が1,104字になった。
ただし「突合していない範囲」だけは残した。検証した範囲は他所から引けるのに対し、検証していない範囲はヘッダにしか書かれておらず、
正本の鮮度を見る唯一の手がかりだからである。
設計書2本から経緯と死んだレビュー番号を落とし、冊子の正本は1,067行から920行になった。
横送りから天綴じの半回転、そして折り目へと4度作り替えた経緯は、この日誌が持てば足りる。
教訓の追加条件を「同じ形の失敗を2度したとき」へ戻した。旧条件の「1度でも構造上また起きる」は実質いつでも真で、

## 2026-09-13 — 「良くなった」を言える物差し

抜粋を「後ろ捨て」から「真ん中捨て」へ変えた判断は理屈としては正しいが、良くなったことを示す測定は無かった。
予算調整は「効果が測れなかったため打ち止め」と記録され、要約の強化案も関連ノートの精度改善も、
効果測定の手段が前提だと自分で書いている。**「良くなった」を言えないことが、次の一手を全部止めていた。**

### 素の文字bigramでは逆転した

採点にAIは使わない。検査が被検査と同じ弱点を持つためである。最初の実装は文字bigramの包含率だった。
固定コーパスへ当てたところ、最も強く出た捏造文が 0.400、最も弱い忠実文が 0.211 と**逆転した**。
助詞と語尾のbigramが値を作っていたのと、裏付けを単一セクションとの一致で測っていたので正しく統合した文ほど低く出ていた。
ひらがなを除いた連続を語とみなし、裏付けは前処理した原文全体に対して測る。両方を直して初めて分離した。

### 人の参照で決めた閾値は、実機の出力に移らなかった

人が書くと原文の語を使い回すので、忠実な文の裏付けが高く出る。Nano は言い換えるので低く出る。
そこで実機が返した要約10本を取り込み、38文に忠実さのラベルを付けて較正し直した。
結果、**実機の出力では忠実な文と誤りの文を閾値で分離できない**。忠実の最小が 0.292、誤りの最大が 0.440。
閾値は動かさず、その事実を検査で固定した。「裏付けが弱い」は手がかりであって合否ではない。

### 13回目で断られた

実機で27組を順に生成していると、**12回成功した直後の13回目が `ErrorCode 9 / BUSY` で拒否された**。
拒否は直前の成功の32ms後で、モデルは動いていない。2回とも同じ位置で起きた。
SDK には長期利用枠とバックグラウンド拒否に別コードがあり、返ったのは短い時間窓の回数制限と読むのが妥当である。
窓の長さは AICore の内部にあり、特定しない。

対策は「同じプロンプトを2度生成しない」。27組のうち12回が同じプロンプトの再生成で、13回目に拒否されたプロンプトは
40秒前に成功したものとバイト単位で同じだった。生成は決定的なので再生成は情報を増やさず枠だけを使う。
実機の計画を純関数に切り出し、失敗した組を含む残りを続きから採れるようにした。
9生成と6生成を約210秒空けて実行し、全27組を重複も欠落もなく取得した。

**「上限（連続12回）」と書きかけて、口頭のレビューで直した。** 全端末に共通する固定の上限と読める。
実際は計測テストの条件で2回観測した境界であり、そう書き直した。
アプリ本体でも同じ境界に届きうる。ノートを開くたびに自動生成が最大3本走るからで、
要約タブに SDK の英文がそのまま出うる件を台帳へ申し送った。本体で何冊目に出るかは測らない、というのがオーナー判断である。

## 2026-09-17〜18 — 要約を端末に残し、当たったことを観測できる形にする

主軸の要約は、開くたびに数十秒走ってその間ずっとAIの錠を持っていた。押した操作はその後ろで待つ。
**保存すれば済む**と分かったのは、生成が決定的だと確かめた後である。SDK の既定値は `temperature=0`・`seed=0` で、
実機でも同じプロンプトからバイト単位で同じ要約が返っていた。**保存済みを出しても画面に出るものは変わらない。
変わるのは待ち時間と錠の占有だけ**なので、迷う余地がなくなった。

鍵は部品の組ではなく**完成したプロンプトそのもののハッシュ**にした。分野判定は部品を並べてプロンプト版の定数を人が上げる形だが、
その定数は上げ忘れる。完成品を鍵にすれば、どこを変えても鍵が変わる。

### 「当たった」を、当たったと言える方法がなかった

外部レビューがここを突いた。**保存ファイルの名前と更新時刻は、同じ入力を生成し直しても同じように変わる。**
つまり「毎回生成する」という回帰が、実機ケースでは合格に見えてしまう。観測できるのは
「その要約のために生成を呼んだか」だけなので、Debug APK でだけ要約のクライアントを包み、
呼ぶたびに本文もタイトルも載せない1行を logcat へ出して、その行数で判定する形にした。

再起動の試行にも同じ落とし穴があった。起動直後に出たノートの要約の後から数え始めると、
**失われた保存をその生成が補った後から数える**ことになり、開き直したノートが当たって0行で合格する。
全ノートを保存済みにしてから、起動の前に数え始める手順にした。実機7ケースは成功で受理し、
AICore の回数制限（BUSY）の文言だけは観測できないまま受理してある。**起こしにいくために生成を投げ続けることはしない**と決めてある。

## 2026-09-18 — 自動で走るAIを「留まってから」にする

Fable 5.1 が `_wip/` を外から読んで出した提案のうち、製品の振る舞いを変えるものが1件あった。
**読書痕跡は「10秒読んだら訪問」という門番を持つのに、AIは0秒で走る。**
冊子から「これを読む」で開いて数秒で捨てるノートにも、要約・分野判定・再会カードの要約・関連ノートの推薦が動く。
錠を占有し、AICore の短い時間窓の回数制限も使う。オーナー判断で採用になった。

**起動の契機はずらさなかった。** 調停側で呼び出しごと遅らせると、保存済みの要約と生の再会カードまで数秒遅れる。
前日に入れたばかりの保存が台無しになるので、待たせるのは**生成を呼ぶ直前だけ**にした。
分野判定の索引の照合も、AIを呼ばないので門番の手前に置いてある。

**「留まる」は足し算にしなかった。** 冊子を見ている間と背面にいる間は数えず、戻ったら3秒を最初から数える。
足していくと、冊子をめくって戻った直後に生成が始まる。読書時間は足し算で測るのに、こちらは数え直す —
測っているものが「読んだか」ではなく「いま居るか」だからである。

### 変異を15通り当てて、2つがすり抜けた

門番の各行と4本の配線を1つずつ壊して、どれかのテストが落ちることを確かめた。13は落ち、2つが緑のまま通った。
どちらも `started`、つまり「本文がまだ出ていない」を見ているフラグだった。
**アプリは起動のたびに `onStart` で復帰の合図を送る。** ノートを読み込む前にも届くし、
次のノートを読み込んでいる最中にも届く。フラグが無いと、そこで数え始めてしまい、本文が出た時には門が開いている。
テストを2本足して両方を落とせるようにした。**不要に見えるガードは、当てる変異を思いつけていないだけのことがある。**

実機では本文が出てから生成開始まで3.0秒、初回の要約が出るまで10.7秒だった。
245ms で切り替えたノートは1回も生成せず、冊子で10.1秒めくる間も生成しない。戻ってから数え直して生成する。
3秒という線は、この実測のままオーナーが受理した。
