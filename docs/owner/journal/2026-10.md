## 2026-10-01 — 平らに開いても、折り目はある

「この部分」の段1は、並べ方の判定と、ペインの枠と、`✎` の遷移だけを入れる段である。中身は今の余白メモをそのまま入れる。

### 公式の説明より、端末の報告を信じる

並べ方は折り目で割る。問題は、平らに開いた Fold が折り目を報告するかどうかだった。
報告されなければ、中央で割るしかない。設計の段階では、ここを「実機でしか決まらない前提」として残してあった。

測ると、平らに開いた Pixel 10 Pro Fold は `FLAT` のまま、`isSeparating` が偽の縦の折り目を報告した。
**平らでも半開きでも割り、`isSeparating` で除外しない**、と決められた。

### 最初の実機は、2件で落ちた

1件目は、書きかけが窓の形ごとに別々の値へ戻ったことだった。原因は Compose の保存値の置き場所である。
`rememberSaveable` は呼び出した位置で保存先を決め、その位置には前にある兄弟の数も入る。
外殻はレールの形とバーの形で本文を組み立てる位置が揃っておらず、Fold を開閉するたびに別の保存先を引いていた。
**どの形でも、本文を最初の子として同じ位置で組む**ように直し、`AppScaffoldContentSlotTest` で構造を固定した。
振る舞いのほうは、作り直しを通す instrumentation が見る。

2件目は、本文が折り目をまたいで描かれたことだった。窓は852dpあるが、左のレールと余白で約100dpを取られ、
折り目で割った本文は約318dpになる。仮置きの下限320dpを割るので折り目では割れず、本文領域の中央で割る道へ落ちていた。
中央は折り目とずれるので、本文と見出しの操作が折り目をまたぐ。
下限は実測から300dpへ下げ、本文領域の中で折り目に割れないときは中央へ逃げずに縦に積むようにした。
再検証で通り、PR #88 でマージした。

## 2026-10-02〜03 — 閉じたシートは、開けなかった

段2で、書いた言葉を扱う部分がまとめて入った。書きかけと送信の照合、本文の節への追従、見出しの照合と件数の印、
本文と併存するスマホのシートである。設計レビューで5回書き直した照合を、初めてコードにする段だった。

### 書きかけは、画面の状態の外に置いた

書きかけをノートごとに持ち、Fold の開閉や全画面の往復をまたいで残すには、画面より長く生きる場所が要る。
素直に置けば、アプリの状態をまとめた1つの型の中である。ただし入力中の文字をその経路で描くと、
**日本語の変換中に入力が崩れやすい。** 打った文字が1フレーム遅れて戻り、変換の途中の状態と食い違う。

オーナーの判断で、書きかけは文字・書き込み先・未確定の送信の一組ごと、状態の型の外へ出した。
ViewModel が Compose の状態で持ち、Controller は口だけを通して読み書きする。一組で持つのは、文字だけを外へ出すと、
書き込み先と受理の対応が切れるからである。

### 机上で5件、実機で6件

コードのレビューでは5件が出た。いちばん分かりやすかったのは、見出しの照合が Main の上で二乗に走っていた件である。
見出しを1万件並べたノートを手元の JVM で測ると、メモが0件なら160ミリ秒、20件なら2.7秒かかった。
照合のたびに見出しを数え直していたので、見出しの索引を本文の解析と一緒に Main の外で1回だけ作るようにした。

実機は5つの条件を重ね、その間に6件が出た。どれも机上では見えない種類だった。

- 閉じたシートから、見出しの印や「前回のメモを見る」を押しても開かない
- キーボードとシートが出ると、残る高さを上の操作が使い切って本文が消える
- Fold を開く方向だけ、入力のフォーカスが外れる
- ペインで書いている間も、再会カードとキーボードで本文が消える
- 閉じたシートの白い面とハンドルが、下端に覗く
- 印の UI テストが、閉じたシートから開く本番の経路を踏んでいなかった

### 効果が、自分を取り消していた

閉じたシートが開かない件は、原因の見当が付くまで時間がかかった。
閉じたシートで印を押すと、「シートを出す」と「広げて送る」の2つの依頼が同じ再構成で届く。
広げる依頼の保留を効果のキーにしていたので、保留が立った瞬間に効果が組み直され、**先に始めた半分への動きごと自分で止めていた。**
保留は1本の見張りが受けるようにし、広げる動きは子に任せた。

フォーカスの件は、順序の問題だった。Fold を開いた直後は、窓の切り替わりを判定するより先にペインが組まれ、
しまう途中のシートと一瞬だけ並ぶ。両方がフォーカスを取りにいき、後からしまわれるシートが持ち去っていた。
**フォーカスを取ってよいのは、出ている面だけ**にした。

条件5で選抜の10行が成功した。確かめていない範囲は消さずに段3の実機検証へ送り、オーナーが段2の完了の線を引いた。
途中でオーナーは、ノート画面の見出しがボタン3つに押されて窮屈に見えることにも気づき、別の課題として台帳へ入れた。PR #89 でマージした。

## 2026-10-03 — かけ直すと変わる整形

段3は、前回の読書の跡である。前回いちばん深く読んだ節に来ると、「前回はここまで読んだ · 9/12」の1行が出る。
訪問の記録はもうあるので、読むだけの小さな段のはずだった。

### 訪問の側だけ、整えていなかった

前回の訪問の見出し名を今の見出しと照合するので、訪問がどう記録されているかを読んだ。
すると、メモの見出し名は保存の前に整えて上限で切っているのに、**訪問の見出し名だけは生のまま**保存していた。
痕跡の検証は見出し名を512バイトまでに限るので、それより長い見出しの節まで読むと、保存が検証で弾かれる。
失敗した訪問は次の機会に書き直すが、同じ見出し名なので毎回失敗する。そのノートの訪問は二度と記録されない。

使っていて気づく種類の不具合ではない。日本語で約170字の見出しは珍しく、壊れても何も表示されないからである。
段3の材料なので、台帳へ入れたうえで同じPRに別のコミットで直した。

### 整形は、冪等ではなかった

実装レビューは2件を返した。1件目は、直した照合のほうにあった。
保存値と旧い生の見出し名の両方を扱うつもりで、照合の前に保存値へもう一度整形をかけていた。
ところがこの整形は前後の空白を削ってから上限で切るので、**切り口の直前が空白だと末尾に空白が残る。** もう一度かけると、その空白が消える。
「あ」を170字並べて空白と「尾」を続けた見出しで、跡は元の節に出ず、「あ」170字だけの別の見出しの節へ出た。

同じ関数を両側に当てていれば揃う、という思い込みが外れた形である。保存値はそのまま引き、整え直すのは
制御文字を含む旧い生の値だけにした。整えた値は制御文字を含まないので、2つを取り違えない。

2件目は寿命だった。離れてすぐ戻ったときのために、記録を頼んだ訪問をメモリに1件持っていた。
前回の保存が失敗した後に開き直し、今の読書を背面へ回すと、同じ枠が今の訪問で上書きされる。
読み直すと今の分は開始時刻で除くので、さらに古い読みかけが前回として戻ってくる。
**寿命の違う2つを1つの枠で持っていた。** 読書ごとに持つように直し、再レビューで解消した。

### 検証は途中で止まり、同じ条件で戻った

実機検証は通し版で進め、途中で検証側のトークンが尽きて止まった。
こちらは端末の状態を読むだけにして、何も消さずに USB を外せる状態であることを確かめ、止まった時点の状態と残りを進行表へ書いた。
条件の記録が中身のハッシュで残っていたので、再開した検証側は同じ条件のまま、それまでの成功を引き継げた。

新しい不具合は出なかった。長い見出しの節を読んで離れると、末尾に空白を残した511バイトの見出し名で訪問が保存され、
再会カードの「続きから読む」が短い見出しの節へ誤らずに長い節へ届いた。

残ったのは3つで、オーナーが線を引いた。保存の失敗を実機で安全に作る方法は無いので、その順序は JVM が持つ。
自動で広がるシートを指で途中で止めることも、動きが一瞬で狙えないので、時計を止めた UI テストが持つ。
平らに開いたままの回転は、やればできるので段4の実機検証へ送った。

検証の記録を書き起こす途中で、起動のケースの手順書に書かれた数え方が、1枚の画面を10と数えることにも気づいた。
検証側は手順を変えて正しく数えていたが、手順書はそのままだった。**回避した側には、直す契機が来ない。**

## 2026-10-04 — 閉じたはずのシートが、画面に残っていた

段4は、部分要約を「この部分」の面へまとめる段である。専用のシートをやめ、余白メモと同じ1枚に載せる。

### 要約は、全画面に入る前のおさらい

着手の前に、オーナーが3つを決めた。部分要約の「確認を終了」はやめ、生成している間だけ「生成を中止」を出す。
再会カードをペインの上に載せる話は、この段ではやらない。全画面の右下の丸は、部分要約の 💬 から余白メモの `✎` に替える。
理由は一言だった。全画面ではメモのほうが嬉しい。**要約は全画面に入る前のおさらい**という位置づけで、全画面の面には要約の行を出さない。

要約は節ごとに持ち、ノートを開いている間は最近の3節分を残す。少し前に要約した節へ戻れば、作り直さずに見返せる。
生成は一度に1本で、別の節を頼めば前の生成を取り消す。結果は要求の番号が一致する要約にだけ書く。

### 机上で4件、組み直しで1件

実装レビューは4件を返した。どれも、順番を変えたときにだけ表に出るものだった。

- モデルの準備待ちを伝える説明には再試行のボタンが無い。持っている要約を見せ続ける規則のままだと、モデルが揃った後も同じ節を要約できない。押し直したら状態を確かめ直すようにした
- 蒸留で本文を差し替えると、新しい解析が届くまで前の解析が描画に残る。その間に頼むと、前の本文の要約が新しい本文の節に残る。解析し直している間は要求を受け付けないようにした
- 見出しの要約ボタンで出した一時のペインは、画面の保存値に置いていた。冊子から別のノートを読んで戻ると、保存値は別のノートを開いた状態で復元され、前のノートのペインが出た。**保存の鍵は復元では照合されない。** 値そのものに持ち主のノートを持たせた
- 面を要約の行まで送る動きは、利用者のスクロールで取り消される。後ろに置いた依頼の解除まで届かず、次に押しても送れなかった。止められても依頼を消し、押すたびに番号を振るようにした

再レビューでは、足した UI テストのほうに1件が出た。1つのテストで画面を2回組もうとしていて、2つ目の条件へ届く前に止まる。2本に分けて直した。

### 閉じたのに、閉じていなかった

実機検証の途中で、シートの「閉じる」が効かなくなった。戻る操作はアプリを抜けてランチャーまで行き、シートは画面に残る。

原因は Material3 のシートの隠し方にあった。閉じる動きの途中で指がシートに触れると、隠す動きが取り消される。
アプリの状態は閉じた扱いのまま、シートだけが画面に残る。そこで「閉じる」を押しても、閉じた扱いをもう一度閉じるだけになる。
**隠し終えるまで頼み直す**ように直し、時計を止めた UI テストで再現してから直したこと、テストが変異で落ちることを実機で確かめた。
検証側は修正したコードも読んだうえで、同じ手順を成功へ判定し直した。段3から送った、平らに開いたままの回転もこの回で確かめた。

## 2026-10-04 — 取り消しても、失敗だけは届く

段5は2本の並べ読みである。ペインの「このノートの関連」から候補を選ぶと、右がそのノートの本文に替わる。
同じ日のうちに段4から続けて入れた。

### 右は眺めるだけ

いちばん大事な線は、**右のノートを今のノートにしない**ことだった。アプリの「今のノート」は1つで、
訪問の記録・要約・分野判定・余白メモの Controller はどれもそれを前提にしている。右のノートをそこへ混ぜた瞬間に機能が増える。
だから右のノートは新しい Controller に閉じ込め、どの記録にも渡さないことにした。

「このノートへ移る」で右の位置から開くには、右と左でブロックの番号が揃っている必要がある。
右の本文は普通に開くときと同じ読み方で読み、同じパーサで解析するので、番号はそのまま使える。
位置は画面の側で左の一覧に置き、新しいノートの解析が届いたところで、飛び越した画像の測定を頼む。

遅れて届いた本文を書かない仕組みには、要求の番号を置かなかった。新しい要求も、戻る操作も、ノートの切替も、
先にジョブを取り消す。取り消しの各行を消す変異を7通り当てて、それぞれが狙いのテストで落ちることも確かめた。
**番号を足しても、それを消して落ちるテストが書けない。** このコードベースで3回やってきた判定と同じ結論だった。

### 協調する偽物は、その枝に届かない

実装レビューは、その結論の穴を突いた。右の本文の読み出しは、SAF の同期の I/O である。
同期の I/O は取り消しでは止まらない。取り消した後に失敗で終わると、その例外は取り消しより優先して、一般の `catch` へ届く。
余白へ戻った後でも、別の候補を読み終えた後でも、古い候補の「読み込めませんでした」が面に出た。

テストは読み出しを `CompletableDeferred` で作っていた。これは取り消しに素直に従うので、後から失敗させても `catch` の枝へ一度も届かない。
**取り消しの1行を消すと落ちることと、取り消しをすり抜ける経路を覆っていることは、別のことだった。**
失敗を書く前にジョブがまだ生きているかを確かめるようにし、読み出しを `NonCancellable` で包んだ偽物で、
4つの契機それぞれについて成功と失敗の後着を作った。直す前に、指摘どおりに落ちることを先に見た。

もう1件は寿命である。右の本文は ViewModel の状態に残るのに、戻る先の関連一覧の並びと開閉は、画面の中にだけ持っていた。
全画面やほかのタブへ行って戻るだけで画面は組み直され、余白へ戻ると一覧が畳まれていた。読み直しの最中なら、候補ごと消えた。
段4の一時のペインと同じく、持ち主のノートを値に持たせて画面の保存値へ移した。

### 24行と、起こせない2行

実機は通し版の24行で、新しい不具合は出なかった。検証側は Fold を閉じて開くこと、回すこと、文字を大きくすること、
TalkBack で触ることを、オーナーの手を借りて1つずつ通した。

確かめられなかったのは2行だけである。実 SAF で、取り消した後の読み出しが遅れて届く順序は、端末の上で作れない。
モデルの準備待ちから使える状態へ自然に移る場面は、端末が初めから使える状態で、起きなかった。
オーナーは、利用者の操作ではどちらも起こせないので実機では確かめない、と線を引いた。順序はどちらも JVM のテストが持つ。

文字の大きさを最大にすると、左のレールが広がって本文の幅が下限を割り、ペインがシートに替わって並べ読みが出ない。
これも仕様どおりで、オーナーは一旦受け入れ、使っていて気になったら見直すことにした。

これで余白ペインの5段がすべて終わった。課題の台帳から項目を外し、凍結していた設計の下書きも消した。
正本があり、下書きの役目は終わっていた。
