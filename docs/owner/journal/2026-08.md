## 2026-08-01 — SAF境界を型で閉じ、「葉である」の定義が甘かったと分かる

`model` パッケージを依存グラフの葉にする作業。**向きの検査（`PackageDependencyTest`）は既にあった**が、
見ているのは `com.example.newproject.*` の import だけで **`android.*` は対象外**だった。

そのため `model` は「プロジェクト内の何も import しない」を満たしながら、
**`android.net.Uri` だけは import する**状態で残っていた。`Uri` は素のJVMではスタブが例外を投げるので、
**これらの型を組み立てられずテストが書けない。**

**「葉である」をパッケージの向きだけで定義したのが穴だった。**
テスト容易性の観点では、プロジェクト内の依存も外部フレームワークへの依存も等しく
「その層を素のJVMで扱えなくする」ので、**同じ規則で数える必要があった。**

### 段取りの引き方も間違えた

**「最小の型から順に」**という段取りを組んだ。`HistoryEntry` は2フィールドで消費箇所も2つなので
ここで形を確かめてから中核の `NoteFile` へ、という理屈。**着手したら1段目で詰まった。**

型は層をまたいで組み立てられている。片方だけ新しい型にすると組み立て側に新旧の変換が要るが、
**変換関数は `data` にあり、`ui` と `domain` はパッケージ依存の規約上 `data` を import できない。**
**「変換を境界に閉じる」という設計判断そのものが、部分移行を禁じていた。**

3型を同時に移すと変換は1つも要らない。**正しい単位は最初から「3型まとめて」だった。**
**小ささは移行の独立性を意味しない。** → [lessons L18](../../dev/lessons/L18.md)

### 「処方」だけ書いて効果を検算していなかった

設計書に「Vaultルートは不透明化してもテスト容易性は1ミリも上がらない」と書いていた。
結論は正しかったが**理由が誤りで、処方の範囲が足りていなかった。**

着手前に測ると、JVMで検証できない壁は**3つ**あった。処方が崩すのは1つ目だけで、
**そのとおり実装しても新しく書けるテストは0件。** 3つ同時に外して初めて21件書けた。

**「これで何が書けるようになるか」を具体的に1件挙げれば、着手前に気づけた。**
→ [lessons L19](../../dev/lessons/L19.md)

### 端末AIのテストが落ちて、beta4 への更新を検討しかけた

`countTokens()` が `[ErrorCode 10003] Tokenization failed` で落ちた。
`FeatureStatus` は `AVAILABLE`、`baseModelName` は `nano-v3`、公式対応端末で生成は普段どおり動く。

**ここまでの材料だと「beta2 の計測APIが Android 17 と非互換」という読みになる。**
実際その線で beta4 への更新（既定値 256→4096 の動作非互換を抱える重い変更）を検討しかけた。

**正解は AICore がバックグラウンドからの利用を拒否していただけ。**
`ActivityScenarioRule` を足したら 6/6 緑になった。

**解いたのは推論ではなく対照実験だった。** 最初の実装は4つのAPIを一続きで呼んでいて
どれが落ちたか分からなかった。分解して、**落ちないはずの `generate()` を対照として同じ実行に入れた**ら、
そちらも `[ErrorCode 30] Background usage is blocked` で落ちて**原因が環境側だと一撃で分かった。**

**対照が無ければ「トークン系だけが壊れている」という誤った像で確定していた。**
→ [lessons L20](../../dev/lessons/L20.md)・[L21](../../dev/lessons/L21.md)

### 孤児掃除 — 「手動にすれば安全」ではなかった

読書痕跡の孤児ファイル掃除。論点は最後まで
**「自動削除は危険だから、手動の確認を挟めば安全になるのでは」**の形で進んでいた。
**実際にはそこが分岐点ではなかった。**

`querySafChildren` は `contentResolver.query(...)?.use { ... }` と書かれていて、
**`query()` が `null` を返すとブロックごと飛ばして空リストを返す。**
つまり「読めなかった」と「本当に空」が**この1行で区別不能に潰れている。**
孤児判定は「ノートが走査結果に現れないこと」だけを根拠にするので、**根拠そのものが壊れていた。**

**確認UIは根拠を検算しない。** 候補一覧を作るのはアプリで、その一覧は壊れたシグナルから生成される。
**手動化が減らすのは「アプリが独断で消す」ことであって、「判定が間違っている」ことではない。**

**健全性チェックの粒度も間違えていた。** 「全体件数が0や激減なら走査失敗とみなす」を一度採りかけたが、
これで弾けるのは走査が丸ごとこけた場合だけで、**小さなサブツリーが1つ欠けても全体件数はほとんど動かない。**
**集計量で部分欠損は捉えられない。** → [lessons L24](../../dev/lessons/L24.md)

結局、**根拠そのものを直した**（`SafChildren(items, isComplete)` を返し、
失敗したフォルダの相対パス集合を運ぶ）。**全体1フラグにしないのがポイント**で、
そうすると1フォルダ読み損ねただけで掃除が全面停止する。

**副産物としてバグが1つ直った。** 従来の null 畳み込みは、同期途中に `collectNotes` が
**黙ってノートを取りこぼす**ことを意味していた。Rediscover の母集団と検索結果が理由なく減り、
ユーザーには「そのノートが無い」としか見えない。**失敗が痕跡を残さないので、報告されても再現できない。**

### 「二択に見えたら選択肢を数え直す」が2度目

Lint の更新系チェックを「ゲートに載せる」か「黙らせる」かで詰まった。
実は severity は4段階あり、**`informational`（hint）は `warningsAsErrors` の昇格対象にならない** —
**「落とさないが、見えている」**という第三の状態が最初から用意されていた。

孤児掃除でも同じ形をやった。「手動か自動か」で詰まったが、見落としていたのは
**「今は手動、実績が出たら自動」という段階の軸**だった。

**1度目は強度の軸、2度目は時間の軸。** 二択で詰まったら両方を疑う。
→ [lessons L17](../../dev/lessons/L17.md)

## 2026-08-02〜08-08 — ノート内画像を出す

**難所は描画ではなくパス解決だった。** Obsidian の既定は wikilink 埋め込みで、
貼り付けた画像は `![[Pasted image ....png]]` になる。
**この形はファイル名しか持たないので、ディレクトリを1段ずつ辿る方式では原理的に解けない。**
Vault横断の画像索引が要る。

### 最大の発見は、画像1枚が読書痕跡を壊すこと

**これはレビュー指摘には無く、着手前の検算で自分で見つけた。**

`visibleFractionOfBlock` は `if (itemSize <= 0) return 1f`（高さが測れていないブロックは全可視扱い）。
これは到達率を不当に下げないための**意図的な既定値**で、高さ0が常態でない前提に立っていた。
画像はこの前提を破る。

1. 読み込み待ちの画像ブロックの高さが0だと、**そのブロックは「全部読んだ」と報告される**
2. 高さ0なので画面に一度に入るブロック数が増え、**最深到達点が実際より先へ進む**
3. **「スクロールを戻しても最深到達点は下げない」**規則により、
   **水増しがそのセッションに固着し、サイドカーへ永続化される**

**「高さを確保したほうが跳ねなくて良い」ではなく、「確保しないと痕跡が壊れる」。**
プレースホルダの高さ確保が、見た目の都合ではなく**必須要件**になった。

### そして「安全な側へ倒す」が上限になっていなかった

「大きすぎる確保は到達率を低く見積もるだけだから安全」と書いた。**これが誤りだった。**
成り立つのは**プレースホルダが実際の高さ以上のとき**だけで、**画面高はそれを保証しない**
（縦長画像なら実際は画面2〜3枚ぶん）。

**「安全な側へ倒す」と言うときは、それが本当に上限かを確かめる。**
向きの議論は上限が取れているときにしか使えないのに、
「画面より大きいものは無いだろう」という**確かめていない前提**を挟んでいた。

最終的に、確保の大きさで解くのをやめて**「測れていないなら報告しない」**へ変えた。

### 「いま画面にあるもの」を状態の根拠にしない

未測定の画像を判定する最初の実装は「いま描かれている画像」から判定していた。
**画面外へスクロールした画像は Composable ごと破棄され、測定も途中でキャンセルされる。**
破棄を「確定した」と読んだ結果、**測っていないのに未確定でなくなり**、
実機で index 2 が未測定のまま index 29 が報告された。

**LazyList は見えなくなった項目を捨てるので、捨てられたことと確定したことは別。**

→ [note_image_rendering.md](../../dev/design/note_image_rendering.md)

## 2026-08-05 — 規則が2箇所にあっても守られなかった

「総評で問題と書いたものは課題台帳へ起票する」は `CLAUDE.md`（常時読み込まれる）と
`document_map` の**両方**に書いてあった。それでも 2026-08-01 の総評の指摘4件が
**2日間どこにも追跡されなかった。** うち1件は**生きた読書痕跡を削除し得る**P1 だった。

**なぜ飛んだか。** 総評を貼るコミットの diff は「1ファイル・+211行」で、
コミットメッセージは「既存内容への変更はない」と書いていた。つまり
**総評を読んで判断する工程ではなく、文書を貼る作業として処理された。**
チェックリストは自分の変更に向いているので、**自分の変更に見えない作業では発火しない。**

**規則を3箇所目へ書いても直らない。** 直ったのは、
**全指摘の処遇を1枚に並べて機械検査に載せた**とき（`ReviewFindingsLedgerTest`）。

**しかもその検査自身が、守りたい性質より狭い対象を数えていた。**
文書再編のリンク検査で「切れ0」を確認したのに、旧パスが**3回に分けて**出てきた —
毎回**記法**で引いていて、守りたい性質は一貫して「文書への参照」だったのに。
2回目に落としたものには**常時読み込まれる唯一の設計書参照 `@docs/design/architecture.md`** が入っていた。

**さらに、その検査は一度も走っていなかった。** 変異を6件当てて**1件も落ちなかった** —
Gradle が `docs/` をテストの入力と見なさず、文書だけ直すとテストが `UP-TO-DATE` で飛んでいた。

**3つとも同じ日に出て、同じ形だと分かった。** → [lessons L29](../../dev/lessons/L29.md)

## 2026-08-08 — instrumentation を34件そろえて実機で回す

実物SAF（`src/debug/` にテスト用 `DocumentsProvider` を置く）・画像復号・端末AI生成・
Activity再生成・Navigation往復まで積み上げて、Pixel 10 Pro Fold で回した。

### テストクラスが丸ごと起動していなかった

4件足して実機で走らせたら**そのクラスが1件も起動していなかった。**
実行結果の見え方は **「1 failed, 30 passed」** — 失敗1件に見え、**消えた3件はどこにも数えられない。**

原因は JUnit4 の `@Test` が `void` を要求すること。Kotlin の `fun x() = runBlocking { ... }` は
**ブロック末尾の式の型がそのまま戻り値になる**ので、末尾を `Log.i()`（`Int` を返す）にした
1メソッドだけが `void` でなくなり、クラス全件が起動しなかった。

**新しいのは「気づけなさ」の形だった。** これまでは「落ちるテストが無い」「検査が一度も走らない」
だったが、今回は**検査は走っており赤も出ている**。それでも
**期待していた件数が出ていないことは、期待値を持っていない限り分からない。**
→ [lessons L30](../../dev/lessons/L30.md)

### 件数トリガーが誤った結論を出させた

「instrumentation が20件を超えたらCIエミュレータを再検討」という条件を置いていた。
**同じ日に34件へ到達して発火し、しかも「入れる価値が出た」という誤った結論を一度出させた。**

実際に踏んだ失敗はどちらも基盤の初期設定ミスで、**実行忘れで流出した実績は1件も無かった。**

**件数は作った量であって、困っている度合いではない。**
しかも閾値は**必ずいつか超える**ので、発火そのものが「やるべき理由」に見えてしまう。
Controller共通化でも同じことをやっていて、**これで2度目だった。**
→ [lessons L31](../../dev/lessons/L31.md)

## 2026-08-09 — 「AI補記メモ」を「ノートへのひとこと」へ作り直す

出発点は**「補記の評価内容がわかりにくい」というオーナーの実感。**
コードを当てて6件へ分解したが、git 履歴まで遡って**3件が1本の因果でつながっている**ことが分かった。

**出力枠は256トークン固定で、ゼロサムだった。** 旧補記はその枠を
分類ラベル4行（固定費）と本命3行（可変費）に割っていた。

そして 2026-07-20 の途切れ対策が、**可変費だけを削っていた。**
「3〜5項目」→3項目固定、「なぜその欠落が理解に効くか」の括弧書き→削除。
**分類ラベル4行は1文字も触られていない**（`git log -S"粒度評価"` で確認）。

**削る対象を、価値ではなく削りやすさで選んでいた。**
そして削られた括弧書きこそが「一般論ではない」を担保していた唯一の要素だった。

**構造的な原因は、補記だけ設計書が無かったこと。** 他機能には設計書があったが補記には無く、
**「補記が何を出すべきか」を書いた文書が存在しなかった**ので、
削減が「何を守るべきか」と突き合わされないまま2か月以上残った。

### そこから5巡した

| 巡 | オーナーの実感 | 何が起きたか |
|---|---|---|
| 1 | 「UI/UXに違和感」 | **自分で書いた仕様に自分の実装が反していた** — 「ノート固有の言葉を必ず含める」と書きながら、リンクがあれば免除する分岐を持っていた |
| 2 | 「ソースコードだけのノートで英語で問われる」「問いのみで終わるのはモヤっとした」 | **category の取り違え。** 要約は本文の言語に従うのが正しいが、ひとことは**アプリがユーザーへ話しかける文**なので読み手の言語に従う。あわせて**返事欄**を入れた |
| 3 | 「まだ違和感がある」 | 外部レビューが**返事を失う経路3つ**を指摘。保存結果を3値へ分け、1往復で閉じる映し返しを入れた |
| 4 | 「長文の時の扱いが雑」 | **上限を1本で決めたのが誤り。** 保存8,000字／AIへは400字抜粋に分離した |
| 5 | — | リンク付き文の問い判定から `でしょう` `だろう` を外した（**推量であって疑問ではない**） |

**一番効いた学びは4巡目。** `MAX_REPLY_CHARS = 400` は「1文だから」と置いた数字からの逆算で、
**ユーザーの文章の長さをAIの都合ですらない思いつきで縛っていた。**
本文は既に「保存は原文・AIへは抜粋」でやっていたのに、返事だけ両方を同じ数字で縛っていた。

**「汎用エディタにしない」は壁ではなく合図で守る**という結論になった。
壁にすると、長く書きたかった回にユーザーの言葉が消える。

→ [reflect_remark.md](../../dev/design/reflect_remark.md)

## 2026-08-10 — 文書体系そのものを作り直す

**きっかけはオーナーの「これ長すぎない？」だった。**

`change_history.md` を測ったら **188KB・100エントリ・1行あたり中央値1,846字**で、
**プロジェクト最大の文書**になっていた。運用ルールには「PRごとに**1行**追記する」と書いてある。
**規約に対して中央値1,846倍。**

**壊れたのは「1行」という語だった。** markdownテーブルの「1行」に長さの上限が無い。
**規則は守られていた**（毎PR 1行足していた）のに壊れた、という新しい形だった。

### そして「Claudeは読んでいるのか」を確かめた

`change_history.md` は `CLAUDE.md` から参照されておらず、
**言及は1箇所だけ、しかも「追記する」＝書き込み指示。**
つまり **Claudeにとっては書き込み専用**で、実質的な読者はオーナー1人だった。

しかも実証データが1つあった — **その日Claudeが唯一読もうとしたとき、
86KBが出力上限を超えて中身を見られなかった。** 役に立つどころか、読もうとすると失敗する状態。

同じ問いを `lessons.md`（671行）にも当てて、フォルダ分割を検討した。
**Codex に相談したら、私の主張の核が文書自身の記録で否定された** —
「同じファイルに並んでいたから再発に気づけた」と書いたが、
§0 は「必要な知識は同じ画面にあった」のに60行下で同じ失敗をしたと記録しており、
L28 は4回直した後に5度目を踏んでいる。**同居は「後から共通パターンを発見する」には効くが、
「次の変更で発火させる」には効いていなかった。**

結論はカード形式（索引＋1件1ファイル）への移行。
**カテゴリ別フォルダは採らなかった** — 既存の4カテゴリのうち §4 が18/31件を抱えて破綻しており、
**破綻している分類でフォルダを切ると破綻が構造として固定される。**

### §0 が自分の廃止条件を超えていた

`lessons.md` の §0（diff後に当てる5問）は、自分でこう書いていた —
**「次の3回のコード変更で評価し、2回目・3回目も同じ結果なら廃止を検討する」。**

1回目の判定（2026-08-05）は「発火しなかった」。**その後17件の変更が走ったが、
2回目・3回目の判定は一度も記録されていなかった。**

**「評価する」と宣言した仕組み自体が、評価されないまま走り続けていた。**
L29「規則は検査へ変えるまで守られない」が、**L29から作られた仕組み自身に当たった**形で、
宣言どおり廃止した。 → [lessons L32](../../dev/lessons/L32.md)

**そして同じ日、その置き換え作業の中で私はまた同じ罠を踏んだ。**
索引の冒頭に「番号は安定させる。振り直さない」と書いた**その同じ編集で**、
L12・L13・L15・L16 を振り直していた。書いた直後に自分へ当てて気づいた。
→ [lessons L33](../../dev/lessons.md#l33-教訓を書く行為は適用を保証しない)
