## この日誌が持つもの

**「なぜそう決まったか」の物語。** 設計書は結論と、その結論を支える理由だけを持つ。
一方で開発の実際は、読み違え・撤回・実機で初めて分かったこと・レビューでの指摘の積み重ねでできている。
**その過程こそが読み物として面白く、技術的に学べる**ので、ここへ分けて書く。

各エントリはおおむね次の形をとる。

- 何を作ろうとしたか / 最初にどう考えたか
- **何を読み違えたか**（ここが一番面白い）
- 実機・レビューで何が起きたか
- どの判断を撤回・変更したか / 最終的にどう決着したか
- そこから得た技術的な学び
- 対応する設計書・教訓カードへのリンク

## 書き方の約束

- **月ごとに1ファイル。** 日付ごとにファイルを増やさない
- **生の作業ログを貼らない。** 読み物として要約・再構成する
- **同じ出来事を設計書と日誌へ二重に長文で書かない。** 設計書は「現在有効な理由」、
  日誌は「そこへ至った過程」。重なる部分はどちらかを要約＋リンクにする
- 細部は git 履歴から引けるので、追わない
