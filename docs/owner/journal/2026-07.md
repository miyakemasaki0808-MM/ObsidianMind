## 2026-07-19 — 906行のViewModelを割る

`NoteViewModel` が906行まで肥大化し、**状態リセット処理が3箇所に重複**していた。
「リセット漏れ→旧状態の残留」バグが何度も出ていて、静的分析をかけたら27項目が挙がった。

**面白かったのは、27項目の多くが同じ形をしていたこと。**
状態リセット3重複・SAFカーソルループ5重複・タブ遷移2重複・AIタイトル整形2重複 —
**バラバラの不具合ではなく「同じコードを複数箇所に書いた」ことの帰結**だった。

マルチモジュール化や機能別ViewModel化ではなく、「窓口は残して実装をControllerへ委譲する」を選んだ。
906行 → 348行・Controller 4つ。**公開APIと `uiState` の形を維持したのでUI層の変更はゼロ**で移行できた。

**この日の一番の学びは「結合点を明示契約に変える」こと。** ノート切替の後始末を各所に散らすのをやめ、
`cancelNoteScopedJobs()`（ジョブ停止）と `withNoteScopedReset()`（状態リセット）の2つに集約した。
呼び出し側へ2手を公開しないことで、**「状態だけ消したが旧ジョブは生きている」という中間状態を作れなくした。**

→ [architecture.md](../../dev/system/architecture.md)

## 2026-07-20 — SDKの制約は、ドキュメントではなくバイナリで確認する

AI補記が途中で切れる問題を追いかけていて、`maxOutputTokens` に 1024 を設定したら
**全AI生成が失敗した。**

原因は SDK 内部のバリデーション「1〜256」。公式ドキュメントの
「256トークン超の出力は避けるべき」は**推奨ではなくAPIレベルの強制**だった。

ローカルのGradleキャッシュからAARを展開して class ファイルの文字列を調べれば、
バリデーション文言・メソッド有無・定数が確実に分かる。**実装前にこれをやっていれば1往復防げた。**

同じ日、吹き出しのタップが「クイズ画面から戻ると完全無反応」になるバグも直した。
`pointerInput(Unit)` が**初回コンポーズ時のクロージャを固定する**のが原因で、
画面遷移から戻ると「その時点の状態」でコンポジションが再生成されるため
**初回＝素の状態という思い込みが通用しない。** → [lessons L34](../../dev/lessons/L34.md)

## 2026-07-21〜25 — TimeCapsule を棄却して ReadingTrace になる

**最初の設計は「読み終わりに未来の自分へ問いを1つ残す」タイムカプセルだった。**
全論点を確定して実装前まで進んでいたが、
「**ボタンではなく、ユーザーが意識することがない補助機能にしたい**」という要求が出た。

検討すると、この機能の成立には3条件があって**同時に3つは満たせない**ことが分かった。

| | 中身が自分由来 | どのノートにも残る | 無意識に作られる |
|---|---|---|---|
| 明示ボタンで問いを書く | ✓ | ✓ | ✗ |
| AIが問いを自動生成 | ✗ | ✓ | ✓ |

**トレードオフを解いたのは「AIの役割を"問いの創作"から"痕跡の要約"に落とす」という一手だった。**
中身はユーザー自身の読み方なので「自分由来」が保たれ、普通に読むだけで痕跡が出るので「どのノートにも」を満たし、
完全自動なので「無意識」も満たす。

**これは今でもこのプロジェクトで一番きれいな設計判断だと思う。**
→ [lessons L3](../../dev/lessons.md#l3-aiの役割を創作から要約へ落とすと導線が要らなくなる)

### 実装レビューで3件の高優先度が出た

書き上げてレビューにかけたら、**JVMテストが全部緑なのに3件の高優先度**が出た。

1. **長大な1ブロックを冒頭だけ見ても到達率100%になる。**
   テストはControllerへ整数の `blockIndex` を直接渡していて、Compose上のブロック内可視量を扱っていなかった
2. **`onStop` で確定後、復帰時にセッションを再開始しない。** Activity lifecycle を通さず Controller 単体を呼んでいた
3. **Vault切替前に起動済みの保存が新Vaultへ到着し得る。** Fake は動的な保存先と遅延I/Oを再現しない

**3件とも「テストが通る範囲の外」で見つかった。** これが後の instrumentation テスト整備につながる。

→ [reflect_reading_trace.md](../../dev/features/reflect_reading_trace.md)

## 2026-07-26 — 世代IDを二層にする／Vault分離が「効いていなかった」

ノート・Vault切替後に**旧要求の結果が画面へ後着する経路が4つ**残っていた。
塞ごうとして、**壊れている4経路がスコープ2種類に分かれている**ことに気づいた。

補記管理画面はノートと無関係なので、ノートを開き直しただけで一覧が消えるのは誤り。
逆に要約をVault世代だけで守ると同じVault内のノート切替を検出できない。
**片方に寄せると必ずどちらかが壊れる**ので、層を分けた。

### そして、Vault分離の修正が効いていなかった

前日に入れた「保存要求にVault識別子を持たせて照合する」対策を、**Codex のレビューが割った。**

```kotlin
if (!isCurrentVault(vaultKey)) throw IOException(...)  // ← 1回目の vaultUri() 読み取り
val current = folderIndex()                            // ← 2回目。ここで再び読む
```

**確認と使用で同じソースを2回読んでいた。** その間にVaultが切り替われば別物を掴む。
`@Synchronized` を付けていたので守られているつもりだったが、`vaultUri` は ViewModel が持つ `var` で
**このクラスのロックの外**から更新される。

**方針が正しかったぶん、実装が効いていないまま文書とコミットメッセージが通っていた。**
これが「修正の主張は、修正コードを別の目で読むまで確定させない」という規約の出発点になった。
→ [lessons L6](../../dev/lessons.md#l6-修正の主張は修正コードを別の目で読むまで確定させない)

## 2026-07-27〜28 — AI入力の切り出しを「後ろ捨て」から「真ん中捨て」へ

**8つのプロンプトが、本文を `String.take()` で先頭から固定長に切っていた。**
切り方が問題だったのではなく、**捨てる場所が常に「後ろ」だった**ことが問題だった。

長いノートの後半には結論・検証結果・残課題が置かれる。つまり
**ノートの価値が集まっている場所が、構造的に毎回捨てられていた。**

実例が分かりやすい。案を3つ検討して案2で解決し残課題を1つ残したノートは、
先頭1,200文字だけを見ると「解決策を検討中のノート」に見える。
**要約は精度が低かったのではなく、系統的に間違っていた。**

真ん中を捨てて、骨格（見出しだけを抜き出した目次）＋冒頭＋末尾を渡す形にした。

**一番面白かった発見は、実際にモデルへ渡る本文が減っていること。**
要約なら以前の1,200文字連続に対し、いまは冒頭406＋末尾272＝678文字しかない。
それでも出力が良くなるなら、結論は一つしかない —
**同じ予算なら、連続した先頭より、構造を伝える不連続な断片のほうが強い。**

**そして「純粋」は「軽い」を意味しなかった。** 切り出しを賢くした結果、
1MBの本文のMarkdown解析に**約460ms**かかるようになり、それをMainスレッドから呼んでいた。
従来の `take()` は実質ゼロコストだったので、**賢くした結果として新しい負荷を持ち込んでいた。**
→ [lessons L13](../../dev/lessons.md#l13-純粋と軽いは別)・[ai_input_excerpt.md](../../dev/system/ai_input_excerpt.md)

## 2026-07-29〜30 — ライト配色のAA是正で2度差し戻される

コントラスト未達7件をまとめて直す作業。**2度差し戻された。**

### 1度目 — 「強制していたのは現実に存在しない条件」だった

テストを「未達を記録するだけ」から「基準を強制する」形へ移した。方向は正しい。
だが**初版は全色を `panel #FDFEFF`（アプリで最も明るい面）の上で測っていた。**
実際に文字が載る面では 4.19〜4.41、グラデーション直上のボタンでは 1.21〜1.84 で**全部未達。**
テストは全緑だった。

**しかも同じコミットの文書に「トークンを検証するときは、その色が実際に載る面すべてを列挙する」と
書きながら、直している当のトークンには適用していなかった。**
**教訓を書く行為は、適用を保証しない。**

### 2度目 — 「代表値で測る」をやめる

対応表を作り直したが、**表に載せていなかった経路がまだ残っていた。**
グラデーション直上の白文字を、**最も有利な停止色でだけ**測っていた
（テストのコメントは「最も明るい停止色」と書きながら、渡していたのは最も暗い Indigo だった）。

原因の一端は二重管理。`AppColorScheme` は `Brush` を受け取っていたが
**`Brush` から色は取り出せない**ので、テストは同じ値を自前で書き写すしかなかった。
停止色のリストを受け取って `Brush` をその場で組み立てる形に変え、実装とテストが同じリストを見るようにした。

**表に載せる範囲を自分で決められる以上、載せ忘れは必ず起きる。**
防ぐには①検証対象を列挙ではなく総当たりにする ②表に載らない書き方をソース走査で禁じる、の2つが要った。

### そして「基準を満たす実装」と「成立しているデザイン」は別だった

グラデーション上の見出しに `LogoNavy` α=0.42 の暗幕を敷いたら数値は通ったが、
**実機で見ると帯として重く、角丸を付けた時点でカードにしか見えなかった**（すぐ下に白い本文カードがあるため）。

解き方を反転して、**白を薄く重ねて停止色を持ち上げ、そこへ濃い文字を置く**形にした。
**白文字と濃い文字では、苦しくなる停止色が逆になる**のが効いた。

→ [theme_and_ui_refactor.md](../../dev/system/theme_and_ui_refactor.md)・[lessons L9](../../dev/lessons.md#l9-検証条件が実物と一致しているかはテストが通ることでは分からない)

instrumentation テストの依存・Runner・スモークテストを置き、CIでコンパイルと組み立ても通した。
**だが実際に実行したのは2日後で、結果は 0 success / 2 failure だった。**

組み立てが通る限りCIは緑のままなので、**「土台がある」という認識だけが先に定着していた。**
→ [lessons L10](../../dev/lessons.md#l10-土台を組み立てられると土台が動くは別)

同じ日、表示用Markdownの解析もMainスレッドから追い出した。
07-27 にAI入力側を逃がしたときの教訓は「同じAPIを呼ぶ全箇所を検索対象にする」だったが、
**当時の走査対象は `buildNoteExcerpt` だけで、同じ重さを持つ `buildNoteSectionModel` は数えていなかった。**
「入力サイズに比例する純関数をMainから呼ばない」という**性質で引くべきところを、関数名で引いていた。**
→ [lessons L14](../../dev/lessons.md#l14-横展開は最後の1本を取り残す)

**非同期化には「描かない」ガードが対で要ることも分かった。** `MarkdownNoteContent` には
`precomputedBlocks ?: parseMarkdownBlocks(content)` というフォールバックがあり、
解析待ちの間に本文を描くと**このフォールバックが働いて結局Mainで解析し直す。**
Main外へ出した意味が消えるどころか、退避ぶんだけ遅くなるところだった。
