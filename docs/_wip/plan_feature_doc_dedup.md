## 1. 何が問題か

**同じ事実の正本が2箇所にあるように見える。**

2026-08-11 に機能仕様を12節の様式へ移したとき、**既存の判断を失わないために §8 へ丸ごと保存した**。
その結果、**数値・状態・データ契約が §5〜§7 と §8 の両方に載っている。**

**壊れてはいない。** 実装との一致は 2026-08-12 に全16本で確認済みで、テストも通っている。
問題は**読む側がどちらを信じればよいか分からない**ことと、**片方だけ古くなる余地**があること。

## 2. やること

**数値・状態・データ契約は §5〜§7 だけを正本にし、§8 は「なぜその値・方式にしたか」へ絞る。**

| 節 | 持つもの |
|---|---|
| §5 機能仕様 | **上限・パラメータの実値**（定数名つき） |
| §6 状態とデータ | **状態の型・永続化・破棄条件** |
| §7 システム設計 | **経路** |
| §8 設計判断 | **なぜその値にしたか・何を却下したか。値そのものは書かず §5 を指す** |

### 対象と優先順

1. ~~**related_notes_ai**~~ **完了**（250 → 289行）
2. ~~**reflect_distill**~~ **完了**（332 → 460行）
3. ~~**reflect_reading_trace**~~ **完了**（480 → 507行）
4. note_age_paper / note_image_rendering / dark_mode ← **残り**

> **行数は3本とも増えた。** §8 の密なリスト記法を §5〜§7 の表と見出しへ展開したためで、
> **重複そのものは消えている**（主要な数値が文書内に1回ずつしか現れないことを確認済み）。
> §6「やらないこと」のとおり行数は目標にしていない。

### 上位3本で分かったこと（残り3本へ引き継ぐ）

- **判断の番号は振り直さない。** `reflect_distill` は §2・§4・§9〜§11 から、
  `reflect_reading_trace` は roadmap・current_issues・instrumentation_testing から
  **判断N を番号で参照されている**。振り直すと一斉に壊れる
- **§8 内にも重複がある。** `related_notes_ai` は「フェーズ別の判断」と「得られた知見」が
  同じ判断を2度書いていた。**移送先を全件書き出してから統合する**と落とさずに済む
- **移送のついでに実装と突合すると食い違いが出る。** 3本で3件見つかった
  （related: 抜粋上限600→800 / reading_trace: ファイル上限64KB→128KB・欠けていた定数3つ）。
  **どちらの版が正しいかはコードでしか決まらない**
- **理由を創作しない。** 値を抜いた跡に「なぜ」を書き足したくなるが、
  **文書に無い理由を足すと記録として嘘になる**。書けるのは元文に根拠がある範囲だけ

## 3. 絶対に守ること

> **§8 の判断を消さない。** これが唯一の失敗条件である。

2026-08-11 に「丸ごと保存」を選んだのは**判断を失わないため**で、今回はその逆をやる。
**値を §5 へ寄せるのであって、判断を削るのではない。**

- 「§8 が短くなった」は成果ではない。**判断の本数が減っていたら失敗**
- 却下案・失敗の型・「なぜ他の値ではないか」は**全部残す**
- 迷ったら残す。**重複は読みにくいだけだが、判断の欠落は取り返せない**

### 具体的な書き換えの型

```markdown
（変更前・§8 に値がある）
### 判断3: 一段目スコアはサリエンス
score = 1.0 * dice(文, タイトル) + 0.7 * dice(文, 直近見出し)
段落先頭文 +0.3／末尾文 +0.4

（変更後・§8 は理由だけ）
### 判断3: 一段目スコアはサリエンス
**タイトルと直近見出しへの近さで測る**（実際の重みは §5）。
本文全体との類似ではなくこの2つを見るのは、**結論が段落や章の端に出やすい**ため。
構造的な加点を入れているのは、**結論の取りこぼしを安価に防ぐ**目的で、意味解析を避けている。
```

**作業前に判断の見出し数を数え、後で照合する**のが最低限の担保になる。

```bash
grep -c '^#### 判断' docs/dev/features/related_notes_ai.md
```

1. **先にコミットする**（変異確認や `git checkout` で未コミットの修正を巻き戻した事故が実際にあった）

5. 判断の見出し数を再度数えて照合する
