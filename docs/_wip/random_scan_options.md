# 大きなVaultの初回ランダム表示 — 3案比較とClaudeへの引き継ぎ

**基準:** 2026-10-12、`fa720900`。Codexによるコード・設計書の分析のみ。製品・テストコードの変更、今回の実機再測定は行っていない。
**状態:** 分析完了・オーナーの方針判断待ち。改善実装・性能の受理は未完了。
**関連:** [課題台帳のPERF-3](current_issues.md#perf-3-大きなvaultほど最初のランダム表示まで長く待つ)。
**寿命:** 使い捨て。判断内容と必要な引き継ぎを設計書・実装依頼へ転記してから削除する。基準値と未解決事項は課題台帳が持つ。

## 1. 結論と判断すること

**推奨はA「Vaultの復元・選択後に走査を先行させ、同時要求は同じ走査を待つ」。**
全体からの一様抽選と60秒の更新方針を保ち、既存の共有経路を使えるため、最初に試す案として変更範囲が小さい。
ただし、**走査自体は速くならない。起動直後に押す場合・初めて選ぶVaultの待ちを解消する案ではない。**
待機中に済んだ分だけボタン後の待ちが減る、という仮説であり、現段階で高速化を保証しない。

| 案 | 初めて読むVault／プロセス再起動直後 | 少し待ってから押す／繰り返す | 主な代償 | 判断案 |
|---|---|---|---|---|
| A. 走査を早く始める | 直後なら残りの走査を待つ | 先行走査が済みTTL内なら再利用 | 使わない機能のI/Oも起きる。起動や他のI/Oとの競合 | **限定的な初手として推奨** |
| B. 結果を長く持つ | TTL延長だけでは変わらない。永続索引なら再起動時に再利用可能だが、初めてのVaultは変わらない | TTL切れによる待ちを減らせる | 追加・削除・改名・更新日時が古くなる。永続化は別の設計が必要 | 初回対策としてTTL延長だけを採らない |
| C. 全走査を待たずに引く | 先に見つかった集合なら速く出せる可能性 | 背景で残りの走査が必要 | 深い階層のノートの抽選確率、紙の地色、共有索引の意味が変わる | 現行の一様抽選を保つ範囲では推奨しない |

オーナーに決めていただくのは次の2点。

1. **Aを最初の改善として試すか。** 「起動直後・初めてのVaultでも必ず短縮」が必須なら、Aだけでは足りない。走査方式そのものの短縮を追加調査する必要がある。
2. **どの条件で何秒以内なら受理するか。** 例として3,000本・起動直後／5秒後／20秒後を別々に測る。5秒・20秒は測定条件の候補であり、許容時間の決定ではない。

## 2. 現状と測定の限界

既存の実機観測は500本で初回5.465秒、1,500本で10.866秒、3,000本で15.521秒（各3回の中央値）。
起動は約0.5秒、60秒以内の2回目は約3秒。詳細・fixtureは[課題台帳](current_issues.md)と[生成手順](random_scan_fixture.py)を参照する。
**画面の文字取得そのものに2.4〜2.9秒かかる測定なので、約3秒をアプリの下限と解釈しない。**
走査単体の時間、TTL切れ後、先行走査の効果は未測定。本数とフォルダ数を同時に増やしたため、どちらの寄与かは分離できていない。

現在の経路は次のとおり。

`loadRandomNote` → `collectAllNotesCached` → `NoteScanCache.get` → `NoteRepository.collectNotes` → `traverseMarkdownPaths` → `querySafChildren`

走査はIO上でフォルダごとに子一覧を問い合わせるBFS。本文は一覧が揃って抽選した後に読む。
`presentDrawnNote` は本文の公開より前に痕跡セッションと紙の地色を決め、冊子の「これを読む」と共有する。
[再発見の設計](../dev/features/rediscover.md)と[責務・世代の契約](../dev/system/architecture.md)を維持すること。

| コードから確認した性質 | 改善時の意味 |
|---|---|
| `NoteScanCache.get` は非空の一覧を60秒再利用。`loadedAt` は走査開始時刻で、空の結果はヒットしない | 先行走査が長いほど、完了後に再利用できる時間は短い。TTL起点の変更や空結果の保持は別途判断・検査する |
| 実行中の走査を共有するJob／Deferred／排他制御は無い | 完了後の再利用と、同時要求の一本化は別。Aで起動とボタンが重なると、そのままでは複数走査になる |
| 公開直前にVault世代を照合。`saveVault` で `clear` | A→B→AをURIの一致だけで許してはいけない |
| `reloadNoteBody` 成功後に `expireAfterBodyWrite`。一覧・knownNotesは消すがlinkIndexは残す | 同じVault内の本文保存も無効化契機。先行走査の古い更新日時が戻らないよう、保存との交錯を検査する |
| `fetchRelatedNotes` は非空なら `cachedNotes` を直接使う。本文リンクの解決も走査しない | 60秒は全利用者に一律適用される自動更新タイマーではない。単に定数を替えても全機能の鮮度は定義できない |
| 読み取り不能な枝は記録しつつ、表示経路は `VaultScan.notes` を使う | 「走査途中の一覧」と「走査を終えたが一部の枝を読めなかった一覧」は別。前者を完成品として流さない |
| BFS内に協調キャンセル確認が無く、queryもCancellationSignalを渡していない | Jobのcancelだけで実際のSAF負荷が直ちに止まると保証しない。結果の不採用とI/O停止を分けて確かめる |

**設計書との差分（DOC-1へ起票、今回はどちらも修正していない）:**
再発見の設計は `.obsidian` を除外対象としているが、`collectNotes` が渡す除外集合は `_AI補記` と `_ReadingTraces` だけで、共通走査にも `.obsidian` の判定が無い。
プロバイダが配下の `.md` を列挙した場合は候補になりうる。実機での混入は未確認。
また、同設計§6の「破棄の契機はVault切替だけ」は本文書き戻し後の失効と一致しない。
「連打しても走査は1回」という記述も、完了済みキャッシュの再利用と同時要求の保証を区別して整理する必要がある。

## 3. 3案の変更箇所と共有機能への影響

| 観点 | A. 先行走査 | B. 長期保持（TTL延長／永続化） | C. 全走査前に抽選 |
|---|---|---|---|
| 変える場所 | `NoteViewModel.restoreVault/saveVault` の完了後の開始経路、`NoteScanCache` の実行中要求の共有・無効化 | `NoteScanCache` と定数。永続化ならVault別ストア・起動復元・版管理・更新失敗時の扱いも追加 | `NoteRepository`／`VaultPathTraversal` の逐次列挙、抽選API、`presentDrawnNote` と索引公開経路 |
| ランダム | 完了済み一覧から `notes.random()` を維持。未完了時は同じ処理を待つ | 古い集合内では一様でも、新規ノートは入らない。消えた参照を引く期間が延びる | 先着集合は未訪問ノートの確率が0。フォルダを等確率で選んでもノート数が異なると偏る |
| 冊子 | 同じキャッシュ経由で恩恵。開いている束や種を先行走査の完了で作り直さない | 古い候補から10枚を引く。既存の束の寿命とキャッシュの寿命を混同しない | 重複なしの最大10枚・全体から引く契約が崩れる。完成済み一覧を待つなら冊子の待ちは残る |
| 関連ノート | 完了後の候補を共有。AI・スニペット読込は先行開始しない | 候補の追加・削除が遅れる。候補側の別キャッシュの無効化も確認する | 未訪問ノートとリンク先が候補から落ちる。全体が揃うまで候補計算を待つ経路が必要 |
| 結晶一覧 | `knownNotes` が先に揃う。Vault切替・本文書込による失効は維持 | 改名・削除済みの根拠が押せる状態を長く残し、新規の根拠は開けない | 一覧途中の不在を「根拠無し」と誤読しない表示と状態の区別が必要 |
| 分野索引 | 完了時だけ `indexNoteFields`。AIの確定を暫定で上書きしない | 古い参照・パスの分類が残る。永続の分野ストアとの混同を避ける | `indexNoteFieldHints` は入力一覧にいない項目を落とすため、断片公開で既存の確定まで落ちうる |
| 本文リンク・痕跡のパス解決 | `linkIndex`／相対パスも完了時に揃える。セッション開始と本文公開の順は維持 | 改名・移動前のリンクとパスが残る。再検証や失敗時の回復が必要 | 初回の本文リンクが未準備になる。再会カード・痕跡・結晶が必要とする相対パスも確保する |
| 紙の地色 | 全体の更新日時分布をそのまま利用 | 古い分布による地色になる。本文書込後の失効を省略しない | 全体の相対順位が未確定。暫定色や後からの色変更は現仕様の変更になる |
| 再測定の重点 | 起動への影響、押すまでの待機時間、重複走査数、TTL切れ、切替・保存中の交錯 | 初回／同プロセス／再起動を分離。外部追加・削除の反映時間、永続索引の破損・権限失効 | 階層・各フォルダ本数を偏らせた抽選、索引が揃うまでの表示、最終母集団との一致 |

Bで「古い一覧を即時返して裏で更新」するなら、単なるTTL延長ではなく**古さを許容する新しい契約**になる。
永続化する場合も本文は保存せず、一覧の保存先・Vault分離・参照権限・形式変更・不完全走査による上書き可否を決める必要がある。
Cでリザーバサンプリングを使えば最終的な一様抽選はできるが、結果確定には全件を見るため待ち時間は解消しない。
未列挙の候補数が不明な現在のSAF走査で、「即時確定」と「現行母集団の一様抽選」を同時に主張しない。

**別経路を巻き込まない:** `SearchController` が呼ぶ `VaultHandle.collectNotesInScope` は検索範囲・除外条件が異なる。
ただし `NOTES_CACHE_TTL_MS` は全体走査と検索範囲のキャッシュが共用しているため、Bで定数だけを延長すると検索にも波及する。
孤児掃除の `ReadingTraceCleanupController` は完全性を持った新しい走査が必要で、表示用キャッシュを流用しない。
画像索引と読書痕跡の索引も別キャッシュ。同じ60秒でも本件の変更を一括適用しない。

## 4. Claudeへ渡す実装案（Aが選ばれた場合）

1. **オーナーの選択・受理条件とDOC-1の扱いを確認する。** この資料はAの実装承認ではない。直後の待ちも大幅に短縮する要求なら、Aで完了扱いにしない。
2. Vault復元・Vault選択の後始末がすべて終わってから、Vault単位の先行走査を開始する。`onVaultChanged` の途中で公開すると、その後の状態リセットで分野索引が消えるため、URI設定ラムダの中で開始しない。
3. 走査の所有者と待機者を分け、同じ有効な要求は1回の走査を共有する。ノート切替・冊子の閉じる操作による待機者の取り消しで共有走査を巻き添えにしない。Vault切替／ViewModel終了では所有するJobを止め、公開直前の世代照合も残す。
4. 本文書き戻しで進行中要求を無効にし、古い結果を公開しない。Vault世代だけでは同一Vault内の保存を区別できない。既存の要求識別・Jobの仕組みを検討し、安易に全体の世代階層を増やさない。新要求が古い要求へ合流しないことも必要。
5. 完成した一覧・リンク索引・knownNotes・分野索引を同じ結果から更新する。空／失敗／取消後は実行中ハンドルを残さず、後続の明示要求で再試行可能にする。先行走査の失敗だけで読書画面をErrorへ変えない。
6. 起動時に抽選・本文読込・訪問記録・AI生成を始めない。ノートを開く時点の処理順と冊子の束は保つ。TTLはまず現状の起点・60秒を維持し、タイマーによる定期走査や永続索引を同時導入しない。
7. 下記の机上検査と計測を行い、設計書を選んだ契約へ更新してCodexへ差分レビュー・実機確認を渡す。計測用の本文・URI・ファイル名を恒久ログへ残さない。

- [`NoteScanCache`](../../app/src/main/java/com/example/newproject/NoteScanCache.kt): `get`、`clear`、`expireAfterBodyWrite`

## 5. 検査・再測定・完了条件

| 層 | 確かめること |
|---|---|
| JVM：`NoteScanCacheTest` の拡張 | 同時2要求でscanが1回、片方の取消でも他方は成功、失敗／取消後に再試行、空Vault、TTL直前・境界・長時間走査。既存5件は同時要求の共有やTTL境界を保証していない |
| JVM：切替・書込の交錯 | A→B→A、旧scanが新scanより遅れて完了、scan中の本文保存／保存後のscanの両方向。古い一覧・knownNotes・linkIndex・分野ヒントが戻らず、実行中状態が残らない |
| JVM：利用側 | `NoteSessionCoordinatorTest`／`BookletControllerTest`／`NoteFieldIndexTest`／`NotePaperAgeTest`／`NoteLinksTest`。束と種、AI確定、本文前の痕跡セッションと地色、書き戻し後のリンク維持を確認 |
| SAF | `VaultScanInstrumentationTest` と一時Vaultで追加・削除・改名・権限失効・部分的な列挙失敗を確認。DOC-1の判断後に `.obsidian` 配下の `.md` も検査する |
| 机上ゲート | `testDebugUnitTest lintDebug --offline`。文書変更は `--rerun-tasks`、instrumentation変更時は `assembleDebugAndroidTest` も実行 |
| 実機 | 同じ合成Vault 500／1,500／3,000本・同じ画面条件・各3回以上。旧実装と改善実装を同じ新しい計測方法で比較する |

実機では、**起動直後／5秒後／20秒後の初回、TTL内の2回目、TTL失効後、プロセス再起動、Vault再選択**を分ける。
経過時間は単調時計で、起動→操作可能、タップ→本文描画、走査開始→完了、一覧公開・本文読込・Markdown準備を切り分ける。
先行走査ではタップ後の時間だけでなく、起動から本文までの時間と走査回数も記録する。
本文描画はSuccessの代入と同一視せず、描画を確かめる計測を組み合わせる。測定器の時間も記載する。
旧値の画面取得方式と新しいアプリ内計測の差を、そのまま改善率にしない。

負荷を切り分ける追加条件として、ノート本数を揃えた平坦／深いフォルダ構成を使う。
自動更新を仮定せず、外部追加・削除はTTL内と失効後の明示操作を分けて反映を確認する。
空・失敗・他機能だけを使う起動では、繰り返し走査や意図しない画面・痕跡・AIの変化がないことも見る。

**完了の線:** オーナーが決めた条件の短縮を同条件比較で示し、起動悪化・抽選の偏り・旧Vaultの混入・本文書込後の巻き戻りが無く、共有機能の回帰が通ること。
Aで待機後だけ改善しても、直後の要求が満たされなければPERF-3は残す。最終受理はオーナーが行う。
