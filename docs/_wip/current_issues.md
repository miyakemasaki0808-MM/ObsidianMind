## REL-1. R8とリリース署名が未設定

- **現状:** `buildTypes { release { } }` と `proguard-rules.pro` は置いたが、
  **`isMinifyEnabled = false`／`signingConfig` 無し**。`assembleRelease` の生成物は
  依然として `app-release-unsigned.apk`（約10MB）で、配布可能性を意味しない。
- **後回しにした理由:** ML Kit GenAI はリフレクションで解決される部分があり、縮小で消えると
  **全AI機能が実機の release ビルドでだけ落ちる**。JVMテストは縮小前のクラスを見るので検出できない。
  Compose の Composable メタデータも同様。つまりR8の有効化は「設定を1行変える作業」ではなく
  **実機検証の計画とセット**になる。
- **対応候補:** keep ルールを書いた上で `isMinifyEnabled = true` にし、release ビルドを実機へ入れて
  `PromptBuilder` の全AI経路を一巡する。
  署名は keystore の保管方針を決めてから。
- **規模感:** 中。実機確認が必須。

## PERF-1. 読書痕跡の索引作成がファイル数に比例する

**実測で問題化するまで着手しない。** 先回りで入れると移行リスクだけを先払いになる。

- **現状:** `_ReadingTraces/` はフラットな1階層で、セッション中1回だけ子一覧を全列挙して
  key→参照の索引を作る。容量は問題にならない（1ファイル最大3.3KB・2,000ノートで約1.4MB）が、
  **列挙コストはファイル数に比例**する。孤児削除（手動）は入ったが**押されるとは限らない**ため、
  ファイル数は単調増加**しうる**（→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」）。
  遠いプロバイダ（Google Drive 等）ほど効く。
- **対応候補:** 削除ではなく**分割**で解く。ファイル名が `sha256Hex(相対パス)` なので、
  **先頭1桁で16フォルダへ分ける**と1件の照合で列挙する件数が 1/16 になる。
  引く側はキーから所属フォルダを計算できるので探索は要らない。
  **生きた痕跡を1つも消さずに性能だけ守れる**のが孤児削除に対する優位点。
  → [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」
- **着手の契機:** 実機で列挙の遅さが体感できたとき。既存ファイルの移行を伴うので、それまで動かさない。
- **規模感:** 中（移行と実機確認を伴う）。

## FOLD-6. 開いた Fold を横に持つと、本文と余白ペインの2面が出ない

- **状態:** 未着手（2026-10-17 起票）。オーナーが実機で見て気になった。
- **現状:** 開いた内側の画面を横に持つと、折り目が横になる。[fold_experience](../dev/system/fold_experience.md) の姿勢の割り当てでは横の折り目は縦積みで、補助の面（余白ペイン）は出さない。
  平らに開いたまま横に持った場合も、卓上の形と同じ扱いになる。
- **問題:** 開いた Fold を横に持つと、縦に持ったときの左右2面（本文と余白ペイン）が使えない。仕様どおりの動きだが、横に持って読む場面で余白が出ない。
- **対応候補:** 着手時に決める。正本の契約での行き先は「上に主、下に補助」だが、書くとキーボードが下を覆うので、この形で読む頻度を確かめてからとしている。
  平らに開いた横持ちを卓上の形と分けて扱うかも、あわせて決める。
- **受理条件:** 開いた Fold を横に持ったときの面の出し方をオーナーが決め、その形で余白ペインを使えるか、使わない理由が正本に書かれている。
- **規模感:** 中（姿勢の判定と並べ方の変更を伴う）。

## PROC-6. 開発の仕組みが効いているかを、数字で測れない

- **出どころ:** ISUCON2026 の優勝者は、過去問などを元にした評価環境で100回以上解かせてハーネスを直したと[参加記](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)に書いている。こちらには同じ課題で比べる場が無いと気づいた。
- **現状:** 検査と教訓は起きた失敗から増えている（教訓55件のうち検査つき24件、`architecture` の検査28本）。効き目を測るものは無い。解決済みの指摘とレビュー本文は消す運用なので、捕まえた数も残らない。変異確認は手作業である。自分を評価する規則は一度失敗している（→ [L32](../dev/lessons/L32.md)）。
- **問題:** 検査や文書を足した・削ったことで生成の質が上がったのかを判断できない。費用に見合わない規則を見分けられない。
- **対応候補:** 過去の修正コミットを過去問にする。親コミットへ戻した一時の worktree で課題文だけを渡して解かせ、その修正で足されたテストを隠しテストにして合格率を測る。10問ほどから始め、仕組みを変えた前後で比べる。固定の材料で測る形は `SummaryCoverageCalibrationTest` に先例がある。
- **懸念:**
  - **答えの混入。** 今の CLAUDE.md と教訓には過去の修正の答えが書かれていることがあるので、そのまま渡すと問題にならない
  - **隠しテストの偏り。** 修正時の名前や形に依存するテストは、別の正しい解き方を落とす
  - **測れない範囲。** 見た目と手触り、実機でしか出ない不具合は測れない
  - **費用。** 優勝者は競技1回で約1.3億トークンを使っている（大半はキャッシュの読み出し）
- **受理条件:**
  - 過去問10問以上を同じ手順で解かせ、合格率を出せる
  - 仕組みを1つ変えた前後で比べた結果が1回以上ある
  - 答えの混入の除き方が書かれている
  - 実行の契機と担い手が決まっている（文書の規則だけでは実行されない）
- **規模感:** 中（足場の作成と、問題の選別）。トークンの消費が別に要る。

## MEMO-20. 痕跡の書き込みの途中で落ちると、そのノートの余白メモが読めなくなる

- **状態:** 未着手（2026-11-14 起票）。Fable 5.2 の見直しで挙がり、オーナーが採用した。実際に壊れた事例は出ていない。
- **現状:** 余白メモ（1ノート20件）と本文の引用は、痕跡ファイル（1ノート1ファイル）に入る。書き込みは直接の上書きで、途中でプロセスが落ちると checksum が合わない壊れた痕跡になる。
  壊れた痕跡はそのノートの記録を止め、整理画面から手で消すしかない（→ [reflect_margin_memo](../dev/features/reflect_margin_memo.md) §10）。退避は手動だけである。
  読めなかったときに上書きしない守りは入っていて、穴は書き込みの途中だけに残る。
- **問題:** 痕跡をベストエフォートとした判断は、機械が取る訪問の記録に対するものだった。今は利用者が書いた言葉が同じファイルに入り、壊れたときの出口が言葉を失うことだけになっている。
  本文を書く蒸留は復旧レコードを持つ。
- **対応候補:** 書く前の中身を端末内に1世代だけ控え、壊れた痕跡を見つけたらメモを控えから戻す（蒸留の復旧レコードと同じ型）。
  または、checksum が合わなくても読める範囲でメモだけを救う。
  **書きかけと預かりがプロセス終了で消える件を同じ控えに載せるかは、着手時に一緒に決める**（設計書は範囲外と宣言している）。
- **受理条件:** 書き込みの途中で止めた痕跡から、保存済みのメモが失われないことを JVM テストが固定している。壊れた痕跡の出口が「手で消す」だけでない。
- **規模感:** 中。

## AI-11. 部分要約と蒸留が、端末AIの失敗を英文のまま出す

- **状態:** 未着手（2026-11-14 起票）。Fable 5.2 の見直しで挙がり、オーナーが採用した。
- **現状:** AICore の回数制限を日本語の案内へ置き換えるのは要約だけである。節を1つ頼んだ部分要約は例外の文をそのまま赤字で出し、蒸留の開始の失敗も同じ。
  全節の要約は断られても待ってやり直すので出ない。
- **影響:** 混み合っただけのときに英語の文が出て、待てば使えることが伝わらない。
- **対応候補:** 回数制限かどうかを見て文言を選ぶ関数を1つにし、要約・部分要約・蒸留が呼ぶ。
- **受理条件:** 回数制限で断られたとき、3つの経路とも日本語の案内が出ることを JVM テストが固定している。
- **規模感:** 小。

## MD-5. リストの項目の下に字下げして置いた引用が、`>` の付いた段落のまま出る

- **状態:** 未着手（2026-11-25 起票）。引用とコールアウトの中を描く変更の範囲を決めるときに Vault を数えて見つけ、その変更の範囲の外に置いた。
- **現状:** 引用は行の頭の `>` でだけ読む（[`parseMarkdownBlocks`](../../app/src/main/java/com/example/newproject/domain/markdown/MarkdownBlocks.kt)）。
  `- 項目` の下に `  > 引用` と字下げして書くと、リストはそこで終わり、引用の行は `>` の付いた段落として出る。
  2026-11-22 に Mac の写しの Vault で数えると101行あった（端末の Vault と同じ中身かは確かめていない）。
- **問題:** Obsidian ではリストの項目の中の引用として読まれる書き方が、記号のまま読まれる。リストの続きの段落も同じく扱わない。
- **対応候補:** リストの項目の続き（字下げした行）を項目の中身として読み、その中の引用を引用として描く。引用の中を描く形（→ [markdown_rendering](../dev/system/markdown_rendering.md) §8）と同じく、
  AI へ渡す文と索引を変えないかを着手時に決める。
- **受理条件:** 字下げした引用とその中の表・箇条を、リストの項目の中で引用として描くことを JVM テストが固定している。本文と見開きで実機で確かめる。
- **規模感:** 中（リストの解析に項目の中身を持たせる）。

## PERF-5. 見出しが本文を挟まず長く続くと、見開きの組版が二乗の手間になる

- **状態:** 未着手（2026-11-27 起票）。見開きの境目でまとまりを割らない変更の Codex レビュー（spread-keep 1回目）の指摘。
- **現状:** まとまりの頭で見出しの節が入るかを確かめる [`paginateSpread`](../../app/src/main/java/com/example/newproject/ui/screen/SpreadPagination.kt) は、
  見出しの連なりの頭から節を詰めてみて、入らなければ次の見出しへ進み、また連なりの頭から詰め直す。節の末尾の本文の無い見出しを節に数えないため、
  見出しは本文が続くまで詰めず、ページの上限での打ち切りも効かない。
- **問題:** 同じ階層の見出しを本文を挟まず2万並べると、ブロックの参照が約2億回、デスクトップ JVM で約43〜49ms になる（8,000で約6.6ms）。
  組版は測った区切りごとに Main で走り直すので、正本 §9 の連続占有の目安（約8ms）を超えて表示と入力を止める。本文1MB・1ブロック8,000字の制限の中で起きる。
- **対応候補:** 連なりの中で節の終わりと本文の有無を一度の走査で求め、候補を縮めるたびに連なりの頭へ戻らない。末尾の本文の無い見出しを節に数えない規則と、途中で出した見開きの不変は保つ。
- **受理条件:** 同じ階層の見出しを8,000・16,000・20,000並べ、末尾の本文の有無と測り終えたかの両方で組めること。
  節の候補を探す手間が入力数の定数倍に収まることを回帰検査で固定する（例: 2万でブロックの参照が200万回以下）。同じ入力で Main の連続占有が §9 の目安に収まり、
  既存の末尾の見出しのテストと、途中で出した見開きが測り終えた組版と一致するテストが通る。
- **規模感:** 小〜中。
