## AI-5. 関連ノートが算出した根拠を捨てている

- **出どころ:** 既存機能の強化点を洗う目的で、オーナーの体感を実装に当てて見つけた。
  原因はプロンプトではなく、AIの外側で根拠の値が上へ伝わっていないことにある。
- **現状:** [`relatedContextScore`](../../app/src/main/java/com/example/newproject/domain/RelatedContextScoring.kt) は
  **タグ一致・本文スニペット類似・タイトル類似を個別に計算**しているが、
  `CandidateScore(score, tieBreak)` という **Double 2つへ畳んで**返す。
  畳んだ後は並べ替えにしか使われず、[`RelatedTab`](../../app/src/main/java/com/example/newproject/ui/screen/RelatedTab.kt) が
  表示するのは `isWikilinked` だけ。
- **影響:** 「なぜこのノートが関連なのか」が画面から分からない。
  **根拠は計算済みなのに捨てているので、表示するのに新しい計算もAI生成も要らない。**
- **不具合ではなく強化。** ただし A-3（ピッカーに1行要約を添える）が Nano 生成を要するのに対し、
  **こちらは追加コストがゼロ**なので、納得感を上げる手段として先に検討する価値がある。
- **対応候補:** `CandidateScore` に内訳を持たせるか、上位候補についてだけ主シグナル
  （タグ一致なら一致したタグ名）を返す。**畳む前の値を1段だけ上へ通す。**
- **懸念:** 内訳を出すと「スコアが見える」ことになり、順位への納得と不満の両方を生む。
  **数値ではなく「タグが一致」のような質的な表示に留める**のが安全。
- **規模感:** 小。

## AI-6. 引用ブロックの問いを、書き手自身の問いとして拾う

- **現状:** 再会カードの候補列挙は
  [`stripMarkdownMarkers`](../../app/src/main/java/com/example/newproject/domain/MarkdownPlainText.kt) を通してから
  文へ割るが、`LINE_PREFIX` が**行頭の `>` を見出し記号や箇条書き記号と一緒に落とす**。
  結果、`> これでいいのか。` は本文の地の文と区別が付かないまま
  [`scanReunionCandidates`](../../app/src/main/java/com/example/newproject/domain/ReunionCandidateScanner.kt) の
  問い候補に入る。
- **影響:** 引用した他人の問いが**候補枠を埋め**、書き手自身の問いが選ばれにくくなる。
  選ばれてしまった場合は「前回のあなたはこの問いで止まっていた」と**事実に反する断定**でカードに出る。
- **同種の混入は一度直っている。** 2026-08-22 の実測で「引用した他人の発言」が問い候補の大半を占めていたが、
  原因は**括弧の内側で文を切っていたこと**で、そこは修正済み（→ [reunion_card](../dev/features/reunion_card.md) §5）。
  **引用ブロックだけが残った** — 括弧と違い、記法を落とす側で消えているため実測にも現れない。
- **AIでは直せない場所にある。** 選別を強めても、候補列挙の時点で引用の情報が失われているので
  AIには引用と地の文の区別が付かない。**非AI段で印を残すことが前提**になる（→ 型1）。
- **対応候補:** `stripMarkdownMarkers` で `>` を落とす前に引用行を判別し、
  問い候補から外すか、候補に「引用である」印を添えてAIへ渡す。
  **落とす対象を減らすのではなく、落とす前に見分ける**（記法は表示・整形の都合で落としている）。
  蒸留側は既に引用行を独立した単位として扱っているので、判別そのものの前例はある。
- **2026-09-27 の測定で、この課題の比重が分かった。** 移行済みの Vault の読んだノート223本に抽出器を当てると、
  引用ブロック（コールアウトを含む）から拾った問いは1本のノートの3件だけだった。
  **引用の形をとらない他人の言葉のほうがずっと多い** — 試験問題の「Q:」、本や記事から写したチェックリスト、
  章の見出し、AIの解説文。引用行を見分けても、これらは地の文と同じ形なので残る。
  **結晶はこの抽出器を使わないと決まった**ので、直すかどうかは結晶と切り離して、再会カードの課題として決める。
- **規模感:** 小。判別と、引用行を含むノートでのJVMテスト。

## REL-1. R8とリリース署名が未設定

- **現状:** `buildTypes { release { } }` と `proguard-rules.pro` は置いたが、
  **`isMinifyEnabled = false`／`signingConfig` 無し**。`assembleRelease` の生成物は
  依然として `app-release-unsigned.apk`（約10MB）で、配布可能性を意味しない。
- **後回しにした理由:** ML Kit GenAI はリフレクションで解決される部分があり、縮小で消えると
  **全AI機能が実機の release ビルドでだけ落ちる**。JVMテストは縮小前のクラスを見るので検出できない。
  Compose の Composable メタデータも同様。つまりR8の有効化は「設定を1行変える作業」ではなく
  **実機検証の計画とセット**になる。
- **対応候補:** keep ルールを書いた上で `isMinifyEnabled = true` にし、release ビルドを実機へ入れて
  `PromptBuilder` の全AI経路を一巡する。
  署名は keystore の保管方針を決めてから。
- **規模感:** 中。実機確認が必須。

  Error になり `lintDebug` タスクが失敗するが、`informational` なら
  **「0 errors, 0 warnings, 12 hints」で成功し、12件はレポートに残る**。
  ゲートに載せずに催促だけ残せる。`--offline` の件数は Lint の最新版情報のキャッシュ次第で、古いと Google Maven 側の8件が出ず4件になる（一度オンラインで解析すれば12件に戻る。2026-09-14 実測）。

  優先して見るべきは2つ。

## PERF-1. 読書痕跡の索引作成がファイル数に比例する

**実測で問題化するまで着手しない。** 先回りで入れると移行リスクだけを先払いになる。

- **現状:** `_ReadingTraces/` はフラットな1階層で、セッション中1回だけ子一覧を全列挙して
  key→参照の索引を作る。容量は問題にならない（1ファイル最大3.3KB・2,000ノートで約1.4MB）が、
  **列挙コストはファイル数に比例**する。孤児削除（手動）は入ったが**押されるとは限らない**ため、
  ファイル数は単調増加**しうる**（→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」）。
  遠いプロバイダ（Google Drive 等）ほど効く。
- **対応候補:** 削除ではなく**分割**で解く。ファイル名が `sha256Hex(相対パス)` なので、
  **先頭1桁で16フォルダへ分ける**と1件の照合で列挙する件数が 1/16 になる。
  引く側はキーから所属フォルダを計算できるので探索は要らない。
  **生きた痕跡を1つも消さずに性能だけ守れる**のが孤児削除に対する優位点。
  → [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」
- **着手の契機:** 実機で列挙の遅さが体感できたとき。既存ファイルの移行を伴うので、それまで動かさない。
- **規模感:** 中（移行と実機確認を伴う）。

## UI-2. Vault を選び直した直後に引くノートが、前のノートで読んでいた位置から始まる

- **状態:** 残りの1経路（2026-10-17）。ランダム・さがす・関連・結晶の元ノート・冊子から開く経路は、先頭から開く境界 `openNoteFromTop` を通し、実機で先頭から始まることを確かめた（→ [rediscover](../dev/features/rediscover.md) §5）。
  本文リンク（見出しつき）と並べ読みの「このノートへ移る」にも回帰は無かった。
- **現状:** Vault を選ぶ画面から戻ったときにノートを引く処理（`MainActivity` の `openVault` の結果）は画面の組み立ての外にあり、本文の一覧の位置（`noteListState`）へ届かない。
- **問題:** 数画面送ったノートを読んでいる途中で Vault を選び直すと、引いたノートが前のノートと同じ段落番号の付近から始まりうる（実機では未確認。コードから見た残り）。
- **対応候補:** Vault を選び直したときにも、ノートを引く前に一覧を先頭へ戻す。
- **受理条件:** Vault を選び直した直後に引いたノートが本文の先頭から始まる。
- **規模感:** 小。

## UI-5. 大きい文字の左右2列で、題名「Rediscover」が語の途中で折り返す

- **状態:** 未着手（2026-10-12 起票）。**優先度は超低**（オーナー判断。文字サイズを大きくすることがまず無いため）。
- **出どころ:** 見出しの丸ボタンを題名の行へ移した変更の実機検証。文字サイズ2.0のカバー横向き（左右2列）の左の列で、オーナーが実機で見て「調整が必要」と回答した。
- **現状:** 見出しの題名の行には、題名と丸ボタン3つ（💬 ✎ ⛶）が並ぶ。左の列の幅では、文字サイズ2.0のとき題名が語の途中で2行に割れる。
  副題も2行になる。ボタンとの重なりや切れは無い。既定の文字サイズでは1行に収まる。
- **対応候補:** 題名とボタンが1行に収まらないときだけ、ボタンを題名の下の行へ回す（題名は大きいまま1語で読める）。

- **受理条件:** 文字サイズ2.0の左右2列で、題名が語の途中で割れない。既定の文字サイズの見出しは変わらない。

  タイトルが分かっていても、粗い絞り込みと Nano の選定で3件から漏れうる。ランダムは Rediscover と役が重なり、偶然に出会いたいときにどちらへ行くかを迷わせる。
- **対応方針（オーナー判断）:**
  - Explore を「タイトル｜AI」の切り替えにする。開いたときはいつも「タイトル」。打った言葉は両方のモードで共有する
  - **タイトル:** 打つたびに Vault 全体のファイル名を部分一致で照らす（AI を使わない）。完全一致 → 前方一致 → 部分一致の順で、3件に限らず並べる。
    大文字小文字と空白の違いは無視し、同じ名前のノートにはフォルダの場所を添える。frontmatter の別名と本文は照らさない。
    打つ前は「今日読んだノート」を出す。0件のときは、同じ言葉で AI のモードへ移って探す1行を出す
  - **AI:** 範囲のチップを「すべて（最初から選択）｜各フォルダ」にし、「ルート直下」は無くす。
    「すべて」では、タイトルが近い40本から選ぶことと、意味で探したいならフォルダを選ぶことを1行で添える。選定は今のまま3件
  - **ランダムは削る。** Vault 全体からの偶然は Rediscover が持つ
  - 走査は Vault 全体を1回にし、Rediscover と同じ一覧を共有する。フォルダの範囲はその一覧を場所で絞り、フォルダごとの走査と Explore だけのキャッシュはやめる。
    最初の1回は全体の走査を待つ（PERF-3 と同じ走査）。`_AI補記`（旧版が書き出したフォルダ）は Rediscover と同じく対象から外れる
  - Explore を開いたときに一覧を1回受け取り、打っている間はその一覧を照らす。打つたびに `NoteScanCache.get` を呼ぶと、寿命の60秒が切れた時点で打っている途中に全走査が走る
  - 走査の途中に来た別の要求は、同じ走査を待つ（同時要求の共有）。`NoteScanCache.get` にこの仕組みが無いので、今のままだと Rediscover の走査中に Explore を開くと走査が2本走る
  - `.obsidian` を走査から外す（DOC-1。全ノートを照らすと、配下の `.md` が候補に出るおそれがあるため）
  - キーボードの確定キーはキーボードを閉じるだけで、AI の検索は走らせない（数十秒かかるので、ボタンを押したときだけ）
- **受理条件:**
  - アプリを起動して Explore を開くとタイトルのモードで、フォルダを選ばずに、どの階層のノートもタイトルの一部を打つだけで出る。並び順が上の規則どおりで、照らす純関数に JVM テストがある
  - Rediscover の走査を終えてから60秒以内なら、タイトルで探すときに走査を待たない（同じ一覧を共有している）
  - Explore を開いたまま60秒を超えて打っても、打っている途中で走査を待たされない
  - 走査の途中に別の要求が来ても走査は1本で済む（走査中の2要求のテスト）。Vault を切り替えた後の要求は、旧い走査を共有しない（A→B→A のテスト）
  - `.obsidian` に `.md` がある fixture で、そのノートがタイトルの結果にも Rediscover にも出ない
  - AI のモードは最初から「すべて」で探せ、フォルダを選べばそのフォルダの中（奥まで）だけから選ぶ。タイトルが0件の行から、同じ言葉で AI の検索へ移れる
  - Vault を切り替えた後に、旧 Vault の一覧・結果・範囲を使わない（今の世代の照合を保つ）
  - Explore にランダムが無い。正本 ai_picker（概要・詳細機能一覧・ユーザーフロー・判断1・ランダムの件数の理由）が新しい形に直っている
- **規模感:** 中（タイトルを照らす純関数・全体の一覧を Explore から引く口・画面の作り直し・ランダムの削除・正本の書き換え）。

- **対応方針（オーナー判断）:**
  - 見出しの 💬 を「全節を要約」にする。面の「この節を要約」は、今の節を1本頼む入口として残す

  - 1回に作る節の数に上限を置く（実機の速さで決める。目安は1〜2分ぶん）。今の節から先へ順に作り、上限で止める。
    上限を超えるノートは「12節中10節」のように部分的に作ったことを示し、もう一度 💬 を押すと続きから作る
  - 作った節の要約は、本文を読み進めて面の節が替わると、押さずに面に出る
- **実装の前に、節の要約1回の所要時間を実機で測る。** 上の3〜8秒は見込みで、[feature_ideas](feature_ideas.md) A-1 は1回数十秒と書いている。

- **作った要約はノートを替えると消える。** 1〜2分かけた結果も同じで、保存しない判断は変えない。保存するなら [feature_ideas](feature_ideas.md) P-1 の側で別に決める
- **着手時に決めること（Claude の提案）:**
  - 今の節から末尾まで作り終えて上限に余りがあれば、先頭から今の節の手前を作る
  - 全節は「作る節の列」として持ち、1つの生成係が先頭から1節ずつ取り出す。今の「生成中に別の節を頼むと前の生成を取り消す」1本の形は、全節の間は使わない

    生成中の節は取り消さず最後まで作る。まだできていない節の面には、ボタンの代わりに「次に作ります」と出す
  - 全節の生成中に「この節を要約」で頼んだ節も、同じ並べ替えで済ませる。割り込んだ節ができたら、列の残りへ続きから戻る
  - 本文がごく短い節（見出しだけ・数行）は作らない。線は実機で決める
  - 💬 の記号は、生成中は進み具合（例: ⏳ 3/12）、作り終えたら ✓、出せなかった節があれば ! にする。全節の生成を止める口を置く
  - 生成は1節ごとに錠を取り直し、間にほかの自動の生成（再会カード・関連など）が入れるようにする（今の `AiClient` の直列化のまま）
- **受理条件:**
  - 見出しの 💬 を押すと今の節から順に要約ができ、読み進めると押さずにその節の要約が面に出る。上限を超えるノートでは部分的と示され、押し直すと続きから作る

  - ノート切替・Vault 切替・蒸留の差し替えで全節の生成を止め、要約を捨てる（契約2箇所への登録のまま）。止めた後に古い生成の結果が書かれない。
    両方向のテスト（全節の生成中に1節を頼む・1節の生成中に全節を頼む）と、走行の印が残らないテストがある
  - 割り込んだ節（読む位置へ合わせた並べ替えと「この節を要約」のどちらでも）ができた後、列の残りが続きから最後まで作られる
  - 1節の失敗や「生成を中止」はその節を飛ばすだけで、全節の生成は止まらない。全節を止めるのは 💬 側の口だけ
  - 実機で、節の多いノートの所要時間と、ほかの自動の生成の遅れを測り、上限の値を決めている
  - 正本 section_ai_chat（概要・詳細機能一覧・ユーザーフロー・上限・判断2）と、[margin_pane](../dev/features/margin_pane.md) §5.4 の入口の記述が新しい形に直っている
