## 1. 高優先度

### 1-1. 検索フォールバックの意味差
- **現状:** 自然文検索の候補が40件以下のとき、bigramによる並べ替えを行わず SAF が返した候補リストの**先頭3件**をそのまま返す。一方、画面文言は「キーワード一致で表示しています」。
- **問題:** AI非対応・未ダウンロード時のフォールバックが、文言の示す「キーワード一致上位」になっていない。
- **対応候補:** `SearchPickerUseCase` のフォールバックを候補数に関係なく bigramスコア順に統一し、UI文言と実装を一致させる。（解析書 §6.5 / §14.2 / §15-1）
- **規模感:** 小。純粋ロジック側で完結しやすくテストも書きやすい。

### 1-2. TimeCapsule 着手の第一関門 — vault相対パス生成
- **現状:** `NoteRepository` のBFS走査（`collectNotesRecursive`）は `documentId`／`displayName` は取得するが、ルートからの**相対パス文字列を保持していない**（`NoteFile` は `name`／`uri`／`lastModified` のみ）。
- **問題:** TimeCapsuleの可搬キー（主キー＝vault相対パス）に相対パスが必須。ここが実装の最初のブロッカー。
- **対応候補:** BFSのキュー要素を「documentId＋そこまでの相対パス」の組へ拡張し、子を辿る際に親パス＋子名を連結して `NoteFile` に相対パスフィールドを追加する。
- **規模感:** 中。リポジトリ層の走査ロジック変更＋既存の `NoteFile` 利用箇所への波及確認が要る。（design/reflect_timecapsule.md 判断4・実装要件）

## 2. 中優先度

### 2-1. Controller共通化のトリガー到達
- **現状:** `QuizController`／`AnnotationController`／`DistillController` が requestId＋Jobガード＋モデルDL自動再開の「相似形」で3つ揃った。解析書 §6.8 に「3機能目が現れた時点で共通化を検討」と明記されている、まさにその地点。
- **注意:** TimeCapsuleはこの型に乗らない（バックグラウンド生成ではなくオンデマンド1回）。共通化の判断は**蒸留までの3つで**行うのが自然。
- **対応候補:** 共通の「requestId採番＋isCurrent()確認＋cancelAndClear()」を薄い基底/ヘルパへ抽出するか、あるいは「相似のまま維持」を明示的に再確認する。（過剰な抽象化を避ける判断も選択肢）
- **規模感:** 中。設計判断を伴うため、まず方針をdesign/へ残すのが望ましい。

### 2-2. 解析書ヘッダの未追従
- **現状:** `source_code_analysis.md` のヘッダは「対象ブランチ `feature/Improve_AI_Function_RelationalNote` / 対象コミット `aae2ea8`（PR #25・#26）」のままだが、本文 §6.10 には蒸留（PR #32）が反映されている。ヘッダと本文でカバー範囲がズレている。
- **対応候補:** 次回更新時にヘッダを `d056e63` 基準へ更新し、規模表（§2.1）の行数・テスト数も蒸留・クイズ改善分で更新する。
- **規模感:** 小。ドキュメント整備。

### 2-3. Job管理の不統一
- **現状:** クイズ・補記・蒸留は requestId＋Job で保護済み。一方、検索・スコープ内ランダム・補記一覧/削除・要約側のモデルDL Job は要求単位で追跡されない。
- **問題:** 短時間に複数要求できる経路で、完了順による状態上書きの余地が残る。将来UI導線が増えると顕在化し得る。
- **対応候補:** 検索にも Job または requestId を導入し、最後の要求だけが状態を更新できるようにする。（解析書 §10.1 / §14.2 / §15-2）
- **規模感:** 中。

### 2-4. AI入力の先頭固定長切り出し
- **現状:** 要約・関連・クイズ・補記いずれも `String.take()` による文字数上限で、意味境界やトークンで切っていない。長いノートの後半（結論が末尾にある等）はAI入力に含まれない。
- **対応候補:** 見出し・冒頭・末尾・重要語を考慮した抽出へ発展させる。ただしNanoの入力予算とのトレードオフあり。
- **規模感:** 中〜大。品質改善だが検証が要る。

## 3. 低優先度（顕在化していないが記録）

### 3-1. 統合テスト不足
- SAF走査・補記保存/削除・Gemini Nano・Compose Navigation・全画面遷移・連続操作時の競合を絡めたテストがない。ローカルユニットテストは純粋ロジックの回帰防止には有効だが、実端末依存の動作は保証範囲外。
- 対応候補: Fake `ContentResolver` または instrumentation テストで Vault走査・保存・削除を検証。（解析書 §13.3 / §15-5）

### 3-2. エラー通知の握りつぶし
- フォルダ一覧取得失敗はユーザーに通知されない。補記削除は `deleteDocument()` の戻り値を確認せず一覧を再読込する。閲覧履歴のJSONパース失敗は空履歴扱い。
- 対応候補: 少なくとも削除失敗・フォルダ取得失敗に明示エラーを出す。（解析書 §11.2）

### 3-3. AI状態の一時エラーと非対応の同一視
- `checkAvailability()` 自体の例外を `Unavailable` にまとめるため、非対応端末と一時的な状態取得失敗を区別できない。
- 対応候補: AI非対応・モデル未準備・一時エラーのUXを要約・検索・クイズ・補記で統一する。（解析書 §11.2 / §15-8）

### 3-4. その他の既知の限定実装
- YAML解析が簡易（複雑なYAML・ネスト・複数行値は未対応 → tags/aliasesの取りこぼし）
- Markdownが限定実装（ordered list番号・クリック可能リンク・画像・埋め込み・数式は未対応）
- キャッシュTTL 60秒により外部同期・編集結果の反映が最大60秒遅れる

## 4. 横断テーマ（課題の背景にある構造）

1. **Nano制約が全設計を規定している** — 出力256トークン上限・Mutex直列化・60秒タイムアウトが、要約字数・クイズ形式・補記項目数・TimeCapsuleの「オンデマンド1回」まで決めている。新機能はこの制約と必ず衝突するため、判断軸として明文化する価値がある。
2. **機能ごとに堅牢性レベルを変える方針への転換** — 蒸留（重厚な原子性・復旧）→ TimeCapsule（シンプル最優先・ベストエフォート）。この使い分けは健全だが、どの機能をどのレベルで守るかの基準を残すと再現性が上がる。
3. **文言と実装の乖離** — 検索フォールバック（1-1）が代表例。機能追加が続く中で、小さいうちに潰すのが得策。
