## IMG-1. 寸法未確定の画像がある間の進捗報告が到達率を水増しする

**画像表示（N-3）の設計が最重要とした保護が、まだ閉じていない。**
→ [design/note_image_rendering.md](../dev/design/note_image_rendering.md) §6

- **現状:** 寸法が取れるまでのプレースホルダは画面1枚ぶんの高さを確保する。
  これは「初期オフセットが0なら直後のブロックを隠す」ことしか保証せず、**元画像の高さの上限ではない。**
- **成立する順序:** ①縦長画像の途中まで通常表示でスクロールする ②全画面へ入る —
  [`FullscreenNoteScreen`](../../app/src/main/java/com/example/newproject/ui/screen/FullscreenNoteScreen.kt#L108) は
  `rememberLazyListState(tabListState.firstVisibleItemIndex, tabListState.firstVisibleItemScrollOffset)` で
  **位置を引き継ぐ** ③全画面側は新規コンポジションなので寸法は未確定で、画像は1画面ぶんしかない
  ④引き継いだオフセットが仮の高さを超えると、後続ブロックが可視項目になる
  ⑤`ReadingProgressReporter` が後続indexを報告し、最深到達点は後から下がらない。
  **寸法取得を待っている間にスクロールした場合も同じ**。
- **設計時の判断が誤っていた:** 設計書 §6 は「大きすぎる確保は到達率を低く見積もるだけ」と書いたが、
  これが成り立つのは**プレースホルダが実際の高さ以上のとき**だけで、画面高はそれを保証しない。
  **「誤るなら大きい側へ」は方向としては正しいが、画面高はその『大きい側』になっていない。**
- **影響:** 見た目の一時的なずれではなく、**未読位置が最深到達点としてサイドカーへ永続化される。**
- **対応候補:** 任意に大きい仮高を置くのをやめ、**寸法未確定の画像より後ろの進捗を報告対象から外す。**
  または通常表示と全画面で画像寸法を共有し、新しいLazyListへ未計測状態を持ち込まない。
  **最大寸法から巨大な仮高を作る案はスクロール体験を壊すので採らない。**
- **受理条件:** 寸法未確定の画像より後ろのblock indexが `onReadingProgress` へ渡らない／
  縦長画像の途中から全画面へ入っても測定完了前に最深到達点が進まない／
  測定完了後は正しい高さと位置で報告を再開する／通常表示と全画面の両方を含む回帰テストがある。
- **規模感:** 中。報告の抑止をどこへ置くか（`ReadingProgressReporter` か Coordinator か）の判断を含む。

## TRACE-3. 連続削除が同じJobを奪い合う

- **現状:** [`ReadingTraceCleanupController`](../../app/src/main/java/com/example/newproject/controller/ReadingTraceCleanupController.kt#L54) は
  洗い出しと削除に**同じ `job`** を使い、削除のたびに前のJobをキャンセルする。
- **問題:** SAFの `deleteDocument()` は同期的な外部I/Oなので、**キャンセル時点で物理削除だけ完了し、
  その後の状態更新が落ちる**ことがある。さらに各削除は開始時の `current` を捕捉するため、
  AとBを素早く押すと **AのJSONは消えたのに画面に残り**、B完了時には古い一覧を基にBだけを外す。
- **自己修復はするが誤解を与える:** 再洗い出しで整合するものの、その前は「削除に失敗した」ように見える。
- **対応候補:** 洗い出し用のJobと削除を分け、削除は `Mutex` か単一キューで直列化する。
  実行中は同じ候補のボタンを無効化し、完了時は**捕捉した `current` ではなく最新状態から**対象を除く。
  連続2件・洗い出し中の削除・Vault切替中の削除をテストする。
- **規模感:** 小〜中。

## IMG-2. 索引ヒット時に画像の世代が更新されず、古い画像が固定される

- **現状:** 復号キャッシュの鍵へ更新日時（`contentVersion`）を足したが、**その値を取り直す契機が無い。**
  [`VaultImageIndexStore.resolve()`](../../app/src/main/java/com/example/newproject/data/VaultImageIndexStore.kt#L80) は
  `if (!first.isMiss() || now() - loadedAt < ttlMillis) return first` で、**解決に成功したら TTL を見ずに返す。**
  索引の作り直しは「解決に失敗し、かつ索引が古いとき」だけなので、**ヒットし続ける限り世代は初回の値のまま。**
- **成立する順序:** ①初回走査で画像Aの参照と `lastModified = 1` を索引へ保存しBitmapをキャッシュ
  ②Obsidian側で同じ画像Aを上書きし、参照は同じまま `lastModified = 2` になる
  ③TTLを超えて再表示しても古い索引で解決自体は成功する ④再走査されず `contentVersion = 1` のまま
  ⑤鍵が変わらず**古いBitmapを返す。**
- **削除＋同名再作成でも同じ:** 参照が変わっても、古い参照が索引上「ヒット」である限り再走査されず、
  **壊れた表示が固定され得る。**
- **影響:** アプリ再起動またはVault世代の変化まで、更新前の画像か読めない古い参照を表示し続ける。
- **対応候補:** 全Vault走査を毎回行う必要はない。`load()` の直前に解決済みドキュメントの
  `COLUMN_LAST_MODIFIED` を個別照会して鍵に使うか、TTL超過後の最初の画像解決で索引を1回だけ更新する。
  どちらでも**miss再走査の連打防止**と、`lastModified` を返さないプロバイダでの既知制約を明記する。
- **受理条件:** 同じ参照の更新日時が変われば同じ表示幅でも復号し直す／TTL超過後のヒットでも新しい世代を取れる／
  削除・同名再作成で古い参照へ固定されない／壊れたリンクで再コンポーズごとに全走査しない／
  Fake時計と可変の走査結果で「初回load → 外部更新 → 再load」を通す統合テストがある。
- **規模感:** 小〜中。

## AI-3. 完成プロンプトにハード上限が無い

- **現状:** 本文の抜粋には用途別の上限があるが、**完成プロンプト全体を閉じる制約が無い。**
  - [`SectionChatController.sendMessage()`](../../app/src/main/java/com/example/newproject/controller/SectionChatController.kt#L95) は

- **認識はされている:** `PromptTokenBudgetTest` 自身が「定義済み計測プロファイルの回帰であって

- **規模感:** 中。

## DISTILL-1. 蒸留候補に wikilink だけの行が上がる

**出発点は「蒸留のレコメンドがイマイチ。`[[リンク情報]]` が候補に上がってきたが重要ではない」という実感。**
コードを当てたところ、**単一の原因ではなく3層が重なって、リンク行が構造的に有利になっていた。**

- **① リンクを候補から外す規則が、そもそも存在しない。**
  リンク範囲（`linkSpans`）は計算済みだが、使われているのは
  [「文の境界がリンクの内側に落ちたら、その文を捨てる」](../../app/src/main/java/com/example/newproject/domain/DistillSourceModel.kt#L140)
  という**分割位置の保護だけ**である。
  しかも [`DistillTextRange.contains`](../../app/src/main/java/com/example/newproject/model/DistillModels.kt#L18) は
  `offset > start && offset < endExclusive` と**両端を含まない**ため、
  **`[[リンク情報]]` のように文とリンクが完全一致する場合は、両端が一致して判定が false になり素通りする。**
  行がまるごとリンクでも、ふつうの文として候補に入る。
- **② 構造ボーナスが、リンク集の置き場所と一致している。**
  [`structuralWeight`](../../app/src/main/java/com/example/newproject/domain/DistillCandidateScoring.kt#L68) は
  `isParagraphFirst`（+0.3）・`isChunkLast || isNoteLast`（+0.4）・`isHeadingAdjacent`（+0.2）を加点する。
  **Obsidian のノートは「関連」「リンク」を末尾の見出し直下に箇条書きで置く慣習がある**ので、
  リンク行はこの3つを同時に取りやすく、**最大 +0.9** になる。
  短文ペナルティは **-0.25 だけ**（15文字未満）なので、まったく釣り合わない。
- **③ チャンクごとに必ず1件が選ばれる（これが決定打）。**
  `leaders = scored.groupBy { chunkIndex }.values.map { それぞれの最高点 }` の形なので、
  **各チャンクから最低1件が候補に入ることが保証されている。**
  「リンク」見出しのセクションは独立したチャンクになり、**中にリンク行しか無ければ、
  それがどれだけ低スコアでも、そのチャンクの代表として必ず候補になる。**
  KDoc の「全文の各所を残しつつ」という意図どおりの動作であり、**バグではなく設計の副作用。**
- **④ 補助的に、タイトル類似でも有利になりやすい。** スコアの主項は
  `TITLE_WEIGHT * dice(文, ノートタイトル)` で、**wikilink の宛先名は関連ノート名なので
  タイトルと文字が重なりやすい。** `[[` `]]` ごと bigram にしている点も雑音になる。

- **影響:** `MAX_AI_CANDIDATES = 24` / `FINAL_SELECTION_LIMIT = 6` と枠が小さいので、
  **リンク行が入るぶんだけ本来の文が押し出される。** AIが選べば太字になるが、
  **リンクは既にリンクであって、太字にしても読み返しの手がかりにならない。**

- **対応候補（①と③を直すのが本筋。②は触らない）:**
  - **①: 文に占めるリンクの割合で候補から外す。** `linkSpans` は既にあるので、
    文の文字数のうちリンクが占める比率が高いもの（例: 過半）を候補から落とす。
    **完全一致だけを弾く形にすると `- [[A]] と [[B]]` のような行が残る**ので、比率で見る。
  - **③: チャンク代表に下限を設ける。** ただし「全文の各所を残す」意図と正面から衝突するので、
    **一律の閾値ではなく「①で全滅したチャンクは代表を出さない」**とするのが安全。
    リンクだけのセクションは代表を持たない、という形になる。
  - **②の構造ボーナスは変えない。** 末尾・見出し直下・段落先頭が重要なのは一般には正しく、
    リンク集がそこに居るのが問題なので、**リンク側で解くほうが副作用が小さい。**
- **受理条件:** 行がまるごと `[[...]]` の文が候補に出ない／リンクだけのセクションが
  チャンク代表として候補に出ない／**通常の文の中に含まれるリンクは候補から落ちない**
  （リンクを含む普通の文まで消さない）／上記3つを固定する回帰テストがある。
- **規模感:** 小。純関数（`selectDistillCandidates` と文生成）とテストのみ。
  **プロンプトにもUIにも触らない。**

## ANNOT-1. 補記の評価4項目が重複し、矛盾した出力を許す

**出発点は「補記の評価内容がわかりにくい」という実感。** コードを当てたところ、
[`buildAnnotationPrompt`](../../app/src/main/java/com/example/newproject/ai/PromptBuilder.kt#L219) が
出させている4項目そのものに問題があった。**AIの出来ではなく、出させ方の設計。**

- **① 見出しと中身が一致していない。** `## 粒度評価` の下に「種別／粒度／状態／補記方針」が並ぶが、
  **粒度なのは1項目だけ**。読み手は粒度の評価を期待して分類ラベルと方針を渡される。
- **② 状態と補記方針が、同じことを2回言っている。** 7つの状態のうち4つが方針と1対1で対応する
  （具体例不足→具体例を足す／背景不足→背景を補う／自分の解釈不足→自分の解釈を書く／論点過多→構成を整理する）。
  **2回選ばせても情報が増えない。**
- **③ 「状態: 十分」でも補記方針を必ず1つ選ばされる。** 補記方針の固定選択肢に**「補記不要」が無い**ため、
  十分と判定したノートにも「具体例を足す」等が付く。**出力が自己矛盾する。**
  これは②の写像から漏れている3つの状態（十分／書きかけ／次アクション不足）のうち、
  「十分」だけが方針を持てない構造になっていることが原因。
- **④ 選択肢の語が読み手に伝わらない。** 「原子メモ」は Zettelkasten の用語で、
  「断片／原子メモ／中粒度／長文」の境界も定義されていない。**AIも一貫して選べない。**
- **対応候補:** 4軸を**「次に何をするか」が決まるものだけ**へ絞る。
  実質は「補記方針（＋補記不要）」1つと、その判断理由で足りる。
  種別・粒度は分類欲を満たすだけで、**ユーザーの次の行動を変えていない。**
  減らすなら §0 の「行動が決まらないラベルは出さない」を先に言語化してから決める。
- **規模感:** 小。プロンプトの選択肢定義のみ。**プロダクトの構造には触らない。**

## ANNOT-3. 本命セクションが空の補記メモが保存される

[`AnnotationComposer`](../../app/src/main/java/com/example/newproject/domain/AnnotationComposer.kt#L31) の
2つの挙動が噛み合っておらず、**中身の無い補記ファイルがVaultへ残る。**

- **現状:** `hasAnnotationBody` は `REQUIRED_SECTIONS.any { ... }` で、**どちらか片方に中身があれば保存を通す**。
  一方 `ensureAnnotationSections` は欠けたセクションを**空の見出しとして補完する**。
  したがって **「粒度評価」だけ埋まって「補記すべき内容」が空のファイル**が正常に保存される。
  **本命が空でも通る門番になっている。**
- **出力の検証がまったく無い。** プロンプトは4項目を固定選択肢から選べと指示し、
  補記3行には "MUST reference a specific concept, claim, or term that actually appears in this note" と
  強く要求しているが、**守られたかを誰も確認していない。**
  蒸留が [`parseDistillResponseIds`](../../app/src/main/java/com/example/newproject/domain/DistillResponseParser.kt#L11) で
  IDを `validIds` と照合しているのと対照的で、**同じ製品内で検証の強さが揃っていない。**
- **影響:** ユーザーのVaultに、開いても何も書かれていない `AI補記メモ` が増える。
  空振りだと分かるのは開いた後なので、**補記機能そのものの信頼を落とす。**
- **対応候補:** `any` を「補記すべき内容は必須」へ変える。
  固定選択肢は集合と照合し、外れた値は既定へ落とすか再生成する。
  補記3行がノート内の語を含むかは、既存の
  [`textBigrams`](../../app/src/main/java/com/example/newproject/domain/RelatedCandidateScoring.kt#L19) で機械的に測れる。
- **受理条件:** 「補記すべき内容」が空の応答は保存されない／固定選択肢外の値が保存用Markdownへ出ない／
  空補完で作られた見出しだけのファイルが生成されない回帰テストがある。
- **規模感:** 小。純関数とテストのみ。

  **「0 errors, 0 warnings, 12 hints」で成功し、12件はレポートに残る**。
  ゲートに載せずに催促だけ残せる。
- **残っている問題:** 方針ができても**依存は12件古いまま**で、1件も上げていない。距離の内訳は
  [dependency_policy.md](../dev/design/dependency_policy.md) §4 のスナップショットにある。
  優先して見るべきは2つ。
  - **`com.google.mlkit:genai-prompt` 1.0.0-beta2 → beta4 は当面着手しない（2026-08-01 決定）**
    → [design/dependency_policy.md](../dev/design/dependency_policy.md) §5。公開APIの削除はゼロでソース互換だが、
    **`maxOutputTokens` の未指定時の既定値が 256 → 4096 へ変わる。**
    実測の `getTokenLimit()` が 4,352 なので入力に許されるのは256トークンだけになり、
    **最小の読書痕跡要約（349）すら通らない。** つまり**そのまま上げると8経路すべてが止まる。**
    上げるなら `maxOutputTokens` の明示設定が**前提条件**で、値の決定・AI 8経路の実機一巡・
    基準線の再取得がセットになる。**新版が出たことは上げる理由にならない**ので、
    beta4 の新機能（構造化出力・`SystemInstruction`）を実際に使いたくなるまで動かさない。
  - **Compose BOM（2024.09.03）はLintの指摘に出てこない。** `platform()` 宣言が更新対象として
    見られていないためで、最新である意味ではない。**棚卸しの自動検出から漏れる唯一の枠**なので手で確認する。
- **規模感:** 調査は小。更新の実行はグループごとに小〜中で、いずれも実機確認を伴う。


## PERF-1. 読書痕跡の索引作成がファイル数に比例する

**実測で問題化するまで着手しない。** 先回りで入れると移行リスクだけを先払いになる。

- **現状:** `_ReadingTraces/` はフラットな1階層で、セッション中1回だけ子一覧を全列挙して
  key→参照の索引を作る。容量は問題にならない（1ファイル最大3.3KB・2,000ノートで約1.4MB）が、
  **列挙コストはファイル数に比例**する。孤児削除（手動）は入ったが**押されるとは限らない**ため、
  ファイル数は単調増加**しうる**（→ [design/reflect_reading_trace.md](../dev/design/reflect_reading_trace.md) §14）。
  遠いプロバイダ（Google Drive 等）ほど効く。
- **対応候補:** 削除ではなく**分割**で解く。ファイル名が `sha256Hex(相対パス)` なので、
  **先頭1桁で16フォルダへ分ける**と1件の照合で列挙する件数が 1/16 になる。
  引く側はキーから所属フォルダを計算できるので探索は要らない。
  **生きた痕跡を1つも消さずに性能だけ守れる**のが孤児削除に対する優位点。
  → [design/reflect_reading_trace.md](../dev/design/reflect_reading_trace.md) §13 判断14
- **着手の契機:** 実機で列挙の遅さが体感できたとき。既存ファイルの移行を伴うので、それまで動かさない。
- **規模感:** 中（移行と実機確認を伴う）。

## MAINT-2. `GradientHeader` の全幅化が呼び出し側との手動契約になっている

**単独では着手しない。** 該当ファイルを別の理由で触るときに、ついでに直す。

- [`GradientHeader`](../../app/src/main/java/com/example/newproject/ui/component/GradientHeader.kt#L50) の
  `horizontalBleed = 20.dp` は、呼び出し側の水平余白と一致している前提で成立する。現在の画面では
  合っているが、**余白を変えた瞬間に見出しだけがずれる**。レイアウトテストは無い。
  配色は「テストで強制する」ところまで持っていったのに対し、寸法の対応関係は約束のままである。
- **規模感:** 極小。
