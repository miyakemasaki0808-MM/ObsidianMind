## 2. 中優先度

### 2-9. instrumentationスモークテストがAndroid 16で2件とも起動前に失敗する（2026-07-31 に内容を書き換え）
- **現状:** E案で置いた [`InstrumentationSetupTest`](../../app/src/androidTest/java/com/example/newproject/InstrumentationSetupTest.kt) の2件を
  Android 16 エミュレータで初めて実行し、**0 success / 2 failure** だった。例外は次のとおり。

  ```text
  NoSuchMethodException: android.hardware.input.InputManager.getInstance []
  ```

- **問題:** 失敗はテスト本体へ入る前の Compose／Espresso のアイドル待機初期化で起きる。
  Contextを見るだけのテストにもクラス共通の `createComposeRule()` が適用されるため、2件が同じ理由で止まる。
  **依存とRunnerはコンパイルできるが、「Runnerが起動しComposeを描画できる」は実証できていない。**
  この状態でSAF・Navigationの実テストを書き始めると、失敗時に「土台の故障」と「テスト対象の故障」を
  切り分けられない — スモークテストはまさにその切り分けのために置いたので本末転倒になる。
- **CIでは検出できない:** [ci.yml](../../.github/workflows/ci.yml) は `assembleDebugAndroidTest` までで、
  エミュレータ上の実行は行わない。組み立ては成功するので、この失敗はCIを素通りする。
- **対応候補:** ①Contextだけのテストを Compose ルールのないクラスへ分離し、Runnerの故障とComposeの故障を
  別々に観測できるようにする ②`espresso-core` を 3.6.1 → [3.7.0](https://developer.android.com/jetpack/androidx/releases/test#espresso-3.7.0)
  へ限定更新する（公式リリースノートに同じ反射呼び出しを `getSystemService` へ置き換えたと明記がある。
  必要なら `ext:junit` も 1.3.0 へ揃える）③再実行して2件が通れば実テスト追加へ進む。
  **同じ範囲で直らなければ、結果を記録して依存互換性の独立課題として調査する。**
- **依存更新方針（3-17）と接続した:** テスト依存と対象APIの互換性が実害になったため、
  依存更新はもう「いつか決める保守課題」ではない。ただし対象は AndroidX Test 系のみで、
  Compose BOM や本番依存を含む一括更新には広げない（CLAUDE.md の「機能単位で上げる」に従う）。
- **規模感:** 小〜中。ただし直らない可能性があり、その場合は点数が動かず調査課題が1件増える。

> **2-7（蒸留の復旧チェック）と 2-8（補記の書込後始末）は 2026-07-31 に F-2 として解消したため削除した。**

### 2-5. 関連ノートは抜粋予算の38%を注意書きに払っている（2026-07-28 追加）
- **現状:** AI入力の抜粋化で、抜粋であることを伝える注意書き（226文字）を用途別上限の**内側**から支払う設計にした。上限を超えない不変条件が保てる代わりに、予算の小さい経路ほど占有率が跳ね上がる。

| 用途 | 上限 | 注意書きの占有率 | AIへ届く実本文 |
|---|---:|---:|---:|
| 要約 | 1,200 | 19% | 678文字 |
| 補記 | 1,500 | 15% | 903文字 |
| **関連ノート** | **600** | **38%** | **228文字** |

- **問題:** 関連ノートの現ノート文脈は実質228文字しかなく、骨格・冒頭・末尾に配分すると各部が数十文字になる。**抜粋化の恩恵がこの経路だけ薄い**可能性がある。
- **単独で数字をいじってはいけない:** 関連ノートのプロンプトは候補ブロック3,500文字＋指示文＋タイトルを含む。600だけを見て増やすと完成プロンプトが Prompt API の入力トークン上限に近づく。**実トークン計測が前提。**
- **その計測手段があるかも未確認（2026-07-31 に判明）:** `countTokens()` / `getTokenLimit()` が使えるという前提で書いていたが、**プロジェクト内に呼び出しは1箇所も無く、公式ドキュメントを見ただけでバイナリ確認をしていない**。CLAUDE.md が禁じている型（`maxOutputTokens` の 1〜256 制限を公式ドキュメントから読み取れず全AI生成が落ちた前例）にそのまま該当する。**着手時はまずAARを展開してメソッドの有無を確かめる。** 無ければこの課題は「測ってから判断する」自体が成立せず、別の approach が要る。
- **対応候補:** 関連ノート専用の短縮注意書きを持たせる（候補側は既にID提示で構造化されているため、注意書きを削っても誤読しにくい）／上限を800→1,000の順で単独調整する。どちらも計測が先。
- **前提:** モデルへ実際に渡ったプロンプトを見る手段が無いため、現状は判断材料が無い（→ feature_ideas D-1 プロンプトログ）。
- **規模感:** 小（短縮注意書きのみ）〜中（予算調整まで含める場合）。

### 2-3. 読書痕跡の孤児ファイルと move/rename 追従
- **現状:** `_ReadingTraces/<相対パスのSHA-256>.json` は相対パスでしか引き当てない。ノートを削除・改名すると対応する痕跡は**誰も掃除せず**、新しいパスで別ファイルが作られる。掃除APIもオプション画面の導線も存在しない。
- **問題:** 容量は問題ない（1ファイル最大3.3KB・2,000ノートで約1.4MB）。効いてくるのは**ファイル数に比例する処理**で、年単位の運用で孤児が単調増加する。
- **v1で見送った理由:** 自動削除は、同期途中や一時的な読み取り失敗でノートが走査結果に現れないときに**生きている痕跡を消す**危険がある。move/rename 追従も、引き当てミスが未読ノートで常時起きるためフォルダ全走査のコストが恒常化する。
- **対応候補:** オプション画面に手動の一括削除を置く（`_AI補記` の `AnnotationManagerScreen` と同じ発想）／痕跡に「最後に確認できた日時」を持たせ、長期間見つからないものだけ落とす。（design/reflect_reading_trace.md §8・roadmap X-3）
- **規模感:** 小〜中。

### 2-4. `_ReadingTraces`索引が外部同期の追加を認識しない
- **現状:** [`ReadingTraceStore`](../../app/src/main/java/com/example/newproject/data/ReadingTraceStore.kt#L210) はVaultごとにフォルダの子一覧を1回だけ読み、key→Uriの `FolderIndex` をプロセス内に保持する。自分で作ったファイルは追記するが、TTLも無効化契機も無く、Google Drive等の外部同期で後から増えたファイルを再走査する契機がない。
- **問題:** 別端末で作られた痕跡が同期されても、現在プロセスではカードが出ない。さらに未存在と判断して保存すると、プロバイダによっては同じkeyの重複ファイルを作り、次回索引時にどちらを採るかが列挙順依存になる。
- **対応候補:** 短いTTL、Rediscover照合でミスした場合だけの再走査、またはContentObserver相当の無効化を検討する。毎回全走査は避けつつ、外部追加を最終的に認識できる設計にする。
- **規模感:** 中。同期プロバイダ上での実機確認が必要。

- 対応候補: Fake `ContentResolver` または instrumentation テストで Vault走査・保存・削除を検証。（解析書 §13.4 / §15-5）

### 3-4. その他の既知の限定実装
- YAML解析が簡易（[`parseMeta`](../../app/src/main/java/com/example/newproject/data/NoteRepository.kt#L217) は `---` 囲みの先頭ブロックから `tags`/`aliases` を単純抽出するだけ。ネスト・複数行値は未対応 → 取りこぼし）
- Markdownが限定実装（ordered list番号・クリック可能リンク・画像・埋め込み・数式は未対応）。
  **ordered list の番号は描画だけでなくAI入力でも失われる** — 予算超過ノートの抜粋は同じパーサを通すため、

- キャッシュTTL 60秒（`NOTES_CACHE_TTL_MS`）により外部同期・編集結果の反映が最大60秒遅れる

### 3-15. バッジの塗りが下部ナビ帯の上で判別できない（2026-07-29 追加）
- **現状:** AIタブのバッジは、パネルではなく**下部ナビ帯**の上に載る。ライトのナビ帯は
  ブランド色 `Indigo #4D3DFF` で、その上での塗りのコントラストは
  **Success 1.61・Error 1.04**（非文字基準は3:1）。
- **問題:** 塗りだけではバッジの存在に気づけない。中の記号（「✓」「!」）は
  D案で対の前景に直したので**読めはする**が、それは見つけた後の話。
- **D案で直さなかった理由:** ライトのIndigoは彩度が高く相対輝度も中位で、
  **その上で3:1を取れる塗りがほとんど無い**。直すならナビ帯の色かバッジの明度、
  あるいは輪郭線の追加になり、いずれもブランド配色そのものへ踏み込む。
  [`AppColorContrastTest`](../../app/src/test/java/com/example/newproject/ui/theme/AppColorContrastTest.kt)
  に実測値を固定するテストだけ置いた。
- **見落としの構造:** ダークモード実装時に「塗りには必ず対の前景を持つ」は決めたが、
  **塗り自身が載る面を数えていなかった**。パネル上の3:1は測っていて、同じトークンが
  ナビ帯にも出ることを見ていない。→ 横断テーマ13
- **規模感:** 小〜中（値を決めるだけなら小。ナビ帯の色に触るなら中）。

## 4. 横断テーマ（課題の背景にある構造）

1. **Nano制約が全設計を規定している** — 出力256トークン上限・Mutex直列化・60秒タイムアウトが、要約字数・クイズ形式・補記項目数・ReadingTraceの「生の痕跡を先に出して要約は裏で」まで決めている。新機能はこの制約と必ず衝突するため、判断軸として明文化する価値がある。
2. **機能ごとに堅牢性レベルを変える方針への転換** — 蒸留（重厚な原子性・復旧）→ ReadingTrace（シンプル最優先・ベストエフォート）。この使い分けは健全だが、どの機能をどのレベルで守るかの基準を残すと再現性が上がる。
3. **文言と実装の乖離** — 検索フォールバックが代表例（画面は「キーワード一致」と言うのに実装は列挙順の先頭3件だった。2026-07-25 に解消）。機能追加が続く中で、小さいうちに潰すのが得策。
4. **AIの役割を「創作」から「要約」へ落とすと導線が要らなくなる** — ReadingTrace で得た知見。ユーザーの操作を増やさずに価値を出せるかは、**既にある行動の痕跡で足りないか**を先に問うと判断しやすい。→ [reflect_reading_trace](../design/reflect_reading_trace.md) §2
5. **「意識させない機能」は他の機能と作法が違う** — 通知しない・失敗を見せない・自動DLしない、が仕様になる。AI状態UXの統一（3-3）を進める際、ReadingTrace は横展開の対象外として扱う必要がある。
6. **「対策を入れた」と「対策が効いている」は別** — Vault分離（2026-07-25）は、方針が正しかったぶん実装が効いていなくても文書・コミットメッセージが通ってしまった。修正の主張は、修正コードを別の目で読むまで確定させない。→ [bugfix_reports](../bugfix_reports.md) #4
7. **「整理した」と「境界が効いている」も別**（2026-07-26 追加、2026-07-27 B案で解消） — パッケージのレイヤー別整理（PR #37）は正しい方向だったが、依存の**向き**は制約されないままで循環が4組残っていた。B案では共有型を葉の `model` へ移し、許可方向をimport走査テストで固定した。状態所有も同様に、KDocの約束ではなく機能別Writerで制限した。同じ型がコントラストテストにもあった。既知未達を「失敗させず実測値で記録する」形にしていたため、**テストが全緑でもAA準拠を意味しない**状態が続いていた（2026-07-29 D案で、記録から強制へ移して解消）。**「何を保証していないか」を測定と同じ場所に書く**と、この型の誤読を防げる。
8. **横展開は「最後の1本」を取り残す**（2026-07-26 追加・A案で解消） — モデルDLの世代管理は `QuizController`・`AnnotationController`・`DistillController` の3つに入っているのに、**Controller化されなかった `NoteViewModel` 直書きの1本だけが取り残されていた**。パターンを横展開するときは、**Controller一覧ではなく「同じAPIを呼ぶ全箇所」を検索対象にする**（`grep downloadModel` で4箇所目が出る）。同じ型の見落としは、痕跡の保存が `viewModelScope` に載ったままだった件（C案で解消）にもあった。

9. **テストが「効いている」かは変異させて確かめる**（2026-07-26 追加） — A案の `SummaryControllerTest` は初版が `cancelAndClear()` 経由で書かれていたため、`downloadJob` が止まって requestId ガードに到達せず、**ガードを外しても落ちなかった**。テーマ6の「対策を入れた≠効いている」はテスト自身にも当てはまる。**新しいガードを入れたら、そのガードを1行消してテストが落ちることを確認する**。落ちなければ、テストが検証しているのは別の機構か、そのガードが等価な冗長コードのどちらか（今回は両方あった）。

10. **「純粋」と「軽い」は別**（2026-07-28 追加） — AI入力の切り出しをAndroid依存の無い純関数へ出したのは判断として正しかったが、**その関数は最大1MBの本文をパースして約460msかかり、それを `Dispatchers.Main` のスコープから呼んでいた**。従来の `take()` が実質ゼロコストだったため、「賢くした」結果として新しい負荷が持ち込まれていた。テーマ7（整理した≠境界が効いている）の同族で、**純関数化はテスト容易性を保証するが実行コストについては何も保証しない**。Mainのスコープから呼ぶ純関数は、**入力サイズに比例するかどうか**を必ず見る。

11. **AI出力を別のAI入力へ流す箇所では、改善も劣化も乗算される**（2026-07-28 追加） — 補記プロンプトは本文だけでなく **AI要約と関連ノートも入力として受け取っている**。抜粋化で3つとも同時に良くなったため、補記の改善だけが突出して体感された。裏返すと**要約の品質は補記の品質でもある**ので、上流を触るときは下流の消費者を数えてから優先度を決める。現在の消費関係は「要約 → 補記」「関連ノート → 補記」の2本。

12. **効果の説明と効果の測定は別**（2026-07-28 追加） — 抜粋化がなぜ効くかはコードから筋の通った説明ができるが、**A/B比較はしていない**。さらに予算内のノートはプロンプトが1文字も変わらないため、短いノートでの体感の変化は Nano の出力揺らぎでしかあり得ない。**「モデルに実際に何を渡したか」を見る手段が無い**ことがこの限界の根で、計測器としてのプロンプトログを feature_ideas に D-1 として起票した。テーマ6を「主張」から「効果」へ広げた形になる。

13. **検証条件が実物と一致しているかは、テストが通ることでは分からない**（2026-07-29 追加・同日に自分で踏んだ） — ダークモード実装で「塗りには必ず対の前景を持つ」規約を作り、D案では「既知未達の記録」を「基準の強制」へ移した。方向はどちらも正しい。それでも**初版のD案は全色を `panel #FDFEFF` の上で測っており、それはアプリで最も明るい面だった**。実際に文字が載るのは `panelBlue`、ボタンが載るのはグラデーションで、そこでは 4.19〜4.41 と 1.21〜1.84 で全て未達。テストは全緑だった。**強制していたのは現実に存在しない条件**で、しかも通っている事実が確認を止めてしまうぶん、テストが無いより悪い。悪いことに、この教訓の前身（「色は載る面とセットでしか意味を持たない」）を**同じコミットの文書に書きながら、直している当のトークンには適用しなかった**。教訓を書く行為は適用を保証しない。テストを追加したら、**アサーションが参照している環境（面・背景・親）を実コードから引き当てたのか、代表値で置いたのか**を必ず区別する。→ 3-15

14. **警告を黙らせると、判断の催促も一緒に消える**（2026-07-29 追加） — Lint警告0を達成する際、依存更新系の3チェックを無効化した。「方針が未定のうちは出しても行動につながらない」という理由は正しいが、**黙らせた瞬間から誰も更新を促さなくなる**。特に ML Kit GenAI は beta2 で、SDKの制約がバイナリを見ないと分からない前例がある。**抑制は「やらない」ではなく「いつやるか決める」とセットにしないと、静かな放置に変わる**。抑制した項目は必ず課題として起票し直す（→ 3-17）。同じことは `@Suppress("UsableSpace")` にも当てはまるが、こちらは理由と代替案をコード内に書いたので起票しない。**2026-07-31 追記: この放置に期限が付いた** — androidTestの実行失敗（→ 2-9）がテスト依存の互換性問題だったため、依存更新はもう「いつか決める」では済まなくなった。

15. **「土台を組み立てられる」と「土台が動く」は別**（2026-07-31 追加・E案で踏んだ） — androidTestの依存・Runner・
スモークテスト2件を置き、CIでコンパイルと組み立ても通した。ここまでは正しい。だが**実行したのはその2日後で、
結果は 0 success / 2 failure だった**。組み立てが通る限りCIは緑のままなので、「土台がある」という認識だけが
先に定着していた。テーマ6（対策を入れた≠効いている）・テーマ7（整理した≠境界が効いている）・
テーマ13（テストが通る≠検証条件が正しい）と同じ形で、**今回は「ビルドが通る≠実行できる」**として現れた。
共通するのは、**確認を1段階手前で止めて、その手前の成功を最終的な成功として記録してしまう**こと。
テスト基盤を足すときは、**1件でいいから実際に実行するまでを完了条件に含める**。
