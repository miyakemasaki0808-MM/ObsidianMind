## TRACE-3. 連続削除が同じJobを奪い合う

- **現状:** [`ReadingTraceCleanupController`](../../app/src/main/java/com/example/newproject/controller/ReadingTraceCleanupController.kt) は
  洗い出しと削除に**同じ `job`** を使い、削除のたびに前のJobをキャンセルする。
- **問題:** SAFの `deleteDocument()` は同期的な外部I/Oなので、**キャンセル時点で物理削除だけ完了し、
  その後の状態更新が落ちる**ことがある。さらに各削除は開始時の `current` を捕捉するため、
  AとBを素早く押すと **AのJSONは消えたのに画面に残り**、B完了時には古い一覧を基にBだけを外す。
- **自己修復はするが誤解を与える:** 再洗い出しで整合するものの、その前は「削除に失敗した」ように見える。
- **対応候補:** 洗い出し用のJobと削除を分け、削除は `Mutex` か単一キューで直列化する。
  実行中は同じ候補のボタンを無効化し、完了時は**捕捉した `current` ではなく最新状態から**対象を除く。
  連続2件・洗い出し中の削除・Vault切替中の削除をテストする。
- **規模感:** 小〜中。

## AI-4. AIピッカーだけID契約から外れている

**同じファイルの中に、なぜIDが良いかまで書いてある。**
[`buildRelatedNotesPrompt`](../../app/src/main/java/com/example/newproject/ai/PromptBuilder.kt) の直前のコメント —
「候補は『ID | タイトル』で提示し、モデルにはIDだけ返させる。ID→ノートの解決は UseCase側で確実に行うため、
**言い換え・翻訳・装飾・同名衝突に強い**」。

- **3経路のうち2経路はこの契約で守られている。** 蒸留は `S001` 形式を `validIds` と照合、
  関連ノートは `C01` 形式を [`parseCandidateIds`](../../app/src/main/java/com/example/newproject/domain/RelatedCandidateId.kt) で照合し、
  **候補外のIDを破棄する。**
- **ピッカーだけ生のタイトル文字列を返させている。**
  [`buildPickerPrompt`](../../app/src/main/java/com/example/newproject/ai/PromptBuilder.kt) は "Return only note titles"、
  受け側は [`notesByTitle[title.toNormalizedObsidianTitle()]`](../../app/src/main/java/com/example/newproject/domain/SearchPickerUseCase.kt) で照合する。
- **影響:** AIがタイトルを言い換える・記号を足す・翻訳すると、`mapNotNull` が**黙って落とす**。
  エラーにならないので、**「3件選ばせたのに1件しか出ない」が原因不明のまま起きる。**
  正規化が吸収する範囲を超えた瞬間に結果が減る。
- **これは横展開の取り残しの型。** 方式もその理由も既に書かれていて、適用が1経路だけ抜けている。
  → [lessons.md](../dev/lessons.md) L14
- **2026-08-22、「提示した候補だけを受理する」部分だけ先に閉じた。**
  入力予算で候補が提示から落ちうるようになったため、`PickerPrompt.presentedTitles` を
  照合表の元にした。**タイトルで照合していること自体は変わっていない**ので、
  AIが言い換え・装飾したときに落ちる問題は残る。
- **対応候補:** ピッカーも「ID | タイトル」で提示してIDだけ返させ、`validIds` と照合する。
  `parseCandidateIds` がほぼそのまま使える。
- **受理条件:** AIが装飾・言い換えたタイトルを返しても結果件数が減らない／候補外のIDは破棄される／
  タイトルに記号や同名が含まれる場合の回帰テストがある。
- **規模感:** 小。プロンプト整形とパーサの差し替えで、既存部品を流用できる。

## AI-5. 関連ノートが算出した根拠を捨てている

- **現状:** [`relatedContextScore`](../../app/src/main/java/com/example/newproject/domain/RelatedContextScoring.kt) は
  **タグ一致・本文スニペット類似・タイトル類似を個別に計算**しているが、
  `CandidateScore(score, tieBreak)` という **Double 2つへ畳んで**返す。
  畳んだ後は並べ替えにしか使われず、[`RelatedTab`](../../app/src/main/java/com/example/newproject/ui/screen/RelatedTab.kt) が
  表示するのは `isWikilinked` だけ。
- **影響:** 「なぜこのノートが関連なのか」が画面から分からない。
  **根拠は計算済みなのに捨てているので、表示するのに新しい計算もAI生成も要らない。**
- **不具合ではなく強化。** ただし A-3（ピッカーに1行要約を添える）が Nano 生成を要するのに対し、
  **こちらは追加コストがゼロ**なので、納得感を上げる手段として先に検討する価値がある。
- **対応候補:** `CandidateScore` に内訳を持たせるか、上位候補についてだけ主シグナル
  （タグ一致なら一致したタグ名）を返す。**畳む前の値を1段だけ上へ通す。**
- **懸念:** 内訳を出すと「スコアが見える」ことになり、順位への納得と不満の両方を生む。
  **数値ではなく「タグが一致」のような質的な表示に留める**のが安全。
- **規模感:** 小。

## AI-6. 引用ブロックの問いを、書き手自身の問いとして拾う

- **現状:** 再会カードの候補列挙は
  [`stripMarkdownMarkers`](../../app/src/main/java/com/example/newproject/domain/MarkdownPlainText.kt) を通してから
  文へ割るが、`LINE_PREFIX` が**行頭の `>` を見出し記号や箇条書き記号と一緒に落とす**。
  結果、`> これでいいのか。` は本文の地の文と区別が付かないまま
  [`scanReunionCandidates`](../../app/src/main/java/com/example/newproject/domain/ReunionCandidateScanner.kt) の
  問い候補に入る。
- **影響:** 引用した他人の問いが**候補枠を埋め**、書き手自身の問いが選ばれにくくなる。
  選ばれてしまった場合は「前回のあなたはこの問いで止まっていた」と**事実に反する断定**でカードに出る。
- **同種の混入は一度直っている。** 2026-08-22 の実測で「引用した他人の発言」が問い候補の大半を占めていたが、
  原因は**括弧の内側で文を切っていたこと**で、そこは修正済み（→ [reunion_card](../dev/features/reunion_card.md) §5）。
  **引用ブロックだけが残った** — 括弧と違い、記法を落とす側で消えているため実測にも現れない。
- **AIでは直せない場所にある。** 選別を強めても、候補列挙の時点で引用の情報が失われているので
  AIには引用と地の文の区別が付かない。**非AI段で印を残すことが前提**になる（→ 型1）。
- **対応候補:** `stripMarkdownMarkers` で `>` を落とす前に引用行を判別し、
  問い候補から外すか、候補に「引用である」印を添えてAIへ渡す。
  **落とす対象を減らすのではなく、落とす前に見分ける**（記法は表示・整形の都合で落としている）。
  蒸留側は既に引用行を独立した単位として扱っているので、判別そのものの前例はある。
- **規模感:** 小。判別と、引用行を含むノートでのJVMテスト。

## REL-1. R8とリリース署名が未設定

- **現状:** `buildTypes { release { } }` と `proguard-rules.pro` は置いたが、
  **`isMinifyEnabled = false`／`signingConfig` 無し**。`assembleRelease` の生成物は
  依然として `app-release-unsigned.apk`（約10MB）で、配布可能性を意味しない。
- **後回しにした理由:** ML Kit GenAI はリフレクションで解決される部分があり、縮小で消えると
  **全AI機能が実機の release ビルドでだけ落ちる**。JVMテストは縮小前のクラスを見るので検出できない。
  Compose の Composable メタデータも同様。つまりR8の有効化は「設定を1行変える作業」ではなく
  **実機検証の計画とセット**になる。
- **対応候補:** keep ルールを書いた上で `isMinifyEnabled = true` にし、release ビルドを実機へ入れて
  7つのAI経路（要約・補記・クイズ・関連ノート・セクションチャット・蒸留・読書痕跡の要約）を一巡する。
  署名は keystore の保管方針を決めてから。
- **規模感:** 中。実機確認が必須。

**優先度は超低。** 2026-08-01 に最大の未知だった `genai-prompt` beta4 を調査し切り、

**着手の契機は「新版に必要な機能が入ったとき」であって、新版が出たことではない。**

  **「0 errors, 0 warnings, 12 hints」で成功し、12件はレポートに残る**。
  ゲートに載せずに催促だけ残せる。
- **残っている問題:** 方針ができても**依存は12件古いまま**で、1件も上げていない。距離の内訳は

  優先して見るべきは2つ。
  - **`com.google.mlkit:genai-prompt` 1.0.0-beta2 → beta4 は当面着手しない（2026-08-01 決定）**

## PERF-1. 読書痕跡の索引作成がファイル数に比例する

**実測で問題化するまで着手しない。** 先回りで入れると移行リスクだけを先払いになる。

- **現状:** `_ReadingTraces/` はフラットな1階層で、セッション中1回だけ子一覧を全列挙して
  key→参照の索引を作る。容量は問題にならない（1ファイル最大3.3KB・2,000ノートで約1.4MB）が、
  **列挙コストはファイル数に比例**する。孤児削除（手動）は入ったが**押されるとは限らない**ため、
  ファイル数は単調増加**しうる**（→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」）。
  遠いプロバイダ（Google Drive 等）ほど効く。
- **対応候補:** 削除ではなく**分割**で解く。ファイル名が `sha256Hex(相対パス)` なので、
  **先頭1桁で16フォルダへ分ける**と1件の照合で列挙する件数が 1/16 になる。
  引く側はキーから所属フォルダを計算できるので探索は要らない。
  **生きた痕跡を1つも消さずに性能だけ守れる**のが孤児削除に対する優位点。
  → [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」
- **着手の契機:** 実機で列挙の遅さが体感できたとき。既存ファイルの移行を伴うので、それまで動かさない。
- **規模感:** 中（移行と実機確認を伴う）。

## APP-1. ランチャーの再タップでMainActivityが積み重なり、OPが毎回再生される

**実装済み・実機検証待ち（2026-09-09）。** 対応候補のとおり `onCreate` の先頭で畳んだ。
**検証が済むまで消さない** — 起動経路そのものを触っており、机上では受理条件を満たせない。
実機は [app_launch](../review/device_validation/app_launch.md) の `LAUNCH-01`〜`LAUNCH-05`、
判断の正本は [opening_animation](../dev/features/opening_animation.md) 判断7。

- **出どころ:** 2026-09-05、実機を使っていたオーナーの体感。
  「**アプリ開いた状態で、別のアプリへ遷移。また、Vigilith AIのアプリボタンをタップすると、
  オープニング画面が走る**」。
- **現状:** OPの再生判定は [`MainActivity`](../../app/src/main/java/com/example/newproject/MainActivity.kt) の
  `onCreate` にある `savedInstanceState == null` **だけ**である。
  マニフェストは `launchMode` を指定せず（＝`standard`）、`isTaskRoot` による多重起動の抑止も無い。
  そのため **`MAIN`＋`LAUNCHER` 以外のIntentでタスクが作られると、ランチャーのアイコンが投げるIntentは
  既存タスクと一致しないと判定され、新しい `MainActivity` を積む** → `onCreate(null)` → OP再生。
- **エミュレータで経路を切り分けた（2026-09-05）:**

  | タスクを作った起動のしかた | ランチャー再タップの結果 |
  |---|---|
  | `MAIN`＋`LAUNCHER` 付き（通常のランチャー／Android Studio の Run） | 既存タスクへ復帰し、**OPは出ない** |
  | 素のコンポーネント指定（`am start -n …`） | **タップのたびに `MainActivity` が1枚増える**（1→2→3→4）。毎回OPが走る |

  プロセス破棄からの復帰・回転・Fold開閉では出ない（保存Bundleが非nullになるため）。
  つまり [opening_animation](../dev/features/opening_animation.md) §5 の再生条件は書かれたとおりに効いており、
  **想定されていなかったのは「タスクの基点Intentが食い違う」経路だけ**である。

- **二次症状のほうが重い。** 積み重なった状態では**戻るボタンでアプリを抜けられない** —
  同じ画面が1枚ずつ剥がれるだけになる（4枚積んだ状態から 4→3→2→1 を実測）。

- **実機でこれを踏んでいるのは実機検証そのものである。**
  Codexは実機でのアプリ起動を一貫して素のコンポーネント指定で行っており、
  `LAUNCHER` カテゴリ付きの起動は8月以降1件も無い。2026-08-26 のバックアップ検証では実際にこれを踏み、
  「新しいActivityが起動され下見画面が失われた」として**その試行を判定対象から除外**している。
  **検証手順の側が経路を替えて回避したので、不具合として起票されなかった。**

- **出荷面では現時点で潜在。** intent-filterはランチャー用の1本だけで、通知もディープリンクも無いため、
  通常の利用では踏まない。**ただし通知や共有からの入口を足した時点で表に出る。**

- **対応候補:** `onCreate` の先頭で「`isTaskRoot` でない、かつ受け取ったIntentが `MAIN`＋`LAUNCHER`」なら
  `finish()` して既存タスクへ委ねる。**`launchMode` は変えない** — `singleTask` はタスク親和性ごと挙動が変わり、
  この1点に対して代償が大きい。

- **受理条件:** 素のコンポーネント指定で起動したあとランチャーを3回叩いても `MainActivity` が1枚のまま／
  その状態から戻るボタンでアプリを抜けられる／通常のランチャー起動・回転・プロセス復帰で
  OPの再生条件が変わらない（`ActivityRecreationTest` が緑のまま）。

- **検証側の起動コマンドは決着した（2026-09-09）。** `am start -n`（素のコンポーネント指定）**のままにする** —
  `MAIN`＋`LAUNCHER` 付きへ揃えると基点Intentが一致してランチャー再タップが既存タスクへ復帰し、
  **ガードが一度も呼ばれない**（＝回帰を検知できない）。**この起動でしか作れない状態を見るために、意図して残す。**
  理由ごと [共通手順](../review/device_validation/README.md) へ書いた。

- **規模感:** 小（数行）。ただし**起動経路そのものを触るので実機確認は必須**。

## PROC-1. 「過剰な検証」の実体は検査ではなく文書の量である

- **出どころ:** 2026-09-05、オーナーの検討メモ。要望は「**過剰な検証を抑えたい**」。
  メモは検査を3種（実行時バグ／文書同期／儀式）へ仕分け、2と3を削ることを提案している。
  **仕分けの軸は正しいが、削る対象の見立ては実測と合わない。**

- **測った（2026-09-05 時点。マージコミットを除く直近99コミット）:**

  | | 2026-08-01 | 現在 | 倍率 |
  |---|--:|--:|--:|
  | `app/src/main` の行数 | 15,005 | 26,502 | 1.8 |
  | JVMテスト（`@Test`） | 508 | 1,296 | 2.6 |
  | `architecture/` の検査 | 3 | 19 | 6.3 |
  | `docs/` の `.md` | 27 | 106 | 3.9 |

- **実行費用はほぼゼロである。** JVM 1,293件の合計実行時間は **2.1秒**。
  うち文書の形を守る7本（`AdrShapeTest`・`DesignDocStateNameTest`・`DeviceValidationDocsTest`・
  `ReviewFindingsLedgerTest`・`SchemaVersionDocsTest`・`SourceDocSyncTest`・`WipIssueReferenceTest`）は
  **合計0.6秒**。**「検査が多いから遅い」という筋ではない。**

- **費用は書く側にある。** 直近99コミットの変更行は `docs/` 6,156行に対し `app/src/main` 6,971行で、
  **99件中39件はコードに1行も触れていない。** 検査を消しても減るのは0.6秒だけで、
  **書き換えの手間はそのまま残る。**

- **問題:** 抑えるべきは検査の本数ではなく**正本の数**である。検査はコードと文書の一致を固定するので、
  文書が増えるほど1つのコード変更が要求する書き換えが増える。
  **いま増えているのは文書のほうで（3.9倍）、検査はそれに追随している。**

### 残っている面

- **`owner/` の同伴更新が本当に止まったかは未確認。**
  [`source_code_analysis.md`](../owner/source_code_analysis.md) は docs churn の19%（1,170行）を占め、
  直近99コミット中**7件（259行）はコード変更に同伴していた** — `owner/` は
  「オーナーが指示したときだけ更新する」と決めてあり、検査からも意図して外してある文書である。
  原因だった `CLAUDE.md` の影響面監査の行（正本として `owner/` を名指ししていた）は外した。
  **効いたかどうかは、次の20コミットで同伴更新が0件になるかで見る。**

- **検査を持つ教訓カードは、検査のKDocと本文が重複しやすい。**
  例えば `L49` の見出し文「中止は要求であって完了ではない」は
  `ReadingTraceBackupThreadingTest` のKDocに**同じ文で入っている**。
  **同じ事件を2箇所に長文で書かない**という既存の規約に反しているが、
  どちらを正本にするかは決めていない（検査のKDocは検査を読む人にしか届かず、
  カードは索引から引ける）。**21枚の当たり外れを1枚ずつ見る作業になる。**

- **同じ性質を守る走査が3本に分かれている。** `NoteExcerptThreadingTest`・
  `NoteSectionThreadingTest`・`ReadingTraceBackupThreadingTest` は
  「入力サイズに比例する純関数をMainから呼ばない」を3ファイルで守り、
  `mainSourceRoot()` を3回コピーしている。**表駆動の1本へ寄せれば4本目は行の追加で済む。**
  ただし**登録漏れの穴は汎用化では閉じない** — 2026-08-26 に踏んだのはまさにその穴で、
  閉じたいなら「重い純関数」を型か注釈で表明し、その呼び出し元を機械的に見る形にする必要がある。

- **採らない案:** 文書検査をCIから外し「気づいたら直す」へ落とす。**節約は0.6秒**で、代わりに乖離が戻る。
  ブロッキングの分離は費用の所在と噛み合っていない。

- **受理条件:** `owner/` がコード変更に同伴して更新されていない（次の20コミットで0件）／
  検査を持つ教訓カードの正本がKDocかカードのどちらかに決まっている／
  Threading系の走査が1本へ寄り、4本目の対象追加がファイル追加ではなく行追加で済む。

- **規模感:** 中。判断が主で、コードに触るのは走査の統合だけ。**各項は独立して着手できる。**


## TRACE-8. 取消後の旧ノートの返事が、新ノートの痕跡へ保存される

- **出どころ:** 2026-09-10 全体コードレビュー P1-1。再現JVMで、保存Jobを取消した後にもAの返事がBの保存データへ混入した。
- **現状:** [`saveReply`／`holdOrLose`](../../app/src/main/java/com/example/newproject/controller/ReadingTraceController.kt) は同期I/Oの読取なし・保存失敗後、現在のセッションを読み直して返事を預ける。要求のVaultキーは固定されているが、この預け先は固定されていない。
- **再現順序:** Aの返事保存の読込を保留→Aを離れ保存Jobを取消→Bを開いてBのひとことを作る→Aの読込を未作成として返す→Bを離脱すると、Bの問いにAの返事が保存される。
- **対応候補:** 要求開始時のセッション・Vault・パスへ預け先を固定し、セッション操作をMainへ戻して所有者を照合する。画面更新のrequestIdだけでは保存副作用を防げない。
- **受理条件:** 同期読込中の取消とA→Bで、Bの状態・保存内容にAの返事が一切入らない。読取なし／保存失敗、同一Vaultの別ノート／別Vaultの同名パスを試す。切替なしの保存も成功する。
- **規模感:** 中。JVMの修正確認後、遅いSAFを使った切替時の実機確認まで保持する。

## FIELD-2. 通常起動時に保存済み分野を復元しない

- **出どころ:** 2026-09-10 全体コードレビュー P2-1。
- **現状:** [`onVaultRestored`](../../app/src/main/java/com/example/newproject/controller/NoteSessionCoordinator.kt) は履歴だけを復元し、分野ストアの読込は `onVaultChanged` にしかない。

- **規模感:** 小〜中。実機のプロセス再起動で復元が確認できるまで保持する。

## FIELD-3. 分野の入力指紋にタイトルが含まれない

## FIELD-5. 入力版の失効後も古い分野の確定が残る
