## REUN-4. 再開で画像を飛び越すと後方の進捗が記録されない

- **状態:** **実機部分確認・遅延SAF待ち。** 測定依頼をノート単位の入れ物へ残す修正はinstrumentationで再成功。2026-09-27の実機では画像を飛び越して通常表示から全画面へ移り、終端不可視の長文対照で訪問を90%から91%へ保存した。ローカル画像は速く、測定保留中に実NavHostをまたぐ順序は観測できていない。
- **原因:** `NoteReaderTab` の `rememberCoroutineScope` で飛び越した画像を測るため、全画面への遷移完了で通常画面が破棄されると測定もキャンセルされる。全画面は位置と未完了の測定状態を引き継ぐが、画面外の画像を測り直さず、最初の未測定画像より後ろの報告が止まり続ける。
- **実測:** 100ブロック・画像index 20・送り先88で、通常画面の測定を保留→呼出し元Job取消→移動先で依頼再開→末尾までの報告とする独立JVMが成功し、保存は2%から100%へ変わった。複数画像・往復・旧入れ物の結果分離も成功。追加の画面テストは実NavHostを使わず、端末でも未実行。
- **対応:** 飛び越した画像の測定と記録を通常／全画面に共通するノート単位の寿命で保持するか、移動先で未完了要求を再開する。未測定画像ガードと、別ノート／Vault切替の取消・世代判定は維持する。
- **受理条件:** 遅延loaderと実NavHostで、画像20を飛び越して88へ送る→測定待ちで全画面へ移り通常ルートを破棄→測定完了→末尾を読む順序で報告が再開し100%を保存すること。通常画面へ戻っても再押下なしに回復すること。送っただけでは末尾扱いせず、通常読書の未測定ガードを維持し、ノート／Vault切替では旧結果を新ノートへ反映しないこと。

## REUN-5. 解析待ち中の印解除が後着した結果で戻る

- **状態:** **対象ごと撤去した（2026-09-27）。** オーナー判断で「まだ考えたい」のボタンと印の表示を撤去したため、印を外す操作そのものが無くなった。台帳から消すかはオーナーが決める。以下は撤去前の記録。現在のカードへ後着結果を合流する修正を独立再確認した。モデル待ち中の印解除は保存先・UIとも維持され、通常／空モデル・再設定・畳み維持の回帰検査も成功（2026-09-26）。
- **原因:** `revealMidway` が印つきカードを先に出し、解析後に操作前の `trace` から再びカードを作る。同じノート内の印解除はノート要求世代では検出できない。
- **実測:** 独立JVMでモデルを保留→印解除・保存→モデル到着の順序が成功し、保存先とUIはともに印なしを保持した。実機操作は未確認。
- **対応:** 位置などの後着結果を最新カードへ合流し、印の明示操作を優先する。空ブロックの分岐も同じ扱いにする。
- **受理条件:** 解析待ち中の解除がモデル到着後もUI・保存先で保持されること。解除→再設定は最後の印を保持すること。通常／空ブロックの両方と、畳んだカードを開き直さないことを確認する。

## REUN-6. 長大ブロックの未読末尾を既読側へ渡す

- **状態:** **机上解消・実機待ち。** ブロック内の割合で前後へ割る修正と近似の契約を独立再確認した。長い段落・コード・リストの部分表示と同率再現の検査が成功（2026-09-26）。
- **原因:** 到達率をブロック番号へ落とした後、`passageAround` がそのブロック全体を既読とし、末尾を切り出す。ブロック内の部分表示が消える。
- **実測:** 前回と同じ長文の独立JVMで10%は前側600字・後側600字、未読終盤は前側に入らず、90%とは完成プロンプトが異なった。実表示・生成品質は未確認。
- **対応:** ブロック内進捗も切り出しへ渡すか、位置を復元できない場合は部分表示であることを明示する。全文を既読と断定しない。訪問数で強制再生成するだけでは直らない。
- **受理条件:** 固有の前半・中盤・終盤を持つ1段落で、10%の既読側が未読末尾だけにならないこと。10%→90%で前後入力が進捗に応じて変わり、同じ10%は同じ入力になること。長いコード・リストでも部分表示を全文既読扱いしないこと。

## REUN-7. 前後の要約に入力用の境界記号が露出する

- **状態:** **別の目で机上解消・実機待ち。** 生成結果から印を落としてから表示・端末内の保存へ渡すようにし、プロンプトにも印を書かない指示を足した（古い保存は鍵が変わって使われない）。本文が同じ言葉を含むノートでは落とさない。以下は起票時の記録。2026-09-26の実機で、独立した途中ノートDと長い1段落Jの再会カードに `[READ UP TO HERE]` が表示された。今回の再開では元fixtureのマニフェストが `/tmp` から失われたため、この2件の成功判定は継承していないが、UI文字の実測とコード経路は残る。
- **原因:** `PromptBuilder.REUNION_READ_MARKER` は既読と未読を区切る生成入力の記号で、本文には無い。`ReunionCardController.passageSummary` は生成結果を空白除去・長さ制限だけでカードへ渡してキャッシュにも保存するため、モデルが記号を復唱するとそのまま再掲される。
- **影響:** 前後を自然な2文で示すカードに機械向けの記号が混ざり、読む意味が崩れる。印を付けると同じ文が痕跡にも保存され得る。
- **受理条件:** 生成が境界記号を含んだ場合でもカード・キャッシュ・印に記号を残さず、既読／未読の2文を保つ。元ノートに同じ文字列が本文として含まれる場合を誤って消さない境界も検査する。

## REUN-8. 初読直後の同一ノート再会でカードが出ない

- **状態:** **別の目で机上解消・実機待ち。** 再会の照合が、走っている訪問の保存を待ってから痕跡を読むようにした。修正前のコードで「切替→本文→照合」の順を通すJVMテストが落ちることを確かめてから直した（保留注入なしでテストスケジューラの順序だけで再現した）。以下は起票時の記録。2026-09-26の実機で、痕跡なしの一時VaultのKを10秒以上読み段落29へ進み、先頭へ戻して直ちに同一ノートを引き直すとカードが出なかった。同時点でサイドカーには初回訪問72%が作成済み。もう1回引くと72%のカードが表示された。今回の再開では元fixtureのマニフェスト喪失により成功判定を継承していないが、この失敗の実測は保持する。
- **原因候補:** `ReadingTraceController.recordVisit()` は `persistScope.launch` で保存を非同期に始める一方、`NoteViewModel.loadRandomNote()` は `session.onNoteChanged()` の後で読み込みを始める。`ReunionCardController.revealTrace()` が保存完了前に `None` を読んだ場合、その再会では再試行しない。実機の「1回目なし→2回目あり」と整合する。保存と読込の順序を注入で固定した再現はまだ無い。
- **影響:** 正本が求める「1回目の再会から枠が出る」を満たさず、本人が読むまで痕跡を残した直後ほど再会カードが欠ける。
- **受理条件:** 痕跡なしから10秒以上読んで最初の訪問を保存する操作と、直後に同じノートを引く操作を連続させ、追加の引き直しなしに前回位置・続きボタンが表示される。保存保留と同一ノート再選択の競合を制御した検査も加える。

## REUN-9. 別ノートの訪問保存が再会カードの表示を止める

- **状態:** **別の目で机上解消・実機待ち。** 保存Jobを保存先（Vaultキーと相対パス）ごとに持ち、照合は同じ痕跡への保存だけを待つようにした。別ノートの保存を錠で止めたまま保存済みのカードが出ることと、同じノートの保存を止めている間は待つことをJVMで固定し、修正前のコードで前者が落ちることを確かめた。以下は起票時の記録。一時JVMテスト1/1で、Aの保存を保留すると、保存済みBの再会カードが出ず、Aを解放すると出ることを確認した。
- **原因:** `ReadingTraceController.awaitVisitSaves()` がVault・相対パスを区別せず、実行中の訪問保存Jobをすべて待つ。`ReunionCardController.revealTrace()` はBの痕跡を読む前にその全件待ちを通る。
- **影響:** 遠いSAFや書込停止中のノートが1件あると、関係のないノートの再会カードも表示されない。データ破損ではなく表示遅延。
- **対応:** 保存先のVaultキー・相対パスに対応したJobだけを待つ。同一ノートの初読直後に保存を待つ順序、切替時の取消と完了Jobの除去は維持する。
- **受理条件:** Aの保存保留中でも保存済みBのカードが出る。同じAの再会は保存を待って初回訪問を含める。A保存中のB切替、保存失敗、保存完了でも旧カードや待機Jobが残らない。

## AI-5. 関連ノートが算出した根拠を捨てている

- **現状:** [`relatedContextScore`](../../app/src/main/java/com/example/newproject/domain/RelatedContextScoring.kt) は
  **タグ一致・本文スニペット類似・タイトル類似を個別に計算**しているが、
  `CandidateScore(score, tieBreak)` という **Double 2つへ畳んで**返す。
  畳んだ後は並べ替えにしか使われず、[`RelatedTab`](../../app/src/main/java/com/example/newproject/ui/screen/RelatedTab.kt) が
  表示するのは `isWikilinked` だけ。
- **影響:** 「なぜこのノートが関連なのか」が画面から分からない。
  **根拠は計算済みなのに捨てているので、表示するのに新しい計算もAI生成も要らない。**
- **不具合ではなく強化。** ただし A-3（ピッカーに1行要約を添える）が Nano 生成を要するのに対し、
  **こちらは追加コストがゼロ**なので、納得感を上げる手段として先に検討する価値がある。
- **対応候補:** `CandidateScore` に内訳を持たせるか、上位候補についてだけ主シグナル
  （タグ一致なら一致したタグ名）を返す。**畳む前の値を1段だけ上へ通す。**
- **懸念:** 内訳を出すと「スコアが見える」ことになり、順位への納得と不満の両方を生む。
  **数値ではなく「タグが一致」のような質的な表示に留める**のが安全。
- **規模感:** 小。

## AI-6. 引用ブロックの問いを、書き手自身の問いとして拾う

- **現状:** 再会カードの候補列挙は
  [`stripMarkdownMarkers`](../../app/src/main/java/com/example/newproject/domain/MarkdownPlainText.kt) を通してから
  文へ割るが、`LINE_PREFIX` が**行頭の `>` を見出し記号や箇条書き記号と一緒に落とす**。
  結果、`> これでいいのか。` は本文の地の文と区別が付かないまま
  [`scanReunionCandidates`](../../app/src/main/java/com/example/newproject/domain/ReunionCandidateScanner.kt) の
  問い候補に入る。
- **影響:** 引用した他人の問いが**候補枠を埋め**、書き手自身の問いが選ばれにくくなる。
  選ばれてしまった場合は「前回のあなたはこの問いで止まっていた」と**事実に反する断定**でカードに出る。
- **同種の混入は一度直っている。** 2026-08-22 の実測で「引用した他人の発言」が問い候補の大半を占めていたが、
  原因は**括弧の内側で文を切っていたこと**で、そこは修正済み（→ [reunion_card](../dev/features/reunion_card.md) §5）。
  **引用ブロックだけが残った** — 括弧と違い、記法を落とす側で消えているため実測にも現れない。
- **AIでは直せない場所にある。** 選別を強めても、候補列挙の時点で引用の情報が失われているので
  AIには引用と地の文の区別が付かない。**非AI段で印を残すことが前提**になる（→ 型1）。
- **対応候補:** `stripMarkdownMarkers` で `>` を落とす前に引用行を判別し、
  問い候補から外すか、候補に「引用である」印を添えてAIへ渡す。
  **落とす対象を減らすのではなく、落とす前に見分ける**（記法は表示・整形の都合で落としている）。
  蒸留側は既に引用行を独立した単位として扱っているので、判別そのものの前例はある。
- **規模感:** 小。判別と、引用行を含むノートでのJVMテスト。

## REL-1. R8とリリース署名が未設定

- **現状:** `buildTypes { release { } }` と `proguard-rules.pro` は置いたが、
  **`isMinifyEnabled = false`／`signingConfig` 無し**。`assembleRelease` の生成物は
  依然として `app-release-unsigned.apk`（約10MB）で、配布可能性を意味しない。
- **後回しにした理由:** ML Kit GenAI はリフレクションで解決される部分があり、縮小で消えると
  **全AI機能が実機の release ビルドでだけ落ちる**。JVMテストは縮小前のクラスを見るので検出できない。
  Compose の Composable メタデータも同様。つまりR8の有効化は「設定を1行変える作業」ではなく
  **実機検証の計画とセット**になる。

## PERF-1. 読書痕跡の索引作成がファイル数に比例する

**実測で問題化するまで着手しない。** 先回りで入れると移行リスクだけを先払いになる。

- **現状:** `_ReadingTraces/` はフラットな1階層で、セッション中1回だけ子一覧を全列挙して
  key→参照の索引を作る。容量は問題にならない（1ファイル最大3.3KB・2,000ノートで約1.4MB）が、
  **列挙コストはファイル数に比例**する。孤児削除（手動）は入ったが**押されるとは限らない**ため、
  ファイル数は単調増加**しうる**（→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」）。
  遠いプロバイダ（Google Drive 等）ほど効く。
- **対応候補:** 削除ではなく**分割**で解く。ファイル名が `sha256Hex(相対パス)` なので、
  **先頭1桁で16フォルダへ分ける**と1件の照合で列挙する件数が 1/16 になる。
  引く側はキーから所属フォルダを計算できるので探索は要らない。
  **生きた痕跡を1つも消さずに性能だけ守れる**のが孤児削除に対する優位点。
  → [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」
- **着手の契機:** 実機で列挙の遅さが体感できたとき。既存ファイルの移行を伴うので、それまで動かさない。
- **規模感:** 中（移行と実機確認を伴う）。
