## TRACE-3. 連続削除が同じJobを奪い合う

- **現状:** [`ReadingTraceCleanupController`](../../app/src/main/java/com/example/newproject/controller/ReadingTraceCleanupController.kt) は
  洗い出しと削除に**同じ `job`** を使い、削除のたびに前のJobをキャンセルする。
- **問題:** SAFの `deleteDocument()` は同期的な外部I/Oなので、**キャンセル時点で物理削除だけ完了し、
  その後の状態更新が落ちる**ことがある。さらに各削除は開始時の `current` を捕捉するため、
  AとBを素早く押すと **AのJSONは消えたのに画面に残り**、B完了時には古い一覧を基にBだけを外す。
- **自己修復はするが誤解を与える:** 再洗い出しで整合するものの、その前は「削除に失敗した」ように見える。
- **対応候補:** 洗い出し用のJobと削除を分け、削除は `Mutex` か単一キューで直列化する。
  実行中は同じ候補のボタンを無効化し、完了時は**捕捉した `current` ではなく最新状態から**対象を除く。
  連続2件・洗い出し中の削除・Vault切替中の削除をテストする。
- **規模感:** 小〜中。

## AI-5. 関連ノートが算出した根拠を捨てている

- **現状:** [`relatedContextScore`](../../app/src/main/java/com/example/newproject/domain/RelatedContextScoring.kt) は
  **タグ一致・本文スニペット類似・タイトル類似を個別に計算**しているが、
  `CandidateScore(score, tieBreak)` という **Double 2つへ畳んで**返す。
  畳んだ後は並べ替えにしか使われず、[`RelatedTab`](../../app/src/main/java/com/example/newproject/ui/screen/RelatedTab.kt) が
  表示するのは `isWikilinked` だけ。
- **影響:** 「なぜこのノートが関連なのか」が画面から分からない。
  **根拠は計算済みなのに捨てているので、表示するのに新しい計算もAI生成も要らない。**
- **不具合ではなく強化。** ただし A-3（ピッカーに1行要約を添える）が Nano 生成を要するのに対し、
  **こちらは追加コストがゼロ**なので、納得感を上げる手段として先に検討する価値がある。
- **対応候補:** `CandidateScore` に内訳を持たせるか、上位候補についてだけ主シグナル
  （タグ一致なら一致したタグ名）を返す。**畳む前の値を1段だけ上へ通す。**
- **懸念:** 内訳を出すと「スコアが見える」ことになり、順位への納得と不満の両方を生む。
  **数値ではなく「タグが一致」のような質的な表示に留める**のが安全。
- **規模感:** 小。

## AI-6. 引用ブロックの問いを、書き手自身の問いとして拾う

- **現状:** 再会カードの候補列挙は
  [`stripMarkdownMarkers`](../../app/src/main/java/com/example/newproject/domain/MarkdownPlainText.kt) を通してから
  文へ割るが、`LINE_PREFIX` が**行頭の `>` を見出し記号や箇条書き記号と一緒に落とす**。
  結果、`> これでいいのか。` は本文の地の文と区別が付かないまま
  [`scanReunionCandidates`](../../app/src/main/java/com/example/newproject/domain/ReunionCandidateScanner.kt) の
  問い候補に入る。
- **影響:** 引用した他人の問いが**候補枠を埋め**、書き手自身の問いが選ばれにくくなる。
  選ばれてしまった場合は「前回のあなたはこの問いで止まっていた」と**事実に反する断定**でカードに出る。
- **同種の混入は一度直っている。** 2026-08-22 の実測で「引用した他人の発言」が問い候補の大半を占めていたが、
  原因は**括弧の内側で文を切っていたこと**で、そこは修正済み（→ [reunion_card](../dev/features/reunion_card.md) §5）。
  **引用ブロックだけが残った** — 括弧と違い、記法を落とす側で消えているため実測にも現れない。
- **AIでは直せない場所にある。** 選別を強めても、候補列挙の時点で引用の情報が失われているので
  AIには引用と地の文の区別が付かない。**非AI段で印を残すことが前提**になる（→ 型1）。
- **対応候補:** `stripMarkdownMarkers` で `>` を落とす前に引用行を判別し、
  問い候補から外すか、候補に「引用である」印を添えてAIへ渡す。
  **落とす対象を減らすのではなく、落とす前に見分ける**（記法は表示・整形の都合で落としている）。
  蒸留側は既に引用行を独立した単位として扱っているので、判別そのものの前例はある。
- **規模感:** 小。判別と、引用行を含むノートでのJVMテスト。

## REL-1. R8とリリース署名が未設定

- **現状:** `buildTypes { release { } }` と `proguard-rules.pro` は置いたが、
  **`isMinifyEnabled = false`／`signingConfig` 無し**。`assembleRelease` の生成物は
  依然として `app-release-unsigned.apk`（約10MB）で、配布可能性を意味しない。
- **後回しにした理由:** ML Kit GenAI はリフレクションで解決される部分があり、縮小で消えると
  **全AI機能が実機の release ビルドでだけ落ちる**。JVMテストは縮小前のクラスを見るので検出できない。
  Compose の Composable メタデータも同様。つまりR8の有効化は「設定を1行変える作業」ではなく
  **実機検証の計画とセット**になる。
- **対応候補:** keep ルールを書いた上で `isMinifyEnabled = true` にし、release ビルドを実機へ入れて
  7つのAI経路（要約・補記・クイズ・関連ノート・セクションチャット・蒸留・読書痕跡の要約）を一巡する。
  署名は keystore の保管方針を決めてから。
- **規模感:** 中。実機確認が必須。

## PERF-1. 読書痕跡の索引作成がファイル数に比例する

**実測で問題化するまで着手しない。** 先回りで入れると移行リスクだけを先払いになる。

- **現状:** `_ReadingTraces/` はフラットな1階層で、セッション中1回だけ子一覧を全列挙して
  key→参照の索引を作る。容量は問題にならない（1ファイル最大3.3KB・2,000ノートで約1.4MB）が、
  **列挙コストはファイル数に比例**する。孤児削除（手動）は入ったが**押されるとは限らない**ため、
  ファイル数は単調増加**しうる**（→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」）。
  遠いプロバイダ（Google Drive 等）ほど効く。
- **対応候補:** 削除ではなく**分割**で解く。ファイル名が `sha256Hex(相対パス)` なので、
  **先頭1桁で16フォルダへ分ける**と1件の照合で列挙する件数が 1/16 になる。
  引く側はキーから所属フォルダを計算できるので探索は要らない。
  **生きた痕跡を1つも消さずに性能だけ守れる**のが孤児削除に対する優位点。
  → [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「性能はファイル数ではなく索引設計で解く」
- **着手の契機:** 実機で列挙の遅さが体感できたとき。既存ファイルの移行を伴うので、それまで動かさない。
- **規模感:** 中（移行と実機確認を伴う）。

## PROC-1. 「過剰な検証」の実体は検査ではなく文書の量である

- **出どころ:** 2026-09-05、オーナーの検討メモ。要望は「**過剰な検証を抑えたい**」。
  メモは検査を3種（実行時バグ／文書同期／儀式）へ仕分け、2と3を削ることを提案している。
  **仕分けの軸は正しいが、削る対象の見立ては実測と合わない。**

- **測った（2026-09-05 時点。マージコミットを除く直近99コミット）:**

  | | 2026-08-01 | 現在 | 倍率 |
  |---|--:|--:|--:|
  | `app/src/main` の行数 | 15,005 | 26,502 | 1.8 |
  | JVMテスト（`@Test`） | 508 | 1,296 | 2.6 |
  | `architecture/` の検査 | 3 | 19 | 6.3 |
  | `docs/` の `.md` | 27 | 106 | 3.9 |

- **実行費用はほぼゼロである。** JVM 1,293件の合計実行時間は **2.1秒**。
  うち文書の形を守る7本（`AdrShapeTest`・`DesignDocStateNameTest`・`DeviceValidationDocsTest`・
  `ReviewFindingsLedgerTest`・`SchemaVersionDocsTest`・`SourceDocSyncTest`・`WipIssueReferenceTest`）は
  **合計0.6秒**。**「検査が多いから遅い」という筋ではない。**

- **費用は書く側にある。** 直近99コミットの変更行は `docs/` 6,156行に対し `app/src/main` 6,971行で、
  **99件中39件はコードに1行も触れていない。** 検査を消しても減るのは0.6秒だけで、
  **書き換えの手間はそのまま残る。**

- **問題:** 抑えるべきは検査の本数ではなく**正本の数**である。検査はコードと文書の一致を固定するので、
  文書が増えるほど1つのコード変更が要求する書き換えが増える。
  **いま増えているのは文書のほうで（3.9倍）、検査はそれに追随している。**

- **2026-09-12、書く量を減らす3手を当てた**（Fable 5.1 報告書05章の案A・B・C）。
  ヘッダの検証内容を落とし（32本・1,834字減）、設計書2本から経緯と死んだレビュー番号を落とし
  （booklet_mode は 1,067行 → 920行）、教訓の追加条件を「2度目」へ戻した。
  **どれも正本を1つに保つ原則には触れていない。** 効果は次の20コミットの docs churn で見る。

### 残っている面

- **`owner/` の同伴更新は止まった（2026-09-12 に確認）。** 元の症状は、
  [`source_code_analysis.md`](../owner/source_code_analysis.md) が docs churn の19%（1,170行）を占め、
  直近99コミット中**7件（259行）がコード変更に同伴していた**こと — `owner/` は
  「オーナーが指示したときだけ更新する」と決めてあり、検査からも意図して外してある文書である。
  原因だった `CLAUDE.md` の影響面監査の行（正本として `owner/` を名指ししていた）を外した。
  **観測窓（20コミット）を超えて数えても0件である** — 2026-09-05 以降のマージを除く80コミットのうち
  `owner/` を触ったのは3件で、**いずれも `app/src` を1行も変えていない**（＝同伴更新ではない）。
  **解析書の同伴更新の面は閉じた。残るのは下の2面。**

- **検査を持つ教訓カードは、検査のKDocと本文が重複しやすい。**
  例えば `L49` の見出し文「中止は要求であって完了ではない」は
  `ReadingTraceBackupThreadingTest` のKDocに**同じ文で入っている**。
  **同じ事件を2箇所に長文で書かない**という既存の規約に反しているが、
  どちらを正本にするかは決めていない（検査のKDocは検査を読む人にしか届かず、
  カードは索引から引ける）。**21枚の当たり外れを1枚ずつ見る作業になる。**

- **同じ性質を守る走査が3本に分かれている。** `NoteExcerptThreadingTest`・
  `NoteSectionThreadingTest`・`ReadingTraceBackupThreadingTest` は
  「入力サイズに比例する純関数をMainから呼ばない」を3ファイルで守り、
  `mainSourceRoot()` を3回コピーしている。**表駆動の1本へ寄せれば4本目は行の追加で済む。**
  ただし**登録漏れの穴は汎用化では閉じない** — 2026-08-26 に踏んだのはまさにその穴で、
  閉じたいなら「重い純関数」を型か注釈で表明し、その呼び出し元を機械的に見る形にする必要がある。

- **採らない案:** 文書検査をCIから外し「気づいたら直す」へ落とす。**節約は0.6秒**で、代わりに乖離が戻る。
  ブロッキングの分離は費用の所在と噛み合っていない。

- **残る受理条件（解析書の同伴更新の面は充足済み）:**
  検査を持つ教訓カードの正本がKDocかカードのどちらかに決まっている／
  Threading系の走査が1本へ寄り、4本目の対象追加がファイル追加ではなく行追加で済む。

- **規模感:** 中。判断が主で、コードに触るのは走査の統合だけ。**各項は独立して着手できる。**


## APP-2. 横画面で再会カードがノート本文の表示領域を占有する

**優先度は超低・据え置き（オーナー判断 2026-09-17）。** カバー画面を横にする使い方は稀で、いまは直さない。
直すときの第一候補は**横長の低い画面だけ左右2列**（左に見出し・ボタン・カード、右に本文）で、
高さを分け合う案（カードの高さ上限・畳む）より本文の高さを取れる。

Pixel 10 Pro Foldのカバー画面を横向き（構成970×443dp、fontScale 1.1）へ回転し、
俯瞰要約付きの「前回のあなた」カードを表示していると、ノート名と本文が画面から消える。
Activityは保存Bundle付きで再生成され、OPの再表示も無いが、本文パネルは下端の薄い空白だけになる。
縦へ戻すと同じノートが再び表示される。データ消失ではなく表示領域の不足。

- **出どころ:** 2026-09-17アプリ起動実機検証の `LAUNCH-05b`。常設検証用Vaultの `waiting.md` 1件で再現。
- **原因:** `NoteReaderTab` のスクロールしないColumn内で、ヘッダー・操作ボタン・高さ上限の無い
  `ReadingTraceCardPanel` を先に測定し、残りだけを `weight(1f)` の本文へ渡している。
- **境界再現:** 実Composeに1ノート＋高さ443dpの制約を与え、再会カード無しではタイトル・本文を表示、
  短い俯瞰要約付きカード追加で両方非表示、カード除去で両方表示へ戻ることを一時テスト1件で確認。
  この補助テストの幅は縦画面の幅であり、970×443dpの物理回転を代替するものではない。
- **既存検査の穴:** `ActivityRecreationTest` はOP不在と `Rediscover` だけを検査し、今回も2件成功。
  `ReadingTraceCardPanelTest` はカード単体、`NoteReadingFlowTest` は再会カード無しの読書状態を扱うため、
  低い画面でカードと本文が高さを奪い合う組み合わせを検査していない。
- **同じ画面の重なり:** 実機画像では、右下のフクロウとセクション名の札がカードの「読んだ」ボタンに重なっている。
  左右2列にすればフクロウは本文側へ移るので、直すときは一緒に確かめる。
- **受理条件:** 再会カードを表示した低い横画面でもノート名・本文を読める領域を確保する。
  カード有無の境界検査を置き、カバー画面を横にした実機でノート名・本文が見えることを確かめる
  （回転の実機ケースはOPとガードだけを判定するので、表示はそれとは別に見る）。起動OPや保存Bundleの条件は変更しない。
