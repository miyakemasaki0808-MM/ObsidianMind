# 蒸留の粒度 — 段階的に句・語句へ落とす設計検討（使い捨て）

**プロジェクト:** Vigilith AI（旧 Obsidian Mind）
**作成日:** 2026-08-15 / **最終更新:** 2026-08-17
**この文書が答える問い:** **蒸留の太字を文単位から落とすとき、どこまでを一度にやるか。**

> **使い捨て。決まったら [reflect_distill.md](../dev/features/reflect_distill.md) へ移して本書は捨てる**（移送先は §7）。
> **正本はあくまで `reflect_distill.md`。** 本書は未決の検討だけを持ち、決まった内容を残さない。
> 課題そのものは [current_issues.md](current_issues.md)、着手順は [roadmap.md](roadmap.md) が持つ。

## 1. 出発点

**2026-08-15、オーナーの実感「蒸留の選定がイマイチ」を分解したところ2つの原因に分かれた。**

| 原因 | 行き先 |
|---|---|
| `[[リンク情報]]` のようなリンク行が候補に上がる | **段階0で解消・実機確認済み**（正本は [reflect_distill](../dev/features/reflect_distill.md) §5） |
| **太字が文まるごとになり、長文だと重い** | **本書 段階1以降** |

**新規発見ではない。** [reflect_distill.md](../dev/features/reflect_distill.md) §11 の v2送りリストに「句単位抽出」として既に入っている。
v1で意図的に切った（判断12）ものが、実運用で表に出た形。

**要望と懸念が逆を向いている点に注意する。** オーナーの実感は「文章単位**の方が多い**」＝もっと語句寄りが欲しい、
一方で懸念は「句単位にすると**単語まみれ**になるのでは」。**下限を一律に上げると要望のほうを潰す**ので、
歯止めは「下限を上げる」ではなく「**候補の種類を分ける**」で置く（→ §5 決定3）。

## 2. 現状 — 文・句・語句の3粒度

- 短文は**文**、閾値を超える長文は読点で**句**、鉤括弧の内側は**語句**として候補を作る
- AIはどの粒度でもIDだけを返し、太字範囲はアプリが原文オフセットから解決する
- 候補集合は互いに重ならず、親と語句が重なれば細かい語句を残す
- `FINAL_SELECTION_LIMIT = 6` / `MAX_BOLD_RATIO = 30%`

**句単位にすると太字率の圧も同時に下がる**（1件あたりの消費が減るため）。これは副次的な利点。

## 3. 外せない制約（全段階に共通）

- **AIに範囲（オフセット）を返させない。** 安全性の核は「AIはIDを返すだけ、オフセットはアプリが解決する」
  （判断1・判断5）。文字列を返させて本文から検索する形にすると、言い換え・装飾で一致せず
  **[AI-4](current_issues.md) と同じ「黙って落ちる」失敗**を蒸留に持ち込む。
  → **アプリが非AIで候補を作ってIDを振り、AIはIDを選ぶだけ**（[feature_ideas](feature_ideas.md) 型1）
- **Nano呼び出しは1回のまま。** 二段生成にすると Mutex 占有が倍（判断2）
- **形態素解析ライブラリを足さない。** 依存追加は [dependency_policy](../dev/system/dependency_policy.md) の範囲に入り、
  実機確認を伴う大ごとになる。**正規表現で割れる範囲に留める**
- 装飾記号の挿入のみ・UTF-16オフセット・frontmatter保護は現行契約のまま

## 4. 段階の切り分け

**小さく始める。段階0だけで独立して出せる。**

| 段階 | 内容 | 触る範囲 | 前提 | 状態 |
|---|---|---|---|---|
| 0 | リンクだけの候補を落とす | 純関数＋テスト | なし | **完了**（実機確認済み） |
| 1 | 長文を読点で割る（`Clause`） | 候補選定＋候補カード表示 | 段階0の実機確認 | **完了**（候補境界・直前文脈とも実機確認済み） |
| **2** | **語句候補（`Term`）** | 候補選定＋候補カード表示 | **段階1の完了（充足）** | **候補・位置・種別・通常件数・保存は実機確認済み**。短文例外の表示修正待ち（DISTILL-4） |
| 3 | 太字範囲のユーザー調整 | **新しいUI・書き戻し** | **v1の実機確認完了** | **本書スコープ外** → [feature_ideas](feature_ideas.md) N-14 |

**段階0・段階1の理由と契約は [reflect_distill.md](../dev/features/reflect_distill.md) 判断13 と §5 へ移した。**
**本書に残るのは段階2以降の未決だけ**で、§5 は移送済みの内容の要約である。

**段階3を分けた理由:** 出発点は「長文まるごと太字が重い」で、範囲調整はそれとは別の（はるかに大きい）機能である。
加えて **蒸留 v1 は通常の語句保存まで実機確認したが、競合・故障復旧の実機確認が未完了**
（[reflect_distill.md](../dev/features/reflect_distill.md) §10・§11）。
**このアプリで唯一ノート本文を書き換える機能**の検証が済まないうちに、書き込み範囲の決まり方を可変にしない。

### 段階0 — 完了

内容と受理条件の正本は [reflect_distill](../dev/features/reflect_distill.md) §5が持つ。**本書が足したのは1点だけ。**

> **リンク判定を `DistillSentence` に固定せず、「テキスト＋リンク範囲」を受ける純関数として書く。**

段階1で候補が文から句へ変わったとき、**同じ判定を候補種別ごとへ再適用する必要がある**ため
（`詳細は[[A]]、実装は[[B]]。` は文としては通常文だが、読点で割ると両断片ともリンクだけになる）。
関数の形さえ決めておけば、段階1では呼ぶ場所が増えるだけで済む。

**判定の中身:** リンク範囲を除いた残りから**記号を取り除き、文字か数字が残るか**で決める。
**接続語（閉じた一覧）を取り除くのは、両側がリンクの断片だけ。**

| 例 | 判定 |
|---|---|
| `[[リンク情報]]` | 除外 |
| `[[A]] と [[B]]` | 除外 |
| `[[A]]、[[B]]、[[C]]、[[D]]。` | 除外 |
| `[[A]]は核。` | **残す** |
| `[[A]]のもの。` | **残す** |
| `[[Vigilith]]を採用する。` | **残す** |

**代理判定を2度作った。段階1で3度目を作らないこと**（→ [実機レビュー一覧](../review/README.md)）。

1. **長さを意味の代理にした。** 「リンク外4文字未満」は区切り記号を実質文字として数えるため、
   `[[A]]、[[B]]、[[C]]、[[D]]。`（読点3＋句点1＝4文字）を残し `[[A]]は核。`（3文字）を落とした
2. **接続語一覧を入れたが適用位置を捨てた。** 文全体へ部分文字列置換したため、
   `[[A]]のもの。` の `のもの` から `の`・`も` が語中ごと剥がれて空になった

**教訓は「何を正規化するか」と「どこで意味を捨てるか」を別々に決めること。**
段階1では句へ割ると断片あたりの文字数がさらに減るので、**長さで判定する誘惑が一段強くなる。**

## 5. 段階1（`Clause`）で決めること

### 決定1: どの文を割るか

**長文だけ割り、短い文はいまのまま文で選ぶ。** 全文を割ると、いま良く効いている短文の選定まで細切れになる。
現状を壊さず、長文まるごと太字の一点だけを潰せる。

**閾値の叩き台は60字。** 実Vaultの分布を見て確定したいが、
[reflect_distill.md](../dev/features/reflect_distill.md) §5 の上限群は**すべて実機調整前提の初期値**という
先例があるので、**分布の測定を着手の前提にしない。** 初期値で出して実機で詰める。

### 決定2: どこで割るか

| 境界 | 扱い | 理由 |
|---|---|---|
| 読点 `、` | **採る** | 正規表現で足りる。既存の文分割機構の延長に置ける |
| 接続助詞（が・ので・けど・ため） | **送る** | 意味の切れ目には近いが、安定して割るには形態素解析が要る（→ §3） |
| 並列の `・` | **割らない** | 列挙は1つの塊。割ると単語になる |
| 英文の `,` ＋接続詞 | 読点と同じ | — |

**割れない長文は割れないままにする。** 読点の無い160字の文は1句のまま残る。
**無理に割ると意味が壊れる**ので、ここは「直せない場合がある」と明示して受け入れる。

### 決定3: 断片の結合規則（**下限だけ決めても足りない**）

読点で割ると下限未満の断片が大量に出る。**どちら向きに結合するかを決めないと、
「下限15字」という数字だけでは挙動が定まらない。**

**前から貪欲に積む。** 断片を順に足していき、下限に届いた時点で1句として閉じる。
末尾に残った下限未満の余りは、**直前の句へ吸収する**（新しい句を作らない）。

```text
本文（読点が約10字ごと）: F1 F2 F3 F4 F5 F6
  F1(10) → 下限未満、積む
  F1+F2(20) → 下限到達、句1として閉じる
  F3+F4(20) → 句2
  F5+F6(20) → 句3
```

下限の叩き台は **15字**（既存の `SHORT_SENTENCE_PENALTY` と揃う）。

**この下限は「長さを意味の代理にする」に当たらない。** 段階0で2度失敗したのは
「**リンクだけか**」という意味の問いへ長さを使ったからで、こちらは
「**太字として読める最小の塊か**」という長さそのものの問い。
**同じ形に見えるので、3度目をやらないために区別を書いておく。**

### 決定4: 候補枠の配分

`MAX_AI_CANDIDATES = 24` / `AI_CANDIDATE_CHAR_BUDGET = 1,500` は現状のまま使う。

- **1文あたり最大2句。** 非AI段で1句に絞ると、そこが外れた時点でAIに挽回手段がなくなる（型1の思想に反する）
- **割った長文では親の全文候補を入れない。** 全文と句が枠を二重に食うのを避ける
- 数値は実Vaultの分布と実機出力を見て確定する

### 決定5: 構造ボーナスを句へどう配るか（**段階0では起きなかった問題**）

`structuralWeight` の4フラグは**すべて位置のフラグ**である。
1文が3句に割れたとき全句へ継承すると、**その文だけで構造点を3倍取り、候補枠を占める。**

**位置のフラグは、その位置を実際に占める句だけへ渡す。**

| フラグ | 渡す先 |
|---|---|
| `isParagraphFirst` / `isHeadingAdjacent` | **先頭句だけ** |
| `isChunkLast` / `isNoteLast` | **末尾句だけ** |

段階0までは1文＝1候補だったのでこの問題は存在しなかった。**判定の分配は割った瞬間に発生する。**

### 決定6: 親文をどう保持するか

候補が句になると、候補カードに出る文字列が断片になり「何について述べた断片か」が分からなくなる。
[reflect_distill.md](../dev/features/reflect_distill.md) §5 は候補カードに
「原文＋所属見出し＋ノート内位置＋（必要なら直前1文の薄いコンテキスト）」を出すと決めているので、
**句になっても親文を引けるようにする。**

**最小の追加は `DistillSentence` へ親文の範囲を1欄足すこと**（割らない文は自分自身を指す）。
これは [feature_ideas](feature_ideas.md) N-14 の `contextRange` と同じもので、
**N-14 に進まなくても単独で成立する**（表示だけに使い、太字範囲は変えない）。

段階1では `positionLabel` を句の並びに合わせた。段階2で親文と語句を重ねた内部draft列が一度表示へ漏れたが、
語句は親の線形位置を借りる修正を実機確認した。残る短文例外の表示境界は [current_issues](current_issues.md) DISTILL-4 が持つ。

## 6. 段階2（`Term`）で決めたことと残り

候補・保存の契約は [reflect_distill](../dev/features/reflect_distill.md) §5・判断14へ移した。
ここには段階2を閉じる前の残りだけを置く。

| 項目 | 決定・実測 |
|---|---|
| 入口 | 鉤括弧（`「」` `『』`）の内側だけ。2〜20 UTF-16文字 |
| 見送り | `〜とは` の定義対象、コロン前、箇条書きラベル |
| 候補枠 | 同じ表層語句は1件、語句は最大2件 |
| 重なり | 選定の出口で非重複。親と重なれば細かい語句を残す |
| スコア | 位置ボーナスと短文ペナルティへ参加しない |
| 実機 | `DIST-18` で重複・上限・非重複、`DIST-19` で語句だけの保存を確認 |

**残りは短いノートの例外表示だけ。** 候補種別、親の線形位置、通常の件数・確認・完了は実機で成立したが、
句を選んだ例外で候補画面と保存プレビューが「最重要の1文」「この1文」と説明する（DISTILL-4）。

## 7. 受理条件

**段階0:** [reflect_distill](../dev/features/reflect_distill.md) §5の契約と実機確認を完了した。

**段階1以降:**

- **長文が丸ごと太字にならない**
- **短い文はいまと同じく文のまま選ばれる**（決定1が効いていることの回帰）
- AIには**IDだけ**を返させ、オフセットはアプリが解決する（範囲を返させない）
- **リンクだけの断片が、句へ割った後にも候補へ出ない**（→ §4 段階0の判定を再適用）
- 変換後から**追加した `**` を除くと原文と完全一致**する（現行の受理条件を維持）
- 上記を固定する回帰テストがある
- 語句は同じ表層1件・最大2件で、親候補と同時に出ない
- 表示上の単位と位置が実際の保存範囲に一致する（**短文例外だけ未達: DISTILL-4**）

## 9. 先に見るべきもの

- **実Vaultの文長分布**（決定1の閾値を詰めるのに使える）。ただし着手の前提にはしない（→ 決定1）
- **`PromptTokenBudgetTest` にコードの更新は要らない**（**2026-08-16、前言を訂正**）。
  この検査に**ハードコードされた期待値は無く**、アサーションは `headroom >= 0`（上限を超えないこと）だけ。
  実測値はログ出力で、人が判断のよりどころにするもの。
  句は文より短いので**入力は減る方向**で、通る見込み。取り直しとは**端末で1回走らせてログを読む**ことを指す
- **リンク判定を句へ再適用すると、判定が緩む方向に働く。** 「接続語を剥がすのは両側がリンクの断片だけ」は
  句の範囲で再計算されるので、親文では「リンク間」だった断片が句では「先頭／末尾」になり剥がされない。
  **意味のある文を落とさない側へ倒れる**ので許容するが、`[[A]]、[[B]]` を割った断片が残り得る点は実機で見る
- **蒸留 v1 の受け入れ条件がどこまで消化されているか。** 候補提示までは実運用で動いているが、
  §10 の書き込み側（故障注入・復旧レコードの4分岐・外部編集後の競合中断）は未確認の見込み。
  **段階3の着手条件がここ**
