**プロジェクト:** Vigilith AI（旧 Obsidian Mind）
**初版:** 2026-07-22（最終更新: 2026-09-18）
**基準:** 何がどこまで進んだかは [change_history.md](../dev/change_history.md) が正、未対応の課題は [current_issues.md](current_issues.md) が正。**ここに進捗のスナップショットを書かない**（書いた瞬間から古くなり、実際 ReadingTrace v1 の記述が2週間ずれていた）。旧 TimeCapsule 設計は棄却

## 0. 北極星 — このアプリは何であろうとしているか

> **Vigilith AI は「過去の自分の思考と再会し、もう一段深める、オンデバイスAIの読書相手」である。**

このアプリの心臓は **Rediscover（ランダムに過去ノートを引く）**。単なるVaultビューアではなく、「たまたま引いた過去のノート」を起点に、**AIが読書相手として思考を深める手伝いをする**ことに独自性がある。

### 3つのコア価値（ぶらさない軸）

1. **再発見（Rediscover）** — 偶然を"再会"へ変える。アプリの入口であり心臓。
2. **省察（Reflect）** — ノートの中身を育てる（蒸留）／前回の自分の読み方と再会する（ReadingTrace）。
3. **オンデバイス完結** — 全AIは端末内Gemini Nano。クラウド送信ゼロ＝プライバシーが差別化の土台。この制約は弱点ではなく設計哲学。

### 判断基準（機能を足すかどうかの物差し）

- **Rediscover→Reflectのループを濃くするか？** YESなら優先。単独で便利なだけの機能は後回し。
- **その結果は、次の再会の材料として残るか？** 上の問いは1回の再会の中を測り、こちらは回をまたいで測る。結果がその場で消える機能は、何本足しても初日と1年後の再会を同じにしたままになる（2026-09-17、オーナー判断で追加）。
- **オンデバイスNanoの制約（出力256トークン・Mutex直列・60秒）の中で成立するか？**
- **機能ごとに堅牢性レベルを意図的に選べているか？**（蒸留＝重厚 / ReadingTrace＝ベストエフォート）
- **本質（ノートを読む）を妨げないか？** AIは主役ではなく相手役。
- **ユーザーに意識させる必要があるか？** ReadingTrace で分かったのは、**AIの役割を「創作」から「要約」に落とすと、ユーザーの操作を増やさずに価値を出せる**ことだった（→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md) の「採らなかった案 — TimeCapsule」）。新機能に導線を足す前に、既にある行動の痕跡で足りないかを先に問う。

## 0.5 ロードマップへの昇格基準

**[current_issues.md](current_issues.md) の優先度は「壊れている度合い」、[feature_ideas.md](feature_ideas.md) の🎯は「北極星への適合度」であって、どちらも「ユーザーがどれだけ気づき、困る／喜ぶか」を直接測っていない。** 台帳・資料からNow/Next/Laterへ拾うときだけ、両方のプールに共通の物差しを1本挟む。

### 判定軸: ユーザーインパクト（2軸のOR）

- **頻度** — 常用導線（Rediscover起動・ノートを開くたび、など）で踏むか、稀な操作（オプション画面の奥・特定の連続操作、など）でしか踏まないか
- **重さ** — 気づいたときが実害（データを失う・機能が使えない・誤解を与える）か、単なる違和感か

**どちらか一方が強ければ昇格候補。両方弱いものは台帳・資料に留め置く。**
**開発コスト（規模感）はこの判定に使わない** — 選ばれた後にNow/Next/Laterのどこへ置くかで別途効かせる。

### 優先度／🎯だけでは昇格しない

current_issuesの優先度・feature_ideasの🎯は「その台帳内での重み」であって、そのままroadmapへ乗せる理由にはならない。実例:

| 項目 | 出どころの評価 | ユーザーインパクト | いまの置き場 |
|---|---|---|---|
| A-2（蒸留の「読み直す観点」） | 🎯・規模感小 | 蒸留を使うときだけ × 違和感どまり → **両軸とも弱い** | **Now** — 物差しでは上がらないが、Reflect 側の空白を埋めるためオーナー判断で入れた |
| 反証の一文（Fable 5.1 の推し） | 出どころの評価なし・規模感中 | 頻度は未測定（候補ゼロ・`NONE`の頻度が分からない）・重さは無し（見えなくても既存画面と同じ） → **物差しでは測れない** | **Next** — 同じくオーナー判断。Reflect の核（反対意見との再会）に直接効く |
| N-2（再会の演出） | 🎯 | 頻度は強いが、設計（頻度と強度）が未決 | **Later** — 設計が決まるまで物差しを通さない |
| P-1（要約のキャッシュ） | 🎯・規模感中 | ノートを開くたび × 生成中は操作が待たされる → **両軸** | 要約は実装・実機検証済み。残り（関連ノート・クイズ・補記）は台帳（[feature_ideas](feature_ideas.md) P-1） |
| TRACE-3（連続削除が同じJobを奪い合う） | 優先度中 | オプション画面の奥の連続操作でだけ踏み、再洗い出しで自己修復する → **低** | **Now** — 物差しでは上がらないが、オーナー判断で先頭に置いた |
| AI-8（「別のひとこと」が同じ一文を返すおそれ） | 優先度中 | ひとことを使うときだけ × **返事が置き換わる** → **重さで高** | **Now** |
| MAINT-2（GradientHeaderの手動契約） | 優先度低・極小 | ユーザーには何も見えていない開発側の負債 → **低** | 台帳（[current_issues](current_issues.md)） |

> **この表は履歴ではない。** 置き場が変わったら**行を書き換え**、**完了したものは行ごと消す**
> （経緯は [change_history](../dev/change_history.md) が持つ）。
> 「いつ Next へ上げたか」を書き足すと、本書が禁じている履歴置き場に戻る。

### 運用

- 昇格判定は単発では行わず、§更新運用の「大きめのPRやマイルストーン到達時の見直し」と同じタイミングでまとめて行う。
- 昇格しても current_issues / feature_ideas 側の記述は消さない。**正本は元の台帳に残る**（roadmap冒頭の「基準」節と同じ非対称）。roadmap側は該当IDへリンクするだけにする。

## 🟢 Now — 直近で着手（ループを豊かにし、土台を強くする）

**テーマ: 見えている取りこぼしを先に閉じ、そのあと Reflect の空白を埋める。**

> **Now の中の順序は上から。**

### TRACE-3. 連続削除が同じJobを奪い合う（→ [current_issues](current_issues.md) TRACE-3）

- **インパクト:** 頻度＝弱い（オプション画面の奥の連続操作）／重さ＝再洗い出しで自己修復するので
  違和感どまり。**物差しでは上がらない。**
- **それでも Now の先頭に置いたのはオーナー判断。** 消えたのに画面へ残る見え方は、
  **直前の操作が失敗したと読める**ので、自己修復することは体感の助けにならない。
- **非同期Jobとキャンセルを変える変更なので、影響面監査の引き金を踏む**（→ CLAUDE.md）。
  **両方向のテスト**（洗い出し中に削除する／削除中に洗い出す）と、走行フラグが残らないテストまでが着手の範囲。
- **正本は current_issues の TRACE-3。** ここは順序だけを持つ。

### AI-8. 「別のひとことをもらう」が同じ一文を返すおそれ（→ [current_issues](current_issues.md) AI-8）

- **インパクト:** 頻度＝弱い（ひとことを使うときだけ）／重さ＝**返事が置き換わる**ので違和感を越える。
  **重さで片軸が立つ。**
- **まず確かめる。実機では未観測である。** 同じノートのひとことを2回もらって文字列を比べるところから始まる
  （関連ノートの候補が途中で変わらないよう、関連ノートの表示が出きってから）。
  **確認は実機なので Codex 側の作業**で、直し方はその結果が出てから決める。
- **生成設定（temperature・seed）を変える案を採るなら、SDKの許容範囲をバイナリで確かめてから**
  （公式ドキュメントで決めない → CLAUDE.md の禁止事項）。
- **正本は current_issues の AI-8。** ここは順序だけを持つ。

### A-2. 蒸留の「読み直す観点」（→ [feature_ideas](feature_ideas.md) A-2）

- **インパクト（2026-09-14）:** 頻度＝弱い（蒸留を使うときだけ）／重さ＝違和感どまり。**物差しでは上がらない。**
- **それでも入れたのはオーナー判断（2026-09-14）。** 北極星の Reflect 側が Now／Next に1件も無く、
  物差しは「困る度合い」を測るので「ループを濃くする」価値を拾えない。物差しの外で線を引いた
  （→ [wip_analysis](../owner/wip_analysis.md)）。
- **着手条件は資料の懸念そのもの。** 「要約＝何が書いてあるか／観点＝どこを読み直すか」の差を言語化できてから。
  生成しない — 本文の既存の文から**選ぶ**。
- **正本は feature_ideas の A-2。** ここは順序だけを持つ。

**テーマ:「読書相手」としての深みと、Vault規模への強さ。**
ループが確立した先の、体験の質とプロダクトの堅牢性を上げる投資。優先度は状況で見直す。

## 意図的にやらないこと（Non-Goals）

北極星に照らして、当面やらないと決めるもの。判断のブレを防ぐために明記する。

- **クラウドAIへの切り替え/併用** — オンデバイス完結がプライバシーの土台。Nanoの制約は受け入れるコストであって、逃げる先ではない。
- **汎用ノート編集機能** — 本アプリは「読む・再発見する・省察する」相手役。フルエディタ化はObsidian本体の領分。**ノート本文への書き込みは蒸留の太字化だけ**に限定し、それ以外（補記・読書痕跡）はサイドカーへ逃がす。
- **単独で便利なだけの機能** — Rediscover→Reflectループを濃くしないものは、どれだけ一般的でも優先しない。

### ReadingTrace の move/rename 追従

**本文で「着手しない」と結論しているので Next には置かない。** 引き当てミスが**未読ノートで常時起きる**ため、
ミス時にフォルダ全走査をすると Rediscover が毎回重くなる。痕跡を失っても `.md` は無傷なので設計原則の範囲内
→ [reflect_reading_trace](../dev/features/reflect_reading_trace.md)（判断7: 可搬キー）。

## 更新運用

- 大きめのPRやマイルストーン到達時に、Now/Next/Laterの中身を1回見直す。
- **完了項目は取り消し線を残さず削除する。** 記録は [change_history.md](../dev/change_history.md) が持つ。
  取り消し線で残すと、完了分がNowの先頭に溜まって「次に何をやるか」が読み取れなくなる。
- 削除でNowが空いたらNextを繰り上げる。**番号は振り直さない**（設計書・`current_issues` が番号で参照するため）。
- 北極星（§0）は安易に変えない。変える時は「なぜ変えたか」をこのセクションに残す。
