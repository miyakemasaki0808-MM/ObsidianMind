## 0. grillで確定したフィルター（採否の物差し）

このフィルターに合う未実装案だけを、本資料の候補として扱う。

### AI分類
- **主軸は要約。** 毎回使う唯一のNano税ペイ機能。AIアイデアは要約の周回軌道に置く。
- **方向は「選ぶAIを徐々に強化」。** 生成（ハルシネーションを許容する自由生成）には賭けない。蒸留の「選ぶだけ」思想の延長。
- **ステートレス維持。** セッションを跨ぐAI記憶・一貫した人格は持たせない。「記憶」はReadingTrace（読書痕跡の.json）とノートの太字（蒸留の痕跡）が担い、AI自身には持たせない。
- **例外はクラウドの先生（A-13）だけ。** 「選ぶAI」を外して自分の言葉で説明する。記憶をクラウドに置くなら「ステートレス維持」も外れる（置き場所は A-13 で検討中）。端末の Nano には今までどおり3つとも当てる。

### 非AI分類
- **Rediscoverは純粋ランダム死守。** 引きに意図を混ぜず、**引きは偶然のまま、引いた後に「前回の自分」を重ねる**のがReadingTraceの解き方。
- **毎日開く仕掛け＝オーバーレイ由来の遊び心。** マスコット＋演出＋称号バッジ。ただし**ポイント/ストリークのような催促ガジェットは避け、「称号（発見の記録）」に寄せる**。
- **驚きはオーバーレイ（演出・キャラ）から湧かせる。** コンテンツ側の作り込みではなく、ノートの外側の演出で驚かせる。
- **Vault書き込みはサイドカーに逃がす。** 本文は原則触らない（本文書き換えは蒸留の太字化だけが例外）。

## 0.5 候補に共通する型（各項目はここを参照するだけにする）

**同じ話を項目ごとに書き直さない。** 以下は複数の候補にまたがって繰り返し現れた型で、
該当する項目は「→ 型◯」とだけ書く。

### 型1: 非AIで候補を出し、AIは選別だけさせる

候補列挙は正規表現・語の一致・類似度で機械的にできる。**AIに任せるべきなのは「そのうちどれが本当にそうか」の選別**で、
そこを言語化できないと「似た文が100件」「疑問文の羅列」「ただの数値抽出」になる。
Nano は Mutex 直列で1回数十秒なので、**前段を非AIにすると生成回数そのものが減る**という実利もある。

- **該当:** A-4（意図的な写しかの判別）・A-8（制約文）
- **前例:** [`RelatedNotesUseCase`](../dev/features/related_notes_ai.md) がタイトルで絞る→本文で再ランク→Nano という同じ形で動いている
- **注意:** 共通化の合図としては読まない（→ [architecture](../dev/system/architecture.md) の Controller 共通化の節）

### 型2: 効果を測る道具が先に要る

**「良くなった」を体感で主張できない候補**がある。改善の前後を比べる形を決めないうちに着手すると、
効いているかどうか永久に分からないものが1つ増える。

- **該当:** A-5（関連ノート推薦の精度）・A-8（制約文の残存率）
- **関連ノートの側は D-2 で解ける。** 関連ノートは候補のIDを返すので、同じ入力で選んだIDを数えれば前後を比べられる。
  A-5 と roadmap の L-1・A-12 が同じ台で測れる。
- **要約の側には道具が無い。** 語の重なりでは Nano の言い換えを測れないと分かった（→ [ai_quality_measurement](../dev/system/ai_quality_measurement.md) 判断7）。
  A-8 が非優先にあるのはこのため。
- **測る道具は、必ずしもアプリの中に作らなくてよい。** A-4 は `docs/` を代理コーパスに、非AI段をアプリの外で回して決めた。

### 型3: 本文は触らない。示すまでに留める

§0 の「Vault書き込みはサイドカーに逃がす」の具体形。本文書き換えの例外は**蒸留の太字化だけ**で、
太字化が「情報を足す」のに対し、統合・修正・タグ追記は「消す・変える」なので同列に置けない。

- **該当:** A-4（発見はする／統合はしない）・A-5（frontmatter へ書かない）
- **判断と作業は人間が Obsidian で行い、アプリは気づきと台帳に徹する。**

## 🔴 AI機能アイデア

### 採用候補（フィルター適合）

#### A-3. さがすの結果に要約の先頭1文を添える
- **内容:** さがすタブの自然文検索で、選ばれた結果のノートに要約の控えがあれば、その先頭1文を添える。控えの無いノートには何も添えず、ここでは生成しない。
- **適合理由:** 「選ぶAI×要約」の合わせ技。結果の納得感が上がる。
- **足場:** 今の `buildPickerPrompt` はタイトルのみを渡し、選定はこのまま変えない。
  要約の控えは完成したプロンプトを鍵に端末へ残っている（→ [note_summary](../dev/features/note_summary.md) 判断6）。
  控えの先頭1文を読むだけで生成しない形は、再会カードが既に使っている（→ [reunion_card](../dev/features/reunion_card.md)）。
- **懸念:**
  - 控えを引くには、結果のノートの本文を読んで要約と同じプロンプトを組み直す。結果は3件なので量は小さいが、結果の表示を待たせないよう後から添える。
  - 一度も要約していないノートには何も出ない。添えられない結果に空欄や断り書きを作らない。
- **規模感:** 小。

#### A-4. 二度書きの発見（Vault棚卸し・重複レコメンド）🎯

- **内容:** 明示のボタンで Vault 全体を走査し、「同じことを別のノートにも書いている」ノートの対を見つける。
  結果は Vault 内の1枚の表（`_Duplicates/duplicates.md`）に書き、走査のたびに全部書き直す。統合はアプリでは行わず、Obsidian 側で人が行う。
- **出所:** 2026-08-01 の壁打ち。「あれ？これ前も書いたかも」というオーナーの実感。
- **適合理由:** Vault が育つほど価値が上がる唯一の候補で、ほかの候補が1ノートの中を扱うのに対し、これだけが Vault 全体を扱う。
- **発見と統合を分ける（いちばん重要な線引き）:** 見せるまでで、書き換えない（→ 型3）。「似ている」と「統合すべき」は別で、
  意図的な写し（日記の反復・文脈違い・引用）を機械は確実には区別できない。
- **決まった形**（`docs/` 80本・31万字を代理コーパスに非AI段を回して決めた。v1 は AI を使わない）:
  - **粒度は段落、記録の単位はノートの対。** 文単位は同じ二度書きを断片の数だけ報告する。段落で束ねてノートの対へ集めると、代理コーパスで25対になる
  - **段構え:** ①段落の高類似の組を非AIで抜く（文分割と除外は [`buildDistillSourceModel`](../../app/src/main/java/com/example/newproject/domain/DistillSourceModel.kt) が持ち、
    段落は `isParagraphFirst` で束ね直す）→ ②ノートの対へ集める（bigram の逆引きで候補を絞るので、ノート数の2乗にならない）→
    ③意図的な写しかだけを AI に判別させる（v1 には入れない → 型1）
  - **ノート全体の類似度（Dice）は使えない。** 分布が0.2〜0.4に山を作り、分離帯が無い。上位を占めるテンプレートの様式行は、実質文字数（`hasSubstance`）で落とす
  - **走査は全 Vault 一括＋進捗＋中断。** 二度書きはフォルダをまたいで起きる。読み出しは全文＋本数の上限
  - **見送った対は、結果のファイルではなく別のサイドカー JSON に追記する。** 結果は毎回全部書き直すので、read-modify-write を作らずに済む
- **足場:** 全走査は [`collectAllNotes()`](../../app/src/main/java/com/example/newproject/data/VaultBrowser.kt)、Vault 単位の実行制御は
  [`ReadingTraceCleanupController`](../../app/src/main/java/com/example/newproject/controller/ReadingTraceCleanupController.kt) の骨格、
  フォルダとファイルの作成は `createRootChildFolder` と `ReadingTraceStore`。**新規で一番重いのは本文の一括読み出し** —
  本文を読む経路はどれも1ノート向けで、全ノートの全文を読む前例が無い。
- **置き場所:** 読書ではなく棚卸しの機能なので、専用画面（設定の奥）に置く。
- **残る未確認:** 実 Vault（300〜1000本）での分布。日記の反復・文脈違い・引用は代理コーパスに現れない。
- **規模感:** 中。類似度・束ね直し・集約は `domain` に収まり JVM テストで閉じる。実機が要るのは SAF の全走査とファイルの作成だけ。

#### A-5. 暗黙タグの抽出（タグの無いノートの関連精度を埋める）

- **内容:** `#タグ` を持たないノートについて、本文から特徴的な概念・名詞を数個だけAIに**選ばせて**サイドカーへ保存する。
  本文には書かない。保存したタグは関連ノート・検索の内部シグナルとして使う。
- **出所:** 2026-08-02 の外部壁打ち（Antigravity）。**ただし採用理由は向こうの挙げた「検索精度が上がる」ではなく、下記の実装事実による。**
- **適合理由・足場:** [`RelatedContextScoring`](../../app/src/main/java/com/example/newproject/domain/RelatedContextScoring.kt) は
  **`W_TAG = 1.0` でタグ一致を主シグナル**に据え、本文スニペット・タイトル類似は `0.5` の従シグナル。
  KDoc が明記するとおり「tags が無い候補は本文・タイトルへフォールバックする」ので、
  **タグの無いノートは関連ノートの再ランクが構造的に弱い**。新機能というより**既存機能の入力を補う**位置づけ。
- **書き込み:** サイドカーのみ。frontmatter へ書き足さない（→ 型3）。
- **懸念:**
  - **効果を測る手段が先に要る**（→ 型2）。関連ノートの推薦精度は現状ほとんど計測されていない。測る台は D-2。
  - AIが選んだタグとユーザーが手で付けたタグが混ざると `W_TAG` の重みの意味が変わる。**出自を分けて持つか、重みを変えるか**を決める。
  - 全ノートへ一括適用するとNanoのMutex直列を長時間占有する。A-4 と同じく明示実行＋上限。
- **規模感:** 小〜中。スコアリング側は既にタグを受け取る形なので、**新規は「抽出の実行制御」と「サイドカーの読み書き」**。

#### A-12. この部分に近いノート

- **内容:** 「この部分」の面（Fold ではペイン、それ以外ではシート）を開いたとき、**今の節の本文**を材料に近いノートを2〜3本出し、飛べるようにする。
- **単独の機能として立てると決めた（2026-10-06、オーナー判断）。** 置き場は [roadmap](roadmap.md) の Later。Fold の机の段には含めない。
- **出所:** 2026-09-28、質問とクイズを撤去するときに代わりの機能としてオーナーが採用した（もう片方の「この部分の余白メモ」は
  [margin_pane](../dev/features/margin_pane.md) の段4に入った）。
- **適合理由:** 自由生成をせず、飛んだ先は痕跡に残せるので「次の再会の材料として残るか」に答える。
- **安く作れる:** 非AIで候補を絞り、AIは並べ替えだけ（→ 型1）。関連ノートと同じ形・同じ配管を流用する。
- **roadmap の L-1 の未決事項を解く。** 「どの時点の節で推薦するか」は、面を開いた時点で節が決まる。
- **着手前に決めること:** 痕跡へ何を残すか。[margin_pane](../dev/features/margin_pane.md) では範囲外なので、面のどこに置くかも併せて決める。
- **規模感:** 小〜中（関連ノートの配管を流用）。

#### A-14. 机に並べた2本を、結晶の候補に入れる

- **内容:** 開いた Fold の机で今のノートの右に並べたノートを、結晶の候補へ優先して入れる。
  並べた相手は、机の記憶がその回の訪問の痕跡に控えている（→ [desk_memory](../dev/features/desk_memory.md)）。
  その相手に結晶の材料（要約の控え）があれば、今のノートと組みやすいよう候補の先頭に置く。
- **出所:** 2026-11-26 の外部の壁打ち（読書と創作の4者）の「化学反応オビ」。2冊の境に「第3の問い」を刻む案を、結晶の形に引き直した。
- **適合理由:** 北極星の Fold の姿「机の上で並べたものも、次の再会の材料として残る」に、いちばん素直に答える。
  机の記憶は並べた相手の名前を残すが、**並べて何が見えたかは残らない。** 結晶は Vault に溜まり、根拠の2本から再会できる。
  AI の仕事は今の結晶と同じく、筋があるかの選別と1文の総括だけ（→ [reflect_crystal](../dev/features/reflect_crystal.md)）。
- **足場:** 候補は今のノートと最近見た他のノート最大5件で、核は今のノート（→ reflect_crystal 判断3）。
  変えるのは候補の選び方だけで、生成・保存・一覧は今のまま使う。
- **懸念:**
  - **「右のノートは眺めるだけ」という約束と矛盾しないかを先に確かめる**（→ [margin_pane](../dev/features/margin_pane.md)）。
    右のノートの上では何も走らせず、使うのは左の痕跡に控えた名前と、既にある材料だけにする
  - 右に並べただけのノートには材料が無いことが多い。材料は30秒読んで要約が出たノートにしか控えない（→ reflect_crystal 判断4）。
    無ければ今までどおりの候補で作る
  - 問いは足さない（結晶の非ゴール）。押して作る結晶も作らない — 結晶は読むだけで溜まり、試すのは1日1回までと決めてある（→ 判断5）
  - 筋が無ければ `NONE` で何も書かない。並べた組だからといって無理につなげさせない
- **規模感:** 小。候補の選び方を変える純関数とテスト。

#### A-15. 蒸留を本文の上で選ぶ

- **内容:** 蒸留の候補文を、✨タブのチェックリストではなく、読んでいる本文の上に淡く浮かべる。押すと選び、もう一度押すと外し、確定すると太字にする。
- **出所:** 2026-11-26 の外部の分析（Gemini）。AI の結果が別のタブで待っている形を読む面へ寄せる提案のうち、蒸留だけを採った。
  要約と結晶を本文の冒頭へ出す形は採らない — 結晶は Rediscover の画面に出さないと決めてあり（→ [reflect_crystal](../dev/features/reflect_crystal.md)）、
  要約の先頭1文は再会カードが出している。
- **適合理由:** 蒸留は「本文のどの文を残すか」を選ぶ機能なので、本文の上で選ぶほうが前後の文脈を見ながら決められる。Reflect のループを濃くする。
- **足場:** 候補の選び方・範囲の調整・太字の書き戻しと復旧（書く前と後のハッシュの照合）は今のまま使う（→ [reflect_distill](../dev/features/reflect_distill.md)）。
  変えるのは入口と、選ぶ面だけ。
- **N-27 と組む。** 型では太字を太字のまま見せると決めた（2026-11-26）ので、候補だけを淡いマーカーで浮かべ、確定すると太字になる。
- **懸念:**
  - 候補の淡い色は、選んでいる間だけの部品の色である。読む面の地の色（年代）とは別に扱う
  - 選んでいる間の状態はノート単位なので、契約2箇所への登録が要る
  - 見開きと全画面でも選べるか。候補の文が見開きの境目で割れたときの見せ方
  - AI の待ち時間をどこで見せるか（→ [background_ai_ux](../dev/system/background_ai_ux.md)）。候補が届くまで、本文は普段どおり読める
  - 蒸留を重厚に作った理由（本文を書き換える唯一の機能）は変わらない。確定の手前で、選んだ文を一覧で見直す段を残すか
  - 候補が届いたときに本文の位置を動かさない（行を押し下げない）（2026-11-26 の外部の壁打ち（デザインの4者））
  - 確定せずに眺めるだけの見せ方もある。背景の文を沈めて候補だけを浮かせ、本文は書き換えない
  - 読み上げ（TalkBack）からも候補を選んで確定できるよう、選ぶ操作を読み上げの操作としても持つ
- **規模感:** 中〜大。

### 前提の例外を伴う候補

§0 のフィルターや ADR の例外を、項目の中で名指しして置く。

#### A-13. クラウドAIの先生（任意・既定オフ）

- **内容:** 端末の Nano を日々の読書の相手役に据えたまま、クラウドの Gemini API を、ユーザーが呼んだときだけ来る「先生」として足す。
  先生は複数のノートや長文の全体を読み、自分の言葉で説明する。設定で有効にしたときだけ使え、初期値はオフ。
- **出所:** 2026-11-25、オーナー起案。設計思想は Local First, Cloud Optional。
- **一番重い前提:** AI をオンデバイスに限った ADR（[一覧](../dev/decisions/README.md)の0002番）と、ロードマップの北極星「オンデバイス完結」・
  Non-Goals「クラウドAIへの切り替え/併用」を、着手の前に同じ日に改める。
- **状態:** 技術検証前。段取りの1つ目（Gemini API への接続と料金の検証）は、アプリの外（Mac のスクリプト）で済む。
- **詳細:** 先生の役・記憶の置き場所・機能要件と非機能要件・構成・クレジット・段取り・懸念は [cloud_teacher](cloud_teacher.md) にある。
- **規模感:** 大。

### 非優先（当面やらないが記録は残す）

#### A-2. 蒸留の「読み直す観点」を選ぶ
- **内容:** 蒸留で太字化する前に、「このノートで読み直すべき観点」をAIが本文の既存の文から**選んで**示す（生成しない）。ユーザーはその観点を手がかりに蒸留対象を選ぶ。
- **非優先の理由:** 要約との違い（要約＝何が書いてあるか／観点＝どこを読み直すか）を言葉にできていない（2026-11-26、オーナー判断）。
  蒸留を使うときにしか効かず、無くて困ることも無い。
- **動かす条件:** 要約との違いを言葉にできたとき。
- **入れるときの足場:** 今の `buildDistillPrompt` は候補文を直接選ばせるので、観点の段階は入っていない。

#### A-8. 但し書きを落とさない要約
- **内容:** 「ただし」「例外」「採用しない」「条件付き」といった**制約文を先に抽出**し、それを必ず残した上で要約する。設計ノート・意思決定メモで効く。
  本書で唯一、要約の周りに足すのではなく要約そのものを良くする案である。
- **非優先の理由:** 効いたかを測る道具が無い（2026-11-26、オーナー判断）。プロンプトで「必ず残せ」と指示しても、
  256トークンの中で制約文と本文の要約のどちらを削るかはモデルが決めるので、出力を検査しないと効いたか分からない。
  語の重なりの物差しは Nano の言い換えを測れなかった（→ [ai_quality_measurement](../dev/system/ai_quality_measurement.md) 判断7）。
- **動かす条件:** 制約文が要約に残ったかを測る方法が決まったとき。
- **入れるときに決まっていること:** 抽出は非AI、要約だけAIにして Nano は1回で済ませる（→ 型1）。
  制約文が多いノートでは要約が制約の羅列になるので、上限が要る。

- **出所:** 2026-08-02 の外部壁打ち（Antigravity）の放置ノートフィルター。一覧を出さずに引く形は 2026-09-08 の外部壁打ち（Gemini）。

#### N-15. 読書中のスリープ防止

- **出所:** 2026-09-08 の外部壁打ち（Gemini）。

#### N-27. 読む面の組版の型（ノートの型で組み方を変える）

- **内容:** 本文をモダンなプレートに組み、ノートの型ごとにプレートの中の組み方を変える。型は「技術書」「読書ノート」「標準」の3つから始める（「暮らし」は後で）。
  どの型もノートの文字は変えず、見出しの役割に合わせて組むだけにする。
  - **技術書:** タイトルの採番を小さなラベルに分ける・🎯 目的をリード文に・📶 レベルをタイトルの下の札に・
    🧪 構文と実践コードをファイル名付きのコード枠と実行結果に・📚 関連知識を用語集に・
    ⚠️ 注意点を黄土の面にまとめ、【件名】に番号を付け、❌ before と ✅ after を上下に並べる
  - **読書ノート:** 🕓 概要の「項目：値」を本の情報カードに（ステータスは札）・📝 紹介文の `[!quote]` を紙面を渡る帯に・
    💡 要点メモを番号付きの要点カードに・🔗 関連をリンクの札に・
    ✍️ コメントを「自分の言葉」の面として分け、「第N章」を章の扉、「N.N」を番号付きの小見出しに
  - **標準:** 番号を付けない見出しと短いアクセントの線・最初の段落をリード文に・やや大きい本文と行間
- **出所:** 2026-11-26、オーナー起案。白い読む面を何とかしたいところから、年代の紙ではなくモダンな紙面に組む方向へ移った。
  Apple の開発者ドキュメント（DocC）の囲みとコード枠、Apple Books のテーマを参考にした。借りるのは組み方だけで、
  見た目と SF フォントは写さない（SF フォントの利用許諾は Apple のプラットフォーム向け）。モックで合意した。
- **型の決め方（2026-11-26、オーナー判断）:** 設定を作らず、ノートの中身で自動に決める。
  1. frontmatter の `cssclasses`（Obsidian 標準の欄）に型の名前があれば従う
  2. 無ければ見出しの骨格で決める — 目的・構文・注意点 → 技術書、概要・要点・コメント → 読書ノート。見出しの語は一般的な語の辞書と照合する
  3. どれにも当たらなければ、コードの枠を持つノートは技術書、持たないノートは標準
  - **分野の判定（AI）は使わない。** 判定は開いた後に届くので最初に読むときに組めず、途中で組み替えると紙面がずれる。
    分野は冊子の紙と宝石の色が持っている
- **Vault の実測（Mac の iCloud の写し・326本。端末の Vault と同じかは未確認）:** コードの枠を持つノートは240本で、ほぼ Python。
  資格試験の166本と `_FileData` は目的・構文・注意点の骨格、読書の30本は概要・要点メモ・コメントの骨格で書かれている。`cssclasses` は0本。
- **適合理由:** 本質の「ノートを読む」を直接良くする。データを増やさず、Vault も書き換えない。
- **前提の変更（2026-11-26、オーナー判断）:**
  - 佇まいのチャネルの「書体・行間」の行に「ノートの型」を持たせる（→ [bearing_channels](../dev/system/bearing_channels.md) §11・[ADR 一覧](../dev/decisions/README.md)の0005番）
  - 型で変えるのはプレートの中の組み方だけ。地の色（年代）とプレートの形（面の役割）は型でそろえる
  - N-9（読書専用タイポグラフィ）を取り下げた理由のうち、配色の衝突は配色を選ばせないので当たらない。字組みの重要度はオーナーが判断を改めた

  - **見出しの大きさの順**（2026-11-27 の外部の壁打ち（UI と色の4者））。ノートの題は 20sp で、本文の H1（24sp）より小さい。H5・H6（15sp・14sp）は本文（16sp）より小さい。題 > H1 > … > 本文の順に組み直す

#### N-33. 余白メモの地層

#### N-23. ほかのノートに書いた言葉を、今のノートを読んでいるときに戻す（保留）

- **非優先の理由:** 補助の面への出し方が決まらない（2026-11-21、オーナー判断で保留）。

- **動かす条件:** バックリンクの読む負荷の直し方が決まり、一覧を増やさずに出せる形が見えたとき。
- **入れるときに決まっていること:** 正は痕跡ファイルのままで、索引は読み写すだけ（→ [knowledge_index](../dev/system/knowledge_index.md) §2）。

- **出し方の案（2026-11-26 の外部の壁打ち（読書と創作の4者））:**
  - **読んでいるあいだに1件だけ戻す。** 一覧ではなく、ほかのノートで書いたメモを1件だけ補助の面に淡く置く。

    どのメモを選ぶかは索引の語の重なりで足りる（→ 型1）。**動かす条件の「一覧を増やさずに出せる形」に当たる案**で、着手するならこの形から確かめる
  - **引き直す側で戻す。** 余白メモを書いたノートだけを母集団にして、純粋乱数で1件引く。N-7 と同じ「別の引き方」で、Rediscover の母集団には触れない。
    補助の面に何も足さないので、上の非優先の理由には当たらない。入口の置き場は N-7 と一緒に決める（→ §2）
- **出所:** Fable 5.2 の見直し（→ [fable51_triage](fable51_triage.md) F-37）。

#### N-24. ノートの本文で探す（全文検索）
- **内容:** さがすに、本文の言葉でノートを探す道を足す。
- **非優先の理由:** 段5で入れないと決めた（2026-11-21、オーナー判断 → [knowledge_index](../dev/system/knowledge_index.md) §1）。

- **動かす条件:** タイトルと AI のモードで見つからない探しものが、実際の利用で繰り返し起きたとき。
- **入れるときの費用:** さがすの非ゴール「全文検索をしない」を書き換える。本文を索引の DB に持つ（今は指紋だけで、3,000本で約4.3MB）。

## 🟡 非機能・データ基盤アイデア

> **§0のフィルターの対象外だが、🔧 とも違う。** ここに置くのは**製品として動くランタイムの挙動**
> （待ち行列・キャッシュ・実行抑制・保存層）で、開発時にしか動かない計測器とは寿命が違う。
> 判断軸は「ユーザーが待たされる／同じ計算を繰り返すのを、どこで止めるか」と
> 「そのデータをどこに置くか」。

### P-1. 入力指紋によるAI結果キャッシュ 🎯

- **内容:** 入力が同じなら AI を呼び直さない。残っているのは関連ノートで、今もノートを開くたびに `generate` を呼び、その間 `generateMutex` を占有する。
- **出所:** 2026-08-05 の外部壁打ち（Codex）。
- **今あるもの:** 要約と再会カードの前後の要約は、完成したプロンプトを鍵に端末へ保存している（→ [note_summary](../dev/features/note_summary.md) 判断6・7、
  [reunion_card](../dev/features/reunion_card.md) 判断6）。分野判定は入力の版（[`NoteFieldInputVersion`](../../app/src/main/java/com/example/newproject/domain/NoteFieldInputVersion.kt)）を鍵にしている。
  **残るのは鍵の発明ではなく、この形を関連ノートへ広げることと、保存層の上限設計である。** 保存先を知識索引の Room に足すかは着手時に決める。
- **鍵の決め方:** 完成したプロンプトそのものを鍵にする形を先に検討する（版の定数を上げ忘れる経路を作らない）。
  結果の読み方が入力の外で決まる部品があるときだけ、版を足す。関連ノートは候補の一覧も入力に入る。機能の種別は分ける。
- **懸念:** 件数の上限（LRU など）を先に決める。効果は P-2 の計測でヒット率を見る。モデルの更新で出力は変わるので、版を鍵に入れられないなら更新後に一度捨てる。
- **規模感:** 中。呼び出し側は `generate` の前後を包むだけで済むはず。

### P-2. Nano実行の優先度と、待ち時間の計測

- **内容:** ①ユーザーが今押した処理 ②画面表示に必要な処理 ③自動生成 を別優先度で直列化する。
  あわせて機能ごとのキュー待ち時間・生成時間・キャンセル率・タイムアウト率を端末内に記録する。
- **出所:** 2026-08-05 の外部壁打ち（Codex）。
- **足場 — 指摘は正しい。** [`AICoreClient`](../../app/src/main/java/com/example/newproject/ai/AICoreClient.kt) の
  `generate` は `generateMutex.withLock` の1本で、**優先度は無い**。
  自動生成（ノートを開いた時の要約・痕跡要約）が先に入ると、その後にユーザーが押した操作は待つ。
  **待ち行列の論点自体は一度考えられている** — `measurePrompt` は
  「計測は生成を伴わないので待ち行列へ入れない」と明記して意図的にMutexへ相乗りさせていない。
  つまり**足りないのは発想ではなく優先度の区別だけ**。
- **順序: 先に計測、後に優先度。** 「手動操作が実際に待たされているか」は現在まったく測られていない。
  P-1（キャッシュ）を入れると自動生成の回数自体が減るので、**キャッシュ後にも問題が残るかは分からない**。
  **計測 → P-1 → 残っていれば優先度**の順が無駄がない。
- **計測の設計上の注意:** 本文もプロンプトも保存しない。**数値だけ・有限件数**。
  D-1 が抱えるプライバシー懸念（本文が画面・共有から漏れる）を持ち込まない。
- **懸念:** 優先度付きキューは飢餓（自動生成が永久に走らない）を作り得る。
  自動生成は「ユーザー操作が無い間だけ走る」形にすると単純だが、
  **[background_ai_ux](../dev/system/background_ai_ux.md) の知らせ方（浮く通知を作らず、結果が出る面の中で示す）と衝突しないか**を先に見る。
- **優先度と知らせ方を組にする（2026-11-27 の外部の壁打ち（UI と色の4者））。** 明示の操作の結果だけを読み上げで知らせ、自動の生成は黙る。
- **規模感:** 計測だけなら小。優先度キューまで含めると中。

### P-4. 出力の枠を広げる（`genai-prompt` を上げ、経路ごとに配分する）

- **内容:** `genai-prompt` を beta2 から上げ、`maxOutputTokens` を経路ごとに明示して、今の256トークンより長い出力を許す。
- **出所:** 2026-11-26 の外部の壁打ち（実務の4者）。3人が「256トークンの壁」を挙げた。
- **足場 — 調べはある:** beta4 では出力の上限が `1..4096` に広がり、既定値も4096になる。ただし入出力の合計の上限は実測で4,352のままなので、
  既定値のまま上げると入力に256トークンしか残らず、全経路が動かなくなる（→ [dependency_policy](../dev/system/dependency_policy.md) §5）。
  **上げるなら `maxOutputTokens` の明示とセットでしか成り立たない。** beta5 は調べていない。
- **効きどころ:** 主軸の要約を長く確かにできる。A-8（但し書きを落とさない要約）の「256の中でどちらを削るか」という前提も変わる。
- **懸念:**
  - 出力を増やすと入力の予算が減る。経路ごとに入力と出力の配分を決め直す（→ [ai_input_excerpt](../dev/system/ai_input_excerpt.md)）
  - 生成時間が延び、60秒のタイムアウトと Mutex の占有が伸びる（→ P-2）
  - 依存の更新は単独で行い、AAR を展開して制約を確かめ、全 AI 経路を実機で一巡する（→ dependency_policy 判断3）
  - 要約の控えの鍵は完成したプロンプトで、出力の枠は入っていない。枠を変えても256で作った控えが出続けるので、鍵に入れるか、上げたときに一度捨てる
- **規模感:** 中（コードは小さいが、実機の一巡が重い）。

## 🔧 開発・検証用アイデア

> **§0のフィルターの対象外。** ここに置くのは製品機能ではなく**計測器**なので、「主軸は要約」「催促ガジェットを避ける」といった product 側の物差しでは採否を決めない。判断軸は「これが無いと何を確かめられないか」。

### D-1. プロンプトログ（モデルに実際に何を見せたかを見る）🎯

- **内容:** AIへ実際に渡ったプロンプト全文と、その組み立て内訳をアプリ内で確認できるようにする。全経路（いまは9本。要約・関連・ピッカー・蒸留・部分要約・再会カードの選別と前後の要約・分野判定・結晶）それぞれについて、最終プロンプト・抜粋かどうか・実文字数・骨格に選ばれた見出し・切り落とされた区間が見えると足りる。
- **位置づけ: あると便利な観測窓。** 予算判断という「これが無いと何も決められない」役割は
  instrumentation テスト（`PromptTokenBudgetTest`）が引き取り済みで（→ [ai_input_excerpt](../dev/system/ai_input_excerpt.md)（トークン計測器））、
  **D-1 に残る価値は「プロンプト全文と組み立て内訳を、開発中に何度でも目で見られる」こと。**
- **これが解けること:**
  - **Nanoが抜粋レイアウトを誤読していないかが分かる。** `## Note outline` を要約対象と誤解して目次を返す、
    足場の文字列が出力へ漏れる、といった失敗は現状ログが無いと気づけない。
  - 将来プロンプトを触るたびに、変更前後の入力を並べて比較できる。
- **設計上の注意（先に決めておくべきこと）:**
  - **Vaultに書かない。** ログはユーザーのノートではない。アプリ内保存に留め、外へ出すなら共有シート経由で都度ユーザーが選ぶ。
  - **プロンプトにはノート本文がそのまま入る。** ネットワーク権限が無いので送信の危険は無いが、画面・スクショ・共有からは漏れる。
    **既定オフ**にして、設定の奥かデバッグビルド限定に置く。
  - **生成を遅らせない。** Nanoは1回数十秒でMutex直列なので、ログ保存は生成完了後に非同期で行う。
  - **保持件数の上限を先に決める。** 決めないと単調増加する（読書痕跡の孤児ファイルと同じ型）。直近N件のリングバッファで足りる。
- **懸念:** 開発用UIが通常画面に混ざると「本質はノートを読む」がぼやける。**ユーザーが偶然たどり着かない場所**に置けるかが分かれ目。
- **規模感:** 小〜中。プロンプト文字列は既に `PromptBuilder` が返し、`countTokens()` の呼び出しも
  `AICoreClient.measurePrompt()` として既にあるので、**そこは作り直さない。**
- **着手契機は症状駆動。** 「抜粋レイアウトの誤読を疑う具体的な症状が出たとき」。

### D-2. 関連ノートの回帰再生器（固定の入力で、選んだノートを数える）🎯

- **内容:** 固定の架空Vaultと固定の入力で関連ノートの経路を流し、プロンプトやスコアを変えた前後で選んだノートのIDを比べる。
  数えるのは、選んだIDが候補に入っているか・該当なしが妥当か・前後で選ぶものがどう変わるか。
- **出所:** 2026-08-05 の外部壁打ち（Codex）。数える中身は roadmap の L-1 が決めた（2026-11-14、オーナー判断）。
- **型2（効果を測る道具が先に要る）を、関連ノートの側で埋める案である。** A-5（暗黙タグ）と roadmap の L-1・A-12 が同じ台で前後を測れる。
- **IDで数えるので、要約の物差しの弱点を持たない。** 語の重なりは言い換えに弱かった（→ [ai_quality_measurement](../dev/system/ai_quality_measurement.md) 判断7）が、
  関連ノートはIDを返すので、架空Vaultに置いた正解と照らせば機械で判定できる。
- **D-1 との関係:** D-1 は「**実際に流れた**プロンプトを事後に見る窓」、D-2 は「**同じ入力を何度でも流せる**台」。
  役割が違うので置き換えではない。D-1 は症状が出たときの調査用で、D-2 は症状を出さないための回帰用。
- **D-1 のプライバシー懸念を持たない。** 架空Vaultなので実ユーザーのノートを保存しない。
- **設計上の注意:**
  - **架空Vaultの中身が品質を決める。** タグのあるノートと無いノート、似たタイトルで中身の違うノート、該当なしが正しい入力など、
    **壊れ方の違う入力を揃える**。実Vaultの分布に似せる必要はなく、**失敗を再現できることが条件**。
  - **非AIの段（タイトルでの絞り込みと本文での再ランク）はJVMテストで数えられる。** 端末が要るのは Nano が選ぶ段だけで、
    A-5 のようにスコアを変える案は、まずJVMの側で前後を比べられる。
  - Nano の段は生成が決定的なので、同じ端末・同じモデルのうちは前後の完全一致で差分が取れる（→ [ai_quality_measurement](../dev/system/ai_quality_measurement.md) 判断8）。
    モデルが更新されても、IDの正誤で数える比較はそのまま使える。
  - Nano の段は実端末が要る（Nanoはエミュレータで動かない）ので、CIには載らない。**手元で回す道具**として設計する。
- **規模感:** 中。架空Vaultと正解の用意と、結果の保存が新規。
