# 設計思想 — AI入力の抜粋

**対象領域:** 7つのプロンプトへ渡す「本文」の作り方（用途別の文字数上限と、その中身の選び方）
**初版:** 2026-07-28（先頭固定長切り出しの解消）
**状態:** 実装済み・**実機確認済み（2026-07-28・[PR #43](https://github.com/miyakemasaki0808-MM/ObsidianMind/pull/43)）**。予算値の見直しと、関連ノートのフォーカスセクション文脈は意図的に別作業として切り離した。2026-08-01 に、その予算見直しの前提だった**実トークン計測器**を instrumentation テストとして追加し、**実機で計測まで完了した**（→ §13）。**予算値そのものは未変更。** 計測により §9.3 の「注意書きが予算の38%」はトークンでは1.7%と判明し、短縮注意書き案は撤回した。

- **今どうなっているか**は [source_code_analysis.md](../source_code_analysis.md) §8.4、**いつ変えたか**は [change_history.md](../change_history.md) を参照。
- 対象コード: `model/NoteExcerpt.kt`・`model/NoteExcerptLimits.kt`・`domain/NoteExcerptBuilder.kt`・`ai/PromptBuilder.kt`。
- 責務をどこへ置くかの横断判断は [architecture.md](architecture.md) の追記「AI本文の切り出し責務を呼び出し側へ置く」が持つ。本書は**抜粋の中身**を扱う。

## 1. 背景 — 「後ろを全部捨てる」実装だった

要約・関連ノート・補記・クイズ・セクション3経路の7プロンプトは、いずれも `PromptBuilder` 内の `String.take()` で本文を先頭から固定長に切っていた。切り方が問題だったのではなく、**捨てる場所が常に「後ろ」だった**ことが問題だった。

長いノートの後半には、結論・検証結果・残課題・次にやることが置かれる。つまり**ノートの価値が集まっている場所が、構造的に毎回捨てられていた**。

これは「後半が少し欠ける」という程度の劣化ではない。実例として、案を3つ検討して案2で解決し残課題を1つ残したノートは、先頭1,200文字だけを見ると「解決策を検討中のノート」に見える。**要約は精度が低かったのではなく、系統的に間違っていた。**

補記はさらに深刻だった。補記プロンプトは次の4項目を要求する。

```
種別 / 粒度（断片・原子メモ・中粒度・長文）/ 状態（十分・書きかけ・具体例不足…）/ 補記方針
```

**この4つはすべてノート全体に対する判定である。** 導入部だけを見せられて粒度を問われれば、どんなノートも「断片」「書きかけ」に見える。プロンプトが `no generic advice` と禁じていても、具体を書くための材料が入力に存在しなかった。

## 2. 判断1 — 捨てる場所を「後ろ」から「真ん中」へ

予算内に収まらないとき、捨てる対象を後半ではなく中盤にした。人が長い文書を斜め読みするときと同じ戦略である。

| | 捨てるもの | 残るもの |
|---|---|---|
| 旧 | 後ろを全部 | 冒頭のみ |
| 新 | **真ん中だけ** | 骨格 ＋ 冒頭 ＋ 末尾 |

真ん中を捨てる代償は「捨てた部分に何があったか分からない」ことなので、そこを**見出しの骨格で補う**（判断2）。骨格は捨てた中盤の地図として働く。

冒頭と末尾は 60% / 40% で配分する。冒頭を厚くするのは、主題の宣言が読み取れないと末尾の結論も解釈できないため。末尾を4割確保するのは、上記のとおりそこが最も価値が高いからである。

## 3. 判断2 — 見出しは削らず、骨格へ「昇格」させる

Markdown記法を削ってスリムにしたのではない。**`#` の行だけを全文から抜き出し、`## Note outline` という専用枠へ並べ直した。** 本文側にも見出しはそのまま残るので、見出しは抜粋中に2回現れる。

**この重複は意図的に許容する。** 骨格は「全体の地図」、本文は「実際の中身」で役割が違い、地図から見出しを間引くほうが害が大きい。重複しても予算不変条件を破らないことをテストで固定している。

見出しが予算に収まらない場合は、**全体から均等選抜する**（先頭からN件ではない）。最初と最後の見出しは必ず含め、飛ばした区間には `…` を置く。先頭からN件では「前半の目次」にしかならず、全体構造を伝えるという目的を果たさない。

## 4. 判断3 — 予算は変えず、配置だけ変える

要約1,200 / 補記・セクション1,500 / 関連600 / クイズ1,200 という既存の文字数上限は**1文字も変えていない**。生成時間・Mutex直列化・出力256トークン上限へ影響を与えないまま、品質だけを動かすためである。

予算調整を分離したのは、**単独の数字を見て増減してはいけない**領域だから。特に関連ノートの600文字は、候補ブロック3,500文字・指示文・タイトルと合わせた完成プロンプト全体で評価する必要がある。Prompt API には入力トークン上限があり、`countTokens()` / `getTokenLimit()` も**AARで実在を確認済み**（→ §13）なので、**実トークン計測を伴う別作業**として切り出した。

同じ理由で、関連ノートの「フォーカスセクション文脈」（[related_notes_ai](related_notes_ai.md) Phase 1 の未実装案）も見送った。関連ノートはノートを開いた瞬間に自動起動するのに対しフォーカスはスクロールで動くため、「どの時点のセクションで推薦するか」を先に決める必要がある。

## 5. 判断4 — 単一の巨大ブロックは、捨てずに切る

段落・コードブロック・表・リストが1個で枠を超える場合、そのブロックを捨てるのではなく**そのブロックだけを枠まで切る**。捨てる仕様にすると「末尾が巨大なコードブロック1つ」のノートで末尾枠が空になり、判断1の目的そのものを失う。

**コードブロックを切ったときは閉じフェンスを復元する。** 未閉じフェンスはモデルの読解を確実に壊す。

## 6. 判断5 — 正規化の副作用は仕様として引き受ける

抜粋は表示用の Markdown パーサ（`parseMarkdownBlocks`）をそのまま流用する。専用パーサを起こさない代わり、次の変換が**予算超過ノートにだけ**起きることを仕様として明記する。

| 変換 | 評価 |
|---|---|
| YAML frontmatter を除去する | **利得**。タグ・別名・プラグインのメタデータが予算を占領しなくなる |
| 段落内の改行を空白へ畳む | 実質無害 |
| ordered list の番号を `-` へ正規化する | **損失**。番号自体に意味があるノートでは情報が落ちる |
| コードフェンスの言語名が落ちる | 軽い損失 |

frontmatter の除去は見落とされやすいが効果が大きい。Obsidian のノートは frontmatter が数百文字に達することがあり、以前はそれが予算の1〜2割を占めていた。なお現ノートのタグは `RelatedNotesUseCase` が `parseMeta()` から別経路で取得して再ランクに使っているため、抜粋から落ちても推薦品質には影響しない。

**短いノート（予算内）はパースせず原文をそのまま渡す。** したがって同じノートでも長短で挙動が変わるが、これは「超過した入力だけを圧縮する」という仕様の当然の帰結として受け入れる。

## 7. 判断6 — 抜粋であることをモデルへ明示する

区切りは `…（中略）…` のような記号ではなく、`## Note outline` / `## Beginning excerpt` / `## Ending excerpt` / `(omitted)` という明示ラベルにした。小さいモデルほど、プロンプト要素間の境界が曖昧だと誤読する。

加えて、抜粋時のみ注意書きを本文の直前へ置く。

> The following content has been compacted and may combine a note outline with excerpts from the beginning and ending. **A (omitted) marker denotes a skipped span when present.** Do not assume the content is continuous or complete。

`when present` と条件付きにしてあるのは、正規化だけで全ブロックが収まり `(omitted)` が出ないケースが実在するため。無条件に「省略箇所は (omitted) で示す」と言うと、モデルが存在しない省略を探しに行く。

注意書きと本文をつなぐ改行までを `ABRIDGED_NOTICE_PREFIX` として描画と予算計算で共有し、**AIへ渡る本文由来領域の全体が用途別上限を1文字も超えない**不変条件へ揃えている。

## 8. 判断7 — 解析はメインスレッドから外す

抜粋生成は最大1MBの本文をMarkdown解析する。レビュー時の実測で、デスクトップJVMでも**1MBノートで約460ms**（200KBで約20ms）を要することが分かった。呼び出し元はいずれも `Dispatchers.Main.immediate` のスコープであり、特に関連ノートは**ノートを開いた瞬間に自動起動する**ため、そのまま操作の引っ掛かりになる。

5クラス・7呼び出しの抜粋生成だけを `Dispatchers.Default` へ移した。各クラスは本番既定値が `Default` の `excerptDispatcher` を持ち、JVMテストではテストスケジューラへ差し替える。従来の `take()` は先頭N文字のコピーで実質ゼロコストだったため、**これは今回の変更が持ち込んだ新しい負荷**である点に注意する。

呼び出しが再びメインスレッドへ戻らないことは、**ソース走査テスト**（`NoteExcerptThreadingTest`）が呼び出し箇所の一覧ごと固定する。Controller一覧ではなく「`buildNoteExcerpt` を呼ぶ全箇所」を対象にしているのは、横展開が最後の1本を取り残す型の失敗を過去に踏んでいるため。

## 9. 得られた知見

### 9.1 効いたのは「量」ではなく「配置」だった

実際にモデルへ渡る本文は**減っている**。要約なら以前の1,200文字連続に対し、いまは冒頭406＋末尾272＝678文字しかない。それでも出力が良くなるなら、結論は一つしかない。

**同じ予算なら、連続した先頭より、構造を伝える不連続な断片のほうが強い。**

プロンプトの文言を磨くより、入力のどこを見せるかを変えるほうが効いた。オンデバイスの小さいモデルでは、指示の精緻化より入力設計のほうが伸びしろが大きい可能性がある。

### 9.2 補記だけが改善を3経路から受け取る

補記プロンプトは本文だけでなく、**AI要約と関連ノートも入力として受け取っている**。したがって今回の変更で補記の入力は3つとも同時に良くなった。

| 補記への入力 | 変化 |
|---|---|
| 本文 | 先頭1,500文字 → 骨格＋冒頭＋末尾 |
| AI要約 | 先頭1,200文字の要約 → 骨格＋冒頭＋末尾の要約 |
| 関連ノート | 先頭600文字で選定 → 骨格＋末尾込みで選定 |

**AI出力を別のAI入力へ流している箇所では、上流の改善が下流で乗算される。** 逆に言えば上流の劣化も乗算されるので、要約の品質は補記の品質でもある。

### 9.3 注意書きは安くない

抜粋であることを伝える注意書きは226文字ある。これは予算の内側から支払っている。

| 用途 | 予算 | 注意書きの占有率 | 実本文 |
|---|---:|---:|---:|
| 要約 | 1,200 | 19% | 678文字 |
| 補記 | 1,500 | 15% | 903文字 |
| **関連** | **600** | **38%** | **228文字** |

**関連ノートは予算の4割を注意書きに払っている。** 短縮版の注意書きを持たせるか予算を上げるかの検討余地があり、予算見直し（判断3）の際に最初に見るべき箇所である。

> **2026-08-01 の実測により、この節の結論は撤回する。** 上表は**文字数**の比率で、
> **トークンで測ると注意書きは44トークン＝完成プロンプトの1.7%**しかない（→ §13）。
> 注意書きが英語で本文と候補が日本語のため、文字数比がトークン比にならない。
> 分母も違う（上表は抜粋予算だけ、実測は完成プロンプト全体）。**2つの誤差が同じ向きに効いて、
> 問題を実際より大きく見せていた。** 短縮注意書きは対応候補から落とす。→ [lessons](../lessons.md) L22

### 9.4 予算内のノートは1文字も変わっていない

短いノートのプロンプトは移行前と文字列単位で同一で、7プロンプトすべてを回帰テストで固定している。**したがって短いノートで品質が変わったように見えるなら、それは Gemini Nano の出力揺らぎである。** 効果を確かめるときは長文ノートを複数回生成して比較する。

## 11. 保証していないこと

- **品質改善は測定していない。** 上記の因果はコードから導いた説明であり、A/B比較は行っていない。現時点の裏付けは実機での主観的な印象のみ。
- **予算は文字数で切っており、トークン数では切っていない。** 日本語と英語で実トークン数は大きく変わる。**測る手段は §13 で入ったが、それで予算の切り方が文字数からトークン数へ変わったわけではない。**
- **Nanoが抜粋レイアウトをどう解釈するかは未検証。** `## Note outline` を要約対象と誤解して目次を返す、足場の文字列が出力へ漏れる、といった失敗は実機でしか確認できない。

## 13. 計測器 — 予算を動かしてよいかを数字で判断する（2026-08-01）

§11 の「トークン数は見ていない」を解消するために、実機でトークンを測る instrumentation テスト
（`PromptTokenBudgetTest`）を置いた。**予算値は1つも変えていない。** 判断材料を作るだけの変更である。

### 判定式を間違えると結論が逆になる

`countTokens()` が数えるのは**入力トークンだけ**で、`getTokenLimit()` は**入力と出力の合計上限**である。
したがって余裕は次で求める。

```text
headroom = tokenLimit − inputTokens − maxOutputTokens
```

`inputTokens < tokenLimit` で判定すると、**出力予約ぶんを二重に使えると誤読する**。
予算を上げた結果として押し出されるのは入力ではなく生成側なので、症状は「入りきらない」ではなく
「応答が途中で切れる」になり、原因に辿り着きにくい。**出力予約を必ず引く。**

`maxOutputTokens` はSDKが未指定時に埋める既定値を `GenerateContentRequest` から読み出す
（定数を書かない）。SDKを上げれば既定値の変化に自動で追随する。

### 注意書きのコストは差分で測る

`ABRIDGED_NOTICE_PREFIX`（226文字）を単体で `countTokens()` にかけても答えにならない。
前後の文字列と結合するとトークン境界が変わるため、完成プロンプトへの寄与と一致しないからである。
**同じ本文で「注意書きあり」と「なし」の完成プロンプトを測り、その差**を実コストとする。

### 経路の数え方を固定する

コード上には数え方が3つ混在していた（抜粋を使う7形状／公開ビルダー8個／internal込み10個）。
計測では次の定義を採る。

| 区分 | 数 | 内訳 |
|---|---|---|
| 機能経路 | 8 | 要約・関連ノート・補記・クイズ・セクション・蒸留・読書痕跡要約・**検索ピッカー** |
| 計測ケース | 12 | 上記のセクションを3種、クイズを3形式へ分解 |

[dependency_policy](dependency_policy.md) の「AI 7経路」は**実際にAIを呼ぶ検索ピッカーを数え落としていた**ので同時に訂正した。

### 保証していないこと（重要）

**これは「定義済み計測プロファイルの回帰テスト」であって、入力長の上限保証ではない。**
本番にはまだ上限の無い可変入力が残っている。

- セクションチャットは会話履歴を**全件そのまま**渡す（`SectionChatController.sendMessage`）
- 関連候補はタイトルだけで文字数予算を超えた場合、**収まらないまま返る**（`RelatedCandidateContext` の最終フォールバックは `fits()` を確認しない）
- 各経路のノートタイトル・検索クエリにも長さの上限が無い

プロファイルは2種（現実的な日本語散文／コード・URL・UUIDが混ざる高密度入力）を置き、
**同じ文字数でもトークン数が変わる**ことを見えるようにしている。それでも網羅ではない。
真の上限保証は本番側へ上限を入れる別作業であり、**緑であることを「どんな入力でも上限内」と読んではいけない。**

### Nano非対応端末では skip する

`countTokens()` / `getTokenLimit()` は AICore へ問い合わせるため、Nano が使えない端末では実行できない。
**skip 判定には生の `FeatureStatus` だけを使う。** `AICoreClient.checkAvailability()` は
例外まで `Unavailable` へ畳む（→ 課題 AI-2）ので、それで判定すると
**SDKの回帰が「非対応端末」に化けて見逃される**。計測呼び出し自体が投げた例外は skip せず失敗させる。

非対応端末で赤にしないのは、その赤が「テスト対象の故障」ではなく「実行環境が要件を満たさない」ことしか
意味さないため。2026-08-01 に instrumentation の土台（Runnerが起動しComposeを描画できること）を
切り分けて緑にした意味が、環境由来の赤と混ざると失われる。

> **この skip 規約が AI 以外の instrumentation にも要るようになったら、独立した文書へ昇格させる。**
> 現時点で対象は端末AIを呼ぶテストだけなので、専用文書を起こさずここに置いている。

| 要約 | 713 | 614 | 3,383 |
| 検索ピッカー | 533 | 533 | 3,563 |
| 読書痕跡要約 | 349 | 349 | 3,747 |

**高密度混在プロファイルのほうがトークンが少ない。** 同じ構成で作った入力なので直感に反するが、
コード・URL・UUID は英数字中心で、日本語より1文字あたりのトークンが安い。
**「トークン密度が高い入力」を作ったつもりが、実際には日本語散文のほうが高かった。**
プロファイルの狙いは外れたが、**言語がトークン数を支配することの実測にはなっている。**

### 注意書きの実コストは 44 トークン（＝ AI-1 の前提が覆った）

関連ノート経路で「注意書きあり − なし」の差を取った結果。

| 見方 | 占有率 |
|---|---:|
| 文字数（抜粋予算600に対して） | 38% |
| **トークン（完成プロンプト2,556に対して）** | **1.7%（44トークン）** |

§9.3 で「関連ノートは予算の4割を注意書きに払っている」と書いたのは**文字数の話**であり、
**トークンで見ると桁が違う**。注意書きが英語で本文と候補が日本語のため、文字数比が
そのままトークン比にならない。

**したがって §12 の「関連ノート専用の短縮注意書き」は、効果が44トークン未満で、
余裕1,684トークンに対して意味を持たない。** 対応候補から落とす。

一方で**予算を上げる余地は実測で確認できた** — 関連ノートは全経路で最も入力が大きいが、
それでも1,684トークンの余裕がある。600文字を上げる方向は、この余裕の範囲で検討できる
（→ [current_issues](../_wip/current_issues.md) AI-1）。

**教訓は [lessons](../lessons.md) L22** — 分母と単位を明示せずに比率を語ると、
問題を実際より大きく見せる。

### 実行にはフォアグラウンドのActivityが要る

AICore はバックグラウンドからの利用を拒否する。`ActivityScenarioRule` で `MainActivity` を
立てないと、`generate()` と `warmup()` は `[ErrorCode 30] Background usage is blocked`、
`countTokens()` は `[ErrorCode 10003] Tokenization failed` で落ちる
（**同じ原因が経路によって別の顔で出る**）。`getTokenLimit()` はメタデータ照会なので
バックグラウンドでも通り、この非対称が切り分けの手がかりになった。

→ 詳細は [lessons](../lessons.md) L20・L21。
