## 1. 着手前の検算 — 資料の記述3件を訂正する

L23（台帳に長く残った課題ほど、着手時には前提が古い）に従い、着手前に実装を当てた。

### 訂正1: 「画像は alt テキストが抜粋から丸ごと落ちている」は誤り

`![alt](img.png)` は単独行だとどのブロック規則にもマッチせず
[`parseMarkdownBlocks`](../../app/src/main/java/com/example/newproject/domain/markdown/MarkdownBlocks.kt) の
段落へ落ちる。`blocksToMarkdown` は段落を原文のまま返すので、
**alt は既にAI入力へ届いている。しかもパス文字列という無意味な文字列まで一緒に予算を食っている。**

効果の向きが逆だったので、`MarkdownBlock.Image` を足すときの注意点は
「alt を拾う」ではなく**「alt を落とさない」**になる（→ §5）。

### 訂正2: 現在の見え方は「何も出ない」ではない

[`inlineMarkdown`](../../app/src/main/java/com/example/newproject/ui/markdown/InlineMarkdown.kt) が
`[alt](path)` をリンクとして拾うため、**`!` が裸で残った上に alt がリンク色＋下線で出る**。
`![](path)`（alt が空）だと**「!」1文字だけ**が本文に落ちている。
`![[img.png]]` も同様に `!` ＋ `img.png` が下線付きで出る。

つまり現状は「未対応で無視されている」のではなく、**リンクとして誤解釈されている**。
実装後の見た目の変化はこの誤解釈の解消も含む。

### 訂正3: 難所は描画ではなくパス解決

資料は「SAFでの画像パス解決・キャッシュ・メモリ」と書いており方向は正しいが、
**規模の重心がパス解決にあることが明示されていなかった**。Compose で `Image` を出す部分は易しい。
§2〜§4 がこの設計書の大半を占めるのはそのためである。

## 2. 判断1 — 索引1本で解く（ディレクトリ walk は採らない）

Vault に現れる画像記法は3種類ある。

| 記法 | Obsidianでの位置づけ | 解決に要るもの |
|---|---|---|
| `![[Pasted image 2026....png]]` | **既定**（貼り付け・ドラッグはこの形になる） | ファイル名だけ → **Vault横断の索引** |
| `![alt](attachments/img.png)` | 手書き・他ツール由来 | パス解決 |
| `![alt](https://...)` | 外部 | **ネットワーク権限が無いので構造的に不可能** |

**`![[...]]` を外すと機能がほとんど役に立たない。** Obsidian の既定は
「Use [[Wikilinks]]」＋「Shortest path when possible」＋添付先はVaultルートで、
画像を貼り付けたときに生成されるのはこの形である。
そして**この形はファイル名しか持たないので、ディレクトリを1段ずつ辿る方式では原理的に解けない。**

検討した2案:

| 案 | 解けるもの | 却下理由 |
|---|---|---|
| ディレクトリ walk（ルートから1段ずつ `query`） | `![](path)` のみ | **既定の記法が解けない。** 機能として成立しない |
| **Vault横断の画像索引** | **両方** | **採用** |
| 両方（まずwalk、外れたら索引） | 両方 | 索引を持つ時点で `![](path)` も同じ索引で解ける。**walk は機構が1つ増えるだけ** |

**索引を持つと `![](path)` 側も同じ索引の相対パス照合で解けるので、機構は1つで済む。**
「まずパスで辿り、駄目なら索引」という二段構えは、速い経路を足しているように見えて
**索引が必ず要る以上は純粋な追加コスト**にしかならない。

走査の骨格は既にある — [`traverseMarkdownPaths`](../../app/src/main/java/com/example/newproject/data/VaultPathTraversal.kt) が
**全フォルダを歩いて `.md` 以外を捨てている**だけなので、受理条件を引数へ出して一般化すれば
画像も同じ走査で拾える。既存呼び出しは `::isMarkdownFile` を渡すだけで等価になる
（**等価であることをテストで固定してから**一般化する。この関数は孤児掃除が依存している）。

## 3. 判断2 — 照合は2段。ノート相対パスは v1 に入れない

**照合順は「正規化した完全パス一致 → ファイル名一致」の2段**とする。

ノート相対（`./img.png` を、そのノートのフォルダ基準で解く）は入れない。理由は2つある。

1. **既定設定では相対パスが生成されない。** Obsidian の「New link format」の既定は
   「Shortest path when possible」で、相対パス形式は opt-in である。
2. **表示中ノートの相対パスがUIに存在しない。**
   [`NoteState.Success`](../../app/src/main/java/com/example/newproject/model/state/NoteState.kt) は
   `title` / `content` / `targetUri` しか持たない。しかも `openNote`（さがす・関連経由）では
   相対パスが**表示時点で未確定**で、表示後に `bindReadingTracePath` が非同期に確定させ、
   その値は**読書痕跡のセッションにしか渡らない**。
   ここへ通すと「画像だけ遅れて解決し直す」挙動を表示経路へ持ち込むことになる。

**そして入れなくても大半は救われる。** `attachments/img.png` のようにパス付きで書かれていても、
完全一致が外れればファイル名 `img.png` へ落ちて索引が拾う。**索引を持つ以上この段は無料である。**

正規化の仕様（照合前に適用する）:

| 入力 | 扱い |
|---|---|
| `%20` などのパーセントエンコード | デコードする |
| `./` | 除去する |
| `../` | 1段上へ畳む。ルートを超えたぶんは捨てる |
| 先頭 `/` | Vaultルート基準として除去する |
| `\` 区切り | `/` へ寄せる |
| 大文字小文字 | **完全一致は区別し、ファイル名一致は区別しない**（SAFプロバイダによって挙動が違うため、拾える側を広く取る） |
| `\|400` / `\|400x300` | **区切って捨てる**（サイズヒントは v1 では使わない） |

**サイズヒントの `\|` は「割る」だけでなく「どちら側を取るか」に注意が要る。**
リンク `[[note\|別名]]` は表示名が後ろなので `last()` だが、
埋め込み `[[file\|400]]` は**ファイル名が前**なので `first()` になる。
[`inlineMarkdown`](../../app/src/main/java/com/example/newproject/ui/markdown/InlineMarkdown.kt) の
既存コードは `last()` なので、**そのまま流用すると必ず外れる**。

**wiki埋め込みは画像拡張子を持つものだけを画像として扱う。**
`![[note]]`（拡張子なし）は他ノートの埋め込みという別機能なので、画像として解決しにいってはいけない。

## 4. 判断3 — 同名が複数あるときは解決しない

`a/img.png` と `b/img.png` が両方ある Vault で `![[img.png]]` を解くとき、
BFSで最初に見つかったほうを黙って出すのは**誤った画像を確信を持って表示する**ことになる。

**曖昧なら表示せず、「同名の画像が複数あります」と候補数を出す。**

これは L24（判定の根拠が壊れているなら、ユーザー確認を挟んでも訂正されない）と同じ向きの判断である。
根拠が一意に定まらないときに、**それらしい答えを1つ選んで見せるのが一番悪い** —
誤りが誤りとして見えないので、報告もされない。

**「見つからない」も2種類に分ける（段階2の実装で追加）。**
索引が不完全なとき（走査で読めなかったフォルダがある）に「Vaultにありません」と言い切ると、
**§7 が索引をキャッシュしない理由と同じ誤り**を表示側で犯すことになる。
解決結果は `NotFound`（索引は完全で、そのうえで無い）と
`Unverifiable`（不完全なので断定できない）を型で分ける。
**完全性を見るのは見つからなかったときだけ**でよい — 見つかったなら索引が不完全でも答えは正しい。

**再検討の契機は症状**（「同名の画像が実際にあって、しかもどちらを出すべきか自明なケース」が出たとき）。
そのときは Obsidian 自身の解決規則（最短パス優先）へ寄せる余地がある。
ただし**ノート相対を入れない限り「同じフォルダを優先」は書けない**（§3）ので、
この2つは一緒に再検討することになる。

## 5. 判断4 — AI入力は現状維持。レンダラは分離しない

`MarkdownBlock.Image` を足すと、`blocksToMarkdown` がそれをどう書き戻すかで
**往復不変条件（`parse → blocksToMarkdown → parse` で型が同値に戻る）と
AI入力からのパス除去が両立しなくなる**。

| 案 | 往復 | AI入力 | 評価 |
|---|---|---|---|
| **`![alt](path)` を忠実に復元** | ○ | 現状維持（パスは残る） | **採用** |
| alt だけを返す | **×**（再パースで段落になる） | パスが消える | 不変条件を壊す |
| レンダラを2本に分ける | ○ | パスが消える | 下記の理由で採らない |

**分離して得られるものを先に数えた。**

- 予算内のノート: [`buildNoteExcerpt`](../../app/src/main/java/com/example/newproject/domain/NoteExcerptBuilder.kt) は
  `content.length <= budget` なら**原文を無加工で返す**ので、分離しても**何も変わらない**
- 予算超過のノート: 今日も**既にパスが残っている**（段落として原文どおり往復するため）。
  分離して初めて減る

つまり利得は「予算超過のノートで画像1つあたり数十文字」に限られる。
そして [ai_input_excerpt](ai_input_excerpt.md) §14 は、**予算を600→800へ増やしても品質は体感で動かなかった**と
記録している。**自分たちで測って「効かない」と結論した軸に、レンダラ2本と全経路のテストを払うのは筋が悪い。**

したがって忠実復元を採り、**AI入力のパスは無回帰**とする。

> **ただし段落の切れ方は変わる（段階1の実装で判明・2026-08-02）。**
> 空行を挟まず本文の直後へ画像を置く書き方（実際のノートで普通に現れる）は、
> 従来は1つの段落へ吸収されていた。画像として描くには切る必要があるので、
> **画像行を段落の区切りに加えた。** その結果 AI入力では
> `説明 ![[zu.png]]` が `説明\n\n![[zu.png]]` になる。
> 差は空白1文字が空行になるだけだが、**「無回帰」と言えるのはパスの扱いについてであって、
> 出力が1バイトも変わらないという意味ではない**ので、ここに明記しておく。
短いノートと長いノートで扱いが違う非対称は、
[`buildNoteExcerpt`](../../app/src/main/java/com/example/newproject/domain/NoteExcerptBuilder.kt) の
KDocが既に「超過した入力だけを圧縮する仕様」として引き受けているものと同じで、新しく持ち込むものではない。

> **再検討の契機は症状。** 「画像だらけのノートで要約が明らかに崩れる」が出たら、そのとき分離する。

## 6. 判断5 — プレースホルダの高さ確保は必須要件（読書痕跡が汚染される）

**これが本機能で最も見落としやすい欠陥である。** 見た目の話ではなく、**永続データの話**になる。

[`visibleFractionOfBlock`](../../app/src/main/java/com/example/newproject/ui/ReadingProgressGeometry.kt) は

```kotlin
if (itemSize <= 0) return 1f   // 高さが測れていないブロックは全可視扱い
```

としている。これは**到達率を不当に下げないための意図的な既定値**で、
高さ0のブロックが常態でない前提に立っている。画像はこの前提を破る。

連鎖は3段:

1. 読み込み待ちの画像ブロックの高さが0だと、**そのブロックは「全部読んだ」と報告される**
2. 高さ0なので画面に一度に入るブロック数が増え、**`deepestBlockIndex` が実際より先へ進む**
3. [`ReadingTraceController.onReadingProgress`](../../app/src/main/java/com/example/newproject/controller/ReadingTraceController.kt) は
   **「スクロールを戻しても最深到達点は下げない」**ので、
   **画像が読み込まれた瞬間の水増しがそのセッションに固着し、サイドカーへ永続化される**

**したがって「高さを確保したほうが跳ねなくて良い」ではなく、「確保しないと痕跡が壊れる」。**

規則は2つ:

- 寸法取得パス（`inJustDecodeBounds`）で得た縦横比からプレースホルダ領域を確保する
- **寸法取得に失敗した場合も、固定の最低高さを必ず置く。高さ0のブロックを作らない**

これは「重い処理を別スレッドへ移すときは、移した先の結果が来るまで元の同期経路が代わりに走らないかを見る」
（[architecture](architecture.md) 2026-07-31 の3）と同じ型の見落としである。
今回は**同期経路ではなく、既定値のほうが代わりに走っていた。**

## 7. 索引の鮮度 — 世代・TTL・miss再走査の歯止め

索引は Vault 単位の状態なので、**ノート単位の契約2箇所には登録しない**
（`cancelNoteScopedJobs()` にも `withNoteScopedReset()` にも載せない）。
`ReadingTraceCleanupController` と同じ扱いで、無効化の契機は Vault 切替だけである。

**世代の配線は既存と同じ。** [`NoteSessionCoordinator.vaultGeneration`](../../app/src/main/java/com/example/newproject/controller/NoteSessionCoordinator.kt) は
`var ... private set` で**外から読めるので**、Annotation / Search / Cleanup と同じく `() -> Long` を渡すだけでよい。
新しい配線機構は要らない。

**Vault切替だけでは足りない。** Obsidian 側で画像を足しても、切替まで出ないのは誤り。
`collectAllNotesCached` の TTL 60秒に倣って索引にも寿命を持たせる。

**miss時の再走査には歯止めが要る。** 「解決に失敗したら索引を作り直す」を無条件に入れると、
**リンク切れの画像が1つあるだけで再コンポーズのたびに全走査が走る。**
規則は「**miss かつ索引がTTLより古いときだけ、1回**」とする。

**不完全な索引もキャッシュする（2026-08-02・段階3の実装で初版から変更）。**

初版は「不完全な索引はキャッシュしない」だった。N-1 段階0（SCAN-1）と同じ型の失敗
—「一度読み損ねただけで、その画像は無いという判断が固定される」— を避けるためである。

**しかし段階2で `Unverifiable` を型として分けた時点で、この規則は不要になった。**
キャッシュを禁じていたのは「無い」と断定させないためであり、
**その保証はいま型が持っている**（不完全な索引で外れた要求は `NotFound` にならない）。

禁じたままにすると別の害が出る。読めないフォルダが1つあるだけで索引が毎回捨てられ、
**画像1枚ごとにVault全走査が走る**（1つのノートは画像を何枚も持つ）。
`_ReadingTraces` の索引が「次回読み直し」で済んでいたのは、
**あちらの再取得がノートを開くたび1回だから**で、画像はその前提を満たさない。

> **同じ型の失敗を避ける規則でも、避け方が2つあるなら安いほうを採る。**
> ここでは「キャッシュしない」（実行時コスト）と「型で分ける」（設計コスト）が
> 同じ性質を守っており、後者を先に払ったので前者が要らなくなった。

## 8. 復号とキャッシュ

**復号は `BitmapFactory` の二段（`inJustDecodeBounds` → `inSampleSize`）。**
minSdk 26 のため `ImageDecoder`（API 28+）は使えない。
12MP の写真を素で復号すると 48MB になるので、この段を省くと確実に OOM する。

**SAF のストリームは2回開く。** `reset()` できる前提には立てない。

**上限は4つを別々に持つ。** ファイルサイズ1つでは画像爆弾を防げない
（小さな圧縮ファイルが巨大な寸法を宣言しうる）。

| 上限 | 目的 |
|---|---|
| 入力バイト数 | 読み込み自体の暴走を止める |
| 縦・横の寸法 | 寸法取得の時点で弾く |
| 復号後のピクセル数 | `inSampleSize` を決めたうえで、なお大きいものを弾く |
| LRU の総バイト数 | 積み上がりを止める |

**LRU は件数ではなくバイト（`allocationByteCount` 相当）で管理する。**
1件の重さが2桁違うので、件数では上限の意味がない。
**表示中の `Bitmap` を eviction 時に `recycle()` しない** — 描画中に呼ぶとクラッシュする。
参照を落とすだけにして GC に任せる。

**single-flight が要る。** 同じ画像が同じ画面に複数回現れる、通常表示と全画面で同じノートを開く、
といった場合に同じ索引走査・同じ復号が重複する。
**Compose のコンポジション破棄だけでは、実行中のブロッキング復号が直ちに止まる保証はない。**

## 9. 結果型と失敗の見せ方

**ローダの戻り値を `ImageBitmap?` にしない。** null だけでは
「未解決／外部URL／SVG／巨大／復号失敗／曖昧」を区別できず、
理由を出すという要件（下記）と型が矛盾する。`Success` / `Failure(reason)` の結果型を持つ。

**失敗は必ず見える形にする。** 枠＋アイコン＋**ファイル名と理由の文字**を出す。

**色だけで伝えない（WCAG 1.4.1）。** [ui_design_principles](ui_design_principles.md) §1 の表は
1.4.3（文字）と 1.4.11（記号・輪郭）を持つが **1.4.1「色の使用」を持っていない**ので、
本機能の着手時にこの行を足す（N-10 が同じ指摘を受けている）。

**帯ではなく面。** [ui_design_principles](ui_design_principles.md) §3 の失敗型は
「小さい部品に濃い装飾を足した」もの。プレースホルダは本文幅の面なので `note_age_paper` 側に属するが、
**地色（＝ノートの放置期間）の上に載る**ことを忘れない。

**alt が空のときの読み上げを決める。** alt を `contentDescription` に入れるのが基本だが、
空のときは「装飾として読み飛ばす（null）」か「ファイル名を読む」かで挙動が変わる。
本アプリはビューアなので**ファイル名を読む**（ノートに置かれた画像は装飾ではなく内容である）。

| 項目 | v1 |
|---|---|
| `![alt](path)`（単独行） | **対応** |
| `![[image.png]]`（単独行・画像拡張子のみ） | **対応** |
| PNG / JPEG / WebP（静止） / BMP | **対応** |
| GIF / WebP のアニメーション | 非対応（先頭フレームのみ） |
| SVG | **非対応**（`BitmapFactory` が扱えない。対応するなら依存追加＝別判断） |
| 外部URL（`http(s)://`） | **非対応**（ネットワーク権限を持たない）。理由を出す |
| EXIF の回転 | **非対応。カメラ写真が横倒しになりうる**（§12） |
| インライン画像（段落の途中） | 非対応。alt をテキストとして残す |
| `![[note]]`（拡張子なしの埋め込み） | **画像として扱わない**（別機能） |
| 1行に画像が2つ／画像の後ろに文が続く行 | **画像として扱わない**（段落のまま＝従来どおり）。§11 の但し書き |
| alt に `[` `]` を含む画像 | **画像として扱わない**（同上） |
| サイズヒント `\|400` | 区切って捨てる（表示サイズには使わない） |
| 除外フォルダ | `.obsidian` / `_ReadingTraces` / `_AI補記` は索引に入れない |
| 表示 | 本文幅にフィット。高さは原寸比（上限なし） |

**インライン画像を外すのは、Compose の `InlineTextContent` が非同期読込と相性が悪く、
`SelectionContainer` 内での挙動に別途検証が要るため。** 実際のノートでは画像は単独行に置かれる。

| 1 | `MarkdownBlock.Image` の解析（単独行のみ・wiki埋め込みは画像拡張子に限定）＋ `blocksToMarkdown` の忠実復元と往復テスト | JVM。**実機確認不要**（見た目は据え置き） |

| 6 | 実機確認 | 下記 |

段階1〜3 だけでも既存の見た目は壊れない。**段階1で止めても損はしないが、利得も無い**
（AI入力は §5 のとおりパスは無回帰）。**利得が出るのは段階5から**である。

> **判定は「迷ったら段落のまま」に倒す（段階1の実装で確定）。**
> 正規表現の最長一致をそのまま使うと、`![図](zu.png) と説明(補足)` の対象が
> `zu.png) と説明(補足` になり、`![[a.png]] ![[b.png]]` の対象が `a.png]] ![[b.png` になる。
> **どちらも往復テストは通ってしまう**（原文どおり復元されるため）ので、
> テストの緑だけでは気づけない。対象から `[` `]` `)` を除外して、
> 曖昧な行は段落へ落とす。**段落は変更前の扱いなので、外した場合の挙動は現状維持**になり、
> 誤った対象を解決しにいくより安全である。

## 12. やらないこと・残るもの

- **EXIF の回転は v1 で非対応。** 解くには `androidx.exifinterface` の追加が要る
  （`ImageDecoder` は API 28+ で使えない）。「依存追加ゼロ」を優先し、
  **カメラ写真が横倒しになりうることを引き受ける**。スクリーンショットの貼り付けは EXIF を持たないので、
  実害はカメラ撮影の画像に限られる。**着手の契機は症状**（横倒しが実際に気になったとき）。
- **表示サイズの指定（`\|400`）は使わない。** 本文幅フィットで足りる。
- **埋め込み `![[note]]`・数式は別問題**（→ `_wip/feature_ideas.md` N-3 の但し書き）。
- **同名の曖昧解決は §4 の再検討条件つきで保留。** ノート相対（§3）と一緒に見る。
