# 設計思想 — ReadingTrace（読書痕跡）

**対象領域:** Rediscover連動・読書位置の記録・ノートメタデータ（サイドカー）
**初版:** 2026-07-21（TimeCapsule として起案）
**改稿:** 2026-07-25（**設計を全面的に置換**。TimeCapsule を棄却し ReadingTrace として実装）
**状態:** v1 実装済み・JVMテスト通過・**実機確認待ち**（レビュー指摘4件＝到達率・Lifecycle・Vault分離・検索フォールバックは PR #35 で解消済み。完了判定は実端末での一巡）

> **改稿の経緯**: このファイルは元々「読み終わりに未来の自分へ問いを1つ残す」タイムカプセル機能の設計書だった（全論点確定・実装前）。実装着手時の検討で**前提が棄却された**ため、同じ狙い（Rediscoverに意図の糸を通す）を別の手段で果たす設計に置き換えた。棄却の理由は §2 に残す。旧設計の内容はこのファイルのgit履歴から辿れる。

## 1. 解決したかった問題

このアプリの心臓は **Rediscover（ランダムに過去ノートを引く）**（`NoteViewModel.loadRandomNote` が `notes.random()` でVault全体から1本引く）。しかし再発見は「たまたま出てくる」だけで、そこに**意図の糸**がない。

ランダム再発見に「前回の自分」を重ねて、**偶然を"再会"へ変える**のがこの機能の狙い。この狙いは旧設計から一貫している。

## 2. なぜ TimeCapsule を棄却したか

旧設計は「Reflectタブに『タイムカプセルを残す』を置き、ユーザーが問いを1つ書く」ものだった。これに対し「**ボタンではなく、ユーザーが意識することがない補助機能にしたい**」という要求が出た。

検討すると、この機能の成立には3条件があり、**同時に3つは満たせない**ことが分かった。

| | (a) 中身が**自分**由来 | (b) **どのノートにも**残る | (c) **無意識**に作られる |
|---|---|---|---|
| 旧設計（明示ボタンで問いを書く） | ✓ | ✓ | ✗ |
| AIが問いを自動生成 | ✗ | ✓ | ✓ |
| **本設計（痕跡を自動記録＋AIは要約のみ）** | ✓ | ✓ | ✓ |

- **(a) を失うと**「前回の自分からの申し送り」が「AIからの宿題」になり、情緒の核が変わる
- **(b) を失うと**再会の確率が落ちる。Rediscoverは全Vaultからのランダムなので、痕跡が一部のノートにしかなければループが回らない

**トレードオフを解いたのは「AIの役割を"問いの創作"から"痕跡の要約"に落とす」という一手**だった。中身はユーザー自身の読み方なので (a) が保たれ、普通に読むだけで痕跡が出るので (b) も満たし、完全自動なので (c) も満たす。

### 副作用として失ったもの

ReadingTrace は行動データなので「**何を考えていたか**」は回収できない。「前回は40%で止まった」は「前回は〇〇が引っかかった」ではない。

当初これをセクションチャットの質問で代替しようとしたが、**実装を確認したところチャットに自由入力は存在せず**（`SectionChatSheet.kt` に `TextField` がない）、Userメッセージが生まれる経路はAIが生成した `suggestions` をタップしたときだけだった（`SectionChatController.kt:84,163`）。つまり「自分の言葉の問い」ではなく「AI候補からの選択」であり、思考の回収としては弱い。よって**今回は見送り、別課題として記録**した（→ §2 末尾の「取りうる道」）。

## 3. ループの形

```
普通に読む ──> 読んだ位置が裏で溜まる（AI呼び出しゼロ）
                       │
                  （時間が経つ）
                       │
Rediscover で引かれる ──> 生の痕跡を即表示 ──> 裏でAIが俯瞰要約を追記
```

## 4. 設計原則: シンプル最優先

**本質はノートを見ること。痕跡は「あれば嬉しい」再会体験**であって、永久保存の記録装置ではない。旧設計から引き継ぐ背骨。

- 痕跡が稀に1個失われても、ユーザーのノート（.md）は無傷であり、本質（ノート閲覧）は損なわれない
- したがって **.bak復旧・アトミック性の作り込み・世代アーカイブは不採用**
- 残す安全策は「**壊れたものを見せない・ノートに波及させない**」の一点（checksum破損検知＋孤立化）のみ

## 5. 判断

### 判断1: 痕跡は「読んだ位置」のみ。訪問ごとに累積する

記録するのは**最深到達セクションと到達率**。1回分では「前回ここで止まった」しか言えないが、累積すれば「3回開いていずれも前半で止まっている」という**俯瞰**が出せる（「1個ずつ追う必要はなく俯瞰的に知りたい」という要求に対応）。

**滞在時間は採らない**。アプリを開いたまま離席すると値が汚れ、テストもしづらい。最深到達点を累積すれば「毎回同じ所で止まる」は表現できるので、シンプル原則により見送る。

### 判断2: 記録は全経路・表示は Rediscover 限定

**ここが非対称**なので実装時に混同しやすい。

| | 条件 |
|---|---|
| **記録**（JSONに訪問を足す） | Rediscover・さがす・関連の**どの経路でも**（10秒以上読んだら） |
| **表示**（再会カード） | **Rediscover 経路のみ** |

検索・関連・直接オープンで出さないのは「目的を持って開いた時には出さず、偶然引いた時だけ"再会"を濃くする」という意図的な割り切り。

**由来フラグ（`isFromRediscover`）は持たない。** 旧設計では `NoteState.Success` にフラグを追加する予定だったが、実装すると冗長だった。カードを設定する経路は `revealTrace` だけ、それを呼ぶのは `loadRandomNote` だけ、そして `resetNoteScopedStates()` がノートを開くたびカードを消す。つまり**「カードが存在する」こと自体が「Rediscover由来」を意味**しており、フラグは二つ目の真実になるだけだった。回転（ViewModel生存＝カード維持）・プロセス復元（`uiState` 初期化＝カードなし）も、フラグなしで正しく振る舞う。

### 判断3: 記録の条件は「能動読書10秒以上」だけ

一瞬引いてすぐ次のノートへ送った分を訪問に数えると痕跡が濁るうえ、ノートを表示するたびSAF書込が走る（Vaultがクラウドなら同期トラフィックにもなる）。

当初は「スクロールが発生した」も条件に入れる設計だったが、**1画面に収まる短いノートが永久に記録されない**ため落とした。時間条件だけで上記2つの目的は達せられる。

> **2026-07-25 レビュー指摘 → 2026-07-25 修正済み（時間モデルの確立）:** 当初は「ノートを開いた時刻から現在まで」を読書時間としていたため、①10秒以上読んで背面へ回ると `recorded` が永久に立ち、復帰後に読み進めた位置が保存されない ②10秒未満で背面へ回ると背面にいた時間が閾値へ混ざる、の2つが起きていた。
>
> **背面にいた時間を除いた「能動読書時間」だけを積算する**モデルへ変更した。`pause()`（`onStop`）で計測を止め、`resume()`（`onStart`）で再開する。
>
> 背面化の時点で訪問を**書き出す**のは、背面のままプロセスが終了しても読書を失わないため。ただし**セッションは残す**ので、復帰して読み進めたら同じ訪問を差し替える。ここを「新しいセッションを開始する」にしなかったのは、**ホームボタンを押すたび「これまで◯回開いています」が増えてしまう**ため。訪問回数は「ノートを開いた回数」であって「背面往復の回数」ではない。
>
> 差し替えは「保存済みトレースの末尾が自分の書いた訪問と構造的に一致する場合」に限定する。別端末が同期で追記していれば末尾が一致しないので、その場合は素直に追記へフォールバックする（他端末の記録を消さない）。前回の書き込みから変化が無ければ書き込み自体を行わない。

### 判断4: 到達率は「最終可視ブロック＋そのブロックの可視割合」で測る

`LazyListState.firstVisibleItemIndex` を使うと、画面に収まる分だけ末尾に届かず**到達率が100%にならない**。`layoutInfo.visibleItemsInfo.last().index` を見ることで「読み切った」を表現できる。

セクション名の解決はUI側（`sectionModel`）で行い、Controllerには解決済みの文字列を渡す。本文の再パースを避け、Controllerが `ui` パッケージへ依存しないようにするため。

> **2026-07-25 レビュー指摘 → 2026-07-25 修正済み:** ブロック番号だけで測ると、長大な段落・コード・表が1ブロックとして描画されるノートで、冒頭しか見えていなくても `1/1 = 100%` になっていた。機能の中心データが誤るため、**最終可視ブロックの可視割合を分子へ足す**方式へ変更した。
>
> ```
> 到達率 = (最深ブロックindex + そのブロックの可視割合) / 総ブロック数
> ```
>
> - **可視割合**は `LazyListItemInfo.offset/size` と `viewportEndOffset - afterContentPadding` から求める。座標（Int）だけを受ける純関数 `visibleFractionOfBlock`（`ui/ReadingProgressGeometry.kt`）へ切り出し、Composeを起動せずJVMテストできるようにした（[architecture](architecture.md) 判断3に沿う）
> - **切り捨て**にしているのは、100%を「最終ブロックの末端が画面へ入った」場合だけに限定するため。丸めると末尾が残っていても100%になり、カードが「最後まで読んでいます」と誤って断定する
> - **報告は5%刻みへ量子化**してから `distinctUntilChanged` に掛ける。可視割合はスクロール中ずっと変わり続けるため、そのまま流すと毎フレーム報告になる
> - 最深判定は「index が深い、または同じ index でより深くまで見えた」。長大ブロック内を読み進めた分も最深に反映され、巻き戻しでは下がらない
>
> 高さが測れていないブロック（`size <= 0`）は全可視扱いにする。到達率を不当に下げないことを優先した（痕跡の性質上、多少緩い方が害が小さい）。

### 判断5: AI要約は再会時・裏で・失敗しても黙って劣化

`AICoreClient.generate()` は companion の Mutex で全機能直列＋60秒タイムアウトなので、要約を待ってからカードを出すと**数十秒何も出ない**。

- **まず生の痕跡でカードを出す**（AIなし・即時）
- 訪問が増えていれば**裏で1回だけ**生成し、届いたら**生の痕跡の下に足す**（置き換えない。置き換えると失敗時に文面が消える）
- `AiAvailability.NeedsDownload` では**自動DLしない**。失敗・タイムアウトも**エラー表示を出さず**生の痕跡のままにする（ユーザーが意識しない機能なので黙って劣化する）
- 生成した要約は `aiSummary` としてサイドカーへ保存し、**訪問が増えていなければ再生成しない**（2回目以降の再会は即表示）

要約の記録件数（`aiSummaryVisitCount`）には「**要約が説明している訪問数**」を入れる。生成中に `flush` が訪問を足すことがあるため、最新の件数を入れると次回の再会で作り直されなくなる。

**AIには新しい内容を作らせない。** プロンプトで「データに無いことを書かせない・助言や問いを足させない」を明示する。これが「前回の自分」という体験を保つ肝。

### 判断6: 保存はvault内の可視フォルダにサイドカー（本文は編集しない）

- 痕跡はノート本文(.md)に埋め込まず**別ファイル**に持つ（frontmatter埋め込み＝本文編集のtruncate窓リスクを避ける）
- 置き場は **vault内の `_ReadingTraces/`**。**アンダースコア始まりの可視フォルダ**にするのは、SAFでは `.` 始まりの隠しフォルダの作成がプロバイダ（Google Drive・OneDrive・一部ローカルファイラー）によって失敗したり不可視化の挙動が異なるため。可搬性を優先し `_AI補記` と同じ流儀にする
- **1痕跡=1ファイル**（`_ReadingTraces/<sha256Hex(相対パス)>.json`）。相対パスは `/` を含み長さ・使用可能文字もプロバイダ依存なので、そのままファイル名にはできない
- `_ReadingTraces/` は**ノート収集の対象から3箇所で除外**する（`collectNotes` / `collectNotesInScope` / `listTopLevelFolders`）。最後の1つを塞がないと、さがすタブのフォルダ選択に「中身ゼロのフォルダ」として現れる

### 判断7: 可搬キーは vault相対パス。documentId は端末内の参考値

**SAF documentId は端末／権限グラントごとに異なる**ため、同期した別端末では同じファイルでも別IDになる＝**可搬キーにならない**。同期をまたいで生き残ることを狙う以上、キーは可搬でなければならない。

- **可搬キー＝vault相対パス**（例 `ideas/habit.md`）を主キーにする
- **documentId** は端末内の参考情報として保持するが、**checksum の対象には含めない**。再バインドで書き換わる値を整合性の対象にすると、キャッシュ更新のたびにユーザー内容の checksum を触ることになる

**3段引き当て（documentId→パス→タイトル再マッチ）は実装しなかった。** 旧設計はこれを要求していたが、サイドカーのファイル名が相対パスのハッシュなので**パス引き当ては既にO(1)**で、documentIdを先に見る意味がない。逆に「見つからない」は**未読ノートで常時起きる**ので、ミス時にフォルダを全走査すると Rediscover が毎回重くなる。→ **move/rename で痕跡を失うことを受け入れた**（.mdは無傷なので設計原則の範囲内）。

### 判断8: サイドカー書き込みはベストエフォート（原子性なし）

**SAF OutputStream への `"wt"`（write-truncate）直接上書き**で更新する（[reflect_distill](reflect_distill.md) の `SafDistillDocumentGateway` と同方式）。

**これは原子更新ではない**。`"wt"` は truncate 後に書き直すため、書込中にプロセスが死ぬと部分破損したまま残り、復旧元は存在しない。SAF の `renameDocument()` はプロバイダ非互換で古典的なatomic-renameが成立せず、`DistillRecoveryStore` の原子パターンは内部ストレージ（`java.io.File`）専用でSAFへ移植できない。設計原則どおり**堅牢化はここまで**とし、破損は checksum で検知して孤立扱いにする。端末間の同時編集は **last-writer-wins**。

## 6. 仕様詳細（v1）

### データモデル（JSON）

```
ReadingTrace(
  schemaVersion: Int,
  vaultRelativePath: String,      // 可搬・主キー
  noteTitle: String,              // 表示＋最新へ寄せ直す
  documentId: String?,            // 端末内の参考値（checksum対象外）
  visits: List<Visit>,            // 累積・最大30件（古いものから捨てる）
  aiSummary: String?,             // 俯瞰要約のキャッシュ
  aiSummaryVisitCount: Int?,      // 要約が説明している訪問数。増えていたら作り直す
  checksum: String
)
Visit(atEpochMillis: Long, deepestSectionTitle: String?, progressPercent: Int)
```

`deepestSectionTitle` は見出しの無いノート・最初の見出しより前で離れた場合に null（その時は到達率だけを見せる）。**記録時点の見出し名をそのまま保持する歴史的記録**なので、後で本文が編集されてその見出しが消えても再解決はしない（「前回は『X』の節で止まっていた」はXが改名されても真）。

`checksum` はモデルには持たせず、保存形式の関心事として `ReadingTraceJson` が encode 時に付与し decode 時に検証する。

### JSON採用理由と canonical payload

JSONを選ぶのは、閲覧履歴（`NoteHistoryStore`）で既にAndroid標準の `org.json` を使っており追加ライブラリが要らないうえ、「データはポータブルで読めるべき」というObsidianの思想に合う（ユーザー自身がテキストエディタで確認・修復できる）ため。`toString(2)` で整形して書く。

**checksum の入力に JSON文字列は使えない。** `org.json` はキー順を保証しないため、同じ内容から別のハッシュが出る。そこで**キー順を固定し、各文字列にUTF-8バイト長を前置して連結した正規形**を別に組む。長さ前置なので、区切り文字をノートタイトルやセクション名に混ぜて別の内容へ偽装できない（`DistillRecoveryStore` の `readSizedString` と同じ考え方）。null と空文字は1バイトの存在フラグで区別する。

### 上限（バイト基準で検証。日本語はUTF-8で1文字≒3バイト）

| 項目 | 上限 |
|---|---|
| 訪問 | 30件（超過時は古いものから捨てる） |
| AI要約 | 2,048バイト（超過分は保存前にバイト境界で丸める） |
| 相対パス | 1,024バイト |
| ノートタイトル／セクション名 | 512バイト |
| ファイル読み込み | 64KB |

**厳格検証（読込時）**: 必須項目・型・上限・未知の `schemaVersion` を検証。checksum不一致・パース失敗・空ファイル・不正UTF-8は**破損＝孤立扱い**（カードを出さず、ノートには触れない）。

### フロー

1. **記録**: ノートを開くとセッション開始 → スクロールで最深到達点を更新（メモリのみ） → ノートを離れる／アプリが背面へ回る時に、10秒以上読んでいれば訪問1件を追記
2. **再会**: Rediscoverで引かれる → 相対パスで照合 → 生の痕跡をカードへ即表示 → 訪問2件以上なら裏でAI俯瞰要約
3. **カード操作**: 「読んだ」で畳む（**永続化しないので次回Rediscoverでは再表示**）

### 実装上の要点

- **vault相対パスの生成**: `NoteRepository` のBFS走査は documentId しか持っていなかったため、キューを「documentId＋そこまでの相対パス」の組に拡張した。ただし `DocumentsContract.buildDocumentUriUsingTree` がAndroid staticでBFSごとテストできないので、**走査とパス連結を純関数 `traverseMarkdownPaths` へ切り出した**（[architecture](architecture.md) 判断3に沿う）。循環対策の visited 集合を入れているのは、パスを持つようになると循環でパスとメモリが無限に伸びるため（パスを持たない従来の走査では無害だった）
- **セッションは表示前に作る**: `uiState` 更新とセッション開始の間でメインスレッドを譲ると、痕跡レポータの初回emitを取りこぼして**訪問がまるごと記録されない**。よってパス解決にI/Oを挟まない
- **パスは後から結び付けられる**: さがす・関連から開いた場合、相対パスは即座に分からない（`SearchController` は `collectNotesInScope` を使い、パス解決が参照する `cachedNotes` を温めない）。パス未確定でもセッションだけ作って進捗を溜め、表示後に `bindPath(sessionId, path)` で埋める。**`sessionId` を要求するのは**、パス未確定のノートを続けて開いた時に前のノートの遅れた解決結果が次のセッションへ吸い込まれ、別ノートのパスで訪問を記録するのを防ぐため
- **フォルダ一覧はセッションキャッシュ**: 毎回 `querySafChildren` すると、ノートを開く／離れるたびフォルダ全走査になり、痕跡ファイルが増えるほど重くなる（特にGoogle Drive等の遠いプロバイダ）。**セッション中1回だけ**一覧を読んで key→Uri の索引に保持し、作成したファイルは即索引へ足す。読み書きは `@Synchronized` で直列化する（訪問の追記はControllerのMutexで直列化されるが、再会時の照合はその外側で走る）。ただし外部同期で後から増えたファイルを再走査する契機がなく、プロセス再起動まで認識しない課題がある（未解決）
- **ファイル名は前方一致で引く**: SAF の `createDocument` は渡した displayName をプロバイダが改名しうる（重複時の `foo (1).json`、MIMEに合わせた `foo.json.json` 等）。先頭64桁のキーだけは残るのでそこを索引キーにする。この置き場には自分が作ったファイルしか入らないため取り違えない
- **read-modify-write は Mutex で直列化**: 訪問の追記と要約の書き戻しが交差すると、読み取りが古いまま上書きして訪問を取りこぼす
- **Vault分離は保存要求自身が運ぶ（2026-07-25 修正）**: 保存は非同期に起動されるため、書き込みが走る時点では利用者が別のVaultへ切り替えているかもしれない。保存先を書込時点の `vaultUri` から解決すると、旧ノートの相対パス・タイトルのまま保存先だけが新Vaultになる。当初は `saveVault()` の `discard()` でセッションを捨てて防ぐ設計だったが、**起動済みのコルーチンには効かない**ことがレビューで判明した。
  **ノートを開いた時点のVault識別子をセッションへ写し取り、保存・照合要求に添えて運ぶ**方式へ変更した。Gateway が書き込み直前に現在のVaultと照合し、不一致なら書かずに捨てる。**照合と保存先の解決で `vaultUri()` を読むのは1回だけ**にしてある（読み直すと、その間の切替で別Vaultを掴む。`@Synchronized` はGateway自身の状態しか守らず、ViewModel側の `vaultUri` は保護しない → [bugfix_reports](../bugfix_reports.md) #4）。識別子を `Uri` ではなく `String` にしているのは、この境界より上（`ReadingTraceStore`）を Android 非依存に保ちJVMテスト可能にするため。`discard()` は「切替後に新しい保存要求が生まれること」を止める役割として残している

## 7. 容量とファイル数

`MAX_VISITS = 30` で保持履歴を打ち切るため**1ファイルは有界**。ファイル数は「10秒以上読んだノートの数」でVaultのノート数が天井。

| 状態 | 1ファイル |
|---|---|
| 訪問1件・要約なし | 約390バイト |
| 訪問3件・要約あり | 約700バイト |
| 訪問30件（上限）・要約あり | 約3.3KB（これ以上増えない） |

2,000ノートのVaultで現実的には**約1.4MB**。容量は問題にならない。先に問題化するのは**ファイル数に比例する処理**なので、上記のセッションキャッシュで対処している。

現在は保持件数 `visits.size` をそのまま「これまで開いた回数」と表示するため、31回目以降も30回と表示される。容量上限と累計回数を両立するには、累計値を別フィールドへ分離する必要がある（未解決）。なお `visits.size` は AI俯瞰要約の再生成判定（`needsAiSummary`）にも使われるため、30件で頭打ちになると**要約が二度と更新されなくなる**副作用がある。

## 8. 意図的に切ったもの（v1）

| 項目 | 理由 |
|---|---|
| move/rename 後の再バインド | ミスが未読ノートで常時起きるため、フォルダ全走査のコストが恒常的にかかる。痕跡を失っても .md は無傷 |

| 「意図して問いを残す」機能 | §2 参照。v1 では見送り、別課題として記録 |

## 10. JVMユニットテストで確認済みの範囲

- ネストしたノートの vault相対パス生成（BFSで親パス連結）／除外フォルダを潜らない／循環しても終わる
- JSONの必須項目・型・上限（**UTF-8マルチバイト境界**）・未知 `schemaVersion`
- checksum不一致・空ファイル・不正UTF-8・途中書き込み → 孤立化しノートに触れない
- documentId を書き換えても checksum は変わらない（端末内の参考値だから）
- 長さ前置により区切り文字の混入で別内容へ偽装できない
- 10秒未満は記録しない／1画面に収まる短いノートも記録される／スクロールを戻しても最深到達点が保たれる
- 長大な1ブロックを冒頭だけ見ても100%にならない／最終ブロックが一部しか見えていなければ100%に届かない／同じブロック内で読み進めた分が最深に反映される
- 可視割合の算出（完全可視・一部可視・画面外・高さ未確定・viewport超過）と5%刻みの量子化
- 背面化で訪問を書き出しても復帰後の読み進めは同じ訪問を差し替える（回数が増えない）／背面にいた時間は10秒判定に入らない／能動読書時間は背面をまたいで積算される／変化が無ければ書き込まない／別端末が追記した訪問は上書きしない
- 保存要求は常に「ノートを開いた時点のVault」へ向かう（要求後に切り替えても変わらない）／切替後に開いたノートは新Vaultへ向かう／Vault未選択なら追跡しない
- Store が vaultKey を Gateway へ素通しする／不一致キーの読み書きは拒まれる
- 訪問が累積し30件で古いものから捨てられる／二重flushで重複しない
- パス未確定で開いて後から結び付けても、結び付け前に届いた進捗ごと記録される／**前のセッション宛の遅れたbindは無視される**
- 痕跡なし・破損ではカードを出さない／生の痕跡を即出す／AI失敗でも生の痕跡が残る
- `NeedsDownload` で自動DLしない／訪問が増えていなければ再生成しない／要約をサイドカーへ保存する
- ノート切替で後着の要約を破棄する／畳んだカードは後から届いた要約で開き直さない
- カードは「前回まで」を見せる（今回の読書は離脱時に足されるので混ざらない）
- `_ReadingTraces/` がノート収集候補・フォルダ選択へ混入しないこと

上記はAndroid依存を外した純粋ロジックとFake Persistenceを中心とする。Composeの実レイアウト、Activity lifecycle、SAFプロバイダ、外部同期を組み合わせたinstrumentation/E2Eテストではない。

## 11. 実装レビューで判明した事項（2026-07-25）

| 優先度 | 事項 | 現行テストで見つからなかった理由 | 状態 |
|---|---|---|---|
| 高 | 長大な1ブロックを冒頭だけ見ても100%になる | テストはControllerへ整数のblockIndexを直接渡し、Compose上のブロック内可視量を扱わない | ✅ 解消（判断4） |
| 高 | `onStop`で確定後、復帰時にSessionを再開始しない。10秒未満なら背面時間も閾値へ混ざる | Activity lifecycleを通さずController単体を呼んでいる | ✅ 解消（判断3） |
| 高 | Vault切替前に起動済みの保存が新Vaultへ到着し得る | Fake Persistenceは動的なVault保存先と遅延I/Oを再現しない | ✅ 解消（§6 実装上の要点） |
| 中 | 外部同期で追加されたサイドカーを索引キャッシュが認識しない | SAFプロバイダの外部変更を再現していない | 未解決（→ 2-4） |
| 中 | 31回目以降も「これまで30回」と表示する | 30件で古い履歴が落ちることだけを検証し、累計表示の意味を検証していない | 未解決（→ 2-5） |

高優先度3件はJVMテスト付きで解消した。ただし**SAF実装そのものの照合（Vault不一致で書かない）と、Activity lifecycle を通した pause/resume の実挙動はJVMテストの範囲外**なので、完成判定には実端末確認を要する。残る中優先度2件は「同期索引が外部追加を認識しない」（§8）と「保持上限と累計回数の混同」（上記）。
