## 1. 解決したかった問題

このアプリの心臓は **Rediscover（ランダムに過去ノートを引く）**（`NoteViewModel.loadRandomNote` が `notes.random()` でVault全体から1本引く）。しかし再発見は「たまたま出てくる」だけで、そこに**意図の糸**がない。

ランダム再発見に「前回の自分」を重ねて、**偶然を"再会"へ変える**のがこの機能の狙い。この狙いは旧設計から一貫している。

## 2. なぜ TimeCapsule を棄却したか

旧設計は「Reflectタブに『タイムカプセルを残す』を置き、ユーザーが問いを1つ書く」ものだった。これに対し「**ボタンではなく、ユーザーが意識することがない補助機能にしたい**」という要求が出た。

検討すると、この機能の成立には3条件があり、**同時に3つは満たせない**ことが分かった。

| | (a) 中身が**自分**由来 | (b) **どのノートにも**残る | (c) **無意識**に作られる |
|---|---|---|---|
| 旧設計（明示ボタンで問いを書く） | ✓ | ✓ | ✗ |
| AIが問いを自動生成 | ✗ | ✓ | ✓ |
| **本設計（痕跡を自動記録＋AIは要約のみ）** | ✓ | ✓ | ✓ |

- **(a) を失うと**「前回の自分からの申し送り」が「AIからの宿題」になり、情緒の核が変わる
- **(b) を失うと**再会の確率が落ちる。Rediscoverは全Vaultからのランダムなので、痕跡が一部のノートにしかなければループが回らない

**トレードオフを解いたのは「AIの役割を"問いの創作"から"痕跡の要約"に落とす」という一手**だった。中身はユーザー自身の読み方なので (a) が保たれ、普通に読むだけで痕跡が出るので (b) も満たし、完全自動なので (c) も満たす。

### 副作用として失ったもの

ReadingTrace は行動データなので「**何を考えていたか**」は回収できない。「前回は40%で止まった」は「前回は〇〇が引っかかった」ではない。

当初これをセクションチャットの質問で代替しようとしたが、**実装を確認したところチャットに自由入力は存在せず**（`SectionChatSheet.kt` に `TextField` がない）、Userメッセージが生まれる経路はAIが生成した `suggestions` をタップしたときだけだった（`SectionChatController.kt:84,163`）。つまり「自分の言葉の問い」ではなく「AI候補からの選択」であり、思考の回収としては弱い。よって**今回は見送り、別課題として記録**した（→ §2 末尾の「取りうる道」）。

## 3. ループの形

```
普通に読む ──> 読んだ位置が裏で溜まる（AI呼び出しゼロ）
                       │
                  （時間が経つ）
                       │
Rediscover で引かれる ──> 生の痕跡を即表示 ──> 裏でAIが俯瞰要約を追記
```

## 4. 設計原則: シンプル最優先

**本質はノートを見ること。痕跡は「あれば嬉しい」再会体験**であって、永久保存の記録装置ではない。旧設計から引き継ぐ背骨。

- 痕跡が稀に1個失われても、ユーザーのノート（.md）は無傷であり、本質（ノート閲覧）は損なわれない
- したがって **.bak復旧・アトミック性の作り込み・世代アーカイブは不採用**
- 残す安全策は「**壊れたものを見せない・ノートに波及させない**」の一点（checksum破損検知＋孤立化）のみ

## 5. 判断

### 判断1: 痕跡は「読んだ位置」のみ。訪問ごとに累積する

記録するのは**最深到達セクションと到達率**。1回分では「前回ここで止まった」しか言えないが、累積すれば「3回開いていずれも前半で止まっている」という**俯瞰**が出せる（「1個ずつ追う必要はなく俯瞰的に知りたい」という要求に対応）。

**滞在時間は採らない**。アプリを開いたまま離席すると値が汚れ、テストもしづらい。最深到達点を累積すれば「毎回同じ所で止まる」は表現できるので、シンプル原則により見送る。

### 判断2: 記録は全経路・表示は Rediscover 限定

**ここが非対称**なので実装時に混同しやすい。

| | 条件 |
|---|---|
| **記録**（JSONに訪問を足す） | Rediscover・さがす・関連の**どの経路でも**（10秒以上読んだら） |
| **表示**（再会カード） | **Rediscover 経路のみ** |

検索・関連・直接オープンで出さないのは「目的を持って開いた時には出さず、偶然引いた時だけ"再会"を濃くする」という意図的な割り切り。

**由来フラグ（`isFromRediscover`）は持たない。** 旧設計では `NoteState.Success` にフラグを追加する予定だったが、実装すると冗長だった。カードを設定する経路は `revealTrace` だけ、それを呼ぶのは `loadRandomNote` だけ、そして `NoteUiStateStore` の `withNoteScopedReset()` がノートを開くたびカードを消す。つまり**「カードが存在する」こと自体が「Rediscover由来」を意味**しており、フラグは二つ目の真実になるだけだった。回転（ViewModel生存＝カード維持）・プロセス復元（`uiState` 初期化＝カードなし）も、フラグなしで正しく振る舞う。

### 判断3: 記録の条件は「能動読書10秒以上」だけ

一瞬引いてすぐ次のノートへ送った分を訪問に数えると痕跡が濁るうえ、ノートを表示するたびSAF書込が走る（Vaultがクラウドなら同期トラフィックにもなる）。

当初は「スクロールが発生した」も条件に入れる設計だったが、**1画面に収まる短いノートが永久に記録されない**ため落とした。時間条件だけで上記2つの目的は達せられる。

> **2026-07-25 レビュー指摘 → 2026-07-25 修正済み（時間モデルの確立）:** 当初は「ノートを開いた時刻から現在まで」を読書時間としていたため、①10秒以上読んで背面へ回ると `recorded` が永久に立ち、復帰後に読み進めた位置が保存されない ②10秒未満で背面へ回ると背面にいた時間が閾値へ混ざる、の2つが起きていた。
>
> **背面にいた時間を除いた「能動読書時間」だけを積算する**モデルへ変更した。`pause()`（`onStop`）で計測を止め、`resume()`（`onStart`）で再開する。
>
> 背面化の時点で訪問を**書き出す**のは、背面のままプロセスが終了しても読書を失わないため。ただし**セッションは残す**ので、復帰して読み進めたら同じ訪問を差し替える。ここを「新しいセッションを開始する」にしなかったのは、**ホームボタンを押すたび「これまで◯回開いています」が増えてしまう**ため。訪問回数は「ノートを開いた回数」であって「背面往復の回数」ではない。
>
> 差し替えは「保存済みトレースの末尾が自分の書いた訪問と構造的に一致する場合」に限定する。別端末が同期で追記していれば末尾が一致しないので、その場合は素直に追記へフォールバックする（他端末の記録を消さない）。前回の書き込みから変化が無ければ書き込み自体を行わない。

### 判断4: 到達率は「最終可視ブロック＋そのブロックの可視割合」で測る

`LazyListState.firstVisibleItemIndex` を使うと、画面に収まる分だけ末尾に届かず**到達率が100%にならない**。`layoutInfo.visibleItemsInfo.last().index` を見ることで「読み切った」を表現できる。

セクション名の解決はUI側（`sectionModel`）で行い、Controllerには解決済みの文字列を渡す。本文の再パースを避け、Controllerが `ui` パッケージへ依存しないようにするため。

> **2026-07-25 レビュー指摘 → 2026-07-25 修正済み:** ブロック番号だけで測ると、長大な段落・コード・表が1ブロックとして描画されるノートで、冒頭しか見えていなくても `1/1 = 100%` になっていた。機能の中心データが誤るため、**最終可視ブロックの可視割合を分子へ足す**方式へ変更した。
>
> ```
> 到達率 = (最深ブロックindex + そのブロックの可視割合) / 総ブロック数
> ```
>
> - **可視割合**は `LazyListItemInfo.offset/size` と `viewportEndOffset - afterContentPadding` から求める。座標（Int）だけを受ける純関数 `visibleFractionOfBlock`（`ui/ReadingProgressGeometry.kt`）へ切り出し、Composeを起動せずJVMテストできるようにした（[architecture](architecture.md) 判断3に沿う）
> - **切り捨て**にしているのは、100%を「最終ブロックの末端が画面へ入った」場合だけに限定するため。丸めると末尾が残っていても100%になり、カードが「最後まで読んでいます」と誤って断定する
> - **報告は5%刻みへ量子化**してから `distinctUntilChanged` に掛ける。可視割合はスクロール中ずっと変わり続けるため、そのまま流すと毎フレーム報告になる
> - 最深判定は「index が深い、または同じ index でより深くまで見えた」。長大ブロック内を読み進めた分も最深に反映され、巻き戻しでは下がらない
>
> 高さが測れていないブロック（`size <= 0`）は全可視扱いにする。到達率を不当に下げないことを優先した（痕跡の性質上、多少緩い方が害が小さい）。

### 判断5: AI要約は再会時・裏で・失敗しても黙って劣化

`AICoreClient.generate()` は companion の Mutex で全機能直列＋60秒タイムアウトなので、要約を待ってからカードを出すと**数十秒何も出ない**。

- **まず生の痕跡でカードを出す**（AIなし・即時）
- 訪問が増えていれば**裏で1回だけ**生成し、届いたら**生の痕跡の下に足す**（置き換えない。置き換えると失敗時に文面が消える）
- `AiAvailability.NeedsDownload` では**自動DLしない**。失敗・タイムアウトも**エラー表示を出さず**生の痕跡のままにする（ユーザーが意識しない機能なので黙って劣化する）
- 生成した要約は `aiSummary` としてサイドカーへ保存し、**訪問が増えていなければ再生成しない**（2回目以降の再会は即表示）

要約の記録件数（`aiSummaryVisitCount`）には「**要約が説明している訪問数**」を入れる。生成中に `flush` が訪問を足すことがあるため、最新の件数を入れると次回の再会で作り直されなくなる。

**AIには新しい内容を作らせない。** プロンプトで「データに無いことを書かせない・助言や問いを足させない」を明示する。これが「前回の自分」という体験を保つ肝。

### 判断6: 保存はvault内の可視フォルダにサイドカー（本文は編集しない）

- 痕跡はノート本文(.md)に埋め込まず**別ファイル**に持つ（frontmatter埋め込み＝本文編集のtruncate窓リスクを避ける）
- 置き場は **vault内の `_ReadingTraces/`**。**アンダースコア始まりの可視フォルダ**にするのは、SAFでは `.` 始まりの隠しフォルダの作成がプロバイダ（Google Drive・OneDrive・一部ローカルファイラー）によって失敗したり不可視化の挙動が異なるため。可搬性を優先し `_AI補記` と同じ流儀にする
- **1痕跡=1ファイル**（`_ReadingTraces/<sha256Hex(相対パス)>.json`）。相対パスは `/` を含み長さ・使用可能文字もプロバイダ依存なので、そのままファイル名にはできない
- `_ReadingTraces/` は**ノート収集の対象から3箇所で除外**する（`collectNotes` / `collectNotesInScope` / `listTopLevelFolders`）。最後の1つを塞がないと、さがすタブのフォルダ選択に「中身ゼロのフォルダ」として現れる

### 判断7: 可搬キーは vault相対パス。documentId は端末内の参考値

**SAF documentId は端末／権限グラントごとに異なる**ため、同期した別端末では同じファイルでも別IDになる＝**可搬キーにならない**。同期をまたいで生き残ることを狙う以上、キーは可搬でなければならない。

- **可搬キー＝vault相対パス**（例 `ideas/habit.md`）を主キーにする
- **documentId** は端末内の参考情報として保持するが、**checksum の対象には含めない**。再バインドで書き換わる値を整合性の対象にすると、キャッシュ更新のたびにユーザー内容の checksum を触ることになる

**3段引き当て（documentId→パス→タイトル再マッチ）は実装しなかった。** 旧設計はこれを要求していたが、サイドカーのファイル名が相対パスのハッシュなので**パス引き当ては既にO(1)**で、documentIdを先に見る意味がない。逆に「見つからない」は**未読ノートで常時起きる**ので、ミス時にフォルダを全走査すると Rediscover が毎回重くなる。→ **move/rename で痕跡を失うことを受け入れた**（.mdは無傷なので設計原則の範囲内）。

### 判断8: サイドカー書き込みはベストエフォート（原子性なし）

**SAF OutputStream への `"wt"`（write-truncate）直接上書き**で更新する（[reflect_distill](reflect_distill.md) の `SafDistillDocumentGateway` と同方式）。

**これは原子更新ではない**。`"wt"` は truncate 後に書き直すため、書込中にプロセスが死ぬと部分破損したまま残り、復旧元は存在しない。SAF の `renameDocument()` はプロバイダ非互換で古典的なatomic-renameが成立せず、`DistillRecoveryStore` の原子パターンは内部ストレージ（`java.io.File`）専用でSAFへ移植できない。設計原則どおり**堅牢化はここまで**とし、破損は checksum で検知して孤立扱いにする。端末間の同時編集は **last-writer-wins**。

## 6. 仕様詳細（v1）

### データモデル（JSON）

```
ReadingTrace(
  schemaVersion: Int,
  vaultRelativePath: String,      // 可搬・主キー
  noteTitle: String,              // 表示＋最新へ寄せ直す
  documentId: String?,            // 端末内の参考値（checksum対象外）
  visits: List<Visit>,            // 保持は直近30件（古いものから捨てる）
  aiSummary: String?,             // 俯瞰要約のキャッシュ
  aiSummaryVisitCount: Int?,      // 要約が説明している延べ回数。増えていたら作り直す
  totalVisitCount: Int,           // 延べ回数（v2で追加）。表示・要約の鮮度判定はこちら
  checksum: String
)
Visit(atEpochMillis: Long, deepestSectionTitle: String?, progressPercent: Int)
```

`deepestSectionTitle` は見出しの無いノート・最初の見出しより前で離れた場合に null（その時は到達率だけを見せる）。**記録時点の見出し名をそのまま保持する歴史的記録**なので、後で本文が編集されてその見出しが消えても再解決はしない（「前回は『X』の節で止まっていた」はXが改名されても真）。

`checksum` はモデルには持たせず、保存形式の関心事として `ReadingTraceJson` が encode 時に付与し decode 時に検証する。

### JSON採用理由と canonical payload

JSONを選ぶのは、閲覧履歴（`NoteHistoryStore`）で既にAndroid標準の `org.json` を使っており追加ライブラリが要らないうえ、「データはポータブルで読めるべき」というObsidianの思想に合う（ユーザー自身がテキストエディタで確認・修復できる）ため。`toString(2)` で整形して書く。

**checksum の入力に JSON文字列は使えない。** `org.json` はキー順を保証しないため、同じ内容から別のハッシュが出る。そこで**キー順を固定し、各文字列にUTF-8バイト長を前置して連結した正規形**を別に組む。長さ前置なので、区切り文字をノートタイトルやセクション名に混ぜて別の内容へ偽装できない（`DistillRecoveryStore` の `readSizedString` と同じ考え方）。null と空文字は1バイトの存在フラグで区別する。

### 上限（バイト基準で検証。日本語はUTF-8で1文字≒3バイト）

| 項目 | 上限 |
|---|---|
| 訪問の保持 | 30件（超過時は古いものから捨てる。延べ回数は `totalVisitCount` が別に持つ） |
| AI要約 | 2,048バイト（超過分は保存前にバイト境界で丸める） |
| 相対パス | 1,024バイト |
| ノートタイトル／セクション名 | 512バイト |
| ファイル読み込み | 64KB |

**厳格検証（読込時）**: 必須項目・型・上限・未知の `schemaVersion` を検証。checksum不一致・パース失敗・空ファイル・不正UTF-8は**破損＝孤立扱い**（カードを出さず、ノートには触れない）。

### 判断9: 保持件数と延べ回数は別に持つ（schema v2・2026-07-26）

v1 は `visits.size` を「これまで開いた回数」として使っていた。保持は30件で打ち切るので、
**31回目以降は表示が「30回」で止まる**。それだけなら見た目の問題だが、
`needsAiSummary` の判定（`aiSummaryVisitCount != visits.size`）も同じ値を見ていたため、
**どれだけ読んでもAI俯瞰要約が二度と更新されず、30件時点の要約が「最新」として出続けていた。**

`totalVisitCount` を別フィールドとして積み上げ、表示・要約の鮮度判定・プロンプトの
`Times opened` をすべて累計基準へ切り替えた。`visits` は「どこで止まったかの傾向」を
見るための直近30件として維持する（AIへ渡すのもこちら）。

**落とし穴**: Kotlin の `copy()` は既定値を再評価しない。背面化→復帰→離脱で訪問を
差し替える経路は「末尾を落として `withVisit` で足し直す」ので、素直に `copy(visits = ...)`
と書くと**累計だけ二重に増える**（＝ホームボタンを押すたび回数が膨らむ）。この不変条件は
`withoutLastVisit()` に閉じ込めてある。保持件数は30で頭打ちになってこの誤りを隠すため、
回帰テストは累計そのものを見ている。

**v1 → v2 の移行**は decode 側で行う。**v1 の checksum は v1 の正規形（累計を含まない）で
計算されている**ので、先にその版で照合してから現行版へ寄せる。順序を逆にすると既存の痕跡が
全部「破損＝孤立」になる。v1 のファイルに `totalVisitCount` が書き足されていても読まない
（v1 の checksum はこの値を含まないため、読むと任意の回数を名乗れる入口になる）。
移行時の初期値は `visits.size`。30件で頭打ちだった分は取り戻せないが、そこから先は正しく積み上がる。

### 判断10: 保存はアプリ寿命のスコープで走らせる（2026-07-26）

判断8（ベストエフォート）は「壊れたら諦める」であって「書きにいく機会を失う」ことまでは
許していない。保存が `viewModelScope` に載っていたため、タスクスワイプや Activity finish では
`onStop()` → `pause()` の直後に `onCleared()` が走り、**IOへディスパッチされる前に
キャンセルされて確定済みの訪問が消えていた**。背面化だけなら成立していたので気付きにくい。

書き出し専用のアプリ寿命スコープ（`SupervisorJob` + `Main.immediate`）を注入する。
`ProcessLifecycleOwner` を使わないのは、`lifecycle-process` の依存追加に対して必要なのが
「`onCleared()` で死なないスコープ」1つだけだから。`Main.immediate` を土台にするのは、
セッション状態をメインスレッドのみで触る既存のスレッド規律を変えないため。

あわせて `ReadingTraceSaveResult` を受ける。消費済みの印（`dirty=false` / `recordedVisit`）は
保存の起動前に立てているので、書けなかったのに戻さないとそのセッションの訪問は恒久的に失われる。
巻き戻すのは**自分が書こうとした訪問がまだ最新のときだけ**（同時に飛んだ後発の訪問を潰さない）。

`persistSummary` は対象外にした。書けなくても `aiSummaryVisitCount` が更新されないだけで、
次回の再会で `needsAiSummary` が真になり自動的に作り直される（自己修復する）。

### フロー

1. **記録**: ノートを開くとセッション開始 → スクロールで最深到達点を更新（メモリのみ） → ノートを離れる／アプリが背面へ回る時に、10秒以上読んでいれば訪問1件を追記
2. **再会**: Rediscoverで引かれる → 相対パスで照合 → 生の痕跡をカードへ即表示 → 訪問2件以上なら裏でAI俯瞰要約
3. **カード操作**: 「読んだ」で畳む（**永続化しないので次回Rediscoverでは再表示**）

### 実装上の要点

- **vault相対パスの生成**: `NoteRepository` のBFS走査は documentId しか持っていなかったため、キューを「documentId＋そこまでの相対パス」の組に拡張した。ただし `DocumentsContract.buildDocumentUriUsingTree` がAndroid staticでBFSごとテストできないので、**走査とパス連結を純関数 `traverseMarkdownPaths` へ切り出した**（[architecture](architecture.md) 判断3に沿う）。循環対策の visited 集合を入れているのは、パスを持つようになると循環でパスとメモリが無限に伸びるため（パスを持たない従来の走査では無害だった）
- **セッションは表示前に作る**: `uiState` 更新とセッション開始の間でメインスレッドを譲ると、痕跡レポータの初回emitを取りこぼして**訪問がまるごと記録されない**。よってパス解決にI/Oを挟まない
- **パスは後から結び付けられる**: さがす・関連から開いた場合、相対パスは即座に分からない（`SearchController` は `collectNotesInScope` を使い、パス解決が参照する `cachedNotes` を温めない）。パス未確定でもセッションだけ作って進捗を溜め、表示後に `bindPath(sessionId, path)` で埋める。**`sessionId` を要求するのは**、パス未確定のノートを続けて開いた時に前のノートの遅れた解決結果が次のセッションへ吸い込まれ、別ノートのパスで訪問を記録するのを防ぐため
- **フォルダ一覧はセッションキャッシュ**: 毎回 `querySafChildren` すると、ノートを開く／離れるたびフォルダ全走査になり、痕跡ファイルが増えるほど重くなる（特にGoogle Drive等の遠いプロバイダ）。**セッション中1回だけ**一覧を読んで key→Uri の索引に保持し、作成したファイルは即索引へ足す。読み書きは `@Synchronized` で直列化する（訪問の追記はControllerのMutexで直列化されるが、再会時の照合はその外側で走る）。ただし外部同期で後から増えたファイルを再走査する契機がなく、プロセス再起動まで認識しない課題がある（未解決）
- **ファイル名は前方一致で引く**: SAF の `createDocument` は渡した displayName をプロバイダが改名しうる（重複時の `foo (1).json`、MIMEに合わせた `foo.json.json` 等）。先頭64桁のキーだけは残るのでそこを索引キーにする。この置き場には自分が作ったファイルしか入らないため取り違えない
- **read-modify-write は Mutex で直列化**: 訪問の追記と要約の書き戻しが交差すると、読み取りが古いまま上書きして訪問を取りこぼす
- **本文の読込には用途別の予算がある（2026-07-26 追加）**: 痕跡そのものとは別だが、同じ「入口で量を決める」話。`readNoteForDisplay`（1MB）／`readNoteSnippet`（8KB）／`readNoteSnapshot`（256KB）に分かれており、バイト数は呼び出し側が選べない。上限で切ると多バイト文字が割れるので、復号前に `dropIncompleteUtf8Tail()` で末尾の不完全なシーケンスを落とす
- **Vault分離は保存要求自身が運ぶ（2026-07-25 修正）**: 保存は非同期に起動されるため、書き込みが走る時点では利用者が別のVaultへ切り替えているかもしれない。保存先を書込時点の `vaultUri` から解決すると、旧ノートの相対パス・タイトルのまま保存先だけが新Vaultになる。当初は `saveVault()` の `discard()` でセッションを捨てて防ぐ設計だったが、**起動済みのコルーチンには効かない**ことがレビューで判明した。
  **ノートを開いた時点のVault識別子をセッションへ写し取り、保存・照合要求に添えて運ぶ**方式へ変更した。Gateway が書き込み直前に現在のVaultと照合し、不一致なら書かずに捨てる。**照合と保存先の解決で `vaultUri()` を読むのは1回だけ**にしてある（読み直すと、その間の切替で別Vaultを掴む。`@Synchronized` はGateway自身の状態しか守らず、ViewModel側の `vaultUri` は保護しない → [bugfix_reports](../bugfix_reports.md) #4）。識別子を `Uri` ではなく `String` にしているのは、この境界より上（`ReadingTraceStore`）を Android 非依存に保ちJVMテスト可能にするため。`discard()` は「切替後に新しい保存要求が生まれること」を止める役割として残している

## 7. 容量とファイル数

`MAX_VISITS = 30` で保持履歴を打ち切るため**1ファイルは有界**。ファイル数は「10秒以上読んだノートの数」でVaultのノート数が天井。

| 状態 | 1ファイル |
|---|---|
| 訪問1件・要約なし | 約390バイト |
| 訪問3件・要約あり | 約700バイト |
| 訪問30件（上限）・要約あり | 約3.3KB（これ以上増えない） |

2,000ノートのVaultで現実的には**約1.4MB**。容量は問題にならない。先に問題化するのは**ファイル数に比例する処理**なので、上記のセッションキャッシュで対処している。

現在は保持件数 `visits.size` をそのまま「これまで開いた回数」と表示するため、31回目以降も30回と表示される。容量上限と累計回数を両立するには、累計値を別フィールドへ分離する必要がある（未解決）。なお `visits.size` は AI俯瞰要約の再生成判定（`needsAiSummary`）にも使われるため、30件で頭打ちになると**要約が二度と更新されなくなる**副作用がある。

## 10. JVMユニットテストで確認済みの範囲

- ネストしたノートの vault相対パス生成（BFSで親パス連結）／除外フォルダを潜らない／循環しても終わる
- JSONの必須項目・型・上限（**UTF-8マルチバイト境界**）・未知 `schemaVersion`
- checksum不一致・空ファイル・不正UTF-8・途中書き込み → 孤立化しノートに触れない
- documentId を書き換えても checksum は変わらない（端末内の参考値だから）
- 長さ前置により区切り文字の混入で別内容へ偽装できない
- 10秒未満は記録しない／1画面に収まる短いノートも記録される／スクロールを戻しても最深到達点が保たれる
- 長大な1ブロックを冒頭だけ見ても100%にならない／最終ブロックが一部しか見えていなければ100%に届かない／同じブロック内で読み進めた分が最深に反映される
- 可視割合の算出（完全可視・一部可視・画面外・高さ未確定・viewport超過）と5%刻みの量子化
- 背面化で訪問を書き出しても復帰後の読み進めは同じ訪問を差し替える（回数が増えない）／背面にいた時間は10秒判定に入らない／能動読書時間は背面をまたいで積算される／変化が無ければ書き込まない／別端末が追記した訪問は上書きしない
- 保存要求は常に「ノートを開いた時点のVault」へ向かう（要求後に切り替えても変わらない）／切替後に開いたノートは新Vaultへ向かう／Vault未選択なら追跡しない
- Store が vaultKey を Gateway へ素通しする／不一致キーの読み書きは拒まれる
- 訪問が累積し30件で古いものから捨てられる／二重flushで重複しない
- パス未確定で開いて後から結び付けても、結び付け前に届いた進捗ごと記録される／**前のセッション宛の遅れたbindは無視される**
- 痕跡なし・破損ではカードを出さない／生の痕跡を即出す／AI失敗でも生の痕跡が残る
- `NeedsDownload` で自動DLしない／訪問が増えていなければ再生成しない／要約をサイドカーへ保存する
- ノート切替で後着の要約を破棄する／畳んだカードは後から届いた要約で開き直さない
- カードは「前回まで」を見せる（今回の読書は離脱時に足されるので混ざらない）
- `_ReadingTraces/` がノート収集候補・フォルダ選択へ混入しないこと
- **累計と保持件数の分離（2026-07-26）**: 保持上限を超えても累計は増える／31回目の再訪でAI要約が作り直される／背面化→復帰→離脱では累計が増えない／v1 の痕跡を累計付きで読める／v1 は読み込み時に現行版へ移行される／改変された v1 は破損扱いのまま／v1 に書き足された累計は無視される
- **保存の寿命と失敗（2026-07-26）**: UI側のスコープをキャンセルしても訪問は書き出される／保存に失敗したら次の契機で書き直される／先行した保存の失敗が後発の訪問を巻き戻さない
- **読込の予算（2026-07-26）**: 日本語・絵文字の途中で切っても化けた文字が残らない／文字境界ちょうどなら1バイトも落とさない／上限を超えたら打ち切る／上限ちょうどは切り詰め扱いにしない／上限に達したら残りを読まない

**これらは「対応する修正を1行外すとテストが落ちる」ことを個別に確認してある**（変異検証）。
A案で「ガードを外してもテストが通る」＝検証していないテストを書いた前例があるため、
新しいガードを入れたら必ずこの確認を通す（→ [architecture](architecture.md) の教訓）。

上記はAndroid依存を外した純粋ロジックとFake Persistenceを中心とする。Composeの実レイアウト、Activity lifecycle、SAFプロバイダ、外部同期を組み合わせたinstrumentation/E2Eテストではない。

## 11. 実装レビューで判明した事項（2026-07-25）

| 優先度 | 事項 | 現行テストで見つからなかった理由 | 状態 |
|---|---|---|---|
| 高 | 長大な1ブロックを冒頭だけ見ても100%になる | テストはControllerへ整数のblockIndexを直接渡し、Compose上のブロック内可視量を扱わない | ✅ 解消（判断4） |

| 高 | Vault切替前に起動済みの保存が新Vaultへ到着し得る | Fake Persistenceは動的なVault保存先と遅延I/Oを再現しない | ✅ 解消（§6 実装上の要点） |

## 12. 実機確認をクローズした理由（2026-07-31）

v1 の完了条件には「到達率・背面化復帰・Vault分離・検索フォールバックを**実端末で**確認する」を
残していたが、**確認せずにクローズした**。安全側に倒せなかったのではなく、**この4項目に限っては
実機確認の費用対効果が成立しない**と判断した。

**1. ロジックは既にJVMテストで覆えている。** §10 のとおり、4項目はいずれも対応するテストがある —
「長大な1ブロックを冒頭だけ見ても100%にならない」「背面化で訪問を書き出しても復帰後の読み進めは
同じ訪問を差し替える／背面にいた時間は10秒判定に入らない」「保存要求は常にノートを開いた時点の
Vaultへ向かう」。**実機でしか確かめられないのはロジックではなく境界だけ**で、実 `ContentResolver`
と実 Activity の `pause`/`resume` が Fake と同じ順序・同じ粒度で振る舞うか、という一点に絞られる。

**2. 再会カードは Rediscover 限定なので、意図して再現できない。** ここが決定的だった。
痕跡を記録したあと結果を目視するには、**同じノートを純粋ランダムで引き当てる**必要がある。
Vaultのノート数が N なら1回の試行で引ける確率は 1/N で、数百ノートのVaultでは実質不可能になる。
**「Rediscoverは純粋ランダム死守」という製品判断が、この経路の実機確認可能性を奪っている。**
確認のために引きを操作できるようにするのは、守るべき性質のほうを壊す。

**3. 壊れたときの検知は別経路で足りる。** 最も実害が大きいVault分離（他Vaultへの誤書き込み）は、
`_ReadingTraces` のファイル数を見れば結果として分かる。到達率や訪問回数のズレは、
使っていて再会カードの文面が実感と合わなければ気づく。**いずれも「使っていれば分かる」種類**で、
事前の網羅確認より事後の気づきのほうが安い。

**したがってこの4項目は、課題台帳から削除して通常運用へ戻す。** 実際に違和感が出たら、
そのとき具体的な症状つきで起票し直す — 症状があれば再現条件を作れるので、
「引き当たるまで待つ」問題も消える。

**この判断を他へ広げない。** ここでクローズできたのは、①ロジックがJVMで覆えていて
②確認が構造的に不可能で ③壊れても事後に気づける、の3つが揃ったから。
1つでも欠けるなら実機確認は省略できない。

## 13. 孤児掃除は手動・自動を問わず採らない（2026-08-01）

§8 で v1 が見送った「孤児ファイルの掃除」を再検討した。当初の論点は
**「手動の一括削除にするか、最終確認日時による自動削除にするか」**だったが、
検討の結果**どちらも採らない**と決めた。手動か自動かは問題の本体ではなかった。

### 判断11: 孤児判定そのものが信用できない

**決定的だったのはコード側の事実である。** `querySafChildren` は
`contentResolver.query(...)?.use { ... }` の形なので、**`query()` が `null` を返すと
ブロックごと飛ばして空リストを返す**（`SafDocuments.kt`）。つまり
**「読めなかった」と「本当に空」がこの1行で区別不能に潰れている。**

ここは `collectNotes` のBFSと痕跡フォルダ索引の**両方が通る共通経路**なので、
あるサブフォルダの列挙が失敗すると、その配下のノートは
**走査が成功したまま静かに0件になる**。孤児判定は「ノートが走査結果に現れないこと」を
唯一の根拠にするため、この時点で根拠が壊れている。

**「全体件数が0や激減なら弾く」という健全性チェックでは塞げない。**
弾けるのは走査が丸ごとこけた場合だけで、**小さなサブツリーが1つ欠けても全体件数はほとんど動かない**。
検討の過程で一度この案を採りかけたが、上記の実装を読んで破棄した。

| 走査の失敗 | 件数ベースの健全性チェックで弾けるか |
|---|---|
| 丸ごとこける（0件・前回比で激減） | 弾ける |
| **一部のサブツリーだけ列挙に失敗する** | **弾けない**（全体件数がほぼ動かない） |

**手動ボタンにしても解決しない。** 候補一覧を作るのはアプリであり、その一覧は上記の
壊れた不在シグナルから生成される。ユーザーが提示された候補をそのまま全選択すれば、
自動削除と同じ事故が同じ確率で起きる。**確認を挟むことは、根拠の誤りを訂正しない。**

### 判断12: 「最終確認日時」は削除基準として価値と逆を向く

仮に不在シグナルが信用できたとしても、時間ベースの判定には別の欠陥がある。

- **通常閲覧時だけ更新する**と、存在するが長く開いていないノートが削除対象になる
- **全走査時に更新する**と、判断11 の同期誤判定がそのまま入り込む
- そして根本的に、**長く再訪していないノートほど ReadingTrace は再会時に価値を持つ**

3つ目が本質である。この機能は Rediscover と対で成立しており（§1）、狙いは
**忘れていたノートに「前回の自分」を重ねること**にある。「最後に見てから長い」は
削除の根拠ではなく、**この機能が最も効く条件そのもの**である。閾値を何日にしても向きは直らない。

> **検討中に一度誤った補正を挟んだので残す。** 「全走査時に更新すると走査コストが戻る」
> という理由付けを検討したが、これは**誤り**だった。全走査は Rediscover が
> Vault全体からランダムに引くために既に回っている（`NoteViewModel` が TTL 60秒で
> `collectNotes` を呼ぶ）ので、相乗りに新しい走査コストは無い。
> **走査コストは反対理由にならず、同期誤判定と価値の逆相関だけで結論は十分に立つ。**

### 判断13: 判定が信用できない前提のもとでは「全リセット」しか置けない

**この判断は §14 の段階0 で条件付きで上書きされた。下の追記を先に読むこと。**

判定が信用できない（判断11）以上、導線を置くとしても**現在のVaultの読書痕跡をすべて削除する**
一手に限る。これは誤判定ではなく**ユーザーによる明示的な履歴破棄**なので、
判定の信頼性に一切依存しない。§4 の「痕跡は永久保存の記録装置ではない」とも整合する。

**ただしこれは SYNC-1 が挙げた問題を解かない。** 元の懸念は
「年単位の運用でファイル数が単調増加する」であり、**押されるか分からないボタンは
GCの代わりにならない**。全リセットは逃げ道であって通常運用の掃除機構ではない。

> **2026-08-01 追記 — 着手対象は「孤児のみ削除」に戻した（オーナー判断）。**
> **全リセットと孤児削除は代替物ではない。** 仕事が違う。
>
> | | 孤児のみ削除 | 全リセット |
> |---|---|---|
> | SYNC-1 の問題（ファイル単調増加）を解くか | **解く** | **解かない** |
> | 生きた痕跡 | 残る | **全部消える** |
> | 判定の信頼性への依存 | する | しない |
> | ユーザーの動機 | 掃除したい | やり直したい／機能ごと捨てたい |
>
> 判断13 は「**判定が信用できないなら**全リセットしか置けない」であって、
> 「全リセットのほうが良い」ではなかった。§14 の段階0（走査を正直にする）で
> **判定の前提そのものが変わる**ため、孤児削除が選択肢に戻る。
> 全リセットは併設しても構わないが、既定は作らない（今回の判断の対象外）。
>
> **元の課題台帳（`922a3dd` 以前）の対応候補①も「孤児の一括削除」だった。**
> 検討途中で全リセットへ寄せた経緯があるので、ここに書き残す。

### 判断14: 性能はファイル数ではなく索引設計で解く

容量は問題にならない（§7・2,000ノートで約1.4MB）。**先に問題化するのは
索引作成がファイル数に比例すること**である。これが実測で問題になったときの解は
**削除ではなく分割**にする。

痕跡のファイル名は `sha256Hex(相対パス)` なので、**先頭1桁で16フォルダへ分割**すれば、
1件の照合で列挙する件数を 1/16 に落とせる。引く側はキーから所属フォルダを計算できるので
探索は不要。**生きた痕跡を1つも消さずに性能だけ守れる**のが、孤児削除に対する決定的な優位点。

現状はセッション中1回だけ列挙して索引を保持する形で既に緩和されている（§6 実装上の要点）ため、
**実測で問題化するまで着手しない**。分割は既存ファイルの移行を伴うので、
実測なしに入れると移行リスクだけを先払いすることになる。

### 再検討の条件

**閲覧時刻ベースの判定（判断12）は打ち切る。** 件数や実測を理由に再提案しない。

**存在ベースの判定（判断11）は、前提が1つ変われば再検討してよい** —
`querySafChildren` が**列挙の失敗を空と区別して返す**ようになったとき。
戻り値を nullable にするか例外を投げるかして、BFS が「この走査は不完全だった」を
呼び出し側へ伝えられれば、不在シグナルは初めて根拠になりうる。

> **2026-08-01 追記:** この節は当初「手動に固定し、前提が変わるまで動かさない」で閉じていたが、
> **同日中に第三の道が出た** — 不在を証拠として蓄積し、実績が出てから自動化へ昇格する段階案。
> `querySafChildren` を直さなくても不在シグナルを扱えるため、上記の再検討条件は
> **唯一の道ではなくなった**。§14 が持つ。**手動は恒久仕様ではなく検証フェーズ**である。

## 14. 手動から自動へ昇格する段階案（2026-08-01）

§13 は「採らない」で閉じたが、**その直後に前提を変える案が出た**。
§13 を撤回はしない — 判断11〜12 の指摘（不在シグナルが壊れている・閲覧時刻は価値と逆を向く）は
そのまま有効で、この案は**それらを回避する形で組まれている**。

### 判断15: 「存在」は事実、「不在」は証拠の1票

§13 判断11 が壊れていると断じたのは、**1回の不在観測を削除の根拠に使うこと**だった。
観測を1票として積み上げ、複数回・複数セッションにまたがって初めて候補にすれば、
一過性の列挙失敗は票を集められない。**根拠の性質を「証明」から「証拠」へ落とすのが要点。**

**閾値は時間ではなく観測回数で持つ。** ノート一覧のTTL 60秒は
**定期実行ではなく再走査の上限**であり（`NoteViewModel.collectAllNotesCached` は
期限内なら早期returnするだけ）、**経過時間は走査が何回走ったかを何も意味しない**。
アプリを半年使わなければ走査はゼロ回で、時間閾値だと全件が候補になる。

**票を入れるのは実際に `collectNotes` が走ったときだけ。** キャッシュ再利用は観測ではない。

### 判断16: 端末内の証拠索引が持つもの

`lastConfirmedAt` だけでは足りない（上記のとおり時間が観測回数の代理にならないため）。

| 項目 | 用途 |
|---|---|
| `lastConfirmedAt` | 最後に**存在が確認できた**走査 |
| `firstMissingAt` / `lastMissingAt` | 欠落が続いている期間の幅 |
| `missingObservationCount` | **票数**（閾値はこれで持つ） |
| 対象パスとトップレベルフォルダ | フォルダ単位の一括欠落を検出するため |
| 「この条件なら自動削除していた」日時 | シャドーモードの記録。**実際には消さない** |

**索引は `vaultKey` で区切る。** ここを落とすと事故る — Vault A を開いている間の走査が
**Vault B の全ノートを「不在」として記録する**。`onVaultChanged` は `cachedNotes` を捨てるので
切替のたびに実走査が走り、**数回往復しただけで B の痕跡が全滅する**。
しかも欠落は全件同時なので「候補が急増したら止める」遮断器には掛かるが、
それは事故を止めているのではなく**正常な運用を止めているだけ**で、機能が永久に前へ進まない。
Vault分離を要求自身に運ばせる既存の方針（§6 実装上の要点）と同じ扱いにする。

### 判断17: 遮断器の粒度を故障の粒度に合わせる

**この案が §13 判断11 に答えられている理由がここにある。**
`querySafChildren` の null 畳み込みは**フォルダ単位で起きる** — 1ディレクトリの列挙が失敗すると
その配下がまるごと消える。したがって遮断器も**フォルダ単位**で置く。

| 遮断器 | 止める故障 |
|---|---|
| 同じフォルダから複数件が同時に欠けたら保留 | **列挙失敗（null 畳み込み）そのもの** |
| 候補が急増したら停止 | Vault未同期・権限失効・ルート差し替え |
| 異なる日・セッションの走査で複数回欠けたことを要求 | 一過性の失敗 |
| 一度に最大1件 | 上記をすり抜けた場合の被害限定 |

**回数を重ねるだけでは持続的な失敗を排除できない**（同じフォルダが毎回失敗すれば票は貯まる）。
効いているのは**粒度の一致**のほうで、票数はその補強である。

**遮断器には穴が1つ残る。** ノートが1件しかないフォルダの列挙が失敗すると、
欠落は1件なのでフォルダ一括判定に掛からず、「一度に最大1件」も通過する。
§4 の「痕跡が稀に1個失われても本質は損なわれない」の範囲内なので受け入れるが、
**遮断器は完全ではない**ことを前提に置く。

### 判断18: 段階は「観測 → 手動 → 限定自動」

昇格は実績で門を開ける。

1. **シャドーモード** — 何も削除せず、候補と**その後の再出現**を記録する。
   再出現は「その条件で自動削除していたら誤削除だった」という**反証そのもの**になる
2. **手動確認** — 「自動なら削除していた候補」を一覧にし、削除は明示操作にする
3. **限定的な自動化** — 十分な実績の後、遮断器（判断17）を通った**孤立した少数だけ**自動削除する

**§13 が挙げた「誰も押さないボタンはGCにならない」は、段階3で解ける** —
通常の単発孤児だけが自動化の対象になる。フォルダ単位の消失やVault事故は
段階3でも自動化しない、という切り分けがそのまま残る。

### 実装順

当初は次の順で置いた。

```
SYNC-2の索引更新 → 不在証拠の端末内索引 → シャドー表示 → 手動削除 → 自動化判定
```

**2026-08-01 に2箇所を訂正した。実装順は下記が正となる。**

```
走査を正直にする → 列挙API → 孤児判定（純関数） → 一覧（削除ボタンなし） → 手動削除 →〔自動化〕
```

**訂正1: SYNC-2 は前提ではない。** 「削除の安全性」からは導けず（索引が古いと起きるのは
取りこぼしであって誤削除ではない）、次に「列挙の完全性」を根拠に挙げたが**これも誤りだった** —
古くなるのは*セッション中のランタイム索引*で、掃除は `_ReadingTraces/` を
**その場で新規列挙すれば足りる**。SYNC-2 は再会照合の課題で、掃除とは独立している。

**訂正2: 証拠索引（判断16）は手動削除の前提ではない。** 手動削除の前に本当に要るのは
**走査を正直にすること**である。`querySafChildren` が失敗を空と区別できれば、候補は
**「完全に走査できた上で見つからなかったもの」**に絞れる。判断11 が「根拠が壊れている」と
言ったその根拠を、直接修理する道がここにある。

**つまり判断11 への答えは2つあり、両方要るわけではない。**

| 答え方 | 何をするか | どこまで効くか |
|---|---|---|
| **根拠を直す**（段階0） | 列挙の失敗を失敗として返す | **null 畳み込みは完全に消える。** 残るのは「プロバイダが成功扱いで空を返す」場合だけ |
| 根拠の性質を落とす（判断15・証拠） | 不在を票として積む | 上記の残余を埋める |

**手動削除には前者で足り、後者は自動化（段階3）の門にする。**
ユーザーが最終確認する限り、残余リスクは §4 の許容範囲に収まる。
**この分割で着手規模が中から小〜中に戻った。**

**段階0 は SYNC-1 と独立にバグ修正でもある。** 従来の null 畳み込みは、同期途中に
`collectNotes` が**黙ってノートを取りこぼす**ことを意味し、Rediscover の母集団と
検索結果が理由なく減る。ユーザーには「そのノートが無い」としか見えない。

### 段階0 の実装（2026-08-01 完了・実機確認待ち）

`SafChildren(items, isComplete)` を返す形にし、`query()` が null なら
`SafChildren.UNREADABLE` を返す。`traverseMarkdownPaths` は失敗したフォルダの
**相対パス集合** `unreadableFolderPaths` を返し、`collectNotes` は `VaultScan` として
ノート一覧と一緒に運ぶ。**走査は中断しない** — 他の枝で見つかったノートは正しいので、
表示系はそれで動き続ける。

**実装して分かった重要な点が2つある。**

**1. 同じ穴が「重複を作る」側にも空いていた。** 発見時は「ノートが消える」問題として
捉えていたが、`findRootChildFolder` が**不在と読み取り失敗の両方を null で返していた**ため、
呼び出し側の `find(...) ?: create(...)` が**ルート列挙に失敗しただけで2つ目の
`_ReadingTraces` / `_AI補記` を作りうる**状態だった。同じことが痕跡ファイルでも起き、
索引が空になれば既存キーを未存在と判断して**同じキーのファイルを二重に作る**
（SYNC-2 が「重複作成の余地」と書いていたのは、外部同期だけでなくこの経路でもあった）。
`RootFolderLookup` を `Found` / `Absent` / `Unreadable` の3値にし、
**`Absent` のときだけ作成する**形へ変えた。

**`find(...) ?: create(...)` という書き方自体が危険の温床**なので、
探索と作成を1回の探索へまとめ、この形をコードから消した。

**2. 不完全な索引はキャッシュしない。** 痕跡フォルダの索引に `isComplete` を持たせ、
false なら新規作成を見送る（書けなかった訪問は判断10 の巻き戻しで次の契機に書き直される）。
ただし**不完全な索引をキャッシュすると、一度読み損ねただけでVault切替まで
新規作成が止まり続ける**ので、完全なときだけキャッシュして次回読み直させる。

**`EXTRA_LOADING` は今回の範囲に入れていない。** プロバイダの実挙動を検証できないまま
分岐を足すと段階0 の完了判定が曖昧になるため、段階3 のシャドーで実態を観測してから判断する。

**変異検証:** `if (!children.isComplete) unreadable.add(path)` の1行を外すと
**5件のテストが落ちる**ことを確認済み。

### 段階1 の実装（2026-08-01 完了）

`ReadingTracePersistence` に2つ足した。

| API | 役割 |
|---|---|
| `listKeys(vaultKey): ReadingTraceKeyListing` | 保存済み痕跡のキーを**毎回読み直して**列挙する |
| `loadByKey(key, vaultKey)` | キーだけを手掛かりに読む |

**孤児の特定にファイル読み込みは要らない。** キーが `sha256Hex(相対パス)` なので、
Vault走査で得たノートのパスをハッシュして集合差を取れば孤児キーが出る。
**N件のサイドカーを開く必要がない**のが効く（遠いプロバイダでは読み込み回数がそのまま体感になる）。
`loadByKey` が要るのは、孤児と分かった**少数**について画面に出す名前を得るときだけ
— 孤児はパスが分からない（ハッシュは不可逆）ので `load` の相対パス指定では引けない。

**`ReadingTraceKeyListing` は `Available(keys)` と `Unavailable(reason)` に分けた。**
ここを `Set<String>` 1本にすると、列挙失敗が空集合として返り
**全痕跡が孤児に見える**。段階0 と同じ誤りを、今度は型で書けなくしてある。

**列挙は索引キャッシュを経由しない。** キャッシュ経由だと外部同期で後から増えたファイルを
見落とす（→ SYNC-2）。掃除は「1回だけ実行される重い操作」なので鮮度をコストより優先してよい。
**逆にフォルダの作成はしない** — 置き場が無ければ痕跡ゼロが正しい答えで、
列挙の副作用で空フォルダができるのは筋が悪い。新鮮で完全な一覧が取れたときだけ
索引キャッシュも更新するので、**掃除の下見をした瞬間だけ SYNC-2 の陳腐化が解消する**（副次効果）。

`load` は `loadByKey` へ委譲したうえで**相対パスの完全一致を追加で確認する**。
`loadByKey` はパスを知らないのでハッシュ一致までしか見られず、
委譲だけにすると既存の検証が弱くなる。

**変異検証:** 列挙失敗を `Available(emptySet())` へ畳むと**2件のテストが落ちる**ことを確認済み。

**段階1 に実機確認は要らない。** UIから到達する経路がまだ無く、既存の動作を変えていない
（`load` の委譲だけが既存経路で、完全一致の検証は維持している）。

### 段階2 の実装（2026-08-01 完了）

`domain/ReadingTraceOrphans.kt` に純関数 `assessReadingTraceOrphans` を置いた。

**設計時に見落としていたことが1つある — 遮断器はパスを要求するが、孤児はキーしか持たない。**
フォルダ単位の判定も「不完全な走査のサブツリー」判定も候補の**相対パス**が要り、
それは痕跡ファイルを読まないと分からない（キーはハッシュで不可逆）。
**急増ガードを resolve より前に置くことで解決した** — 候補が多すぎる時点で判定ごと見送るので、
「Vaultが丸ごと見えない」状況で全ファイルを読みにいくことがない。
**安全ガードがコスト上限を兼ねている。**

| 遮断器 | 効き方 |
|---|---|
| ルート列挙の失敗 | `Blocked(VAULT_ROOT_UNREADABLE)`。全ノートが不在に見えるので数える意味がない |
| 候補の急増 | `Blocked(TOO_MANY_CANDIDATES)`。**resolve の前に判定**するのでコスト上限を兼ねる |
| 不完全な走査のサブツリー | そのフォルダの候補だけ `UNREADABLE_FOLDER` で保留（**他の枝は通す**） |
| 同じフォルダから複数件 | `FOLDER_WIDE_ABSENCE` で保留。故障の粒度と一致させた本体 |
| 中身を読めない候補 | `UNRESOLVABLE` で保留。**何を消すか確認できないものは消さない** |

**`Blocked` を空の `Assessed` で代用しない。** 「判定できなかった」を「孤児は無かった」と
同じ形で返すと、段階0・段階1 で型に固定してきた区別がここで崩れる。

**前方一致は区切りを足して比較する。** 素の `startsWith` だと `ideas2` が `ideas` の
配下と見なされ、無関係なフォルダの候補まで保留になる。

**代償を設計として明記した — フォルダごと削除した場合の痕跡は掃除されない。**
「同じフォルダから複数件が欠けた」は列挙失敗と区別できないため保留になる。
この機能が狙うのは**日常的に発生する単発の孤児**のほうで、一括削除の後始末ではない。

**変異検証: 6箇所すべてで落ちるテストがあることを確認した。**
①フォルダ一括ガード（2件）②不完全走査ガード（3件）③ルート不読ガード（1件）
④急増ガードを resolve の後ろへ回す（2件・**ファイルを読まないことの検証を含む**）
⑤読めない候補の保留（2件）⑥区切り無しの `startsWith`（2件）。

**既存機能は壊さない。** Rediscover・さがす・関連ノートは**不完全でも見つかった分で動き続ける**
（今より悪くならない）。完全性フラグを見るのは掃除だけ。**ここを混ぜると、
同期が遅いVaultでランダム表示が止まるという別の不具合を作る。**

### 規模の現実

SYNC-1 は「台帳の中で一番着手が軽い」という理由で選ばれたが、
**この段階案まで含めると複数フェーズの中規模作業になる**。
段階1だけでも証拠索引・走査への相乗り・Vault分離・シャドー記録が要る。
**軽い課題ではなくなったことを承知の上で選ぶ**（判断13 の全リセットだけなら軽いままである）。

### 着手の契機（この節は設計であって計画ではない）

> **2026-08-01 追記:** **段階0〜4（手動削除まで）は着手が決まった**（オーナー判断・順序は
> `_wip/roadmap.md` N-1 が持つ）。以下の歯止めが掛かり続けるのは**段階5（限定自動化）だけ**である。
> 訂正2 のとおり手動削除は証拠索引を必要としないため、規模の見積もりも小〜中へ下がっている。

**着手の契機は実測であって、段階案が存在することではない。**
書いてあることは「やる」を意味しない。自動化へ進む条件は、
**PERF-1 の列挙コストが実機で体感できたとき**、または
**孤児が実運用で目に見えて溜まったとき**である。

**この歯止めを置く理由は、自動化が回収する価値が思ったより小さいから。**
当初この課題は「ファイル数が増えると重い」を根拠にしていたが、
判断14 でそれは**削除しなくても索引分割で解ける**ことが分かった（PERF-1）。
結果として自動削除に残る価値は「ユーザーが何もしなくて済む」だけになり、
**遮断器を4つ積んで取りに行くほどの価値かどうかは、実測が出るまで判断できない。**

したがって現時点の実質的な到達点は**判断13 の全リセット1本**でよく、
段階2で止めても設計として破綻しない。**段階3は目標ではなく選択肢である。**

> 同じ形の歯止めを MAINT-1（依存更新）でも使っている —
> 「着手の契機は新版が出たことではなく、新機能を実際に使いたくなったとき」。
> **選択肢を書き切ってから着手条件で止める**のは、調べ直しの費用を先に払って
> 判断だけ保留する形であり、優先度を下げて放置するのとは違う。
