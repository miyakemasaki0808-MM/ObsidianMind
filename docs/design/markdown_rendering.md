# 設計思想 — Markdown解析（準拠先・リスト構造）

**対象領域:** `domain/markdown/`（ブロック解析・LLM入力への再構成）と `ui/markdown/`（描画）
**初版:** 2026-08-02（FEAT-1 のMarkdown部分）
**状態:** リストの入れ子・番号・タスク混在は実装済み・実機確認済み（2026-08-02）。クリック可能リンク・画像・埋め込み・数式は未着手

---

## 1. 前提 — このパーサはどの規格にも準拠していない

**まずここを明示する。** 本アプリのMarkdownパーサは CommonMark にも Obsidian にも準拠しておらず、
**準拠を目標にもしていない。** 個別の記法を必要になった順に足してきた結果であり、
段落の遅延継続・ネストした引用・setext見出しなどは今も未対応である。

準拠しないことを選んだ理由は2つある。

1. **必要なのは「読めること」であって規格適合ではない。** 本アプリはVaultビューアであり編集器ではない。
   ノートは Obsidian 側で書かれ、ここでは読むだけなので、規格の隅を実装しても回収できる価値が小さい。
2. **同じパーサがAI入力にも使われる。** 表示だけなら多少崩れても読み手が補完できるが、
   AI入力では欠落がそのまま品質に効く（→ §4）。**規格適合より「意味を落とさないこと」を優先する。**

**したがって個別の判断は「規格がどう言っているか」ではなく「意味が落ちるか」で決める。**
以下の判断はすべてこの基準に沿っている。

## 2. 判断1 — リスト項目は1つの型に、属性として持つ

2026-08-02 まで `MarkdownBlock.ListBlock` は `items: List<String>` の単一型で、
パース時に行頭の `^\s*` とマーカーを捨てていた。結果として
**①入れ子段数 ②番号 ③箇条書きか番号付きかの種別** の3つが同時に落ちていた。

```kotlin
data class ListItem(
    val depth: Int,
    val marker: ListMarker,   // Bullet | Ordered(number: String, delimiter: Char)
    val text: String,
    val checked: Boolean? = null
)
```

**タスクを専用ブロックにしない。** 旧構造は `TaskListBlock` を別に持ち、`TaskListRegex` が
通常リストより先にマッチしていた。段数を持たせた瞬間、これが実害になる —
`- 親` / `  - [ ] 子` の混在で入れ子が2ブロックへまたがり、**段数の追跡がブロック境界で切れる。**
チェック状態は項目の属性であって、ブロックの種類ではない。

**`1. [ ]` は受理しない。** 型としては `Ordered` + `checked` を表現できてしまうが、
**型の表現力が広がったことを仕様拡大の理由にはしない。** 受理するなら、それは別途
「そう書かれたノートが実在する」という理由で決めることになる。

## 3. 判断2 — 原文尊重を非対称に適用する

| 要素 | 扱い | 理由 |
|---|---|---|
| 番号（`1.` / `1)` / `01.`） | **原文のまま保持** | 番号は書き手が込めた意味を持つ |
| 箇条書き記号（`-` / `*` / `+`） | `-` へ正規化 | 記号の違いは意味を持たない |
| インデントの列幅 | 段数だけ保持 | 幅の絶対値に意味はない（→ §4） |

**`number` を `Int` ではなく `String` で持つ。** `Int` にすると区切り記号（`.` と `)`）と
先頭ゼロ（`01.`）を失い、桁数によっては変換自体が失敗する。「原文をそのまま保持する」と決めながら
`Int` に落とすのは自己矛盾で、**型が判断を裏切らないようにする**のが `String` を選ぶ理由である。

**描画は原文の番号をそのまま出し、自動採番しない。** Markdownの慣習で `1. 1. 1.` と書く人がいるが、
自動採番すると**表示が原文と食い違う。** 編集器なら採番が親切だが、ビューアでは
「ファイルに書いてあるものが見える」ことが優先される。

箇条書き記号を正規化する側にも理由がある。`*` を書き戻しで復元すると、
インライン強調（`*italic*`）やAIプロンプトの箇条書きと紛らわしくなる。

## 4. 判断3 — 段数は列位置ではなく相対的な深浅で決める

**CommonMark にも Obsidian にも準拠しない、意図的に寛容な規則を採る。**
CommonMark は入れ子を「親のマーカー直後の列位置」で定義するため、`- 親` の子は
3列目以降でなければ子と認められない。この定義を採ると、**インデント幅が 2/4スペースで揺れる
実際のVault（複数のツールやプラグインを経たノート）を取りこぼす。**

規則は5つで、`ListDepthTracker` が段ごとのインデント列幅をスタックで保持する。

1. 同じ幅は同じ段数
2. 直前より深ければ、幅の差に関係なく段数 +1（`  ` でも `        ` でも1段）
3. 既知の祖先幅へ戻れば、その段数
4. 未知の浅い幅は「直近の浅い祖先 +1」へ正規化する
5. ある枝を抜けたら、その枝の幅は忘れる（別の枝で同じ幅が違う段数になり得る）

規則4がこの設計の要点である。次のような入力は規格上は不正だが、実際のノートには現れる。

```markdown
- 親
    - 子
  - 幅の異なる兄弟   ← 4はpop済み、2はどの祖先幅とも一致しない
```

**捨てず・例外にせず、直近の祖先の1段下へ寄せる。** 読み手にとって「親より深い」という
情報だけは確かであり、それは保存できる。規則5があるので、別の枝で同じ幅が
以前と違う段数になっても矛盾しない。

**タブは4文字加算ではなく、次の4列境界まで展開する。** `"  \t"` は 2 → 4 列であって
2+4=6 ではない。単純置換にすると、スペースとタブが混在した行だけ段数がずれる。

**書き戻しでは元の列幅を復元しない**（1段 = 2スペース固定）。段数までしか保持していないうえ、
幅の絶対値には意味がないためである。往復（`parse → blocksToMarkdown → parse`）で
**型が同値に戻る**ことをテストで固定してある。

## 5. なぜ「表示の問題」ではなくAI入力の問題だったか

この変更の起点は表示の崩れではなく、**同じパーサが `buildNoteExcerpt` を通じて
AI入力にも使われている**ことだった（→ [ai_input_excerpt](ai_input_excerpt.md)）。
番号が `- ` へ潰れると、手順書のように**順序自体が意味を持つノートで、
その意味がモデルへ届かない。**

[ai_input_excerpt](ai_input_excerpt.md) §6 は「正規化の副作用は仕様として引き受ける」と決めているが、
**この1件はその範囲を超えていた。** 他の副作用（frontmatter除去・改行の畳み込み・
コードフェンス言語名）はいずれも**冗長な情報**を落とすのに対し、番号の消失だけが
**本文の意味**を落としていた。

> **副作用を引き受けるかどうかは、損失の大小ではなく種類で決める。**
> 「表記の揺れ」なら引き受けてよく、「書き手が込めた意味」なら引き受けてはいけない。

**ただし品質が上がると期待しすぎない。** [ai_input_excerpt](ai_input_excerpt.md) §14 は
「予算を減らしても増やしても品質が動かなかった」と記録している。今回効くのは
**番号自体に意味があるノートに限られる**ので、効果を一般化して測ると見えない。

## 6. 描画側の扱い

- 段数は字下げ（1段16dp）だけで示し、**記号は段によって変えない**（`•` 固定）。
  入れ子の深さは字下げで十分に読めるため、記号を3種類使い分ける必要を認めなかった。
- 番号付きの表記幅（`1.` と `10.`）が異なるため本文の左端は揃わない。許容する。
- チェック状態を持つ項目だけ `Checkbox` を出し、完了項目は取り消し線と減光を掛ける（旧実装を踏襲）。
