## 解決したかった問題

Reflectの理想は「**自分の考えをもう一段深くする読書相手**」。蒸留（[reflect_distill](reflect_distill.md)）は"ノートの中身"を育てるが、**ノートをまたぐ思考の連続性**は扱えない。

このアプリの心臓は **Rediscover（ランダムに過去ノートを引く）**。しかし現状、再発見は「たまたま出てくる」だけで、そこに**意図の糸**がない。

タイムカプセルは、読み終わりに**未来の自分へ1問だけ残し**、後日 **Rediscover でそのノートが引かれた時に問いが蘇る**機能。ランダム再発見に「前回の自分からの申し送り」という意味を与え、再発見を"偶然"から"再会"へ変える。**このループを持つこのアプリでしか作れない**のが最大の狙い。

## 設計原則: シンプル最優先（v1の背骨）

**本質はノートを見ること。タイムカプセルは「あれば嬉しい」再会体験**であって、永久保存の記録装置ではない。この原則から、v1では**堅牢性の作り込みを意図的に削る**：

- カプセルが稀に1個失われても、ユーザーのノート（.md）は無傷であり、本質（ノート閲覧）は損なわれない
- したがって **.bak復旧・アトミック性の作り込み・世代アーカイブ・revision管理は不採用**（オーバーエンジニアリングを避ける）
- 残す安全策は「**壊れたものを見せない・ノートに波及させない**」の一点（checksum破損検知＋孤立化）のみ

## 判断1: 残すのは「1問」。反応は累積、問いは上書き（シンプル版で確定）

- 読み終わりに、未来の自分への**問いを1つ**残す
- **蘇り（再会）時に、その問いへ自由記述の反応を残せる**（日付付き）。反応は**累積**し、**問い→反応→反応… の思考の糸**になる
- 1ノートにつき**アクティブなカプセルは1つ**（問い＋その反応スレッド）
- **問い＝上書き / 反応＝累積**：
  - **反応の追記**では問いは変わらず、反応スレッドに積み増す
  - **新しい問いを残す**と、前の問い＋その反応スレッドは**破棄**され、新しい問いに置換される（**旧スレッドの保持・複数世代管理はv2**）

## 判断2: AIは「叩き台を1つ」だけ、オンデマンドで提案

- 白紙から書いてもよい。「AIに叩き台をもらう」タップで**AIが問いを1つ提案**
- **入力欄が空の時だけ生成**し、**ユーザーが書いた文章は上書きしない**。入力には**タイトル＋本文先頭＋本文末尾**を使う
- **自動では呼ばない・自動ダウンロードしない**（`AICoreClient.generate()` は Mutex 直列＋数十秒。読み終わるたびに強制発火させない）
- 生成は短い1回のみ。**失敗/タイムアウト時も入力内容を維持**し、**Snackbarではなく入力欄付近に短いインライン説明**を出して手入力へ戻す（完全な無反応にはしない）
- 蒸留（生成しない）と違い、**生成的AIの正当な使いどころ**。主役はユーザーの問いで、AIは種を出すだけ

## 判断3: 保存は vault内の可視フォルダにサイドカー（本文は編集しない）

- カプセルはノート本文(.md)に埋め込まず**別ファイル**に持つ（frontmatter埋め込み＝本文編集の truncate窓リスクを避ける）
- 置き場所は **vault内の `_TimeCapsules/` フォルダ**（アンダースコア始まりの可視フォルダ）。**選択した同期サービスが `_TimeCapsules/` を同期対象にしている場合に限り**、別端末・再インストールをまたいで生存する（同期対象外・作成不可・書込不可の場合は説明付きの無効状態にする）
  - **なぜ隠しフォルダ（`.`始まり）を避けるか**：SAF（Storage Access Framework）では、プロバイダ（Google Drive・OneDrive・一部ローカルファイラー）によって `.` 始まりの隠しフォルダ／ファイルの**作成が失敗したり不可視化の挙動が異なる**。可搬性・確実性を優先し、`_AI補記` と同じくアンダースコア始まりの可視フォルダを採用する
- `_AI補記`（ユーザーが読む機能成果物・`AnnotationManagerScreen` が全削除）とは**用途が違う**ため同居させず、`_TimeCapsules/` を別に切る。**`_TimeCapsules/` は `NoteRepository` のノート収集対象から明示的に除外**する（`_AI補記` と同様。中身は .json のため .md 検索には入らないが、走査自体を避ける）
- **1カプセル=1ファイル**（`_TimeCapsules/<hash>.json`）。ファイル名はキー（後述）から導出（安全化のためハッシュ等）
- **書き込みは SAF OutputStream への `"wt"`（write-truncate）モードでの直接上書き一気書き**（[reflect_distill](reflect_distill.md) の `SafDistillDocumentGateway` と同方式）。反応追記でファイルを更新するため。
  - **これは原子更新ではない（ベストエフォート・復旧なし）**：`"wt"` はファイルを一度 truncate してから書き直すため、書込中にプロセスが死ぬと**部分破損したまま残り、復旧元は存在しない**（truncate窓）。SAF の `renameDocument()` はプロバイダ非互換で古典的な atomic-rename が成立しないため、これを許容する。**蒸留の `DistillRecoveryStore` の原子パターンは内部ストレージ（`java.io.File`）専用でSAFへは移植不可**
  - **失われるのはカプセルのみ**（ユーザーのノートには一切触れない）。設計原則どおり、堅牢化はここまで。破損は次項の checksum で検知し孤立化する
  - **端末間の同時編集は last-writer-wins**（後勝ち）。マージや世代解決はv1では行わない

## 判断4: 可搬キーは「vault相対パス＋タイトル」。documentId は端末内キャッシュ（草案から精密化）

**SAF documentId は端末／権限グラントごとに異なる**ため、同期した別端末では同じファイルでも別IDになる＝**documentId は可搬キーにならない**。判断3が「同期で生き残る」ことを狙う以上、キーは可搬でなければならない。

- **可搬キー＝vault相対パス**（例 `ideas/habit.md`）を主キーにする（同期をまたいで安定）
- **タイトル**を副キー（表示＋再マッチ）に保持
- **documentId** は端末内の高速引き当てキャッシュに留める（グラント内で安定・別端末では無効）
- 引き当て順：documentId（端末内・速い）→ vault相対パス（可搬）→ **タイトル再マッチ**（ユーザー指定のフォールバック）
- **タイトル再マッチのあいまい性**：同名ノートが複数ある時は**自動で結び付けない**（誤マッチ防止）。一意に定まる時だけ再バインドしてパス/documentId を更新。あいまい時は孤立扱い（v2で「未回答カプセル一覧」から手動解決）

### 実装要件: 相対パスの生成・キャッシュ（リポジトリ層への追加）

- 現状 `NoteRepository` のBFS走査（`collectNotesRecursive`）は各ファイルの `documentId`／`displayName` は取得するが、**ルートからの相対パス文字列は保持・構築していない**（`NoteFile` は `name`／`uri`／`lastModified` のみ）。
- タイムカプセルの主キーに相対パスを使うため、**BFS走査時に親フォルダのパスを繋ぎ合わせて相対パスを生成・キャッシュするロジックの追加が必要**。具体的にはキュー要素を「documentId＋そこまでの相対パス」の組に拡張し、子を辿る際に親パス＋子名を連結して `NoteFile` に相対パスフィールドを持たせる。

## 判断5: 蘇りは Rediscover 限定（草案から変更）

- カプセルのあるノートが **Rediscover（`loadRandomNote`）で引かれた時だけ**、本文冒頭に「前回の自分からの問い」カードを出す
- **検索・関連・直接オープンでは出さない**（"再会"感を濃くするユーザー選択）。意図の糸が濃くなる代わりに、目的を持って開いた時には出ない、という**意図的な割り切り**
- 実装上は「今回の表示が Rediscover 由来か」を state で区別し、その経路でのみカプセル照合する
  - **実装要件**：`NoteUiState.Success`（現状 `title`／`content`／`targetUri`／`originalHash`／`distillUnavailableReason` を保持）に `isFromRediscover: Boolean` を追加する。`NoteViewModel.loadRandomNote()` の成功時のみ `true`、`openNote()`（検索・関連・直接オープン経路）では `false` にリセットする。カプセル照合は `isFromRediscover == true` のときだけ実行する
  - 回転・プロセス復元をまたいでの誤判定を避けるため、このフラグは復元される state に含める（`loadRandomNote` を経ずに復元された表示で誤ってカードが出ないこと）
- **残す**のは Reflect（AIタブ）の「タイムカプセルを残す」アクション

## 判断6: 通知はカードのみ

Rediscover で蘇った時は**本文冒頭のカード表示のみ**（Snackbar等は出さない）。カードは dismissible（「読んだ」で畳む／「反応を残す」／「新しい問いに置換」）。

## 仕様詳細（v1）

### データモデル（最小スキーマ・JSON）
シンプル原則に沿い、世代アーカイブ・revision 等は持たない**単一アクティブ世代のみ**の最小構成。

```
TimeCapsule(
  schemaVersion: Int,          // 将来のフォーマット変更に備える
  vaultRelativePath: String,   // 可搬・主キー
  noteTitle: String,           // 副キー（再マッチ）＋表示
  documentId: String?,         // 端末内キャッシュ（可搬でない）
  question: String,            // ユーザーの問い（AIは叩き台のみ）
  responses: List<Response>,   // 再会時の自由記述（日付付き・累積）
  createdAt: Long,
  sourceContentHash: String?,  // 参考: 残した時点の本文（キーには使わない）
  checksum: String             // checksum欄を除いた canonical payload に対して計算
)
Response(text: String, createdAt: Long)
```

**厳格検証（読込時）**：必須項目・型・上限（下記）・未知の `schemaVersion` を検証。checksum不一致・パース失敗・空ファイルは**破損＝孤立扱い**（カードを出さず、ノートには触れない）。

**上限（バイト基準で検証。日本語はUTF-8で1文字≒3バイトのため文字数上限とは別にバイト予算を持つ）**：
- 問い：**200字**
- 反応1件：**1000字**
- スレッドの反応：**最大30件**（超過時は追記を拒否）
- カード表示は**最新3件**、それ以前は「過去の反応を見る」で展開
- ※アーカイブ世代を持たない設計のため、ファイルサイズは上記上限で自然に有界（総サイズ上限の別途管理は不要）

### フロー
1. **残す**：Reflectで「タイムカプセルを残す」→ 問いを入力（任意でAI叩き台1回）→ サイドカーへ保存（`"wt"` 一気書き）。**同一ノートの既存カプセルは破棄して置換**（旧反応スレッドも破棄）
2. **蘇る**：Rediscover でノートが引かれる → 可搬キーで照合（判断4の順）→ ヒットなら冒頭カードに問い＋過去の反応（最新3件）を提示
3. **反応する**：カードから自由記述で反応を追記（日付付き・累積）→ サイドカーを `"wt"` で更新
4. カード操作：「読んだ」で畳む（現在のRediscover表示中だけ・**次回Rediscover時は再表示**）／「新しい問いに置換」

### AI設計
`AICoreClient` を流用。**オンデマンド1回のみ**の叩き台生成。入力欄が空の時だけ生成しユーザーの入力は上書きしない。失敗/タイムアウト時は入力を保持し、**入力欄付近に短いインライン説明**を出して手入力へ戻す（判断2参照）。

### サイドカー書き込みの安全性（ベストエフォート・原子性なし）
反応追記・置換で更新が発生するため、**SAF OutputStream への `"wt"`（write-truncate）直接上書き**で更新する（[reflect_distill](reflect_distill.md) の `SafDistillDocumentGateway` と同方式）。**これは原子更新ではない**：`"wt"` は truncate 後に書き直すため書込中クラッシュで部分破損が残り、復旧元はない（truncate窓）。SAF の `renameDocument()` はプロバイダ非互換で atomic-rename が成立せず、`DistillRecoveryStore` の原子パターンは内部ストレージ専用でSAFへ移植不可。**設計原則どおり堅牢化はここまで**とし、破損は checksum で検知して当該カプセルを孤立扱いにする（ユーザーのノートには一切触れない）。端末間同時編集は last-writer-wins。

## オープン論点（v1向け・確定 — レビュー＋シンプル方針で決着）
1. **サイドカーのファイル形式**：**JSON採用**。閲覧履歴（`NoteHistoryStore`）で既にAndroid標準の `org.json` を導入済みで追加ライブラリ不要。Obsidianの「データはポータブルで読めるべき」思想にも合致し、ユーザー自身がテキストエディタで確認・修復できる
2. **タイトル再マッチのあいまい解決UI**：**v1はUIなし（サイレント孤立扱い）**。複数ヒット時に誤バインドするリスクを避け、一意に定まらない場合は「カプセルなし」として冒頭カードを出さない。手動解決の一覧はv2へ
3. **反応スレッドの上限**：**問い200字／反応1件1000字／スレッド反応30件／カード表示は最新3件**（データモデル参照）。将来この反応スレッドをAIプロンプトのコンテキストに含める場合の入力文字数上限への防御も兼ねる
4. **置換時の旧スレッド**：**v1は完全破棄（上書き）**。世代アーカイブのデータ構造・複数世代の閲覧UIはいずれもv2（シンプル原則により、v1ではデータ構造も持たない）

## スコープ外（v2以降）
- 複数世代の履歴（問いの世代管理）
- 「未回答カプセル一覧」ビュー（Vault横断で"考えかけ"と孤立カプセルを俯瞰・手動解決）
- 蒸留（案A「読み直す観点」）との連携
- 反応の思考差分テンプレ（今も同意/変わった/新しい気づき＝Codex案2）

## レビュー観点（レビュー用）
1. **可搬キー設計**：vault相対パスを主キー・documentIdをキャッシュ・タイトル再マッチという三段が、同期・rename・move で破綻しないか
2. **Rediscover限定の判定**：「今回の表示が Rediscover 由来か」を state で確実に区別できるか（回転・プロセス復元をまたいでの誤判定はないか）
3. **サイドカー書き込み（ベストエフォート）**：`"wt"` 直接上書きで truncate窓を許容し、破損は checksum 検知→孤立化でノートに波及させない、という割り切りが妥当か
4. **反応スレッドのスコープ**：自由記述をv1に入れたことで肥大化しないか（上限200/1000/30・カード3件・置換で破棄）
5. **AIオンデマンド1回**：負荷・失敗時のインライン説明フォールバック・空欄時のみ生成
6. **タイトル再マッチのあいまい性**：同名ノート時に誤バインドを避けられるか

## 受け入れテスト観点（v1）
- ネストしたノートの vault相対パス生成（BFSで親パス連結）
- 同名ノートが一意／複数の場合の再マッチ（一意時のみ再バインド・複数時は孤立）
- move・rename 後の documentId／パス／タイトル再バインド
- Rediscover と 検索・関連・履歴の由来判定（`isFromRediscover`）
- 回転後もカードが維持されること／プロセス再起動後に古い Rediscover 由来が復元されないこと
- JSON の必須項目・型・上限（**UTF-8マルチバイト境界で200字/1000字**）・未知 `schemaVersion`
- checksum不一致・途中書き込み（truncate窓）・空ファイル → 孤立化しノートに触れない
- 反応30件上限で追記拒否
- 置換時に旧スレッドが破棄されること
- 「読んだ」が次回 Rediscover で再表示されること
- AIが入力済み文章を上書きしないこと／AI失敗後も手入力・保存できること
- `_TimeCapsules/` がノート収集候補へ混入しないこと
