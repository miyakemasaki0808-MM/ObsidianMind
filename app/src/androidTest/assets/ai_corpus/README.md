# 固定コーパス（要約の品質を測るための架空Vault）

**これはテスト入力であって、ユーザーのノートではない。** 実Vaultの分布に似せる必要はなく、
**壊れ方の違う入力を揃えること**だけが条件である（→ `docs/dev/system/ai_quality_measurement.md`）。

架空の個人ノートとして書いてあり、このアプリ自身の話は書かない
— 題材が開発の話だと、要約の良し悪しと設計の正しさを読み手が混同する。

## 何を再現するためのノートか

| ファイル | 文字数 | 再現する壊れ方 |
|---|--:|---|
| `0100_constraints_heavy.md` | 676 | **但し書きと例外が本体**。「ただし」「例外は」「採用しない」を落とすと意味が反転する |
| `0200_long_nested.md` | 2,290 | **抜粋予算（1,200字）を超える長文＋深い見出し**。中盤が落ち、終盤は骨格と末尾からしか見えない |
| `0300_bullet_list.md` | 376 | **地の文がほぼ無い箇条書き**。要約する対象が文ではなく一覧 |
| `0400_tiny_memo.md` | 82 | **短すぎるメモ**。抜粋も要約も効かない下限 |
| `0500_code_fence.md` | 587 | **コードフェンスが本文の大半**。コードを落とすと手順が消え、拾うと要約がコードになる |
| `0600_frontmatter_table.md` | 603 | **frontmatter と表が判断を持つ**。表を落とすと結論の根拠が消える |
| `0700_no_heading.md` | 441 | **見出しが1つも無い**。セクション分割が縮退する |
| `0800_tail_conclusion.md` | 1,309 | **結論が末尾にある**。冒頭だけ読む切り出し方が最も損をする形 |
| `0900_middle_key.md` | 2,454 | **決め手が中盤にある**。冒頭＋末尾を残す切り出し方が損をする形。抜粋予算の2倍も超える |

## 触るときの約束

- **ノート本文に「これはテストです」と書かない。** 本番のプロンプトへそのまま入る入力なので、
  足場の文字列が混ざると測っているものが変わる
- **ファイル名はASCIIにする。** assets の非ASCIIファイル名が `AssetManager` を通って
  そのまま返るかは端末で確かめるまで分からず、**外して確かめられるなら外す**（実機セッションは高い）。
  ノートらしい日本語のタイトルは本文の `#` 見出しが持ち、実機の基準線はそこからタイトルを採る。
  `0700_no_heading.md` だけは見出しが無いので、**タイトルにファイル名が入る**（ノートらしくない唯一の1本）
- 文字数を変えたら上の表も直す。**長さそのものに意味がある3本**に注意する —
  `0200_long_nested.md` と `0800_tail_conclusion.md` は抜粋予算（1,200字）を超えていること、
  `0900_middle_key.md` は**その2倍（2,400字）も超えている**ことが条件である
  （超えていないと、抜粋の作り方を変えた変種どうしが同じ入力になり、比較が成立しない）
- 参照要約（良い要約／わざと落とした要約）は `references/` にある。**本文を変えたら参照も作り直す**
- **実機の Nano が返した要約**は `references/nano/` に分けて置き、文ごとに忠実さのラベルを付けてある。
  人が書いた参照とは混ぜない。**本文を変えたら、その要約は古い入力に対する出力になる**ので取り直す
