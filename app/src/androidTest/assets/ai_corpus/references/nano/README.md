# 実機の Nano が返した要約（ラベル付き）

**これは人が書いた参照要約ではない。** 2026-09-13 に実機で `SummaryCoverageBaselineTest` が
本番のプロンプトから生成させた要約を、そのまま取り込んだものである。
隣の `../*.good.txt` / `../*.fabricated.txt`（人が書いた参照）とは**混ぜない**。

置いた理由は、人が書いた参照だけで決めた閾値が**実機の出力には移らなかった**ためである。
人が書くと原文の語を使い回すので、忠実な文の裏付けが高く出る。Nano は言い換えるので低く出る。
較正の材料に実物を加えるため、文ごとに忠実さのラベルを付けた。

## 生成の条件

| | |
|---|---|
| 日付 | 2026-09-13 |
| 端末 | Pixel 10 Pro Fold / Android 17 |
| APK | 製品 SHA-256 先頭 `3564909d`、test `a5bec0b6` |
| SDK | `com.google.mlkit:genai-prompt:1.0.0-beta2` |
| 生成パラメータ | 未指定＝既定値。**`temperature=0`・`seed=0`・`topK=3`・`maxOutputTokens=256`**（`GenerateContentRequest.Builder.build()` を逆アセンブルして確認） |
| プロンプト | 本番の `PromptBuilder.buildSummarizePrompt`。抜粋は `SUMMARY_EXCERPT_VARIANTS` の各変種 |
| AICore のモデル版 | **未記録** |

**生成は決定的である。** 既定値が温度0・seed 0であり、実機でも同じプロンプトになる組
（`0100` と `0300` の本番と旧方式）はバイト単位で同じ要約を返した。
**したがって同じプロンプトを繰り返しても揺らぎは測れない。** 出力が変わるのは、入力が変わったときか
モデル版が変わったときである。

## 何があって何が無いか

9本 × 3変種の27組のうち、12回生成したところで13回目が AICore の `ErrorCode 9 / BUSY` で止まった。

| 変種 | 置いたファイル | 状況 |
|---|---|---|
| 本番（`production`） | 9本すべて | 取得済み |
| 冒頭のみ・旧方式（`head_only`） | `0200` だけ | `0100`・`0300` は本番とバイト単位で同一なので写しを置かない。`0400`〜`0900` は未取得（`0400` で BUSY） |
| 本番・予算2倍 | なし | 未取得 |

**別々の要約は10本・38文**である。

## 取り込み方

- **logcat から復元した。** 1行ごとの行頭4空白を外し、行を改行で繋ぎ直した。ファイル末尾に改行を1つ足した。
  logcat は行末の空白を保存しないので、**行末の空白までは保証しない**
- テストは応答の先頭6行だけを出力する設定だったが、6行に達した応答は無かった（切れていない）
- **取り込んだ本文を、取り込み時点の採点器へ掛け直すと、実機の logcat の値（文数・裏付けの最小と平均・被覆）と10件すべてで一致した。**
  実機で採点されたものと同じ本文である。**その後に採点器の誤判定を直したので、今の採点器では値が変わる**
  （文の割り方は変えていないので、`labels.tsv` の `index` の対応は保たれる。`SummaryCoverageCalibrationTest` が固定している）

## `labels.tsv`

| 列 | 中身 |
|---|---|
| `note` / `variant` | どの出力か。ファイル名は `<note>.<variant>.txt` |
| `index` | 1始まり。**採点器（`measureSummaryCoverage`）の `sentences` と同じ順序** |
| `label` | 下の4値 |
| `kind` | 判定の種類（転記・言い換え・解釈・改変・反転・捏造・見出しの漏れ） |
| `sentence` | 応答の文。**Markdown記法は落としていない** |
| `evidence` | 原文の該当箇所の引用と、判定の理由 |

**文の割り方は採点器と同じ規則**（行ごと、括弧の内側では切らない、終止符は `。！？!?`）。
ただし採点器はインラインコードと記法を落としてから比べるので、**`sentence` の文字列は採点器の文と一致しないことがある**
（例: `0500` の3文目は採点器側で `rsync` と `--delete` が消える）。**照合は文字列ではなく `index` で行う。**

### ラベルの基準

| label | 基準 |
|---|---|
| `faithful` | 文の主張がすべて原文で支えられる。言い換え・一般化・原文から導ける総括は含めてよい |
| `partial` | 支えられる主張と、原文に無い／反する主張が1文に混ざっている |
| `unfaithful` | 文の中心の主張が原文に反する、または原文に無い |
| `not_a_claim` | 主張ではない（見出しが要約へ混入した等） |

**網羅していないことは忠実さの問題として数えない。** `0900` 本番の4文目は試算の結果に触れていないが、
書いてあることに誤りは無いので `faithful` とし、欠落は理由欄に書いた。それは被覆の側で測る。

| label | 件数 |
|---|--:|
| `faithful` | 28 |
| `partial` | 6 |
| `unfaithful` | 3 |
| `not_a_claim` | 1 |

## まだ確定していないこと

**ラベルは1人の判断である**（Claude、2026-09-13）。**別の目（Codex の机上レビュー）を通すまで確定しない。**
境界で迷ったのは次の3件で、読み手によって変わりうる。

- `0300` 本番3文目「再読したい本もいくつかある」— 原文は1冊。数量の誤りとして `partial` にした
- `0700` 本番4文目「作業風景の中で笑っている写真」— 原文は「作業の合間に座って」。写真の要点が逆の像になるので `partial` にした
- `0800` 本番2文目「快適な通勤とは言えませんでした」— 原文に無い総括だが、各月の記述から導けるので `faithful` にした

## 触るときの約束

- **`*.txt` を手で直さない。** 実機の出力そのものである
- 取り直したら、**古い出力と混ぜずに置き換え、ラベルも付け直す。** モデル版が変われば同じプロンプトでも出力が変わる
- 取り直すときは、この表にモデル版も書く
