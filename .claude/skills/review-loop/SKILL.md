# レビューの往復

仕組みと止まる条件の正本は [harness/README.md](../../../docs/dev/harness/README.md) §3。ここは順序だけを持つ。

**前提:** 変更はすべてコミットしてあり、`.claude/gate/gate.sh` を通している。前のレビュー本文は受付を済ませて消してある。

1. **シリーズの名前と範囲を決める。** 名前は英小文字・数字・`-`（例 `search-fixes`）。範囲は `<往復を始める前の HEAD>..HEAD` で、往復の間は基準を動かさない
2. **観点のファイルを scratchpad に書く。** 差分の範囲、特に見てほしい観点を3〜6項目（ファイル名と、疑っている失敗の形）、
   開発中に自分で確かめたこと（判定ではないと明記）、手を付けていない範囲。合否の期待は書かない
3. `.claude/review/codex_review.sh <シリーズ> <範囲> <観点のファイル>` を**背景で**流す。数分から十数分かかる
4. 置かれた本文を Skill `review-intake` で受け付ける
5. スクリプトの最後の行に従う
   - **P1・P2 が0件:** 往復を終えて 7 へ
   - **P1・P2 が残り、回数も残っている:** 指摘を1件1コミットで直す。修正前に落ちるテストを先に書き、ゲートを通す。3 へ戻る
   - **上限の回で残った:** 直さずに 7 へ
6. **次のどれかに当たったら、回数が残っていても止めて 7 へ。** 同じ指摘が2回続けて「未解消」か「部分解消」と判定された。
   Codex が追跡しているファイルを変えた（終了コード 5）。Codex が2回続けて失敗した（トークン切れなど）。
   指摘がオーナーの判断を要する（正本と実装のどちらに寄せるか、見た目や体験の好み）
7. **オーナーへ渡す。** シリーズ名、回数、各回の P1〜P3 の件数、かかった時間とトークン（`.git/vigilith-review/log.tsv`）、
   残った指摘とその受付、止めた理由。往復が終わっても「確定」とは書かない — 完了の線はオーナーが引く

P3 は直してよいが、P3 だけのために次の回を頼まない。
